# 仕様整理

## ほぼ確定でよい方針

### 1. いきなり削除しない

Cloud Functions は remote 側とのズレや旧運用依存が起きやすいため、まず分類してから削除する方が安全です。

### 2. `index.ts` を live の基準にする

現行エントリーポイントから export されているかどうかは、少なくとも「今のソース構成上の live 判定」として強い基準になります。

### 3. legacy は退避場所を明示して残すのはあり

`unused_function_lib` のような置き場は、きちんと説明できるなら悪くありません。  
問題は、置いてある理由がわからない状態です。

## ユーザー判断が必要な仕様

### 1. 削除ポリシー

選択肢:

1. 一定期間 parked のまま残す
2. 理由が確認できたら順次削除する
3. `legacy/` へ移してしばらく凍結する

おすすめは 3 です。  
削除より安全で、用途も明示しやすいためです。

### 2. docs での表現

選択肢:

1. live docs からは完全に消す
2. legacy 一覧として別紙で残す

おすすめは 2 です。  
後から「あれはどこへ行ったか」を辿りやすくなります。
