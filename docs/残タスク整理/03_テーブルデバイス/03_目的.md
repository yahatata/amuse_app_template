## 1. この実装で何を作るか

`tableDevice` を、**店舗従業員（ディーラー）が卓運用のために使う専用端末機能**として実装する。

今回の実装対象は、単一画面の追加ではなく次の一式である。

1. `role: table` の追加
2. `devices.optionParams.table_device_table.tableId` を使った卓紐付け
3. `tables/{tableId}` を単一参照先とする卓状態管理
4. `tournamentDetail` を使ったトーナメント復帰情報の保持
5. `storeMeta/config` を使った卓デバイス設定管理
6. 卓専用 Home / Drawer / 詳細画面
7. 卓デバイス専用 callable 群
8. 既存 tournament / sideGame 実装の整合修正

---

## 2. なぜ今やるか

現状のコードベースには、`terminal + option` による暫定的な卓向け導線が存在するが、専用 role としては未実装である。  
そのため、以下の問題が残っている。

- 卓専用端末として閉じた導線になっていない
- `tables.status` / `sideGame` / `tablesSeat` の扱いが一貫していない
- トーナメント登録中の卓を `tables/{tableId}` だけで判定できない
- 卓端末向け機能の有効化設定が実装上つながっていない
- 実装が `terminal` 導線と混在しており、今後の保守が難しい

`tobe_spec` は既に正本として確定させたため、ここからは仕様議論ではなく、**安全に実装へ落とし込む段階**に入る。

---

## 3. 今回の実装スコープ

### 3.1 含むもの

- Flutter 側の `table` role 対応
- device 登録・device 管理での `table` 端末対応
- `tables.tournamentDetail` の導入
- `tablesSeat.isEnabled` の論理削除対応
- `tableDevice.forceClearPasscode` を含む `storeMeta/config` 対応
- 卓専用 Home / Drawer / tournament / sideGame 画面
- 卓デバイス用 callable の実装
- テスト追加
- 実機確認計画の作成

### 3.2 含まないもの

- この段階では本番運用開始の判断自体は含まない
- 長期運用後の UI 改善や監視強化は別タスクで扱う
- 実装前に未定だった仕様の再議論は行わない（`tobe_spec` を正とする）

---

## 4. 完了の定義

以下をすべて満たしたら、`tableDevice` 実装タスクを完了扱いにできる。

- `role: table` が Flutter / Functions / device registration に反映されている
- `table_device_table` を使った卓紐付けができる
- `tableId` 未設定の `table` 端末に専用案内が表示される
- `tables/{tableId}` と `tournamentDetail` を使って卓 Home の遷移が決定できる
- サイドゲーム時に `tables.status` がゲーム名で運用される
- トーナメント解除が `tablesSeat.isEnabled = false` の論理削除に変わっている
- 卓専用 Home / Drawer / 詳細画面が実装されている
- 卓デバイス向け register / unregister callable が実装されている
- `storeMeta/config.features.tableDeviceRegistrationEnabled` と `tableDevice.forceClearPasscode` をコードが読める
- テストが追加され、必要なコンパイル確認とテスト実行が通る
- 実機確認計画に基づく確認が完了している
