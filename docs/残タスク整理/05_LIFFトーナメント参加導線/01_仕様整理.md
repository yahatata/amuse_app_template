# 仕様整理

## ほぼ確定でよい仕様

### 1. 現行 `registerForTournament` は bill 前提の参加処理である

`activeStays` と `billId` を必須にして `recordTournamentAction` まで行くため、これは単なる興味登録ではなく、実質的に「参加 + 売上記録寄り」の処理です。

### 2. 入店前の意思表明は別フローに分けるべき

もし未入店状態でも応募させたいなら、現行の `registerForTournament` を流用するのは避けるべきです。  
予約と参加を同じデータにすると、課金と実入店の整合が崩れます。

### 3. backend 側で意図を明示した条件判定を持つべき

今は `activeStays` が無いことで結果的に失敗していますが、ドメインルールとして「入店中のみ参加可」なら、明示的にその条件を表現した方が安全です。

## ユーザー判断が必要な仕様

### 1. 未入店ユーザーに何を許すか

選択肢:

1. **許さない**  
   LIFF では一覧を見るだけ。参加は入店後のみ。
2. **予約のみ許す**  
   予約データを別管理し、入店後に正式参加へ変換する。
3. **事前参加まで許す**  
   未入店でも先に席を押さえ、必要なら事前決済も考える。

おすすめは 2 です。  
集客余地を残しつつ、会計や no-show の整合を保ちやすいためです。

### 2. no-show の扱い

選択肢:

1. 一定時刻で予約失効
2. 店舗側が手動で失効
3. 入店しなければ自動キャンセルだが、再参加制限をかける

ここは現場運用次第なので、店舗オペレーション優先で決めるのがよいです。

### 3. LIFF での表示方針

選択肢:

1. 未入店時はトーナメント一覧も隠す
2. 一覧は見せるが、参加ボタンは予約用に変える
3. 一覧も参加も見せるが、参加処理の種類を分ける

集客を考えるなら 2 がバランスが良いです。
