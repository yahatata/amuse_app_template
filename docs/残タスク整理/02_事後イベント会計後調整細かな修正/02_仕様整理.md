# 仕様整理

## ほぼ確定でよい方針

### 1. 細かな修正でビジネスルールを拡張しない

このタスクは大きな仕様追加の場ではなく、既に決めた会計後調整の current-scope を整える場として扱うのが自然です。

### 2. 「見た目の小ささ」ではなく「本番影響」で優先順位を決める

たとえば旧ラベル残りよりも、誤操作を招く導線や rules 漏れの方が優先です。  
分類基準は、作業量ではなく本番リスクに置くべきです。

## ユーザー判断が必要な仕様

### 1. どこまでを本番前必須とするか

選択肢:

1. **厳しめ運用**  
   旧導線や docs 不整合も含め、かなり整理してから出す
2. **最低限運用**  
   誤課金・誤集計・誤操作に直結するものだけ先に直す

おすすめは 2 です。  
小修正タスクで広がりすぎると、本体の判断が遅れやすいためです。

### 2. 残件の管理方法

選択肢:

1. docs 内のチェックリストで管理する
2. GitHub Issue 等へ切り出す
3. 今回の整理 docs のまま最終一覧にする

本番前後で継続的に見るなら 2 が強いですが、まずは docs で粗整理してから issue 化でも十分です。
