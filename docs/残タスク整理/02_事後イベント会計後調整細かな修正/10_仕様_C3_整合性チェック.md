# C-3 整合性チェック 仕様書

## 概要

`analyticsMonthly` および `reportingMonthly` / `reportingEntries` の整合性チェックを  
admin callable として実装し、Flutter UI からの手動起動と、スケジューラー経由の定期実行を可能にする。

バッチ処理ログ基盤（`batchJobLogs` コレクション）を本タスクで先行構築し、今後の全バッチ処理に共通利用する。

---

## analyticsMonthly と reportingMonthly の根本的な違い

この違いを理解せずにチェックを設計すると、正しい突合ができない。

### 日付基準の違い

| | analyticsMonthly | reportingMonthly |
|---|---|---|
| **settle 時の日付基準** | `businessDate`（店舗営業日） | `settledAt`（実際の会計完了 Timestamp）※デフォルト |
| **cashAction 時の基準** | `originBusinessDate` | `cashActionExecutedAt`（cashActionDate ルール）|
| **reopen 時の扱い** | 当該月から差し引き delta | 元の settle と**同じ月** に負のエントリを追加 |
| **月キー形式** | `"2026-05"`（YYYY-MM） | `"202605"`（YYYYMM、ハイフンなし） |

### 「同じ伝票が別の月に入る」ケース

```
例: 5月31日 23:50 に会計した伝票（ただし営業日は6月1日）
  → analyticsMonthly: 2026-06 に計上（businessDate = 2026-06-01）
  → reportingMonthly: 202605 に計上（settledAt = 2026-05-31T23:50）
```

**→ analyticsMonthly と reportingMonthly を同じ「月」で直接比較することは意味がない。それぞれ独立したチェックが必要。**

### 何が書き込まれるか

| イベント | analyticsMonthly | reportingMonthly |
|---|---|---|
| settle | `aggregationMarkers/{billId}_cycle{N}_settle` + 月次/日次集計更新 | `reportingEntries/{billId}_settle_{N}` + monthlyUpdater |
| cashAction（会計後徴収/返金） | `aggregationMarkers/events_{eventId}` + 月次/日次更新 | `reportingEntries/{billId}_cashAction_{id}` + monthlyUpdater |
| reopen | ロールバック delta（`analyticsMonthly` の値を差し引き） | `reportingEntries/{billId}_reopen_{N}`（元月に負のエントリ） |

## callable 仕様詳細

### 共通事項

- **認証**: Firebase Auth 必須
- **エラー時**: 処理失敗しても `batchJobLogs` に `status: "failed"` で記録して正常終了（Flutter 側へエラーを返さない）
- **targetDate/targetMonth 省略時のデフォルト**:
  - 日次: JST で前日の businessDate / 前日日付
  - 月次: JST で前月

**共通レスポンス:**
```typescript
{
  jobKey: string;
  executionId: string;
  targetDate?: string;
  targetMonth?: string;
  status: "success" | "failed";
  judgment: "ok" | "ng" | "warning" | null;
  failedChecks: string[];
  errorMessage: string | null;
}
```

### callable 1: `analyticsDailyCheck`

**何を確認するか:** 「昨日の businessDate の settle が analytics に正しく反映されたか」

> **設計上のポイント**: `analyticsMonthly/{YYYY-MM}/days/{targetDate}` サブドキュメントがその日の
> businessDate 分の settle 処理回数（`orderCount`）を保持している。これを settled bills 数と比較する。
>
> **インデックス制約による簡略化（2026-06 実装）**: 当初設計では `aggregationMarkers` への
> 複合クエリと `AggregateField.sum()` による bills の grossSales 集計を含んでいたが、
> Firestore の sum 集計には `(businessDate, status, amounts.grandTotalRounded)` という
> 未定義の複合インデックスが必要なため、実装時にこれらを除外し `count()` のみに簡略化した。

**リクエスト:**
```typescript
{ targetDate?: string; }  // "2026-05-30" 形式。省略時は前日(JST)
```

**処理フロー:**

```
Step 1: analyticsMonthly/{YYYY-MM}/days/{targetDate} を読む（1 doc）
  → dayGrossSales, dayOrderCount（その日に settle 処理が走った回数、resettle 含む）を取得

Step 2: bills where businessDate==targetDate AND status==settled → count のみ
  → billsCount を取得
  ※ 既存インデックス bills:[businessDate, status, createdAt] を使用

Step 3: チェック実行
  Check A: dayOrderCount >= billsCount
    （settle→reopen→resettle で dayOrderCount > billsCount になるのは正常。
     dayOrderCount < billsCount = analytics に未反映の伝票が存在 → 異常）
  Check B: days doc が存在しない かつ billsCount > 0
    → analytics 書き込み自体が未実行（未反映）
```

**マーカーの docId 形式（参考）:**
- `{billId}_cycle{N}_settle`（cycleNo 指定あり、現在の新仕様）
- `{billId}`（legacy、cycleNo なし）
- マーカードキュメントは `{ type: 'settle', billId, cycleNo, businessDate, processedAt }` を持つ
- ※ マーカーへの直接クエリはこの callable では行わない（`days/{date}.orderCount` で代替）

**`details` フィールド:**
```typescript
details: {
  targetDate: string;
  billsCount: number;              // businessDate==targetDate の settled bills 数
  dayGrossSales: number;           // days/{targetDate}.grossSales（参考値）
  dayOrderCount: number;           // days/{targetDate}.orderCount（settle処理回数）
  dayExists: boolean;              // days/{targetDate} doc が存在するか
  dayOrderCountGeBills: boolean;   // dayOrderCount >= billsCount（Check A）
  dayMissing: boolean;             // !dayExists && billsCount > 0（Check B）
}
```

**`judgment` ルール:**
- Check A・B ともに ok → `"ok"`
- `dayMissing == true`（days doc なし・bills あり）→ `"ng"`
- `dayOrderCount < billsCount` かつ差が1件 → `"warning"`
- `dayOrderCount < billsCount` かつ差が2件以上 → `"ng"`
- `days/{targetDate}` ドキュメント自体が存在しない かつ billsCount == 0 → `"ok"`（その日に会計なし）

### callable 2: `analyticsMonthlyCheck`

**何を確認するか:** 「対象月全体の集計金額が正しいか（内部整合 + 遡及変更の検知）」

> **設計上のポイント**: `grossSales == itemsSales + extraCostSales + sideGameChipSales + tournamentsSales` の
> カテゴリ内部整合と、`sum(dailySales.values) == grossSales` の日次/月次整合が最も重要なチェック。
> 全件取得は不要（1 doc 読み取りで完結）。
>
> **インデックス制約による簡略化（2026-06 実装）**: 当初設計では Step 2 として
> `aggregationMarkers where type=='settle' → count` を行い `orderCount == settleMarkerCount` を
> Check A とする予定だったが、インデックスビルド中の FAILED_PRECONDITION を回避するため
> この Step と Check を除外した。代わりに `orderCount` は内部整合チェックの参考値として記録する。

**リクエスト:**
```typescript
{ targetMonth?: string; }  // "2026-05" 形式。省略時は前月(JST)
```

**処理フロー:**

```
Step 1: analyticsMonthly/{YYYY-MM} を読む（1 doc）
  → grossSales, itemsSales, extraCostSales, sideGameChipSales, tournamentsSales,
     orderCount, dailySales（Map）を取得

Step 2: 前回の月次ログ（直近の analyticsMonthlyCheck の success executionId）を取得（1 doc）
  → prevGrossSales を取得（遡及変更検知用）

Step 3: チェック実行
  Check A: grossSales == itemsSales + extraCostSales + sideGameChipSales + tournamentsSales（カテゴリ内部整合）
  Check B: sum(dailySales.values) == grossSales（日次合算 == 月次合計）
  Check C: 前回ログと比較して grossSales が変化していないか（遡及変更検知）
```

**チェック内容補足:**
- Check A: カテゴリ合算が grossSales と一致しない → 特定カテゴリの集計が壊れている
- Check B: 日次の dailySales マップの全値合算 == 月次 grossSales → 日次/月次の二重管理が整合しているか
- Check C: 前回のチェック時点の grossSales と現在が一致しない → 遡及会計や修正が発生した可能性

> **将来の拡張候補**: `aggregationMarkers where type=='settle'` の count と `orderCount` の突合
> (旧 Check A) は、インデックスが安定した段階で追加を検討する。

**`details` フィールド:**
```typescript
details: {
  targetMonth: string;
  grossSales: number;
  itemsSales: number;
  extraCostSales: number;
  sideGameChipSales: number;
  tournamentsSales: number;
  computedCategorySum: number;        // itemsSales + extraCostSales + ... の合算
  categorySumMatch: boolean;          // Check A
  dailySalesSum: number;              // sum(dailySales.values)
  dailySumMatchMonthly: boolean;      // Check B
  orderCount: number;                 // 参考値（チェック対象外）
  prevGrossSales: number | null;
  retroactiveChangeDetected: boolean; // Check C（前回ログと grossSales が一致しないか）
  prevExecutionId: string | null;
}
```

**`judgment` ルール:**
- 全 Check ok → `"ok"`
- Check C のみ ng（遡及変更検知）→ `"warning"`（遡及会計自体は正常な運用の場合もある）
- Check A / B いずれかが ng → `"ng"`

### callable 3: `reportingDailyCheck`

**何を確認するか:** 「昨日の settledAt（JST日付）の settle・cashAction が reporting に正しく反映されたか」

> **注意点**: reporting の日付基準は `settledAt` または `cashActionExecutedAt`（`eventAt`）。  
> analytics の `businessDate` とは**異なる**ため、チェック対象を「昨日の eventAt を持つ entries 」で絞る。

**リクエスト:**
```typescript
{ targetDate?: string; }  // "2026-05-30" 形式。省略時は前日(JST)
```

**処理フロー:**

```
JST 日付範囲の変換（重要）:
  targetDate "2026-05-30"（JST）
  → startUtc = 2026-05-29T15:00:00Z（= JST 2026-05-30 00:00）
  → endUtc   = 2026-05-30T15:00:00Z（= JST 2026-05-31 00:00）

Step 1: 前日ログ取得（1 doc）
  batchJobLogs/reportingDailyCheck/executions から最新の success ログを1件読む

Step 2: 昨日 JST に eventAt がある reporting entries を取得
  reportingEntries where eventAt >= startUtc AND eventAt < endUtc
  → entryType ごとに件数と totalAmountIncl を集計

Step 3: 昨日 JST に closedAt がある bills を count クエリ
  bills where closedAt >= startUtc AND closedAt < endUtc AND status==settled → settledBillsCount
  ※ bills ドキュメントの会計完了タイムスタンプフィールドは `closedAt`（`settledAt` ではない）

Step 4: チェック実行
  Check A: newSettleEntriesCount == settledBillsCount
    （settle 型の reporting entry 数 == その日に会計完了した bills 数）
  Check B: newEntriesTotal ≈ 前日ログからの reportingMonthly.totalAmountIncl の増分
    ※ cashAction / reopen entries の影響もあるため誤差許容範囲あり
```

**チェック内容:**

- **Check A**: `settle` 型の entries 数 == その日 `closedAt` の bills 数（基本的な漏れ検知）
- **Check B**: 昨日の entries 合算金額 ≒ reportingMonthly の totalAmountIncl の増分（金額の反映確認）

> **注意**: cashAction / reopen 分の entries も Check B に含まれる。Check A は `entryType=='settle'` で絞る。
> **フィールド名注意**: `bills` ドキュメントの会計完了時刻は `closedAt` フィールドに格納されている。
> `settledAt` というフィールドは存在しないため、クエリは必ず `closedAt` を使うこと。

**`details` フィールド:**
```typescript
details: {
  targetDate: string;
  newSettleEntriesCount: number;     // 昨日 eventAt の settle 型 entries 数
  newSettledBillsCount: number;      // 昨日 settledAt の bills 数
  newCashActionEntriesCount: number; // 昨日 eventAt の cashAction 型 entries 数
  prevReportingTotal: number;        // 前日ログの totalAmountIncl
  currentReportingTotal: number;     // 現在の totalAmountIncl
  reportingTotalDelta: number;       // 増分
  computedNewEntriesTotal: number;   // 昨日 entries の合算
  settleCountMatch: boolean;
  totalAmountDeltaMatch: boolean;    // delta と entries 合算が一致するか
  prevLogExecutionId: string | null;
}
```

**`judgment` ルール:**
- 全 Check ok → `"ok"`
- `settleCountMatch == false` かつ差が1件 → `"warning"`
- `settleCountMatch == false` かつ差が2件以上 → `"ng"`
- `totalAmountDeltaMatch == false`（差が2円以上）→ `"ng"`
- 初回実行 → `"ok"`（スナップショット取得のみ）

### callable 4: `reportingMonthlyCheck`

**何を確認するか:** 「対象月の reportingMonthly が reportingEntries の全件合算と一致するか」

> **注意**: `reportingMonth` は `YYYYMM` 形式（ハイフンなし）。  
> callable の入力 `"2026-05"` から内部で `"202605"` に変換して照合。

**リクエスト:**
```typescript
{ targetMonth?: string; }  // "2026-05" 形式。省略時は前月(JST)
```

**処理フロー:**

```
Step 1: reportingMonthly/{YYYYMM} を読む (1 doc)
Step 2: reportingEntries where reportingMonth == 'YYYYMM' を全件取得
Step 3: reportingMonthly/{YYYYMM}/aggregationMarkers を全件取得（件数確認）
Step 4: チェック実行
```

**チェック内容:**

- **Check A**: `markerCount == entriesCount`（件数突合）
  - `reportingMonthly/{YYYYMM}/aggregationMarkers` の count = `reportingEntries where reportingMonth==YYYYMM` の count
  - marker と entry は1対1対応（`entries_{entryId}` 形式で管理されるため）
- **Check B**: `monthlyTotalAmountIncl == sum(entries.totalAmountIncl)`（金額突合）
- **Check C**: カテゴリ別合算突合
  - `reportingMonthly.categoryBreakdown.{key}.amountIncl == sum(entries[].categoryBreakdown[key].amountIncl)`
- **Check D**: 支払い方法別合算突合
  - `reportingMonthly.paymentMethodBreakdown.{method} == sum(entries[].paymentBreakdown[method])`
  - ※ Firestore の実フィールド名は `paymentMethodBreakdown`（`ReportingMonthly` 型）
- **Check E**: 前回月次チェックのログと比較して totalAmountIncl が変化していないか（遡及変更検知）

**`details` フィールド:**
```typescript
details: {
  targetMonth: string;              // "2026-05"
  reportingMonthKey: string;        // "202605"（内部変換後）
  entriesCount: number;
  markerCount: number;
  markerCountMatch: boolean;        // Check A
  monthlyTotalAmountIncl: number;   // reportingMonthly の totalAmountIncl
  computedTotalFromEntries: number; // entries の totalAmountIncl 合算
  totalAmountMatch: boolean;        // Check B（差が1円以内を ok とする）
  totalAmountDiff: number;
  categoryBreakdownMatch: boolean;  // Check C
  paymentBreakdownMatch: boolean;   // Check D（paymentMethodBreakdown との照合）
  mismatchedCategories: string[];
  mismatchedPayments: string[];
  retroactiveChangeDetected: boolean; // Check E
  prevMonthlyLogTotal: number | null;
  prevExecutionId: string | null;
}
```

**`judgment` ルール:**
- 全 Check ok → `"ok"`
- Check B のみ差が1円以内 → `"warning"`（浮動小数点許容）
- Check E のみ ng（遡及変更） → `"warning"`（遡及会計自体は正常な運用の場合もある）
- Check A / C / D いずれかが ng → `"ng"`
