# 仕様整理

## ほぼ確定でよい仕様

### 1. scheduler の中心は `schedulerSupervisor` でよい

現行コードは、個別 scheduler を乱立させず、`schedulerSupervisor` が計画して task を作る方式です。  
この設計は運用整理の観点でも妥当です。

### 2. job ごとの ON/OFF や時刻変更は `schedulerConfig` で持つ

コード固定ではなく Firestore 設定で調整できる今の方向性は、店舗運用に合っています。

### 3. task ID と idempotency を前提に重複作成を避ける

現行 supervisor は `taskId` や `idempotencyKey` を持っているため、この方針は維持すべきです。

## ユーザー判断が必要な仕様

### 1. 失敗時の扱い

選択肢:

1. 一部 job 失敗でも他は流す
2. 1つでも失敗したら run 全体を fail とみなす

現行実装は hard error をまとめて投げる方向です。  
運用監視を重視するなら妥当ですが、業務影響の小さい job まで止めるかは判断の余地があります。

### 2. `schedulerConfig` の編集主体

選択肢:

1. Firestore 直接変更を認める
2. 管理 UI / callable 経由に限定する

本番運用では 2 の方が安全です。

### 3. 監視の粒度

選択肢:

1. supervisor 成功だけ監視する
2. job ごとの enqueue まで監視する
3. downstream 実行完了まで追う

おすすめは 3 です。  
supervisor だけ成功でも、実処理が失敗していれば業務は止まるためです。
