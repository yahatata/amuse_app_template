# 横断マトリクス

この資料は、残タスクを「どれがどの程度進んでいて、何が足りず、何を先に判断すべきか」で横並びに比較するためのものです。

## 見方

- `仕様`: docs としてどこまで整理されているか
- `実装`: コードとしてどこまで存在するか
- `検証`: テストや確認資料がどれだけあるか
- `運用安心度`: 本番で安心して回せるか

評価の目安:

- `高`: かなり揃っている
- `中`: 一部揃っているが未決や未検証が残る
- `低`: ほぼ未着手または判断材料不足

## 根拠の強さで見た分類

### A. 仕様・コード・検証が揃い始めている

- `01`
- `06`
- `07(+08)`
- `11`
- `12`

このグループは「ゼロから考える」より、「どこまで採用し、どこまで本番条件に入れるか」を決める段階です。

### B. 仕様はあるが実装が薄い

- `03`

このグループは、実装前に spec を再採択するかを決めるべき段階です。

### C. 仕様も実装も薄い

- `04`

このグループは、まず業務ルールを作らないと実装に入れません。

### D. 実装はあるが、運用整理が不足

- `02`
- `05`
- `09`
- `10`

このグループは、現場運用・権限・残件整理の観点で再設計が必要です。

## 依存関係の強いもの

### 強くつながっている組み合わせ

- `01` → `02` → `02.1` → `02.5`
- `05` ←→ `10`
- `06` ←→ `07(+08)`
- `07(+08)` ←→ `12`
- `04` ←→ `11` / `12`
- `03` ←→ `10`

### 依存の意味

- `06` を曖昧にすると、`07(+08)` の fallback / 有効化判断がぶれます。
- `07(+08)` で給与通知の技術確認が未完了だと、`12` の業務判断材料が不足します。
- `05` を決めないまま UI を整えると、`10` の導線設計が無駄になりやすいです。
- `04` を考えずに `11` や `12` だけ進めると、退職 staff の扱いであとから整合性問題が出ます。

## このマトリクスからの実務判断

最初に手をつけるべきは、単純に未実装のものではなく、次の2条件を満たすものです。

1. 本番事故に直結する
2. 他タスクの判断基準にもなる

その意味で、最優先は `01`, `05`, `06`, `07(+08)` です。  
次点で `11`, `12`, `10` を進めると、全体の判断がかなりしやすくなります。
