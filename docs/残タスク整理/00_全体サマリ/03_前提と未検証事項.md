# 前提と未検証事項

この資料は、今回の残タスク整理がどの前提で書かれており、どこまでが確認済みで、どこから先が未検証かを明示するものです。  
認識ずれを減らすため、意図的に「まだ断定しないこと」も書いています。

## 前提

### 1. 今回のゴールは docs 整理であり、実装ではない

- 本整理は、コード改修よりも調査・整理・仕様判断支援を優先しています。
- そのため、実装の正誤を最終的に確定するより、「どこが未決か」「何を見て判断すべきか」を重視しています。

### 2. 現行コードと既存 docs の両方を見る

- 既存 docs には深い検討が多い
- ただし stale なものもある
- よって、現行コードに存在する事実を優先しつつ、既存 docs を背景資料として扱っています

### 3. 本番判断で重要なのは機能有無だけではない

今回の整理では、次も同じ重みで扱っています。

- 実装があるか
- 誤操作しにくいか
- 失敗時に説明・復旧できるか
- 今後の運用や監査に耐えるか

## 今回は確認していない、または断定していないこと

### 1. 本番環境の実リソース状態

- 実際の Cloud Scheduler job 一覧
- 実際の Cloud Tasks queue 内の pending task 全件
- 実環境の service account 権限
- 本番 Firestore / Storage の中身

これらは repo 外要素のため、資料上では「要確認」として扱っています。

### 2. すべての end-to-end 実行

- 会計後調整の全シナリオ
- scheduler から downstream 実行完了まで
- 給与通知の全 triggerType
- LIFF の全境界ケース

代表ルートは追えていますが、全網羅 E2E ではありません。

### 3. ユーザーの業務優先順位の最終確定

資料上の優先度は、主に次で置いています。

- 本番事故リスク
- 他タスクへの依存
- 現時点での実装成熟度

ただし、実際の事業優先順位や納期優先順位までは断定していません。

## 認識合わせのために重要な暗黙前提

### 1. `table device` は「あった方が便利」ではなく、独立機能として設計が必要

もしユーザーの想定が「terminal の軽量版を少し出したい」程度であれば、今の spec はやや重い可能性があります。

### 2. `LIFF トーナメント参加` は現状のままだと予約機能ではない

ここは認識差が起きやすいです。  
現行コード上は、参加意思表示より「bill を伴う参加処理」に近いです。

### 3. `requiredStaffByTimeSlot` と `給与通知` は未実装ではない

ユーザーの体感では「古くから残っているタスク」に見えていても、技術的には既にかなり進んでいます。  
論点は、未実装というより「採用しきるか」です。

### 4. `config 整理` は defaults 削減の話だけではない

fallback 方針、Secrets 境界、server/client 責務、store 差分といった設計判断が本体です。
