# 観点別レビュー

この資料は、「今回の残タスク整理が本当に十分か」を多角的に見直した結果をまとめたものです。  
単にタスクを並べただけでなく、どの観点が十分で、どこがまだ薄いかを明示します。

## レビュー結論

今回の整理は、**タスク単位の現状整理としては十分実用的**です。  
一方で、次の3観点は補足がないと使いづらくなると判断しました。

1. 横断比較
2. 未検証事項の明示
3. 前提・認識合わせの整理

この3点は、今回のレビューに合わせて補強しました。

## 観点別評価

### 1. アプリの目的との整合

評価: `十分`

- 単機能アプリではなく、店舗運営基盤として整理できている
- 会計、トーナメント、勤怠、デバイス、自動化を横断して見ている

### 2. 実装実態との整合

評価: `概ね十分`

- code / docs / tests を照合している
- とくに `01`, `05`, `06`, `07`, `08`, `11`, `12` は実装実態を前提に整理できている

残る注意:

- 全機能を実行して確かめたわけではない
- 一部は docs とコード差分からの推定を含む

### 3. 運用フロー観点

評価: `十分`

- 会計後調整、LIFF 参加、退職、HOME 権限、給与通知など、現場運用に結びつく観点を分けている

### 4. 権限制御・安全性観点

評価: `十分`

- HOME の permissive 表示
- LIFF 参加の bill 前提
- config の fallback
- Cloud Tasks / scheduler の運用安全性

が拾えている

### 5. データ整合・監査観点

評価: `概ね十分`

- `01` で税務・会計 read model を main 論点として扱えている
- `04` で staff 退職を削除ではなく状態管理問題として扱えている

残る注意:

- reporting / accounting 正式 ledger の詳細設計はまだ future のまま

### 6. 本番リスク観点

評価: `十分`

- 優先順位が「開発しやすさ」ではなく「事故に直結するか」で組めている
- `07` と `08` を強く上位に置けている

### 7. テスト・検証観点

評価: `中`

- 代表テストの存在確認はできている
- 一部 build / Flutter test も確認した

不足:

- end-to-end 実行確認は限定的
- Functions 側の広いテスト実行運用には追加確認余地がある

### 8. docs の鮮度観点

評価: `十分`

- stale docs の存在を前提に整理できている
- 「既存 docs は良いが、そのまま本番判断資料にしない方がよい」という方針が示せている

### 9. ユーザー判断を助ける観点

評価: `概ね十分`

- 各タスクで「ほぼ確定」と「ユーザー判断が必要」を分離できている
- 選択肢提示もある

改善した点:

- 今回のレビューで横断マトリクスを追加し、優先度比較しやすくした

### 10. 認識合わせ観点

評価: `やや不足 → 補強対象`

ユーザーが特に重視していた点です。  
前回版では、暗黙前提や未検証事項を十分に明示しきれていなかったため、今回あらためて補強対象と判断しました。

## 今回のレビューで「修正した方がよい」と判断した点

### 修正した点

- 横断マトリクスを追加
- 観点別レビューを追加
- 未検証事項と前提整理を追加
- config / scheduler / requiredStaff 周辺に、コード保守性の追加論点があることを docs に反映

### 修正しなかった点

- 各タスク docs を細かい根拠リンクだらけにはしなかった

理由:

- まずは読みやすさと意思決定しやすさを優先したため
- 既存 docs 側に原典が多く、ここで全面的に写し直すと逆に読みにくくなるため

## このレビュー後の評価

現時点の `docs/残タスク整理/` は、少なくとも次には使える状態になっています。

- どの残タスクが何者かを把握する
- 優先順位を決める
- ユーザー判断が必要な論点を見つける
- 実装に入る前の整理資料として使う

一方で、次を行う段階では追加の深掘りが必要です。

- 実装着手直前の仕様凍結
- 実環境でのログ確認と運用確認
- 実機 end-to-end 確認
