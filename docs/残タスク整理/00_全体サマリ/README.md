# 全体サマリ

## まず読むべき結論

現時点の残タスクは、性質で大きく4種類に分かれます。

1. **本番化の最終詰め**
   `01`, `02`, `05`, `06`, `07`, `08`, `12`
2. **未実装または仕様途中**
   `03`, `04`
3. **既に一部実装済みだが、採用するか再判断が必要**
   `11`, `12`
4. **構造整理・UX 改善**
   `09`, `10`

## アプリ全体の状態感

- ドメインは広いですが、中心にあるのは「店舗運営を1つのアプリで回すこと」です。
- そのため、残タスクを個別に進めるだけではなく、「会計」「トーナメント」「勤怠」「デバイス権限」「自動化」が矛盾しないことが重要です。
- とくに本番運用の観点では、仕様の正しさだけでは足りず、次の3つが必要です。
  - 失敗時にどう振る舞うか
  - 誰がどこまで触れるか
  - 自動ジョブが本当に動いているか

## 横断で見えた重要論点

### 1. 仕様はあるが、最終判断が残っている

- 会計後調整は current-scope の設計がかなり進んでいます。
- ただし税務・会計用 read model を今スコープに入れるかは未決です。
- `requiredStaffByTimeSlot` や給与通知も、技術的には存在しますが、運用上採用しきるかが未決です。

### 2. docs の鮮度差が大きい

- 既存 docs は非常に多く、深い検討も残っています。
- 一方で、現行コードと完全には一致しない資料もあります。
- そのため、今後は「本番判断に使う資料」と「検討履歴資料」を分ける運用が必要です。

### 3. 本番品質のボトルネックは自動化と権限

- `scheduler` / `Cloud Tasks` は構成自体はあります。
- ただし、壊れた旧タスク、サービスアカウント、リージョン、ログ整合、再実行手順など、運用面の詰めがまだ必要です。
- HOME 画面も、現状は端末権限に対して表示がかなり緩く、本番運用では再設計した方が安全です。

## 今回の調査で確認できた事実

- `schedulerSupervisor` と scheduled-job 系のコードは存在し、代表テストもあります。
- `processPayrollNotifications` と給与通知仕様も存在します。
- `requiredStaffByTimeSlot` は専用 doc 化され、Functions/Flutter とも実装があります。
- `table device` は詳細 spec がある一方で、コード実装はほぼ着手前です。
- スタッフ退職処理は、専用ドメインとしては未着手に近いです。
- LIFF のトーナメント参加は、現状では `activeStays` と bill に強く結びついています。
- `storeMeta/config` は既に Functions/Flutter 両方で読み取りとデフォルト補完の実装があります。
- `unused_function_lib` は意図的な退避場所として残っており、単純に「全部削除」で進めるべき状態ではありません。

## 簡易検証で見えたこと

- `functions` の `npm run build` は通りました。
- Flutter 側では `requiredStaffByTimeSlot` と会計後調整の要対応一覧まわりの代表テストは通りました。
- 一方で Functions 側の広めの Jest まとめ実行は、個別 PASS が確認できるものがある一方、実行まとまりとしては終了確認しづらいケースもありました。
- つまり「テストがない」ではなく、「テストの存在」と「継続的に安心して回せる検証運用」はまだ別論点です。
