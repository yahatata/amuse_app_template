# 検証計画

## 1. 検証方針

- **PASS 条件**: 各 enabled job について **処理完了まで**（[01_目的.md](./01_目的.md)）
- 可能な限り CLI（gcloud / logging read）と Firestore で確認する
- 週次・年次 job は cron 待ちせず **Task Queue へ手動投入** して検証する
- 実行結果は PASS / FAIL / SKIP（理由付き）で記録する

参照: `docs/タスク実行復旧_20260407/検証計画.md`（2026-04-07 復旧時の手順。本計画は job 完了までを明示的に含む）

## 2. 共通 PASS 連鎖

enabled な scheduled job ごとに、次を 1 セットとする。

```
[1] schedulerSupervisor
      logOpsInfo(start) → logOpsSuccess
[2] schedulerDispatchLogs
      eventType: enqueued（または skip + reason）
[3] executeScheduledJobTask（該当 jobKey）
      logOpsInfo(start) → execution log completed / skip
[4] 業務 handler（該当時）
      logOpsSuccess または仕様どおりの skip
[5] downstream（該当時）
      例: assessment task 生成、tournament task 投入 等
```

**FAIL 例**

- [1] のみ成功し [3] の start がない → 未配送・未到達
- [3] start あり、[4] success も error もない → 処理中 or ログ欠落
- pending / retry task が増え続ける → queue / payload / IAM 問題

## 5. CLI 確認（例）

プロジェクト ID は環境に合わせて置換する。

```bash
# Queue 一覧
gcloud tasks queues list --location=asia-northeast1

# Scheduler
gcloud scheduler jobs list --location=asia-northeast1

# supervisor 直近ログ
gcloud logging read \
  'jsonPayload.functionEntry="schedulerSupervisor"' \
  --limit=20 --freshness=7d --format=json

# job 完了ログ（例）
gcloud logging read \
  'jsonPayload.functionEntry="executeScheduledJobTask" AND jsonPayload.eventType="start"' \
  --limit=20 --freshness=7d
```

Firestore:

- `schedulerDispatchLogs` — 直近 `planningDate` / `jobKey`
- `schedulerExecutionLogsByCloudTask` — `idempotencyKey` で突合

## 6. 合格基準サマリ

| 項目 | PASS |
|------|------|
| enabled scheduled job | 上記連鎖が代表 run で取れる |
| 代表 HTTP / Task queue | 手動投入で 2xx + start → success |
| queue 整理 | 不要・重複・旧版が parked または削除済み |
| pending 滞留 | 増え続けない |
| ログ | [06_ログと検知方針.md](./06_ログと検知方針.md) と整合 |

---

## 7. 失敗時の切り分け順

1. queue 側（body / header / scheduleTime / retry）
2. auth（OIDC SA、IAM）
3. function 側（payload validation、config）
4. downstream（Firestore、設定不整合）
