## 1. 背景と As-Is 問題

| ID | 問題 | 6/4 での現れ方 |
|----|------|----------------|
| P1 | supervisor 1 回で job あたり **複数 dispatch** があるが UI は **最新 1 slot** のみ | 「skip 20 + enqueue 3」が 1 行に潰れる |
| P2 | dispatch skip だと execution が「対象外」になり当日本処理が見えない | 04:40 weeklyPlanner が「②対象外」 |
| P3 | 見出し「今日の 6 job」と実装（直近 40 件の最新 1 件）が不一致 | 運用者の期待とズレ |
| P4 | open/close 等が Scheduler 6 行だけでは追いにくい | 責務混在 |

### 合意済み方向性

- **Scheduler 監視** = タスク生成（dispatch）の正しさ専用
- **Task 監視（定期）** = キュー × 期間で実行予定・実行結果
- **Task 監視（都度）** = 一旦作り Phase 8 で要否判断
- **Scheduler 正常判定** = dispatch の error / 不適切 skip のみ（execution は Task 監視）

## 2. システム構造（前提）

### 2.1 3 層

```
[Layer A]  Cloud Scheduler  03:00 JST → schedulerSupervisor

[Layer B]  dispatch（① タスク生成）
             → scheduled-job-* キューへ Cloud Tasks 投入
             → ログ: 中央 schedulerLogs/{storeId}/runs (phase="dispatch")

[Layer C]  execution（本処理）
             → onTaskDispatched が plannedRunAt に実行
             ├─ 振分け型: 下位キューへ child task
             └─ 完結型: handler 内で Firestore 直接更新
             → ログ: schedulerLogs (phase="execution"), taskLogs,
                     schedulerTaskDispatchLogs（child dispatch）
```

### 2.2 supervisor dispatch ルール

正本: `amuse_app_template/functions/src/domains/scheduler/supervisor/schedulerSupervisorCore.ts`

- 毎日 **03:00 JST**、1 回
- `planningHorizonDays`（既定 **7**）、offset 0..6
- 各 offset 日 × enabled job で `shouldRunOnDate` が true なら 1 slot 試行
- 結果: `enqueued` / `skip`（reason 付き）/ `error`

#### skip reason

| reason | 意味 | 判定 |
|--------|------|------|
| `task_already_exists` | 同一 idempotencyKey の task が既存 | **正常** |
| `planned_run_at_in_past` | plannedRunAt が supervisor 実行時刻より過去 | **要確認** |
| error 系 | enqueue 失敗 | **異常** |

### 2.3 scheduled-job キューの 2 種

| 種別 | 役割 | jobKey |
|------|------|--------|
| **振分け型** | 起動後 **下位キューへ child 投入** | weeklyPlanner, enqueueTournamentTasksByScheduler, payrollNotificationScheduler |
| **完結型** | 起動後 **handler 内で完結** | generateRecurringTournamentsByScheduler, scheduledCleanup, scheduleGenerateNextYearBusinessHours |

6 本すべてが supervisor の dispatch 先（Layer B）。

### 2.4 キュー対応図

```
supervisor (03:00)
  ├─ scheduled-job-weekly-planner                    [振分け] → business-date-assessment-queue
  ├─ scheduled-job-enqueue-tournament-tasks-by-scheduler [振分け] → tournament-queue
  ├─ scheduled-job-payroll-notification-scheduler      [振分け] → processPayrollNotifications
  ├─ scheduled-job-generate-recurring-...              [完結] Firestore 生成
  ├─ scheduled-job-scheduled-cleanup                   [完結] Firestore 削除
  └─ scheduled-job-schedule-generate-next-year-...     [完結・年次] 営業時間生成

（scheduler 外）
  executeMonthlyPayroll 等 → processStaffPayroll → finalizePayrollRun
```

## 3. Scheduler 監視タブ ToBe

### 3.1 定義

| 項目 | 内容 |
|------|------|
| 目的 | 当日 `planningDate` の supervisor による **dispatch** が正しいか |
| 見ないもの | top-level / child の **実行結果**（Task 監視へ） |
| 時間軸 | `planningDate = 当日（JST）` の supervisor 1 回 |

### 3.2 レイアウト

```
[supervisor サマリ行]  enqueued / skipped / failed 合計
[6 job 折りたたみ行]  planningDate=当日
  └─ 展開: slot 一覧（A/B/C + エラー）+ キュー説明
[履歴セクション]  既存フィルタ（dispatch 中心）
```

### 3.3 As-Is → ToBe

| As-Is | ToBe |
|-------|------|
| ① dispatch + ② execution | **① dispatch のみ** |
| job あたり最新 1 slot | **当日全 slot 集計** |
| 「今日の 6 job」 | 「当日 supervisor のタスク生成（6 job）」等 |
| Scheduler 内 child セクション | **廃止 → Task 監視（定期）§4.3 セクション 2** |

### 3.4 折りたたみ行サマリ

**集計単位:** `planningDate + jobKey`

| 項目 | 定義 |
|------|------|
| 新規作成 | dispatch `enqueued` |
| 重複 skip | `skip` + `reason=task_already_exists` |
| その他 skip | `skip` + 上記以外 |
| エラー | dispatch `error` |

**行判定:**

- **正常:** エラー 0 かつ その他 skip 0
- **要確認:** エラー > 0、`planned_run_at_in_past` ≥ 1、supervisor 未到達

### 3.5 展開 slot 一覧 — 区分 A / B / C（初版必須）

| 区分 | ラベル | 定義 |
|------|--------|------|
| A | 今回作成したタスク | dispatch `enqueued` |
| B | 重複のため作成しなかったタスク | `skip` + `task_already_exists` |
| C | 今回の作成対象外 | horizon 内だが `shouldRunOnDate` 不一致で **dispatch 試行なし** |
| — | エラー | dispatch `error` |
| — | その他 skip | `planned_run_at_in_past` 等 |

**区分 C 算出:**

1. `stores/{storeId}/config/schedulerConfig`（§5 同期済み）を読む
2. `planningHorizonDays` + 各 job schedule から **期待 slot 一覧** を UI で合成
3. 当日 dispatch ログの idempotencyKey と diff → ログ無し = C

**yearly job 特別ルール:**  
`scheduleGenerateNextYearBusinessHours` は 1/29 以外、「年次 job: 今日は対象日でないため試行なし（対象: 毎年 1/29）」と **1 行**表示。offset×7 行は出さない。

**読込:** サマリは初回取得可。slot 一覧は展開時遅延読込可。Config 未同期時はバナー。

### 3.6 child 移管

既存 `buildSchedulerChildTaskSummaries`（`amuse-admin/src/lib/monitoring.ts`）を Task 監視（定期）で **再利用**。ロジック再実装不要。

### 3.7 キュー説明パネル

schedulerConfig（同期済み）+ 静的説明（§6 ドキュメント）で、job の schedule と下位キューを表示。

## 4. Task 監視タブ ToBe

### 4.1 タブ

- **定期実行系**（新規メイン）
- **都度実行系**（現行改修、Phase 8 で要否判断）

### 4.2 定期 — 共通

**期間フィルタ:** 前日 / 当日（デフォルト）/ 翌日 / 期間指定

**キュー折りたたみサマリ:**

```
実行予定 N / 実行済 M / 未実行 (N-M) / エラー E  [正常 | 要確認]
```

**実行予定件数の正本:** `schedulerTaskDispatchLogs` + `schedulerLogs` phase=execution。Cloud Tasks API は補助。

### 4.3 キュー 3 分類（表示順）

#### セクション 1: タスク生成用キュー（scheduler 起点）

supervisor が dispatch する `scheduled-job-*` 6 本。Layer C の **scheduled-job 実行**を期間で見る。

| キュー名 | jobKey | 種別 |
|----------|--------|------|
| scheduled-job-weekly-planner | weeklyPlanner | 振分け |
| scheduled-job-enqueue-tournament-tasks-by-scheduler | enqueueTournamentTasksByScheduler | 振分け |
| scheduled-job-payroll-notification-scheduler | payrollNotificationScheduler | 振分け |
| scheduled-job-generate-recurring-tournaments-by-scheduler | generateRecurringTournamentsByScheduler | 完結 |
| scheduled-job-scheduled-cleanup | scheduledCleanup | 完結 |
| scheduled-job-schedule-generate-next-year-business-hours | scheduleGenerateNextYearBusinessHours | 完結・年次 |

**execution ログ正本:** `schedulerLogs` phase=execution（主）、`taskLogs` functionEntry=`executeScheduledJobTask`（補助）。

| | Scheduler 監視 | セクション 1 |
|--|----------------|-------------|
| 焦点 | dispatch 試行 | plannedRunAt の **実行** |
| 指標 | 新規/skip/エラー | 実行予定/実行済/未実行/エラー |

#### セクション 2: 業務実行キュー（scheduler 起点）

振分け型の下位キュー。`buildSchedulerChildTaskSummaries` 再利用。

| キュー | 生成元 | handler |
|--------|--------|---------|
| business-date-assessment-queue | weeklyPlanner 等 | openAssessmentTask / closeAssessmentTask |
| tournament-queue | enqueueTournamentTasksByScheduler | controlHookHttp |
| processPayrollNotifications | payrollNotificationScheduler | 同名 handler |

#### セクション 3: 業務実行キュー（単独起点）

scheduler 起点でない task。

| キュー | 起点 |
|--------|------|
| processStaffPayroll | executeMonthlyPayroll 等 Callable |
| finalizePayrollRun | processStaffPayroll 連鎖 |

給与**通知** → セクション 2。給与**計算 run** → セクション 3。

### 4.4 都度実行系

`taskLogs` のうち **scheduler 起点でない** もの。

```typescript
function isSchedulerOriginTaskLog(log: TaskLog): boolean {
  const ctx = log.context ?? {};

  if (typeof ctx["schedulerParentIdempotencyKey"] === "string" &&
      ctx["schedulerParentIdempotencyKey"].length > 0) {
    return true;
  }

  // executeScheduledJobTask の start ログは idempotencyKey 未設定だが supervisorRunId あり
  if (log.functionEntry === "executeScheduledJobTask" &&
      typeof ctx["supervisorRunId"] === "string" &&
      ctx["supervisorRunId"].length > 0) {
    return true;
  }

  return false;
}
// 都度 = !isSchedulerOriginTaskLog(log)
```

**実装者向け補足:**

- child handler（openAssessmentTask 等）は start 時点から `schedulerParentIdempotencyKey` を context に持つ
- `executeScheduledJobTask` の success ログは `schedulerParentMetadata` 展開で idempotencyKey を持つ
- start ログのみ条件 3 で補完

**都度の例:** processStaffPayroll, finalizePayrollRun, scheduler メタデータなし controlHookHttp, continueBusinessTerminal 経由 openAssessmentTask

**Phase 8 廃止 OK:** 1 週間、都度系障害が errorLogs + 重要度で漏れなかった

## 5. 店舗 Config 中央同期

### 5.1 目的

区分 C・キュー説明・設定参照 UI のため、店舗 config を中央にコピー。

### 5.2 同期対象

| configKey | 店舗正本 |
|-----------|----------|
| schedulerConfig | storeMeta/schedulerConfig |
| storeConfig | storeMeta/config |
| payrollConfig | storeMeta/payrollConfig |
| reportingGroupConfig | storeMeta/reportingGroupConfig |
| taxReportingBehavior | storeMeta/taxReportingBehavior |
| requiredStaffByTimeSlot | storeMeta/requiredStaffByTimeSlot |

### 5.3 中央保存先

```
stores/{storeId}/config/{configKey}
  payload, syncedAt, sourceProjectId, syncedBy
```

### 5.4 実装経路（現行）

初案は Next.js Server Action だったが、現行実装は中央 Cloud Function
`syncStoreConfigFromAdmin` を直接呼ぶ。

```text
設定 UI（ブラウザ）
  → syncStoreConfigFromAdmin
  → 中央 Admin SDK
  → cross-project read 店舗 Firestore
  → 中央 Firestore write
```

理由:

- Firebase Hosting preview + Next.js 16 環境で `settings/store-config` の Server Action POST が
  静的 HTML として返る事象があった
- 同期処理を Next bundle の外に出す方が deploy/runtime の切り分けが容易

必要なら `NEXT_PUBLIC_STORE_CONFIG_SYNC_URL` で endpoint を上書きできる。

**IAM:** 中央 runtime SA に各店舗 `roles/datastore.viewer`。店舗追加 setup 手順に組み込む。

### 5.5 設定 UI

`設定 > 店舗 Config 同期`: 店舗選択 → 取得 → 6 種 upsert → 読みやすい参照 UI
