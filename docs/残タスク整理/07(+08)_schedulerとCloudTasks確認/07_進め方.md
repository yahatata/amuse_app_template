# 進め方（Phase 順序と運用ルール）

## 基本方針

各 Phase は **確認が主** とする。確認中に動いていない・おかしいものが見つかったら **その都度直し**、再度確認してから次へ進む。

```
確認する → 問題があれば直す → 再確認 → 次へ
```

一括で全部確認してからまとめて修正するのではなく、**見つけた単位で PASS を取る**。

### 修正の粒度

| 種類 | 対応 |
|------|------|
| 明らかな不具合（payload 欠落、設定 typo、ログ欠落など） | その Phase 内で都度修正 |
| 影響が大きい変更（queue 構成変更、supervisor 失敗ポリシー変更など） | changeSpec を書いてから実装 |

---

## Phase 一覧

| Phase | 名前 | 主な内容 | 修正 |
|-------|------|----------|------|
| 0 | 期待状態の固定 | コード正本・Firestore 設定・GCP 実態の diff | 基本は記録のみ |
| 1a | きれい化（洗い出し） | 不要・重複・旧版を parked リスト化 | リスト作成のみ |
| 2 | Scheduler 層確認 | supervisor が仕事を振れているか | 都度修正 |
| 3 | Handler 完了確認 | enabled job が **完了まで** 動くか（PASS 条件） | 都度修正 |
| 1b | きれい化（削除） | Phase 3 PASS 後、parked の物理削除 | ユーザー GO 後 |
| 4 | ログ統一 | 未対応 handler の start ログ等（11 件は触らない） | 計画作業 |
| 5 | 検知・ルール | クエリ草案・日次手順・`.cursor/rules` | ドキュメント中心 |
| 6 | クローズ | 実施結果・マトリクス更新・運用資料引き継ぎ | — |

### Phase 1 を 1a / 1b に分ける理由

**検証前に queue を消すと、動作確認の経路が失われる**ため、次の順序とする。

1. **Phase 0〜1a**: diff と parked リストまで（削除しない）
2. **Phase 2〜3**: 現行経路が PASS するまで確認・修正
3. **Phase 1b**: PASS 後にのみ、parked 対象の物理削除（復元不可のため ID 一覧保存 + ユーザー GO）

## Phase 0 でやること（詳細）

1. [04_期待状態一覧.md](./04_期待状態一覧.md) をコード正本として確定（済みなら実環境との突合のみ）

**Phase 0 では削除しない。**

## Phase 2〜3 の PASS（再掲）

enabled な各 job について、代表 run で次が取れること。

```
schedulerSupervisor
  → schedulerDispatchLogs（enqueued または skip + reason）
    → handler logOpsInfo(start)
      → logOpsSuccess または仕様どおり skip
```

supervisor 成功のみ・enqueue のみでは **PASS にしない**。
