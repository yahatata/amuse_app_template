# 仕様整理

## ほぼ確定でよい仕様（合意・現行コードベース）

### 1. scheduler の中心は `schedulerSupervisor`

個別 onSchedule を乱立させず、supervisor が `schedulerConfig` に基づき job を計画・enqueue する方式を維持する。

- 入口 cron: 毎日 03:00 JST（`0 3 * * *`, `Asia/Tokyo`）
- job の ON/OFF・時刻は `storeMeta/schedulerConfig`（未設定時は `schedulerConfigDefaults.ts`）

### 2. PASS 条件は job 完了まで

監視・検証の粒度は **downstream 実行完了まで**（supervisor 成功だけでは不十分）。

### 3. region / SA

- region: `asia-northeast1` に統一
- HTTP Cloud Tasks の invoker SA: `tasks-invoker@{projectId}.iam.gserviceaccount.com`

### 4. idempotency

supervisor は `taskId` / `idempotencyKey` で重複 enqueue を避ける。維持する。

### 5. きれい化の基準

**不要・重複・旧版** を主軸とする。明らかに不正な payload の task は整理の副産物として削除してよい。

### 6. 給与通知（12 との切り分け）

- **07+08**: `payrollNotificationScheduler` → `processPayrollNotifications` を他 job と同様に **動く・ログ・検知** 可能に保つ
- **12**: 通知機能の **必要性・中身の調整** を検討し、必要なら修正する

### 7. ログの役割分担（概要）

| ログ | 意味 |
|------|------|
| `logOpsInfo`（`eventType: "start"`） | handler **到達**のみ（正常完了ではない） |
| `logOpsSuccess` | **正常完了** |
| `logOpsError` | **到達後の失敗** |
| `schedulerDispatchLogs` | supervisor による **enqueue / skip / error** |
| `schedulerExecutionLogsByCloudTask` | scheduled job handler の **started / completed / skip / error** |

詳細は [06_ログと検知方針.md](./06_ログと検知方針.md)。

### 8. GCP未実行検知 11 handler

`docs/エラーログ運用/GCP未実行検知/changeSpec/changeSpec_GCP側未実行検知_logOpsInfo追加.md` で start ログ追加済みの 11 件は **本タスクのログ統一対象外**（触らない）。  
未対応 handler（例: `weeklyPlanner` 本体、`scheduledCleanup`、`scheduleGenerateNextYearBusinessHours`）は同方針へ揃える。

## ユーザー判断が必要な仕様

### 1. supervisor run 全体の失敗扱い

| 選択肢 | 内容 |
|--------|------|
| A | 一部 job 失敗でも他は流す |
| B | 1 つでも失敗したら run 全体を fail |

**現状**: B に近い（hard error をまとめて throw）。  
**推奨**: 現状維持を起点に、業務影響の小さい job の扱いだけ必要なら後から調整。

### 2. `schedulerConfig` の編集主体

| 選択肢 | 内容 |
|--------|------|
| A | Firestore 直接変更 |
| B | 管理 UI / callable 経由に限定 |

**推奨**: 本番は B。本タスクでは現状の編集経路を確認し、docs に記載する。

### 3. queue 構成の再編

| 選択肢 | 内容 |
|--------|------|
| A | ドメインごと現状維持 |
| B | scheduled-job 系をさと集約 |
| C | ドメインごとに分離し直す |

**推奨**: 本タスクでは **A（現状維持）**。動作確認と不要・旧版整理を優先。

### 4. `default-store` 依存

| 選択肢 | 内容 |
|--------|------|
| A | 補完ロジックで当面しのぐ |
| B | 早めに完全排除 |

**推奨**: A（段階移行継続）。本タスクでは task producer が正しい storeId を渡しているかの確認にとどめる。

## 実機確認計画（仕様）

テストだけでは担えない確認。

| 確認项 | 方法 | 担当 |
|--------|------|------|
| 各 enabled job の完了連鎖 | 手動 enqueue または supervisor 実行後のログ + Firestore | Cursor（gcloud 権限あれば） |
| weekly / yearly job | cron 待ちせず Task Queue へ手動投入 | Cursor |
| assessment 連鎖の副作用 | weeklyPlanner 実行後、`business-date-assessment-queue` に task が生成されること | Cursor + 必要時ユーザー |
| 給与通知の完了 | `processPayrollNotifications` の start → 完了ログ | Cursor |
| queue 削除後の業務影響 | 削除前に parked 理由・代替経路を記録 | ユーザー最終確認 |
