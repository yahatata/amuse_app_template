# ログと検知方針

## 1. ログ 3 層（混同しない）

| 層 | 名前 | 正本 | 意味 |
|----|------|------|------|
| **A** | Scheduler 起動 | `schedulerSupervisor` の start / success + GCP Scheduler ログ | cron が supervisor を叩いた |
| **B** | Dispatch | `schedulerDispatchLogs` + supervisor success の context | 計画どおり enqueue / skip した |
| **C** | Handler 到達・完了 | `logOpsInfo(start)` → `logOpsSuccess` / `logOpsError` + `schedulerExecutionLogsByCloudTask` | task が handler に届き、処理が終わった |

**検知のクリア条件（合意済み）**: 層 **C まで**（job 完了または仕様どおり skip）。  
A だけ・B だけでは「正常」とみなさない。

---

## 2. 層ごとの出力ルール

### 層 A — schedulerSupervisor

- 入口: `logOpsInfo(start)` — context: `planningDate`
- 完了: `logOpsSuccess` — context: `supervisorRunId`, `enqueuedCount`, `skippedCount`, `failedCount`
- 失敗: `logOpsError`

### 層 B — dispatch

- Firestore `schedulerDispatchLogs` を第一証跡
- `writeSchedulerDispatchLogBestEffort` の logOpsSuccess は **補助**（dispatch log 本体を優先）

### 層 C — handler

| ログ | 役割 |
|------|------|
| `logOpsInfo`（`eventType: "start"`） | **到達のみ** |
| `logOpsSuccess` | 正常完了 |
| `logOpsError` | 到達後失敗 |

`schedulerExecutionLogsByCloudTask` は scheduled job 経路の **started / completed / skip / error** を Firestore に残す。

## 5. 運用判定（到達・完了・失敗）

| 状態 | 判定 |
|------|------|
| start なし（plannedRunAt + grace 経過） | 未実行・未配送・未到達 **疑い** |
| start あり + error あり | 到達後 **失敗** |
| start あり + success あり | 到達後 **正常完了** |
| start あり + success も error もなし | 処理中 / ログ欠落 / 早期 return — **要確認** |
| dispatch skip + reason | 仕様どおり **skip**（層 C 不要な場合あり） |

grace 時間は job ごとに [05_検証計画.md](./05_検証計画.md) 実施時に log から確定する（本書では数値固定しない）。

## 6. 相関キー

突合に使うキー（最小限）:

- `planningDate`, `supervisorRunId`
- `jobKey`, `idempotencyKey`, `plannedRunAt`
- `runId`, `staffId`, `paymentPeriodKey`（給与）
- `tournamentId`, `taskType`, `planHash`（tournament）

---

## 7. 検知（本タスクのスコープ）

### やる

- Logs Explorer 用クエリ草案（functionEntry + eventType + context キー）
- 日次確認手順: supervisor 実行日の翌朝、enabled job ごとに層 B → C を確認
- `.cursor/rules` 更新案

### やらない（別 ChangeSpec / 別タスク）

- Cloud Monitoring アラートポリシーの本番作成
- 自動 replay Callable
- Firestore stuck 状態監視

## 9. 12 との関係（再掲）

給与通知（`processPayrollNotifications`）は層 C の対象として **他 job と同様に** start → 完了を確認する。  
通知テンプレート・triggerType・採用可否は `12` で扱い、本書の検知方針からは除外しない。
