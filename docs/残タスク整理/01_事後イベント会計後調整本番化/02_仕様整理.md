# 仕様整理

## ほぼ確定でよい仕様

### 1. `bills` を SoT とし続ける

既存 docs でも、今回の会計後調整は `bills` を中心に派生させる前提で整理されています。  
ここはぶらさず、`settlementCycles`、`baselineSnapshot`、`adjustments`、`cashActions` の責務分担を維持するのが自然です。

### 2. `analyticsMonthly` は税務 ledger の代替ではない

現行 docs でも `analyticsMonthly` は運用ダッシュボード用途寄りです。  
税務・会計の正式説明責任まで担わせるのは不自然なので、税務用 read model が必要なら別に持つ前提で考えるべきです。

### 3. 会計後調整の業務フローは「要対応一覧」中心でよい

現行実装と docs は、`要対応の会計` 画面を中心導線に寄せています。  
UI 導線をここへ寄せる方針は妥当です。

### 4. 税務・会計上の3軸は分けて考えるべき

既存 docs どおり、少なくとも次は概念上分けて残す前提が妥当です。

- 売上発生日
- adjustment 確定日
- cashflow 実行日

## ユーザー判断が必要な仕様

### 1. 税務・会計データの保存レベル

選択肢は大きく3つです。

1. **最小対応**  
   今回は `bills` とその subcollection を正式 SoT とし、税務 read model は後続で派生させる。
2. **中間対応**  
   `reportingEntries` だけ先に導入し、月次集計系は後続に回す。
3. **フル対応**  
   `reportingEntries` / `reportingMonthly` / `cashflowMonthly` まで今回まとめて整備する。

判断材料:

- 早く本番化したいなら 1 が有利
- 税理士説明や月次確認まで早めに固めたいなら 2 以上が有利
- 実装コストと検証量は 3 が最も重い

### 2. このタスクを「税務方針未確定でも出してよいか」

選択肢:

1. **会計後運用が回るなら先に出す**
2. **最低限の税務データ保持まで終えてから出す**

この判断は、アプリとしての納品優先なのか、監査説明まで今回で固めたいのかで変わります。

### 3. 旧経路をどう扱うか

選択肢:

1. **新経路確認後すぐ廃止**
2. **一定期間だけ併存**
3. **当面残すが非推奨扱いにする**

おすすめは 2 です。  
急に消すより、安全確認後に撤去時期を切る方が事故を減らせます。

### 4. 本番前の確認範囲

最低でも次は含めた方が良いです。

- carryover bill の再会計
- 追加徴収
- 要返金
- reopen 後の再会計
- analytics rollback
- 要対応一覧での表示更新

ここをどこまで「完了条件」に入れるかは、ユーザー判断が必要です。
