# やること整理

## 最優先でやること

1. current-scope で既に実装済みの範囲を正式に確定する  
   「どこまでが今回の本番対象で、どこから先は future か」を固定しないと、完了条件がぶれます。
2. 税務・会計用データ保持の最低ラインを決める  
   `bills` から将来派生できればよいのか、今の時点で `reportingEntries` 相当まで持つのかを決める必要があります。
3. 実機・実運用シナリオでの最終確認を終える  
   reopen 後の再会計、後続徴収、後続返金、要対応一覧、analytics rollback を実環境想定で確認する必要があります。
4. 旧経路の扱いを決める  
   旧 dialog・旧 callable を残したままにするのか、廃止時期を切るのかを決める必要があります。

## 追加で発生している実務タスク

- `firestore.rules` を本番前提で見直すか判断する
- `firestore.indexes.json` の必要 index を最終確認する
- 実機確認 docs の結果欄を埋める
- analytics 関連の障害時リカバリ手順を整える
- commit 前の未整理差分を整頓する

## ユーザーが未記載だが実際には必要なタスク

- **完了条件の明文化**  
  「UI が動く」ではなく、「運用・監査・説明責任まで含めて何を満たせば本番化完了か」を決める必要があります。
- **データ移行や既存 bill への影響確認**  
  新フィールドや親 doc summary を前提にするなら、既存データで欠損が起きたときの扱い確認が必要です。
- **会計責任者向けの運用手順書**  
  現場担当者が追加徴収・返金・reopen をどう使い分けるかの簡易運用書が必要です。
- **障害時の手戻り方針**  
  間違った後続徴収・返金を行った場合の是正フローを明文化する必要があります。

## 完了の定義

次がそろえば、このタスクは「本番化完了」にかなり近いと言えます。

- 今回スコープと future スコープの線引きが固定されている
- 税務・会計用データ保持方針が決まっている
- 要対応一覧からの `collection` / `refund` / `reopen` が実機で確認済み
- 旧経路の残置方針が決まっている
- rules / indexes / 運用確認の残件が洗えている
