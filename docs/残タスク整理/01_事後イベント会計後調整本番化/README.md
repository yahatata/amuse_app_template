# 事後イベント会計後調整本番化

## このタスクの要点

会計後に追加徴収や返金が必要になったときの業務フローは、現行コード上かなり進んでいます。  
ただし「本番化完了」と言い切るには、税務処理用データの残し方と、実運用での確認範囲をまだ詰める必要があります。

## 現状整理

- 仕様書はかなり豊富です。
- UI・callable・trigger・analytics 関連の実装差分も多く存在します。
- 会計後の `collection` / `refund` / `reopen` 系はテストも存在します。
- 一方で docs 側に「strict な税務・会計 read model は current-scope 外」と明記されています。

## いま言える状態評価

- 仕様整理: かなり進んでいる
- アプリ実装: 大部分あり
- テスト裏付け: かなりある
- 本番完了判定: まだ不可
- 最大の未決点: 税務・会計のために何を正式保存対象とするか

## 根拠として強い事実

- `docs/事後イベント（会計後調整系）本番化/...` に current-scope の設計と実装サマリが大量にある
- `docs/.../05_今後検討_税務会計read_model拡張.md` に、税務・会計用 read model が future 扱いとして切り分けられている
- `docs/.../04_改修対象外と後続事項.md` に、旧経路撤去や rules 強化が後続扱いと明記されている
- `test/Accounting/...` と `functions/__tests__/callables/...` に代表テストがある

## このタスクで本当に決めるべきこと

このタスクの本質は「追加徴収・返金の UI を作ること」ではありません。  
本質は次の2つです。

1. 店舗運用上、会計後の差額処理を安全に回せること
2. 将来の税務・会計説明責任に耐える形でデータを残すこと

- 次に `02_仕様整理.md` で、今すぐ決められる仕様と、ユーザー判断が必要な仕様を分けて確認する
