## Firestore rules の方針

```
// reportingEntries
// 書き込み: Cloud Functions のみ（クライアントからの直接書き込み禁止）
// 読み取り: 将来的に admin UI から参照可能にするが、現時点は Functions のみ

match /reportingEntries/{entryId} {
  allow read, write: if false;  // クライアント禁止（Functions の Admin SDK は rules をバイパスする）
}

match /reportingMonthly/{monthKey} {
  allow read, write: if false;
}

match /reportingMonthly/{monthKey}/aggregationMarkers/{markerId} {
  allow read, write: if false;
}
```

---

## Firestore indexes の方針

クエリパターンに応じて以下を検討する（実装後に実際に必要なものを追加）。

| クエリ | インデックス |
|---|---|
| `reportingEntries` を `billId` で検索 | `billId ASC, eventAt DESC` |
| `reportingEntries` を `reportingMonth` で検索 | `reportingMonth ASC, eventAt ASC` |

## staging デプロイと実機確認（必須）★

### デプロイ手順

```bash
# Functions のみデプロイ
firebase deploy --only functions --project {staging-project-id}

# rules と indexes もデプロイ
firebase deploy --only firestore:rules,firestore:indexes --project {staging-project-id}
```

### 実機確認シナリオ（全統合の最終確認）

staging 環境で `reportingAggregatorEnabled = true` に設定した上で以下を確認する。

| # | シナリオ | 確認内容 |
|---|---|---|
| 1 | 通常会計 | `{billId}_settle_1` が作成されるか |
| 2 | carryover（翌日以降会計） | `originBusinessDate` が入店日、`reportingMonth` が会計した月になっているか |
| 3 | 即時返金 adjustment | `{billId}_cashAction_{id}` が作成されるか（pending では作成されないか） |
| 4 | 後続徴収 cashAction | `{billId}_cashAction_{id}` が作成されるか |
| 5 | reopen | `{billId}_reopen_1` が負値で作成されるか |
| 6 | resettle（再会計） | `{billId}_resettle_2` が作成されるか |
| 7 | `reportingMonthly` 整合性 | 上記シナリオ後の月次集計が全エントリの合算と一致しているか |
| 8 | 冪等性（全シナリオ） | 同一操作を2回実行しても重複しないか |
| 9 | `analyticsMonthly` 共存 | analytics 側の動作が変わっていないか |
