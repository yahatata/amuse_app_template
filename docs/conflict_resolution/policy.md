# コンフリクト解消 行動指針

_最終更新: 2025-12-23 (JST)_

## 基本方針

### 最優先原則
**安全性を最優先**。会計・冪等・集計などの不整合を絶対に避ける。

### 実装ルール
- **ファイル単位で進める**: userに指定されたファイルのみを解消し、完了確認してから次へ
- **推測で決めない**: 既存の挙動を推測して勝手に決めない

## 独断解消の判断基準

### 独断解消OK条件（意味が変わらない変更）

**基本原則**: "書き込みの有無"ではなく、"意味（セマンティクス）が不変"であることを条件とする。

以下の**不変条件をすべて満たす**場合のみ、独断で解消可能：

#### 必須不変条件（最低限）
1. **書き込み先不変**
   - コレクション/ドキュメント/サブコレクションの書き込み先が不変
   - 例: `bills/{billId}` → `bills/{billId}` はOK、`bills/{billId}` → `todaysBills/{billId}` はNG

2. **更新フィールド不変**
   - 更新するフィールド名と型が不変
   - 例: `amounts.grandTotalRounded` の更新が不変はOK、`amounts.grandTotalRounded` → `amounts.totalPrice` はNG

3. **条件分岐不変**
   - いつ書き込むかの条件（if文、ガード条件）が不変
   - 例: `status === 'settled'` の条件が不変はOK、条件の追加・削除はNG

4. **トランザクション境界・バッチ単位不変**
   - トランザクションの範囲が不変
   - バッチ書き込みの単位が不変

5. **idempotencyKey / eventId の生成と使用不変**
   - 生成方法（形式・入力値）が不変
   - 使用箇所（保存先・チェック方法）が不変

6. **businessDate / updatedAt の決め方・更新タイミング不変**
   - businessDateの決定ロジック（`calcBusinessDate`の呼び出し・引数）が不変
   - updatedAtの更新タイミング（冪等リプレイ時の扱い）が不変

7. **paymentsSummary / postEvents / analytics の更新ロジック不変**
   - 金額計算式が不変
   - 集計処理の順序・方法が不変

8. **callable の request/response shape とエラーコード互換性不変**
   - リクエストパラメータの型・必須性が不変
   - レスポンスの型・構造が不変
   - エラーコードの値・意味が不変

#### Cursorに任せる安全観点（追加で独断OK）
以下の変更は、上記の必須不変条件を満たす限り、Cursorが独断で解消可能：

1. **import順・未使用import削除・lint/format（意味不変の範囲）**
   - 理由: 実行時の意味に影響しない静的解析レベルの変更

2. **型注釈の追加や型の明確化（実行時意味不変の範囲）**
   - 理由: 型安全性向上のみで、実行時の挙動は不変

3. **ログ文言の変更/追加（PIIや運用影響に注意、ログ削除は独断NG）**
   - 理由: デバッグ支援のための変更で、実行ロジックに影響しない
   - 注意: 個人情報（PII）を含むログ追加はNG、既存ログの削除はNG

4. **エラーメッセージの文言修正（エラーコード/型は不変）**
   - 理由: エラーメッセージの可読性向上のみで、エラーコードや型は不変

5. **リネーム（変数名/関数内ローカル）で挙動不変が明確なもの**
   - 理由: スコープが限定的で、外部への影響がない

6. **定数化（magic number→const）で意味不変が明確なもの**
   - 理由: 値が同一で、可読性向上のみの変更

#### 原則NG-A（選択肢提示が必要）に移した項目
以下の項目は事故りやすいため、**原則としてNG-A（選択肢提示）**とする：

7. **nullガード/early return の追加**
   - **原則**: NG-A（選択肢提示が必要）
   - **例外（極めて狭い条件で独断OK）**: 以下の**すべて**を満たす場合のみ独断OK
     - 既存の分岐と論理的に等価であることを、コード上で示せる（重複ガードの整理に近い）
     - そのブロックに Firestore書き込み・イベント作成・集計更新などの副作用が存在しない
     - callableの返却shape/エラーコードに影響しない
   - **理由**: 既存の挙動を変更する可能性があり、安全性を優先するため

8. **冗長コードの削除**
   - **原則**: NG-A（選択肢提示が必要）
   - **例外（極めて狭い条件で独断OK）**: 以下の**すべて**を満たす場合のみ独断OK
     - tsc/ESLint等で unreachable が明示される、または repo 検索で参照が0であることが確認できる
     - 削除対象が export/public API ではない
     - 仕様・運用上のスイッチ（フラグ）で将来使う可能性がないと判断できる根拠がある
   - **理由**: 将来使用される可能性や、仕様上の意図がある可能性があり、安全性を優先するため

### 独断解消NG条件

必須不変条件のいずれかに違反する場合は、独断解消NG。以下の2段階に分類する：

#### NG-A: 選択肢提示で済む（2〜4案に絞れる）
以下の場合は、**選択肢を2〜4案に絞って提示し、人間の判断を待つ**：

1. **書き込み先の変更**
   - 例: `bills` → `todaysBills` への移行、サブコレクションの追加・削除

2. **更新フィールドの変更**
   - 例: フィールド名の変更、新規フィールドの追加

3. **条件分岐の変更**
   - 例: ガード条件の追加・削除、分岐ロジックの変更

4. **idempotencyKey / eventId の生成方法変更**
   - 例: 生成形式の変更、入力値の変更

5. **callable の request/response shape の変更**
   - 例: 必須パラメータの追加・削除、レスポンス構造の変更

6. **エラーコードの変更**
   - 例: エラーコード値の変更、新規エラーコードの追加

7. **nullガード/early return の追加（原則NG-A）**
   - 理由: 既存の挙動を変更する可能性があり、安全性を優先するため
   - 例外: 上記「原則NG-Aに移した項目」の例外条件を満たす場合のみ独断OK

8. **冗長コードの削除（原則NG-A）**
   - 理由: 将来使用される可能性や、仕様上の意図がある可能性があり、安全性を優先するため
   - 例外: 上記「原則NG-Aに移した項目」の例外条件を満たす場合のみ独断OK

#### NG-B: 仕様決定が必須（判断不能として人間に委ねる）
以下の場合は、**明確に「判断不能」と記録し、人間に委ねる**：

1. **両方の変更が重要で、統合方法が不明確**
2. **既存の挙動が不明で、推測が必要**
3. **影響範囲が広く、安全に統合できない**
4. **テストが不足しており、動作確認できない**
5. **必須不変条件の複数が同時に違反している**
6. **選択肢が5案以上になり、絞り込めない**

### 判断不能時の情報テンプレ

判断不能と判断した場合は、以下の情報を `log.md` に記録し、人間が判断できるようにする：

```markdown
## 判断不能: [ファイルパス]

### コンフリクト箇所
[コンフリクトが発生している行番号と内容の要約]

### 関連仕様書
- [docs/bills_migration/* の該当ドキュメント]
- [API契約書の該当セクション]

### 呼び出し元
- **Flutter**: [呼び出し元ファイル/画面]
- **Functions**: [呼び出し元callable/helper]

### 期待するデータ不変条件
- **SSoT**: [bills/todaysBills の扱い]
- **DualWrite**: [DualWriteの有無/条件]
- **冪等性**: [idempotencyKeyの扱い]

### 既存テスト
- [テストファイルの有無]
- [テストカバレッジの状況]

### 必要テスト案
- [追加すべきテストケース]

### 不明点・懸念事項
- [判断を妨げている不明点]
- [統合時の懸念事項]
```

## 選択肢提示のフォーマット

選択肢を提示する際は、以下の形式で記載する：

```markdown
## ファイル名: [ファイルパス]

### コンフリクト箇所
[コンフリクトが発生している行番号と内容の要約]

### 選択肢

#### 選択肢A: [選択肢名]
- **内容**: [具体的な変更内容]
- **メリット**: 
  - [メリット1]
  - [メリット2]
- **デメリット**: 
  - [デメリット1]
  - [デメリット2]
- **影響範囲**: 
  - [影響を受けるファイル/機能]
- **リスク**: [高/中/低] - [理由]

#### 選択肢B: [選択肢名]
[同様の形式]

### 推奨
[推奨する選択肢と理由]

### 確認事項
[人間が判断する際に確認すべき事項]
```

## 各ファイル処理後のログ項目

各ファイルのコンフリクト解消後は、以下の手順を実行する：

### 必須手順
1. **git add**: コンフリクト解消後は**必ず** `git add <ファイルパス>` を実行する
   - コンフリクト解消の完了をGitに通知するため
   - この手順を省略すると、Gitがコンフリクトが解消されたことを認識しない

### ログ記録項目
以下の項目を `log.md` に記録する：

1. **日時**: 解消日時（YYYY-MM-DD HH:MM:SS）
2. **対象ファイル**: ファイルパス
3. **判断方法**: 独断解消 / 選択肢提示 / 判断不能
4. **選択内容**: 採用した選択肢（選択肢提示の場合）
5. **変更内容**: 具体的に何を変更したか
6. **影響範囲**: 影響を受けるファイル/機能
7. **テスト結果**: tsc / jest の実行結果
8. **備考**: その他注意事項

## 検証タイミング

### 各ファイル解消後
- `tsc --noEmit` でTypeScriptの型チェック
- 該当ファイルのテストがあれば実行（`jest [ファイル名]`）

### フェーズ完了後
- `jest` で全テスト実行
- `tsc --noEmit` で全ファイルの型チェック

### 全ファイル解消後
- `jest` で全テスト実行
- `tsc --noEmit` で全ファイルの型チェック
- 手動テストの実施（必要に応じて）

## プロジェクト方針（解消判断の基準）

### SSoT（Single Source of Truth）
- **正本**: `/bills` コレクション
- **todaysBills**: 最小デュアルライト（フラグがある場合のみ、no-op保証を崩さない）

### updatedAt
- **更新主体**: Functions 専任
- **冪等リプレイ**: updatedAt を更新しない

### businessDate
- **決定主体**: Functions（`calcBusinessDate` で確定）
- **クライアント**: 提案値のみ送信

### events.eventId
- **形式**: idempotencyKey を使用
- **重複適用**: no-op（既存イベントは無視）

### 整合性保証
- `paymentsSummary` / `postEvents` / `analytics` 等の整合性を壊さない
- callable の request/response 形式やエラーコード互換性を壊さない（Flutter/LIFF 側に影響）

## 注意事項

- 各ファイルのコンフリクト内容は、実際のファイルを確認してから判断する
- 判断不能な場合は、明確に「判断不能」と記録し、人間に委ねる
- 独断解消OK条件を満たす場合でも、疑わしい場合は選択肢提示を優先する
