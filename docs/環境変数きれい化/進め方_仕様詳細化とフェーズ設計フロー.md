## このドキュメントの目的

`仕様書/tobe仕様書_全体像.md` を起点に、どの順番で仕様を詳細化し、実装前準備を進めるかを明確にする。

- `monthlyPayrollTrigger` は削除する（手動給与計算運用へ統一）。
- 詳細仕様確定後、フェーズは依存順で再設計する。
- 以後のフェーズ構成は `tobe仕様書_全体像.md` の最新記載を正とする。
- 進め方は、既存提案に追加推奨項目を加えた運用で進める。

## これからの進め方（確定版）

1. 詳細仕様を直接実装し始めるのではなく、まずフェーズ単位に再整理する。
2. フェーズは「仕様カテゴリ」ではなく「安全に実装できる依存順」で設計する。
3. 各フェーズで `changeSpec` を作成し、そのフェーズで扱う詳細仕様の章を対応付ける。
4. `changeSpec` ごとに、コード変更と GCP / GitHub / Firebase Console 上の人手作業を分離して記載する。
5. 各フェーズ完了時に、サマリ・未解決事項・次フェーズへの伝達事項を残す。
6. 各フェーズを開始する際は、**必ず下記「各フェーズで実施する標準ステップ（確定）」を参照する**。
7. 各フェーズの `changeSpec`・実装・テスト・運用資料作成は、上記標準ステップに従って進める。

## 各フェーズで実施する標準ステップ（確定）

1. As-Isコードと直近修正の確認
2. 当該フェーズの `changeSpec` 作成
3. 必要テストの検討（`changeSpec` にどのようなテストを行うか明記する）
4. ユーザーへ `changeSpec` のレビュー依頼を行う（この `changeSpec` で実装を進めてよいか確認する）
5. ユーザーから実装に進んでよい旨の承認を得た後、実装を行う  
   補足: 必要に応じてユーザー依頼が必要な GCP 操作を明文化して依頼し、テストファイルも作成する
6. テスト実行
7. テスト結果を出力し、実機で確認すべきことがあればここで明確にユーザーへ依頼する
8. ユーザーから承認が得られたら、主に設定等に関して運用時資料の作成の必要がないか検討し、必要があれば資料を作成する
9. サマリ作成と引き継ぎ事項の記録

## 追加推奨項目（採用）

- 各フェーズに `Entry条件` / `Exit条件` / `ロールバック条件` を定義する。
- GCPコンソール作業が必要なフェーズは、依頼テンプレート（目的・操作手順・確認項目）を事前に用意する。
- 各 `changeSpec` で「対象仕様章」「対象ファイル」「外部操作」「テスト」「ロールバック」を明記する。
