## 1. この文書の役割

本書は、旧方針で作成したカテゴリ別資料群を、
「残タスクの作業管理資料」と「今後も参照し続ける正式資料」に分け直すための方針正本である。

本書で固定すること:

- 再編の目的
- 新方針の設計原則
- 正式資料とタスク資料の役割分担
- ID 体系と命名方針
- 目指すフォルダ構成
- 現時点で想定する正式資料の一覧
- 既存資料ごとの扱い、影響、修正要否
- 再編作業の進め方

本書で固定しないこと:

- 各 workbook の最終列定義
- 各 `TSK` の細粒度な作業分割
- 店舗ごとの実行インスタンスの最終保存場所
- 各実行タスクの個別手順やコマンド
- カテゴリ A の現行管理方法

本書は「何をどう再編するか」の正本であり、
個別タスクの実施内容や個別資料の詳細は、後続の `TSK` と `ART` に委ねる。

## 2. 背景と再編が必要な理由

旧方針では、カテゴリ B〜I の工程整理を主目的として、
`検討時叩き2.md` をカテゴリごとに配置し、
一部の作業中資料もカテゴリフォルダ直下に置いていた。

この構成で見えてきた問題は次の通り。

- タスク管理用の資料と、導入後も参照し続ける正式資料が同じ場所に混在している
- カテゴリ記号が正式資料名に残り、資料の性質ではなく旧検討経路が名前に残る
- `B-1_Config台帳_進め方.md` のように再利用価値が高い資料と、`検討時叩き2.md` のような参照用資料の区別が弱い
- `00_資料台帳` は正式資料を管理する想定だが、旧方針のカテゴリ設計の影響を受けている
- `統合ワークブック` の位置づけが未整理なままだと、定義正本と確認記録が混ざりやすい
- repository 上では現時点で `xlsx` 正本が確認できず、説明資料だけが先行しているものが多い

そのため、新方針では次を明確に分ける。

- 作業を進めるための `TSK`
- 今後も参照・更新する正式資料 `ART`
- 個別対象を識別する `FN / CFG / FLOW / TEST / DEF`

## 3. 再編で固定する設計原則

### 3.1 正式資料とタスク資料を分ける

- `docs/残タスク_0623` は、残タスクの作業管理資料を置く場所とする
- `docs/業務管理資料` は、今後も参照・更新し続ける正式資料を置く場所とする
- 旧カテゴリ名は、正式資料名には残さず、必要なら移行履歴や備考で保持する

### 3.2 正式資料の ID は `ART-xxx` に統一する

- `md` 正本も `sheet` 正本も、正式資料はすべて `ART-xxx` を使う
- `sheet` 正本と説明用 `md` は同じ `ART-xxx` を共有する
- `DOC-xxx` は今後の正式資料命名では使わない

### 3.3 タスクは `TSK-xxx` で管理する

- 残タスク側の単位は `TSK-xxx` とする
- 各 `TSK` は少なくとも `内容` と `進め方` を持つ
- `実施まとめ` と `申し送り` は必要時のみ作成する
- `進め方.md` は原則として `TSK` 側に置き、`ART` 側には成果物を読むための `説明.md` を置く

### 3.4 定義正本と確認テンプレを分ける

- `ART-101 / 102 / 103 / 104` は「何であるべきか」を定義する正本
- `ART-201` は「実際にどう確認し、どうだったか」を残す確認実行テンプレ
- `ART-201` に新しい仕様定義を生やさない

### 3.5 行を増減させず、意味を列で表現する

- 実機テストや gate 確認の項目は、原則として固定行で持つ
- 設定差分は `実行要否` `適用状態` `期待状態` `非適用理由` `結果` `判定` で表現する
- 非有効化された機能も、原則として「無効時の期待挙動」を持つ

### 3.6 数式だけを真実にしない

- `統合ワークブック` のロジックは数式で実装してよい
- ただし、どの入力が何に効くかの原理は説明資料にも残す
- 派生ルールを独立資料にしない代わりに、説明資料で構造を説明可能にする

### 3.7 GitHub Issue は前提にしない

- 現時点では GitHub Issue 管理を前提にしない
- その代わり、確認シート内に `NG有無` `NG理由` `対応状態` `再確認要否` `関連メモ` を持たせる

### 3.8 done は資料完成だけにしない

- 資料作成を中心に据えるタスクは増える
- ただし done は `資料完成 + 実確認 + 必要修正 + 資料反映` とする
- 実行が必要なタスクを、資料作成だけで閉じない

## 4. 新方針での資料体系

### 4.1 正式資料

正式資料は `ART-xxx` とし、次の区分で持つ。

| 区分 | 役割 |
|---|---|
| 共通資料 | 全体ルール、用語、正式資料台帳 |
| 実装定義台帳 | config、function、業務フロー、外部設定の定義正本 |
| 確認実行テンプレ | テンプレアプリ検証と導入時確認の実行テンプレ |
| 導入手順書 | 第2店舗以降の導入再現性を支える手順正本 |
| 後続資料 | 運用資料、技術資料、営業資料、契約資料など |

### 4.2 タスク資料

タスク資料は `TSK-xxx` とし、次の役割を持つ。

| ファイル | 役割 |
|---|---|
| `TSK-xxx_内容.md` | そのタスクで何を扱うかを定める |
| `TSK-xxx_進め方.md` | どの順で、何を根拠に、どう進めるかを定める |
| `TSK-xxx_実施まとめ.md` | 実際に何をやったかを残す |
| `TSK-xxx_申し送り.md` | 他タスクへ返す論点や依存を残す |

原則:

- すべての予定タスクに空の `実施まとめ` を先置きしない
- `申し送り` は必要時のみ作成する
- `TSK` は `ART` の作成・更新・確認・修正を進めるために存在する

## 6. 統合ワークブックの位置づけ

`ART-201` は、次の役割だけを持つ。

- `ART-101` を元に config 条件を受け取る
- `ART-104` を元に外部設定条件を受け取る
- `ART-102` を元に function 挙動確認を行う
- `ART-103` を元に業務フロー確認を行う
- 全体の go / no-go をまとめる

`ART-201` の基本シート構成は次を想定する。

| シート | 役割 |
|---|---|
| `Config入力` | 採用する config 値を入力する |
| `外部設定入力` | 外部設定の方式、確認状態、必要条件を入力する |
| `期待値計算` | 検証プロファイル、期待状態、実行要否などを計算する |
| `Gateチェック` | rules / auth / secret / env / scheduler / debug 残存などを横断確認する |
| `Function挙動確認` | 主要 function の期待挙動を確認する |
| `実機テスト` | 画面・端末・認証・外部連携など実機必須項目を確認する |
| `業務フロー確認` | 業務フロー単位の受入確認を行う |
| `判定サマリ` | NG 数、保留数、再確認要否をまとめる |

固定原則:

- `同一設定` ではなく `同一検証プロファイル` を使う
- 行は増減させず、列で意味を表現する
- 数式だけを真実にしない
- GitHub Issue は前提にしない

## 7. 資料作成だけでは終わらないタスクの扱い

旧方針では、資料作成以外の実行タスクがカテゴリ B / D / F / I に散っていた。  
新方針では、これらを「資料中心の実行タスク」として再配置する。

### 7.1 `scheduler / queue / log / central write`

- 構造整理は `ART-102_Function台帳` 側の別シートへ寄せる
- 実確認結果は `ART-201` の `Gateチェック` で持つ
- これにより、定義正本と実行記録を分ける

### 7.2 `rules / auth / secret / 固定値`

- `Secret / IAM / env / LINE / LIFF` は `ART-104` で扱う
- `rules / auth / 固定値 / debug route / placeholder` は `ART-201` の `Gateチェック` で扱う
- したがって、旧 `B-3` をそのまま単独カテゴリ的に残さない

### 7.3 `D-3 実行と記録`

- 新方針では `ART-201` によるテンプレアプリ検証実行へ再配置する
- 旧 `D-4` の修正ループは、`TSK-202` 系の差分修正・再確認タスクへ吸収する

### 7.4 `F` 以降の実設定

- `F` 以降の実設定・疎通確認は、引き続き実行タスクとして持つ
- ただし定義正本と切り離し、`ART-104` と導入手順書を前提に進める

## 13. 再編作業の進め方

再編自体は、次の順で進める。

1. `ART-900_全体再編方針.md` を作成し、再編の正本を先に固定する
2. 旧共通資料 `00` `01` `02` と repository guidance `AGENTS.md` `.cursor/rules/document-lifecycle-rules.mdc` を、現行 path のまま新方針へ整合させる
3. `共通` フォルダに再編基盤資料の枠を作る
4. `ART-902_タスク管理台帳` の列設計を行う
5. 旧資料を `残す / 再利用 / 参照用化 / アーカイブ候補` に分類する
6. `TSK-101` `102` `103` `104` `201` の `内容` と `進め方` を暫定作成する
7. `ART-001` `ART-002` `ART-003` の実ファイル移設または改名の段階で、`AGENTS.md` と Cursor rules の参照 path を再度更新する
8. A 完了待ちの並走作業として、後続資料の骨格だけ整える
9. A 完了後に workbook 実体、検証実行、差分修正、資料反映へ進む

原則:

- 先に方針を固定し、あとで個別資料を作る
- 個別資料の中身は、この時点で過度に固定しない
- 構造変更と内容投入を同時に進めない
