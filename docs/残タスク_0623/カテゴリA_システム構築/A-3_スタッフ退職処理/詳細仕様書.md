## 3. 退職の業務定義

退職とは、店舗側が当該スタッフを今後の **スタッフ本人操作対象・現役運用対象から外す** 状態を指す。

- 厳密な雇用関係の法的終了そのものではない
- システム上の現役スタッフ運用から外す処理として扱う

退職理由・経緯の例:

- 本人申告 / 音信不通 / 無断欠勤 / 店舗判断 / 他スタッフ経由の連絡 / 管理者誤操作

---

## 4. 状態管理方式

### 4-1. 方針

退職者を別コレクションへ移動しない。`staffs/{staffId}` を残し、`staffs.status` で管理する。

### 4-2. status 定義（初期実装）

```ts
status: "active" | "retired"
```

### 4-3. 初期実装で採用しない status

- `retirement_scheduled`
- 退職予定日到来 scheduler
- 退職予定者状態・退職予定者UI

### 4-4. 既存データの補正

既存 `staffs` ドキュメントには、マイグレーションまたは初期補正で `status: "active"` を付与する。

**要確認（C-04）**: マイグレーションの実行タイミング（デプロイ前バッチ / 初回参照時 lazy 補正）は changeSpec で確定する。

---

## 5. 退職処理タイミング

**即日停止方式** とする。

管理者が退職処理を実行した時点で `status` を `retired` に変更する。

退職処理後、対象スタッフは以下の対象外となる。

- スタッフ本人操作
- 未来勤務
- 新規勤怠発生
- QR生成

## 6. 退職処理時の保存フィールド

退職処理時に `staffs/{staffId}` へ保存・更新するフィールド:

```ts
staffs/{staffId}: {
  status: "retired",
  retiredAt: Timestamp,      // 退職処理実行日時
  retiredDate: "YYYY-MM-DD", // 業務上の退職日（JST暦日）
  retiredReason: string | null,
  updatedAt: Timestamp
}
```

| フィールド | 内容 |
|-----------|------|
| `status` | `active` / `retired` の正本 |
| `retiredAt` | システム上で退職処理を実行した日時 |
| `retiredDate` | 業務上の退職日 |
| `retiredReason` | 任意の退職理由・メモ |
| `updatedAt` | staff ドキュメントの最終更新日時 |

### `retiredDate` の扱い

- 形式: JST 暦日 `YYYY-MM-DD`
- 初期値: Functions 側で算出した JST 当日
- 管理者が退職処理 UI で変更可能（必須入力）

### 初期実装では保存しないフィールド

```ts
retiredByDeviceId
retiredByDeviceName
retiredByUid
retirementScheduledAt
retirementEffectiveDate
```

## 7. 退職時に保持・削除するスタッフ情報

### 7-1. 保持するフィールド

```text
uid / docId
status
retiredAt
retiredDate
retiredReason
updatedAt
createdAt
fullName
fullNameKana
hourlyWage
bankInfo
```

| フィールド | 保持理由 |
|-----------|----------|
| `uid / docId` | 同一LINE識別、再登録検出、履歴紐付け |
| `fullName / fullNameKana` | 退職後の管理者表示、勤怠・給与・履歴確認 |
| `hourlyWage` | 最終給与計算、再計算、差額確認の可能性 |
| `bankInfo` | 最終給与支払い、支払い確認、問い合わせ対応の可能性 |
| 退職情報・日時 | 退職情報の確認 |
| `createdAt / updatedAt` | 管理・整合性確認 |

`hourlyWage` / `bankInfo` は退職時も給与支払い完了後も **A-3 初期実装では削除しない**。  
将来の削除・マスクは [後続検討事項](../../後続検討事項/退職者・利用者情報の保持期間と削除方針.md) で扱う。

### 7-2. 削除・クリアするフィールド

```text
email
phoneNumber
birthMonthDay
loginId
qrCodeUrl
qrExpiresAt
qrExpiresAtMs   // 存在する場合
StaffName
StaffFullName
StaffFullNameKana  // 存在し未使用であれば対象
```

`StaffName` / `StaffFullName` 等は管理者端末作成時のみ保存され、LINEミニアプリ登録を正とする運用では正本ではないため、退職時の削除・クリア候補とする。

### 7-3. クリア方法

- Firestore 上は `FieldValue.delete()` または `null` 代入のいずれかを changeSpec で統一
- QR Storage 上の画像ファイル削除は **初期実装の必須要件としない**（doc フィールドのクリアを優先）

## 8. LINEミニアプリ登録を正とする方針

### 8-1. 本流

リリース時の本流は、スタッフ本人が **LINEミニアプリ（スタッフLIFF）** から登録する方式とする。

管理者端末からの `createStaffByApp` は、テスト・確認・開発用の **補助経路** とする。

### 8-2. LINE 登録スタッフの ID 関係

```text
LINE userId 相当
= Firebase Auth uid
= staffs/{staffId}
```

現行実装では明示的な `lineUserId` フィールドはなく、`staffs/{auth.uid}` が同一LINEアカウントの staff doc として扱われる。

同一 UID で `users/{uid}` と `staffs/{uid}` が共存し得る。

### 8-3. 補助経路（`createStaffByApp`）の注意

- Auth uid は LINE uid と一致しない（サーバーで `createUser` したランダム uid）
- リッチメニュー・再登録フローは LINE 本流と異なる可能性がある
- **要確認（C-01）**: 補助経路スタッフの退職・再登録の運用方針

退職処理・再登録・個人情報削除/保持の判断は、原則として **LINEミニアプリ登録スタッフ** を基準に行う。

## 9. 退職者本人操作の制御

退職済みスタッフ本人は、スタッフ向け本人操作を利用できない。

### 9-1. 退職後に不可とする操作

| カテゴリ | 操作 |
|---------|------|
| LIFF | スタッフLIFF通常画面の利用 |
| QR | QR生成 |
| 勤怠 | 新規出勤・退勤・休憩開始・休憩終了・QR勤怠確定 |
| シフト | シフト申請・シフト修正 |
| 募集 | 募集応募・募集要請承諾 |
| 勤怠修正 | 勤怠修正申請 |
| プロフィール | プロフィール編集 |

### 9-2. 例外

同一LINEアカウントによる **再登録導線** のみ提供する（§16 参照）。

### 9-3. 制御レイヤー

| レイヤー | 内容 |
|---------|------|
| スタッフLIFF入口 | `staffs/{auth.uid}.status === "retired"` の場合、通常画面ではなく再登録画面へ分岐 |
| Callable / API | スタッフ本人操作系で `active` チェックを追加し、`retired` は拒否 |
| `getFirebaseCustomToken` | **retired ブロックを行わない**（ユーザーLIFF利用を止めないため） |

### 9-4. エラー方針

- エラーキー・メッセージは changeSpec で統一（例: `STAFF_RETIRED`）
- 利用者向けには「退職済みのため利用できません」等の分かりやすい文言

## 10. QR・勤怠発生の制御

### 10-1. 既存QRの即時無効化

**初期実装の必須要件としない。**

理由: 既存QRには有効期限があり、退職後のQR再生成を止めれば実務上のリスクを抑えられる。

退職時は doc 上の QR 関連フィールドをクリアするが、過去に発行済みのQR画像・有効期限内のQRが即時無効になる保証は初期実装では設けない。

### 10-2. active チェック必須の Callable

以下には必ず **active staff** チェックを入れる。

| Callable | 備考 |
|----------|------|
| `generateQRCode`（`type=staff`） | `functions/src/domains/user/callables/generateQRCode.ts` |
| `clockIn` | `functions/src/domains/attendance/callables/clockIn.ts` |
| `clockOut` | `functions/src/domains/attendance/callables/clockOut.ts` |
| `startBreak` | `functions/src/domains/attendance/callables/startBreak.ts` |
| `endBreak` | `functions/src/domains/attendance/callables/endBreak.ts` |
| `createManualClockInRecord` | `functions/src/domains/attendance/callables/createManualClockInRecord.ts` |

**要確認（C-05）**: 上記以外のスタッフ本人操作 Callable（シフト申請・勤怠修正申請・プロフィール更新等）の網羅リストは changeSpec 作成時にコードベースから確定する。

### 10-3. 退職済みスタッフの新規勤怠

**不可** とする。

## 11. Firebase Auth disabled を使わない理由

Firebase Auth `disabled` は **A-3 初期実装に含めない**。

### 理由

LINEミニアプリ登録スタッフでは:

```text
LINE sub = Firebase Auth uid = staffs/{docId}
```

同一 UID で `users/{uid}` と `staffs/{uid}` が共存し得る。

Auth を `disabled` にすると、スタッフ利用だけでなく **同一LINEのユーザーLIFF利用** まで止まる可能性がある。

A-3で止めたいのは LINEアカウント全体ではなく、**スタッフ権限・スタッフ導線のみ** である。

### 代替手段

- `staffs.status = "retired"`
- スタッフLIFF入口での retired 分岐
- スタッフ本人操作 Callable の active チェック
- QR生成・勤怠発生・シフト申請の retired 拒否
- LINEスタッフ用リッチメニュー解除

`getFirebaseCustomToken` では retired ブロックを行わない。

## 13. 未来予定がある場合の退職ブロック

退職は即日停止のため、退職処理後に本人操作・勤怠発生・勤務参加が必要になる **未来予定** が残っている場合は退職処理をブロックする。

### 13-1. ブロック対象

```text
未来の shiftRequests.status = pending
未来の shiftRequests.status = interim_confirmed
未来の shiftRequests.status = confirmed

未来日の shifts/{yearMonth}/days/{dateKey}.assignments に staffId が含まれるもの
```

「未来」の定義: `dateKey` またはシフト対象日が **退職処理実行日（JST）より後** のもの。

### 13-2. ブロック対象外

```text
過去シフト
過去勤怠
給与未払い
支払い状態未完了
declined / 却下済み
履歴確認用データ
```

### 13-3. エラー応答

未来予定が残っている場合、管理者に整理を促すエラーを返す。

- 例: 「未来のシフト予定が残っています。シフトを整理してから退職処理を実行してください。」
- 可能であれば、該当件数・日付の概要をレスポンスに含める（実装詳細は changeSpec）

### 13-4. 実装場所

`retireStaff` Callable 内で、status 更新前にチェックを行う。

## 16. 再登録・再有効化

### 16-1. 方針

- 店舗端末に復旧・退職取消・再雇用ボタンは **提供しない**
- スタッフLIFF起動時、同じLINEアカウントの `retired` staff を **必ず検出**（未登録扱いにしない）
- 同一LINEアカウントによる再登録を **許可**
- 同一人物の厳密保証ではなく、同じLINEに紐づく retired doc を active に戻す処理

### 16-2. 現行実装との差分

現行 `createStaffAccount` は `staffs/{uid}` が存在すると `alreadyRegistered: true` で終了する。**retired でもブロックされる**。

→ `reactivateStaffAccount` Callable を **新規追加** し、スタッフLIFFは retired 時に `createStaffAccount` ではなく再登録フローへ誘導する。

### 16-3. 再登録フロー

```text
スタッフLIFF起動
  ↓
staffs/{auth.uid} を確認
  ↓
status = retired
  ↓
退職済みアカウント画面
  ↓
店舗側と合意済みか確認ダイアログ
  ↓
再登録入力
  ↓
reactivateStaffAccount
  ↓
status = active
  ↓
retiredAt / retiredDate / retiredReason をクリア
  ↓
linkStaffRichMenu(uid)
```

確認ダイアログは **本人申告ベース**。店舗管理者の正式承認フローは初期実装では設けない。

### 16-4. 再登録時の入力

| フィールド | 扱い |
|-----------|------|
| `fullName` | 既存値を初期表示。修正可 |
| `fullNameKana` | 既存値を初期表示。修正可 |
| `email` | 再入力 |
| `phoneNumber` | 再入力 |
| `birthMonthDay` | 再入力 |
| `loginId` | 再生成 |

新しい `staffs` doc は作成せず、同じ `staffs/{auth.uid}` を再利用する。

### 16-5. `reactivateStaffAccount` の処理概要

1. 認証済み `auth.uid` の `staffs` doc が `retired` であることを確認
2. 入力バリデーション（`createStaffAccount` と同等の形式チェック）
3. `status: "active"` に更新
4. 退職情報フィールドをクリア
5. 連絡先・`loginId` を再設定
6. QR を新規生成（`createStaffAccount` と同様の処理を再利用可能）
7. `linkStaffRichMenu(uid)`
8. 成功レスポンス

## 17. 給与・支払い状態管理

### 17-1. 退職後も給与対象に含める

退職済みスタッフでも、対象期間内に勤怠・給与対象データが存在する場合は **給与計算・支払い状態管理の対象に含める**。

### 17-2. 退職ブロック条件にしないもの

- 給与未払い
- 支払い状態未完了

### 17-3. 保持するフィールド

退職後も以下を保持（§7-1）:

- `hourlyWage`
- `bankInfo`

用途: 最終給与計算、支払い状態管理、差額調整、勤怠修正後の再計算、問い合わせ対応

### 17-4. 給与計算との関係（調査結果）

`processStaffPayroll` 等は `staffs` を参照する。`status` フィルタ追加時は **retired を除外しない** よう注意する（§15-2）。
