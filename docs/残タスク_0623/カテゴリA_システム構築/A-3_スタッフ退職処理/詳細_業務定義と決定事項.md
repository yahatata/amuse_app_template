# A-3 詳細: 業務定義と決定事項

## 残っている理由

退職処理の実装はゼロから必要だが、「退職とは業務上何をすることか」が未定義のため実装に着手できない。
以下の各事項について業務上の判断が必要。

---

## 決定が必要な事項

### 1. 退職の業務モデル

**即日停止方式**
- 管理者が退職処理を実行した瞬間に全機能が無効化される
- シンプルだが、退職日が未来の場合に先行して処理できない

**退職予定日登録方式**
- 退職予定日を登録しておき、当日のスケジューラーで自動停止
- 事前準備ができる反面、スケジューラー実装が追加で必要

### 2. Firebase Auth アカウントの扱い

**無効化する（`admin.auth().updateUser(uid, { disabled: true })`）**
- アプリへのログイン自体を Auth レベルで遮断できる
- 再雇用時に `disabled: false` で復元可能

**アプリ側のみブロック（`staffs` の status チェック）**
- Auth は生かしたまま、アプリ内の操作を status チェックで拒否する
- Auth コストは変わらないが実装がシンプル

### 3. 再雇用時の UID 方針

**同一 UID を再利用する**
- 過去のシフト・給与・勤怠記録がそのまま紐づいて参照できる
- `staffs` ドキュメントの status を `active` に戻すだけで再開できる

**新規 UID で再登録する**
- 過去データと切り離した状態で再スタートできる
- 過去データとの紐付けが必要な場合は別途対応が必要

### 4. 未払い給与・未消化シフト申請の扱い

**退職処理前に処理必須（ガードをかける）**
- 退職処理 callable の中で未払い・未確定シフトの存在チェックを行い、残っていればエラーを返す
- データの整合性は保ちやすいが、管理者の事前作業が必要

**退職後も残して処理可能**
- 退職後のスタッフに対して給与確定・シフト処理を行えるようにする
- 実装の柔軟性は上がるが、退職済みスタッフが各画面に表示され続ける可能性がある

### 5. 個人情報の保持期間

- 退職後に口座情報・電話番号等の個人情報をいつ削除するか
- 法令（労働基準法等）上の保存義務がある書類との兼ね合いを確認する必要がある
