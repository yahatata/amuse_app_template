# A-3 スタッフ退職処理 概要仕様書

**調査基準日**: 2026-07-03  
**ステータス**: **完了**（2026-07-09）  
**詳細仕様**: [詳細仕様書.md](./詳細仕様書.md)

---

## 1. このタスクで実現すること

店舗管理者がスタッフを「退職済み」として扱えるようにし、退職後はそのスタッフが **スタッフ向け本人操作（QR・勤怠・シフト申請など）を行えない** 状態にする。

同時に、過去の勤怠・シフト・給与の履歴は残し、最終給与の支払いや問い合わせ対応に必要な情報は保持する。

再雇用時は、店舗端末からの復旧ボタンは設けず、**スタッフ本人がスタッフLIFFから再登録** する。

---

## 2. 退職の定義

退職とは、店舗側が当該スタッフを **今後のスタッフ本人操作対象・現役運用対象から外す** 状態を指す。

これは厳密な雇用関係の法的終了そのものではなく、**システム上の現役スタッフ運用から外す処理** として扱う。

退職理由・経緯には以下があり得る。

- 本人申告
- 音信不通
- 無断欠勤
- 店舗判断
- 他スタッフ経由の連絡
- 管理者誤操作

---

## 3. 退職処理をするとどうなるか

管理者が退職処理を実行すると、対象スタッフは **即日** 現役運用の対象外になる。

| 観点 | 退職後の扱い |
|------|-------------|
| スタッフ状態 | `staffs` ドキュメントは残し、`status` を `retired` に変更 |
| 本人操作 | QR生成・出勤/退勤・休憩・シフト申請・プロフィール編集などは不可 |
| スタッフLIFF | 通常画面は利用不可。再登録導線のみ例外 |
| LINEリッチメニュー | スタッフ用を解除し、ユーザー用へ切り替え（または解除） |
| 過去データ | 勤怠・シフト・給与の履歴は削除しない |
| 個人情報 | 連絡先・QR関連など一部を削除・クリア。氏名・給与関連は保持 |
| Firebase Auth | **無効化しない**（同一LINEのユーザーLIFF利用を止めないため） |

---

## 4. 未来予定がある場合

退職は即日停止のため、**未来のシフト申請・確定シフト割当** が残っている場合は退職処理を **ブロック** する。

管理者は先に未来予定を整理してから退職処理を行う。

給与未払い・支払い状態未完了は、退職処理のブロック条件には **しない**。

---

## 5. スタッフ本人から見た挙動

退職後、スタッフ本人はスタッフ向け通常操作を利用できない。

- スタッフLIFFの通常画面は操作不能
- QR生成・新規勤怠・シフト申請・募集応募・勤怠修正申請・プロフィール編集は不可
- 必要な確認・修正は店舗へ連絡し、店舗端末・管理者側で対応

**例外**: 同じLINEアカウントでスタッフLIFFを開いたとき、退職済みアカウントが検出された場合は **再登録画面** を表示する。未登録扱いにはしない。

再登録は、店舗側と合意済みであることを本人が確認したうえで行う（店舗管理者の承認フローは初期実装では設けない）。

---

## 6. 店舗管理者から見た挙動

### 退職処理

- スタッフ **詳細画面** から退職処理を実行する（一覧の各行に退職ボタンは置かない）
- 確認ダイアログ → 退職日（必須）・退職理由（任意）入力 → 未来予定チェック → 実行
- 退職日の初期値は JST 当日

### 退職済みスタッフの表示

- 現役スタッフ一覧は **active のみ**
- 退職済みは別一覧・フィルタ・詳細画面で参照可能
- 名前の近くに「退職済み」を明示表示
- 詳細画面で退職日・退職処理日時・退職理由を確認可能

### 管理者ができないこと（初期実装）

- 退職取消・復旧・再雇用ボタン（店舗端末から active に戻す操作は提供しない）

---

## 7. LINEリッチメニューの挙動

| 状態 | 表示されるリッチメニュー |
|------|------------------------|
| ユーザーのみ | ユーザー用 |
| active staff のみ | スタッフ用 |
| ユーザー + active staff | スタッフ用 |
| ユーザー + retired staff | ユーザー用 |
| retired staff のみ | なし |

退職時: `users/{uid}` があればユーザー用へ切替、なければリッチメニュー解除。  
再登録時: スタッフ用を再設定。

---

## 8. 再登録の挙動

- 新しい `staffs` ドキュメントは作らず、既存の `staffs/{auth.uid}` を `active` に戻す
- 退職情報（`retiredAt` / `retiredDate` / `retiredReason`）はクリア
- 連絡先など削除した項目は再入力
- `loginId` は再生成
- スタッフ用リッチメニューを再設定

同一人物の厳密保証ではなく、**同じLINEアカウントに紐づく retired staff doc を active に戻す** 処理として扱う。

---

## 9. 退職後も残す情報・消す情報の概要

### 残す（概要）

- 識別子（uid / docId）
- 氏名（`fullName` / `fullNameKana`）
- 時給・銀行口座（給与・支払い対応のため）
- 退職情報・作成/更新日時
- 勤怠・シフト・給与などの履歴データ

### 消す・クリアする（概要）

- メール・電話・誕生日
- `loginId`
- QR関連（URL・有効期限）
- 管理者端末作成時のみ存在する重複フィールド（`StaffName` 等）

`hourlyWage` / `bankInfo` の退職後削除・マスクは **A-3 では行わない**。プロジェクト全体の後続検討事項とする。  
→ [../../後続検討事項/退職者・利用者情報の保持期間と削除方針.md](../../後続検討事項/退職者・利用者情報の保持期間と削除方針.md)

---

## 10. 初期実装に含めないこと

- 退職予定日登録・予定日到来自動停止
- Firebase Auth の `disabled` 化
- 店舗端末からの退職取消・復旧・再雇用
- 再登録の店舗承認待ち UI
- 既存QRの即時無効化（必須要件としない）
- 給与未払いを理由とした退職ブロック
- `hourlyWage` / `bankInfo` の一定期間後削除・マスク
- shifts rules / IDOR / `getShifts` auth の全面セキュリティ改修（退職停止に直接必要な最低限のみ A-3 に含める）
