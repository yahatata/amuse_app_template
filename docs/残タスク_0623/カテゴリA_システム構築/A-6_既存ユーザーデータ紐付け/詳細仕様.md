## 2. 目的

新規店舗へのシステム導入時に、店舗が既存台帳や物理チップ等で管理している既存ユーザーと、その保有残高を新システムへ引き継げるようにする。

また、LINE を利用しないユーザーを店舗端末上で継続管理できるようにし、店舗管理ユーザーが後から LINE を利用し始めた場合の移行も扱う。

---

## 3. ユーザー種別

ユーザーは次の 2 種類とする。

### 3-1. LINEユーザー

| 項目 | 内容 |
|------|------|
| 登録経路 | LIFF から本人が登録する |
| 概念フィールド | `userType: "line"` |
| 対象機能 | LIFF 本人操作、QR 表示、LINE 連携機能等 |

### 3-2. 店舗管理ユーザー

| 項目 | 内容 |
|------|------|
| 位置づけ | LINE を利用しない、または利用できないユーザー。仮ユーザーではなく正式な管理対象ユーザー |
| 登録経路 | 店舗端末から登録する |
| 概念フィールド | `userType: "store_managed"`。作成時は `isMigrated: false` |
| 対象機能 | ポイント、サイドゲームチップ、会計、トーナメント参加等 |
| 対象外 | LIFF 本人操作、LINE 通知、LINE 連携機能 |

---

## 4. 引き継ぎ対象

### 4-1. 引き継ぐもの

初期対応で引き継ぐのは、次の現在残高のみとする（A-7 以降の標準フィールド）。

- `pointA`〜`pointE`
- `sideGameChip`

初期ポイント設定 UI では、`storeMeta/config` で `enabled:true` の通貨型と、有効な `sideGameChip` のみ入力する。無効残高は UI で触らず、初期設定 Callable でも 0 上書きしない（A-7 changeSpec）。

### 4-2. 引き継がないもの

次は引き継がない。

- 過去のポイントログ
- 過去の会計履歴
- 過去のトーナメント参加履歴
- 過去のサイドゲーム履歴
- QR 情報
- Firebase Auth 情報
- その他、導入前の業務履歴

導入前の履歴は旧台帳・旧運用側を正本とする。

## 5. 導入時の登録フロー

### 5-1. LINE を利用する既存ユーザー

1. 本人が LIFF から LINEユーザーとして登録する
2. 管理者が初期ポイント設定機能から、旧台帳上の現在ポイントを設定する

### 5-2. LINE を利用しない既存ユーザー

1. 店舗端末から店舗管理ユーザーとして登録する
2. 管理者が初期ポイント設定機能から、旧台帳上の現在ポイントを設定する

---

## 6. 初期ポイント設定

| 項目 | 要求 |
|------|------|
| 対象 | LINEユーザー・店舗管理ユーザーの両方 |
| 入力項目 | A-6 完成時は 3 項目固定。**A-7 以降**は有効な `pointA`〜`pointE` と有効な `sideGameChip` のみ（各項目必須） |
| 残高なし | 当該項目には `0` を入力する |
| 更新方式 | 加算ではなく、指定値への上書き |
| 許容値 | `0` および正の整数 |
| 禁止値 | 負数・小数 |
| 再設定 | 許可する |

設定済みの場合は、現在の有効ポイント残高と前回設定日時を表示し、上書きであることを確認させる。

対象ユーザーには、初期ポイント設定済み判定と前回設定日時表示のため、次の概念フィールドを持たせる。

| 概念フィールド | 意味 |
|----------------|------|
| `initialBalanceSetAt` | 初期ポイントを設定した日時。再設定時は最新日時に更新する |

---

## 7. 初期ポイント設定画面

初期ポイント設定機能は、通常のユーザー一覧・ユーザー詳細画面には配置しない。

低頻度かつ高リスクな操作であるため、管理者専用領域の独立ページに配置する。

配置方針：

```text
admin専用ホーム
└── 詳細設定
    └── 初期ポイント設定
```

画面は次の2画面に分割する。

1. 対象ユーザー選択画面
2. 選択した1名の初期ポイント設定画面

対象ユーザー選択画面はカードUIとし、次の要求を満たす。

- 検索対象は `pokerName` のみとし、`loginId` や uid 等の内部情報では検索しない
- 検索結果は完全一致、前方一致、部分一致の順に表示する
- 移行済み店舗管理ユーザーは候補に表示しない
- 初期表示は未設定ユーザーとし、トグル「設定済みユーザーのみ表示」で設定済みユーザーへ切り替える
- 候補カードには店舗運用上必要なユーザー名だけを表示する

設定画面では現在ポイント、初期ポイント設定日時、設定後ポイントを確認でき、上書き確認後に保存する。

## 8. 管理者向けユーザー確認

Adminホームに店舗向けのユーザー一覧を配置し、詳細設定には配置しない。

一覧では次を表示する。

- ポーカーネーム
- 入店中／未入店

ユーザー詳細では次を表示する。

- ポーカーネーム
- 誕生日
- 入店中／未入店
- 最終来店日時
- 有効な通貨型残高（A-7 以降: config 表示名。`pointA`〜`pointE` のうち enabled）
- `sideGameChip`（有効時）

店舗向け画面では「残高」ではなく「ポイント」と表記する。`loginId`、uid、メールアドレス、ユーザー種別、移行先uid等の内部管理情報は表示しない。

ユーザー一覧・詳細画面には、初期ポイント設定操作や後日LINE化操作を置かない。移行済み店舗管理ユーザーは一覧から除外する。

## 9. 移行履歴

移行履歴は、1 回の管理操作で設定した残高スナップショットを記録する（A-7 以降 `balances` は標準 6 フィールド）。

### 9-1. 保存先（要求上の想定）

```text
users/{targetUserId}/balanceMigrationLogs/{migrationId}
```

初期ポイント設定・後日LINE化の移行履歴は `balanceMigrationLogs` を正本とし、次には保存しない（A-7 の通貨型ログ `pointLogs` も含めない）。

- `pointALogs` / `pointBLogs`（レガシー。A-7 以降新規書込なし）
- `pointLogs`
- `sideGameChipLogs`

### 9-2. 概念項目

| 項目 | 内容 |
|------|------|
| `migrationType` | 移行種別（下記） |
| `sourceUserId` | 移行元 uid。`initial_import` では値なし。`store_managed_to_line` では移行元店舗管理ユーザーの uid |
| `balances` | 移行先ユーザーへ設定した最終残高（`pointA`〜`pointE` + `sideGameChip`）。変更前残高は保存しない |
| `createdAt` | 移行履歴の作成日時 |
| `note` | 任意の補足情報 |

### 9-3. `migrationType`

| 値 | 用途 |
|----|------|
| `initial_import` | 初期ポイント設定 |
| `store_managed_to_line` | 店舗管理ユーザーから LINEユーザーへの移行 |

## 10. 店舗管理ユーザーの後日 LINE 化

後日 LINE 化は A-6 の対象に含める。

発生頻度の低い例外機能として扱い、現行認証設計への影響を最小限にする。

既存店舗管理ユーザーに LINE 認証を直接紐付けず、本人が新しい LINEユーザーを通常どおり作成し、標準残高を引き継ぐ。

### 10-1. 配置方針

```text
admin専用ホーム
└── 詳細設定
    └── 店舗管理ユーザーからLINEユーザーへの移行
```

### 10-2. 移行元条件

- `userType: "store_managed"`
- `isMigrated: false`

### 10-3. 移行先

本人が新規作成した LINEユーザー。

### 10-4. 移行時に要求すること

- 移行元店舗管理ユーザーの選択
- 移行先 LINEユーザーの選択
- 新旧ユーザー情報の比較確認
- 管理者による同一人物確認
- 移行元の標準残高（6 フィールド）を移行先へ設定（A-7: データ上は全標準残高コピー。UI は有効分のみ表示）
- 移行先ユーザー配下に移行履歴を保存
- 移行元ユーザーを移行済みにする
- 新旧ユーザーの対応関係を保持
- 移行済み旧ユーザーを通常業務対象から除外
- 旧ユーザーは削除せず、過去履歴参照用に保持

後日LINE化は、移行元・移行先の双方に進行中または未完了の業務がない場合だけ許可する。検査対象は入店、未精算・処理中伝票、会計後未完了、卓・席、トーナメント、サイドゲーム、未解消置きバケとする。

トーナメントの検査対象は、現在営業日の未終了トーナメントだけとする。営業日は次の開店処理まで切り替わらず、未終了トーナメントがある状態では閉店できないため、現在営業日の未終了参加は進行中業務として扱う。一方、過去営業日の未終了トーナメントは残留データとして扱い、後日LINE化の拒否理由にはしない。

具体的な判定条件、更新順序、途中失敗時の扱いは `changeSpec.md` で定義する。

### 10-5. 移行先の既存残高

店舗管理ユーザーから LINEユーザーへの移行では、移行先 LINEユーザーの標準残高がすべて `0` であることは **必須にしない**。

移行先 LINEユーザーに既存残高がある場合も、一律には拒否しない。

ただし、移行操作では移行先 LINEユーザーの現在残高を必ず表示し、移行元店舗管理ユーザーの残高によって標準残高フィールドが上書きされることを管理者へ明示する（UI 上は有効ポイントを中心に表示）。

管理者が現在残高と上書き後の残高を確認したうえで、移行を確定するものとする。

移行先に進行中業務や、残高以外の不整合要因がある場合の検査・拒否条件は、`changeSpec.md` で定義する。

### 10-6. 後日LINE化画面

詳細設定には初期ポイント設定と後日LINE化だけを配置する。

後日LINE化画面は次の要求を満たす。

- 画面上部に目的と操作手順を表示する
- 移行元・移行先の検索対象は `pokerName` のみとし、完全一致、前方一致、部分一致の順で表示する
- 候補一覧は常時表示せず、検索欄のフォーカス中または入力中だけ表示する
- 候補カードにはユーザー名だけを表示し、`loginId` や uid 等の内部情報は表示しない
- 選択後は選択ユーザーをカード表示し、「変更」から選び直せる
- 移行元・移行先の両方を選択した後に現在ポイントと移行後ポイントを比較表示する
- 同一人物確認と最終確認を経て「ポイント移行を実行」する

## 11. 移行済み店舗管理ユーザー

### 11-1. 通常の店舗管理ユーザー

```text
userType: store_managed
isMigrated: false
```

### 11-2. 移行済み店舗管理ユーザー

```text
userType: store_managed
isMigrated: true
migratedToUserId
migratedAt
```

| 項目 | 要求 |
|------|------|
| `isMigrated` | 店舗管理ユーザーだけが持つ。LINEユーザーには持たせない |
| `migratedToUserId` | 移行先 LINEユーザー uid |
| `migratedAt` | 後日 LINE 化の実施日時 |
| 業務対象 | `isMigrated: true` のユーザーは、通常のユーザー選択、会計、トーナメント参加、チップ操作等の新規業務対象から除外する |
| 履歴 | 過去履歴の参照は可能とする |

## 12. pokerName

現行の重複禁止方針を維持する。

- LINEユーザー・店舗管理ユーザーを問わず、`users` 全体で重複禁止
- 後日 LINE 化でも例外を設けない
- 新しい LINEユーザーは、旧店舗管理ユーザーとは異なる `pokerName` を使用する
- 旧店舗管理ユーザーの `pokerName` は変更しない

## 13. 権限

次の操作は admin device のみ実行可能とする。

- 初期ポイント設定
- 店舗管理ユーザーから LINEユーザーへの移行

一般ユーザー、LIFF、一般スタッフ端末からは実行不可。

使用する既存権限ヘルパー等の具体実装は `changeSpec.md` で定義する。

---

## 14. CSV

初期実装では CSV 等によるユーザー登録・残高の一括インポートには対応しない。

1 件ずつ登録・設定する。

必要性が実導入で明確になった場合のみ、別タスクとして再検討する。

---

## 15. 対象外

少なくとも次を対象外とする。

- 過去履歴の移行
- 店舗管理ユーザーへの LINE 認証の直接追加
- Firestore ユーザードキュメントの統合
- Firebase Auth アカウントの統合
- CSV 一括登録・一括移行
- 通常業務における任意ポイント加算・減算
- 会計・精算後調整等の既存ログ不足の修正
- `ART-304` の作成
- 既存テストユーザー向けの本番互換フォールバック・恒久的な一括移行機能

---

## 16. 既存テストデータの扱い

A-6 実装前から存在する `users` ドキュメントは、すべて実顧客ではなくテストアカウントである。

そのため、既存ユーザーに `userType` 等が存在しないことに対する本番互換処理や読取フォールバックは実装しない。

既存テストユーザーに必要な次のフィールドは、開発時の一回限りの補正スクリプトで設定してよい。このスクリプトは dry-run を既定とし、明示指定時だけ更新する開発用ツールであり、店舗向け製品機能や導入時の一括移行機能には含めない。

この対応は既存テストデータに対する開発時作業であり、店舗向けの製品機能には含めない。

### 16-1. 補正値（開発時）

#### LINEユーザーとして扱うテストアカウント

```text
userType: line
```

#### 店舗管理ユーザーとして扱うテストアカウント

```text
userType: store_managed
isMigrated: false
```

### 16-2. 新規作成ユーザー（製品仕様）

A-6 実装後に新規作成されるユーザーについては、登録経路に応じて必要なユーザー種別フィールドを必ず設定する。

---

## 17. 完了の定義（要求レベル）

次の要求を満たし、実装・自動テスト・実機確認まで完了した。

1. LINEユーザー・店舗管理ユーザーを、要求どおり区別して登録・管理できる
2. 管理者が初期ポイント設定により有効残高を上書き設定・再設定でき、移行履歴が残る
3. 管理者がユーザー一覧・詳細で店舗運用に必要なユーザー情報とポイントを確認できる
4. 店舗管理ユーザーからLINEユーザーへのポイント引き継ぎ（後日LINE化）ができる
5. 移行済み店舗管理ユーザーが通常の新規業務対象から除外される
6. CSV 一括・履歴移行・アカウント統合を行わない（対象外どおり）
