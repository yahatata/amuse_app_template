## 2. 背景

店舗ごとに既存のポイント名称・種類数が異なる。現行は次の理由で導入時の合わせ込みが難しい。

- 通貨型ポイントが `pointA` / `pointB` に固定
- 表示名が複数箇所でハードコード
- `sideGameChip` も表示名・有効性がコード固定
- 支払換算がチップ向けfloatレート中心で、通貨型は1残高=1基準値の暗黙前提
- 支払実績に実減算残高量・換算条件が残らない

A-7は、**導入前に提供側がconfigで店舗制度へ合わせる**ための基盤整備である。店舗向け設定UIは作らない。リリース後に店舗が自由編集する運用は想定しない。

### 検討経緯（不採用）

旧調査時点では「現状維持」「表示名のみconfig化」等も候補にあった。現在は次を**確定方針**とし、それらを現行候補としては扱わない。

- 通貨型最大5スロット（`pointA`〜`pointE`）
- 表示名・有効性のconfig化
- 支払換算・用途・順位報酬の整合
- `sideGameChip` は別種別維持

旧文書の工数目安（8〜12h / 20〜38h 等）は、確定仕様より前の概算であり、確定工数ではない。

## 3. 現状実装

確定仕様と混同しないよう、調査時点の実装事実のみを記す。

### 3.1 残高

- `users/{uid}` 直下に `pointA` / `pointB` / `sideGameChip` のみ
- ユーザー作成時に3種を0初期化
- クライアントからの直接書込は rules で禁止（Functions経由）

### 3.2 タイプ一覧・表示名

- 一覧の代表: `lib/globalConstant.dart` の `pointTypes = ['pointA','pointB','sideGameChip']`
- 表示名: `Formatters.getPaymentMethodDisplayName` のほか、会計系ローカルswitch・EN直書き・トーナメントでの生ID表示が混在
- configに `pointSettings` / `sideGameChipSettings` は**存在しない**

### 3.3 換算・丸め

- `pointA` / `pointB`: 暗黙的に1残高単位＝1基準値（実質円）
- `sideGameChip`: `billing.sideGameChipRate`（float、円/枚）
- 丸め: `roundingUnits.pointAB` は基準値（円）側、`roundingUnits.sideGameChip` は枚数側
- 会計後調整などで chip 換算に `floor` / `round` の不一致がある

### 3.4 支払い・bill

- 可否は主に `billing.paymentPolicy.categoryPaymentMethods`
- 優先順は `pointPriority`
- billの支払実績は method ID → 基準値量（円）が中心
- 実減算残高量・換算条件のスナップショットは**ない**
- `paymentMethodsByAmount` 経路ではカテゴリ別allowlistを再検証していない

### 3.5 ログ

- `pointALogs` / `pointBLogs` / `sideGameChipLogs` がタイプ別
- 会計減算・会計後の返金・追加徴収はポイントログへ**記録されない**
- `balanceMigrationLogs` はA-6用（固定3残高）

### 3.6 トーナメント順位報酬

- 大会（テンプレート／mainView）単位で `pointType` を1つ保持
- UIは `pointTypes` により `sideGameChip` も選択可能
- Functions（`setRankingData`）は通貨型（A/B）前提。chip選択時は誤ったログ書込が発生し得る

### 3.7 A-6

- `BalanceTriple` が `pointA` / `pointB` / `sideGameChip` 固定
- 初期残高UI・移行UIも3種固定

### 3.8 analytics

- 支払手段の固定whitelistを使用
- 未知の支払い手段を cash へ落とす処理がある

## 4. 確定仕様

### 4.1 ポイント種別

| 区分 | 内部ID | 備考 |
|------|--------|------|
| 通貨型 | `pointA`〜`pointE` | 標準最大5スロット。通常店舗は多くても4種程度を想定 |
| 別種別 | `sideGameChip` | 通貨型に含めない |

5種類を超える要望は、標準仕様ではなく当該店舗リポジトリの個別拡張とする。
動的な任意ポイントIDは採用しない。

### 4.2 ユーザー残高構造

`users/{uid}` 直下の固定フィールドを維持・拡張する。map化しない。

```text
pointA
pointB
pointC
pointD
pointE
sideGameChip
```

- 新規ユーザー作成時: 上記すべてを0で初期化
- A-7実装前の開発用ユーザーで `pointC`〜`pointE` が欠損している場合: 読取時は0として扱う
- 既存ユーザー全件への0フィールド一括マイグレーションは行わない
- 初めて残高を書き込む際に、該当フィールドが作成される

### 4.3 config

設定正本は `storeMeta/config`。

#### ポイント基本設定（支払い専用ではない → `billing` 配下に置かない）

```yaml
pointSettings:
  pointA:
    enabled: true
    displayName: トーナメントポイント
  pointB:
    enabled: true
    displayName: 来店ポイント
  pointC:
    enabled: false
    displayName: ポイントC
  # pointD / pointE も同様

sideGameChipSettings:
  enabled: true
  displayName: サイドゲームチップ
```

#### トーナメント順位報酬の許可一覧（概念）

```yaml
tournament:
  rankingRewardPointTypes:
    - pointA
    - pointC
```

#### 支払い関連（既存を正本とし、換算を拡張）

- `billing.paymentPolicy.categoryPaymentMethods` … カテゴリ別支払可否の正本
- `billing.paymentPolicy.pointPriority` … 自動充当の優先順位（可否ではない）
- 通貨型ポイントごとの換算設定 … `billing.paymentPolicy` 配下に保持（正式フィールド名はchangeSpec）

概念例（整数比）:

```yaml
conversion:
  referenceUnits: 10
  balanceUnits: 1
# 残高1単位 = 基準値10単位

conversion:
  referenceUnits: 1
  balanceUnits: 2
# 残高2単位 = 基準値1単位
```

フィールド名に `yen` / `円` は使わない。現会計では基準値は実質円額だが、将来の支払機能見直しも踏まえ中立な名称とする。

支払いに使わないポイントへ換算設定は要求しない。
`categoryPaymentMethods` にポイントを含める場合は、対応する換算設定を必須とする。

`displayOrder` や `pointCount` は追加しない。表示対象は `enabled:true` から判断する。

### 4.4 enabled

`enabled` は、その店舗で当該残高種別を運用対象とするかを表す。主に導入前のconfigで決定する。

`enabled:false` の種別は、店舗向けの新規操作・選択UIから除外する。

- 残高表示
- 初期残高設定、店舗管理→LINE移行画面
- トーナメント順位報酬の選択
- 預入・引出
- その他の新規操作

ポイント履歴について、`pointLogs` は複数ポイントをまとめた共通ログになる。履歴画面自体を消すのではなく、`enabled:false` のポイントについては店舗向け履歴画面の通常表示対象から除外する。履歴データ自体は削除しない。

UI非表示だけでなく、Functionsでも無効なポイントへの**新規操作を拒否**する。

支払い可否は `enabled` だけでは決まらない。次の両方を満たす必要がある。

1. 対象残高が `enabled:true`
2. 対象カテゴリの `categoryPaymentMethods` に含まれている

途中無効化しても、既存残高・ログ・bill・analyticsは削除しない。
店舗向け管理画面へ無効残高を残表示する必要はない。確認が必要な場合は提供側のシステム管理者が調査する。

### 4.5 支払い用途

カテゴリごとの支払い可否は `billing.paymentPolicy.categoryPaymentMethods` を正本として維持する。
ポイント設定側に用途別支払い可否フラグを重複して持たない。

UIとFunctionsの双方で検証する。

- 残高種別が有効であること
- 対象カテゴリで支払手段として許可されていること
- 未知のポイントIDではないこと

現行の `paymentMethodsByAmount` 経路でカテゴリ別allowlistを再検証していない問題も修正対象とする。

### 4.6 トーナメント順位報酬

1. configの `rankingRewardPointTypes`（名称はchangeSpecで確定）で付与先候補を定義
2. **トーナメントテンプレート作成・編集時**に、許可一覧から1種類を選択
3. 選択条件:
   - `pointA`〜`pointE` のいずれか
   - `enabled:true`
   - 許可一覧に含まれる
   - `sideGameChip` ではない
4. テンプレートから作成された個別トーナメントに `pointType` を保存
5. 順位確定・取消は、個別トーナメントに保存された `pointType` を使用（現在configに依存して付け替えない）

UIとFunctionsのchip選択不整合はA-7で修正する。

1大会で複数ポイント種別を同時付与する構造にはしない（現行どおり大会あたり1種類）。

### 4.7 sideGameChip

- 通貨型とは別の残高種別として維持
- `sideGameChipSettings.enabled` は機能全体の上流条件
- `enabled:true` で残高表示・預入・引出を利用可能
- 支払い利用は、さらに `categoryPaymentMethods` に `sideGameChip` が含まれる場合のみ
- `depositEnabled` / `withdrawEnabled` 等の個別フラグは設けない
- `enabled:false` ではUI除外、Functionsで預入・引出等の新規操作を拒否

専用業務（購入明細、専用billサブコレクション、物理チップ数量前提の処理等）は通貨型へ統合しない。

### 4.8 換算・利用単位

- 支払換算は通貨型ポイントごとに設定可能（整数比）
- 浮動小数点値を計算正本にしない。整数演算で行う
- 利用単位は**基準値側で統一**する（例: 基準値1000単位ごとに利用可能）
- sideGameChipだけ枚数側で丸める例外は廃止し、共通方針へ揃える
- 会計方法・自動充当の基本挙動は変更しない

#### 手動指定（エラーとする場合）

- 指定額が利用単位に一致しない
- 指定した基準値量を整数の残高量へ変換できない
- 残高不足
- カテゴリで許可されていない / 残高種別が無効

#### 自動充当（現行方式を維持）

- 優先順位順に処理する
- 利用単位を満たす候補額を大きい順に確認し、整数の残高量へ変換できる最大額を充当する
- そのポイントで成立する正の充当額がない場合は、次の支払手段へ進む
- 残額は現金等へ回す
- 小数残高へ丸める処理は行わない

会計後のchip換算における `floor` / `round` 不一致も、共通計算仕様へ揃える。

### 4.9 支払い実績

ポイントまたはsideGameChipで支払った場合、billへ少なくとも次を保存する。

- 残高種別の内部ID
- 充当した基準値量
- 実際に減算した残高量
- 使用した換算設定（`referenceUnits` / `balanceUnits`）
- 使用した利用単位

これにより、後からconfigの換算が変わっても元の支払いを再現できる。

- **返金**: 現在configで再計算せず、元の支払実績の減算残高量を使用
- **追加徴収**: 新しい取引として、その時点の設定で計算し、新たな実績を保存

正式なbillフィールド名はchangeSpecで定める。

### 4.10 残高ログ

#### 通貨型（A-7以降）

共通コレクションへ統合する。

```text
users/{uid}/pointLogs/{logId}
```

少なくとも次を保存する。

- `pointType`
- `balanceBefore`
- `changeAmount`
- `balanceAfter`
- `reasonType`
- `relatedId`（`reasonType`に応じて解釈。例: accounting→billId、tournament_reward→tournamentId）
- `createdAt`

`relatedEntityType` は保存しない。

原則ログ対象（通常運用で残高が変化する処理）:

- トーナメント順位報酬の付与・取消
- 会計での減算
- 会計後の返金・追加徴収
- 管理者による手動調整

取消時に元ログ削除か取消ログ追加かはchangeSpecで決定する。

#### sideGameChip

`sideGameChipLogs` は統合せず独立維持する。
会計減算・返金・追加徴収の記録形式は、「残高変動は原則ログへ残す」方針に沿ってchangeSpecで具体化する。

### 4.11 A-6

#### 初期残高設定UI

表示するのは次のみ。

- `enabled:true` の `pointA`〜`pointE`
- `sideGameChipSettings.enabled:true` の場合の `sideGameChip`

表示対象はすべて入力必須。残高がない場合は0を入力する。

#### 店舗管理→LINE移行

- データ上の移行対象: `pointA`〜`pointE` および `sideGameChip` の全標準残高
- UIに無効ポイントは表示しないが、データ消失を避けるため処理では全標準残高を扱う

#### ログ

- 初期残高・LINE移行は引き続き `balanceMigrationLogs` を正本
- `pointLogs` へ重複保存しない
- `balances` はフラット構造を維持し、`pointC`〜`pointE` を拡張

### 4.12 analytics・表示名

- analyticsは `pointA`〜`pointE` に対応
- 内部IDで集計し、画面表示時に現在のconfig `displayName` へ変換
- 未知の支払い手段をcashへ落とさないよう修正する（`pointC`〜`pointE` の誤集計防止）
- 過去実績・無効化ポイントのデータは削除しない
- 履歴・bill・analyticsは内部IDを正本とし、表示は現在のconfig名を使用
- `displayNameSnapshot` は今回保存しない

## 5. 現行実装からの主な変更

| 領域 | 現行 | 確定後 |
|------|------|--------|
| 通貨型スロット | A/Bのみ | A〜E（enabledで運用） |
| 表示名 | ハードコード多数 | config `displayName` |
| 有効性 | 概念なし | `enabled` + Fn拒否 |
| 残高フィールド | 3種 | 6種固定フィールド |
| 換算 | A/Bは1:1暗黙、chipはfloat rate | 整数比。支払利用時必須 |
| 利用単位 | A/Bは基準値、chipは枚数 | 基準値側へ統一 |
| 支払実績 | 基準値中心、換算スナップショットなし | 基準値・減算量・換算条件を保存 |
| 返金 | 現行config再計算の経路あり | 元実績の減算量を使用 |
| 通貨型ログ | 別コレクション、会計未記録 | `pointLogs` 統合、残高変動を原則記録 |
| 順位報酬 | UIがchip選択可、Fn不整合 | 許可一覧＋通貨型のみ |
| A-6 | 固定3種 | UIは有効のみ、移行データは全標準残高 |
| analytics | 未知→cash | 未知をcashに落とさない |
| 後方互換 | （想定なし） | 開発段階のため旧互換・fallbackなし |

## 6. 主な影響範囲

実装ファイルの網羅一覧はchangeSpecで作成する。本書では機能単位の影響を示す。

| 機能領域 | 影響の要点 | 実装（2026-07-24） |
|----------|------------|-------------------|
| config / defaults / loader | `pointSettings` / `sideGameChipSettings` / 換算 / 報酬許可一覧の追加。Flutter・Functions双方 | Phase 1 済 |
| ユーザー作成・残高helper | `pointC`〜`pointE` 初期化、読取時欠損=0、共通ID定義 | Phase 1 済 |
| 会計・split・validator・丸め | 有効性検証、整数比換算、ByAmount経路のallowlist再検証、利用単位統一 | Phase 2〜3 済 |
| 会計後返金・追加徴収 | 実績参照／新規取引の切替、換算式統一 | Phase 3 済 |
| トーナメント template / prize / ranking / undo | 許可リスト、chip排除、保存済みpointType利用 | Phase 4 済 |
| sideGameChip預入・引出UI/Callable | `enabled` ゲート | Phase 4 済 |
| ポイント履歴UI | `pointLogs` 読取（無効ポイントの通常表示除外）。chipログは `sideGameChipLogs` 維持 | Phase 6 済 |
| A-6 UI / Callable / balanceMigrationLogs | 動的表示、balances拡張、移行全残高 | Phase 5 済 |
| analytics / dashboard | whitelist拡張、displayName変換、未知methodのcash落とし廃止 | Phase 6 済 |
| 表示名 | Formatters・会計直書き・LIFF等のconfig化 | Phase 6 済 |
| LIFF 残高表示 | `public/user` 等で有効残高を config 表示名で表示 | Phase 6 済 |
| テスト | 上記全域。開発用configの直接書換を前提 | 単体テスト追加済（未コミット） |

## 7. 実施しないこと

- 店舗向けポイント設定UI

- 通貨型とsideGameChipの構造統合
- `displayOrder` / `pointCount` の保存
- `displayNameSnapshot`
- 旧config fallback、旧店舗・本番向け互換読取・移行・バックフィル
- config未設定を正常運用として支えるfallback
- 既存ユーザー全件への0フィールド一括マイグレーション

## 8. 開発データ・後方互換

本タスクは開発段階であり、既存導入店舗・本番ユーザーデータは存在しない前提とする。

そのため次は対象外である。

- 旧configのfallback・互換読取
- 既存店舗向けconfig移行
- 本番ユーザーのバックフィル
- 旧bill / 旧ログ / 旧 `balanceMigrationLogs` の本番互換

必要な開発用データは、新仕様に合わせて作り直すか、Firestoreの `storeMeta/config` をテスト条件に合わせて直接書き換える。
config未設定状態を正常運用として支える実装は行わない。

## 9. changeSpecで具体化する事項

業務・構造方針は本書で確定済みである。実装方法は [changeSpec.md](./changeSpec.md) に具体化済み（Phase 1〜6 コード完了、2026-07-24）。

少なくとも次を含める。

- configの正式なフィールド名・型・validation
- Flutter / Functionsの共通ポイントID定義
- 残高読取・更新helper
- 会計換算式と自動充当アルゴリズム（整数演算）
- billの新保存フィールド
- 返金・追加徴収の参照方法
- `pointLogs` / `sideGameChipLogs` の書込仕様
- `reasonType` と `relatedId` の対応
- 順位報酬付与・取消（ログ削除か取消ログか含む）
- A-6の request / response・transaction
- UI変更箇所
- analytics変更
- エラーコード
