## A-1: テーブルデバイスの挙動確認

### 現状サマリ

PR #131 でコア実装はマージ済み。以下は**実装済み**：

- `role: table` のルーティング・Flutter/CF 全体
- `lib/tableDevice/` 全6ファイル（Home・Drawer・Detail・SideGame・Model・Service）
- 4つの callable（registerTableToTournament / unregisterTableFromTournament / registerTableToSideGame / unregisterTableFromSideGame）
- `tables.tournamentDetail`・`tablesSeat.isEnabled` 論理削除
- `tableDeviceRegistrationEnabled`・`forceClearPasscode` の config 読み取り・CF 強制

### 残タスク

コードの実装完了を受けて、**実機で網羅的に挙動を確認する**フェーズ。

#### 1. テーブルデバイスの登録動線の確認

- admin デバイスから卓端末を `role: table` として登録し、卓 ID を紐付けるまでの一連の動線が期待どおりに動くか
- 紐付けが完了していない状態での表示（未紐付けメッセージ）が出るか
- `tableDeviceRegistrationEnabled` を OFF にしているときに登録ボタンが正しく非表示・無効化されるか

#### 2. テーブルデバイス側からトーナメント登録を解除した場合のデータ確認

- テーブルデバイスの Drawer から「トーナメント解除」を行った際に、Firestore 上で以下が正しく更新されるか
  - `tables/{tableId}.status` が `'open'` に戻るか
  - `tables/{tableId}.tournamentDetail` が削除されるか
  - `scheduledTournaments/{tournamentId}/tablesSeat/{tableId}.isEnabled` が `false` に変わるか（論理削除）
- 解除後、トーナメント管理側（admin デバイス）から見たときに卓が外れた状態として表示されるか

#### 3. トーナメント側から卓を外した場合のテーブルデバイスへの影響確認

- admin デバイスのトーナメント管理画面から卓を取り外した際に、テーブルデバイス側のホーム画面が正しく `idle`（空き状態）に戻るか
- `tournamentDetail` が消えた後、テーブルデバイスの状態表示が不整合状態（`inconsistent`）にならないか

#### 4. Firestore rules の本番化（コード対応）

- `tables` / `sideGame` ドキュメントへの write が現在 dev 用の全許可ルールのまま
- CF 側での権限制御は実装済み（callable 内で `requireTableDeviceCaller` 等）だが、Firestore rules レベルの制限がない
- **実装内容:** `firestore.rules` に table-device の write 制限ルールを追加

## A-5: 給与関連通知の整理と最終化

### 概要

給与に関する通知が複数の仕組みで実装されているが、「どのタイミングで・どんな条件で・何を通知するか」が整理されていない。通知種類の精査・頻度の見直し・設定の可変化を行い、運用に適した最終形に仕上げる。

### 現状の通知の仕組み

通知は **イベント駆動** と **スケジューラー駆動** の2種類がある。

#### イベント駆動通知（`payrollNotificationHelper.ts`）

アクション発生時に即時 Firestore へ書き込まれる通知。

| 通知種別 | トリガー |
|---|---|
| 給与計算実行完了 | `finalizePayrollRun` 完了時 |
| 給与計算実行失敗 | `executeMonthlyPayroll` エラー時 |
| 確定済み期間の勤怠修正 | `attendanceOnWrite` が確定期間への変更を検知した時 |

#### スケジューラー駆動通知（`payrollNotificationScheduler` → `processPayrollNotifications`）

毎日 05:00 JST に実行され、条件を満たす場合に通知を作成する。

| 通知種別 | 内容 | 補足 |
|---|---|---|
| `payroll_period_start` | 給与期間が始まった | 期間開始日を通知 |
| `payroll_calc_remind` | 計算がまだ行われていない | 支払日から逆算して督促。一定日数前に `strong_warning` に昇格 |
| `payroll_confirm_remind` | 計算済みだが確定がまだ | 確定期限の督促 |
| `payroll_payment_overdue` | 確定済みだが支払い登録がまだ | 支払い遅延の警告 |
| `payroll_hold_reminder` | 保留スタッフがいる | 保留状態の解消を促す |

#### 通知の表示場所

- Flutter の管理者 HOME ベルアイコン（未読バッジ付き）
- `PayrollNotificationListPage`（全件・未読・フラグ別フィルタ）

### 残タスク

#### 1. 現状の通知種類の整理・精査

- 上記の通知種別について、実際の運用で「必要・不要・頻度調整が必要」を確認する
- 特に確認が必要な観点：
  - スケジューラー通知は毎日実行されるが、同一条件で何日も通知が出続けることへの対処
  - `payroll_payment_overdue` が「確定済みだが支払い登録なし」のみをチェックしており、スタッフごとの未払い数まで見ていない
  - `payroll_period_start` は毎期間必要か

#### 2. 通知頻度・エスカレーションルールの確定

- 同一条件で通知が重複しないよう、頻度制限や「1期間1通知」などのルールを設計する
- `payroll_calc_remind` の `strong_warning` 昇格タイミング（現在：支払日 −3 日）が適切か確認する

#### 3. 通知から給与計算画面への導線

- 現状、通知をタップしても対象の給与計算画面へ遷移しない（既読になるだけ）
- 「この通知から該当期間の給与計算ページへ移動できる」というディープリンク的な動線が必要か検討する

#### 4. 通知設定の可変化（必要であれば）

- 通知種別ごとの有効・無効、督促開始タイミング等を `payrollConfig` で設定可能にする
- 現状の `schedulerNotificationHour`・`reminderStartDaysAfterPeriodEnd` に加えて、どこまで設定可能にするかを検討する

#### 5. スケジューラー通知の E2E 確認

- `payrollNotificationScheduler` → `processPayrollNotifications` の実際の動作確認が未実施
- B-2（Scheduler 確認）と連動して実施する

## A-6: 導入時の既存ユーザーデータ紐付け

### 背景・概要

新規店舗にシステムを導入する際、その店舗にはすでに常連ユーザーが存在する。これらの既存ユーザーはすでに何らかの形でポイント等を保有していることが多い（例：店舗が台帳で管理しているポイント残高、ユーザーが物理的に持っているチップやコイン等）。

システム導入と同時に「ゼロリセット」にするのか、既存データをシステムに移行して引き継ぐのかを決め、引き継ぐ場合の方法を設計・実装する必要がある。

### 検討が必要な事項

- **引き継ぎ方針:** 既存ポイントを引き継ぐか、導入時点でゼロスタートにするか
- **ユーザー登録方法:** 既存ユーザーを LINE 連携でシステムに登録するフロー
- **ポイント付与方法:** 登録後に過去の保有ポイントを初期付与する手段（管理者が手動入力？ 一括インポート？）
- **その他引き継ぎデータの範囲:** ポイント残高のみか、過去の参加履歴等も引き継ぐか

### 現時点のステータス

**仕様未策定。** まずどのような方法で実施するかを検討することがタスク。

## A-7: ポイントタイプの名前変更・個数変更

### 概要

### 検討・実装が必要な事項

- **名前変更:** ポイントタイプの表示名を管理者が変更できる機能（どの画面で設定するか・Firestore の何を更新するか）
- **個数変更:** ユーザーの保有ポイント数を管理者が修正できるか、またそれが必要なユースケースを整理する
- **影響範囲の確認:** 名前変更・個数変更が既存の会計ロジック・履歴データに与える影響
