## H-1: エラー詳細 → 重要度ルール登録ショートカット

### 概要

エラーログの詳細画面に「このエラーの重要度ルールを作成」ボタンを追加し、  
`functionEntry` / `errorKey` / `service` を自動入力した状態でルール作成画面へ遷移できるようにするショートカット機能。

### 背景・現状

現状のフロー:
1. エラー詳細画面でエラーの内容を確認
2. 別途 `/settings/importance-rules` へ移動
3. ルール作成フォームに `functionEntry` / `errorKey` / `service` を**手入力**
4. 保存

これが手間になる。

### 実装後のフロー

1. エラー詳細画面の「重要度ルールを変更」ボタンをクリック
2. `/settings/importance-rules` のルール作成画面に **`functionEntry` / `errorKey` / `service` が自動入力された状態**で遷移
3. 確認・調整して保存

### 注意点

- ルールの粒度が細かくなりすぎるリスクがある（1エラー1ルール化の防止）
- 自動入力はあくまで「入力補助」であり、保存前に内容確認を促す UI にする

### 参照ドキュメント

- `amuse-admin/docs/改善案一覧.md`（改善案 C として記載）
- `amuse-admin/src/app/(authenticated)/stores/[storeId]/errors/[logId]/page.tsx`（エラー詳細画面）
- `amuse-admin/src/app/(authenticated)/settings/importance-rules/page.tsx`（ルール作成画面）

### 想定工数

1〜2時間（AI フル利用）

## H-2: エラー一括操作

### 概要

エラー一覧画面でチェックボックスによる複数選択を可能にし、選択したエラーをまとめて「対応済み」または `assessment` 設定できるようにする機能。

### 背景・現状

現状は1件ずつ操作する必要がある。同種のエラーが大量発生した際に1件ずつ対応するのは非常に手間。

### 実装内容

- エラー一覧の各行にチェックボックスを追加
- 選択後に「一括対応済みにする」「一括 assessment 設定」のアクションバーを表示
- 誤操作防止のため確認ダイアログを挟む

### 参照ドキュメント

- `amuse-admin/docs/改善案一覧.md`（改善案 F として記載）
- `amuse-admin/src/app/(authenticated)/stores/[storeId]/page.tsx`（エラー一覧）

### 想定工数

2〜3時間（AI フル利用）

## H-3: blockers 異常検知・中央 write ヘルス（後回し事項）

### 概要

scheduler 監視の後回し事項（R1・R2）の実装。

### 現状

| 項目 | 実装状況 |
|---|---|
| blockers の UI 表示（「スキップ（理由あり）」バッジ） | **実装済み**（U5） |
| blockers の自動 anomaly 化・LINE 通知 | **未実装**（§9 R1 として後回し） |
| 中央 write ヘルス doc + HOME 連携表示 | **未実装**（§9 R2 として後回し） |

### blockers とは

HTTP 200 + `logOpsSuccess` で返却されたが、業務上の理由でスキップされたタスクのこと。  
例: `already_running_different_date`（別日付で既に実行中のためスキップ）等。  
技術的には「成功」だが、意図した処理が実行されなかった可能性があるため、監視上の attention が必要。

### 残タスク

1. **blockers の自動 anomaly 化**（R1）  
   - 重要度の高い blocker のみ `schedulerAnomalies` に記録する仕組み
   - 通知対象にするかどうかの判断基準の設計
2. **中央 write ヘルス doc**（R2）  
   - 中央 Firestore への write が部分的に失敗しているケースを検知する仕組み
   - HOME 画面への連携表示

### 参照ドキュメント

- `amuse-admin/docs/scheduler監視強化・UI改善 実装計画.md` §9（後回し事項 R1・R2）
- `amuse-admin/functions/src/detectSchedulerAnomalies.ts`

## H-4: 都度 Task 監視タブの存続判断

### 概要

`amuse-admin` の店舗詳細ページに「都度 Task 監視」タブが実装済みだが、実運用上の価値があるかを観察期間を経て判断し、存続か削除かを決定する。

### 現状

- タブの実装は完了（Phase C として実装・デプロイ済み）
- 2026-06-05〜06-09 の観察で都度系 `taskLogs` 302件、エラー 0件
- 現時点では「タブがないと見逃すケース」の証拠がまだ不十分
- 正本: `amuse-admin/docs/運用時資料/Phase8_都度Task監視要否判断.md`

### 残タスク

1. 一定期間（1週間〜1ヶ月程度）の継続観察
2. 「このタブでしか気づけなかったケース」が発生したかの確認
3. 存続 or 削除の意思決定
4. 削除する場合: タブの非表示化または完全削除

### 判断基準

- 都度系 taskLogs にエラーが記録され、かつ errorLogs では見えにくかったケースがあれば **存続**
- 継続観察期間中もエラー 0件・異常なしであれば **削除候補**

### 参照ドキュメント

- `amuse-admin/docs/運用時資料/Phase8_都度Task監視要否判断.md`

## H-5: LINE 通知送信機能（amuse-admin）

### 概要

amuse-admin の重要度判定機能と連携し、`shouldNotify: true` のエラーが発生した際に LINE で通知を送る機能。

### 現状

| コンポーネント | 状況 |
|---|---|
| 通知先管理 UI（LINE / Email の登録） | **実装済み** |
| `sendLineNotification.ts`（CF） | **実装済み** |
| `POST /api/notify` ルート | **実装済み** |
| `shouldNotify: true` 時の送信処理 | **実装済み**（エラー作成トリガーから呼び出し） |
| LINE Official Account の作成 | **未実施**（人的作業） |
| Channel Access Token の取得・Secret Manager 登録 | **未実施** |
| 実際の送信テスト | **未実施** |

### 残タスク

コード実装は揃っているため、残タスクは**外部サービス設定と疎通確認**が主。

1. LINE Official Account の作成（Messaging API チャンネル）
2. Channel Access Token の取得
3. 中央プロジェクト（`amuse-central-monitoring`）の Secret Manager に Token を登録
4. 通知先として LINE ユーザーを登録
5. テスト通知を送って動作確認

### 参照ドキュメント

- `amuse-admin/docs/後回し事項.md`（§1 として記載）
- `amuse-admin/functions/src/sendLineNotification.ts`
- `amuse-admin/src/app/api/notify/route.ts`
- `amuse-admin/src/app/(authenticated)/settings/notification-targets/page.tsx`
