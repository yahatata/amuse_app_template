## 1. この文書の役割

本書は、`B-1_Config台帳.xlsx` を実際に作成する前に、
「何を根拠に」「どの順で」「どこまでを AI が担い」「どこからを人が判断するか」
を固定するための文書である。

本書で決めること:

- B-1 の作成方針
- 根拠の優先順位
- 全体の進め方
- AI と人の役割分担
- 中間成果物
- 最終成果物
- done 条件

本書で決めないこと:

- 各 config row の具体値
- 実行コマンドの詳細
- 実環境確認の個別手順
- 当日作業のタイムライン
- row 投入の実施順の細部

これらは、config 系の別軸修正が一段落した後に、実作業用の具体化として扱う。

## 3. 作成の前提

B-1 の具体作成は、config 系の別軸実装・修正が一定程度落ち着いた後に行う。  
そのため、本書では「今すぐ埋める方法」ではなく、「後から正確に埋める方法」を定める。

着手開始条件の目安は次の通り。

- config 系の大きな構造変更が一段落している
- 対象とする設定群が概ね固まっている
- 実装、テスト、実環境確認の参照元が把握できる
- `B-1_Config台帳.xlsx` の列構造が確定している

この条件を満たさない段階では、row の大量投入を開始しない。

## 4. 根拠の優先順位

B-1 の記載内容は、次の優先順位で根拠を取る。

| 優先順位 | 根拠 | 使い方 |
|---|---|---|
| 1 | 実装コード | 設定項目の存在、保存先、型、fallback、読取箇所、初期化方法の主根拠とする |
| 2 | テストコードとテスト実行結果 | 実装解釈が正しいか、境界条件や fallback が確認済みかの根拠とする |
| 3 | Firestore 実値 / Emulator / Log / 実行結果 | 実装想定と実データ構造が一致しているかの確認根拠とする |
| 4 | 既存ドキュメント | 背景説明、業務意図、既存整理内容の補助根拠とする |

重要事項:

- 既存ドキュメントだけを根拠に row を確定しない
- docs は補助資料であり、正本ではない
- 実装と docs が食い違う場合は、まず実装を正として差分を記録する
- 実装が不十分で業務意図が不明な場合のみ、人判断で補う

---

## 5. B-1 の位置づけ

`B-1_Config台帳` は、設定項目の「現在値台帳」ではなく「定義台帳」である。  
主に次を正本として持つ。

- どの設定項目が存在するか
- どこに保存されるか
- 何を制御する設定か
- どのような値を許容するか
- 未設定時にどう動くか
- どの値を標準値として推奨するか
- 誰がどう変更する設定か
- 導入時にどう初期設定するか
- どの function / 画面 / 処理が参照するか

原則として持たないもの:

- 環境ごとの現在値
- Secret の実値
- 単なるコード定数
- 一時デバッグ値
- 仕様未確定の試験用値

対象設定群の初期候補は、
`docs/残タスク_0623/カテゴリB_本番化横断整理/B-1_Config台帳_説明.md`
の管理対象叩きを起点とし、実作業着手時に確定する。  
カテゴリ B 全体の中で B-1 が担う範囲は、
`docs/残タスク_0623/カテゴリB_本番化横断整理/検討時叩き2.md`
を参照する。

## 6. 全体の進め方

B-1 は、次の段階で作成する。

| 段階 | 目的 | この段階で行うこと | 気をつけること | 中間成果物 | CFG ID の扱い |
|---|---|---|---|---|---|
| 0. 着手判定 | 今着手してよい状態かを確認する | 別軸 config 修正の進捗、対象範囲、参照元の準備状況を確認する | 構造変動中に row を大量投入しない | 着手可否メモ | まだ採番しない |
| 1. 対象範囲固定 | 何を B-1 に入れるかを確定する | 対象設定群と対象外を明示する | 現在値管理と定義管理を混同しない | 対象一覧 | まだ採番しない |
| 2. 根拠棚卸し | どこを見れば埋められるかを揃える | 実装、テスト、実環境確認方法、既存 docs を棚卸しする | docs を先に正にしない | 根拠一覧 | まだ採番しない |
| 3. AI 一次草案 | 台帳 row のたたきを作る | AI がコードを読み、各 row の草案を出す | 推測を断定しない。未確定は未確定と残す | row 草案 | 仮採番可 |
| 4. 根拠強化 | 草案に証拠を付ける | テストコード確認、必要に応じて test 実行結果や実環境 shape 確認を行う | コード上の定義と実運用 shape の差を見逃さない | 根拠付き草案 | 仮採番のまま可 |
| 5. 人判断 | 業務判断を確定する | 標準値、変更方法、初期設定方法、現役区分などを確定する | AI が埋めにくい運用判断を放置しない | 確定前レビュー版 | 未採番・仮採番の最終確認 |
| 6. 正本反映 | Excel 正本と説明資料を完成させる | 承認済み row を `B-1_Config台帳.xlsx` へ反映し、`B-1_Config台帳_説明.md` を Excel と整合した状態に仕上げる | 構造変更と内容更新を混ぜない | 正本更新版 | 確定採番 |
| 7. 閉じ方整理 | B-1 完了状態を整える | `検討時叩き2`、関連資料、差し戻し先との整合を確認し、done 判定を整理する | 未解決を B-1 に埋め込んだまま閉じない | 完了記録 / 差し戻し先整理 | 確定済み前提 |

## 7. 各段階での考え方

### 7.1 対象範囲固定時の考え方

対象範囲固定では、「どの doc を含めるか」ではなく「どの設定概念を B-1 で管理すべきか」を決める。  
この時点では row 単位の詳細確定までは行わない。

特に次を分けて考える。

- 本番挙動に直接効く設定
- 導入時に初期投入する設定
- 将来拡張用の設定
- 読取はされるが現在は業務上の重要度が低い設定

判断観点:

- 店舗運用や本番動作に実際に影響するか
- 設定値により function / UI / scheduler / 業務フローの挙動が変わるか
- 導入時や保守時に人が判断する必要があるか
- 定義を持つべき対象か、現在値管理に寄せるべき対象か

### 7.2 AI 一次草案作成時の考え方

AI 一次草案では、まず「コードから確実に言えること」を埋める。  
逆に、業務判断や運用判断が必要なものは仮説として扱う。

AI が優先して埋める対象:

- `保存path`
- `field名`
- `型`
- `許容値・形式`
- `未設定時挙動`
- `デフォルト値`
- `主な利用元`
- `反映タイミング` の仮説
- `業務意味` の草案

AI が仮置きに留める対象:

- `標準値（推奨値）`
- `変更方法`
- `初期設定方法`
- `現役区分`
- 一部の `業務意味`
- 将来用設定の扱い

重要事項:

- 実装にない事実を断定しない
- fallback と initial write を混同しない
- docs の文言をそのまま転記して終わらない
- `未確認` `判断待ち` を適切に残す
- 候補値列（`config区分`、`現役区分`、`未設定時挙動` など）の正式意味は `docs/残タスク_0623/共通資料/02_用語・ステータス定義.md` を正本とする
- AI 一次草案では、`B-1_Config台帳_説明.md` の初期候補値リストを参照してよいが、意味の最終判断は `02` に合わせる

### 7.3 根拠強化時の考え方

一次草案の後は、各 row の裏取りを行う。  
ここでは「書けるか」ではなく「書いた内容を正としてよいか」を確認する。

主な確認観点:

- defaults と loader の整合
- runtime fallback と initialize 時の初期値の差
- enum / 範囲 / null 許容の扱い
- 実際にテストで通っているか
- Firestore 実値の shape が実装想定とズレていないか
- 読取元と利用元の洗い出し漏れがないか

### 7.4 人判断時の考え方

人が決めるべきことは、「実装がどうなっているか」ではなく「運用としてどう扱うか」である。

人判断の主対象:

- 標準値として何を推奨するか
- ユーザーが UI で変えてよいか
- 保守運用者が導入時に設定すべきか
- 現時点で `live / legacy / planned / delete候補` のどれか
- 将来拡張用設定を現時点でどの重さで扱うか

## 8. AI と人の役割分担

| 領域 | AI が担うこと | 人が担うこと |
|---|---|---|
| 実装把握 | code search、loader/defaults/types 読解、利用元洗い出し | 解釈の最終承認 |
| 草案作成 | row 草案、業務意味の初稿、候補値整理 | 初稿の採否判断 |
| テスト整理 | 対応テスト抽出、実行候補整理、結果要約 | 実行要否判断、結果の最終評価 |
| 実環境確認 | 実行用コマンド案、抽出観点整理、結果整理 | 認証が必要な確認実行、結果の信用判断 |
| 運用判断 | 判断論点の列挙、選択肢整理 | 標準値、変更方法、初期設定方法、現役区分の最終決定 |
| 正本反映 | Excel 反映用の整形出力、説明資料の更新案作成 | ChatGPT for Excel 実行、最終確認 |

原則:

- AI は「広く拾う」「整理する」「たたきを作る」を積極的に担う
- 人は「本番運用の意思決定」と「認証が必要な確認」に集中する
- AI が不確かなものは、無理に埋めず `未確認` `判断待ち` として残す

## 9. 中間で持つ成果物

B-1 作成の途中では、最終正本とは別に次の中間成果物を持つ。  
ただし、正式資料を増やしすぎないことを優先し、必要最小限に留める。

| 中間成果物 | 目的 | 持ち方 |
|---|---|---|
| 対象一覧 | B-1 に入れる設定群と対象外を固定する | 本書の章または作業メモ |
| 根拠一覧 | どのコード、テスト、実環境確認を根拠にするかを揃える | 本書の章または作業メモ |
| row 草案 | Excel 反映前の候補行を作る | 表形式の作業出力 |
| 未解決論点一覧 | 人判断が必要な点を残す | 作業メモまたはレビューコメント |
| 差し戻し先一覧 | B-1 だけでは閉じられない問題を返す先を明確にする | 完了時まとめ |

運用方針:

- 中間成果物は原則として恒久資料にしない
- 恒久的に残すべき情報だけを `B-1_Config台帳.xlsx`、`B-1_Config台帳_説明.md`、または関連正式資料へ反映する
- 一時的な作業メモを正式正本に昇格させない

## 10. 最終成果物

B-1 完了時点での最終成果物は次の通り。

| 成果物 | 役割 |
|---|---|
| `B-1_Config台帳.xlsx` | 設定定義のデータ正本 |
| `docs/残タスク_0623/カテゴリB_本番化横断整理/B-1_Config台帳_説明.md` | 台帳の目的、列、管理対象、更新ルールの説明 |
| 差し戻し先整理 | B-1 だけでは閉じない論点を B-2、C-1、G-3 などへ返すための整理結果 |

必要に応じて副次的に残すもの:

- 作成時の確認結果要約
- 実環境 shape 確認結果
- テスト実行結果の参照先

ただし、これらを新たな恒久資料として増やすかは、情報の再利用性を見て判断する。

## 11. B-1 のゴール

B-1 のゴールは、「設定項目の定義と扱い方が、コード・テスト・実運用の観点から説明できる状態」を作ることである。

B-1 完了時に言えるべきこと:

- 対象設定項目が漏れなく列挙されている
- 各設定がどこに保存されるか説明できる
- 各設定の型、許容値、未設定時挙動が説明できる
- デフォルト値と標準値の違いが説明できる
- どの function / UI / 処理が参照するか追える
- 変更方法と初期設定方法が説明できる
- 不明点は不明点として残され、返却先が決まっている

---

## 12. done 条件

高リスク設定とは、未設定・誤設定・fallback の誤解により、給与・会計・scheduler・権限・本番停止など、店舗運用または法令・会計処理に直結しうる設定項目を指す。  
高リスク設定については、段階 4 でテストまたは実環境 shape 確認を省略しない。

B-1 は、次の条件を満たした時に done とする。

- `B-1_Config台帳.xlsx` に対象範囲の row が投入されている
- `docs/残タスク_0623/カテゴリB_本番化横断整理/B-1_Config台帳_説明.md` が Excel と整合した完成状態になっている
- `B-1_Config台帳_説明.md` と Excel の列構造、候補値方針、更新ルールが一致している
- 高リスク設定について、コード・テスト・必要な実環境確認の裏取りが済んでいる
- 人判断が必要な列が放置されていない
- B-1 だけで閉じない論点の差し戻し先が決まっている

次の状態は done としない。

- docs を見て埋めただけ
- コード参照が不十分
- 実環境 shape 確認が必要な項目を未確認のまま閉じる
- `標準値` や `変更方法` が曖昧なまま残っている
- 不明点を備考に埋め込んだだけで返却先がない

---

## 13. B-1 で特に注意すること

- `現在値` と `定義` を混同しない
- runtime fallback と initialize 時の初期書き込み値を混同しない
- `config` と `requiredStaffByTimeSlot` のように挙動設計が異なる設定を同列に雑に扱わない
- `taxReportingBehavior` や `reportingGroupConfig` のように、実装・テスト根拠が相対的に薄い設定群は確認強度差を意識する
- 将来拡張用設定を、現行必須設定と同じ重さで扱わない
- 一時作業メモをそのまま正本にしない

---

## 14. 着手時に再確認すること

実際に B-1 作成へ着手する時は、まず次を再確認する。

- config 系の別軸修正で対象 field が変わっていないか
- `B-1_Config台帳.xlsx` の列構造に追加修正が必要ないか
- 対象範囲に増減がないか
- 実環境確認の方法が変わっていないか
- `検討時叩き2`、B-2、C-1、G-3 との役割分担が変わっていないか

この再確認で差分が出た場合は、B-1 の実作業開始前に本書を更新する。
