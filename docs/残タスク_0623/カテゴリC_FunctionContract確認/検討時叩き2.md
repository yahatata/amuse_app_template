# カテゴリC: Function/Contract確認 — 検討時叩き2

> 位置づけ: 業務フロー確認の前に、function 単位で構造・契約・確認責任を揃える工程

---

## このカテゴリで答える問い

- 各 function は、何を受けて何を更新するか
- 前提条件、権限、`businessDate`、`idempotency` はどう扱うか
- どこまでを自動テストで担保し、どこからを実機確認に回すか
- 未整理の危険点は、どのカテゴリへ返すべきか

---

## 目標と実施内容

| 目標 | 実施内容 | 主な成果物 |
|---|---|---|
| 対象 function を漏れなく洗い出す | callable / trigger / schedule / app 起点処理を列挙し、営業開始スコープを確定する | Function一覧、Function-Flow対応表 |
| contract を明文化する | 入力、前提条件、更新先、エラー、監査ログ、config 依存を整理する | Function/Contract台帳 |
| 確認責任を分ける | `自動テストで担保` `実機必須` `人レビュー必須` を function ごとに決める | 確認責任マッピング |
| 問題を前工程へ返す | 危険な未実装、未決仕様、未テスト箇所を A/B/D に起票する | 高リスク論点一覧 |

---

## このカテゴリで作成する資料

| 資料名 | 目的 | 資料だけで完了か |
|---|---|---|
| Function/Contract台帳 | function 単位の事実整理 | はい |
| Function-Flow対応表 | function と業務フローの接続整理 | はい |
| 確認責任マッピング | 自動テストと実機確認の境界整理 | はい |
| 高リスク論点一覧 | 差し戻し先を明確にする | はい |

---

## サブタスク

### C-1: 対象 function の棚卸し

- callable / trigger / schedule / app 起点処理を列挙する
- 営業開始対象と営業開始後対象を分ける
- Flow ID と結び付けるための識別子を付ける

### C-2: Function/Contract台帳の作成

- 1 function 1行で整理する
- 入力パラメータ、前提条件、主要更新コレクション、主要更新フィールドを記載する
- ログ、監査、エラー出力、戻り値の扱いも記載する
- `businessDate`、`idempotencyKey`、config 依存も記載する

### C-3: 確認方法の切り分け

- 自動テストで十分なものを分ける
- emulator / integration / device / manual が必要なものを分ける
- 実機必須の理由を残す

### C-4: 差し戻し論点の整理

- A に返すもの: 未決仕様、未実装機能
- B に返すもの: rules、権限、config、secret、暫定実装
- D に返すもの: 業務フロー受入で確認すべき論点

---

## 完了条件

- 営業開始対象の function が漏れなく列挙されている
- 各 function に contract 情報が埋まっている
- 確認責任が `自動テスト / 実機 / 人レビュー` に切り分けられている
- 未整理の危険点が放置されず、返却先が決まっている

---

## 他カテゴリとの依存

- B の config / rules / secret 方針が固まっているほど精度が上がる
- D は C の台帳を前提資料として使う
- C 自体は資料中心で進めるが、必要に応じて人による spot check を入れる
