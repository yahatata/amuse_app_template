# カテゴリE: 導入フロー設計 — 検討時叩き2

> 位置づけ: 第2店舗以降への導入を、再現可能な手順として固定する工程

---

## このカテゴリで答える問い

- 新規店舗へ、どの順で、誰が、何を設定すれば稼働まで進められるか
- 端末設定、LINE/LIFF、初期データ移行をどこで実施するか
- 導入時に失敗しやすい箇所を、手順とチェックリストでどう潰すか

---

## 目標と実施内容

| 目標 | 実施内容 | 主な成果物 |
|---|---|---|
| 導入全体の順序を固定する | Firebase 作成、初期設定、スタッフ発行、端末設定、初回確認までを並べる | 導入チェックリスト |
| 端末設定を再現可能にする | admin / terminal / table ごとの設定手順、再インストール時挙動、アップデート手順を整理する | デバイス設定手順書 |
| LINE / LIFF の導入手順を固める | OA 作成、LIFF 登録、Webhook 設定、疎通確認の順序を決める | LINE/LIFF設定手順書 |
| 初期データと切替を整理する | 既存ユーザーデータ移行、初期ポイント、担当者、所要時間、切替順序を整理する | 移行手順書、切替 runbook |

---

## サブタスク

### E-1: 店舗導入フローの整理

- テンプレート適用から本番稼働までの順序を定義する
- 担当者、所要時間、前提条件を明記する

### E-2: デバイス設定フローの整理

- admin / terminal / table の初期設定手順を分ける
- 再ダウンロード、再インストール、アップデート時の挙動を確認する

### E-3: LINE / LIFF 導入手順の整理

- 顧客向け LIFF、スタッフ向け LIFF、リッチメニュー、Webhook を整理する
- F の実設定と矛盾しないように順序を揃える

### E-4: 既存ユーザーデータ移行方針の整理

- 初期ポイント、既存会員、引継ぎ範囲、登録方法を整理する
- A-6 と連動して、導入時に必要な現実解を定める

### E-5: 導入 dry-run と手順修正

- 手順を机上で終わらせず、模擬実施または試験導入で確認する
- トラブルや抜け漏れを反映して最終版化する

---

## 完了条件

- 導入順序、担当者、前提条件が資料で一意に分かる
- 端末設定と LIFF 設定の手順が再現可能になっている
- 既存ユーザーデータ移行の扱いが決まっている
- dry-run または模擬実施で大きな手戻りがない

---

## 他カテゴリとの依存

- A-6 の仕様整理と強く連動する
- F の実設定内容を E の手順に落とし込む
- G の導入マニュアル類は E の成果物を元に作る
