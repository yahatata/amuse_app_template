# 01_資料ライフサイクル・更新ルール

> 概要: 残タスク整理に関する資料の作成・更新・参照・廃止の共通ルールを定める文書
> 主な目的: 正本管理、更新漏れ防止、形式統一、運用開始後の維持方針の固定
> 正本区分: md正本
> 対象: 現時点では `docs/残タスク_0623` 配下の全資料、およびそれに対応する sheet
> 更新区分: 変更時
> 参照元: なし
> 参照先: `00_資料台帳`、`02_用語・ステータス定義`

---

## 1. 目的

この文書は、資料を「作る」「更新する」「参照する」「廃止する」までの共通ルールを定める。  
各資料の個別目的、個別done条件、個別の更新頻度、個別の許容条件は本書では持たず、`00_資料台帳` で管理する。  
本書は全資料に共通する原則と運用方法のみを扱う。

現時点の正本ファイルは本ファイルだが、再編後は `ART-002_資料ライフサイクル・更新ルール.md` へ移設・改名する前提で運用する。  
ただし、実移設が完了するまでは、参照 path は現在の file path を正とする。

---

## 2. 適用範囲

本書は以下に適用する。

- `docs/残タスク_0623` 配下の md 資料および TSK 資料
- `docs/業務管理資料` 配下の ART 正式資料
- `docs/残タスク_0623/共通/` 配下の共通資料（ART-901〜906）
- 正本または補助資料として利用する sheet
- sheet の説明用 md
- 今後追加される関連資料
- Cursor rules、Codex memory、ChatGPT memory に反映する要約ルール

`docs/残タスク_0623` 配下は残タスク管理資料の置き場、`docs/業務管理資料` 配下は今後も参照・更新し続ける正式資料の置き場として確定している。  
本書のルールはこの両方に適用する。

## 3. 共通原則

### 3.1 正本原則

- 1つの事実は1つの正本にだけ持つ
- 同じ事実を複数資料に直書きしない
- 正本を更新した場合は、参照資料側へ追随反映する
- 参照資料は正本の代替として扱わない
- 暫定メモは正本として扱わない
- 資料完成と実体反映は分けて扱う
- 資料の削除より、アーカイブを優先する

### 3.2 形式原則

- 一覧管理は台帳、説明は md を原則とする
- 行が増える管理資料は sheet を原則とする
- 方針、説明、手順、補足は md を原則とする
- sheet を正本にする資料は、必ず対応する説明用 md を持つ
- 対応する説明用 md には、その sheet が何の資料か、何のために使うか、どの列を持つか、どのように更新するかを記載する
- sheet 正本の説明用 md には、必ず「1行の単位」を記載する
- 説明用 md はあくまで補助であり、基本的には台帳(sheet)のみで内容が理解できるものの作成を目指す
- md のみで完結する資料は、md 自体を正本とする

### 3.3 構造原則

- 1ファイル1目的を原則とする
- 1資料1正本を原則とする
- 1行1件、1列1意味、1セル1値を原則とする
- 色は意味の補助としてのみ使い、意味は必ず列値でも持つ
- 結合セルは禁止する
- 空行・空列を構造として使わない
- 行削除より状態変更を優先する
- 色、装飾、セル位置だけに意味を持たせない
- 意味のある状態、重要度、区分は必ず文字列または列として保持する

### 3.4 参照原則

- 正本を更新した場合は、まず `ART-001_資料台帳` の `参照元` `参照先` と本文中の明示参照を使って関連資料を洗い出す
- 参照先資料は漏れなく確認する
- 参照先資料の更新要否を、網羅的かつ丁寧に判断する
- 正本更新後に参照先資料を放置しない
- 正本の更新が完了するまで、参照資料のみを先に更新しない
- 独立した `03_資料対応表` は、現時点では作成前提にしない

### 3.5 配置変更耐性原則

- 将来的に資料が `docs/残タスク_0623` の外へ移る可能性を前提とする
- 資料本文では「このフォルダのカテゴリXを参照する」など、現在の親子フォルダ構造に強く依存した表現を原則避ける
- 参照は、可能な限り `資料ID + repo相対パス` の組み合わせで表現する
- フォルダの近さや同階層であることを前提に意味を持たせない
- フォルダ構成が変わっても、資料の意味や参照先が追える構造を保つ

## 4. 標準記法

### 4.1 日付・時刻・日時

- 日付は `YYYY-MM-DD` で統一する
- 時刻は `HH:mm` の24時間表記で統一する
- 日時は `YYYY-MM-DD HH:mm` で統一する
- タイムゾーンが意味を持つ場合は、`JST` または `UTC` を明記する
- タイムゾーンが暗黙になる表記は避ける

### 4.2 真偽値

- sheet 上の真偽値は `TRUE/FALSE` に統一する
- md 上で説明文として書く場合は自然文でよいが、表や定義として持つ場合は `TRUE/FALSE` を優先する

### 4.3 空欄・不明値

- 空欄を意味値として使わない
- 不明な場合は `未確認`
- 将来確定予定の場合は `TBD`
- 該当しない場合は `該当なし`
- 廃止済みの場合は `廃止`
- 意図的な未入力と未確認を混同しない

### 4.4 パス表記

- repo 内資料の参照は、原則として repo ルートからの相対パスで記載する
- 参照先がファイルかフォルダかを明確にする
- パスの表記ゆれを避ける

### 4.5 バージョン表記

- バージョンを持つ場合は `vX.Y.Z` を原則とする
- 日付ベースで管理する場合は `YYYY-MM-DD` を使う
- バージョンと日付を併用する場合は役割を分ける

### 4.6 ID と参照表記

- 他資料から参照される対象には、原則として固有IDを持たせる
- 最低限、正式資料と function には固有IDを持たせる
- 推奨として、config項目、flow、test、defect、外部サービス設定項目も固有IDを持たせる
- IDの付番ルールそのものは本書で定義し、実際の採番は各台帳作成時に行う
- 一度採番したIDは再利用しない
- 名称変更があってもIDは維持する
- 他資料から参照する時は、原則として `ID + 短い名称` の形で記載する
- 正式資料は `ART-xxx` を使う
- 残タスク管理側のタスク資料は `TSK-xxx` を使う
- 旧資料に残る `DOC-xxx` は移行対象であり、新規の正式資料命名には使わない
- 接頭辞の正式意味、補助状態、候補値の正式定義は `02_用語・ステータス定義` を正本とする
- 例:
- `ART-002 資料ライフサイクル・更新ルール`
- `FN-012 finalizePayrollRun`

### 4.7 ID接頭辞の標準

- 正式資料: `ART-xxx`
- タスク資料: `TSK-xxx`
- function: `FN-xxx`
- config: `CFG-xxx`
- flow: `FLOW-xxx`
- test: `TEST-xxx`
- defect: `DEF-xxx`
- 必要に応じて追加してよいが、接頭辞の意味は `02_用語・ステータス定義` に追記する

## 5. 資料先頭の必須記載

すべての md 資料の先頭には、最低限以下を記載する。

- 概要
- 主な目的
- 正本区分
- 対象
- 更新区分
- 参照元
- 参照先

sheet が正本の資料に対応する説明用 md では、上記に加えて以下も記載する。

- 対応する workbook 名
- 主シート名
- 1行の単位
- 主な列
- 更新時の注意点

## 6. 命名規則

### 6.1 正式資料の md 正本

- 形式: `ART-xxx_資料名.md`
- 例: `ART-002_資料ライフサイクル・更新ルール.md`

### 6.2 正式資料の sheet 正本

- 形式: `ART-xxx_資料名.xlsx`
- 例: `ART-001_資料台帳.xlsx`

### 6.3 sheet の説明用 md

- 形式: `ART-xxx_資料名_説明.md`
- 例: `ART-001_資料台帳_説明.md`

### 6.4 タスク資料

- `内容`: `TSK-xxx_資料名_内容.md`
- `進め方`: `TSK-xxx_資料名_進め方.md`
- `実施まとめ`: `TSK-xxx_資料名_実施まとめ.md`
- `申し送り`: `TSK-xxx_資料名_申し送り.md`

### 6.5 命名上の判別ルール

- `ART-xxx` は正式資料
- `TSK-xxx` は残タスク管理側のタスク資料
- `.md` かつ `_説明` があるものは、対応する sheet の説明資料
- `.xlsx` は sheet 正本
- 正本か説明かが一目で分かる名前を必ず採用する
- 旧方針で作成済みの `00_` `01_` などの命名は、移設・改名完了までの暫定 legacy として扱う

## 7. 資料ライフサイクル定義

| 状態 | 意味 |
|---|---|
| 構想中 | 作成要否を検討中で、正本未作成 |
| テンプレ確定 | フォーマットだけ固まっている |
| 作成中 | 初回記入を進めている |
| レビュー中 | 内容確認中で確定前 |
| 運用中 | 正本として維持している |
| 凍結 | 変更予定がなく履歴として保持 |
| 廃止予定 | 置換や統合により終了予定 |
| 廃止済 | 現行用途を終えた |
| アーカイブ | 閲覧専用で保持 |

補足:

- 各状態の正式な使い分けは `02_用語・ステータス定義` を正本とする

---

## 8. 作成前ルール

- 新しい資料は、作成前に `ART-001_資料台帳` へ登録する
- 新しい正式資料は、`ART-xxx` を前提に設計する
- 新しい作業タスクは、`TSK-xxx` を前提に設計し、`ART-902_タスク管理台帳` へ登録する
- 作成前に、その資料が正本か参照資料かを決める
- 作成前に、md 正本か sheet 正本かを決める
- 作成前に、参照元資料と参照先資料を決める
- 作成前に、更新区分を `継続 / 変更時 / 節目 / 単発` から決める
- 既存資料で代替可能な場合は、新規資料を増やさない
- 目的が曖昧な資料は作成しない
- 用語、候補値、接頭辞、補助状態の定義が必要な場合は `02_用語・ステータス定義` を先に確認する

---

## 9. 初期フォーマット作成時ルール

- カラムや章立ては「何を判断するために必要か」で決める
- 便利そうという理由だけで列を増やさない
- 共通項目と資料固有項目を分ける
- 共通項目は可能な範囲で統一する
- 初版は小さく作り、試行後に拡張する
- 状態、重要度、区分、更新区分、真偽値などは入力規則で選べるようにする
- 状態、区分、更新区分、利用タイミングなどの候補値は、`02_用語・ステータス定義` を基準にそろえる
- 条件付き書式は一般的な範囲で積極的に利用してよい
- ただし、条件付き書式だけに意味を持たせない
- 数式列がある場合は、説明用 md に「どの列が数式列か」を記載する

---

## 10. 具体資料作成時ルール

- 未確認事項は空欄ではなく `未確認` `判断待ち` `保留` などで記載する
- 推測は推測であると明記する
- 正本にない事実を断定記載しない
- 他資料から転記した内容は転記元を辿れるようにする
- 暫定記載には `暫定` と分かる表現を付ける
- 導入開始後に不要となる開発時専用情報は、原則として削除ではなく `非表示 / アーカイブ / 別シート退避` で扱う
- 開発時専用情報を削除する場合は、削除前に履歴をどこへ残すか決める

---

## 11. レビュー・確定ルール

- 正本化前に、最低限の内容確認を行う
- 確認観点は以下を基本とする
- 目的に沿っているか
- 正本と参照の関係が崩れていないか
- 他資料と矛盾していないか
- 更新時に迷わない構造になっているか
- 説明用 md が必要な資料に説明用 md が存在するか
- 確定後はライフサイクル状態を更新する

---

## 12. 更新時ルール

- 正本更新時は、まず `ART-001_資料台帳` の `参照元` `参照先` と本文中の明示参照から関連資料を全件抽出する
- 抽出した参照資料は、すべて更新要否を確認する
- 正本の更新を行った場合、それを参照している資料がもれなく抽出できるよう、網羅的かつ丁寧な確認を行う
- 仕様変更、画面変更、設定変更、権限変更、フロー変更、運用変更のいずれかが発生した場合は、関連資料の更新要否を確認する
- 意味変更を伴う更新と、体裁だけの更新は区別する
- 変更理由と変更点が後から追えるようにする
- 正本の更新が完了するまで、参照資料のみを先に更新しない

---

## 13. 更新区分の定義

| 区分 | 意味 |
|---|---|
| 継続 | 運用中も継続的に更新される |
| 変更時 | 関連仕様や構造が変わった時だけ更新する |
| 節目 | リリース、受入、導入、監査などの節目で更新する |
| 単発 | 開発終盤や個別案件で一度作成し、完了後は履歴として保持する |

## 14. sheet / Excel 作成ルール

- 原則として 1資料 = 1 workbook とする
- 原則として 1資料 = 1主シート とする
- 補助シートは `master` `validation` `history` `readme` 程度に限定する
- workbook 名と説明用 md の資料名は一致させる
- 主シートは Excel のテーブル機能を使う
- 先頭行は固定する
- フィルタは有効化する
- 結合セルは禁止する
- 空行・空列を構造として使わない
- 状態、重要度、区分、真偽値、更新区分などは入力規則によるリスト化を積極的に利用する
- 条件付き書式は一般的な範囲で積極的に利用してよい
- ただし色だけに意味を持たせない
- 数式列がある場合は、説明用 md に「どの列が数式列か」を記載する
- 日付形式は `YYYY-MM-DD` で統一する
- ID列は途中で意味変更しない
- 履歴が必要な台帳では、行削除より状態変更を優先する
- 説明用 md は補助資料であり、sheet 単体でも内容理解と更新判断ができる構造を目指す
- 複雑な sheet は、生成時に用いた代表プロンプトの要約を説明用 md に残す

## 15. ChatGPT for Excel 利用ルール

### 15.1 基本方針

- sheet の新規作成、列設計、更新、抽出には ChatGPT for Excel を利用してよい
- Cursor、Codex、ChatGPT は sheet を直接安定的に扱えない前提で運用する
- そのため、sheet 正本には必ず説明用 md を付ける
- その上で、必要に応じて ChatGPT for Excel に対して適切なプロンプトを投げて補助させる

### 15.2 新規作成プロンプトで必ず指定すること

- workbook 名
- 主シート名
- この資料の目的
- 1行1件の単位
- 必須列と列順
- 各列の意味
- 各列の入力値の型
- 入力規則にする列と候補値
- 数式列の有無
- フィルタ、固定、テーブル化の要否
- 条件付き書式の要否
- 作ってはいけないもの
- 出力後に要約してほしい内容

### 15.3 更新プロンプトで必ず指定すること

- 対象 workbook 名
- 対象シート名
- 今回の更新目的
- 追加する列、削除する列、変更する列
- 既存データへの影響
- 入力規則の変更有無
- 維持すべき列順
- 変更後に出力してほしい差分要約

### 15.4 抽出プロンプトで必ず指定すること

- 対象 workbook 名
- 対象シート名
- 何を知りたいか
- 必要な列だけ
- 必要な行だけ
- 抽出条件
- 並び順
- 出力形式
- 件数の明記
- 抽出日時の明記

### 15.5 差分確認プロンプトで必ず指定すること

- 比較対象
- 比較観点
- 列定義の差分
- 入力規則の差分
- データの差分
- 変更理由の候補
- AIへ返すための機械可読な出力形式

### 15.6 プロンプト作成時の共通ルール

- 目的を最初に書く
- 1行の単位を明示する
- 列順を固定で指定する
- 候補値は列挙で指定する
- 自由入力列と制約列を分けて指示する
- ChatGPT for Excel への抽出依頼は、必ず出力形式を指定する
- 出力形式は、その時々で最も AI が理解しやすいものを選ぶ
- 不要な自動補完や推測を禁止する
- 例示行が必要なら、例示であることを明記する
- 構造変更とデータ更新を同時依頼しない
- 大きな更新は、構造変更と内容更新を分けて依頼する

### 15.7 推奨する出力形式

| 用途 | 推奨形式 |
|---|---|
| 構造説明 | Markdown |
| 行データ抽出 | TSVコードブロック |
| 差分確認 | Markdown表 + 短い要約 |
| 候補値一覧 | 箇条書きまたはTSV |
| 条件付き要約 | Markdown |

### 15.8 再現性の確保

- 複雑な sheet については、作成や更新に使った代表プロンプトを説明用 md に残してよい
- 少なくとも「どのような条件で作ったか」は説明用 md 側に要約する
- 複雑な sheet は、生成プロンプト要約を説明用 md に残す
- 構造変更時は、説明用 md 側の列説明も同時に更新する

## 16. AI が sheet 内容を把握する時のルール

- Cursor、Codex、ChatGPT が sheet の中身を知る必要がある時は、まず説明用 md を読む
- 説明用 md を読んだ後で、必要な情報だけを ChatGPT for Excel に抽出させる
- AI は人に「要約して」と頼まず、ChatGPT for Excel に投げるための具体プロンプトを生成する
- ユーザーはそのプロンプトを ChatGPT for Excel に渡し、出力結果をそのまま AI に戻す
- 抽出結果は、可能な限り機械可読な形式で受け取る
- 抽出時は、出力形式を必ず指定する
- 出力形式は、その時点で最も AI が理解しやすい形式を選ぶ
- 抽出結果には、件数・抽出日時・抽出条件を必ず含める
- 必要な列だけを抽出し、全件出力は避ける
- 意味解釈が必要な時は、行データと説明用 md をセットで読む

## 17. 導入開始後の更新ルール

- 導入開始後も `運用中` の資料は正本として維持する
- 各資料の更新区分は `継続 / 変更時 / 節目 / 単発` で管理する
- 運用開始後の仕様変更、設定変更、障害対応、運用改善が発生した場合は、関連資料の更新要否を確認する
- 月次、またはリリース単位で、資料未反映がないか点検する
- 単発資料は運用中に継続更新しない
- 節目資料は、次の節目まで履歴として保持する
- 継続資料でも、更新のたびに構造を変えない
- 開発時専用情報は、導入開始後に原則アーカイブまたは非表示とする
- 開発時専用情報を完全に削除する場合は、削除前に履歴保全を行う

---

## 18. 廃止・統合・置換ルール

- 資料を廃止する時は、なぜ廃止するかを残す
- 新しい正本に置き換える時は、置換先を明記する
- 廃止した資料は削除せず、`廃止済` または `アーカイブ` にする
- 旧資料には「この資料は正本ではない」と明記する
- `00_資料台帳` の `参照元` `参照先` と、関連資料側の参照記載を更新する
- sheet を廃止する場合も、対応する説明用 md に廃止理由と置換先を書く

---

## 19. 例外運用ルール

- 緊急障害時は、先に実装修正して後追いで資料更新してよい
- ただし資料更新は、原則として当日中または翌営業日中に行う
- 暫定対応は正本ではなく `暫定対応` として記録する
- 暫定状態を恒久状態として放置しない
- 例外運用を行った場合は、後で正本へ反映するか、廃止するかを必ず判断する

## 21. Cursor / Codex / ChatGPT memory への反映方針

- この文書を docs 上の正本とする
- rules や memory は、本書の要約版または実行版として扱う
- 本書を更新した場合は、Cursor rules、Codex memory、ChatGPT memory も網羅的に更新する
- rules や memory だけを先に変更しない
- 変更順は `docs 正本更新 -> rules 更新 -> memory 更新` を原則とする
- rules や memory に記載する内容は、本書と矛盾させない
- rules や memory への反映が未了の時は、その状態を明示する
