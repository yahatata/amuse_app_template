## 2. 背景

店舗デバイス側では、既にトーナメント参加登録、待機者確認、着席・配置など、トーナメント運営に必要な基本操作が行える。

一方、実際の店舗運営では、ユーザー本人がまだ店舗に到着していない状態であっても、店舗側が事前に参加意思を確認し、置きバケとして扱うケースがある。

置きバケは、単なる予約や軽い参加意思表示ではなく、店舗がユーザー本人の参加意思を確認したうえで、トーナメント上の参加者として扱うための運用である。

現状、この置きバケ運用をシステム上で明確に扱えない場合、以下の問題が発生する。

- 実際の参加状態とシステム上の参加状態がズレる
- 参加人数やプライズ計算に置きバケ分を反映しづらい
- 置きバケ参加者を席・テーブル状態に正しく反映しづらい
- 後から実ユーザーや会計に接続しづらい
- ユーザーが来店しなかった場合の未接続・未会計状態を確認しづらい
- トーナメント履歴やリシート上に置きバケ操作を残しづらい
- 操作を戻す対象として置きバケを扱いづらい

そのため、本仕様では、置きバケを店舗デバイス上の正式な運用対象として扱えるようにする。

なお、今回の主対象は LINEミニアプリ機能ではない。

LINEミニアプリ側は、入店済ユーザーの通常参加登録やトーナメント情報表示の整理など、置きバケ対応に関連する周辺機能として扱う。

置きバケ操作そのものは、LINEミニアプリからは行わず、店舗デバイス上で店舗スタッフが行う。

## 3. 基本方針

### 3.1 標準運用を主軸にする

本仕様では、置きバケについて、標準的な店舗運用を前提に主要な導線を設計する。

標準フローでは、店舗がユーザー本人の参加意思を確認したうえで、レジスト締切までに置きバケ参加者として扱い、レジスト締切を目安として席へ配置する。

### 3.2 店舗運用の幅を許容する

実際の店舗運営では、店舗判断により以下のタイミングや扱いが前後する場合がある。

- 参加登録の受付可否
- 席配置タイミング
- アドオン確認
- 実ユーザー・`bills` 接続
- 未接続・未会計状態の確認
- 無効化・戻し操作

そのため、本システムでは、レジスト締切を過ぎていること自体を理由に、参加登録や席配置を自動的に禁止しない。

システムは、標準的な運用に沿った操作導線を提供しつつ、店舗運用上必要な例外対応ができる余地を残す。

### 3.3 置きバケ操作は店舗デバイスで行う

置きバケに関する操作は、LINEミニアプリからは行わない。

ユーザーから店舗へ置きバケの連絡があった場合、店舗スタッフが店舗デバイス上で置きバケ用の一時参加者を作成する。

### 3.4 置きバケ一時参加者は専用データで管理する

置きバケ一時参加者は、既存の `waiting` には直接保存しない。

置きバケ一時参加者は、専用データである `okibakeTemporaryEntries` で管理する。

既存の `waiting` は、実ユーザー・`activeStays`・`billId` を前提とした通常参加者の待機情報として維持する。

置きバケ一時参加者は、実ユーザーや `bill` が未接続の状態でも扱う必要があるため、通常の `waiting` とはデータモデルを分ける。

ただし、店舗デバイス上の待機者一覧では、通常の `waiting` と `okibakeTemporaryEntries` を UI 上で統合表示する。

これにより、店舗スタッフは通常参加者と置きバケ一時参加者を同じ画面で確認できるが、内部データとしては区別して扱う。

### 3.5 `pendingBillCharges` は採用しない

今回の置きバケ対応では、`pendingBillCharges` は採用しない。

理由は、置きバケ一時参加者を表す `okibakeTemporaryEntries` が、`bill` 接続前の会計予定状態も含めて管理するためである。

`pendingBillCharges` を別途作成すると、置きバケ一時参加者の状態と `bill` 接続前会計状態が分離し、二重管理になる。

そのため、未接続・未会計状態は `okibakeTemporaryEntries` の状態として管理する。

### 3.6 会計・売上反映は最終的に `bills` 側で行う

置きバケ一時参加者の専用データだけで、会計済み・売上反映済みとして扱ってはならない。

置きバケ参加者が後から来店した場合、店舗デバイス上で一時参加者と実ユーザー、および対象ユーザーの既存・未精算の `bills` を手動で接続する（§5.7）。接続処理の集約先は詳細仕様書 §14 とする。

接続後の会計・精算・売上反映・analytics 反映は、通常の `bills` 側の処理に乗せる。

## 4. 本仕様における置きバケの定義

本仕様における「置きバケ」は、店舗運営上の一般的な呼称・文化を踏まえつつ、本プロジェクトでシステム化する対象として定義する。

そのため、本仕様に記載する置きバケの定義は、すべての店舗・すべてのトーナメント運営における一般定義ではなく、本プロジェクト内で扱うための業務定義である。

本仕様では、置きバケを以下のように扱う。

置きバケとは、ユーザー本人が未到着の状態であっても、店舗が事前に参加意思を確認したうえで、置きバケ一時参加者として作成し、レジスト締切を目安として席へ配置する運用である。

標準フローでは、置きバケ一時参加者は作成時点でトーナメント参加者として扱う。

標準フローでは、レジスト締切までは、置きバケ参加者は参加登録済みであるが、原則として席には配置されていない状態として扱う。

レジスト締切を迎えたタイミングを、置きバケ参加者を席へ配置する標準的な運用タイミングとして扱う。

ただし、本システムでは、レジスト締切を過ぎていること自体を理由に、参加登録や席配置を自動的に禁止しない。

実際の参加登録可否、席配置タイミング、アドオン確認、実ユーザー・`bills` 接続のタイミングは、店舗運用側の判断に従う。

席に配置された後は、ユーザー本人が未到着であっても、トーナメント上の着席済み参加者として扱う。

そのため、本人が到着するまでの間、ブラインドやアンティによりスタックが減る前提となる。

ただし、本システムでは、以下は管理しない。

- スタック残量
- ブラインドによるスタック減算
- アンティによるスタック減算
- チップ推移

本システムでは、置きバケを以下の対象として扱う。

- トーナメント参加者
- 参加人数への反映対象
- プライズ計算への反映対象
- 席配置対象
- トーナメント履歴への反映対象
- 操作戻しの対象
- リシート対象
- 後続の実ユーザー・会計接続対象
- 未接続・未会計確認対象

## 5. 用語定義

### 5.1 レジスト

本仕様では、レジストを「トーナメントへの参加登録」として扱う。

### 5.2 レジスト締切

本仕様では、レジスト締切を「開催中トーナメントにおける参加受付の目安となる締切時刻」として扱う。

ただし、本システムでは、レジスト締切を過ぎていること自体を理由に、参加登録を自動的に禁止しない。

レジスト締切後に参加登録を受け付けるかどうかは、店舗運用側の判断として扱う。

### 5.3 参加登録後

参加登録後とは、ユーザーまたは一時参加者がトーナメント参加者として登録された後の状態を指す。

「レジスト後」という表現は、参加登録後なのか、レジスト締切後なのかが曖昧になるため、本仕様では原則として使用しない。

### 5.4 置きバケ一時参加者

置きバケ一時参加者とは、ユーザー本人が未到着または `bills` 未接続の状態で、店舗スタッフが店舗デバイス上で作成する置きバケ用の一時的な参加者である。

表示上は「オキバケA」「オキバケB」などの仮名を持つ。

後から実ユーザーおよび `bills` と接続される。

### 5.5 通常 waiting

通常 waiting とは、既存の `scheduledTournaments/{tournamentId}/tablesSeat/waiting` に保存される通常参加者の待機情報である。

通常 waiting は、実ユーザー・`activeStays`・`billId` を前提とする。

置きバケ一時参加者は、通常 waiting には直接保存しない。

### 5.6 UI 上の統合表示

UI 上の統合表示とは、店舗デバイス上の待機者一覧において、通常 waiting の参加者と `okibakeTemporaryEntries` の置きバケ一時参加者を同じ一覧上に表示することである。

ただし、内部データとしては通常 waiting と `okibakeTemporaryEntries` を分けて扱う。

### 5.7 `bills` 接続

`bills` 接続とは、置きバケ一時参加者を、実ユーザーの既存の未精算・進行中 `bills` に正式に接続することである（サーバ側の集約先 Callable は `linkOkibakeTemporaryEntryToBill`。詳細仕様書 §14）。

初期仕様では、置きバケ一時参加者と `bill` の**自動統合は採用しない**。作成時に `linkedUserId` が指定されていても、対象ユーザーの `bills` が新規作成されたからといって自動で接続してはならない。`linkedUserId` がある置きバケ一時参加者は**接続候補**として扱い、実際の接続は**システム上は手動実行**とする。

手動接続の実行導線は1箇所に限定しない。初期仕様では、例えば（1）ユーザー来店・ログイン時に対象ユーザーに紐づく置きバケ一時参加者を接続候補として表示して手動接続する、（2）トーナメントページ上で対象の置きバケ一時参加者を選び接続先 user / `bill` を指定して手動接続する、といった導線を想定する。誤接続を防ぐため、手動接続の実行時には、接続対象の置きバケ一時参加者・接続先 user・接続先 `bill` を確認できるダイアログを表示する想定とする。いずれの導線でも、最終的な接続処理は `linkOkibakeTemporaryEntryToBill` に集約する。

会計上重要な境界は、最終的に `bills` に接続できたかどうかである。実ユーザーとの紐付け候補は `linkedUserId` で保持する（詳細仕様書）。

## 6. 機能の目的

本機能の目的は、トーナメント運営における置きバケを、店舗デバイス上で一貫して扱えるようにすることである。

具体的な目的は以下である。

- 置きバケ連絡を受けた店舗スタッフが、一時参加者を作成できるようにする
- 作成された置きバケ一時参加者を、トーナメント参加者として扱えるようにする
- 通常 waiting とは別データで管理しつつ、店舗デバイスの待機者一覧では統合表示できるようにする
- レジスト締切を目安として、置きバケ参加者を席へ配置できるようにする
- 店舗判断により、標準フロー外の参加登録・席配置にも対応できるようにする
- 置きバケ参加者を参加人数・プライズ計算に反映できるようにする
- 置きバケ操作をトーナメント履歴に残せるようにする
- 置きバケ操作を戻し操作の対象にできるようにする
- 置きバケ参加者をリシート対象にできるようにする
- 後から実ユーザーおよび `bills` と手動で接続できるようにする（§5.7）
- 来店しなかった場合でも、未接続・未会計対象として店舗側が確認できるようにする
- LINEミニアプリ側の通常参加導線や表示情報と矛盾しないようにする

## 7. 想定場面

### 7.1 店舗が置きバケ連絡を受ける場面

ユーザー本人が店舗へ未到着の状態で、店舗に対して置きバケの意思を連絡する。

店舗スタッフは、その意思を確認したうえで、店舗デバイス上で置きバケ用の一時参加者を作成する。

この操作は LINEミニアプリからは行わない。

### 7.2 店舗スタッフが置きバケ一時参加者を作成する場面

店舗スタッフは、店舗デバイス上で「オキバケA」「オキバケB」などの仮表示名を持つ一時参加者を作成する。

置きバケ一時参加者は、作成時点でトーナメント参加者として扱う。

作成時に、対象ユーザーが分かっている場合は、任意で実ユーザー情報を指定できる。

作成時に、ユーザーから確認したアドオン意思を登録できる。

### 7.3 待機者一覧で通常参加者と置きバケ参加者を確認する場面

店舗デバイス上の待機者一覧では、通常 waiting の参加者と `okibakeTemporaryEntries` の置きバケ一時参加者を UI 上で統合表示する。

ただし、内部データとしては分けて扱う。

通常参加者に対する着席操作は、既存の通常参加者向け経路を用いる。

置きバケ一時参加者に対する席配置操作は、置きバケ専用の経路を用いる。

### 7.4 レジスト締切を目安として置きバケ参加者を席へ配置する場面

レジスト締切を迎えたタイミングを目安として、店舗スタッフは置きバケ参加者を席へ配置する。

席に配置された後、置きバケ参加者はトーナメント上の着席済み参加者として扱われる。

本人が未到着であっても、ブラインドやアンティによりスタックが減る前提となる。

ただし、本システムではスタック残量の自動管理は行わない。

また、実際にその時点で配置するかどうかは店舗運用側の判断に従う。

### 7.5 置きバケ参加者がレジスト締切前に来店する場面

置きバケ参加者がレジスト締切前に来店した場合、店舗スタッフは必要に応じて、置きバケ一時参加者と実ユーザー・未精算・進行中の `bills` を**手動で接続**する（§5.7・詳細仕様書 §14）。

接続後は、通常の会計・精算・analytics 経路に乗せる。

アドオン有無については、その場で本人に確認して処理する（実施は `entryStatus: "seated"` 段階の `applyOkibakeAddon` 等。詳細仕様書 §16）。

### 7.6 置きバケ参加者が席配置後に来店する場面

置きバケ参加者が席配置後に来店した場合、店舗デバイス上で一時参加者と実ユーザー、および対象ユーザーの `bills` を**手動で接続**する（§5.7）。

接続後の会計・精算・売上反映・analytics 反映は、通常の `bills` 側の処理に乗せる。

### 7.7 置きバケ参加者が来店しなかった場面（未接続のまま残る場合）

来店せず `bills` に接続されないまま営業日を跨ぐなど、閉店時点で未接続が残る場合がある。初期仕様では、閉店処理時に **`entryStatus != "voided"` かつ `billLinkStatus == "unlinked"`** の置きバケ一時参加者を **`billLinkStatus: "pending_review"`** とする（§8.3）。これは店舗側が確認すべき**未接続状態**であり、会計済み・精算済み・売上反映済みを意味しない。

`voided` は登録取消であり、`linked` は既に `bills` 接続済みであるため、この遷移の対象外である。

状態は通常の未接続 `bills` ではなく `okibakeTemporaryEntries` 上で管理する。後日ユーザーが来店し `bills` が作成されていても、**自動統合は行わず**、接続候補として手動実行（`linkOkibakeTemporaryEntryToBill`）で接続する（§5.7）。

## 8. データ管理方針

### 8.1 `okibakeTemporaryEntries`

置きバケ一時参加者は、専用データである `okibakeTemporaryEntries` で管理する。

`okibakeTemporaryEntries` は、以下の役割を持つ。

- 置きバケ一時参加者を表す
- 対象トーナメントと紐付く
- 仮表示名を保持する
- 任意で対象ユーザー情報を保持する
- アドオン希望（`addonIntent`）を保持する
- 実際の addon 実施履歴（`okibakeAddonRecords`）を保持する（`addonEvents` サブコレクションは採用しない）
- トーナメント上の状態を保持する
- `bills` 接続状態を保持する
- 未接続・未会計確認対象かどうかを表す
- 履歴・戻し・リシート対象として扱える

具体的なコレクション配置、ドキュメントID、フィールド構成は詳細仕様書で定義する。

### 8.2 `entryStatus`

置きバケ一時参加者のトーナメント上の状態は、`entryStatus` で管理する。

初期仕様では、以下の状態を扱う。

```ts
entryStatus:
  | "registered"
  | "seated"
  | "busted"
  | "voided";
```

各状態の意味は以下である。

```text
registered
= 置きバケ一時参加者として作成済み
= トーナメント参加者として扱う
= 原則として席未配置
= 参加人数・プライズ計算への反映対象

seated
= 席配置済み
= 本人未到着でも着席済み参加者として扱う
= ブラインド/アンティでスタックが減る前提

busted
= トーナメント参加者として成立した上で敗退した状態
= 置きバケ一時参加者が席配置後にバーストした状態
= 参加人数・プライズ計算上は参加者として扱う
= voided とは異なり、登録取消ではない

voided
= 店舗判断により、置きバケ一時参加者としての登録を取り消した状態
= 登録自体の取消であり、busted とは別概念
```

以下も明確にしておく。

```text
busted と voided は別概念である。

busted は、参加者として成立した後に敗退した状態である。
voided は、置きバケ一時参加者としての登録自体を取り消した状態である。

busted の置きバケ一時参加者を voided として扱わない。
また、voided を来店しなかった状態や bills 未接続の確認待ち状態として使わない。
来店せず bills 未接続のまま確認が必要な場合は、billLinkStatus: "pending_review" で管理する。
```

`created` は採用しない。

理由は、今回の初期仕様では、置きバケ一時参加者を作成すること自体が、置きバケ参加者として登録することとほぼ同義であるためである。

### 8.3 `billLinkStatus`

置きバケ一時参加者の `bills` 接続状態は、`billLinkStatus` で管理する。

初期仕様では、以下の状態を扱う。

```ts
billLinkStatus:
  | "unlinked"
  | "linked"
  | "pending_review";
```

各状態の意味は以下である。

```text
unlinked
= まだ bills に接続されていない

linked
= bills に接続済み
= 以後の会計・精算・analytics は bills 側で処理する

pending_review
= bills 未接続のまま残り、店舗側が確認すべき未接続状態
= 会計済み・精算済み・売上反映済みを意味しない
```

**`pending_review` への遷移（初期仕様）**

`pending_review` への遷移は、初期仕様では**閉店処理時**に行う。

閉店処理時に、以下を満たす置きバケ一時参加者を `pending_review` にする。

```text
entryStatus != "voided"
かつ
billLinkStatus == "unlinked"
```

遷移の対象となりうる `entryStatus` は次である。

```text
registered
seated
busted
```

次はこの遷移の対象外である。

```text
voided
linked
```

（前者は `entryStatus` が登録取消のため、後者は `billLinkStatus` が `linked` で既に `bills` 接続済みのため。）

補足:

```text
voided は、置きバケ登録自体の取消状態であるため pending_review の対象外とする。

billLinkStatus: "linked" は、すでに bills 接続済みであるため pending_review の対象外とする。

pending_review は、店舗側が確認すべき未接続状態であり、会計済み・精算済み・売上反映済みではない。
```

（上記以外の状態遷移・Callable・カウンタの詳細は詳細仕様書 §15 を参照する。）

### 8.4 ユーザー情報

対象ユーザーが分かっている場合、`okibakeTemporaryEntries` に `linkedUserId` / `linkedUserPokerName` などのユーザー情報を保持できるようにする（フィールド名は詳細仕様書に従う）。

ただし、初期仕様では、ユーザー接続状態を `userLinkStatus` のような独立状態軸としては管理しない。

理由は、今回の運用上重要なのは、最終的に `bills` に接続できたかどうかであり、かつ自動統合ではなく接続候補としての紐付けに留めるためである。

`linkedUserId` があっても `bills` 作成時に自動接続は行わず、実際の接続は手動実行とする（§5.7）。

### 8.5 `pendingBillCharges` は作成しない

`pendingBillCharges` は作成しない。

`bill` 接続前の未接続・未会計状態は、`okibakeTemporaryEntries.billLinkStatus` によって管理する。

## 9. 要件定義

### 9.1 置きバケ一時参加者作成要件

店舗デバイス側では、置きバケ用の一時参加者を作成できる必要がある。

一時参加者には、以下を扱える必要がある。

- 仮表示名
- 対象トーナメント
- 任意の対象ユーザー情報
- アドオン意思
- 作成日時
- 作成操作を行った店舗デバイス
- `entryStatus`
- `billLinkStatus`
- 接続済み `billId`
- 無効化状態

作成直後の状態は、原則として以下である。

```ts
entryStatus: "registered";
billLinkStatus: "unlinked";
```

### 9.2 通常 waiting との関係

置きバケ一時参加者は、既存の `waiting` には保存しない。

既存 `waiting` は、通常参加者用の待機情報として維持する。

店舗デバイス上の待機者一覧では、通常 `waiting` の参加者と `okibakeTemporaryEntries` の置きバケ一時参加者を UI 上で統合表示する。

UI 上では同じ待機者一覧に見えるが、操作時には通常参加者と置きバケ一時参加者を区別する。

### 9.3 席配置要件

店舗スタッフは、レジスト締切を目安として、置きバケ参加者を席へ配置できる必要がある。

置きバケ一時参加者の席配置は、既存の通常参加者向け `assignSeatToPlayer` とは分けて扱う。

理由は、既存の `assignSeatToPlayer` が `activeStays` と `billId` を前提としているためである。

席に配置された置きバケ参加者は、本人未到着であっても着席済み参加者として扱う。

席配置後の状態は以下である。

```ts
entryStatus: "seated";
```

### 9.4 プライズ反映要件

置きバケ参加者は、トーナメント参加者として扱うため、参加人数およびプライズ計算への反映対象とする。

初期仕様では、置きバケ一時参加者を作成した時点で `entryStatus: "registered"` とし、参加者として扱う。

ただし、具体的に `views/main.entries` など既存カウンタへどのタイミングで反映するかは、詳細仕様書で定義する。

### 9.5 アドオン意思・実施記録・アドオン実施 Callable

#### アドオン意思（`addonIntent`）

置きバケ連絡時に、ユーザーからアドオン有無の意思を確認する場合がある。

店舗スタッフは、置きバケ用の一時参加者作成時に、アドオン意思を登録できる必要がある。

アドオン意思は、スタッフが操作時に確認するための情報であり、システムが自動でアドオンを確定するものではない。

次のような区分で扱う（詳細仕様書）。

```text
addonIntent
= ユーザーから聞いたアドオン希望（聞き取り情報）
```

#### 実際のアドオン実施記録（`okibakeAddonRecords`）

置きバケにおける addon の実施記録は、`addonEvents` サブコレクションではなく、`okibakeTemporaryEntries/{okibakeEntryId}` ドキュメント内の `okibakeAddonRecords` 配列で管理する。

```text
addonEvents サブコレクションは初期仕様では採用しない。

okibakeAddonRecords は addon 実施1回ごとの最小記録である。

addon の通常想定は1回程度だが、仕様上は複数回可能とする。

addon 実施のたびに既存 record を上書きせず、新しい OkibakeAddonRecord を配列へ追加する。
```

```text
okibakeAddonRecords
= スタッフが実際に addon 処理を行った履歴

okibakeAddonCount
= rollback されていない有効 addon 回数のサマリ
```

実際のアドオン反映タイミング・`bills` への載せ方は詳細仕様書 §16 とする。

#### `applyOkibakeAddon`（実行可能条件）

実際の addon 実施 Callable（`applyOkibakeAddon`）は、`entryStatus: "seated"` の置きバケ一時参加者にのみ実行可能とする。

次の状態では実行不可である。

```text
registered
busted
voided
```

理由の趣旨は次である。

```text
registered の段階では addonIntent により希望は保持できるが、実際の addon 実施は行わない。

busted は敗退済みのため、新規 addon 対象外とする。

voided は登録取消済みのため、addon 対象外とする。
```

### 9.6 `bills` 接続要件

置きバケ参加者が後から来店した場合など、店舗デバイスから一時参加者と対象ユーザー・対象ユーザーの既存・未精算・進行中の `bill` とを**接続できる**こと（自動ではない）が必要である。以下の全体方針に従う（詳細処理は詳細仕様書 §14）。

```text
初期仕様では、置きバケ一時参加者と bill の自動統合は採用しない。

置きバケ一時参加者作成時に linkedUserId が指定されている場合でも、対象ユーザーの bills 作成時に自動で接続してはならない。

linkedUserId がある置きバケ一時参加者は、接続候補として扱う。

実際の bills 接続は、システム上は手動実行とする。
```

手動接続の導線は次とする。

```text
手動接続の実行導線は1箇所に限定しない。

初期仕様では、以下のような導線を想定する。

- ユーザー来店・ログイン時に、対象ユーザーに紐づく置きバケ一時参加者を接続候補として表示し、手動で接続する
- トーナメントページ上で、対象の置きバケ一時参加者を選択し、接続先 user / bill を指定して手動で接続する
```

```text
誤接続を防ぐため、手動接続の実行時には、接続対象の置きバケ一時参加者・接続先 user・接続先 bill を確認できるダイアログを表示する想定とする。
```

```text
いずれの導線でも、最終的な接続処理は linkOkibakeTemporaryEntryToBill に集約する。
```

接続後は、通常の `bills` 側で会計・精算・売上反映・analytics 反映を行う。

一時参加者の専用データだけで、会計済み・売上反映済みとして扱ってはならない。

接続後の状態は以下である。

```ts
billLinkStatus: "linked";
```

### 9.7 未接続・未会計管理要件

置きバケ参加者が来店しないなどで、`bills` に接続されないまま残る場合がある。初期仕様では、**閉店処理時に**§8.3 の条件で `billLinkStatus: "pending_review"` とし、店舗側が未接続状態を確認できるようにする（会計済み等を意味しない）。

この状態は、通常の `bills` ではなく、`okibakeTemporaryEntries.billLinkStatus` で管理する。

当該状態に入った場合は以下である。

```ts
billLinkStatus: "pending_review";
```

### 9.8 履歴・戻し要件

置きバケ操作は、トーナメント履歴に反映する必要がある。

履歴対象とする操作は、少なくとも以下である。

- 置きバケ一時参加者作成
- 置きバケ席配置
- 置きバケにおける addon 実施・bust
- `bills` 接続
- pending_review 化（閉店処理時の未接続扱い。§8.3）
- 無効化（`voided`）
- 戻し操作

置きバケ操作は、既存のトーナメント操作と同様に、戻し操作の対象とする。

戻し時に何を復元・取消するか、および **`bills` 接続後の rollback／補正の扱い**は詳細仕様書で定義する（上位方針は §9.11）。

### 9.9 リシート反映要件

置きバケ参加者は、トーナメント上の参加者として扱うため、リシート対象に含める。

リシート上で置きバケ参加者を通常参加者と同じ表示にするか、置きバケとして区別するかは詳細仕様書で定義する。

### 9.10 置きバケ席移動・全員リシート

置きバケ席位の変更・ドローにも、次の上位方針を適用する（詳細は詳細仕様書 §19）。

```text
置きバケ席移動・全員リシートに、通常席と異なる追加の業務制約は設けない。

bill 未接続の置きバケ席も、entryStatus: "seated" で seat に存在する場合は、席移動・全員リシート対象にする。

bills 接続済みの置きバケ由来席は、seatXXUserId を優先し、通常ユーザー席として扱う。

seatXXOkibakeEntryId は、置きバケ由来の追跡用として維持する。

registered / busted / voided / pending_review は、seat 上に存在する移動対象ではないため、席移動・全員リシート対象外とする。

席移動・全員リシート時に entries / playersIn / waitingCount / seatedCount は変更しない。
```

### 9.11 `bills` 接続後の rollback・補正

すべての rollback を一律禁止するのではなく、詳細仕様書 §14.12 に従い、通常ユーザーとして発生した操作と、`bills` 接続前に置きバケ側で発生し接続時に後追い反映される操作とを切り分けて扱う。

```text
bills 接続後だからといって、すべての rollback を禁止するわけではない。

bills 接続後に通常ユーザーとして発生した addon / bust は、通常ユーザーと同じ rollback を許可する。

bills 接続前に置きバケとして発生し、bills 接続時に後追い反映された addon / bust の取消・補正は、通常 rollback では扱わず、専用補正・手動確認対象とする。

bills 接続そのものの rollback は、初期仕様では通常操作として提供せず、必要な場合は専用補正・手動確認対象とする。
```

### 9.12 LINEミニアプリ側の関連要件

今回の置きバケ対応では、LINEミニアプリから置きバケ操作は行わない。

ただし、LINEミニアプリ側では、入店済ユーザーの通常参加登録や、参加対象トーナメントの表示情報を整理する。

LINEミニアプリ側では、以下を扱う。

- 入店済ユーザーの通常参加登録
- 参加対象トーナメントの最小表示
- 自分の参加状態の表示
- 操作結果の表示
- エラー表示
- 処理中表示・二重実行防止

LINEミニアプリ側では、以下を扱わない。

- 置きバケ申請
- 置きバケ一時参加者作成
- 置きバケ席配置
- 置きバケ参加者と `bills` の接続
- 置きバケ未接続・未会計管理

## 10. 機能構成

### 10.1 店舗デバイス側

店舗デバイス側では、以下の機能を扱う。

- 置きバケ一時参加者作成
- 置きバケ一時参加者一覧表示
- 通常 waiting と置きバケ一時参加者の UI 上の統合表示
- 置きバケ参加者のアドオン意思の登録
- **`entryStatus: "seated"`** に対する実際のアドオン実施（`applyOkibakeAddon`。履歴は `okibakeAddonRecords` で管理）
- 置きバケ参加者の **バースト（敗退、bust）** 処理（詳細仕様書 §16）
- レジスト締切を目安とした置きバケ席配置
- 店舗判断による例外的な参加登録・席配置
- **置きバケ参加者が seat 上にある場合の**席移動・全員リシート（§9.10・詳細仕様書 §19）
- 置きバケ参加者と **`bills` の手動接続**（複数導線、`linkOkibakeTemporaryEntryToBill` に集約）
- 置きバケ参加者の未接続・未会計表示
- 置きバケ操作の履歴表示
- 置きバケ操作の戻し
- 置きバケのリシート反映

### 10.2 専用データ管理

置きバケでは、実ユーザーが未確定または `bill` 未接続の状態でも、トーナメント参加者として扱う必要がある。

そのため、置きバケ用の一時参加者を表す専用データ `okibakeTemporaryEntries` を作成する。

この専用データは、以下の役割を持つ。

- 置きバケ一時参加者を表す
- 対象トーナメントと紐付く
- 任意で対象ユーザー情報を持つ
- アドオン希望（`addonIntent`）および実際の addon 実施履歴（`okibakeAddonRecords`）を保持する（`addonEvents` は採用しない）
- `entryStatus` を保持する
- `billLinkStatus` を保持する
- `bills` との接続情報を保持する
- 未接続・未会計確認対象として扱える
- 履歴・戻し・リシート対象として扱える

具体的なコレクション名、配置、フィールド構成、状態遷移は詳細仕様書で定義する。

### 10.3 LINEミニアプリ側

LINEミニアプリ側では、以下の機能を扱う。

- 参加対象トーナメントの最小表示
- 入店済ユーザーの通常参加登録
- 参加登録結果の表示
- エラー表示
- 処理中表示・二重実行防止

LINEミニアプリ側では、以下は扱わない。

- 置きバケ申請
- 置きバケ一時参加者作成
- 置きバケ席配置
- 置きバケ参加者と実ユーザー・会計の接続
- 置きバケの未接続・未会計管理
