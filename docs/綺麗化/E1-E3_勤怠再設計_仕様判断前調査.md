## 0. 調査結論（先に読む）

**2026-08-19:** 仕様は §32.11 で確定。実装は案件化・本開発再開まで保留。営業向け綺麗化の残件からは除外する（実装済みではない）。

現行 write は **「未退勤 open が無ければ常に新規 auto-ID doc」** である。同日再出勤は製品として拒否されていない。一方、LINE 履歴・修正申請・承認・勤務日数・給与の日次残業は **1 staff + 1 date = 1 件** を暗黙前提にしている。

ユーザー意向（同日再出勤は許可、中抜けは勤務に含めない、1 営業日 1 doc）と現行コードは、**write が複数 doc、read が 1 件前提** で衝突している。実装前に決めるべきは「1 doc 化するか」ではなく、**1 doc の中身（session / break / 派生 clockIn-Out / correction 粒度 / 既存データの扱い）** である。

推奨（詳細は §36）: **1 staff + 1 `date` = 1 attendance。勤務区間は `workSessions[]`（各 `sessionId`）。break は現行どおり `breaks` サブコレに `sessionId` を付与。親に firstClockIn / lastClockOut を派生保存。** 中抜けを break にしない。

## 1. Root cause（同日複数 doc）

`clockIn` は次の 2 点だけを見ている。

1. `staffId` 一致かつ `clockOut == null` の open があるか（transaction）
2. そのうち `clockIn != null` かつ `closedStoreWithoutClockOut !== true` なら `already-clock-in`

**`date`（businessDate）の uniqueness は見ていない。** 新規は常に `db.collection('attendances').doc()`（auto-ID）。

したがって:

```
clockIn → clockOut（doc A, date=D）
→ 再度 clockIn（open が無い）
→ doc B 新規作成、date は再び getBusinessDateForAttendance()
```

店舗が `running` のままなら D は同じ。これが第一巡 ATT-02 の 04:05 と 04:08 の 2 doc である。

根拠: `functions/src/domains/attendance/callables/clockIn.ts`（`newRef = db.collection('attendances').doc()`、open 判定 `isOpenUnclockedAttendance`、`date` は作成時に書くだけ）。

Admin `createAttendance` は uniqueness チェック自体が無い（`.add()`）。手動 `createManualClockInRecord` も open のみ拒否で、退勤後の同日再作成を許可する。

## 3. Document ID / uniqueness

| 項目 | 現行 |
|------|------|
| doc ID | Firestore auto-ID（`doc()` / `.add()`） |
| unique 相当 | **なし**。`staffId+date` の unique index もなし |
| 同日検索 | 多数の consumer が `staffId + date` で query するが、件数 1 を保証しない |
| clockIn transaction | open（clockOut==null）の同時作成だけ 1 件化。**同日の退勤済みは対象外** |
| race | 退勤後の二重 clockIn は 2 doc。Admin create は完全に並行可 |
| 安定 ID | なし。correction は `uid_date` で申請 ID は安定だが、対象 attendanceId は lookup 依存 |

**なぜ複数作れるか:** uniqueness が「1 staff 1 日」ではなく「1 staff あたり open は 1」だから。

## 4. Write flows

### 4.1 clockIn

```
QRScanPage / Terminal → AttendanceService.clockIn
→ callable clockIn
→ getBusinessDateForAttendance()
→ tx: staffId + clockOut==null に open が無ければ attendances.doc().set(...)
```

- 既存同日の **退勤済み** は無視して新規。
- 既存同日の **open** だけ `already-clock-in`（soft `{ success:false, code }`）。
- QR token consume なし。
- idempotency key なし。

### 4.2 clockOut

```
QR / staffId または docId
→ callable clockOut
```

- `docId` 指定ならその doc。
- なければ `staffId + date==今日の businessDate + clockOut==null` の **最初の clockIn あり**。
- 同日に open が 2 件ある異常時は `find` の先頭。
- **別日の open**（昨日の未退勤）は staffId のみ経路では拾わない（date フィルタ）。一方 clockIn の open ガードは **全日** の clockOut==null を見る。昨日未退勤があると今日の clockIn は拒否される。
- 進行中 break は clockOut 時刻で endedAt を埋めてから集計。
- grace: `closedStoreWithoutClockOut` かつ closedAt から 1 時間超は `grace-period-expired`。

### 4.3 break start / end

- `startBreak({ attendanceId })` → `breaks.doc()` 新規、親 `isOnBreak=true`。
- `endBreak({ attendanceId, breakId? })` → endedAt 更新、`recalculateAttendanceFromBreaks`。
- 複数 break 可。進行中は `endedAt==null` を 1 件想定（start は `isOnBreak` で拒否）。
- **勤務区間 ID は無い**ので、将来 session 化しても現行 break は「親 doc の全期間」に紐づく。

### 4.4 同日再出勤（re-entry）

コード上の正規経路は **新規 attendance**。reopen / 延長 / workSessions は未実装。

中抜け（18:00–20:00）を break にすると、現行 helper は `actualWorkMinutes = (lastOut-firstIn) - break` なので、中抜けを break に入れれば数値上は控除できる。ただし:

- 深夜帯の中抜けも nightBreak として控除される
- UI は「休憩」と表示する
- 修正申請は clockIn/Out のみで、中抜け区間を表せない

これが E2 で break 流用を非推奨とする根拠。

### 4.5 overnight

`date` は **clockIn 時刻から暦日計算しない**。`storeMeta/currentBusinessDay` が `running` なら `currentBusinessDateKey`、否则 JST 当日（`generateJstDateKey`）。

例: 店舗 running、営業日 8/18。

| 操作 | 結果 |
|------|------|
| 8/18 22:00 clockIn | doc A, date=2026-08-18, clockOut=null |
| 8/19 03:00 clockOut | **同じ doc A** を更新（open を docId または staffId+date=8/18 で特定）。payroll 対象日は 8/18 |
| その後 04:00 再 clockIn（店舗まだ running） | **doc B**, date=2026-08-18 |

店舗が close 済みで status≠running のとき、新規 clockIn の date は JST 当日。8/19 03:00 過ぎなら 8/19 になり得る（**推測: 閉店直後の運用時刻に依存**）。open が残っていれば全日ガードで再出勤不可。

### 4.6 その他 write

| callable | 同日複数への影響 |
|----------|------------------|
| createAttendance（Admin） | uniqueness なし。意図せず 3 件目も可 |
| createManualClockInRecord | clockIn と同様 open のみ |
| updateAttendance | 既存 ID の clockIn/Out/break/論理削除。date 変更不可 |
| updateManualClockOutRecord / updateUnclockedAttendanceWithAuth | 特定 doc の退勤 |
| closeStoreTerminal markUnclocked | clockOut==null 全件に closedStoreWithoutClockOut（営業日フィルタなし） |
| approveAttendanceCorrectionRequest | `staffId+date` の **docs[0]** を更新（保存済み attendanceId を使わない） |
| seedAttendancesDemo | QA。auto-ID |

書き込みは Rules 上 Functions 専任（`allow write: if false`）。

## 5. businessDate 計算

正本は `getBusinessDateForAttendance`（`getCurrentBusinessDateKeyOrThrow.ts`）。

- running → `currentBusinessDateKey`
- それ以外 → JST 暦日
- attendance 独自の closingHour 計算は **しない**
- bills 等の `calcBusinessDate` helper とは別経路

表示用（非 running）は `lastClosedBusinessDateKey`（`getStaffListForAttendance` の出勤日）。打刻用とはずれる点に注意。

## 6. 同日再出勤ケース（コードトレース）

前提: 店舗 running、businessDate=D、break なし。

### Case A: 10:00–18:00 と 20:00–22:00

| | doc 数 | IDs | fields | LINE 履歴 | Admin 一覧 | payroll |
|--|--------|-----|--------|-----------|------------|---------|
| 現行 | 2 | auto×2 | 各 1 pair | `attendanceData[D]` が後勝ち 1 行 | **2 行**（doc 単位） | **2 件**として日次 8h 上限を **別々に** 適用。合算 12h でも各 doc が 8h 以下なら日次残業 0 |

### Case B: 10:00–12:00 と 13:00–18:00（退勤→再出勤。昼休憩ではない）

Case A と同じ構造。gap 1h はどちらの doc にも入らない（正しい）。ただし LINE は 1 行しか見えない。

### Case C: 22:00–02:00 と 03:00–05:00（同一 running 日）

2 doc、どちらも date=D。夜勤分は **各 pair で独立計算後に payroll が合算**。日次 8h は再び **doc 単位**。  
1 doc + 2 session にすると、夜勤 helper は session ごとに呼ぶ必要あり（単純に firstIn–lastOut だと 22:00–05:00 の gap 03:00 前を労働に含めてしまう）。

## 9. ATT-03 / correction

### なぜ起きるか

1. LINE は `getStaffAttendance` の配列を `date` キーで上書き → **表示は 1 区間だけ**（順序不定の後勝ちまたは先勝ち）。
2. 申請作成は `staffId+date` limit(5) の **最初の isDeleted≠true** の clockIn/Out を current* にコピー。任意で `attendanceId` を保存。
3. 申請 ID は `{uid}_{date}` で **日に 1 申請**。一度 rejected でも再申請不可（pending/approved/rejected いずれも）。
4. **承認は `attendanceId` を使わず** `staffId+date` の `docs[0]` を更新する。

第一巡: LINE が 04:05–04:05 を見て申請、Admin 側の対象勤怠は 04:08–04:09。却下後は同日再申請不可。  
これは UI バグというより **同一キーに 2 実体がある設計欠陥**。

### 現行修正粒度

LINE: `clockIn` / `clockOut` / `both` / `other`。break 修正は LINE に無い。  
Admin `updateAttendance`: clockIn/Out、break 追加・更新・論理削除、勤怠論理削除。

将来 session がある場合の判断材料:

- 日全体の「最初の出勤・最後の退勤」だけ直すなら現行 type で足りる
- 2 回目の 20:00 だけ直すなら **sessionId 必須**
- 中抜けを誤って break にした場合、break 修正が必要 → Admin 経路のみ

承認の HH:mm は **申請の `date` + JST** で Timestamp 化。overnight の 03:00 を「翌日 03:00」にしたい場合、現行は date 当日 03:00 になり **早い時刻になるリスク**（clockOut < clockIn）。overnight 修正は別論点。

## 10. Payroll

- 取得: `paymentPeriodKey` または attendanceId リスト。**date で group しない**。
- 1 件処理: `processAttendanceDay` が `actualWorkMinutes` に対し日次法定 8h（`DAILY_LEGAL_LIMIT_MINUTES`）を適用。
- 週次残業は doc を時系列に積む。
- 深夜は各 doc の `nightWorkMinutes` を金額側で使用。

同日 2 doc（6h + 6h）:

- 総労働 12h は **足される**（二重でも欠落でもない）
- 日次残業は 0+0（各 6h < 8h）→ **本来 12−8=4h 残業が落ちる**
- totalDays が 2 → 勤務日数過大

これは「正しく合算」でも「一方が落ちる」でもなく、**時間合算・日次ルール破綻**。

`calculateNightWorkMinutes` は **1 つの Timestamp pair** 前提。gap を含む first–last にそのまま使うと中抜けを深夜労働に含む。session ごとに呼ぶ必要あり。

## 19. Concurrency / idempotency

1 日 1 doc になると **同じ doc に clockIn(session 追加) / break / clockOut / correction が集中**する。

現行:

- clockIn は open 作成を tx
- startBreak は tx だが事前 read の isOnBreak
- endBreak は tx なし（read-modify-write）
- idempotency key は **修正申請の clientNonce のみ**
- clockIn に operation id なし → 退勤後ダブルタップで 2 doc（現行）。1 doc 化後は **2 session** になり得る

必要になりそうなガード:

- 「open session がある間は session 追加禁止」（現行 open ガードの再定義）
- session 追加を attendance tx
- 任意: clientNonce / sessionId をクライアントが送る（二重 tap）

複数端末 QR は現行どおり「誰かが open なら拒否」。1 doc でも同じ。

## 20. Rules / Functions / query

- write は Functions のみ。1 doc 化しても Rules の「ネスト array 検証」は今もしていない。
- index: `staffId+date` 既存。1 doc ならこの query が **0 or 1** になる（unique はアプリ/tx 側）。
- `staffId+clockOut`、`date+clockOut`、閉店フラグ index は open 検索用に残る。
- 新規: `staffId+date` の tx get が clockIn の正になる。複合 index 追加は必須ではない。

## 24. 推奨仕様

**1 staff + 1 `date` = 1 `attendances` doc。**  
**正本の区間は `workSessions[{ sessionId, startedAt, endedAt }]`。**  
**break は現行サブコレ + `sessionId`。中抜けは session 間 gap。**  
**親の clockIn/clockOut は first/last の派生（名前は判断 5）。**  
**open ガードは「open session が既にある」。**  
**correction v1 は日 1 件・first/last。approve は attendanceId 必須。**  
**payroll は親の actualWorkMinutes を 1 日 1 回。**

理由: 現行 consumer の大半が「1 日 1 pair」で書かれている。pair の意味を「日の端」に広げ、区間の正本だけ配列にするのが、完全正規化（A）より修正量が少なく、break 流用（中抜け=休憩）より給与が安全。

### 代替

- **代替 1:** 同日再出勤禁止。実装は最小だがユーザー意向と不一致。
- **代替 2:** 複数 doc のまま LINE/approve/payroll だけ date group。write は簡単だが uniqueness が無く ATT-03 再発、日次残業は group 側の新規計算が必要で、1 doc 化と工数が近づく。

### 32.2 Q1 — 1 staff + 1 businessDate = 1 attendance?

#### Option A — 1 businessDate = 1 attendance + workSessions[]

- write: 同日再出勤は既存 doc に session 追加。open session がある間は追加禁止（現行 open ガードの再定義）
- read: LINE / Admin はその日の 1 doc を読み、UI は **全 session 表示**（first–last を 1 区間に見せない）
- payroll: 親の `actualWorkMinutes`（全 session 合計 − 全 break）を `processAttendanceDay` に **1 回**
- break: 現行サブコレ維持 + sessionId
- uniqueness: `staffId + date` を tx で保証（auto-ID または deterministic ID）

同一 doc への write 集中:

| 操作 | 推奨実装 |
|------|----------|
| session 追加 / endedAt 更新 | **transaction 内で workSessions 配列を読み、対象 `sessionId` を書き換え、配列全体を write back**。`arrayUnion` は endedAt 更新・対象特定に使えない |
| break start/end | サブコレは親 array と独立。親の `isOnBreak` 等は **同じ tx** に含める |
| Admin と QR 同時 | 双方が同一 attendance を tx 更新すれば last-write 負けは防げる。現行 `endBreak` の tx なしは 1 doc 化後にリスク増 → write 経路は tx 必須化が前提 |
| double tap / retry | open session ガード + 任意 clientNonce。sessionId をクライアント生成して送るのも可 |
| document size | 1 日数 session + breaks サブコレ。1MB 到達は非現実（推測: ポーカー店舗で 2〜3 session/日が上限に近い） |

**1日1doc は給与のためだけではない。** 現行の不整合（ATT-03、LINE 上書き、totalDays=件数、日次残業が doc 単位）はすべて「同じ日に複数実体がある」ことが原因。日次の正本を 1 実体にするのがデータモデルとして自然。給与はその最大の被害者。

#### Option B — session = attendance doc のまま + date group

- write は現行に近い（再出勤 = 新規 doc）。Q2 の workSessions はほぼ使わない
- payroll / LINE / correction / totalDays を **すべて date group で組み直し**
- uniqueness は無く、ATT-03 の docs[0] 問題を group 側で再発明する
- Q9 と矛盾。実装量は「group 計算 + 全 consumer」で A に近づくか超える
- **非推奨**

#### Deterministic ID（A の実装バリエーション）

現状: auto-ID（`doc()` / `.add()`）。

| | 案1 auto-ID + `staffId+date` query + tx | 案2 `{staffId}_{YYYY-MM-DD}` |
|--|------------------------------------------|------------------------------|
| uniqueness | アプリ保証。query 漏れで 2 件ありうる | ID 衝突で 2 件目を物理的に作れない |
| clockIn | query open + query 同日 doc | `tx.get(doc(id))` のみ。簡素 |
| staffId 文字種 | 不問 | Auth uid。`/` は不可。通常は英数字。uid に `_` があっても date が末尾 `YYYY-MM-DD` なら split 可能 |
| date 変更 | ID 不変 | 現行 `updateAttendance` は date 変更不可。ID も不変でよい |
| logs / correction | attendanceId は不安定 | 日次で安定。Q8 破棄前提なら移行不要 |
| security | ID 推測不可 | ID は推測可能。**write は Rules `false`（Functions 専任）なので実害は小さい** |
| helper 影響 | 現行 get(docId) はそのまま | 作成時 ID 決定が変わる。読取は doc(id) 直アクセスが増える |

**推奨（A 採用時）: 案2 deterministic ID。** Q8 で旧 auto-ID を捨てる前提なら移行コストがなく、uniqueness が ID で強制される。案1 は query 漏れが ATT-03 の再発源。

#### Comparison table

| 観点 | A 1日1doc + sessions | B 複数doc + group | C = A + deterministic ID |
|------|----------------------|-------------------|--------------------------|
| 日次残業 / totalDays | 親 1 件で正しい | group 新設が必要。忘れると現行どおり壊れる | A と同じ |
| LINE / correction / Admin | 1 doc + session 配列 | 複数 doc の合成。ATT-03 再発しやすい | A と同じ + lookup 直 |
| Write | session 追加は tx。やや増 | 現行に近い | tx が `get(id)` で簡単 |
| Read | 全 consumer が sessions 対応 | group ヘルパーが全読取に必要 | A と同じ |
| Concurrency | 同一 doc 集中。tx 必須 | doc 分散。open は現行どおり全日 query | A と同じ |
| Idempotency | session 重複追加に nonce/open ガード | 退勤後ダブルタップで 2 doc（現行） | A と同じ |
| Firestore size / array | 配列 write-back。size は問題にならない | 問題なし | A と同じ |
| Index | `staffId+date` が 0 or 1。open 検索は `hasOpenSession` 等が必要になりうる | 現行 index 維持 | 直 get が増え query 減 |
| Audit | attendanceId 安定 + sessionId | attendanceId = session。logs は現行型 | ID が日付で追える |

| 利用者の分かりやすさ | 履歴は「その日の勤務」 | 一覧が 2 行のまま分かりにくい | A と同じ |

#### Q1 recommendation（→ §32.11 で確定）

- **recommendation:** **A**（1 staff + 1 `date` = 1 attendance + `workSessions[]`）。ID は **deterministic `{staffId}_{date}` を採用**
- **confidence:** **High**（Q9 との整合）。ID 案だけ Medium（uid 文字種の実データを本番で見ていない）
- **biggest downside:** 同一 doc への mutation 集中。抜けた tx が session 上書き・重複追加になる
- **mitigation:** 全 write を attendance tx。配列は sessionId で更新（index 禁止）。open session がある間は追加禁止。任意 clientNonce。`arrayUnion` は使わない

#### Current clockIn / clockOut consumers

#### A — 親に時刻キャッシュなし

- 正本は `workSessions[]` のみ。必要時 `min(startedAt)` / `max(endedAt)` / `some(endedAt==null)` を pure function で算出
- 二重管理なし。session 追加・修正・削除・correction で親時刻を忘れない
- open 判定を親 `clockOut==null` に残せない → query 用に **状態フラグが別途必要になりうる**（後述）

#### B — firstClockIn / lastClockOut を派生保存

- UI 正本にはしない（規則どおり）
- **open 判定には使えない。** 10–18 退勤後は lastClockOut 非 null。20:00 再出勤中も lastClockOut を「最後の確定退勤」にすると open と矛盾。逆に open 中は lastClockOut=null にすると「日の最後」ではなく現行 clockOut と同じ罠
- 全 mutation で同期が必要。実装量に対し、UI も計算も first/last を正にしないため **価値が薄い**
- payroll 候補の表示短縮程度

#### C — 既存 clockIn / clockOut の意味を「日の端」に変更

- 既存読取はコンパイル通り動くが、**意味が「この勤務区間」から「日の端」に変わる**
- LINE が 10–22 の 1 区間に見える（**UI 規則違反**）
- `clockOut==null` が「今日まだ誰も退勤していない」にも「現在勤務中」にも読め、QR/閉店が壊れる
- **非推奨**

#### Open 状態

現行の正は `clockOut == null`（かつ閉店未退勤フラグの組み合わせ）。  
新正本は **`workSessions` に `endedAt == null` がある**。

親に時刻を残すと open が曖昧になる。時刻キャッシュより、query 用なら:

- `hasOpenSession: boolean` または `openSessionId: string | null`

の方が安全。現行 index（`staffId + clockOut`、`date + clockOut`）は open 検索用。1日1doc なら「その日の doc を 1 件 get して array を見る」でも足りる店舗規模（推測）。フラグを足すなら **時刻の派生ではなく open の派生**に限る。

集計値 `actualWorkMinutes` / `nightWorkMinutes` / `breakMinutes` は現行どおり recalc で親に書いてよい（payroll が読む。時刻区間ではない）。

#### Q5 recommendation（→ §32.11 で確定。open field は実装時）

- **recommendation:** **A**（親に first/last / 意味変更した clockIn・clockOut を持たない）
- **parent fields:** `staffId`, `date`, `workSessions[]`。集計 `actualWorkMinutes` / `nightWorkMinutes` / `breakMinutes`。状態 `isOnBreak`, `currentBreakStartedAt`。`hasOpenSession` / `openSessionId` は **実装時に検討**（clockIn/Out を残す理由にはしない）
- **canonical fields:** `workSessions[].sessionId/startedAt/endedAt`。breaks サブコレ + `sessionId`
- **deprecated fields:** 親 `clockIn` / `clockOut` / `nightMinutes`（legacy）/ `totalMinutes`（休憩控除前。session 合計で再定義するなら親に残さず算出）
- **UI rule:** **勤務履歴・詳細では全 workSessions を表示する。first/last を 1 区間に見せない**

前回調査の「B 派生保存で consumer 修正を減らす」は、全 session 表示が確定したため **撤回方向**。consumer は sessions 対応が必須で、親時刻キャッシュの節約効果は消える。

### 32.4 Q10 — overnight の Timestamp

#### Current overnight behavior（事実）

- **live QR clockIn/Out:** `Timestamp.now()`（調整オフセット可）。22:00 出勤 → 翌 03:00 退勤は **実時刻なので clockOut > clockIn**。overnight は live 打刻では動く
- **clockOut:** 調整後時刻が出勤より前なら拒否。**24h 上限はコードに無い**
- **correction 承認:** `` `${date}T${HH:mm}:00+09:00` ``。`date` は attendance.date（businessDate）。03:00 は **営業日当日 03:00** → 22:00 より前になりうる
- **LINE 修正 UI:** `<input type="time">` のみ。日付・翌日トグルなし。client は HH:mm 形式チェックのみ
- **Admin 作成/編集:** `_selectedDate` + `TimeOfDay`。**退勤が出勤より前ならエラーで拒否** → overnight を **保存できない**
- **grace:** 閉店マークから 1 時間は通常退勤可（`GRACE_HOURS = 1`）
- **businessDate:** running 中は `currentBusinessDateKey`。closingHour による attendance 独自計算はしない
- **24h 超 session:** コード上は禁止していない。閉店しても clockOut は付かない（フラグのみ）。**推測:** ポーカー店舗の 1 session が 24h を超える運用は稀。仕様として許容する根拠は repo に無い

#### A — 自動翌日判定

- session の startedAt 基準で、ended の HH:mm < started の HH:mm なら **started の翌暦日**
- UI は現行 `type=time` のまま
- リスク: 10:00–09:00 が 23h session になる。誤入力を overnight とみなす

#### B — 日付も選択

- 曖昧性なし。LINE は日付 UI が増え重い。Admin には自然

#### C — 「翌日」トグル

- 明示性と LINE の簡潔さの中間。Q6 で original endedAt が翌暦日なら **初期 ON** にできる

#### Q6 との整合

1申請=1session なら original startedAt/endedAt がある。

- 自動判定は **requested ended HH:mm と requested/original started HH:mm** を比較すれば足りる
- original が overnight ならトグル初期値や +1 day の default に使える
- businessDate ではなく **startedAt の JST 暦日** を基準にする（01:00 出勤の running 日など）

#### Q10 recommendation（overnight 判定は §32.11 で確定。16h 上限は未確定）

- **recommendation:** **A**（自動翌日）。LINE は日付入力を増やさない。Admin は同じ server 規則に合わせ、現行の「退勤 < 出勤なら拒否」を実装時に見直す
- **validation（確定）:** endedAt > startedAt。**16h 上限は未確定**（分析時の提案。案件化時の運用で決める）
- **validation（実装時）:** duration > 0、break は session 区間内、上限時間は別途
- **timestamp rule:**
  1. startedAt: original startedAt の JST 日付 + 新 HH:mm（新規 session は businessDate または実際の Timestamp）
  2. endedAt: startedAt と同じ JST 日付 + 新 HH:mm。**HH:mm(end) < HH:mm(start) なら +1 暦日**
  3. businessDate 文字列に HH:mm を直結しない（現行 approve のバグ）
- **edge cases:**
  - 22:00–03:00 → 翌 03:00。OK
  - 01:00–05:00（running で暦日は翌日、businessDate は前日）→ 同暦日。+1 しない
  - 22:00–22:00 → duration 0。拒否
  - 10:00–09:00 → 23h。上限時間は実装時（16h 案は未確定）
  - live 打刻 overnight は今どおり Timestamp 実時刻。本規則は **HH:mm 入力経路**（correction / Admin）

代替: 誤入力をさらに減らすなら **C**（翌日トグル、original overnight なら初期 ON）。B は LINE には重い。

### 32.11 最終仕様判断（2026-08-19 確定）

**営業向け綺麗化としての扱い:** 仕様判断完了 / **実装保留** / **残件から除外**。  
実装済み・解決済み・不具合修正済みではない。現行の同日複数 attendance 挙動は残る。

**保留理由:** 機能重要度は高いが、営業時に同日複数 session・session 単位修正・overnight 補正まで説明・実演する可能性は低い。大規模 schema 変更の費用対効果が営業前では低い。案件化・導入準備で §32.11 を正として再開する。

#### 確定仕様

| ID | 確定内容 |
|----|----------|
| Q1 | **1 staff + 1 businessDate = 1 attendance doc** を canonical とする。同日複数勤務は別 doc にしない。attendanceId は原則 `{staffId}_{businessDate}` |
| Q2 | 複数勤務は `workSessions[]`（例: 10–18 と 20–22 なら 2 session） |
| Q3 | 各 session に安定 `sessionId`。array index は識別子にしない。基本 field: sessionId / startedAt / endedAt |
| Q4 | 現行 `breaks` サブコレ維持 + 各 break に sessionId。break = session 内休憩。session 間 gap = 中抜け（gap を break にしない）。実働 = 全 session 時間合計 − 全 break 時間合計 |
| Q5 | 時刻の正本は **workSessions のみ**。親に clockIn / clockOut / firstClockIn / lastClockOut を時刻正本として持たない。履歴・詳細は **全 session 表示**（10–22 の 1 区間に畳まない）。親の日次集計 `actualWorkMinutes` / `nightWorkMinutes` / `breakMinutes` は保持してよい |
| Q6 | LINE 修正は **1 申請 = 1 session**。履歴は全 session 表示。現行 `{uid}_{date}` は同日複数 session で衝突するため、実装時に session 単位 ID へ変更（例 `{uid}_{businessDate}_{sessionId}`。最終形式は実装時） |
| Q7 | 修正対象は **attendanceId + sessionId**。`staffId + date → docs[0]` は廃止方向 |
