## 2. 綺麗化の目的

営業時に顧客へ見せられる状態へ整えること。具体的には次を含む。

- UI・導線・文言・状態表示の整備
- 主要業務フローの実機確認（Flutter + LINE 統合）
- dead code / unused file / unused Function の整理
- QA / debug / demo residue の隔離または削除
- 利用者向けエラー表示の安全化（Flutter / LINE）
- cleanup に伴う docs / registry 同期
- production 上の obsolete Function undeploy

含まないもの（例）: システム内部資料（ART/TSK）の本作成、営業提案資料、新機能開発、大規模仕様変更、本番インフラ再設計、Functions 契約の全面再設計。

## 4. 判定ルール

| 表現 | 意味 |
|------|------|
| DONE | 当該 cleanup 作業が完了している |
| PASS / RESOLVED | 実機または検証で合格し、残件として扱わない |
| KEEP | 意図的に残置（削除しない）。理由を正本に残す |
| HOLD | 条件待ち・方針保留（再開条件を明示） |
| DEFERRED | 別 track / 営業後等へ延期。実装済み・解消済みではない |
| CLOSED | 当該 batch / 工程の完了宣言（例: Final Cleanup Batch） |

補足:

- **Final Cleanup Batch = CLOSED** と **営業向け綺麗化全体の課題ゼロ** は同義ではない
- KEEP / DEFERRED / separate track が残っても、cleanup batch を CLOSED にできる
