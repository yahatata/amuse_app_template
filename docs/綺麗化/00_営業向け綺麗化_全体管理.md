## 1. 綺麗化の目的

- 営業時に顧客へ見せられる状態へ整える
- UI、導線、文言、状態表示、主要業務フローを確認する
- デッドコード、未使用ファイル、未使用 Function 等を整理する
- 開発途中・テスト・デバッグ要素を営業デモから排除する
- 利用者向けエラー表示を安全・一貫させる（Flutter / LINEミニアプリ）

---

## 2. 綺麗化の定義

### 含むもの

- デッドコード削除
- 未使用ファイル削除
- 未使用 Cloud Functions 整理
- 未使用依存整理
- 不要画面・不要導線・不要ボタン整理
- debug / test / demo UI の隔離または非表示化
- 利用者向けエラー経路の安全化（Flutter / LINE）
- 主要業務フローの実機確認（**Flutter と LINE をまとめた統合実機確認**）
- UI の見た目・操作性・文言の改善
- 営業デモシナリオの通し確認

### 含まないもの

- システム内部資料の作成
- 営業提案資料の作成
- 新機能開発
- 大規模な仕様変更
- 本番インフラの再設計
- 運用設計全般
- Functions 契約の全面再設計（将来改善候補。営業向け綺麗化のブロッカーではない）

---

## 3. 基本方針

- まず機械的に確認できる不要物を整理する
- 利用者向けエラーは、実装・自動検証のあと **統合実機確認** で検収する
- Flutter だけを先に実機確認せず、LINE 側の調査・実装・自動検証と Functions / Hosting deploy を終えてからまとめて確認する（**この先行工程は完了**）
- 統合実機確認は、その場の思いつきではなく **確認対象の機械抽出 → 重複整理 → 正式チェックリスト → 実機確認** の順で行う
- 削除は小さなバッチ単位で行う
- 各バッチで analyze / build / test を確認する
- 不明なものは削除しない
- 仕様判断と技術的削除判断を分ける
- Firebase Console 上の Function 削除はコード削除と分ける
- UI 非表示とコード削除を分ける
- QA / debug / 破壊的 UI・デッドコードは **統合実機確認完了まで残す**

## 8. 統合実機確認

### 8.1 方針変更（重要）

Flutter 実装完了後に **Flutter だけ**を実機確認する想定は取りやめた。

新しい方針（2026-08-13 時点の進捗を併記）:

1. Flutter 側の実装・自動検証を完了 ← **完了**
2. LINEミニアプリ側の横断調査 ← **完了**
3. LINEミニアプリ側の実装 ← **完了**（L1〜L7）
4. LINEミニアプリ側の自動テスト・再監査 ← **完了**
5. Functions + Hosting 本番デプロイ ← **完了**
6. 統合実機確認の確認対象抽出 ← **現在（次工程）**
7. 抽出結果の重複整理 → 正式チェックリスト作成 ← **未着手**（本更新では作成しない）
8. Flutter と LINEミニアプリをまとめて実機確認 ← **未着手**
9. 実機確認結果に基づく修正（問題があれば: 修正 → 自動確認 → commit → 必要反映 → 再実機）
10. QA／debug／破壊的 UI・デッドコードの削除判断
11. 削除後の回帰テスト・analyze・build（必要なら再 deploy／再実機）
12. `cleanUp` push と営業向け綺麗化の最終完了判定
13. **綺麗化完了後:** 営業時に使用するポートフォリオ作成（次フェーズ）

**実機確認を省略したのではなく、統合実機確認へまとめた。**

延期理由:

- Flutter と LINE で連動する業務フローが多い
- 同じ異常状態・ユーザー・伝票・トーナメントを使って一括確認した方が効率的
- Flutter だけ先に確認すると、LINE 実装後に同じフローを再確認する必要がある
- QA／debug UI は両側の実機確認完了まで残す必要がある

### 8.4 統合実機確認の準備手順

実機確認は項目数が多いため、その場で思いついた項目を確認する運用にはしない。
