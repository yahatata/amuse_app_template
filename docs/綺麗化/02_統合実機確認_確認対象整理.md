---

## 2. 整理方針

1. **業務フロー単位**で統合する（ファイル単位・errorKey単位にしない）
2. **正常系と、人工再現が必要な異常系を分離**する
3. **Flutter↔LINE 統合を単体より優先**する
4. **sales quality は主要フロー実施時に同時確認**する。見せたくない UI だけ独立
5. **破壊的操作は露出確認と実行を分ける**
6. **`01` の到達性補正を維持する**
7. Flutter Phase 1〜9 は **現 working tree からのアプリ起動**が前提（`01` §2）

### 確定到達性（`01` より。戻さない）

| 対象 | 扱い |
|------|------|
| `submitAllShifts` / `createMultipleShifts` | **live 非到達**（DOM/listener 残、`#pending-shifts-container` 常時 none） |
| `confirmShiftRequest` | **hash 深リンクのみ**（初回 `handleHashNavigation`。hashchange なし） |
| Staff 作成 | LINE = `createStaffAccount` / Flutter Admin = `createStaffByApp`（**別経路**） |

### result unknown の代表方針

実装は `liff_errors.js` の classify + pending lock で同型。public tests 134 PASS。

| 代表 | 理由 |
|------|------|
| **ORD-03** LINE 注文 | カート凍結・nonce 保持・履歴照合解除があり、最も観測しやすい |
| **STF-02**（任意） staff create/reactivate unknown | 注文と UI が違う（フォーム残置）。余裕があれば 2本目 |

トーナメント登録・シフト提出・勤怠修正の unknown は **同型のため D（自動確認で代替）**。実機で偶然観測したら記録する。

### 強制閉店

通常閉店（CLS-02）で core はカバー。強制閉店は **通常がゲートで進めない場合のみ**。独立必須にはしない。

### accounting start rollback の人工障害

Emulator でカバー済み。実機で commit 失敗を注入しない → **D**。

### SG 部分成功（預入後・退席失敗）

実機再現が不安定。widget 回帰あり → 実機は **偶然観測 / 自動代替（D寄り B）**。独立 EXECUTE にはしない。

## 4. 分類基準

### necessity

| 記号 | 意味 |
|------|------|
| A | 実機必須（LIFF / camera / cross-device / 本番 CF / 見た目判断） |
| B | 実機推奨（自動済みだが代表フローとして見る） |
| C | 到達性・見た目のみ（操作しない／危険） |
| D | 自動確認で十分 |
| E | 実機後 dead/legacy cleanup 判断 |

### action policy

`EXECUTE` / `OBSERVE_ONLY` / `DO_NOT_EXECUTE` / `STATIC_ONLY` / `POST_DEVICE_CLEANUP`

### destructive

`NONE` / `LOW` / `MEDIUM` / `HIGH`

### check class

`IMPLEMENTATION` / `REGRESSION` / `INTEGRATION` / `CLEANUP` / `ERROR_UX` / `SALES_QUALITY` / `LEGACY` / `DESTRUCTIVE`（複数可）
