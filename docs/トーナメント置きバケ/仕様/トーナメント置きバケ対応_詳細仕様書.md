## 2. 基本方針

### 2.1 置きバケ操作は店舗デバイスで行う

置きバケに関する操作は、LINEミニアプリからは行わない。

ユーザーから店舗へ置きバケの連絡があった場合、店舗スタッフが店舗デバイス上で置きバケ用の一時参加者を作成する。

### 2.2 置きバケ一時参加者は専用データで管理する

置きバケ一時参加者は、既存の `waiting` には保存しない。

置きバケ一時参加者は、専用のサブコレクションである `okibakeTemporaryEntries` で管理する。

既存の `waiting` は、実ユーザー・`activeStays`・`billId` を前提とした通常参加者の待機情報として維持する。

### 2.3 通常 waiting とは UI 上だけ統合表示する

データ上は以下のように分離する。

```text
通常参加者:
scheduledTournaments/{tournamentId}/tablesSeat/waiting

置きバケ一時参加者:
scheduledTournaments/{tournamentId}/okibakeTemporaryEntries/{okibakeEntryId}
```

店舗デバイス上の待機者一覧では、通常 waiting と置きバケ一時参加者を UI 上で統合表示する。

ただし、内部データおよび操作経路は分ける。

### 2.4 `pendingBillCharges` は採用しない

今回の置きバケ対応では、`pendingBillCharges` は作成しない。

理由は、置きバケ一時参加者を表す `okibakeTemporaryEntries` が、`bill` 接続前の状態も含めて管理するためである。

未接続・未会計確認対象は、`okibakeTemporaryEntries.billLinkStatus` によって管理する。

### 2.5 会計・売上反映は最終的に `bills` 側で行う

置きバケ一時参加者の専用データだけで、会計済み・売上反映済みとして扱ってはならない。

置きバケ由来の会計・精算・売上反映・analytics 反映は、最終的に通常の `bills` 側の処理に接続して行う。

### 2.6 レジスト締切による自動禁止は行わない

レジスト締切を過ぎていること自体を理由に、システムで置きバケ作成・参加登録・席配置を自動禁止しない。

レジスト締切は、店舗が判断するための目安として扱う。

### 2.7 スタック残量管理は対象外とする

本機能では、トーナメント進行におけるスタック残量管理は行わない。

対象外とするものは以下である。

- スタック残量の保存
- ブラインドによる自動減算
- BBアンティによる自動減算
- チップ推移の管理
- 置きバケ中の残スタック算出

置きバケ参加者を席に配置した後、現場上はスタックを置いて進行するが、システム上は参加状態・席状況・参加人数・`bills` 接続状態を管理対象とする。

## 3. データ配置

### 3.1 `okibakeTemporaryEntries` の配置

置きバケ一時参加者は、対象トーナメント配下のサブコレクションに保存する。

```text
scheduledTournaments/{tournamentId}/okibakeTemporaryEntries/{okibakeEntryId}
```

### 3.2 この配置を採用する理由

置きバケ一時参加者は、店舗全体に独立して存在するデータではなく、特定トーナメントに従属する参加者データである。

そのため、対象トーナメントの配下に置く。

この配置により、以下の操作を `tournamentId` 起点で扱える。

- 置きバケ一時参加者作成
- 通常 waiting との UI 上の統合表示
- 置きバケ席配置
- 置きバケ取消・無効化
- トーナメント終了時の未接続確認
- トーナメント履歴・戻しとの紐付け

### 3.3 横断検索

`pending_review` など、トーナメントを横断して確認する必要がある場合は、Firestore の collection group query を使用する。

```text
collectionGroup("okibakeTemporaryEntries")
```

将来的に横断検索の負荷や表示要件が強くなった場合は、トップレベルに補助インデックスを追加する可能性がある。

ただし、初期仕様ではトップレベルの本体コレクションは作成しない。

## 4. ドキュメントID

### 4.1 `okibakeEntryId`

`okibakeTemporaryEntries` のドキュメントIDは Firestore の自動IDとする。

```text
scheduledTournaments/{tournamentId}/okibakeTemporaryEntries/{autoId}
```

この自動IDを `okibakeEntryId` として扱う。

### 4.2 自動IDを採用する理由

`okibakeEntryId` は、内部処理用の安定した識別子である。

以下の操作で使用する。

- 対象置きバケ一時参加者の取得
- 席配置
- `bills` 接続
- 無効化
- 履歴・戻し
- リシート表示

店舗スタッフに見せる表示名とは役割が異なるため、ドキュメントIDに `オキバケA` などの業務表示名は使用しない。

## 5. 仮表示名

### 5.1 `temporaryDisplayName`

置きバケ一時参加者には、作成時に仮表示名を付与する。

フィールド名は以下とする。

```ts
temporaryDisplayName: string
```

例:

```text
オキバケA
オキバケB
オキバケC
```

### 5.2 `temporaryDisplayName` の意味

`temporaryDisplayName` は、置きバケ一時参加者作成時に付与される追跡用の仮表示名である。

実ユーザーと接続された後も、`temporaryDisplayName` は原則として変更しない。

理由は、履歴・戻し・接続修正・監査において、元の置きバケ枠を追跡できるようにするためである。

### 5.3 実ユーザー指定時の扱い

置きバケ作成時に実ユーザーを指定した場合でも、`temporaryDisplayName` は必ず付与する。

例:

```ts
{
  temporaryDisplayName: "オキバケB",
  linkedUserId: "uid_123",
  linkedUserPokerName: "山田"
}
```

この場合、店内 UI の主表示は `山田`（対象ユーザー名）としてよい（§11.7）。

ただし、内部的には `オキバケB` の置きバケ一時参加者として追跡する。

### 5.4 UI 表示名の解決

画面上の主表示名は、以下の優先順位で決定する。

```ts
primaryDisplayName = linkedUserPokerName ?? temporaryDisplayName;
```

店舗向け画面上の名前の出しわけおよび「対象ユーザー」「アドオン希望」「メモ」の登録入力は §11.7 と整合させ、実装語を避けるラベル付けは §11.9 に従う。

表示例:

```text
実ユーザー未指定:
オキバケA

実ユーザー指定済み:
山田
補助表示: オキバケB
```

詳細画面、履歴画面、戻し画面では、必要に応じて両方を表示する。

```text
オキバケB（山田）
```

## 6. 採番カウンタ

### 6.1 `okibakeNextDisplayNumber`

`temporaryDisplayName` の採番カウンタは、親トーナメントドキュメントに持たせる。

```text
scheduledTournaments/{tournamentId}.okibakeNextDisplayNumber
```

型は number とする。

```ts
okibakeNextDisplayNumber: number
```

### 6.2 初期値

`okibakeNextDisplayNumber` が未設定の場合は、初期値 `1` として扱う。

### 6.3 採番処理

置きバケ一時参加者を作成する際、Cloud Functions の transaction 内で以下を行う。

```text
1. scheduledTournaments/{tournamentId}.okibakeNextDisplayNumber を読む
2. 現在値をもとに temporaryDisplayName を生成する
3. okibakeTemporaryEntries/{okibakeEntryId} を作成する
4. okibakeNextDisplayNumber を +1 する
```

### 6.4 実ユーザー指定時も加算する

実ユーザーを指定して置きバケ登録した場合でも、`okibakeNextDisplayNumber` は加算する。

理由は、すべての `okibakeTemporaryEntries` に追跡用の仮表示名を一貫して付与するためである。

例:

```text
1件目:
temporaryDisplayName: オキバケA
linkedUserPokerName: null
UI表示: オキバケA

2件目:
temporaryDisplayName: オキバケB
linkedUserPokerName: 山田
UI表示: 山田

3件目:
temporaryDisplayName: オキバケC
linkedUserPokerName: null
UI表示: オキバケC
```

この場合、画面上で `オキバケA` と `山田` が表示されている場合でも、次に作成される実ユーザー未指定の置きバケは `オキバケC` となる。

### 6.5 アルファベット連番

`temporaryDisplayName` は以下の形式とする。

```text
オキバケ + アルファベット連番
```

採番例:

| okibakeNextDisplayNumber | temporaryDisplayName |
| -----------------------: | -------------------- |
|                        1 | オキバケA                |
|                        2 | オキバケB                |
|                       26 | オキバケZ                |
|                       27 | オキバケAA               |
|                       28 | オキバケAB               |
|                       52 | オキバケAZ               |
|                       53 | オキバケBA               |

26件を超えた場合は、Excel の列名と同じ考え方で `AA`, `AB` のように採番する。

## 7. 状態管理

### 7.1 `entryStatus`

置きバケ一時参加者のトーナメント上の状態は、`entryStatus` で管理する。

```ts
entryStatus:
  | "registered"
  | "seated"
  | "busted"
  | "voided";
```

### 7.2 `entryStatus` の意味

```text
registered
= 置きバケ一時参加者として作成済み
= トーナメント参加者として扱う
= 原則として席未配置
= 参加人数・プライズ計算への反映対象

seated
= 席配置済み
= 本人未到着でも着席済み参加者として扱う
= ブラインド/アンティでスタックが減る前提

busted
= トーナメント参加者として成立した上で敗退した状態
= 置きバケ一時参加者が席配置後にバーストした状態
= 参加人数・プライズ計算上は参加者として扱う
= `voided` とは異なり、登録取消ではない

voided
= 店舗判断により、置きバケ一時参加者としての登録を取り消した状態
= 登録自体の取消であり、`busted`（敗退）とは別概念である
```

`busted` と `voided` は別概念である。

`busted` は、トーナメント参加者として成立した後に敗退した状態である。

`voided` は、置きバケ一時参加者としての登録自体を取り消した状態である。

`voided` は、来店しなかった状態や `bills` 未接続の確認待ち状態を表すものではない。

来店せず `bills` 未接続のまま確認が必要な場合は、`billLinkStatus: "pending_review"` で管理する。

誤作成、対象トーナメント間違い、重複作成、ユーザーからのキャンセルなどは、`voided` にする理由であり、`voided` の状態定義そのものではない。

また、操作履歴から行う「戻し」は `voided` とは別概念である。

戻しは、選択された操作が行われなかった状態に戻すための処理であり、`entryStatus` の状態定義には含めない。

### 7.3 `created` は採用しない

`entryStatus` に `created` は採用しない。

理由は、今回の仕様では、置きバケ一時参加者を作成すること自体が、置きバケ参加者として登録することと同義に近いためである。

作成直後の状態は以下とする。

```ts
entryStatus: "registered"
```

## 8. `bills` 接続状態

### 8.1 `billLinkStatus`

置きバケ一時参加者の `bills` 接続状態は、`billLinkStatus` で管理する。

```ts
billLinkStatus:
  | "unlinked"
  | "linked"
  | "pending_review";
```

### 8.2 `billLinkStatus` の意味

```text
unlinked
= まだ bills に接続されていない

linked
= bills に接続済み
= 以後の会計・精算・analytics は bills 側で処理する

pending_review
= トーナメント終了時点で伝票未接続のまま残っており、
  店舗側が対応確認すべき状態（詳細は §15）
```

### 8.3 作成直後の状態

置きバケ一時参加者作成直後の状態は以下とする。

```ts
entryStatus: "registered"
billLinkStatus: "unlinked"
```

### 8.4 `userLinkStatus` は採用しない

実ユーザーとの接続状態を表す `userLinkStatus` は採用しない。

理由は、会計上重要な境界は、最終的に `bills` に接続できたかどうかであるためである。

ただし、対象ユーザーが分かっている場合は、接続先または接続候補としてユーザー情報をフィールドに保持する。

## 9. ユーザー情報

### 9.1 実ユーザー情報の保持

置きバケ作成時または後続操作で実ユーザーが特定できる場合、以下を保持する。

```ts
linkedUserId: string | null;
linkedUserPokerName: string | null;
```

### 9.2 `linkedUserId` があり `linkedBillId` がない状態

以下の状態は許容する。

```ts
linkedUserId: "uid_123"
linkedUserPokerName: "山田"
linkedBillId: null
billLinkStatus: "unlinked"
```

この状態は、実ユーザーは特定済みだが、まだ `bills` には接続されていない状態を表す。

### 9.3 `linkedUserPokerName` の扱い

`linkedUserPokerName` は、UI 表示と履歴表示のために保持する。

ただし、ユーザー情報の正本は既存のユーザーデータ側であり、`linkedUserPokerName` は置きバケ一時参加者作成・接続時点の表示用スナップショットとして扱う。

## 10. `okibakeTemporaryEntries` データ構造

本書のコード例における `now` は、文字列 `"now"` ではなく、Cloud Functions 側で生成した現在時刻の `Timestamp` を意味する shorthand とする。

現時点で確定している基本構造は以下とする。

```ts
type OkibakeTemporaryEntry = {
  okibakeEntryId: string;

  tournamentId: string;

  temporaryDisplayName: string;

  linkedUserId: string | null;
  linkedUserPokerName: string | null;

  linkedBillId: string | null;
  linkedAt: Timestamp | null;

  entryStatus: "registered" | "seated" | "busted" | "voided";
  billLinkStatus: "unlinked" | "linked" | "pending_review";

  addonIntent: "unknown" | "yes" | "no";

  memo: string | null;
  okibakeAddonCount: number;
  lastOkibakeAddonAt: Timestamp | null;
  okibakeAddonRecords: OkibakeAddonRecord[];

  assignedTableId: string | null;
  assignedSeatKey: string | null;
  seatedAt: Timestamp | null;

  bustedAt: Timestamp | null;
  bustedTableId: string | null;
  bustedSeatKey: string | null;

  createdAt: Timestamp;
  updatedAt: Timestamp;

  createdByDeviceId: string | null;
  updatedByDeviceId: string | null;

  voidedAt: Timestamp | null;
  voidedByDeviceId: string | null;
};
```

```ts
type OkibakeAddonRecord = {
  addonRecordId: string;
  operationId: string;

  occurredAt: Timestamp;
  createdByDeviceId: string | null;

  reflectedToBill: boolean;
  reflectedToBillAt: Timestamp | null;
  linkedBillId: string | null;

  rolledBack: boolean;
  rollBackAt: Timestamp | null;
  rollBackBy: string | null;
};
```

### 10.1 `okibakeEntryId`

Firestore の自動ドキュメントIDと同値を保持する。

### 10.2 `tournamentId`

対象トーナメントIDを保持する。

`scheduledTournaments/{tournamentId}` 配下に保存されるためパス上も `tournamentId` は分かるが、collection group query で横断検索するため、フィールドとしても保持する。

### 10.3 `temporaryDisplayName`

作成時に自動採番された仮表示名を保持する。

例:

```text
オキバケA
オキバケB
オキバケAA
```

### 10.4 `linkedUserId`

実ユーザーが特定済みの場合、その Firebase UID を保持する。

未特定の場合は `null` とする。

### 10.5 `linkedUserPokerName`

実ユーザーが特定済みの場合、そのユーザーの表示名スナップショットを保持する。

未特定の場合は `null` とする。

### 10.6 `linkedBillId`

`bills` に接続済みの場合、接続先の `billId` を保持する。

未接続の場合は `null` とする。

### 10.7 `linkedAt`

`bills` に接続した日時を保持する。

未接続の場合は `null` とする。

### 10.8 `entryStatus`

トーナメント上の置きバケ一時参加者状態を保持する。

`registered` / `seated` / `busted` / `voided` の意味は §7.2 を参照する。

### 10.9 `billLinkStatus`

`bills` 接続状態を保持する。`pending_review` の意味・遷移・来店なし入金登録との関係は **§15** を正とする。

### 10.10 `addonIntent`

置きバケ連絡時点でユーザーから聞いたアドオン希望を保持する。

```ts
addonIntent: "unknown" | "yes" | "no";
```

意味は以下とする。

```text
unknown
= アドオン希望を聞いていない、または不明

yes
= ユーザーがアドオン希望あり

no
= ユーザーがアドオン希望なし
```

`addonIntent` は、あくまで希望・聞き取り情報であり、実際にアドオン処理が行われたことを意味しない。

```text
addonIntent: "yes"
≠ addon 実施済み
```

### 10.11 `okibakeAddonCount`

`okibakeAddonRecords` のうち `rolledBack: false` に該当する有効 addon 実施記録の件数を、親ドキュメント上にキャッシュとして保持する表示・検索用サマリである。

初期値は `0` とする。

**Addon 実行可能な総回数の上限は `scheduledTournament.addonLimitPerPlayer` と `isAddon` により決まる（§16.0）**。boolean だけでは実施回数や履歴を表せないため、count と **`okibakeAddonRecords` 配列**で管理する。

### 10.12 `lastOkibakeAddonAt`

`okibakeAddonRecords` のうち `rolledBack: false` に該当する有効 addon 実施記録のうち、最後に実施された addon の `occurredAt` を、親ドキュメント上にキャッシュとして保持する表示・検索用サマリである。

有効な addon 記録が1件もない場合は `null` とする。

### 10.13 `assignedTableId`

置きバケ一時参加者が席配置済みの場合、配置先の `tablesSeat/{tableId}` の `tableId` を保持する。

席未配置の場合は `null` とする。

### 10.14 `assignedSeatKey`

置きバケ一時参加者が席配置済みの場合、配置先の席キーを保持する。

例:

```text
seat01
seat02
```

席未配置の場合は `null` とする。

### 10.15 `seatedAt`

置きバケ一時参加者を席配置した日時を保持する。

席未配置の場合は `null` とする。

### 10.16 `bustedAt`

置きバケ一時参加者がバーストした日時を保持する。

`entryStatus` が `busted` ではない場合は `null` とする。

### 10.17 `bustedTableId`

置きバケ一時参加者がバーストした時点の `tableId` を保持する。

`entryStatus` が `busted` ではない場合は `null` とする。

### 10.18 `bustedSeatKey`

置きバケ一時参加者がバーストした時点の `seatKey` を保持する。

`entryStatus` が `busted` ではない場合は `null` とする。

### 10.22 `seatedByDeviceId` は採用しない

初期仕様では、`seatedByDeviceId` は採用しない。

席配置した店舗デバイスは、席配置時に更新される `updatedByDeviceId` により追跡する。

### 10.23 `okibakeAddonApplied` / `okibakeAddonAppliedAt` は採用しない

初期仕様では、`okibakeAddonApplied` / `okibakeAddonAppliedAt` は採用しない。

理由は、 Addon 実行は **複数回になり得る**（上限は **`addonLimitPerPlayer`**。§16.0）ほか、boolean だけでは実施回数・履歴・bills 反映・rollback を正しく扱えないため、`okibakeAddonRecords` 配列で管理するためである。

### 10.24 `bustedByDeviceId` は採用しない

初期仕様では、`bustedByDeviceId` は採用しない。

バースト操作を行った店舗デバイスは、操作時に更新される `updatedByDeviceId` により追跡する。

### 10.25 `createdAt` / `updatedAt`

作成日時・更新日時を保持する。

### 10.26 `createdByDeviceId` / `updatedByDeviceId`

作成または更新操作を行った店舗デバイスを保持する。

認証・権限確認の詳細は、Callable 仕様で定義する。

### 10.27 `okibakeAddonRecords`

置きバケ addon の実施記録は、`addonEvents` サブコレクションではなく、`okibakeTemporaryEntries/{okibakeEntryId}` ドキュメント内の配列フィールドとして保持する。

```ts
okibakeAddonRecords: OkibakeAddonRecord[];
```

型は以下とする。

```ts
type OkibakeAddonRecord = {
  addonRecordId: string;
  operationId: string;

  occurredAt: Timestamp;
  createdByDeviceId: string | null;

  reflectedToBill: boolean;
  reflectedToBillAt: Timestamp | null;
  linkedBillId: string | null;

  rolledBack: boolean;
  rollBackAt: Timestamp | null;
  rollBackBy: string | null;
};
```

`okibakeAddonRecords` は、addon 実施1回ごとの最小記録である。

**同一参加者が Addon を複数回行ってよい場合の上限は、トーナメントの `addonLimitPerPlayer` と `isAddon` により決まる（§16.0）。**運用上は多くで 1回で足りることもあるが、**上限が複数であるトーナメントでは複数回の実行と履歴が生じうる**。

複数実行が許されている範囲では、複数履歴になり得る前提として、addon 実施のたびに既存 record を上書きせず、新しい `OkibakeAddonRecord` を配列へ追加する。

addonRecordId

addon 実施 record の識別子を保持する。

operationId

二重実行防止・冪等性・`operationLog` 紐付け用 ID を保持する。

occurredAt

addon を実施した日時を保持する。

createdByDeviceId

addon 処理を行った店舗デバイス ID を保持する。

reflectedToBill

対象 addon record が `bills` 側へ反映済みかどうかを保持する。

```text
false
= bills 側へ未反映

true
= bills 側へ反映済み
```

reflectedToBillAt

対象 addon record を `bills` 側へ反映した日時を保持する。

未反映の場合は `null` とする。

linkedBillId

対象 addon record の反映先 `billId` を保持する。

未反映の場合は `null` とする。

rolledBack

対象 addon record が rollback 済みかどうかを保持する。

```text
false
= 有効な addon 実施記録。bills 接続時の反映対象になり得る。

true
= rollback 済みの addon 実施記録。bills 側へ反映対象にしない。
```

rollBackAt

対象 addon record が rollback された日時を保持する。

`rolledBack: false` の場合は `null` とする。

rollBackBy

対象 addon record を rollback した主体を保持する。

`rolledBack: false` の場合は `null` とする。

#### `rolledBack` / `rollBackAt` / `rollBackBy`（補足）

`voided` はすでに `entryStatus: "voided"` として「置きバケ登録自体の取消」を表す語である。

addon 実施記録の取消に `voided` を使うと混同しやすい。

既存 rollback 実装では、`operationLogs` 側で `rolledBack` / `rollBackAt` / `rollBackBy` が使われているため、その語彙に合わせる。

#### 配列更新時の注意

`okibakeAddonRecords` は、通常想定では少数件の履歴配列として扱う。

配列内 record の更新は、Cloud Functions の transaction 内で `okibakeTemporaryEntries/{okibakeEntryId}` を読み取り、`okibakeAddonRecords` 配列をメモリ上で更新し、配列全体を書き戻す。

addon の大量履歴管理が必要になった場合は、将来的に `addonEvents` サブコレクション化を再検討する。

#### `addonEvents` サブコレクションは採用しない

初期仕様では、以下のサブコレクションは採用しない。

```text
scheduledTournaments/{tournamentId}/okibakeTemporaryEntries/{okibakeEntryId}/addonEvents/{addonEventId}
```

理由は、サブコレクション配下にさらに addon 用サブコレクションを作らず、置きバケ一時参加者ドキュメント内で少数件の addon 記録を管理するためである。

### 10.28 `voidedAt`

置きバケ一時参加者を `voided` にした日時を保持する。

`entryStatus` が `voided` ではない場合は `null` とする。

### 10.29 `voidedByDeviceId`

置きバケ一時参加者を `voided` にした店舗デバイスIDを保持する。

`entryStatus` が `voided` ではない場合は `null` とする。

### 10.30 `voidReason` は採用しない

初期仕様では、`voided` にした理由を分類する `voidReason` は採用しない。

理由は、取消理由の分類管理よりも、まずは「取消されたか」「いつ取消されたか」「どの店舗デバイスで取消されたか」を管理できれば十分であるためである。

### 10.31 `memo`

置きバケ登録時にスタッフが入力した任意メモを保持する。

フィールド名は `memo` とする（`okibakeTemporaryEntries` 配下であるため、`okibakeMemo` としない）。

```ts
memo: string | null;
```

仕様は以下とする。

```text
- memo は置きバケ登録時の任意メモである
- 型は string | null である
- 最大長は 200 文字とする（Cloud Functions で検証）
- 未入力・空文字・空白のみは null として保存する（入力は trim し、結果が空なら null）
- 対象ユーザー未指定時や、まだ来店ユーザーデータに存在しない参加者の識別補助として使う
- 伝票紐付け時・来店・ログイン後の置きバケ確認時の確認材料として表示し得る
- 初期仕様では検索対象にしない（理由は §11.2 に記載する）
```

## 11. 置きバケ作成仕様

### 11.1 概要

店舗スタッフは、店舗デバイス上で置きバケ一時参加者を作成できる。

置きバケ一時参加者は、作成時点でトーナメント参加者として扱う。

### 11.2 作成時の入力

現時点で想定する入力は以下である。

```ts
type CreateOkibakeTemporaryEntryInput = {
  tournamentId: string;

  linkedUserId?: string | null;
  linkedUserPokerName?: string | null;

  addonIntent: "unknown" | "yes" | "no";

  memo?: string | null;
};
```

`addonIntent` は、置きバケ登録ダイアログ経由での作成においては**省略不可・必ずいずれかを選択させる**。選択肢と内部値の対応は §11.7 を参照する。

`addonIntent` は、ユーザーから聞いたアドオン希望を表す。

`addonIntent: "yes"` であっても、実際の addon 処理済みとは扱わない。

#### `memo`

`memo` は任意とする。

仕様は以下とする。

```text
- Cloud Functions 側で trim する
- trim 後に空文字の場合は null として保存する（未入力・空白のみも null）
- 最大 200 文字とし、超過する場合はエラーとする
```

保存時の正規化イメージは以下とする（実装では 200 文字上限の検証を必ず行う）。

```ts
memo: input.memo?.trim() ? input.memo.trim() : null
```

`memo` は補助的な確認情報であり、**初期仕様では検索対象にしない**。

理由は以下である。

```text
- memo は主検索キーではないため
- 自由記述を検索対象にすると、曖昧検索・インデックス設計・個人情報の扱いが重くなるため
```

### 11.3 作成時に行う処理

置きバケ作成処理では、最低限以下を行う。

```text
1. 店舗デバイス権限を確認する
2. 対象トーナメントの存在を確認する
3. scheduledTournaments/{tournamentId}.okibakeNextDisplayNumber を取得する
4. temporaryDisplayName を生成する
5. okibakeTemporaryEntries/{okibakeEntryId} を作成する
6. okibakeNextDisplayNumber を +1 する
7. `scheduledTournaments/{tournamentId}/views/main` のカウンタを §11.5 に従い更新する
8. 操作ログを記録する
```

### 11.4 作成時の初期状態

```ts
entryStatus: "registered"
billLinkStatus: "unlinked"
linkedBillId: null
linkedAt: null
addonIntent: input.addonIntent
memo: （§11.2 の `memo` 仕様に従い正規化した値。未入力・空白のみは null）
okibakeAddonCount: 0
lastOkibakeAddonAt: null
okibakeAddonRecords: []
assignedTableId: null
assignedSeatKey: null
seatedAt: null
bustedAt: null
bustedTableId: null
bustedSeatKey: null
voidedAt: null
voidedByDeviceId: null
```

実ユーザー未指定の場合:

```ts
linkedUserId: null
linkedUserPokerName: null
```

実ユーザー指定ありの場合:

```ts
linkedUserId: "uid_123"
linkedUserPokerName: "山田"
```

### 11.5 作成時のカウンタ反映

置きバケ一時参加者は、作成時点で `entryStatus: "registered"` とし、トーナメント参加者として扱う。

そのため、作成時に以下のカウンタを更新する。

```text
views/main.entries +1
views/main.playersIn +1
views/main.waitingCount +1
```

一方で、作成直後は席未配置であるため、以下は更新しない。

```text
views/main.seatedCount
```

`entries` は、置きバケ一時参加者を参加人数・プライズ計算への反映対象として扱うため、作成時に `+1` する。

`playersIn` は、既存の通常参加登録と同様に、トーナメント参加者として登録された人数として作成時に `+1` する。

`waitingCount` は、物理的な `tablesSeat/waiting` の件数だけではなく、店舗デバイス上の待機者一覧に表示される業務上の待機者数として扱う。

置きバケ一時参加者は既存 `tablesSeat/waiting` には保存しないが、`entryStatus: "registered"` の間は待機者一覧に表示されるため、作成時に `waitingCount` を `+1` する。

`seatedCount` は、席配置済み参加者数を表すため、作成時点では更新しない。

### 11.6 トーナメント操作画面の「置きバケ登録」ボタン

店舗デバイスのトーナメント操作画面に、`置きバケ登録` ボタンを追加する。

配置場所は、画面下部の `トーナメント操作` エリアとする。

`置きバケ登録` ボタンは、`全員リシート` と `終了処理` の間に配置する。

想定する並びは以下である。

```text
参加者登録
順位確定
全員リシート
置きバケ登録
置きバケ一覧
終了処理
プライズ確定
操作履歴
```

`置きバケ登録` ボタンを押下すると、置きバケ一時参加者を作成するための登録ダイアログを表示する。

`置きバケ一覧` ボタンを押下すると、該当トーナメントの置きバケ一時参加者を状態別に一覧表示するダイアログを開く（§12.8）。

### 11.7 置きバケ登録ダイアログ

置きバケ登録ダイアログでは、画面文脈上すでに明らかな情報は表示しない。

以下は表示しない。

```text
- 説明文
- 対象トーナメント名
```

理由は、トーナメント操作画面上の `置きバケ登録` ボタンから開くため、対象トーナメントは文脈上明らかであるためである。

登録ダイアログの入力項目は以下とする。

```text
- 対象ユーザー: 任意
- アドオン希望: 必須
- メモ: 任意
```

登録実行前には確認ダイアログを必ず表示する。対象ユーザー選択の有無に関わらず、スタッフが「対象ユーザーあり/未設定」を確認したうえで登録を確定できる導線とする。具体文言は既存 UI の文体に合わせ、ここでは固定しない。

#### 対象ユーザー

対象ユーザーの指定は任意とする。

対象ユーザーを指定しない場合は、作成される置きバケ一時参加者の UI 上の主表示名として、自動採番される `temporaryDisplayName` を使用する（§5.4）。

対象ユーザーを指定する場合は、ユーザー検索または既存ユーザー選択によりユーザーを選択する。

**トーナメント終了処理（通常終了および `force_ended` を含む）を完了させるまでに、すべての該当置きバケに対象ユーザー（`linkedUserId`）を紐付けなければならない。** 未接続かつ未設定の置きバケが残る場合は終了を完了させない（§15.4）。

店舗向けガイダンス（登録ダイアログまたは対象ユーザー入力付近へ **軽く** 載せてよい。レイアウトは UI 実装時に調整してよい）:

```text
分かる場合は対象ユーザーを選択してください。選択しておくと、通常トーナメント参加との重複を防ぎやすくなります。（詳細 §22）
```

対象ユーザーが指定されている場合、UI 上の主表示名は対象ユーザーの表示名（`linkedUserPokerName` を第一候補とするデータ）を優先する。

ただし、対象ユーザーが指定されている場合でも、`temporaryDisplayName` は必ず自動採番する（作成仕様および §5.3 と同様）。これは内部的な追跡用として維持する。

```text
対象ユーザー指定なし:
主表示名 = temporaryDisplayName

対象ユーザー指定あり:
主表示名 = （UI としての）対象ユーザー表示名 ← データ上は linkedUserPokerName 等
補助表示 = temporaryDisplayName
```

#### アドオン希望

アドオン希望は **必須入力** とする。

選択肢は以下とする。

```text
あり
なし
不明
```

内部値との対応は以下とする。

```text
あり → addonIntent: "yes"
なし → addonIntent: "no"
不明 → addonIntent: "unknown"
```

`addonIntent` は、アドオン希望・聞き取り情報であり、実際に addon が実施されたことを意味しない。

実際の addon 実施は、参加者の経路により **`applyOkibakeAddon`**（置きバケ entry として扱う参加者）または **既存の通常参加者向け addon Callable**（通常ユーザーとして扱う参加者）によって行う。待機者一覧からでも実行できる（§12.7）。

`registered` であっても、置きバケ entry とみなして `applyOkibakeAddon` を実行できる（詳細・カウンタは §16.7）。

#### メモ

メモは **任意入力** とする。

仕様は以下とする。

```text
- 最大 200 文字とする
- 対象ユーザーを指定しない場合や、まだ来店していないためユーザー検索に存在しない参加者について、後続の伝票紐付けや来店確認の補助として使う
- 入力例:「田中さんの友人」「初来店予定」「20時頃来店予定」など
```

Cloud Functions での trim・空保存ルール・文字数チェックは §11.2 に従う。

### 11.8 登録ダイアログの表示例

対象ユーザー未指定の場合:

```text
置きバケ登録

対象ユーザー
未指定
[ユーザーを選択]

アドオン希望 *
○ あり

○ 不明

メモ
[例: 田中さんの友人 / 初来店予定 / 20時頃来店予定]

```

```text

[変更] [未指定に戻す]

アドオン希望 *
○ あり

[例: 田中さんの友人 / 初来店予定 / 20時頃来店予定]

```

### 11.9 店舗スタッフ向け UI 文言

店舗スタッフ向け UI において、`bills`、`linkedBillId`、`billLinkStatus` のような実装詳細フィールドを表示ラベルのままユーザーに見せない。

置きバケ一時参加者を来店後のユーザーの伝票へ紐付ける操作は、精算開始ではなく「伝票への紐付け」である。そのため UI では **`会計`** より **`伝票`** を主語とした語を用いる。

```text
bills
→ 伝票

bill 未接続
→ 伝票未接続

bill 接続済み / linked 状態の文脈
→ 伝票接続済み

linkedUser
→ 対象ユーザー

linkOkibakeTemporaryEntryToBill（Callable 名は変更しない）
→ 伝票紐付け
```

ボタン名としては **`伝票紐付け`** を用いる（「会計接続」などは使わない）。

理由は以下である。

- この操作は精算・会計開始ではなく、既存の未精算伝票へ置きバケ一時参加者を接続する処理であるため。
- 店舗スタッフにとって「伝票」の方が操作対象を把握しやすいため。

```text
NG:
bills に接続します
bill 未接続
linkedUserId を指定してください

OK:
伝票に紐付けます
伝票未接続
対象ユーザーを選択してください
```

待機者一覧・卓画面などにも同趣旨でラベルを揃える（例:「伝票未接続」を用い、`bill未接続` のような開発者向け表記だけをユーザーに見せない）。

### 11.10 UI 実装の進め方（メモ）

本書では、置きバケ対応に必要な UI 仕様を段階的に確定していく。

ただし、UI 実装は本書に記載された UI 仕様を一括でまとめて実装する前提ではない。

実装時は、ユーザーの指示に従い、対象画面・対象導線ごとに順次実装する。

## 12. 通常 waiting との UI 統合表示

### 12.1 基本方針

店舗デバイス上の待機者一覧では、以下を UI 上で統合表示する。

```text
通常参加者:
scheduledTournaments/{tournamentId}/tablesSeat/waiting

置きバケ一時参加者:
scheduledTournaments/{tournamentId}/okibakeTemporaryEntries
  where entryStatus == "registered"
```

### 12.2 データ上は統合しない

置きバケ一時参加者は、通常 waiting には保存しない。

`waiting.requestType` のようなフィールド追加によって通常 waiting に混在させる設計は採用しない。

### 12.3 `waitingCount` の扱い

置きバケ一時参加者は、既存 `tablesSeat/waiting` には保存しない。

ただし、`entryStatus: "registered"` の置きバケ一時参加者は、店舗デバイス上の待機者一覧に表示される。

そのため、`views/main.waitingCount` は、物理的な `tablesSeat/waiting` の件数だけではなく、店舗デバイス上の待機者一覧に表示される業務上の待機者数として扱う。

`waitingCount` の対象は以下である。

```text
通常 waiting の参加者
+
entryStatus: "registered" の置きバケ一時参加者
```

したがって、置きバケ作成時には `tablesSeat/waiting` には保存しないが、`views/main.waitingCount` は `+1` する。

置きバケ一時参加者が席配置され、`entryStatus: "seated"` になった場合は、待機者一覧から外れる。このときの `views/main.waitingCount` は §13.12 に従い `-1` する（`seatedCount` は変更しない）。

### 12.4 表示上の区別

待機者一覧では、通常参加者と置きバケ一時参加者を区別できるようにする。

表示例:

```text
通常参加者:
山田

置きバケ一時参加者・実ユーザー未指定:
オキバケA
ラベル: 置きバケ

置きバケ一時参加者・実ユーザー指定済み:
佐藤
補助表示: オキバケB
ラベル: 置きバケ / 伝票未接続
```

一覧・その他の店舗向け画面上の文言は、`bills` 等の実装語をそのまま出さず、§11.9 に従う。

#### 待機者一覧カードにおける `memo` 表示（暫定）

待機者一覧の置きバケカードでは、**`memo` が `null` でない場合に「メモあり」と表示する案を暫定とする**。

```text
確定ではない。カード上に全文を表示すると UI が重くなる可能性があるため、初期案として「メモあり」に留める。
最終表示は実装時または UI 確認時に調整し得る。
```

`memo` の全文は、必要に応じて詳細ダイアログや伝票紐付け・来店確認の導線で確認する（§14.2）。

### 12.5 操作経路

置きバケ一時参加者の**作成（登録）** は、§11.6 の `トーナメント操作` エリアにある `置きバケ登録` ボタンおよび §11.7 のダイアログから行う。

通常参加者に対する着席操作は、既存の通常参加者向け経路を使用する。

置きバケ一時参加者に対する席配置操作は、置きバケ専用経路を使用する。

待機者一覧からの Addon は §12.7 を参照する。

置きバケ一時参加者の状態確認・伝票紐付け漏れ解消は、§12.8 の `置きバケ一覧` からも行える。

### 12.6 待機者一覧からの伝票紐付け

`entryStatus: "registered"` の置きバケカードには、通常の着席操作ボタンの横に **`伝票紐付け`** ボタンを配置する。

通常参加者カードの例:

```text
[着席]
```

置きバケカードの例:

```text
[着席] [伝票紐付け]
```

`伝票紐付け` を押下すると、伝票紐付けダイアログを開く（§14.2）。

この導線は、来店済みだがまだ席についていない置きバケ一時参加者を、対象ユーザー・伝票へ紐付けるために使用する。

ボタンのみに限らず、§12.7 の操作ダイアログ内から伝票紐付けへ進む構成も許容する（待機者一覧 UI は暫定）。

### 12.7 待機者一覧からの Addon

#### 概要

待機者一覧から **Addon を実行可能とする**。

対象は次の両方とする。

```text
通常ユーザー（scheduledTournaments/.../tablesSeat/waiting にいる参加者）
置きバケ一時参加者（entryStatus が registered のとき待機者一覧に表示される者）
```

内部処理経路は次により分離する。

```text
通常ユーザー:
既存の通常参加者向け addon Callable（addon.ts が表す処理群）を用いる。

置きバケ（okibake entry として扱う参加者）:
applyOkibakeAddon を用いる。
```

伝票接続済みで **通常ユーザーとして扱う参加者** は、これまでどおり **`seatXXUserId` を優先する経路へ合流**させ、通常 addon 側で処理する（§13.9・§14.2 と整合）。

#### Addon 経路選択と `billLinkStatus`

Addon 実行可否および Callable 選択の **主軸に `billLinkStatus`／伝票接続有無を置かない**。

整理は次とする。

```text
経路選択の主軸:
通常ユーザーとして扱う参加者 → 通常 addon Callable
置きバケ entry として扱う参加者 → applyOkibakeAddon
```

`billLinkStatus: "linked"` の置きバケ entry が **`applyOkibakeAddon`** にわたってきた場合は、**誤経路として拒否してよい**（防御実装）。

#### 通常ユーザーの待機者一覧 Addon

通常ユーザーについては、**既存 addon の成立条件を満たせば**、待機者一覧から Addon を実行してよい。

成立条件として少なくとも次を確認する。

```text
- activeStay がある
- billId がある
- 対象トーナメントへの参加済み（bills 側 tournament 記録の存在等、既存ロジックに従う）
- 当該トーナメントが addon を許す状態である（snapshot.isAddon 相当の判定に従う）
- `scheduledTournaments/{tournamentId}` が `isAddon` true などとして Addon を許しており、`bills` 側の当該 templateId の **`addonCount` が `scheduledTournament.addonLimitPerPlayer` 未満**であること（未定義フィールド時の読み込みフォールバックは §16.0）
```

**着席済みであることは Addon 実行条件に含めない。**

卓上 Addon でも `tablesSeat` から卓・席を探す処理はあるが、その主用途は **`operationLog` への補助情報付与である。待機者一覧から実行する Addon では、tableId／seatNumber が無いことを理由に失敗させない。**

#### 置きバケの待機者一覧 Addon・`applyOkibakeAddon` の `entryStatus`

置きバケについて、`applyOkibakeAddon` は次のときに **実行可能**とする。

```text
実行可能:
- registered
- seated

実行不可:
- busted
- voided
```

ほか、`scheduledTournaments/{tournamentId}` で **`isAddon` が実質 false**、または効果 **`addonLimitPerPlayer` が 0** と解釈される場合も Addon **不可**。**`okibakeAddonCount >= addonLimitPerPlayer`** のときも **不可**。**`addonIntent` は実行可否ゲートとはしない（§16.2）。**

`registered` の置きバケへ Addon を実施しても、**entryStatus は `registered` のまま変更しない**。Addon は参加状態・席状態を変える操作ではないため、`entries` / `playersIn` / `waitingCount` / `seatedCount` も変更しない。

Addon 実施時は、`okibakeAddonRecords` に record を追加し、`okibakeAddonCount` / `lastOkibakeAddonAt` を更新し、`views/main.addons` を +1 する。

置きバケは実施時点で伝票が無いまたは未接続であるため、Addon 実行時に **`bills` 側へは反映しない**。未反映は `okibakeAddonRecords` に保持し、`linkOkibakeTemporaryEntryToBill` 時に後追い反映する（§14.8）。

伝票紐付け済みの置きバケ由来参加者は **通常ユーザーとして扱い、通常 addon 経路とする**。その経路での Addon は **既存の recordTournamentAction 等に従いリアルタイムに伝票側へ記録できる**。

#### `addonIntent` と Addon の関係（置きバケ）

```text
addonIntent は、スタッフが置きバケ登録時に聞いたアドオン希望情報である。

addonIntent は Addon 実行可否の判定には使用しない。

Addon 実行後も addonIntent は自動変更しない。

addonIntent が no または unknown の場合でも、Addon 実行自体は可能とする。
```

#### Addon 実行時の確認ダイアログ（通常ユーザー・置きバケ共通）

Addon 実行前は、通常ユーザー・置きバケの **両方**で確認ダイアログを表示する。

```text
- 文言は基本的に卓上 Addon 実行時と同じでよい
- 置きバケの場合は addonIntent をダイアログに表示する
- 対象ユーザー指定済みの置きバケでも、temporaryDisplayName の補助表示は必須としない
```

addonIntent が `no` のときは、次の趣旨を表示してから実行確認する。

```text
この参加者は「アドオン希望なし」として登録されています。
Addon を実施しますか？
```

addonIntent が `unknown` のときは、次の趣旨を表示する。

```text
この参加者はアドオン希望が不明です。
Addon を実施しますか？
```

いずれの場合も、**実行可否のブロック条件にはしない**。

#### UI 上の操作導線（暫定）

待機者一覧カードについて、次は **暫定案** とする。**実装時の画面構成に応じて調整可能である。**

```text
- 待機者一覧のカード自体をタップ可能にする
- カードタップで操作ダイアログを表示する
- Addon はこの操作ダイアログ内から実行する
- 置きバケの操作ダイアログには、Addon に加えて「伝票紐付け」も載せる
- 着席操作は現行どおりカード上のボタンとして維持する（§12.6 の「伝票紐付け」ボタン配置と併用・整理も許容）
```

#### `operationLog` と卓・席情報の欠落

待機者一覧 Addon では、通常ユーザー・置きバケのいずれでも **`tableId` / `seatNumber` が無いことがある**。これにより Addon を失敗させない。

rollback に必要な識別子は **`operationLog` に必ず残す**。

```text
通常ユーザーの場合:
rollback に必要な billId / templateId / playerUid を operationLog に残す。

置きバケの場合:
rollback に必要な okibakeEntryId / addonRecordId を operationLog に残す（既存規則に合わせ、payload細目は実装時に確定可）。
```

席情報が無いときは、その旨を許容した `operationLog` とする。**卓からの Addon で付く席情報は補助であり、待機者一覧 Addon の成立条件ではない**。

#### rollback / 伝票側の補正

待機者一覧からの Addon も rollback 対象とする。

```text
通常ユーザー:
既存 addon の rollbackAction 経路で戻す。

置きバケ:
rollbackAction における既存の置きバケ専用 undo 分岐（§18.6）で戻す。今回の待機者一覧 Addon は、この rollback 対象に含める（新規 undo 種別の導入自体が主目的ではない）。
```

伝票紐付け後に `reflectedToBill: true` となった addon の単体 rollback と、**誤った伝票への紐付け解除**とは区別して整理する。**誤伝票への会計前解除**は §14.14、接続後全般の補正方針との関係は §14.12 も参照する。

### 12.8 トーナメント操作タブの「置きバケ一覧」

#### 12.8.1 目的と位置づけ

`置きバケ一覧` は、トーナメント操作タブから開く **該当トーナメント専用の置きバケ一時参加者一覧ダイアログ** である（§11.6 配置）。

主目的は、**「退席後かつトーナメント進行中」（`entryStatus: "busted"` かつ `billLinkStatus: "unlinked"`）の置きバケ一時参加者に対する伝票紐付け導線を確保すること**である。

待機者一覧（§12.6・§12.7）は `entryStatus: "registered"` のみを表示し、卓ページ操作ダイアログ（§14.2）は `seated` のみを対象とするため、`busted` の置きバケが店舗端末から見えない／触れないというギャップが生じる。`置きバケ一覧` はこのギャップを埋める Phase 4 補完の店舗端末導線である。

加えて、状態確認用に `registered` / `seated` も同一ダイアログから操作できるようにする。これにより、置きバケの状態が混在する場面でも一つの導線で確認・操作を完結できる。

#### 12.8.2 表示対象

`置きバケ一覧` ダイアログでは、該当トーナメントの `okibakeTemporaryEntries` のうち、以下の状態を **操作可能な表示対象** とする。

```text
entryStatus == "registered" かつ billLinkStatus == "unlinked"
entryStatus == "seated"     かつ billLinkStatus == "unlinked"
entryStatus == "busted"     かつ billLinkStatus == "unlinked"
```

`entryStatus: "voided"`、および `billLinkStatus: "linked"` / `"pending_review"` は、**初期実装の操作対象としない**。

ただし、確認用に `linked` 済みを参照表示する余地は仕様上残してよい。表示する場合でも、本ダイアログから `linked` に対する伝票紐付け操作は提供しない（接続後の補正は §14.12・§14.14 を参照）。

`pending_review` は **§15 の要対応会計ページ側で扱う**（§14.15 と整合）。本ダイアログからは操作しない。

#### 12.8.3 ダイアログ表示

`置きバケ一覧` ダイアログは、置きバケ一時参加者をカード形式で縦方向に並べる。

カード上に最低限表示する項目は以下である。

```text
- 主表示名（§5.4 に従う）
  - linkedUserPokerName があれば優先
  - なければ temporaryDisplayName
  - いずれも欠ける場合は「置きバケ」相当のラベル
- 置きバケバッジ
- entryStatus に応じた状態ラベル
  - registered: 待機中
  - seated:     着席中
  - busted:     退席済み
- billLinkStatus に応じた伝票状態ラベル
  - unlinked:        伝票未接続
  - linked:          伝票紐付け済み（参照表示時のみ）
  - pending_review:  要対応（参照表示時のみ）
- Addon 表示
  - Addon: 現在 x / y 回
  - Addon: 上限到達 x / y 回
  - Addon: 無効
  - Addon: 回数情報を取得できませんでした
```

状態別に追加で表示する情報:

```text
registered（待機中）:
- 待機時間（既存待機者一覧と同形式）

seated（着席中）:
- 卓 / 席が分かる場合は assignedTableId / assignedSeatKey をもとに表示

busted（退席済み）:
- 退席済みであること
- bustedAt がある場合は退席時刻または経過時間
```

メモ表示の方針は §12.4（暫定「メモあり」）に準じてよい。詳細レイアウトは ChangeSpec 側で確定する。

#### 12.8.4 カードタップ時の操作ダイアログ

`置きバケ一覧` の各カードをタップすると、その置きバケに対する **操作ダイアログ** を表示する。操作内容は `entryStatus` により分岐する。

##### registered（待機中）

対象:

```text
entryStatus == "registered"
billLinkStatus == "unlinked"
```

操作:

```text
- 席配置
- Addon
- 伝票紐付け
```

これは §12.6 / §12.7 の待機者一覧と同等の操作セットとする。実装は既存の待機者一覧の操作ダイアログを再利用してよい。

##### seated（着席中）

対象:

```text
entryStatus == "seated"
billLinkStatus == "unlinked"
```

操作:

```text
- Addon
- 伝票紐付け
```

`置きバケ一覧` 経由では **Bust を表示しない**。Bust は既存の卓席タップ導線（§14.2）に残す。

理由:

```text
- 「置きバケ一覧」は伝票紐付け漏れの解消と状態確認のための導線である
- 着席中の Bust は卓上の席操作として扱う方が自然である
```

##### busted（退席済み）

対象:

```text
entryStatus == "busted"
billLinkStatus == "unlinked"
```

操作:

```text
- 伝票紐付け
```

`busted` では以下を表示しない。

```text
- 席配置（退席済みのため不要）
- Addon（§16.7・§3356 に従い busted は不可）
- Bust（既に完了済み）
```

これは、**退席後かつトーナメント進行中に来店した置きバケ参加者** を、店舗端末から正規 `bills` へ接続できるようにするための主導線である。

#### 12.8.5 伝票紐付け処理

`置きバケ一覧` から起動する伝票紐付けは、既存の §14.2 伝票紐付けダイアログ・§14.3 `linkOkibakeTemporaryEntryToBill` をそのまま再利用する。

候補条件（来店中ユーザー絞り込み）は、待機者一覧・卓ページ経路と同じとする。

```text
linkedUserId あり:
- activeStay.isActive == true
- activeStay.billId が非空
- activeStay.billId に同一トーナメント（templateId）が未参加
- activeStay.userId == linkedUserId

linkedUserId なし:
- activeStay.isActive == true
- activeStay.billId が非空
- activeStay.billId に同一トーナメント（templateId）が未参加
```

接続後の `okibakeTemporaryEntries` / `seats` / `bills` 反映は §14.6〜§14.9 を正とする。`busted` の場合は §14.7 に従い `seats` 更新なし、§14.9 に従い bust 反映を行う。

接続成功で `billLinkStatus: "linked"` となり、`unlinked` のみを表示対象とする `置きバケ一覧` からは自然に消える。

#### 12.8.6 既存導線との関係

`置きバケ一覧` は、以下の既存導線を **置き換えない**。あくまで追加の導線として共存する。

```text
- 待機者一覧の置きバケカード（§12.6・§12.7）
- 卓ページの置きバケ参加者操作ダイアログ（§14.2）
- ユーザー来店・ログイン後の案内（§14.15）
```

待機・着席中の主導線は引き続き既存経路を優先する。`置きバケ一覧` は、特に `busted + unlinked` への到達経路と、状態をまたいだ一括確認のための補助導線として位置づける。

#### 12.8.7 Phase 4 / Phase 5 / Phase 8 との境界

`置きバケ一覧` は **Phase 4 補完** として扱う。Phase 5 / Phase 8 の領域とは目的・タイミングが異なるため、混ぜない。

```text
Phase 4 補完（本節）:
- トーナメント進行中の店舗端末操作に限定する
- registered / seated / busted の unlinked を対象とする
- 既存 linkOkibakeTemporaryEntryToBill を利用する
- 新規 bill 作成・pending_review 化は行わない

Phase 5:
- トーナメント終了後の pending_review 化（§15）
- 来店なし入金登録による linked 化（§15・§9.13）
- 要対応会計ページ（§15）

Phase 8:
- 次回来店時の link_prompt（§14.15）
- LIFF / LINE ログイン経路での案内
```

`置きバケ一覧` から `pending_review` を直接操作することはしない。`pending_review` は §15 の要対応会計ページから処理する。

#### 12.8.8 実装方針メモ（再利用）

具体ファイル・ウィジェット選定は ChangeSpec に委ねるが、**既存実装の再利用** を前提とする。

```text
- 待機中操作: 待機者一覧の置きバケ操作ダイアログ相当を再利用
- 着席中操作: 卓ページ着席済み置きバケ操作ダイアログ相当を再利用（Bust 非表示）
- 退席後操作: 既存の伝票紐付けダイアログを呼び出す薄い分岐のみ
- 伝票紐付け: 既存の OkibakeLinkBillDialog 相当 + linkOkibakeTemporaryEntryToBill
- 候補条件: 既存 helper（待機・着席で使っているもの）を共通利用
- 状態別の操作差分は entryStatus で判定する
- bills 側に busted 専用フィールドは追加しない
- functions/src への追加実装は原則不要
```

## 13. 席配置仕様

### 13.1 基本方針

通常参加者の席配置と、置きバケ一時参加者の席配置は、別経路で扱う。

理由は、既存の通常着席処理が `activeStays` と `billId` を前提としているためである。

### 13.2 置きバケ専用席配置

置きバケ一時参加者の席配置には、通常参加者向けの `assignSeatToPlayer` とは別に、置きバケ専用 Callable を用意する。

Callable 名は以下とする。

```text
assignOkibakeTemporaryEntryToSeat
```

この Callable は、`activeStays` や `billId` を前提にせず、`okibakeTemporaryEntries/{okibakeEntryId}` を正本として置きバケ一時参加者を席に配置する。

### 13.3 `assignOkibakeTemporaryEntryToSeat` の入力

`assignOkibakeTemporaryEntryToSeat` の入力は、初期仕様では以下とする。

```ts
type AssignOkibakeTemporaryEntryToSeatInput = {
  tournamentId: string;
  okibakeEntryId: string;
  tableId: string;
  seatKey: string;
  operationId: string;
};
```

#### `tournamentId`

対象トーナメントIDを指定する。

#### `okibakeEntryId`

席配置する置きバケ一時参加者の `okibakeEntryId` を指定する。

#### `tableId`

配置先の `tablesSeat/{tableId}` を指定する。

#### `seatKey`

配置先の席キーを指定する。

例:

```text
seat01
seat02
```

この `seatKey` をもとに、以下の seat フィールドを更新する。

```text
seatXXUserId
seatXXPokerName
seatXXOkibakeEntryId
```

#### `operationId`

二重実行防止・冪等性・操作履歴との紐付けのために使用する操作IDである。

同一操作の再送時には、同じ `operationId` を使用する。

`deviceId` は、既存の認証・店舗デバイス文脈から取得できる場合は input に含めない。

既存 Callable の設計上、店舗デバイスIDを input で受け取る必要がある場合は、既存方式に合わせる。

いずれの場合も、席配置時には `updatedByDeviceId` に席配置を行った店舗デバイスIDを記録する。

### 13.4 `assignOkibakeTemporaryEntryToSeat` の operationLog

`assignOkibakeTemporaryEntryToSeat` は、置きバケ席配置操作として operationLog に記録する。

operationLog action 名は候補名をベースに、既存 operationLog の命名規則に合わせて実装時に確定する。

初期候補は以下とする。

```text
assign_okibake_temporary_entry_to_seat
```

既存 action 名が camelCase 等で統一されている場合は、既存規則を優先する。

### 13.5 `assignOkibakeTemporaryEntryToSeat` の冪等性方針

`assignOkibakeTemporaryEntryToSeat` は、二重実行防止・冪等性を考慮する。

初期仕様では、`operationId` を用いて同一操作の再送を識別する。

同一 `operationId` の再送は、同じ結果を返す、または no-op 成功として扱う。

すでに対象の `okibakeEntryId` が、同じ `tableId` / `seatKey` に `entryStatus: "seated"` として配置済みの場合は、成功扱いとする。

一方で、すでに対象の `okibakeEntryId` が別の `tableId` / `seatKey` に `entryStatus: "seated"` として配置済みの場合は、エラーとする。

また、対象 seat がすでに通常ユーザーまたは別の置きバケ一時参加者で埋まっている場合も、エラーとする。

idempotency の保存先・requestHash・再送レスポンスは、既存の operationId / idempotency 実装規則に準拠する。

### 13.6 席配置時の状態遷移

置きバケ一時参加者を席に配置した場合、状態を以下のように更新する。

```ts
entryStatus: "registered"
→ entryStatus: "seated"
```

`billLinkStatus` は、席配置だけでは変更しない。

```ts
billLinkStatus: "unlinked"
```

のまま維持する。

### 13.7 既存 seats の前提

既存の通常参加者の席配置では、`assignSeatToPlayer` が対象ユーザーの `activeStays/{userId}` を取得し、`activeStay` 由来の `pokerName` と `billId` を確認したうえで、`tablesSeat/{tableId}.seats` に `seatXXUserId` / `seatXXPokerName` を書き込む。

既存の seats は、実装上、`seatXXUserId` が Firebase UID であることを前提に扱われている。

そのため、置きバケ一時参加者の `okibakeEntryId` を `seatXXUserId` に保存する設計は採用しない。

### 13.8 seats への格納方式

置きバケ一時参加者を席配置する場合、既存の `seatXXUserId` に `okibakeEntryId` は保存しない。

`seatXXUserId` は、実ユーザーの Firebase UID を保持するフィールドとして維持する。

置きバケ一時参加者の席配置では、置きバケ用の追加フィールドとして `seatXXOkibakeEntryId` を使用する。

`seatXXOccupantType` は採用しない。席種別は `seatXXUserId` と `seatXXOkibakeEntryId` の有無で判定する（§13.9）。

```ts
seatXXUserId: string | null;
seatXXPokerName: string | null;
seatXXOkibakeEntryId?: string | null;
```

通常ユーザー席の例:

```ts
{
  seat01UserId: "uid_123",
  seat01PokerName: "山田",
  seat01OkibakeEntryId: null
}
```

置きバケ席・実ユーザー未指定の例:

```ts
{
  seat01UserId: null,
  seat01PokerName: "オキバケA",
  seat01OkibakeEntryId: "okibakeEntryId_abc"
}
```

置きバケ席・実ユーザー指定済みの例:

```ts
{
  seat01UserId: null,
  seat01PokerName: "山田",
  seat01OkibakeEntryId: "okibakeEntryId_abc"
}
```

`seatXXPokerName` は表示用フィールドとして扱う。

置きバケ一時参加者の場合も、`seatXXPokerName` には卓表示用の表示名を保存する。

置きバケ一時参加者の `seatXXPokerName` は、以下で解決する。

```ts
seatXXPokerName = linkedUserPokerName ?? temporaryDisplayName;
```

ただし、`seatXXPokerName` はあくまで表示用スナップショットであり、席種別判定や正本ID判定には使用しない。

既存データには `seatXXOkibakeEntryId` が存在しない場合がある。読み取り側では §13.9 の判定ルールに従う。

### 13.9 席種別の判定

この節での「通常ユーザー席 / bill 未接続の置きバケ席 / bill 接続済みの置きバケ由来ユーザー席 / 空席」の判定は、席移動・全員リシートでの処理分岐の前提にもなる（詳細は §19）。

席の種別は、`seatXXUserId` と `seatXXOkibakeEntryId` の有無で判定する。

```text
seatXXUserId がある、かつ seatXXOkibakeEntryId がない
→ 通常ユーザー席

seatXXUserId がない、かつ seatXXOkibakeEntryId がある
→ bill 未接続の置きバケ席

seatXXUserId がある、かつ seatXXOkibakeEntryId がある
→ bill 接続済みの置きバケ由来ユーザー席

seatXXUserId も seatXXOkibakeEntryId もない
→ 空席
```

操作上の優先順位は以下とする。

```text
seatXXUserId がある
→ 通常ユーザー操作を優先

seatXXUserId がなく、seatXXOkibakeEntryId がある
→ 置きバケ専用操作

どちらもない
→ 空席
```

`seatXXOkibakeEntryId` は、接続後も置きバケ由来を追跡するために残す場合がある。

そのため、`seatXXOkibakeEntryId` があることだけを理由に、常に未接続置きバケ席として扱ってはならない。

`seatXXPokerName` だけで、着席中か空席かを判定してはならない。

理由は、`seatXXPokerName` は表示用スナップショットであり、正本IDではないためである。

空席判定では、少なくとも以下を確認する。

```ts
const isEmptySeat =
  !seatXXUserId &&
  !seatXXOkibakeEntryId;
```

### 13.10 `assignOkibakeTemporaryEntryToSeat` の読み込み対象

`assignOkibakeTemporaryEntryToSeat` では、最低限以下を読み込む。

```text
- scheduledTournaments/{tournamentId}
- scheduledTournaments/{tournamentId}/okibakeTemporaryEntries/{okibakeEntryId}
- scheduledTournaments/{tournamentId}/tablesSeat/{tableId}
- scheduledTournaments/{tournamentId}/views/main
```

対象の `okibakeTemporaryEntries/{okibakeEntryId}` は、`entryStatus: "registered"` である必要がある。

対象 seat は空席である必要がある。

空席判定では、`seatXXUserId` と `seatXXOkibakeEntryId` の両方が未設定であることを確認する。

### 13.11 `assignOkibakeTemporaryEntryToSeat` の書き込み対象

`assignOkibakeTemporaryEntryToSeat` では、最低限以下を更新する。

#### 1. `okibakeTemporaryEntries/{okibakeEntryId}`

```ts
{
  entryStatus: "seated",
  assignedTableId: tableId,
  assignedSeatKey: seatKey,
  seatedAt: now,
  updatedAt: now,
  updatedByDeviceId: deviceId
}
```

#### 2. `tablesSeat/{tableId}.seats`

```ts
{
  [`${seatKey}UserId`]: null,
  [`${seatKey}PokerName`]: linkedUserPokerName ?? temporaryDisplayName,
  [`${seatKey}OkibakeEntryId`]: okibakeEntryId
}
```

#### 3. `views/main`

```text
views/main.waitingCount -1
views/main.seatedCount 変更なし
views/main.entries 変更なし
views/main.playersIn 変更なし
```

`waitingCount` は、置きバケ一時参加者が待機者一覧から外れるため `-1` する。

`seatedCount` は、置きバケ関係では更新しない。

`entries` / `playersIn` は、置きバケ作成時に反映済みのため、席配置時には更新しない。

### 13.12 席配置時のカウンタ更新

置きバケ一時参加者を席配置する場合、§13.6 の状態遷移を行う。

このとき、待機者一覧から外れるため、以下を更新する。

```text
views/main.waitingCount -1
```

一方で、置きバケ関係では `seatedCount` は更新しない。

```text
views/main.seatedCount 変更なし
```

また、席配置時には `entries` / `playersIn` は更新しない。

理由は、置きバケ一時参加者作成時点で、すでに `entries +1` / `playersIn +1` を反映済みであるためである。

§13.11 に、`assignOkibakeTemporaryEntryToSeat` における書き込み内容を具体的に示す。

## 14. `bills` 接続仕様

### 14.1 基本方針

置きバケ一時参加者は、後から実ユーザーおよび `bills` に接続できるようにする。

正式な接続処理は、`linkOkibakeTemporaryEntryToBill` Callable（§14.3）に集約する。店舗デバイス等からの実行導線は §14.2 を参照する。

接続後の会計・精算・analytics は、通常の `bills` 側の処理に乗せる。

### 14.2 `bills` 接続の実行導線（UI は「伝票紐付け」）

データモデルおよびサーバ側では従来どおり `bill`／`bills`／`linkedBillId`／`billLinkStatus` を用いるが、**店舗スタッフ向け画面上ではこの操作を「伝票紐付け」と呼ぶ**（語彙対応・ボタン名は §11.9）。

初期仕様では、置きバケ一時参加者と bill の自動統合は採用しない。

置きバケ一時参加者作成時に `linkedUserId` が指定されている場合でも、対象ユーザーの伝票が作成されたからといって自動で接続してはならない。

`linkedUserId` がある置きバケ一時参加者は、接続候補として扱う。

実際の接続は、システム上は手動実行とする。

#### 伝票紐付け UI の導線（初期仕様）

伝票紐付けの UI 導線は、初期仕様では以下を想定する。

```text
1. 待機者一覧の置きバケカードからの伝票紐付け（§12.6）
2. 卓ページ上の置きバケ参加者操作ダイアログからの伝票紐付け
3. トーナメント操作タブの「置きバケ一覧」からの伝票紐付け（§12.8。Phase 4 補完）
4. ユーザー来店・ログイン後の案内（店舗設定 §14.15。`notice_only` は通知のみ、`link_prompt` は候補表示と手動の伝票紐付け導線）
```

追加で、待機者一覧から **Addon** を開始する経路および操作ダイアログの構成は **§12.7** とする。

`置きバケ一覧`（§12.8）は、特に **退席後かつトーナメント進行中**（`busted + unlinked`）の置きバケへ到達するための補助導線である。待機者一覧（§12.6）が `registered` のみ、卓ページ（本節以下「卓ページからの伝票紐付け」）が `seated` のみを対象とするため、それ以外の状態の置きバケへ店舗端末からアクセスできるようにする目的を持つ。

いずれの導線でも自動接続は行わず、最終的な接続処理は **`linkOkibakeTemporaryEntryToBill`** に集約する。

#### 卓ページからの伝票紐付け

卓ページで通常ユーザー席をタップした場合は、従来どおり通常ユーザー向けの操作ダイアログを表示する。

通常ユーザーの操作例:

```text
注文
Bust&リエントリー
Bust&退席
Addon
```

一方で、伝票未接続の置きバケ参加者をタップした場合は、置きバケ向けの操作ダイアログを表示する。

置きバケ参加者の操作例:

```text
Bust&退席
Addon
伝票紐付け
```

各処理と Callable の対応は以下である。

```text
Bust&退席
→ bustOkibakeTemporaryEntry

Addon
→ applyOkibakeAddon

伝票紐付け
→ linkOkibakeTemporaryEntryToBill
```

伝票未接続の置きバケ参加者には、**`注文` ボタンは表示しない**。

理由は以下である。

- 伝票未接続の置きバケ参加者は、注文を紐付ける伝票がまだ確定していないため。
- 注文は通常ユーザー・伝票接続済み参加者の操作として扱うため。

#### 来店・ログイン後の置きバケ候補ダイアログ

**店舗設定**により、ユーザー来店・ログイン直後に置きバケ案内を出すか／出さないか・どの強さかが変わる（**§14.15**。`storeMeta/config.okibake.loginPromptMode`）。

**`linkedUserId` が入店ユーザーと一致し、`billLinkStatus != "linked"` など §14.15.6 を満たす候補がある場合にのみ**、この導線（または通知のみ）が有効となる。**`linkedUserId` 未設定のオキバケA 等は案内対象外**。`pending_review` も対象に含める。

- `loginPromptMode == "notice_only"` … 候補があるとき **通知のみ**。この導線上では伝票紐付けボタンは出さない。  
- `loginPromptMode == "link_prompt"` … 候補を示し、下記のように **「あとで」「伝票紐付け」** など手動の伝票紐付けへの導線を出せる。

いずれの mode でも **自動接続は行わない**（§14.15.5）。

**`memo` が `null` でない場合は、確認材料として表示できる。**

表示例（`link_prompt` 相当。**具体的な Dialog / SnackBar / Card 等は ChangeSpec**）:

```text
タイトル:
置きバケ候補

このユーザーに紐づく置きバケがあります。

置きバケ:
オキバケB

メモ:
初来店予定

対象ユーザー:
山田

[あとで] [伝票紐付け]
```

`伝票紐付け` を押下した場合は、最終的に `linkOkibakeTemporaryEntryToBill` を呼び出す。

`あとで` を選択した場合は、接続せずに閉じる。

#### 伝票紐付けダイアログ

伝票紐付けダイアログの表示項目は必要最小限とする。

基本表示項目は以下である。

```text
- 置きバケ
- 対象ユーザー
```

加えて、**`memo` が `null` でない場合は、確認材料として表示できる**（誤紐付け防止のため。全文表示でよい）。

以下は基本表示しない。

```text
- 接続先伝票
- アドオン
- 状態
```

理由は以下である。

- 接続操作でスタッフが確認すべき主情報は、どの置きバケをどの対象ユーザーへ紐付けるかであるため。
- 接続先伝票は、対象ユーザーの現在の来店状態に紐づく未精算伝票を Cloud Functions 側で解決するため。
- アドオンや状態は詳細として有用だが、伝票紐付けダイアログに常時表示すると情報過多になるため。
- `memo` は任意入力の補助情報であり、存在する場合のみ確認材料として足せば足りるため、必須の基本項目には含めない。

##### 対象ユーザー未指定の場合

対象ユーザー未指定の置きバケでは、ダイアログ内で対象ユーザーを選択する。

表示例:

```text
タイトル:
伝票紐付け

置きバケ:
オキバケA

メモ:
田中さんの友人

対象ユーザー:
[ユーザーを選択]

[キャンセル] [紐付ける]
```

##### 対象ユーザー指定済みの場合

対象ユーザー指定済みの置きバケでは、そのユーザーを初期表示する。

表示例:

```text
タイトル:
伝票紐付け

置きバケ:
オキバケB

メモ:
20時頃来店予定

対象ユーザー:
山田
[変更]

[キャンセル] [紐付ける]
```

対象ユーザーは変更可能としてよい。

理由は以下である。

- 置きバケ登録時に対象ユーザーを誤指定している可能性があるため。
- 現場で正しいユーザーに修正してから伝票へ紐付けられるようにするため。

##### 接続先伝票の扱い

接続先伝票は、通常 UI では表示しない。

接続先伝票は、対象ユーザーの現在の来店状態に紐づく未精算伝票を Cloud Functions 側で解決する。

同一ユーザーに複数の未精算伝票が存在し得る仕様になった場合は、将来的に伝票選択または表示を検討する。

初期仕様では、対象ユーザーの現在の `activeStay` に紐づく未精算伝票が1つである前提で扱う。

誤紐付け防止のため、実行前には上記の伝票紐付けダイアログで **置きバケと対象ユーザー** を確認する。`memo` があればあわせて確認材料として表示できる。ボタンおよび説明文言は §11.9 に合わせ、`bill`／`bills` をユーザーに見せない。

### 14.3 `linkOkibakeTemporaryEntryToBill`

`linkOkibakeTemporaryEntryToBill` は、`okibakeTemporaryEntries/{okibakeEntryId}` と既存の未精算 bill を正式に接続する Callable である。

この Callable は、`bills` を新規作成するものではない。

既存の未精算・進行中 bill に、置きバケ一時参加者を接続する。

また、伝票紐付け時には **置きバケ参加費として `entryCount` / `entryFeeIncl` 等を `bills/{billId}/tournaments/{templateId}` に反映する**（既存 `recordTournamentAction` 相当の形式に寄せ、`linkOkibakeTemporaryEntryToBill` 内の専用反映処理とする。詳細は §14.10・§14.11）。

また、接続前に置きバケ側で発生した addon は、必要に応じて `bills` 側へ後追い反映する。bust は `okibakeTemporaryEntries` 側の状態として保持し、`bills` 側へ bust 専用フィールドとして後追い反映しない。

接続前の履歴は `okibakeTemporaryEntries` / `okibakeAddonRecords` に残す。

接続後の会計・通常操作は `bills` 側に残す。

両者は `linkedUserId` / `linkedBillId` / `okibakeEntryId` によって追跡可能にする。

### 14.4 `linkOkibakeTemporaryEntryToBill` の入力

入力は以下とする。

```ts
type LinkOkibakeTemporaryEntryToBillInput = {
  tournamentId: string;
  okibakeEntryId: string;
  userId: string;
  billId: string;
  operationId: string;
};
```

tournamentId

対象トーナメントID。

okibakeEntryId

接続する置きバケ一時参加者 ID。

userId

接続先の実ユーザー ID。

billId

接続先の未精算 bill ID。

operationId

二重実行防止・`operationLog` 紐付け用 ID。

`userId` と `billId` は input で受けるが、input を信用してそのまま接続してはならない。

Cloud Functions 側で、`activeStay` / `bill` / `okibakeTemporaryEntry` の整合を検証する。

### 14.5 接続できる bill の条件

初期仕様では、未精算・進行中の bill のみ接続可能とする。

対象 bill は、対象ユーザーの現在の `activeStay` に紐づく bill であり、会計・トーナメント記録の追加反映が可能な状態である必要がある。

精算済み、締め済み、または売上・analytics へ確定反映済みの bill への接続は、初期仕様では原則不可とする。

settled 済み bill への接続が必要なケースは、通常の接続処理では扱わず、別途手動補正・取消補正の対象とする。

Cloud Functions 側では、少なくとも以下を検証する。

```text
- 対象 okibakeTemporaryEntry が存在する
- okibakeTemporaryEntry がまだ bill 未接続である、または同一 operationId の再送である
- activeStays/{userId} が存在する
- activeStay.billId が input.billId と一致する
- bill が存在する
- bill の userId が input.userId と整合する
- bill が未精算・進行中である
- settled 済み bill ではない
```

### 14.6 接続時の `okibakeTemporaryEntries` 更新

`linkOkibakeTemporaryEntryToBill` では、対象の `okibakeTemporaryEntries/{okibakeEntryId}` に以下を保存する。

```ts
{
  linkedUserId: userId,
  linkedUserPokerName: resolvedPokerName,
  linkedBillId: billId,
  linkedAt: Cloud Functions 側で生成した現在時刻の Timestamp,
  billLinkStatus: "linked",
  updatedAt: Cloud Functions 側で生成した現在時刻の Timestamp,
  updatedByDeviceId: deviceId
}
```

`linkedUserPokerName` は、以下の優先順位で解決する。

1. `activeStays/{userId}.pokerName`
2. bill 側に保持されている pokerName / customerName 相当
3. それでも取れない場合はエラー

基本仕様としては、`activeStays/{userId}.pokerName` を `linkedUserPokerName` として保存する。

`linkedAt` は、置きバケ一時参加者を bill に接続した操作時点の Timestamp である。

文字列 `"now"` を保存するものではない。

`entryStatus` は変更しない。

理由は、`entryStatus` はトーナメント上の状態であり、`billLinkStatus` とは別軸であるためである。

`bills` 接続後も、`temporaryDisplayName` は変更しない。

### 14.7 `bills` 接続時の seats 更新

`linkOkibakeTemporaryEntryToBill` では、`entryStatus` に応じて seats 更新を分ける。

#### `entryStatus: "registered"`

```text
- seats 更新なし
- linked* 更新のみ
```

まだ席についていないため、更新対象の seat は存在しない。

待機者一覧では、`linkedUserPokerName` を優先表示する。

#### `entryStatus: "seated"`

`okibakeTemporaryEntries.assignedTableId` / `assignedSeatKey` をもとに、対象 seat を更新する。

接続前:

```text
{
  [`${seatKey}UserId`]: null,
  [`${seatKey}PokerName`]: temporaryDisplayName または linkedUserPokerName,
  [`${seatKey}OkibakeEntryId`]: okibakeEntryId
}
```

接続後:

```text
{
  [`${seatKey}UserId`]: linkedUserId,
  [`${seatKey}PokerName`]: linkedUserPokerName,
  [`${seatKey}OkibakeEntryId`]: okibakeEntryId
}
```

`seatXXOkibakeEntryId` は削除しない。

`seatXXUserId` は接続後の通常操作用 `userId` として使用する。

`seatXXOkibakeEntryId` は、置きバケ由来であることを追跡するための ID として保持する。

接続後の操作では、`seatXXUserId` がある場合は通常ユーザー操作を優先する。

ただし、`seatXXOkibakeEntryId` がある場合は、置きバケ由来であることも追跡可能にする。

#### `entryStatus: "busted"`

```text
- seats 更新なし
- linked* 更新のみ
- busted は okibakeTemporaryEntries 側の状態として扱う
- busted 専用情報は bills 側へ反映しない
```

すでに seat から除去済みであるため、`seats` は更新しない。

#### `entryStatus: "voided"`

`voided` の置きバケ一時参加者は、`bills` 接続不可とする。

理由は、`voided` が置きバケ登録自体の取消状態であるためである。

### 14.7.1 置きバケ由来 seat の整合性補正

Phase 4 以降、着席中の置きバケを伝票紐付けすると、同一 seat に以下の3フィールドが同時に存在する状態が発生する。

```text
seatXXUserId = linkedUserId
seatXXPokerName = linkedUserPokerName
seatXXOkibakeEntryId = okibakeEntryId
```

この状態は、元置きバケ由来の参加者が実ユーザーへ接続された状態を表す。

Flutter 表示上は `seatXXUserId` がある場合は通常ユーザー席を優先し、`seatXXOkibakeEntryId` は置きバケ由来の追跡用として扱う。

一方で、その後に Bust / Reentry / 全員再配置 / rollback などで seat を空ける場合は、`seatXXUserId` / `seatXXPokerName` だけでなく、`seatXXOkibakeEntryId` も必ず null にする。

seat を空ける処理では、以下の3フィールドを席単位で同時に空にする。

```text
seatXXUserId = null
seatXXPokerName = null
seatXXOkibakeEntryId = null
```

通常ユーザーを seat に割り当てる処理では、`seatXXUserId` だけでなく `seatXXOkibakeEntryId` も見て空席判定を行う。

`seatXXUserId` が null でも `seatXXOkibakeEntryId` が残っている seat は、整合性上は空席として扱ってはならない。この状態は不整合または未解消の置きバケ seat として扱い、通常着席処理では拒否する。

卓削除や卓の occupied 判定でも、`seatXXUserId` だけでなく `seatXXOkibakeEntryId` を占有判定に含める。

#### 補正対象

```text
1. bustAndExit / bustAndReentry
   - 通常 Bust / Reentry により seat を空ける際、seatXXOkibakeEntryId も null にする。

2. reseatAllPlayers
   - 全席初期化時、seatXXUserId / seatXXPokerName に加え seatXXOkibakeEntryId も null にする。

3. assignSeatToPlayer
   - 通常ユーザーの着席先判定で seatXXOkibakeEntryId も確認する。
   - seatXXOkibakeEntryId が残っている席を空席扱いしない。

4. removeTableFromTournament
   - 卓削除時の occupied 判定で seatXXOkibakeEntryId も確認する。

5. rollback 系
   - seat 解除を伴う rollback で seatXXOkibakeEntryId も null にする。
```

#### Flutter 表示判定

Flutter 側の seat 表示判定は、現行方針を維持する。

```text
userId あり + okibakeEntryId あり
→ 通常ユーザー席を優先

userId なし + okibakeEntryId あり
→ 置きバケ席
```

今回の ghost okibake 問題は Flutter 表示判定ではなく、Functions 側で `seatXXOkibakeEntryId` だけが残る不整合状態を作ることが原因である。

そのため、Flutter 側で `okibakeEntryId` を無視するような回避策は採用しない。

### 14.8 置きバケ addon の `bills` 反映

`bills` 接続時、`okibakeAddonRecords` のうち以下を満たす record を `bills` 側へ反映する。

```text
rolledBack == false
and
reflectedToBill == false
```

反映先は、通常 addon と同じ bill 側トーナメント記録とする。

```text
bills/{billId}/tournaments/{templateId}
```

概念上、以下を反映する。

```text
addonCount + 反映対象 addon record 数
lastAddonAt 更新
addonFeeIncl 等は既存 recordTournamentAction 相当の形式に合わせる
```

通常 addon Callable にそのまま流すのではなく、`linkOkibakeTemporaryEntryToBill` 内の専用反映処理として行う。

内部的には、既存 recordTournamentAction 相当の処理・形式に寄せる。

反映後、対象 record を以下のように更新する。

```ts
{
  reflectedToBill: true,
  reflectedToBillAt: Cloud Functions 側で生成した現在時刻の Timestamp,
  linkedBillId: billId
}
```

`rolledBack: true` の record は、過去に実施されたが rollback 済みの addon 実施記録であるため、`bills` 側へ反映しない。

### 14.9 置きバケ bust の扱い

`entryStatus == "busted"` の置きバケも `linkOkibakeTemporaryEntryToBill` の接続対象に含める。

ただし、bust はトーナメント側の状態として `okibakeTemporaryEntries.entryStatus` / `bustedAt` / `bustedTableId` / `bustedSeatKey` で保持し、`bills` 側へ bust 専用フィールドとして後追い反映しない。

`bills` 接続時に反映する会計情報は、entry と addon に限定する。

### 14.10 `linkOkibakeTemporaryEntryToBill` の実行順序

`linkOkibakeTemporaryEntryToBill` の基本的な実行順序は以下とする。

```text
1. 店舗デバイス権限を確認する
2. okibakeTemporaryEntries/{okibakeEntryId} を取得する
3. activeStay / bill を取得して接続条件を検証する
4. bill が未精算・進行中であることを確認する
5. okibakeTemporaryEntry が未接続、または同一 operationId 再送であることを確認する
6. linkedUserId / linkedUserPokerName / linkedBillId / linkedAt / billLinkStatus を更新する
7. entryStatus: seated の場合は seats を更新する
8. 置きバケ参加費として、bills/{billId}/tournaments/{templateId} に entry 相当を反映する（entryCount / entryFeeIncl 等。recordTournamentAction 相当の形式に寄せ、本 Callable 内の専用処理とする）
9. 有効かつ未反映の okibakeAddonRecords を bills 側へ反映する
10. 反映した addon record に reflectedToBill / reflectedToBillAt / linkedBillId を設定する
11. operationLog を記録する（rollback に必要な before / after および反映差分は §14.14 に従い payload に保存する）
```

### 14.11 `linkOkibakeTemporaryEntryToBill` の transaction 範囲

`linkOkibakeTemporaryEntryToBill` では、以下を基本的に同一 transaction 内で整合させる。

```text
- okibakeTemporaryEntries の linked* 更新
- entryStatus: seated の場合の seats 更新
- bills/{billId}/tournaments/{templateId} への entry（参加費）反映
- okibakeAddonRecords の reflectedToBill 更新
```

`bills` 側への entry / addon 反映は、既存 recordTournamentAction 相当の処理に寄せる。

ただし、通常 entry / addon Callable にそのまま流すのではなく、`linkOkibakeTemporaryEntryToBill` 内の専用反映処理として行う。bust は通常 bust Callable に流さず、bill 側への専用反映もしない。

既存実装の transaction / idempotency / recordTournamentAction の制約がある場合は、既存方式に準拠する。

### 14.12 `bills` 接続後の rollback / 補正

`bills` 接続後だからといって、すべての rollback を禁止するわけではない。

以下のように区別する。

```text
1. bills 接続後に通常ユーザーとして発生した addon / bust
   → 既存の通常ユーザー処理および既存 rollbackAction の undo 経路で許容する。

2. bills 接続前に置きバケとして発生し、bills 接続時に後追い反映された addon
   → 伝票接続自体は正しい場合、個別の undoAddon（1 件単位）等だけでは `bills` と `okibakeAddonRecords` の整合が取りきれないことがある。
   → 一方で、「誤った伝票へ紐付けた」事案を現場が検知した **会計前** の場合は、§14.14 の誤紐付け解除（専用 undo）により、誤った `bills` 側への後追い反映とオキ側の反映済みフラグをあわせて戻す。

3. bills 接続済みだから全 rollback 不可、とはしない。

4. 「接続そのもの」を戻す操作のうち、会計前の誤伝票紐付けについては §14.14 に従い、rollbackAction 体系と専用 undo service で提供する。
   これは置きバケ参加そのものの取消ではなく、誤った bill との接続および置きバケ由来の `bills` 側反映を戻す操作である。
   bill が settled の場合は伝票紐付け rollback の対象外とし、既存の post-settlement adjustment / collection / refund に乗せる。
```

接続後の seat は `seatXXUserId` を持つため、接続後に新しく発生した通常 addon / bust は、通常ユーザーとして既存処理の対象とする。

伝票とオキ側の状態が食い違ったままになるのを避けるため、**単体のアドオン undo だけで済ませるべきではないケースは §14.14 を前提に整理する**。

### 14.13 `recordTournamentAction` との関係

置きバケ由来の addon / bust を `bills` に反映する場合、`linkOkibakeTemporaryEntryToBill` は内部的に既存 `recordTournamentAction` 相当の処理・出力形式に寄せる。

細部（共通関数への委譲有無、`views/main.entries` との二重反映防止との境界、`bills/{billId}` 側のロックや idempotency の持ち方など）は実装フェーズで詰めるが、機能要件として bills 側トーナメント記録への統合は本章に従う。

`recordTournamentAction` 相当処理の helper 化、`idempotencyKey`、`requestHash`、書き込み粒度などの細目は、実装時に既存の通常 addon / bust 実装および `recordTournamentAction` の規則へ準拠する。

### 14.14 置きバケ伝票紐付け後の誤紐付け解除（会計前・rollback）

#### 14.14.1 位置づけ（検知）

誤紐付けの検知は、**システムが自動で行うものではない**。

現場スタッフが **`オキバケA`** のように置きバケ登録時に対象ユーザーを指定しておらず、後から伝票紐付けで **誤った来店ユーザー** の伝票へ接続してしまった、などにより誤りに気づいた場合を想定する（対象ユーザー指定済みでも、理論上は別 bill への誤操作があり得る）。

現場スタッフが誤りに気づいたとき、**紐付け先 bill が会計前であれば**、本節に従う **置きバケ伝票紐付け専用 rollback** により、紐付け前の **`okibakeTemporaryEntries` および伝票側の自然的な状態**へ戻せるようにする。

#### 14.14.2 「戻す」の意味

伝票紐付け後の誤紐付け解除は、**置きバケ参加そのものの取消ではない**。置きバケと **誤った bill** の接続を外し、接続により **誤って載った伝票側のトーナメント entry / addon 等の反映のみ** を取り除く。bust は bill 側へ専用反映しないため、取り除き対象に含めない。

**解除後に維持・戻すべき状態の要点**

```text
置きバケ側:
- temporaryDisplayName（オキバケA など）として登録された okibakeTemporaryEntry は残る
- billLinkStatus は linked から unlinked に戻す
- linkedBillId は null に戻す
- linkedAt は null に戻す（§14.6 における「未接続」相当の状態へ）
- entryStatus は原則変更しない（registered / seated / busted と linked の組み合わせを、その entryStatus と unlinked へ）

来店済みユーザー側（誤って紐付けた伝票側）:
- 来店により作成された通常 bills は削除しない。activeStay も維持する
- 通常注文や、当該トーナメント以外の伝票情報は削除しない
- 誤って反映された置きバケ由来の tournament 記録（entry / addon 等）、および seated で実ユーザーへの seat 書き換えだけを伝票紐付け前の状態に戻す。bust は bill 側へ専用反映しないため戻し対象に含めない
```

#### 14.14.3 rollbackAction 体系に載せる方針

置きバケ伝票紐付け解除は **rollback 系操作**として扱い、以下を **確定**とする。

```text
- 既存 rollbackAction Callable に、識別用の operationName / action enum を追加し、置きバケ伝票紐付け解除専用の undo service から復元処理を実行する。
- 既存の undoRegisterForTournament / undoRegisterParticipants は、通常参加そのものを取り消す責務のため、この解除では単純流用しない。
- 既存の undoAddon / undoBustAndExit 等も、置きバケ伝票紐付けの「接続ごと」の巻き戻しとしてそのまま当てはめない（カウンタ・件数・金額の差が複合するため）。
```

**理由（要約）**  
通常参加 rollback は `usersList` / waiting / views/main / bill tournament を「参加が無かったこと」へ近づける。一方本操作は **置きバケ参加者は維持**し **`bills` との誤接続と置き由来の反映だけ** を戻す。責務が異なるため **専用 undo service を追加する**。

#### 14.14.4 専用 undo service（実装時の名前候補）

実装時に `functions/.../logs/services/` 配下などへ、次を候補とする **専用 undo service** を追加する。

```text
undoOkibakeTemporaryEntryBillLink （推奨候補）
または短縮して undoOkibakeBillLink
```

ファイル名・export 名は実装フェーズで確定してよい。本 service は **`rollbackAction` から呼び出される**ことを前提とする。

#### 14.14.5 operationName / action enum の候補

既存 `rollbackAction` は `operationLogs.operationName` を主として分岐するため、伝票紐付け operation 側も一覧・rollback と整合した識別子を持つ。

```text
operationName の候補: 「置きバケ伝票紐付け」
action enum の候補: okibake_bill_link （rollbackAction の入力側。実装での正確な文字列・クォートはコード生成時に確定）
```

実装では **`rollbackAction.ts` の分岐、`rollbackActionSchema` の action enum、`getActionLogs.ts` の `OPERATION_NAME_TO_ACTION` を整合**させる。

#### 14.14.6 解除可能な bill.status（確定）

| bill.status | 解除可否 | 理由 |
|-------------|----------|------|
| `open` | 可能 | 会計前であり、bill 側 tournament 記録を戻しやすい |
| `in_progress` | 可能 | 既存の `recordTournamentAction` が許可する範囲（未精算の進行中伝票）と整合する |
| `settling` | 不可 | 会計処理中であり、途中変更は整合性が危険 |
| `settled` | 不可 | 会計完了・売上反映済みのため、この rollback では扱わない |

確定文言:

```text
置きバケ伝票紐付け解除は、紐付け先 bill.status が open または in_progress の場合のみ許可する。
settling は会計処理中として解除を拒否する。
settled の場合は伝票紐付け rollback ではなく、既存の post-settlement adjustment / collection / refund フローで補正する。
```

#### 14.14.7 settled 後の扱い（確定）

```text
bill が settled の場合、okibakeTemporaryEntry を unlinked に直接戻したり、bill 側 tournament 記録を論理削除・直接ゼロ戻ししたりしない。
金額誤りや返金・追加徴収が必要な場合は、既存の post-settlement adjustment / collection / refund に載せる。
```

**理由**: settled は会計完了・売上・analytics と整合済みとなるため、単純 unlink では不整合となる。

#### 14.14.8 `okibakeTemporaryEntries` の戻し方（確定）

**基本**

```text
billLinkStatus: linked → unlinked
linkedBillId: 値あり → null
linkedAt: Timestamp → null
```

**`entryStatus` は原則維持**する。状態の組み合わせイメージ:

```text
registered / linked → registered / unlinked
seated / linked → seated / unlinked
busted / linked → busted / unlinked
```

`entryStatus` はトーナメント上の参加者状態、`billLinkStatus` は伝票接続状態であり、誤紐付け解除は **後者と誤伝票側の投影だけ** を戻す。

#### 14.14.9 `linkedUserId` / `linkedUserPokerName` の戻し方（確定）

**紐付け前に既にユーザーが確定済みだった場合（例: §9.2）**

```text
紐付け前から linkedUserId / linkedUserPokerName が非 null であったときは、解除後も両者は維持する。
linkedBillId / linkedAt / billLinkStatus のみ、未接続状態へ戻す。
```

**紐付け時に初めて対象ユーザー（実 UID）が確定した場合（例: オキバケA と誤伝票ユーザー）**

```text
紐付け直前が linkedUserId / linkedUserPokerName が null であったときは、解除時に両者も null に戻す。
```

この A/B の判定には **紐付け操作直前のスナップショット**が必要であり、§14.14.13 の **`operationLog.payload.before`** に保存する。

#### 14.14.10 誤った `bills` 側から外す対象（確定）

次を **限定**して取り除く。**通常 bill／activeStay／通常注文・他 tournament を削除しない。**

```text
- 置きバケ由来の entry（参加費）反映として載せた entryCount / entryFeeIncl などの差分
- 置きバケ由来の addon 後追い反映
- 伝票紐付け処理にともない、bills/{billId}/tournaments/{templateId} へ載せたその他会計上の投影（実装が追加する項目があれば同様）
```

伝票紐付け時に **置きバケ参加費として entryCount / entryFeeIncl も反映する**（§14.3・§14.10）。解除時は **その投影分だけ** を戻す。

#### 14.14.11 addon / bust の戻し方

**Addon**  
伝票紐付けにより `reflectedToBill: false → true` となった記録がある場合の解除では、以下をセットで満たす。

```text
- bills/{billId}/tournaments/{templateId} の addonCount / addonFeeIncl / lastAddonAt 等を、置きバケ由来の反映分だけ差し引いて整合させる。
- 対応する okibakeAddonRecords 要素について reflectedToBill / reflectedToBillAt / linkedBillId を「未伝票反映」状態に戻せるようにする。
```

単体 undoAddon を繰り返すだけでは数量・金額の整合が取れないことがあるため、**専用 undo service 内で一貫した差分復元とする**。

#### 14.14.12 `seats` の戻し方（`entryStatus: seated`）

伝票紐付けにより **実ユーザーの UID／表示名へ席を置き換えた**場合、解除では **伝票で差し込んだ実ユーザー情報を除去**し、**紐付け前の置きバケ由来の seat 表示**へ戻す（§14.7 の「接続前」に準拠。**`seatXXOkibakeEntryId` は維持**。**座席自体と entryStatus は維持**）。

実装上、紐付け前の seats 状態は **`operationLog.payload.seatBefore`**（または同趣旨のフィールド）に保存することを要件とする。フィールド構成は実装時に seat モデルへ合わせて確定する。

#### 14.14.13 紐付け時の `operationLog.payload` に必須とする情報

`linkOkibakeTemporaryEntryToBill` が成功するとき、その **同一 operationId の operationLog** に rollback に必要な情報を **`payload`** に保持する。**before / after** と、`bills` への投影差分の要約を含める。**型名と細目プロパティ名は実装時に確定**してよいが、論理的に次を満たすこと。

概念例（フィールド構成の例示）:

```ts
payload: {
  okibakeEntryId: string;
  tournamentId: string;
  linkedBillId: string;

  before: {
    billLinkStatus: "unlinked" | "linked" | "pending_review";
    linkedBillId: string | null;
    linkedUserId: string | null;
    linkedUserPokerName: string | null;
    linkedAt: Timestamp | null;
  };

  after: {
    billLinkStatus: "linked";
    linkedBillId: string;
    linkedUserId: string | null;
    linkedUserPokerName: string | null;
    linkedAt: Timestamp;
  };

  reflectedEntry: {
    reflected: boolean;
    templateId: string;
    entryCountDelta: number;
    entryFeeInclDelta: number;
  };

  reflectedAddonRecordIds: string[];

  seatBefore?: {
    tableId: string;
    seatKey: string;
    // 実装時の seat モデルに合わせて追記してよい
  } | null;
}
```

**undo** は、この payload と **現在ドキュメント**を照らし、`operationId` 冪等等を満たしつつ §14.14.8〜14.14.12 の状態へ戻す。

### 14.15 店舗端末入店時の置きバケ案内挙動（店舗設定）

来店ユーザーがログインした直後に、そのユーザーに紐付く置きバケ候補がある場合の **案内挙動**は、固定仕様ではなく **店舗ごとの設定**で切り替える。

#### 14.15.1 保存場所と形

Firestore の単一ドキュメント **`storeMeta/config`** に、既存の `features` / `billing` / `tournament` 等と同様、**並列のオブジェクトとして** `okibake` を追加する。**サブコレクション `storeMeta/config/okibake` のような別ドキュメント分割はしない。**

```text
正: storeMeta/config.okibake.loginPromptMode
避ける: storeMeta/config を okibake 用に分割した別ドキュメントパスへの退避（単一 config ドキュメント方針を崩さない）
```

概念的な保存例:

```ts
storeMeta/config
{
  // ... existing fields ...
  okibake: {
    loginPromptMode: "notice_only"
  }
}
```

現行構造により、`features` / `billing` / `tournament` と同並びで **オブジェクトひとつ**として `okibake` を増やす。

#### 14.15.2 選択肢と永続化

許容値の **一覧自体**は Firestore に保存しない。**選択肢・デフォルトはコード上の型・バリデーションとして持ち**、`storeMeta/config` には **現在選択されている値のみ** を保存する。

```ts
type OkibakeLoginPromptMode = "none" | "notice_only" | "link_prompt";

interface StoreConfig {
  okibake?: {
    loginPromptMode?: OkibakeLoginPromptMode;
  };
}
```

実際の `StoreConfig` 定義名・ファイル配置は実装時に決めてよい。

#### 14.15.3 各値の意味

| 値 | 意味 |
|----|------|
| `none` | 店舗端末での入店処理後に置きバケ案内を出さない。 |
| `notice_only` | 店舗端末での入店処理後に **候補がある場合のみ** 通知する。**伝票紐付け操作はこの mode では出さない**。 |
| `link_prompt` | 店舗端末での入店処理後に候補を示し、**手動の伝票紐付けへ進める導線**を出す。自動接続はしない（§14.15.5）。 |

文言・ウィジェットの具体は ChangeSpec とする。

#### 14.15.4 デフォルトとフォールバック

**デフォルトは `notice_only`**。フィールド欠損または不正値の場合は読み込み時に **`notice_only` にフォールバック**する。

**理由（要約）**: `none` は気づきにくい。`link_prompt` はログイン直後の誘導が強めになりうる。`notice_only` は両者の間を取る。

#### 14.15.5 自動接続は行わない

`none` / `notice_only` / `link_prompt` のいずれでも **入店処理をトリガとした自動接続は行わない**。`link_prompt` でも、入店処理が自動で `billLinkStatus` を `linked` に更新しない。

ログイン後に **来店中ユーザーの通常伝票**へ置きバケを接続させるときは、`linkOkibakeTemporaryEntryToBill` を **スタッフが手動実行**する（§14.2・§14.3）。本節の「自動接続しない」は、このログイン〜来店伝票との接続に限定する。**`billLinkStatus` を `linked` とする経路すべてがここで列挙されるわけではない**（例: §15 の来店なし入金など）。

#### 14.15.6 入店時案内の候補検索条件

候補は次をすべて満たす `okibakeTemporaryEntries` に限定する。

```text
- 当該店舗運用上の対象 tournament に属する置きバケ（同一 tournamentId 等。tournament の絞り込みは既存入店・状態取得実装に合わせ ChangeSpec で定める。）
かつ linkedUserId == ログインユーザー ID
かつ billLinkStatus != "linked"
かつ entryStatus != "voided"
```

**`linkedUserId` 未設定（null）の置きバケは案内対象外**。**`temporaryDisplayName`・`memo` による自動照合はしない**。
対象には `billLinkStatus == "unlinked"` と `billLinkStatus == "pending_review"` を含める。

#### 14.15.7 mode 別の表示方針（UI 細部は ChangeSpec）

- **`none`**: 店舗端末での入店処理後に置きバケ案内を出さない。
- **`notice_only`**: 候補がある場合 **通知のみ**（文言イメージ「このユーザーには未接続の置きバケがあります。要対応会計ページを確認してください。」）。**伝票紐付けボタンは付けない**。
- **`link_prompt`**: 候補を示し、既存の手動伝票紐付け導線へ進める（文言・ウィジェット細部は ChangeSpec）。

#### 14.15.8 設定 UI と初期実装

初期実装では **`storeMeta/config.okibake.loginPromptMode` を読み、アプリ側で挙動を切り替える**。

店舗向け **`loginPromptMode` 変更 UI** は **初期実装で必須としない**。Firestore コンソールまたは後続の ChangeSpec で足してよい。

#### 14.15.9 Flutter（店舗端末）と Cloud Functions の責務

```text
Flutter（店舗端末）:
- storeMeta/config.okibake.loginPromptMode を読み、入店処理後の案内の有無・種別を決める。

Cloud Functions:
- 必要なとき候補検索を用意する場合、linkedUserId / billLinkStatus / entryStatus 等を検証した上で結果を返す。
- linkOkibakeTemporaryEntryToBill は既存の手動・安全検証を維持する。
- loginPromptMode を理由にバリデーションを緩めたり自動接続を許可したりしない。
```

## 15. 未接続・未会計確認（`pending_review`）および来店なし入金登録

### 15.1 `pending_review` の状態定義

`pending_review` は、**トーナメント終了時点で、置きバケ一時参加者が伝票未接続のまま残っているため、店舗側が対応確認すべき状態**である。

```ts
billLinkStatus: "pending_review"
```

正本データは **`okibakeTemporaryEntries`** とする。本状態は、`bills` 親ドキュメントの `status` / `closeSummary` / `postSettlementState` と同一モデルには載せない。

`pending_review` は本章の「要対応の会計」領域で扱うことを基本としつつ、§14.15 に従い店舗端末の入店時通知候補には含めることができる。
#### `pending_review` が意味するもの

```text
- 伝票未接続である
- 店舗側の対応確認対象である
- 要対応の会計ページで既存 UI を再利用して表示・処理する対象になり得る
- 後続で「来店時の伝票紐付け」または「来店なし入金登録」などを判断するための状態である
```

#### `pending_review` が意味しないもの

```text
- 会計済みではない
- 入金済みではない
- 売上反映済みではない（analytics 済みでもない）
- 伝票作成済みではない
- 登録取消（voided）ではない
```

`pending_review` へ遷移しても **`entryStatus` は変更しない**。

例として、以下の組み合わせは許容される。

```text
entryStatus: registered かつ billLinkStatus: pending_review
entryStatus: busted     かつ billLinkStatus: pending_review
```

（`linked`／既に別経路で `bills` 接続済みの参加者は、`pending_review` の対象外とする）

### 15.2 `pending_review` 化のタイミング

初期仕様では、**トーナメント終了時に** `pending_review` 化する。閉店処理のみをトリガとする記述ではない。

```text
通常終了:
endTournament 完了時に、対象者を確認し pending_review 化する

強制終了:
force_ended 化されるタイミングにおいても、同様に対象者を確認し pending_review 化する
```

### 15.3 `pending_review` 化の対象条件と対象外

#### 対象（すべてを満たす置きバケ一時参加者）

```text
entryStatus != "voided"
かつ
billLinkStatus == "unlinked"
かつ
linkedUserId が設定済み（非 null）
```

#### 対象外

```text
entryStatus == "voided"
billLinkStatus == "linked"
billLinkStatus == "pending_review"
linkedUserId 未設定（null）
```

### 15.4 対象ユーザー紐付け必須とトーナメント終了前チェック

`pending_review` 化には **対象ユーザー紐付け（`linkedUserId` が非 null）を必須**とする。そのため **`pending_review` 状態で要対応の会計ページに載せる置きバケは、ユーザー名が表示できる紐付け済みのみ** とする。

トーナメント終了処理を完了させる前に、以下を検出する。

```text
entryStatus != "voided"
かつ
billLinkStatus == "unlinked"
かつ
linkedUserId 未設定
```

**該当する置きバケが 1 件でもある場合、終了処理を完了させない。**

このチェックは、**通常の `endTournament` に限らず、閉店処理等で対象トーナメントが `force_ended` になる経路にも適用する。**

店舗向けメッセージ例:

```text
未接続の置きバケがあります。
トーナメントを終了する前に、対象ユーザーを指定してください。
```

#### 15.4.1 Phase 5-A' 補正（対象ユーザー設定の制約）

Phase 5 初期実装では、対象ユーザー設定は「未設定の置きバケに初回設定する操作」に限定する。

```text
linkedUserId 未設定:
対象ユーザー設定を許可

linkedUserId 設定済み:
対象ユーザー設定/変更アクションを表示しない
Functions 側でも変更を拒否する
```

対象ユーザー変更・誤設定修正・誤紐付け修正は Phase 7 rollback / undo で扱う。

#### 15.4.2 Phase 5-A' 補正（置きバケ同士の linkedUserId 重複防止）

同一 tournament 内では、他の `okibakeTemporaryEntry` で既に使用中の `linkedUserId` を、別の置きバケへ再設定してはならない。

```text
重複判定対象:
entryStatus != voided
かつ billLinkStatus in [unlinked, pending_review, linked]
```

適用対象:

```text
createOkibakeTemporaryEntry
updateOkibakeTemporaryEntryLinkedUser
Flutter の対象ユーザー候補 picker
```

本補正は「置きバケ同士の linkedUserId 重複防止」であり、Phase 6 の通常参加重複防止とは別に扱う。

### 15.5 終了時のユーザー指定の前提（未入店ユーザーを主とする）

トーナメント終了時の「未接続置きバケ」の対応では、対象ユーザーは **基本的に未入店ユーザーから選択する**前提とする。

```text
未入店ユーザー:
現在 activeStay を持たず、現在の運用での「使用中の伝票」と紐付いていないユーザー
```

**入店済みで現行の未精算伝票が解決できるユーザーは、終了処理専用のユーザーピッカの主対象とはしない。** そのようなユーザーは、通常の伝票紐付け経路での接続が主となる。UI のコンポーネント細部・検索クエリ仕様は未確定とし、**業務前提として本节に留める**。

### 15.6 要対応の会計ページでの扱い

`pending_review` の表示先は **既存の「要対応の会計」ページ（メニュー上の集合）を前提**とする。

初期実装では、置きバケ専用カード・置きバケ専用レイアウトを新規作成しない。表示文言・カード形状・一覧レイアウトは既存 UI に合わせる。

```text
正本:
okibakeTemporaryEntries（billLinkStatus: pending_review）

収集条件:
既存 bills の status / closeSummary / postSettlementState に依存しない

UI:
同一「要対応の会計」画面内で、既存のカード/行/一覧 UI を再利用して表示する

内部処理:
見た目は既存 UI を再利用するが、内部データソースは okibakeTemporaryEntries の pending_review とし、操作時は okibake 用処理へ分岐する
```

`pending_review` であることは業務的に重要だが、置きバケ由来であることを主表示で強調することは初期実装の必須要件としない。

### 15.7 来店なし入金登録（概要）

`pending_review` の置きバケについて、ユーザーが来店しなくとも、店舗外で支払を受領済みとして **入金済み処理**できる。

```text
pending_review（bill は未作成）
→ 店舗が「来店なし入金登録」を実行
→ bills/{billId} に来店なし置きバケ精算 bill を作成
→ 業務上は即精算済み（settled）
→ billsOnSettle / analytics 経由で売上反映
→ okibakeTemporaryEntries を billLinkStatus: linked にする
```

**`pending_review` となった時点では `bills` は作成しない。** 専用 bill は **「来店なし入金登録」実行時のみ**作成する。

`pending_review` を閉店時に自動で未会計 bill 化する案は、Phase 5 初期実装では採用しない。閉店時の自動 bill 化は、`closeStoreTerminal` の責務拡張、activeStay なし bill、businessDate、closeSummary / closeSnapshot、analytics 整合を別途整理したうえで中期検討とする。

経路は **`linkOkibakeTemporaryEntryToBill`（来店後の伝票紐付け）とは別 Callable** とし、名前・入力・エラーキーは実装フェーズで既存規則に合わせて決める。

### 15.8 来店なし置きバケ精算 bill（`bills` コレクション）

来店なし置きバケ精算 bill は **`bills/{billId}`** に作成する。専用コレクションは使わない。

理由:

```text
- billsOnSettle と既存 analytics 集計への乗車
- 売上処理を通常 bills と同一仕組みに寄せる
```

識別フィールドを親に保持する。

```ts
billType: "okibake_remote_payment";
sourceOkibakeEntryId: string;
sourceTournamentId: string;
```

`visitLinked` のような追加フィールドは不要。

### 15.9 `activeStay`

来店なし置きバケ精算では **`activeStays/{userId}` を作成しない**。

```text
通常 bill（来店）:
来店ログイン → activeStay → bills

来店なし置きバケ精算:
pending_review → 来店なし入金登録 → bills（activeStay は作らない）
```

### 15.10 `businessDate`

来店なし置きバケ精算 bill の **`businessDate` は、`scheduledTournaments/{sourceTournamentId}.businessDate` を使用する。**

理由:

```text
bill.businessDate は売上・analytics の帰属日キーであり、当該トーナメント売上として扱うため
```

**実際の入金日・登録時刻は `businessDate` に載せず、`remotePayment.paidAt` / `remotePayment.recordedAt` で保持する。**

### 15.11 `remotePayment`（監査・表示）

bill 親に `remotePayment` を保持する。

```ts
remotePayment: {
  expectedAmountIncl: number; // entry + addon から算出される本来金額
  amountIncl: number;         // 入金済みとして登録する金額＝売上反映の基準（§15.13 との整合あり）
  method: "cash" | "electronic_money";
  paidAt: Timestamp;
  recordedAt: Timestamp;
  recordedBy: string;
  memo: string | null;
}
```

初期仕様の `method` は **`cash` / `electronic_money` のみ** とする。

店舗向けラベル例:

```text
現金 → cash
電子マネー・キャッシュレス（PayPay 等を含む）→ electronic_money
```

`bank_transfer` / `other` は初期仕様では採用しない。

`expectedAmountIncl` と `amountIncl` が異なる場合は **`memo` を必須** とする。**差額自体はエラーとしない**。差額を discount / adjustment として構造化する要件はない（メモで理由を残す）。

### 15.12 `meta.paymentMethodsByAmount`（billsOnSettle / analytics 用）

来店なし置きバケ精算では **初期仕様として `bills/{billId}/payments` サブコレクションを作成しない**。現行加盟店の通常会計でも `/payments` を書く経路に依拠しない前提とし、`meta.paymentMethodsByAmount` を使う。

```text
remotePayment:
監査および店舗向け説明の正本

meta.paymentMethodsByAmount:
calculatePaymentTotals / billsOnSettle / analytics が参照する親フィールド経路への入力
```

**選択された method のキーだけ**を保存し、もう一方を `0` で持つ必要はない。

```ts
// 現金の例
meta: {
  paymentMethodsByAmount: { cash: amountIncl },
};

// electronic_money の例
meta: {
  paymentMethodsByAmount: { electronic_money: amountIncl },
};
```

**`/payments` と `meta.paymentMethodsByAmount` を同じ bill に併記しない**。既存 `calculatePaymentTotals` は `/payments` 優先のため二重定義・不整合の原因となる。

### 15.13 `bills/{billId}/tournaments/{templateId}` と金額

`tournaments` サブコレクション側の entry / addon 金額は **「本来発生した置きバケ参加内容の記録」** とする。

```text
- remotePayment.amountIncl と数値完全一致を必須としない
- 不一致でもシステムエラーにしない
- 不一致理由は remotePayment.memo に残す（§15.11）
```

### 15.14 実装上のフェーズ（`open` 作成後に `settled`）

業務上は即精算だが、`billsOnSettle` は **`onDocumentUpdated` で「非 settled → settled」の遷移**を検知するため、**同一ドキュメントの初回書き込みだけで `status: settled` としない**。

```text
1. bills/{billId} を status: "open" で作成する
2. 必要な tournaments / meta.paymentMethodsByAmount / remotePayment / 初期 skeleton（§15.15 と整合）を書き込む
3. 別コミットで status: "settled" に update する（あわせて §15.16 の ops）
4. billsOnSettle が遷移を検知して親スナップショット更新・analytics enqueue
```

### 15.15 初期作成時の親イメージ（`open`）

通常 bill 作成時の親 skeleton（`createBillWithActiveStay` と同種の構造）に寄せたうえで、識別子と `remotePayment` など来店なし入金用の情報を付与する。**以下は論理構造であり、フィールド完全一致を実装に強制しない。**

（`buildInitial*` は Cloud Functions／parentSummary の意味に合わせ実装側で適用）

```text
billId（docId と同値の慣例）
businessDate（トーナメント businessDate）
status: open

billType: okibake_remote_payment
sourceOkibakeEntryId / sourceTournamentId

party: { userId: linkedUserId, pokerName: linkedUserPokerName }
place: { table: null, seat: null }

ops / draftAccountingInput / settlementSnapshot / currentSummary /
postSettlementState / reopenSummary / closeSummary （各 buildInitial〜）

meta: {
  schemaVersion: "1.3",
  contentHash: null,
  paymentMethodsByAmount: { [method]: amountIncl } // method は cash または electronic_money
}

remotePayment: { … §15.11 … }

createdAt / updatedAt: serverTimestamp
```

### 15.16 `settled` update 時の `ops`

`billsOnSettle` のガード（`ops.accountingStartedAt` または `ops.accountingCompletedAt` が存在すること）を満たすため、`settled` へ更新するとき最低限以下をセットする。

```text
status: settled
ops.accountingStartedAt / ops.accountingStartedBy
ops.accountingCompletedAt / ops.accountingCompletedBy（同一処理内で同時刻でもよい）

accountingStartedBy / accountingCompletedBy には recordedBy（操作スタッフ）を用いてよい
updatedAt: serverTimestamp
```

### 15.17 `okibakeTemporaryEntry` を `linked` にする順序

`okibakeTemporaryEntries` を `billLinkStatus: linked` とする更新は **`bills` 側の `settled` 更新がコミット完了した後**に行う。

```text
bill open + 明細作成
→ bill settled update（および billsOnSettle の処理完了を待つ必要がある論点は実装時に Callable 順序で担保）
→ okibakeTemporaryEntry を更新

billLinkStatus: "linked";
linkedBillId: <作成した billId>;
```

通常来店後の伝票接続済みとも、置きバケ側では **区別せず bills 接続済みとして扱う**。`remoteSettlementStatus` は新設しない。

### 15.18 後日来店時の二重請求防止

```text
billLinkStatus == "linked" の置きバケは、後日来店時の「通常請求」「通常の伝票紐付け候補」に載せない
```

### 15.19 取消・補正・`reopen`・ログ

```text
- 来店なし置きバケ精算専用の rollback / 専用取消 Callable / 専用補正 Callable は初期仕様では作らない
- settled 後の追加徴収・返金が必要になった場合は、既存の post-settlement adjustment / collection / refund（現行 bills モデル）に乗せる
- reopenAccountedBill 型の reopen は、activeStay を作らない本経路と相性が悪いため、来店なし置きバケ精算 bill では原則対象に含めない（誤って reopen UI から選べないようにするなど、実装でガードする想定）
```

重要操作として、**実装フェーズでは `logOpsSuccess`／`operationLog` 等へ以下を残せることを前提**とする（既存ログ方針に合わせ、どちらを主とするかは実装で決める）。

```text
billId, okibakeEntryId, tournamentId, linkedUserId,
expectedAmountIncl, amountIncl, method, paidAt, recordedAt, recordedBy
```

### 15.20 `pending_review` 段階での会計済みフラグについて

置きバケドキュメント上で **`okibakeTemporaryEntries` だけを直接「会計済み」状態にしない**。会計済み・売上反映済みとする効果は、**必ず `bills` と `billLinkStatus: linked`** により表現する。

## 16. アドオン意思・実施記録・置きバケ席の addon / bust

### 16.0 Addon 上限回数（`addonLimitPerPlayer`）

トーナメントごとの **1人あたり Addon 実行上限回数**を表す。Firestore およびアプリ側の **フィールド実名は実装時に既存データモデルの命名との整合で最終確定する**が、本章では仕様名称として **`addonLimitPerPlayer`** と記す。

#### 値の意味

```text
0 = Addon 不可（許容実行回数 0）
1 = 1人あたり 1回まで Addon 可能
2 = 1人あたり 2回まで Addon 可能
…（非負整数）
```

#### 既存フィールド `isAddon` との関係

```text
isAddon … Addon 機能を有効にするかどうか
addonLimitPerPlayer … 機能有効時に、1人あたり何回 Addon 実行できる上限か
```

**実行時の正:**

```text
isAddon が false のトーナメントでは Addon はできない。
```

`isAddon: true` で **`addonLimitPerPlayer` が未設定**の場合は、**現行互換の既定として 1 回扱い**とする。新規データの既定は **`isAddon: true` なら `addonLimitPerPlayer = 1`（未設定や省略時）、`isAddon: false` なら `addonLimitPerPlayer = 0`（未設定時も 0 扱い）**とする。

`isAddon: false` 時に **`addonLimitPerPlayer` をどう格納するか**について、UI とデータ整合のため実装では次のいずれかに寄せる。

```text
案A:
isAddon false の場合、addonLimitPerPlayer は 0 としてテンプレート／scheduledTournament に保存する

案B:
isAddon false の場合も addonLimitPerPlayer を値として保持してよいが、実行時には 0 扱いとし Addon は実行しない
```

#### テンプレート → `scheduledTournament` へのコピー

テンプレート側に **`addonLimitPerPlayer`** を設定できる。トーナメント作成時に、選択されたテンプレートの **`addonLimitPerPlayer`** を、作成される **`scheduledTournaments/{tournamentId}`** へ **コピーする**。

```text
tournamentTemplate.addonLimitPerPlayer
↓ 作成時にコピー
scheduledTournament.addonLimitPerPlayer
```

**理由**: 作成後にテンプレートを変更しても **既に作成済みトーナメントの Addon 上限が勝手に変わらない**ようにするため。

実行時の Addon 判定では、 **`scheduledTournaments/{tournamentId}` にコピーされた `addonLimitPerPlayer`（および同ドキュメント上の snapshot などで確認される `isAddon`）を参照する**。**テンプレートを参照し直して上限を変える運用とはしない（原則）**。

#### 通常参加者と置きバケ参加者での共通適用

**両者とも、同一トーナメントの上限 `addonLimitPerPlayer` を用いる。置きバケ専用の別上限ルールにはしない。**

```text
通常参加者（bills 側 tournament 記録の addonCount）

addonCount >= addonLimitPerPlayer → Addon 不可
addonCount < addonLimitPerPlayer → isAddon が true でそのほか成立条件を満たすなら Addon 可能

置きバケ参加者（applyOkibakeAddon）

okibakeAddonCount >= addonLimitPerPlayer → Addon 不可
okibakeAddonCount < addonLimitPerPlayer → §16.7 のそのほか実行条件および isAddon: true を満たせば Addon 可能
```

`isAddon` が false、または効果上限が 0 と解釈される場合は、上記比較の前に拒否してよい。

#### 既存データの互換

**既存テンプレート**に `addonLimitPerPlayer` が無い場合:

```text
isAddon: true かつフィールド欠損 → addonLimitPerPlayer = 1 扱い
isAddon: false → Addon 不可。addonLimitPerPlayer = 0 扱い
```

**既存 `scheduledTournament`** に `addonLimitPerPlayer` が無い場合も同様とする。

### 16.1 `addonIntent` は採用する

`addonIntent` は、置きバケ連絡時点でユーザーから聞いたアドオン希望として採用する。

**店舗デバイス上での置きバケ登録（§11.6・§11.7）において、アドオン希望は必ずいずれかの選択肢を選ばせ、省略させない。** 結果として Callable 入力にも `addonIntent` を必ず渡すことを前提としてよい（§11.2）。

値は以下とする。

```ts
addonIntent: "unknown" | "yes" | "no";
```

意味の詳細は §10.10 を参照する。

### 16.2 アドオン希望と addon 実施記録は分ける

`addonIntent` は、アドオン希望・聞き取り情報である。

`okibakeAddonRecords` は、スタッフが実際に addon 処理を行った記録である。

`okibakeAddonCount` / `lastOkibakeAddonAt` は、`okibakeAddonRecords` をもとに親ドキュメント上に保持する表示・検索用サマリである。

この3つは役割を分けて扱う。

```text
addonIntent: "yes"
= ユーザーがアドオンを希望している

okibakeAddonRecords
= スタッフが実際に addon 処理を行った履歴

okibakeAddonCount
= rollback されていない有効 addon 回数のサマリ
```

`addonIntent` は Addon の **実行許可ゲートとはしない**。Addon 実行可否は `applyOkibakeAddon`／通常 addon のそれぞれの状態・権限チェックおよび §12.7 に従う。

```text
addonIntent は Addon 実行可否の判定には使用しない

Addon 実行後も addonIntent は自動変更しない

addonIntent が no または unknown の場合でも Addon 自体は可能とする（ただし §12.7 の確認ダイアログで趣旨を明示する）
```

### 16.3 UI 表示

スタッフは UI 上で以下を確認できるようにする。

登録フェーズでの「アドオン希望」の入力（必須・あり／なし／不明）、対象ユーザー欄、および任意の「メモ」は §11.7 に従い、画面上の開発者向け語の避け方は §11.9 に従う。

```text
アドオン希望: あり / なし / 不明
アドオン実施回数: （履歴より）〜回（参加可能な総回数の上限は当該トーナメントの `addonLimitPerPlayer` と `isAddon` に従う。§16.0）
```

例:

```text
オキバケA
アドオン希望: あり
アドオン実施回数: 0回
```

Addon 実行前の確認ダイアログ（文言・addonIntent が no/unknown のときの注意表示を含む）は **§12.7** とする。

### 16.4 置きバケ addon 実施時の扱い

置きバケ参加者に対して実際に addon 処理を行った場合は、以下を行う。

実装エントリは置きバケ専用 Callable `applyOkibakeAddon`（§16.7）とする。通常参加者用 addon Callable への分岐追加ではなく、別 Callable として実装する。

```text
1. okibakeAddonRecords に新しい record を追加する
2. okibakeTemporaryEntries/{okibakeEntryId}.okibakeAddonCount を +1 する
3. okibakeTemporaryEntries/{okibakeEntryId}.lastOkibakeAddonAt を addon 実施時刻に更新する
4. okibakeTemporaryEntries/{okibakeEntryId}.updatedAt / updatedByDeviceId を更新する
5. views/main.addons を +1 する
```

追加する record は、少なくとも以下を持つ。

```ts
{
  addonRecordId,
  operationId,

  occurredAt: Cloud Functions 側で生成した現在時刻の Timestamp,
  createdByDeviceId: deviceId,

  linkedBillId: null,
  reflectedToBill: false,
  reflectedToBillAt: null,

  rolledBack: false,
  rollBackAt: null,
  rollBackBy: null
}
```

会計・売上・analytics への正式反映は、後で bills 接続時に行う（§14.8）。

文字列 `"now"` を保存するものではない。

日時フィールドには、Cloud Functions 側で生成した現在時刻の Timestamp を保存する。

### 16.5 addon 実施回数と上限（`addonLimitPerPlayer`）

置きバケ一時参加者に対しても、通常参加者に対しても、**許容 Addon 実行回数の上限は、`scheduledTournament` にコピーされた `addonLimitPerPlayer` と `isAddon`** により決まる（詳細 §16.0）。

- **通常参加者**: `bills/{billId}/tournaments/{templateId}` における **`addonCount` が `scheduledTournament.addonLimitPerPlayer` 以上**のとき Addon **不可**。未満のとき、ほか成立条件も満たせば Addon 可能。  
  既存コードの **`addonCount >= 1` 固定拒否は、将来的に **`addonCount >= addonLimitPerPlayer`** へ置き換える（※実装フェーズ）。
- **置きバケ**: **`okibakeAddonCount >= addonLimitPerPlayer`** のとき **`applyOkibakeAddon`** は実行 **不可**。**`okibakeAddonCount < addonLimitPerPlayer`** のとき、そのほか §16.7 の条件を満たし **`isAddon: true`** なら Addon 可能。**`addonIntent` は実行可否ゲートとはしない（§16.2）。**

`okibakeAddonRecords` は **実行のたびに要素を追加する配列として履歴を残す**（§10.27）。親ドキュメントの **`okibakeAddonCount`** / **`lastOkibakeAddonAt`** は、§10.11・§10.12 のとおりとする。

### 16.6 置きバケ席に対する addon / bust の基本方針

業務上、置きバケ一時参加者も、通常参加者と同様に addon および bust の対象になる。

ただし、bill 未接続の置きバケ一時参加者は `activeStays` / `billId` を持たない可能性があるため、既存の通常ユーザー向け addon / bust Callable の処理をそのまま流用してはならない。

通常参加者と置きバケ一時参加者では、正本データ・前提条件・書き込み先が異なる。

通常参加者用 addon / bust は主に以下を前提にしている。

```text
- seatXXUserId
- activeStays/{userId}
- bills/{billId}
- bill 側 tournament action / recordTournamentAction
```

一方、置きバケ一時参加者用 addon / bust は以下を正本とする。

```text
- seatXXOkibakeEntryId
- okibakeTemporaryEntries/{okibakeEntryId}
- okibakeAddonRecords
- views/main
```

置きバケ addon / bust は、通常参加者用 Callable に専用分岐を追加して処理するのではなく、置きバケ専用 Callable として実装する。

理由は、通常参加者と置きバケ一時参加者では、正本データ・前提条件・書き込み先が異なるためである。

通常参加者用 Callable の処理をそのまま流用しない。

ただし、通常参加者用 Callable の業務ロジック・検証観点・transaction・operationLog・カウンタ更新の考え方は参照し、置きバケ用の正本データに合わせて専用 Callable として再実装する。

通常ユーザー席と置きバケ席は、seat 上で §13.9 の判定ルールに従う。

通常ユーザー席の場合は、既存の通常ユーザー向け addon / bust Callable を使用する。

置きバケ席（bill 未接続の置きバケ席）の場合は、`seatXXOkibakeEntryId` をもとに、置きバケ専用 Callable `applyOkibakeAddon`（§16.7）および `bustOkibakeTemporaryEntry`（§16.8）を呼び出す。

#### 通常参加者用 Callable との線引き

置きバケ addon / bust では、以下を前提にしない。

```text
- activeStays/{userId} が存在すること
- linkedBillId が存在すること
- seatXXUserId が存在すること
- recordTournamentAction へ即時反映すること
```

置きバケ addon / bust の正本は以下である。

```text
- okibakeTemporaryEntries/{okibakeEntryId}
- okibakeAddonRecords
- seatXXOkibakeEntryId
```

したがって、通常参加者用 Callable に置きバケ処理を混在させず、置きバケ専用 Callable として実装する。

### 16.7 `applyOkibakeAddon`

置きバケ一時参加者に addon を実施する Callable。

通常参加者用 addon Callable とは別の入口として実装する。

#### 入力

```ts
type ApplyOkibakeAddonInput = {
  tournamentId: string;
  okibakeEntryId: string;
  operationId: string;
};
```

#### 実行可能な `entryStatus`

`applyOkibakeAddon` は、対象の `okibakeTemporaryEntry.entryStatus` が **`registered` または `seated`** の場合に実行可能とする。

実行不可とするのは次である。

```text
busted
voided
```

`busted` は敗退済みのため、新規 Addon の対象外とする。

`voided` は登録取消状態のため、Addon 対象外とする。

`registered` の状態で Addon を実施しても **entryStatus は `registered` のまま**とする（待機者一覧上の分類は変えない）。Addon は参加状態・席状態を変えない操作である。

`billLinkStatus: "linked"` が付いた置きバケ entry を `applyOkibakeAddon` に渡した場合は、**経路誤りとして拒否してよい**。linked 後の参加者は通常ユーザーとして **通常 addon Callable** を使用する（§12.7・§13.9）。

`addonIntent` は Addon 実行可否判定に用いない（§16.2）。

#### Addon 実行上限（`addonLimitPerPlayer`）

**通常参加者・置きバケ参加者と同一上限**であり、実行時 **`scheduledTournaments/{tournamentId}` にコピーされた `addonLimitPerPlayer`**（未定義時の読み込みフォールバックおよび `isAddon` の解釈は §16.0）により判定する。**`okibakeAddonCount < addonLimitPerPlayer`** が満たされないとき、または Addon が機能として無効なときは、`applyOkibakeAddon` を **拒否してよい**。

#### 主な処理

```text
1. 店舗デバイス権限を確認する
2. scheduledTournaments/{tournamentId} を確認する（§16.0 に従い isAddon と addonLimitPerPlayer を解釈する）
3. views/main を確認する
4. okibakeTemporaryEntries/{okibakeEntryId} を確認する
5. entryStatus が registered または seated であること、かつ billLinkStatus が linked でないことを確認する（linked は誤経路として拒否）
6. `isAddon` が実質許可されていない、または `addonLimitPerPlayer` が 0 と解釈される、または **`okibakeAddonCount >= addonLimitPerPlayer`** のときは Addon 実行不可としてエラーとする
7. okibakeAddonRecords に新しい record を追加する
8. okibakeTemporaryEntries.okibakeAddonCount を +1 する
9. okibakeTemporaryEntries.lastOkibakeAddonAt を現在時刻の Timestamp に更新する
10. okibakeTemporaryEntries の updatedAt / updatedByDeviceId を更新する
11. views/main.addons を +1 する
12. operationLog を記録する（rollback に必要な okibakeEntryId / addonRecordId 等を含める。§12.7）
```

この処理では **`entries` / `playersIn` / `waitingCount` / `seatedCount` は変更しない**（registered からの実行でも同様）。

`busted` / `voided` / （誤経路の）`linked` / **Addon 上限到達（`okibakeAddonCount >= addonLimitPerPlayer`）または Addon 機能無効（`isAddon` false または上限 0 相当）** の場合はエラーとする。

#### 書き込み先

```text
- scheduledTournaments/{tournamentId}/okibakeTemporaryEntries/{okibakeEntryId}
- scheduledTournaments/{tournamentId}/views/main
- operationLogs
```

#### bills 反映

`applyOkibakeAddon` 実行時点では、`bills` 側へは反映しない。

置きバケ addon の正式な `bills` 反映は、後続の `bills` 接続時に `okibakeAddonRecords` から行う。

`bills` 接続時の `okibakeAddonRecords` 反映対象は以下とする。

```text
rolledBack == false
and
reflectedToBill == false
```

#### 冪等性

`applyOkibakeAddon` は `operationId` によって二重実行を防ぐ。

同一 `operationId` の再送は、同じ addon record を再利用する、または no-op 成功とする。

別 `operationId` で同じ `okibakeEntryId` に対して実行された場合は、それぞれを別 addon 実施として扱う。その際も **実行のたびに §16.0 の上限（`addonLimitPerPlayer`）および `okibakeAddonCount` を満たす必要がある**。

`addonRecordId` の生成方法、idempotency の保存先、requestHash、再送レスポンスは、既存の operationId / idempotency 実装規則に準拠する。

#### operationLog action 名（候補）

operationLog action 名は候補名をベースに、既存 operationLog の命名規則に合わせて実装時に確定する。

初期候補は以下とする。

```text
apply_okibake_addon
```

### 16.8 `bustOkibakeTemporaryEntry`

置きバケ一時参加者を bust する Callable。

通常参加者用 bust Callable とは別の入口として実装する。

#### 入力

```ts
type BustOkibakeTemporaryEntryInput = {
  tournamentId: string;
  okibakeEntryId: string;
  operationId: string;
};
```

`tableId` / `seatKey` は入力で受け取らず、原則として `okibakeTemporaryEntries.assignedTableId` / `assignedSeatKey` を正本として使用する。

理由は、呼び出し側が誤った席情報を渡した場合でも、現在の置きバケ一時参加者の実際の着席状態を基準に処理するためである。

#### 主な処理

```text
1. 店舗デバイス権限を確認する
2. scheduledTournaments/{tournamentId} を確認する
3. views/main を確認する
4. okibakeTemporaryEntries/{okibakeEntryId} を確認する
5. entryStatus: "seated" であることを確認する
6. assignedTableId / assignedSeatKey が存在することを確認する
7. 対象 seat に seatXXOkibakeEntryId が存在し、okibakeEntryId と一致することを確認する
8. 対象 seat をクリアする
9. entryStatus を "busted" に更新する
10. bustedAt / bustedTableId / bustedSeatKey を記録する
11. views/main.playersBusted を +1 する
12. updatedAt / updatedByDeviceId を更新する
13. operationLog を記録する
```

#### 書き込み先

```text
- scheduledTournaments/{tournamentId}/okibakeTemporaryEntries/{okibakeEntryId}
- scheduledTournaments/{tournamentId}/tablesSeat/{assignedTableId}
- scheduledTournaments/{tournamentId}/views/main（playersBusted）
- operationLogs
```

#### カウンタ

置きバケ bust 成功時の `views/main` 更新は以下とする。

```text
views/main.playersBusted +1
```

以下のカウンタは変更しない。

```text
views/main.entries 変更なし
views/main.playersIn 変更なし
views/main.waitingCount 変更なし
views/main.seatedCount 変更なし
views/main.addons 変更なし
```

理由は、置きバケ bust もトーナメント上の参加枠として bust した脱落者数に含めるため `playersBusted` を更新する一方、bust は登録取消ではなく参加者として成立した後の敗退であり、置きバケの席配置時点で待機者一覧からは外れているため `entries` / `playersIn` / `waitingCount` 等は変更しないためである。

#### 冪等性

`bustOkibakeTemporaryEntry` は `operationId` によって二重実行を防ぐ。

同一 `operationId` の再送は no-op 成功とする。**replay 時は `playersBusted` を二重更新しない**。

すでに同じ `okibakeEntryId` が `entryStatus: "busted"` の場合でも、それが同一 `operationId` による再送であれば成功扱いにする。

一方、すでに `busted` の置きバケ一時参加者に対して、別 `operationId` で再度 bust しようとした場合はエラーとする。

idempotency の保存先、requestHash、再送レスポンスは、既存の operationId / idempotency 実装規則に準拠する。

#### operationLog action 名（候補）

operationLog action 名は候補名をベースに、既存 operationLog の命名規則に合わせて実装時に確定する。

初期候補は以下とする。

```text
bust_okibake_temporary_entry
```

### 16.9 置きバケ bust（状態・データ）

実装エントリは `bustOkibakeTemporaryEntry`（§16.8）とする。

置きバケ一時参加者がバーストした場合、`entryStatus` を以下のように更新する。

```ts
entryStatus: "seated"
→ entryStatus: "busted"
```

あわせて以下を更新する。

```ts
bustedAt: now
bustedTableId: assignedTableId
bustedSeatKey: assignedSeatKey
updatedAt: now
updatedByDeviceId: deviceId
```

置きバケ bust 時には、対象 seat から置きバケ参加者を除去する。

```ts
{
  [`${seatKey}UserId`]: null,
  [`${seatKey}PokerName`]: null,
  [`${seatKey}OkibakeEntryId`]: null
}
```

`entries` / `playersIn` は減算しない。

理由は、`busted` は登録取消ではなく、トーナメント参加者として成立した上で敗退した状態であるためである。

`waitingCount` は更新しない。

理由は、対象者はすでに席配置時に待機者一覧から外れているためである。

`seatedCount` は、置きバケ関係では更新しない。

`playersBusted` は **+1** する（§16.8 カウンタ。置きバケ bust もトーナメント上の脱落者数に含める）。

`addons` は更新しない。

### 16.10 まとめてAddon（`bulkAddon`）の置きバケ対応

卓単位の「まとめてAddon」は、該当テーブル内の**通常着席ユーザー**に加え、**`seated` + `unlinked` の置きバケ**も対象に含める。

#### 対象

```text
entryStatus == seated
billLinkStatus == unlinked
seatXXOkibakeEntryId が該当 seat に存在する（Flutter 側収集）
```

#### 対象外

```text
registered / busted / voided / pending_review / linked
```

#### 実装方針

```text
- UI 上は「まとめてAddon」1 操作
- operationLog は 1 件（action: bulk_addon）
- rollback も 1 回（undoBulkAddon）
- 通常参加者分と置きバケ分は Callable 内部で分けて処理する
```

通常参加者分は既存どおり `recordTournamentAction` / `bills` を更新する。置きバケ分は `applyOkibakeAddon` と同様に `okibakeAddonRecords` 追加・`okibakeAddonCount` 更新・`views/main.addons +1` を行う。

payload 例:

```text
normalUsers: [{ userId, pokerName }, ...]
okibakeEntries: [{ okibakeEntryId, pokerName? }, ...]
```

#### rollback（`bulk_addon` undo）

`undoBulkAddon` 1 回で、通常参加者分 + 置きバケ分をまとめて戻す。

```text
- views/main.addons を (通常分 + 置きバケ分) だけ -1
- 通常参加者: bills 側 addonCount を -1
- 置きバケ: operationLog の okibakeEntryBefore を正として okibakeTemporaryEntries を復元
```

### 16.11 未確定事項

```text
- okibakeAddonRecords の rollback 時に rollBackBy に保存する値は、既存 operationLog の rollBackBy と揃える前提で実装時に確定する
- pending_review・来店なし入金フローを含む要対応会計画面上の細部は §25.2、関連 Callable・型の具体化は §25.3、本章冒頭を参照する
```

## 17. 取消・無効化仕様

### 17.1 `voided`

`voided` は、店舗判断により、置きバケ一時参加者としての登録を取り消した状態である。

`busted` と `voided` は別概念である。

`busted` は、参加者として成立した後に敗退した状態である。

`voided` は、置きバケ一時参加者としての登録自体を取り消した状態である。

そのため、`busted` の置きバケ一時参加者を `voided` として扱ってはならない、という意味での同一視は行わない。

`voided` は、来店しなかった状態や `bills` 未接続の確認待ち状態を表すものではない。

来店せず `bills` 未接続のまま確認が必要な場合は、`billLinkStatus: "pending_review"` で管理する。

誤作成、対象トーナメント間違い、重複作成、ユーザーからのキャンセルなどは、`voided` にする理由であり、`voided` の状態定義そのものではない。

操作履歴から行う「戻し」は、`voided` とは別概念である。

戻しは、選択された操作が行われなかった状態に戻すための処理であり、`entryStatus` の状態定義には含めない。

無効化するときは `entryStatus` を次のようにする。

```ts
entryStatus: "voided"
```

### 17.2 物理削除しない

置きバケ一時参加者は、原則として物理削除しない。

理由は、履歴・監査・未接続確認との整合を保つためである。

### 17.3 `voided` 時のカウンタ戻し

置きバケ一時参加者を `voided` にする場合、現在の `entryStatus` に応じて、作成時に反映したカウンタを戻す。

`entryStatus: "registered"` の置きバケを `voided` にする場合は、以下を更新する。

```text
views/main.entries -1
views/main.playersIn -1
views/main.waitingCount -1
views/main.seatedCount 変更なし
```

`entryStatus: "seated"` の置きバケを `voided` にする場合は、以下を更新する。

```text
views/main.entries -1
views/main.playersIn -1
views/main.waitingCount 変更なし
views/main.seatedCount 変更なし
```

`seated` の置きバケを `voided` にする場合、`okibakeTemporaryEntries/{okibakeEntryId}` の `assignedTableId` / `assignedSeatKey` をもとに対象席を特定する。

対象 seat では、少なくとも以下をクリアする。

```ts
{
  [`${seatKey}UserId`]: null,
  [`${seatKey}PokerName`]: null,
  [`${seatKey}OkibakeEntryId`]: null
}
```

`seatXXOccupantType` は採用しないため、参照・更新しない。

`billLinkStatus: "linked"` の置きバケ一時参加者は、初期仕様では `voided` にできない。

理由は、`bills` 接続後に `okibakeTemporaryEntries` 側だけを取り消すと、会計・精算・analytics 側と不整合になる可能性があるためである。

`entryStatus: "busted"` の置きバケ一時参加者を `voided` にできるかどうかは、初期仕様では原則不可とする。

理由は、`busted` は参加者として成立した後の敗退状態であり、登録取消である `voided` とは意味が異なるためである。

### 17.4 `voidedAt` / `voidedByDeviceId`

置きバケ一時参加者を `voided` にする場合、以下を更新する。

```ts
voidedAt: now;
voidedByDeviceId: deviceId;
```

`voidReason` は初期仕様では採用しない。

## 18. 履歴・戻し仕様

### 18.1 基本方針

置きバケ操作は、トーナメント操作履歴の対象にする。

対象候補は以下である。

```text
- 置きバケ一時参加者作成
- 置きバケ席配置
- 置きバケ席移動・全員リシート
- 置きバケ addon / bust
- bills 接続
- pending_review 化
- voided 化
- 戻し操作（rollback）
```

通常参加者の Addon（卓上のみならず **待機者一覧から開始した経路** を含む）の rollback は、**既存の通常 addon に対する rollbackAction／undoAddon** の規則に従う（§12.7）。

### 18.2 `rollbackAction` における置きバケの扱い

置きバケ操作も `rollbackAction` の対象にする。

ただし、通常ユーザー向けの `userId` 前提の undo 処理にそのまま流してはならない。

`rollbackAction` の枠組みは既存を利用しつつ、`seatXXOkibakeEntryId` や `okibakeEntryId` が関係する操作では、置きバケ用の undo 分岐で処理する。

rollbackAction に追加する置きバケ系 action 名および payload 詳細は、既存 rollbackAction / operationLog の設計に準拠し、各操作の復元に必要な最小情報を保持する。

#### 18.2.1 Phase 7 初期実装の対象（確定）

Phase 7 初期実装で rollbackAction に接続する対象は、次の 2 操作に限定する。

1. 置きバケ対象ユーザー設定 undo（`updateOkibakeTemporaryEntryLinkedUser`）
2. 置きバケ来店中 bill 紐付け undo（`linkOkibakeTemporaryEntryToBill`）

対象ユーザー設定 undo の制約:

```text
- billLinkStatus == unlinked の場合のみ許可
- pending_review / linked は不可
- seated の場合は seatXXPokerName も before に戻す
```

来店中 bill 紐付け undo の制約:

```text
- linked 先 bill.status が open / in_progress の場合のみ許可
- settling は初期実装では不可
- settled / post_settlement_pending / refunded / partially_refunded / voided は不可
- pending_review からの紐付け取り消しは、operationLog の before を正として pending_review 状態へ戻す
```

来店なし入金（`resolveOkibakePendingReviewWithRemotePayment`）の undo は Phase 7 初期実装の対象外とする。
来店なし入金で settled 済みとなった bill の誤処理は、bills 側の post-settlement / refund / 事後調整レールで扱う。

#### 18.2.2 Phase 7 追加実装の対象（確定）

Phase 7 追加実装で rollbackAction に接続する対象は、次の 2 操作とする。

1. 置きバケ登録 rollback（`createOkibakeTemporaryEntry`）
2. 置きバケ席配置 undo（`assignOkibakeTemporaryEntryToSeat`）

action key は以下とする。

```text
- 置きバケ登録 -> okibake_create_entry
- 置きバケ着席 -> okibake_assign_seat
```

getActionLogs は operationName と action key を上記で対応付け、ActionHistory は表示名と action key を分離して扱う。

#### 18.2.3 置きバケ登録 rollback（追加実装）

置きバケ登録 rollback は、作成 doc の物理削除ではなく voided 化で扱う。

```text
対象 operationName:
- 置きバケ登録

許可条件:
- entryStatus == registered
- billLinkStatus == unlinked
- linkedBillId == null
- okibakeAddonCount == 0

拒否条件:
- entryStatus == seated / busted / voided
- billLinkStatus == pending_review / linked
- linkedBillId あり
- okibakeAddonCount > 0
```

復元方針:

```text
- okibakeTemporaryEntry は削除しない
- entryStatus を voided に更新
- voidedAt / voidedByDeviceId / updatedAt / updatedByDeviceId を更新
- linkedUserId / linkedUserPokerName は voided entry 上に残してよい
```

views/main は登録時の差分を補正して戻す。

```text
- entries -1
- playersIn -1
- waitingCount -1
```

各カウンタは max(0, current - 1) で下限 0 ガードする。

`okibakeNextDisplayNumber` は戻さない。採番再利用を避け、表示番号と操作履歴の混乱を防ぐためである。

#### 18.2.4 置きバケ席配置 undo（追加実装）

置きバケ席配置 undo は、operationLog の before を正として seated から registered へ戻す。

```text
対象 operationName:
- 置きバケ着席

許可条件:
- entryStatus == seated
- billLinkStatus == unlinked
- linkedBillId == null
- okibakeAddonCount == 0

拒否条件:
- entryStatus == registered / busted / voided
- billLinkStatus == pending_review / linked
- linkedBillId あり
- okibakeAddonCount > 0
```

復元方針:

```text
- okibakeTemporaryEntry を payload.okibakeEntryBefore ベースで復元
- entryStatus は registered に戻る
- assignedTableId / assignedSeatKey / seatedAt などを before に戻す
- tablesSeat は seatBefore に復元
- seatXXUserId / seatXXPokerName / seatXXOkibakeEntryId を before に戻す
- views/main.waitingCount は +1
```

entries / playersIn は変更しない。席配置 undo は参加人数を変えないためである。

#### 18.2.5 Phase 7 rollback 対象外（継続）

Phase 7 では、以下は引き続き rollback 対象外とする。

```text
- 来店なし入金 rollback
- settled bill rollback
- analytics の直接巻き戻し
- bill 削除型 rollback
- Addon rollback
- Bust rollback（**fallbackSeat / seat selection required** は §18.7・§18.8）
- ~~busted + linked のランキング / bustedUser 反映~~ → **getRankingData read-time 補完で対応済み（§19.7）**
- Phase 8 link_prompt / LIFF
```

来店なし入金 settled 済み bill の誤処理は、bills 側の post-settlement / refund / 事後調整レールで扱う。

### 18.3 戻し（rollback）と `voided` の関係

操作履歴から行う「戻し（rollback）」は、`voided` とは別概念である。

rollback は、選択された操作が行われなかった状態へ戻す処理であり、原則として `voided` を使って代替しない。

戻しは、選択された操作が行われなかった状態に戻すための処理であり、`entryStatus` の状態定義には含めない。

operation ごとの undo では、対象データを `voided` にするのではなく、当該操作前の状態へ復元することを基本とする（作成 rollback など例外・細目は §18.8、§14.12・§14.14（伝票誤接続および解除）、および関連節で整理する）。

### 18.4 置きバケ席配置の rollback

`assignOkibakeTemporaryEntryToSeat` を戻す場合、置きバケ一時参加者を席配置前の状態に戻す。

更新内容は以下である。

#### 対象 seat

```ts
{
  [`${seatKey}UserId`]: null,
  [`${seatKey}PokerName`]: null,
  [`${seatKey}OkibakeEntryId`]: null
}
```

#### `okibakeTemporaryEntries/{okibakeEntryId}`

```ts
{
  entryStatus: "registered",
  assignedTableId: null,
  assignedSeatKey: null,
  seatedAt: null,
  updatedAt: now,
  updatedByDeviceId: deviceId
}
```

#### `views/main`

```text
waitingCount +1
seatedCount 変更なし
entries 変更なし
playersIn 変更なし
```

置きバケ一時参加者は `tablesSeat/waiting` には保存しない。

そのため、rollback 後の待機者一覧復帰は、`entryStatus: "registered"` の `okibakeTemporaryEntries` が再び待機者一覧に表示されることで実現する。

### 18.5 置きバケ席移動・全員リシートの rollback

置きバケ席移動または全員リシートを戻す場合、移動前の席配置へ戻す。

#### 全員リシート（`reseat_all_players`）と `okibakeReseatTargets`

`reseatAllPlayers` の operationLog には、置きバケ対象がある場合 **`okibakeReseatTargets`** を保存する。

```text
okibakeEntryId
okibakeEntryBefore（entryStatus / assignedTableId / assignedSeatKey / seatedAt 等）
okibakeEntryAfter（リシート後の entryStatus / assignedTableId / assignedSeatKey / assignedSeatNumber 等）
```

`undoReseatAllPlayers` は **`tablesSeat` を復元するだけでなく、`okibakeTemporaryEntries` も `okibakeEntryBefore` に戻す**。

#### 現在状態検証

rollback 前に、対象 entry の以下が **`okibakeEntryAfter` と一致**することを検証する。不一致時は安全側で rollback を拒否する。

```text
entryStatus
assignedTableId
assignedSeatKey
assignedSeatNumber（after に含まれる場合）
```

#### 旧ログ互換

`okibakeReseatTargets` がない旧 operationLog は、**従来どおり `tablesSeat` のみ復元**する。

#### 席配置の復元

更新内容は以下である。

```text
- 移動後 seat をクリアする
- 移動前 seat に `seatXXOkibakeEntryId` / `seatXXPokerName` を戻す
- `okibakeTemporaryEntries.assignedTableId` / `assignedSeatKey` / `entryStatus` / `seatedAt` を before に戻す
- `updatedAt` / `updatedByDeviceId` を更新する
- `seatedAt` は before の値を復元（初回着席時刻を維持）
```

#### カウンタ

```text
registered → seated を rollback して registered に戻す場合:
  views/main.waitingCount +1

seated → seated の rollback:
  waitingCount 変更なし

entries / playersIn / seatedCount:
  変更なし
```

理由は、registered 置きバケをリシートで seated にしたとき `waitingCount -1` しているため、undo では対称に +1 する。seated 同士のリシートでは waitingCount を変更しない。

対象 seat がすでに別参加者で埋まっている場合、自動 rollback は危険であるため、エラーまたは手動確認対象とする。

### 18.6 置きバケ addon の rollback

置きバケ addon の rollback は、`okibakeAddonRecords` の要素（`addonRecordId`）単位で行う。

rollback payload には、少なくとも対象の `addonRecordId` を含める。

```ts
addonRecordId: string;
```

addon rollback では、対象 record を配列から物理削除しない。

対象 `OkibakeAddonRecord` には、既存 `operationLogs` の rollback 語彙に合わせて以下を設定する。

```ts
{
  rolledBack: true,
  rollBackAt: Cloud Functions 側で生成した現在時刻の Timestamp,
  rollBackBy: operatorId
}
```

そのうえで、以下を行う。

```text
- transaction 内で `okibakeTemporaryEntries/{okibakeEntryId}` を読み取り、`okibakeAddonRecords` 配列をメモリ上で更新し、配列全体を書き戻す
- `okibakeTemporaryEntries.okibakeAddonCount` を、`rolledBack: false` の有効 record 数に合わせて再計算する
- `lastOkibakeAddonAt` を、`rolledBack: false` の有効な `okibakeAddonRecords` から再計算する
- `views/main.addons` を -1 する
```

`okibakeAddonCount` および `views/main.addons` は 0 未満にしない。

すでに `bills` 側へ反映済み、つまり `reflectedToBill: true` の record に対して、**単体のアドオン rollback だけ**を適用することは、初期仕様では原則不可とする（`bills` と `okibakeAddonRecords` の整合や金額差分があり得るため）。

伝票との接続は正しく、伝票側に投影済みの置き addon のみを取り除きたい等の要件は、`bills` 側取消・post-settlement 補正等の別経路になり得る。一方、**誤った伝票へ紐付けたことを現場が会計前に検知した場合**は、§14.14 の誤紐付け解除（専用 undo）の一環として、当該 record の未反映状態への戻しと `bills` 側の差し引きを **あわせて**行う。

#### 待機者一覧からの `applyOkibakeAddon`

待機者一覧経路で実施した置きバケ Addon も、上記と同じ **rollback 方針（`addonRecordId` 単位）** の対象に含める。新しい undo 種別を定義することが主目的ではない（§12.7）。

**`bulk_addon` rollback** は §16.10 に従い、`undoBulkAddon` 1 回で通常参加者分 + 置きバケ分をまとめて戻す。

### 18.7 置きバケ bust の rollback（`okibake_bust`）

置きバケ bust を戻す場合の目的は、**元の席に戻すこと**ではなく、**bust 前の参加中状態（seated）に戻すこと**である。

#### 基本復元

`entryStatus` を `busted` から `seated` に戻し、復元先 seat へ置きバケ参加者を復帰させる。

#### `okibakeTemporaryEntries/{okibakeEntryId}`

```ts
{
  entryStatus: "seated",
  bustedAt: null,
  bustedTableId: null,
  bustedSeatKey: null,
  updatedAt: now,
  updatedByDeviceId: deviceId
}
```

#### 対象 seat

rollback payload に保持している bust 前の `tableId` / `seatKey` / `seatPokerName` / `okibakeEntryId` をもとに、以下を復元する。

```ts
{
  [`${seatKey}UserId`]: null,
  [`${seatKey}PokerName`]: seatPokerName,
  [`${seatKey}OkibakeEntryId`]: okibakeEntryId
}
```

#### 席復元と `fallbackSeat`

```text
元席が空いている:
  → 元席へ自動復元

元席が埋まっている:
  → DB は変更せず seat selection required error を返す
  → Flutter 側で空席選択 UI を表示

fallbackSeat が指定され、空席である:
  → fallbackSeat へ復元

fallbackSeat も埋まっている / 空席がない:
  → undo 不可
```

**seat selection required の段階では DB を変更しない**（`playersBusted` も更新しない）。

Functions error:

```text
errorKey: TOURNAMENT_BUST_UNDO_SEAT_SELECTION_REQUIRED
details: originalSeat, availableSeats, participantType: okibake 等
```

#### カウンタ（rollback 成功時のみ）

```text
views/main.playersBusted -1（下限 0 ガード）
views/main.entries 変更なし
views/main.playersIn 変更なし
views/main.waitingCount 変更なし
views/main.seatedCount 変更なし
views/main.addons 変更なし
```

rollback 済み operationLog の再 rollback では **`playersBusted` を二重更新しない**。

置きバケ中に発生した bust は `okibakeTemporaryEntries` 側の状態として扱い、`bills` 側へ bust 専用反映は行わない。

### 18.8 通常参加者 bust の rollback（`bust_and_exit` / `bust_and_reentry`）

`undoBustAndExit` / `undoBustAndReentry` も、目的は **bust 前の参加中状態に戻すこと**である（§18.7 と同じ席復元方針）。

#### rollback 成功時

```text
- 元席または fallbackSeat に復元する
- views/main.playersBusted -1
- views/main.playersIn +1（exit / reentry 種別に応じた既存規則）
- tablesSeat/busted.bustedUser.{userId} を削除する
```

**linked 後に通常 bust された元置きバケ**も、通常 bust undo 経路で `bustedUser` から削除される。

#### seat selection required / fallbackSeat 拒否時

```text
- DB は変更しない
- bustedUser は削除しない
- playersBusted は変更しない
```

Functions error は置きバケ bust undo と同様 **`TOURNAMENT_BUST_UNDO_SEAT_SELECTION_REQUIRED`**（`participantType: normal`）。

### 18.9 未確定事項

```text
- 置きバケ作成操作の rollback 時に、対象データを voided にするか、作成前状態に復元するか
- 置きバケ作成操作の rollback 時に、entries / playersIn / waitingCount をどう戻すか
- §14.14 の誤紐付け解除 undo の実装上の細目（transaction 粒度、カウンタ二重調整、`recordTournamentAction` と idempotency の境界）
- pending_review 化の戻しを許可するか
```

rollbackAction に追加する置きバケ系 action 名・payload の細目、および operationLog に残す action 名の詳細は、既存 rollbackAction / operationLog の実装規則に準拠する（§18.2、§25 冒頭）。

## 19. リシート仕様

### 19.1 業務制約と対象（席移動・全員リシート共通）

置きバケ席の席移動は許可する。

置きバケ席移動・全員リシートにおいて、通常席と異なる追加の業務制約は設けない。

bill 未接続の置きバケ席であっても、`entryStatus: "seated"` で実際に seat 上に存在する場合は、席移動・全員リシートの対象にする。

接続済み置きバケ由来席は、seat 上では以下の状態になり得る。

```ts
{
  [`${seatKey}UserId`]: linkedUserId,
  [`${seatKey}PokerName`]: linkedUserPokerName,
  [`${seatKey}OkibakeEntryId`]: okibakeEntryId
}
```

この場合、操作上は `seatXXUserId` を優先し、通常ユーザー席として扱う。

ただし、`seatXXOkibakeEntryId` は置きバケ由来を追跡するための ID として維持する。

席の種別・操作上の優先順位については §13.9 に従う。

席移動・全員リシートの対象判定は以下とする。

```text
seatXXUserId がある
→ 通常ユーザー席として処理する

seatXXUserId がなく、seatXXOkibakeEntryId がある
→ bill 未接続の置きバケ席として処理する

seatXXUserId も seatXXOkibakeEntryId もない
→ 空席として扱う
```

以下の状態の置きバケ一時参加者は、**seat 上の個別席移動**対象外とする。

```text
busted
voided
pending_review
```

`registered` は seat 上には存在しないが、**全員リシートの候補**には含める（§19.2）。

理由は、busted / voided / pending_review は seat 上に存在する移動対象ではないためである。registered は待機者一覧相当の状態であり、全員リシートで seated へ配置し得る。

### 19.2 全員リシート（`reseatAllPlayers` 相当）

全員リシートは**スタッフが対象者を選択する機能**である。置きバケも候補に含め、実際に選ぶかはスタッフに委ねる。

#### 置きバケ候補条件

```text
entryStatus in [registered, seated]
billLinkStatus in [unlinked, linked]
```

対象外: `busted` / `voided` / `pending_review`

#### linked の重複表示防止

`linked` を一律除外しない。ただし **`linkedUserId` が通常参加者候補（着席・通常 waiting）として既に出ている場合**は、通常参加者側を優先し、置きバケ側は**重複表示しない**。

#### seat 書き込み

通常参加者:

```text
seatXXUserId
seatXXPokerName
```

置きバケ（bill 未接続）:

```text
seatXXOkibakeEntryId
seatXXPokerName
okibakeTemporaryEntry.entryStatus / assignedTableId / assignedSeatKey / seatedAt を更新
```

`registered → seated` に遷移した場合:

```text
views/main.waitingCount -1
```

トーナメント操作の「全員リシート」では、§19.1 に従い、通常ユーザー席に加え、bill 未接続の置きバケ席および bills 接続済みの置きバケ由来席もリシート対象に含める。

全員リシートの対象抽出では、`seatXXUserId` だけでなく `seatXXOkibakeEntryId` も確認する。

Flutter 側の「全員リシート」ボタンは基本的に既存のままでよい。

ただし、そのボタンが呼び出す Cloud Functions 側の全員リシート処理では、§19.1 の `seatXXUserId` / `seatXXOkibakeEntryId` の組み合わせに応じた処理分岐を用意する。

Flutter 側でリシート対象者を事前に組み立てて Callable に渡している場合は、Flutter 側でも `seatXXOkibakeEntryId` を確認して置きバケ席を対象に含める。

個別席移動・全員リシートの Callable 名・入力・冪等性の保存形式などは、既存トーナメントの Callable / idempotency / operationLog の実装規則に準拠する。表示については §19.6 を参照する。

### 19.3 `bill` 未接続の置きバケ席の seats 更新

個別席移動・全員リシートのどちらでも、`seatXXUserId` が null かつ `seatXXOkibakeEntryId` が設定されている bill 未接続の置きバケ席を移動する場合は、以下のように更新する。

この場合は、移動元 seat をクリアし、移動先 seat に置きバケ情報を保存する。

bills 接続済みの置きバケ由来席は、通常ユーザー席として扱い、`seatXXUserId` を維持したまま、`seatXXPokerName` / `seatXXOkibakeEntryId` を含めて既存の通常席移動と同様に移動させる。

#### 移動元 seat

```ts
{
  [`${fromSeatKey}UserId`]: null,
  [`${fromSeatKey}PokerName`]: null,
  [`${fromSeatKey}OkibakeEntryId`]: null
}
```

#### 移動先 seat

```ts
{
  [`${toSeatKey}UserId`]: null,
  [`${toSeatKey}PokerName`]: linkedUserPokerName ?? temporaryDisplayName,
  [`${toSeatKey}OkibakeEntryId`]: okibakeEntryId
}
```

上記コードブロックの更新は、`seatXXUserId` を null のまま維持する bill 未接続の置きバケ席に限る。

### 19.4 置きバケ席移動時の `okibakeTemporaryEntries` 更新

置きバケの座席が移動し、`assignedTableId` / `assignedSeatKey` が変わる場合、`okibakeTemporaryEntries/{okibakeEntryId}` では以下を更新する。

```ts
{
  assignedTableId: newTableId,
  assignedSeatKey: newSeatKey,
  updatedAt: now,
  updatedByDeviceId: deviceId
}
```

`seatedAt` は初回着席時刻を表すため、席移動・全員リシートでは更新しない。

### 19.5 席移動・全員リシート時のカウンタ扱い

席移動・全員リシートでは、原則として以下のカウンタは変更しない。

```text
views/main.entries 変更なし
views/main.playersIn 変更なし
views/main.seatedCount 変更なし
```

**例外**: 全員リシートで **`registered` 置きバケを `seated` に配置**した場合のみ `views/main.waitingCount -1`（§19.2）。rollback では §18.5 に従い +1。

理由は、席移動・全員リシートは原則として座席配置の変更のみであり参加登録・敗退・取消の状態を変えないためである（registered → seated の waitingCount は待機者一覧からの除外に対応）。

### 19.6 順位確定・`getRankingData` の linked + busted 補完

`getRankingData` は、既存の `tablesSeat/busted.bustedUser` に加え、**linked + busted の元置きバケ**を **read-time merge** で `bustedPlayers` に補完する。

#### 補完対象

```text
billLinkStatus == linked
entryStatus == busted
linkedUserId あり
```

#### 補完対象外

```text
unlinked / pending_review / registered / seated / voided
linkedUserId なし
```

#### 方針

```text
- bustedUser への永続書き込みはしない
- link / bust / rollback の既存処理は変更しない
- getRankingData の返却時だけ合成する
- 既存 bustedUser に同一 uid がある場合は bustedUser 側を優先する（二重表示しない）
```

#### 表示名 fallback（補完行）

```text
1. linkedUserPokerName
2. temporaryDisplayName
3. displayName
4. 不明
```

bust 時刻は `okibakeTemporaryEntries.bustedAt` を使用する。

### 19.7 未確定事項（表示・実装詳細）

- operationLogs をリシート相当として扱っているのか
- 別のレポート・履歴UIがあるのか
- 置きバケ参加者を通常参加者と同じ表示にするか

## 22. 置きバケ登録済みユーザーと通常トーナメント参加の重複防止

同一トーナメントにおいて、置きバケとして **`okibakeTemporaryEntries` に現実に存在しているユーザー参加** と、LIFF／店舗デバイスからの **通常トーナメント参加 Callable** とが両方走った場合、`views/main` 系カウンタ・`tablesSeat/waiting`・`views/usersList`・`bills/.../tournaments` に **二重反映**され得る。本節はそれを防止する。**置きバケの正本は `okibakeTemporaryEntries`** とする（§23「対象外」とは論点が異なることに留意）。

### 22.1 対象 Callable

通常参加の重複防止は、以下の **両方** が対象とする。

```text
LIFF:
registerForTournament

店舗デバイス / スタッフ一括登録:
registerParticipants
```

両者は別 Callable であり事前条件も対称ではない。**いずれか片方のみの対策では不十分**とし、両 Callable で **`scheduledTournaments/{tournamentId}/okibakeTemporaryEntries` を評価**する仕様とする。

### 22.2 Cloud Functions を正として防ぐ

重複防止の **決定的なチェックは Cloud Functions 側で必ず実行**する。クライアント（LIFF／店舗アプリ）の表示や任意確認は **補助線**のみとする。

```text
- 経路が LIFF と店舗とで分離しているため
- 競合やクライアント迂回を防ぐため
- counters / bills tournaments 側の整合をサーバ側で保証するため
```

### 22.3 通常参加拒否条件

次を **すべて満たす** `okibakeTemporaryEntries` が 1件でもある場合、対象ユーザー ID に関する **`registerForTournament` は失敗させ、`registerParticipants` はその userId 行のみ失敗**とする（同一 callable 呼び出しの他ユーザー分は処理継続可。§22.11）。

```text
scheduledTournaments/{tournamentId}/okibakeTemporaryEntries いずれかのドキュメントについて:

linkedUserId == 参加しようとしている userId（null 不可。null は §22.7）

かつ entryStatus != "voided"

かつ billLinkStatus in ["unlinked", "pending_review", "linked"]
```

（対象 tournamentId が一致することは親パスおよびデータ上から自明な前提）

#### 22.3.1 `linked` を含める理由

`linked` は **bills 接続済み**であり、業務としては通常の追加入力は不要。**LIFF 側は `bills/{billId}/tournaments/{templateId}` で多くの場合は検知できる**一方、**店舗 `registerParticipants` は `views/usersList` に依存した初回／再参加用の判定**があり、これのみではリンク済みを保証できない。そのため **`linked` も防衛的に拒否集合へ含める**。

### 22.4 状態別整理（一覧）

適用論理は **§22.3 の式が正**。表中の「未接続系」は `billLinkStatus` が `unlinked` または `pending_review` の読みである。

| 組み合わせのイメージ | 通常トーナメント参加 |
| --- | --- |
| `registered` + 未接続系（上記） | **拒否** |
| `seated` + 未接続系 | **拒否** |
| `busted` + §22.3 に該当する `billLinkStatus`（通常は unlinked） | **拒否**（§22.5） |
| `billLinkStatus: linked` で §22.3 が成立する場合 | **拒否** |
| `entryStatus: voided`（§22.3 の論理外になる） | **許可**（§22.6） |

### 22.5 `busted / unlinked` の拒否と通常リエントリーへの自動寄せ

`entryStatus: "busted"` であり **§22.3 が成立する場合** は通常参加を **拒否**する。

```text
初期仕様では、busted の置きバケ参加者を、bustAndReentry 等による通常参加者のフローや、その意味での「自動リエントリー」処理へ自動的に誘導・統合しない。
```

理由:

```text
通常参加／通常リエントリー／置きバケ復帰の境界が語彙として混線し、recordTournamentAction の entry / reentry の語義とも衝突し得るため。
```

### 22.6 `voided`

`entryStatus: "voided"` は **§22.3 で除外**される。

```text
voided は登録取消済みであり、通常参加阻止の自動判定には載せない。
```

カウンタの前提:

```text
voided 化にあたって、登録作成時に +1 した views/main.entries / playersIn / waitingCount 等が §17.3 に従い戻っていること。
```

### 22.7 `linkedUserId` 未設定

```text
linkedUserId が null の okibakeTemporaryEntry は、参加ユーザー ID と自動照合できないため §22.3 の拒否チェック対象としない。
temporaryDisplayName / memo 等のみでの自動マッチングはしない。
別トーナメントに未紐付けの置きバケがある事実のみを理由に、そのユーザーの通常参加時に警告を出しても断定できないので、義務とはしない。（注意表示しない方針）
```

### 22.8 置きバケ作成では `views/usersList` に書き込まない

```text
置きバケ作成時に scheduledTournaments/.../views/usersList に linkedUserId を載せない（users フィールドへの追加しない）。
理由: 現行実装では registerParticipants が usersList で初回と再参加の分岐の材料にしている。ここへ置きバケ状態を混入すると語義が崩れるため。

役割分担:
views/usersList — 現状の運用意味を維持（通常参加者登録側の一覧）
okibakeTemporaryEntries — 置きバケ参加者の正本
```

ただし Phase 4 以降、置きバケを伝票紐付けした後は、置きバケ由来で実ユーザーへ接続された参加者を通常表示導線に載せるため、`views/usersList.users.{userId}` に追加する場合がある。

そのため Phase 6 では、`views/usersList` に存在するユーザーを通常参加済みまたは実ユーザー接続済み参加者として扱い、通常参加 / 一括参加 / reentry の二重処理を防ぐ必要がある。

特に以下を確認・修正対象とする。

```text
- registerParticipants が usersList 既存ユーザーを reentry 扱いすることの妥当性
- registerForTournament が usersList 既存でも初回 entry 加算し得ること
- 置きバケ由来 linked user と通常参加の重複拒否
```

### 22.9 自動統合はしない

検知時、`okibakeTemporaryEntries` と **同一人物として自動マージしたり伝票自動接続しない**。**処理をサーバ側で中止**させ、店舗が **伝票紐付け**等の経路へ向かう運用とする。

### 22.10 共通 helper と実行順序

**`registerForTournament` / `registerParticipants` の共通 helper** で §22.3 を評価し、callable 側にロジックの二重記述を増やさない。関数名としての例:

```ts
assertNoOkibakeBlockingRegistration(tournamentId, userId);
```

チェック実行順序:

```text
次の処理よりも前で拒否評価を完了させる：
- views/main の entries / playersIn / waitingCount 等の増分
- tablesSeat/waiting への参加者としての作成・更新
- views/usersList のユーザー行更新
- recordTournamentAction および bills 側 tournament 親子の関連更新が走る処理
```

transactions との関係、`okibakeTemporaryEntries` のクエリインデックス要否などは実装フェーズが決める。

### 22.11 重複検知時の `errorKey`・UI・一括継続

#### 22.11.1 `errorKey`

```text
errorKey: TOURNAMENT_PARTICIPANT_CONFLICT_WITH_OKIBAKE

意味: 同一トーナメントにおいて参加しようとしている userId について §22.3 が成立しているため通常参加を中止した。
```

#### 22.11.2 LIFF 向け・店舗向け文言例

LIFF メッセージ例:

```text
このトーナメントは店舗側で登録済みです。
店舗スタッフに確認してください。
```

店舗側例:

```text
このユーザーは置きバケ登録済みです。
通常参加ではなく、置きバケの伝票紐付けを行ってください。
```

**現在の HTTP Callable 応答経路だけでは、`errorKey` を LIFF／Flutter が安定して読んでの文言出し分けとは限られない**。専用文言を確実に出す場合は **`errorKey` をクライアントが解釈できる形式で返す**仕組み変更が別途前提となりうる。**応答フィールド詳細や画面レイアウトは §25.2・§25.3** とする。

#### 22.11.3 一括登録時のユーザー単位失敗と継続

`registerParticipants` で複数 `userIds` を渡したとき、**一部のみが §22.3 にヒットした場合でも、該当 userId を失敗扱いのみとし、他ユーザー分の処理は継続**する。

## 24. 現時点の確定事項まとめ

現時点で確定している事項は以下である。

```text
- okibakeTemporaryEntries は scheduledTournaments/{tournamentId} 配下に置く
- ドキュメントIDは Firestore 自動IDとする
- okibakeEntryId は docId と同値を保持する
- temporaryDisplayName を採用する
- displayName / okibakeLabel は採用しない
- temporaryDisplayName は作成時に付与し、原則変更しない
- 実ユーザー指定ありでも temporaryDisplayName は付与する
- okibakeNextDisplayNumber は scheduledTournaments/{tournamentId} のフィールドに置く
- okibakeNextDisplayNumber は作成ごとに必ず +1 する
- 実ユーザー指定ありでも okibakeNextDisplayNumber は加算する
- 26件超過時は AA, AB のようにアルファベット連番を継続する
- entryStatus は registered / seated / busted / voided
- created は採用しない
- billLinkStatus は unlinked / linked / pending_review
- pending_review 化はトーナメント終了時に行う。通常終了（`endTournament`）と強制終了（`force_ended` を含む）のいずれも同様である（§15.2）。閉店処理だけをトリガとする要件ではない
- pending_review 化は `entryStatus != "voided"` かつ `billLinkStatus == "unlinked"` かつ `linkedUserId` 設定済みの置きバケのみを対象とする（§15.3）

- Flutter 側の seat 表示判定は現行方針を維持し、`userId` あり + `okibakeEntryId` ありは通常ユーザー席を優先する。ghost okibake は Functions 側の seat 整合性で解消し、Flutter 側で `okibakeEntryId` を無視する回避策は採用しない（§14.7.1）
- 置きバケ中の addon は `okibakeAddonRecords` 側に一時保持し、`bills` 接続時に反映する。bust は `entryStatus` 等とあわせ `okibakeTemporaryEntries` に保持し、`bills` 側へ bust 専用反映はしない（§14.8・§14.9）
- 伝票紐付け時には、置きバケ参加費として `bills/{billId}/tournaments/{templateId}` に entry 相当（entryCount / entryFeeIncl 等）を反映する。追加の tournament 投影があれば同様に記録する（§14.3・§14.10・§14.11）
- `bills` 接続時の `okibakeAddonRecords` 反映対象は `rolledBack == false` かつ `reflectedToBill == false` とし、`bills/{billId}/tournaments/{templateId}` へ反映し、反映後に各 record を `reflectedToBill` / `reflectedToBillAt` / `linkedBillId` で更新する（§14.8）
- bills 接続後に通常ユーザーとして発生した addon / bust は、既存 rollbackAction / undo 経路で許容する（§14.12）
- 誤った伝票への紐付けを現場が検知した場合、**会計前（bill.status が open または in_progress）** に限り §14.14 の置きバケ伝票紐付け専用 rollback（rollbackAction + 専用 undo service）で、`okibakeTemporaryEntries` の接続情報と誤った bill への置き由来投影を戻す。自動検知は行わない（§14.14）
- settling / settled の bill への誤紐付けの補正は伝票紐付け rollback の対象外とし、post-settlement adjustment / collection / refund に寄せる（§14.14）。接続後の rollback 全般の区別は §14.12
- `linkOkibakeTemporaryEntryToBill` 成功時は §14.14 に従い、`operationLog.payload` に rollback に必要な before / after および entry / addon / seat の反映差分を保存する（§14.14.13）
- `undoRegisterForTournament` / `undoRegisterParticipants` / 単体 undoAddon 等への単純流用は行わず、誤紐付け解除は専用 undo service とする（§14.14）
- 誤紐付け解除後、`okibakeTemporaryEntry` は `billLinkStatus: unlinked`、`linkedBillId` / `linkedAt` は null。`entryStatus` は原則維持する。`linkedUserId` / `linkedUserPokerName` は紐付け直前の状態へ戻す（事前に非 null なら維持、事前に null なら null に戻す）（§14.14）
- `seated` で伝票紐付けにより seat を実ユーザー表現へ変えた場合は、解除時に §14.7 接続前準拠へ戻し、`seatBefore` を payload に保存する（§14.14）
- 置きバケ addon / bust / entry の反映は `linkOkibakeTemporaryEntryToBill` の実行順序および transaction 範囲（§14.10・§14.11）に従い、`recordTournamentAction` 相当に寄せる（集約 Callable は §14.3、関係は §14.13）
- 置きバケ bust 時は対象 seat から置きバケ参加者を除去する
- 置きバケ bust 時に `views/main.playersBusted` を +1 する
- 置きバケ bust 時に entries / playersIn / waitingCount / addons は減算しない
- 置きバケ席移動・全員リシートに、通常席と異なる追加の業務制約は設けない（§19.1）
- bill 未接続の置きバケ席も、`entryStatus: "seated"` で seat に存在する場合は席移動・全員リシート対象とする。bills 接続済みの置きバケ由来席は `seatXXUserId` を優先し通常ユーザー席として扱い、`seatXXOkibakeEntryId` は追跡用として維持する（§19.1）
- `registered` 置きバケは全員リシート候補に含める（`busted` / `voided` / `pending_review` は seat 上移動対象外）（§19.1・§19.2）
- 置きバケ席の席移動は許可し、全員リシートにも置きバケを含める。対象抽出では `seatXXUserId` に加え `seatXXOkibakeEntryId` も確認する（§19.1・§19.2）
- bill 未接続の置きバケとして移動する場合は、移動元 seat をクリアし、移動先 seat に `seatXXOkibakeEntryId` / `seatXXPokerName` を保存する（§19.3）
- bills 接続済みの置きバケ由来席の seats 更新は、通常ユーザー席として既存処理に準拠する（§19.3）
- 置きバケ席移動時は `okibakeTemporaryEntries.assignedTableId` / `assignedSeatKey` を移動先へ更新する（§19.4）
- 置きバケ席移動時・全員リシート時は `seatedAt` を更新しない（§19.4）
- 置きバケ席移動・全員リシートでは、原則 entries / playersIn / seatedCount は変更しない。registered 置きバケを全員リシートで seated にした場合のみ waitingCount -1（§19.2・§19.5）
- 全員リシート rollback では okibakeReseatTargets に従い okibakeTemporaryEntries も復元。registered 復帰時は waitingCount +1（§18.5）
- まとめてAddon（bulkAddon）は seated + unlinked 置きバケを対象に含め、rollback は undoBulkAddon 1 回で通常分 + 置きバケ分を戻す（§16.10）
- getRankingData は linked + busted 元置きバケを read-time で bustedPlayers に補完する（§19.6）
- bust undo（通常 / 置きバケ）は bust 前参加状態への復帰が目的。元席占有時は TOURNAMENT_BUST_UNDO_SEAT_SELECTION_REQUIRED。成功時のみ playersBusted -1（§18.7・§18.8）
- 通常 bust undo 成功時は tablesSeat/busted.bustedUser.{userId} を削除する（§18.8）
- 待機者一覧からの Addon も rollback 対象とする（通常ユーザーは既存 addon undo、置きバケは §18.6、`bulk_addon` は §16.10）（§12.7・§18.1）
- 置きバケ addon rollback は `addonRecordId` 単位（§18.6）。`reflectedToBill: true` の単体 rollback は原則不可（§18.6・§14.14）
- entryStatus: "busted" の置きバケ一時参加者を voided にすることは初期仕様では原則不可とする
- okibakeAddonApplied / okibakeAddonAppliedAt / okibakeAddonAppliedByDeviceId は採用しない（`okibakeAddonRecords` による複数履歴を前提とするため）
- UI 実装は本書に載せた UI 仕様を一括でまとめて実装する前提ではなく、対象画面・対象導線ごとに順次実装する（§11.10）
```
