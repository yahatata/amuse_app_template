# 要判断事項（エージェントが決めず、ユーザー判断が必要な項目）

作成日: 2026-04-07

## D-01 `default-store` の扱い（最重要）

背景:

- 現在の一部処理は「本番で `default-store` を禁止」する前提で動いている
- 一方、運用方針は「1 Firebase Project = 1 店舗」であり、店舗識別子の多店舗前提は弱めたい

判断オプション:

1. **段階移行（推奨案）**  
   - 当面はバリデーションを残しつつ、`storeId` 未指定時は「プロジェクト既定 storeId」を補完する  
   - `default-store` 文字列依存を段階的に削る
2. **即時単一店舗化**  
   - `default-store` 依存ロジックと厳格チェックを広範囲で一気に外す
3. **現状維持**  
   - 全 producer / scheduler / data に明示 storeId を入れる運用で継続

比較観点:

- 実装コスト
- 影響範囲
- リリース前の安全性
- 将来の新規店舗導入時の再利用性

決定:

- `1（段階移行）` を採用済み
- ただし「復旧後に排除フェーズを必ず実施する」ことを条件とする
- 最終到達点は、`default-store` 依存の排除

## D-02 Task 実行用 SA の統一方針

背景:

- 実環境で `tasks-invoker@...` は存在
- 一部コード/設定は `openclose-tasks-invoker@...` を参照しており、環境差で `NOT_FOUND` になりうる

判断オプション:

1. **既存 SA へ統一（推奨案）**  
   - `tasks-invoker@...` に寄せる
2. **新 SA へ統一**  
   - `openclose-tasks-invoker@...` を作成し全設定を寄せる
3. **用途別に複数 SA を維持**  
   - 命名規約と権限管理手順を別途厳格化

比較観点:

- 既存運用との整合
- 新規プロジェクト導入時の手順の簡単さ
- 権限の最小化と監査性

決定:

- `1（既存 SA へ統一）` を採用済み
- 統一先は `tasks-invoker@...`

## D-03 既存失敗タスクの削除範囲

背景:

- 壊れたタスクを再利用するより削除したほうが安全という方針

判断オプション:

1. **ピンポイント削除（推奨案）**  
   - `business-date-assessment-queue` の malformed task のみ削除
2. **同型失敗の一括削除**  
   - 400/invalid payload が明確なものを複数 queue で削除
3. **全 pending/retry を全削除**  
   - 検証が早いが、必要タスクを誤って削除するリスクが高い

比較観点:

- 安全性
- 復旧スピード
- 誤削除リスク

決定:

- `1（ピンポイント削除）` を採用済み

## D-04 `us-central1` 残存フローの扱い

背景:

- 既に `asia-northeast1` 化済みの関数群と、`us-central1` 残存の処理が混在している

判断オプション:

1. **段階移行（推奨案）**  
   - 今回は障害復旧を優先し、リージョン統一は別フェーズで実施
2. **同時移行**  
   - 今回の修正と同時に `us-central1` 残存を移す
3. **恒久混在**  
   - 明示的に mixed region 方針として運用資料化する

比較観点:

- 復旧優先度
- 本番切替前のリスク
- 運用負荷

決定:

- `1（段階移行）` を採用済み
- かつ、今回修正の作業フェーズ内に移行フェーズを必ず含める

## D-05 検証時の副作用許容範囲

背景:

- タスク実行確認は副作用を伴う（データ書き込み、状態更新）

判断オプション:

1. **副作用を制御した限定検証（推奨案）**  
   - テスト用データに限定し、対象フローを決めて実行
2. **本番相当フル検証**  
   - 網羅性は高いが、不要データ生成が増える
3. **ログ確認中心の軽量検証**  
   - 手間は小さいが、実データ整合の保証が弱い

比較観点:

- 網羅性
- 検証コスト
- データ汚染リスク

決定:

- `2（本番相当フル検証）` を採用済み
