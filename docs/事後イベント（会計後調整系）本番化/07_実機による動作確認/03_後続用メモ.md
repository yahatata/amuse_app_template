- シナリオ: `10-C` 会計開始後に「会計開始前に戻る」を押下

  - 仕様上の意図と UX 上の期待を照合し、保持 / クリアのどちらが正しいか判断する

### 2026-05-11 / Codex
- 対象ファイル: `10_通常会計と親サマリとbaseline確認.md`
- シナリオ: `10-D` 通常 settle 完了後の支払方法表示 / 保存値確認
- 現象:
  - `categoryBreakdown.sideGameChips = 5000`
  - `sideGameChips[]` では `purchase.qty = 1000`, `purchase.amountIncl = 5000`
  - 一方で `paymentTotals.sideGameChip = 1000` と保存されていた
  - 画面表示も「ゲームチップ1000枚と現金14200円を請求」のように見え、金額軸と枚数軸が混在して見える
- 想定原因:
  - `paymentTotals.sideGameChip` の単位設計が円額ではなく chip 枚数寄りになっている可能性
  - あるいは保存値自体は意図どおりでも、表示面が単位を適切に実装できておらず、ユーザーに誤解を与えている可能性
- 必要対応:
  - `paymentTotals.sideGameChip` の仕様上の単位を確認する
  - DB 保存値と UI 表示文言が同じ単位で解釈されているか確認する
  - 必要なら chip 系支払表示に「枚 / 円」の明示を追加する
- 優先度: 中
- 関連ファイル:

### 2026-05-11 / Codex
- 対象ファイル: `10_通常会計と親サマリとbaseline確認.md`
- シナリオ: `10-C` cancel 後および `10-D` settle 後の `draftAccountingInput` 残存確認
- 現象:
  - cancel 後も `draftAccountingInput.paymentMethodsByAmount` が残っていた
  - さらに通常 settle 完了後も `draftAccountingInput` が parent に残っていた
- 想定原因:
  - current-scope の意図として、再会計や確認用に直近の入力内容を parent に保持している可能性
  - 一方で、本来は cancel 時または settle 時にクリアすべき入力キャッシュが残っている可能性もある
- 必要対応:
  - `draftAccountingInput` の保持期間を仕様として確認する
  - 「再利用用の保持」なのか「完了後は削除 / null 化すべき」なのかを UI/UX 観点も含めて判断する
  - 後続シナリオで再会計開始時の初期表示がこの値をどう使うか確認する
- 優先度: 中
- 関連ファイル:
  - `docs/事後イベント（会計後調整系）本番化/07_実機による動作確認/10_通常会計と親サマリとbaseline確認.md`

### 2026-05-11 / Codex
- 対象ファイル: `10_通常会計と親サマリとbaseline確認.md`
- シナリオ: `10-D` 通常 settle 完了後の root 直下互換 field 確認
- 現象:
  - parent root 直下に旧互換 field と見られる値が残っていた
  - 確認できた主な field:
    - `amounts`
    - `categoryBreakdown`
    - `paymentTotals`
    - `paymentsSummary`
    - `postEvents`
    - `itemsSnapshot`
    - `tournamentsSnapshot`
- 想定原因:
  - 旧画面や旧ロジックとの互換維持のため dual-write を残している可能性
  - ただし、SoT と参照先の整理が不十分なまま残っていると、今後どの field を信じるべきか分かりづらくなる可能性がある
- 必要対応:
  - current-scope で互換維持のために残す field と、後続で削除対象にする field を整理する
  - UI / callable / trigger / analytics がどの root 互換 field をまだ参照しているか棚卸しする
  - 新スキーマへの切替完了後に削除計画を作る
- 優先度: 中
