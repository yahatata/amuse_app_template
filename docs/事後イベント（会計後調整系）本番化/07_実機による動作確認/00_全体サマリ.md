# 00_全体サマリ

## 1. このファイルの役割

このファイルは、実機確認フェーズ全体の要約と、確認単位の分割理由をまとめる。

## 2. 実機確認の目的

今回の大規模改修では、以下が広く変更されている。

- bills 親 summary
- settlementCycles / baselineSnapshot
- adjustments / cashActions
- reopen と再会計
- `要対応の会計` UI
- analyticsMonthly 反映

そのため、単一の画面確認だけでは不十分であり、**UI・Callable・Firestore 状態・analytics 結果を横断して確認する必要がある**。

## 3. なぜ Step 単位ではなく再分割するのか

`05_changeSpecと実装` の Step01〜07 は実装責務としては適切だが、実際の動作確認では次の問題がある。

- Step03〜05 は UI 導線と Callable 直接実行が混在する
- Step06 は Step04 / Step05 の結果状態がないと十分に確認できない
- Step07 は通常会計・事後調整・reopen の全てに依存する

したがって、実機確認は **オペレーション順** と **状態遷移のまとまり** で再構成する。

## 4. 実機確認の単位

### 4.1 通常会計と親サマリと baseline
- bill 作成
- 会計開始 / 取消
- 通常 settle
- `settlementCycles/1`
- `baselineSnapshot/snapshot`

### 4.2 会計後調整と即時精算
- `terminalHome` の `会計後操作`
- 会計後調整作成
- 即時返金
- 即時徴収
- `adjustments` と immediate `cashActions`

### 4.3 要対応一覧と後続徴収返金
- `要対応の会計` メニュー
- `日付ごと / ユーザー別`
- `すべて / 未会計 / 追加徴収 / 要返金`
- 後続 cashAction の実行

### 4.4 reopen と再会計
- `terminalHome` の `会計後操作`
- reopen
- old cycle の close
- new cycle の open
- 再会計後の baseline 再作成

### 4.5 analyticsMonthly
- settle 時反映
- adjustment 反映
- collection / refund 反映
- reopen rollback
