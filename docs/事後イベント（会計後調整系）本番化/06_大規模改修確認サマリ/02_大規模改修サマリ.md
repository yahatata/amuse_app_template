# 02_大規模改修サマリ

## 1. 改修目的

## 1.1 何を解決するための改修か

今回の改修は、会計後に発生する差額調整を、

- `bills` 親 doc の現在状態
- `settlementCycles` による確定版の管理
- `adjustments` による会計後差分
- `cashActions` による返金 / 追加徴収履歴
- `analyticsMonthly` への段階的反映

として整理し、旧 `events` 中心の曖昧な運用から、より追跡しやすい構造へ移すことを目的としている。

## 1.2 旧実装の課題

旧実装の主な課題は次のとおり。

- 会計確定版と会計後差分の責務が分離しきれていない
- 返金 / 追加徴収 / reopen の扱いが分散しやすい
- UI 上で「要対応の会計」を一元的に扱いづらい
- `analyticsMonthly` への反映ルールが、通常 settle と会計後差分で分断されやすい
- 今後の税務・会計 read model 拡張に向けて、日付軸と履歴軸を分ける土台が弱い

## 1.3 新実装で実現したこと

新実装で実現したことは次のとおり。

### bills / settlement model

- `bills` 親 doc を current summary として整理
- `settlementCycles/{cycleNo}` を導入
- `baselineSnapshot/snapshot` を 1 doc full snapshot として保存

### post-settlement processing

- `adjustments` に 4 パターンの会計後差分を保存
- `cashActions` に later refund / collection を保存
- `reopen` による cycle 切替の runtime を追加

### UI

- `要対応の会計` 画面を追加
- `未会計 / 追加徴収 / 要返金` を 1 画面で扱えるように整理
- ユーザー別 / 日付ごと表示、件数内訳、primary action 導線を追加

### analytics

- adjustment / cashAction / reopen rollback の `analyticsMonthly` 反映を追加
- settle marker を cycle 単位に拡張
- reopen 後 resettle に備えた rollback-and-resettle 戦略を導入

## 2. 全体像

今回の大規模改修は、実質的には次の 7 ステップで構成されている。

1. bills 親 doc と current state 整理
2. `settlementCycles` と `baselineSnapshot` 導入
3. `adjustments` 導入
4. `cashActions` 導入
5. `reopen` / 再会計導入
6. `要対応の会計` UI 導入
7. `analyticsMonthly` 反映導入

## 3. 改修後の構造イメージ

```text
bills/{billId}
├─ 親 doc（current state summary）
├─ settlementCycles/{cycleNo}
│  ├─ cycle 親 doc
│  ├─ baselineSnapshot/snapshot
│  ├─ adjustments/{adjustmentId}
│  └─ cashActions/{cashActionId}
└─ 既存 live subcollections（items / extras / tournaments / sideGameChips / payments）
```

## 4. まとめ

今回の改修は、単なる機能追加ではなく、**会計後イベントの保存モデル・UI・analytics をまとめて新構造へ寄せる再設計**である。

そのため、現在の状態を一言で表すなら次になる。

**「旧経路を即廃止せず互換を残しつつ、新しい settlement / adjustment / cashAction / reopen / analytics の本筋を追加した改修」**
