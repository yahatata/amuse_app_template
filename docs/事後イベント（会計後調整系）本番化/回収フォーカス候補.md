# 事後イベント（会計後調整系）本番化 — 回収フォーカス候補

会計後調整まわりの本番化に向け、**現状コードと照らしたうえで回収・改修のフォーカス候補**を整理したものです。詳細な根拠説明はチャットで展開した内容と対応します。実装が変わったら本ファイルの更新が必要です。

関連: [初期検討事項まとめ.md](./初期検討事項まとめ.md)

---

## F1. 未会計タブ「修正」— フード／ドリンクが表示されず適切に修正できない

### 現状（コード上）

- `AccountingEditDialog` は `widget.bill['items']`（親ドキュメントの配列）から初期表示する（`lib/Accounting/accountingEditDialog.dart`）。
- `_loadActiveBills` が組み立てる一覧用マップに **`items` が含まれない**（`lib/Accounting/accountingPage.dart`）。
- 注文行は **`bills/{billId}/items` サブコレクション**に保存される新スキーム（`appendItem` 等）。

### 問題・懸念

- 画面上は注文のある伝票でも修正ダイアログでは **フード／ドリンクが空**に見える。
- 空状態のまま保存すると、意図しない内容送信のリスク。**UI のデータ源泉がサブコレクションと一致していない**（旧 todaysBills 前提の残骸）。

### 回収の方向性（例）

- 修正前に **サブコレクション（または正規 API）から明細を読み込む**、または Callable 側で **現状スナップショットを返してダイアログに載せる**。

## F2. 事後イベント UI を会計管理「会計完了」タブへ寄せる（タブ再設計）

### 現状（コード上）

- 事後イベント操作は主に `PostAccountingAdjustmentsPage`（ターミナル「会計後調整（テスト）」等）。
- `AccountingPage` の会計完了タブは **事後イベント操作と未接続**。

### 問題・懸念

- 導線が二重になり、**「会計は会計管理から」**という運用とずれる。
- F4・F15 とセットで、**クエリ条件・表示項目・閉店中挙動**をまとめて設計する必要がある。

### 回収の方向性（例）

- 会計完了タブで **返金・調整・再開・（必要なら）キャンセル**まで完結する UI に再設計し、テスト導線を本番用に置き換える。

## F3. 事後イベント時の支払内訳・現金／ポイントとダッシュボード蓄積

### 現状（コード上）

- 返金イベント: `amountIncl`・`reason`・`method`（文字列）程度。`balanceDueIncl` / `postEvents` はトリガで更新。
- 調整イベント: `sign`・金額・`reason`。**`paymentsSummary.byMethod` を動かす処理はない**。
- ダッシュボード向けは確定時 `billsOnSettle` → `enqueueSettlement`（設定次第）だが、**事後イベント後の Analytics 連携は別途 TODO**（F9）。

### 問題・懸念

- 「何で払ったか」「返金を現金で返したのかポイントで返したのか」が **データとして追いにくい**。
- **ダッシュボード用に正しく積み上がる**状態にはなっていない可能性が高い（F9 と一体）。

### 回収の方向性（例）

- 返金／追加徴収を **byMethod 配分**や **別イベント／別テーブル**で表現するかを仕様化し、集計パイプラインと接続する。

## F4. 返金・追加徴収後に「会計完了」タブから状況が見えない

### 現状（コード上）

- `_loadSettledBills` は **`status == 'settled'` のみ**取得。`partially_refunded` / `refunded` は **一覧から消える**。
- カード内訳は `bill['items']`・`bill['sideGameChip']` 等の **親の旧配列前提**で、一覧マップに載っていない項目が多い（F1・F7 と同源）。
- **`postEvents`（返金・調整・純売上）を会計完了タブで表示していない**。

### 問題・懸念

- 返金後は **「消えた」ように見える**。追加徴収しても **調整の事実がカードから読み取りにくい**。

### 回収の方向性（例）

- 取得条件を **`settled` + 返金系ステータス**に拡張し、カードに **`postEvents`・残高**を必須表示する。

---

## F5. 追加徴収と「実際に受け取った記録」／未収との切り分け

### 現状（コード上）

- 調整は `totalAdjustmentsIncl`・`netSalesIncl`・`balanceDueIncl` の関係で表現。**`paidTotalIncl` を増やす「入金記録」はない**。

### 問題・懸念

- **その場で徴収した**のと **未収のまま帳簿だけ増やす**のを区別できない。運用・監査上の論点。

### 回収の方向性（例）

- 操作を **二系統**に分ける、または **`payments` 追記＋調整イベント連動**などモデル拡張を検討する。

---

## F6. 追加徴収後の減額が「不安定」に感じられる件

### 現状（コード上）

- `postEventAdjustment` は **`netSalesIncl < 0`** および **`balanceDueIncl < 0`** を拒否（`lib/domains/bills/repos/postEventAdjustment.ts`）。
- 上限は **「直前の追加額」単体ではなく**、合計・既払い・返金・既調整の組み合わせで決まる。

### 問題・懸念

- 利用者には **「追加した分だけ戻せない」**と誤解されやすい。**理由が画面上見えない**。

### 回収の方向性（例）

- 許容範囲を仕様として文書化し、UI で **不可理由（残高・純売上の下限）**を表示する。

---

## F7. 会計明細確認でサイドゲームチップが 0／空に見える

### 現状（コード上）

- カード内訳 `_buildBillBreakdown` は **`bill['sideGameChip']` 配列と `chip['price']`** 前提（`lib/Accounting/accountingPage.dart`）。一覧マップにその配列は **載っていない**。
- 実データはサブコレクションの **`amountIncl`** 等。別経路のカテゴリ内訳ダイアログは `purchase` の `amountIncl` で集計しており、**画面ごとにデータ源が不一致**。

### 問題・懸念

- システム上はチップがあるのに **内訳が 0 や非表示**になりやすい。

### 回収の方向性（例）

- 内訳表示を **常にサブコレクションまたは親の正規サマリ**に統一する（`_fetchSideGameChipPurchaseSummary` や `sideGameChipsSummary` の活用）。

---

## F8. 「会計前に戻す」後の孤児伝票と analytics 未減額

### 現状（コード上）

- `postEventReopen` 適用後、`status` は **`in_progress`**（`billsEventsOnCreate`）。
- `_loadActiveBills` は **`open` と `settling` のみ**で **`in_progress` が含まれない** → **会計管理未会計タブに出ない**。
- `billsOnSettle` は **`settled` 遷移時の加算**のみ。**`in_progress` への戻しで集計を減らす処理はない**。

### 問題・懸念

- **触れない伝票**が残る。**月次等の集計が確定時のまま**残るリスク。

### 回収の方向性（例）

- クエリに `in_progress` を含める、または再開時に **`open` へ正規化**する方針を決める。集計は **差分イベント or ロールバック**を設計する（F9 と連動）。

## F11. G3 — 営業日 AMBIGUOUS と `selectedBusinessDateKey`

### 現状（コード上）

- `postEvent*` ヘルパは `selectedBusinessDateKey` を解釈できる。
- **`processRefund` / `updateAccounting` の Zod に含まれず**、Callable からヘルパへ **未伝播**。
- Flutter は一部ダイアログで `selectedBusinessDateKey` を送っている。

### 問題・懸念

- 曖昧時間帯で **再試行してもサーバに届かず失敗し続ける**可能性。

### 回収の方向性（例）

- 両 Callable のスキーマ拡張と **ヘルパへの引き渡し**を実装する。

## F15. 閉店中会計管理が使えない（事後イベントと相性）

### 現状（コード上）

- `AccountingPage`: `currentBusinessDay` が **`running` でない**と本文全体が **「閉店中」**のみ（`lib/Accounting/accountingPage.dart`）。
- ターミナルホーム: 強警告時 **店舗管理端末がゲートで全面ブロック**（`store_strong_warning_ui.dart`）。

### 問題・懸念

- **閉店後に起きやすい返金・調整**が、会計管理から **実行できない**。

### 回収の方向性（例）

- **閉店中でも表示するサブ領域**（会計完了＋事後のみ等）を仕様化し、`AccountingPage` のガードを **機能別に分割**する。ゲートとの関係も整理する。
