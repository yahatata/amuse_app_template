# 事後イベント（会計後調整系）本番化 — 初期検討事項まとめ

本ファイルは、テンプレアプリにおける **会計確定後の返金・調整・キャンセル・再開**（いわゆる事後イベント／会計後調整）について、現時点の実装状況・ギャップ・本番化前に決めるべき論点を漏れなく整理したものです。コード調査時点のスナップショットであり、実装が変わった場合は本文の更新が必要です。

---

## 1. 背景・スコープ

- 1 リポジトリから複数店舗アプリをリリースするテンプレート前提で、会計周りは **新 `bills` スキーマ** と **`/bills/{billId}/events`** による事後イベント記録（P1-07 系）が中心。
- 「会計データの変更」は、明細の直接編集というより **`postEvents` / `paymentsSummary` を事後イベントで差し替える** 形が現状の実装方針に沿う。
- 「返金の旨の追記」に相当するのは、現状 **返金・調整イベントに紐づく `reason` テキスト** を `/events` に保存する形（金額ゼロの「注記のみ」専用 API は別途存在しない）。

---

## 2. 現状実装されている仕様（バックエンド）

### 2.1 事後イベントの記録と反映

- **書き込み**: `bills/{billId}/events/{eventId}` にイベントを作成。`eventId` は **`idempotencyKey`** と同一（冪等性の鍵）。
- **種別**（`type`）: `refund` / `adjustment` / `cancel` / `reopen`。
- **親伝票の更新**: Firestore トリガ `billsEventsOnCreate`（`bills/{billId}/events/{eventId}` の onCreate）が、`appliedAt` 未設定のイベントを適用し、概ね以下を更新する。
  - `postEvents.totalRefundedIncl` / `totalAdjustmentsIncl` / `netSalesIncl`
  - `paymentsSummary.balanceDueIncl`
  - 必要に応じて `status`（例: `partially_refunded` / `refunded` / `voided` / `in_progress`）
- **イベント doc に保存される情報の例**
  - 調整: `reason`（任意）、`adjustment.sign` / `amountIncl`
  - 返金: `reason`（任意）、`refund.amountIncl` / `method`（任意）
  - `originBusinessDate` / `eventBusinessDate`（営業日・計上日まわり）

### 2.2 Callable と内部ヘルパの対応

| Callable | 内部で利用するヘルパ | 備考 |
|----------|----------------------|------|
| `processRefund` | `postEventRefund` | `billId`, `idempotencyKey`, `eventPayload: { amountIncl, reason?, method? }` |
| `updateAccounting` | `postEventAdjustment` / `postEventCancel` / `postEventReopen` | **返金は含まない**（返金は `processRefund` のみ） |

### 2.3 権限

- 上記 Callable はいずれも、**`role === 'admin'`** またはデバイス **`options.accounting`** を満たす端末からの呼び出しを想定（実装は `getCallerDeviceByUid` 等で確認）。

### 2.4 ステータス・業務ルール（コード上の制約）

- **返金・調整**（`postEventRefund` / `postEventAdjustment`）: 親伝票の `status` が **`settled` / `partially_refunded` / `refunded`** のときのみ許可。
- **会計後キャンセル**（`postEventCancel`）: 仕様上 **未払い・未返金の `settled`** に限定（`paidTotalIncl` や `totalRefundedIncl` があれば不可）。
- **再開**（`postEventReopen`）: **`settled` のみ**許可。部分返金済みなど **`settled` 以外では再開不可**。
- **ユーザー残高への返還**: P1-07 コメントどおり **`postEventRefund` のスコープ外**（別途必要なら未実装／別 Callable 等の検討対象）。

### 2.5 その他 API

- **`getRefundHistory`**: Callable は存在するが、現状 **空の履歴を返すスタブ**（TODO で本実装が未着手）。

## 3. 現状実装されている仕様（Flutter）

### 3.1 会計後調整専用画面

- **`PostAccountingAdjustmentsPage`**
  - `storeMeta/currentBusinessDay` を参照して初期表示日付を決定し、`bills` を **`businessDate`** と **`status`** でクエリして一覧表示。
  - 伝票カードから **返金 / 減額 / 追加徴収 / 会計前に戻す（再開）** を起動可能。
  - 返金は **`processRefund`**、調整・キャンセル・再開は **`updateAccounting`** を呼ぶダイアログ群と接続済み。
  - Firestore 複合インデックス都合で **`orderBy` がコメントアウト**され、**クライアント側ソート**の暫定対応あり（インデックス整備後の復帰が TODO）。

### 3.2 導線

- **ターミナルホーム**からは、現状 **`会計後調整（テスト）`** というラベルで `PostAccountingAdjustmentsPage` に遷移する定義があり、**本番メニューとしての名称・配置は未確定**。

### 3.3 会計管理画面からの返金ダイアログ（旧実装の残骸）

- **`accountingPage.dart`** から開く **`RefundProcessingDialog`** は、**旧ペイロード**（`idempotencyKey` なし、`refundAmount` / `refundReason` 等）で `processRefund` を呼ぶ可能性があり、**現行 Cloud Functions の Zod スキーマと不整合**になる。社内ドキュメント（ローディング／現状パターン整理系）でも別タスクとして言及あり。
- 会計後調整用の **`PostAccountingRefundDialog`** は新スキーマに沿った呼び出しを行う実装になっている。

### 3.4 会計後キャンセル UI

- **`PostAccountingCancelDialog`** および **`_canCancel`** は実装されているが、**伝票一覧の操作行にキャンセルボタンがなく**、**テスト用タブ経由**でしか起動しにくい状態（本番運用フローではギャップ）。

## 5. 閉店中・営業状態と会計 UI（追加の問題点・検討事項）

### 5.1 要望（プロダクト観点）

- 基本的に **会計周りの操作は会計管理メニュー（ターミナルホームから遷移）上**で完結させたい。
- **支払い済み系**（会計完了後の調整・返金など）は、**閉店中であっても**運用上発生しうるため、**会計管理経路で実行できる方が適切**。
- よって現状の「閉店中は会計管理が使えない」に近い挙動は **やめたい**。
- 事後イベントは **閉店中に実施する可能性が高い**ため、**閉店中に「何を表示し、どの処理まで許可するか」** を設計として再定義する必要がある。

### 5.2 現状コード上の挙動（根拠）

1. **`AccountingPage`（会計管理）**  
   - `storeMeta/currentBusinessDay` を監視し、**`status != 'running'` または `currentBusinessDateKey == null` のとき、本文全体を「閉店中」表示にし、タブ（未会計／会計完了）もデータ読込も行わない**。  
   - 参照: `lib/Accounting/accountingPage.dart`（`StreamBuilder` 内の `status` / `currentBusinessDateKey` 判定）。
   - 結果として、**閉店中は会計管理画面から会計完了タブ経由の操作も含め、通常フローが利用不能**。

2. **ターミナルホームの強警告オーバーレイ**  
   - `StoreStrongWarningOverlay` により、**店舗管理権限端末**では強警告発生時に **`StrongWarningGate` が子全体を覆い、メニュー操作自体がブロック**される場合がある。  
   - 参照: `lib/Home/terminalHomePage.dart`、`lib/Utils/store_strong_warning_ui.dart`。  
   - 「閉店中」とは別軸だが、**会計管理メニューに到達できない**要因として本番化検討に含める。

### 5.3 検討すべき論点（本ファイルでのインプット用）

- **閉店中の定義**と画面の対応  
  - `currentBusinessDay.status !== 'running'` のみを対象にするか、強警告ゲートも含めて整理するか。
- **会計管理画面の責務分割**  
  - **営業中専用**: 未会計一覧・会計進行・確定など。  
  - **営業状態に依存しない**: 会計完了済み伝票の **事後イベント（返金・調整・必要ならキャンセル／再開）**、会計履歴など。  
  - 閉店中は後者のみ表示・操作可能にする、といった **UI 分離**が現実的か。
- **データの営業日**  
  - 事後イベントは **`bill.businessDate`**（売上帰属）と **`eventBusinessDate`**（計上日）が絡む。閉店中 UI では **どの日付をデフォルト表示するか**（当日カレンダー日 vs 最終営業日 vs ユーザー選択）を決める必要がある。  
  - `PostAccountingAdjustmentsPage` は既に日付選択と `businessDate` クエリを持つため、**会計管理配下に統合する場合の UX 一貫性**も検討対象。
- **権限・監査**  
  - 閉店中に返金・調整を許す場合、**誰が・どの端末から**実行可能とするか（`accounting` オプションのみか、店舗管理と分離するか）。
- **バックエンドとの整合**  
  - 閉店中でも Callable は通る設計になっているが、**AMBIGUOUS 営業日**（G3）が未解決だと、深夜跨ぎ等で **事後イベントが失敗しうる**。UI 側で許可範囲を広げるほど **G3 の優先度が上がる**。

### 5.4 推奨される次ステップ（ドキュメント上の提案）

- 上記 5.3 を踏まえ、**「閉店中に許可する操作一覧」** を 1 枚（表形式）で ToBe 定義する。  
- 実装方針案の例（要合意）:  
  - `AccountingPage` を **営業状態でガードする範囲を「未会計・進行中フロー」に限定**し、**会計完了後の調整は別タブまたは同一画面のサブセクションで常時表示**する。  
  - または **会計管理メニューから `PostAccountingAdjustmentsPage` 相当へ常時遷移可能**にし、会計管理トップは営業中のみ従来 UI、など。
