## 1. このファイルの役割

本ファイルは、事後イベントをどの画面導線に統合するか、閉店中や強警告中にどこまで操作を許可するか、旧ダイアログをどう整理するかを決めるための作業ファイルである。

ここが決まらないまま実装すると、利用者が `どこから入ればよいか分からない`, `同じようなボタンが複数ある`, `閉店中だけできない` といった混乱が残る。

## 2. この項目の進め方

1. Codex が、画面導線の問題を `どの画面`, `どのボタン`, `どの権限制御` に分けて chat で整理する
2. 各問題について、技術的に整理できるものと、運用判断が必要なものを分ける
3. 旧導線を残すか廃止するか、閉店中の許可範囲をどうするかを会話で確定する
4. 決定事項をこのファイルに蓄積し、Step4 で画面遷移、権限制御、非表示条件に落とせる状態にする

## 4. chat で必ず整理する内容

各論点について、chat では次の順で出力する。

1. 現状:
   - どの画面から入れるか
   - どのボタンがあるか
   - 誰に見えてしまうか、または見えないか
2. 問題:
   - 利用者が迷う点
   - 権限や運用の危険
   - 画面の二重化による保守リスク
3. 判断主体:
   - Codex が整理してよい UI 設計か
   - ユーザーが決めるべき運用ルールか
4. 改善案:
   - 推奨導線
   - 廃止対象
   - 閉店中 / 強警告中の扱い
5. 決定後の出口:
   - Step4 で画面遷移、ボタン配置、権限制御、非表示条件を書ける状態にする

## 5. 決定記録

### 5.1 決定済み

- `I3-01`: post-settlement の本番導線は `terminalHome` から入る `要対応の会計` に集約する
- `I3-01`: `要対応の会計` では、閉店持ち越し未会計と会計後要対応を同じ画面で扱う
- `I3-02`: `要対応の会計` の表示軸は `日付ごと / ユーザー別` とする
- `I3-02`: `要対応の会計` のカテゴリフィルタは `すべて / 未会計 / 追加徴収 / 要返金` とし、デフォルトは `すべて` とする
- `I3-02`: 日付ごとでは、対象日付に属する要対応 bills 一覧を表示する
- `I3-02`: ユーザー別では、該当 bill を持つユーザー一覧を表示する
- `I3-02`: ユーザーカードには少なくとも `総件数`, `未会計 x件`, `追加徴収 x件`, `要返金 x件` を表示する
- `I3-02`: 画面ラベルは `未会計 / 追加徴収 / 要返金` を使う
- `I3-03`: 閉店中でも `AccountingPage` には入れるようにし、閉店中は会計後に必要な操作だけを使える制限モードとする
- `I3-03`: 閉店中に許可する操作は `refund`, `adjustment`, `post-settlement collection` とし、`reopen` は禁止する
- `I3-04`: 強警告中は会計後調整の例外許可を行わず、まず `閉店処理へ` または `営業継続` の判断を先に求める
- `I3-04`: 強警告が出ている場合は閉店中許可ルールよりも強警告ルールを優先し、会計後管理も含めて例外を設けない
- `I3-05`: 会計完了済み bill に対して旧 `AccountingEditDialog` / `AccountingCancelDialog` / `RefundProcessingDialog` を本番導線に残さない
- `I3-05`: 会計後操作は `要対応の会計` -> 対象詳細 -> post-settlement 系 UI に統一する
- `I3-05`: 旧テストタブ群は本番導線完成後は撤去対象として扱う
- `I3-06`: `reopen` 後の status は `open` とし、`in_progress` は採用しない
- `I3-06`: `reopen` 後の bill は会計後要対応一覧ではなく、通常の未会計 bill 導線へ戻す
- `I3-06`: `voided` を current-scope の標準 UI 状態としては採用しない

## 6. Step4 に進める条件

- `terminalHome` からの入口名称が `要対応の会計` で確定している
- `要対応の会計` の表示軸とフィルタが決まっている
- カードから通常会計再開 / 追加徴収 / 返金の各導線へ遷移できる設計が決まっている
- 閉店中にできる操作とできない操作が決まっている
- 強警告中の例外有無が決まっている
- 本番メニューとページ自身の両方で権限制御を行う方針が決まっている
- 旧ダイアログの扱いが決まっている
- `reopen` 後を `open` に戻して通常未会計導線へ返す方針が決まっている
