## 1. このファイルの役割

本ファイルは、一覧取得の最終クエリ、必要な Firestore インデックス、N+1 解消方針、ページング有無など、リリース前に性能面で固めるべき事項を決めるための作業ファイルである。

I5 は後ろの工程だが、Step3 の段階で「何を固定しないとリリースで詰まるか」を先に明確にしておく。

## 2. この項目の進め方

1. Codex が、一覧取得の負荷要因を `query`, `index`, `追加 read`, `件数増加時のふるまい` に分けて整理する
2. 画面要件に依存するものは I2 / I3 の決定とつなげて整理する
3. 技術的に妥当な性能対策は Codex が推奨案を提示する
4. 操作性や運用件数に関わるものは、必要に応じてユーザーと相談して決める
5. 決定事項を本ファイルに追記し、Step4 と Step5 で query / index / test の仕様に落とせる状態にする

## 4. chat で必ず整理する内容

各論点について、chat では次の内容を整理する。

1. 現状:
   - どの query が走っているか
   - どこで余計な read が増えているか
2. 問題:
   - 遅くなる原因は何か
   - インデックス不足で止まる可能性は何か
3. 判断主体:
   - Codex が技術設計として決めてよいか
   - ユーザーが運用条件を決める必要があるか
4. 改善案:
   - 最終 query
   - 必要 index
   - N+1 解消方法
   - limit / ページング方針
5. 決定後の出口:
   - Step4 で性能要件を文章化し、Step5 でテスト項目と index 定義に落とせる状態にする

## 5. 決定記録

### 5.1 決定済み

- `I5-01`: 本番の一覧性能要件は旧 `PostAccountingAdjustmentsPage` ではなく、`terminalHome` から入る「要対応の会計」を基準に定義する
- `I5-01`: 「要対応の会計」一覧は `日付ごと / ユーザー別` の表示軸と、`すべて / 未会計 / 追加徴収 / 要返金` のフィルタを前提にする
- `I5-01`: current-scope の対象判定は old status 群ではなく、親 doc の `status`, `closeSummary.unresolved`, `postSettlementState.requiredActionType` から導出する
- `I5-01`: 「要対応の会計」一覧の標準ソートキーは `updatedAt DESC` とし、最近変更された bill が先頭に来る並びを正とする
- `I5-01`: `ops.accountingCompletedAt DESC` は current-scope の主ソートキーにはしない
- `I5-02`: `firestore.indexes.json` 上の本番必須複合インデックスは、old status 群ではなく `closeSummary.unresolved` と `postSettlementState.requiredActionType` を使う query 前提で整理する
- `I5-02`: current-scope では、持ち越し未会計と会計後要対応を別 query で取得し UI 側でマージすることを許容する
- `I5-02`: Step5 では、既存インデックスを「本番必須」「残してよいが主導線依存ではないもの」に分けて整理する
- `I5-03`: 一覧カードの sideGame チップ表示は親 doc の summary fields を正とし、bill ごとの `sideGameChips` サブコレクション read を一覧構築時に行わない
- `I5-03`: bill 詳細やカテゴリ内訳の再構築など、明細が必要な場面だけサブコレクション read を許可する
- `I5-04`: `limit / paging` は全画面一律ではなく、「要対応の会計」一覧だけに適用する
- `I5-04`: 「要対応の会計」一覧の初回取得は `limit(50)` とし、それ以降は `もっと見る` で追加取得する
- `I5-04`: 未会計一覧は現時点では全件表示のままとし、I3 で決めた通常業務導線の一覧性を優先する
- `I5-05`: リリース前の性能確認基準は、単なる index エラーなしではなく、実用上支障がないことを確認する運用基準で定める
- `I5-05`: 最低限の完了条件は、本番必須 index が反映済みであること、「要対応の会計」初回表示で index エラーが出ないこと、一覧の N+1 が解消されていることとする
- `I5-05`: 性能確認では、同一営業日に 100 件規模の bill を想定し、初回表示、フィルタ切替、営業日切替、ユーザー別切替、`もっと見る`、post-event 実行後の再反映確認を行う
- `I5-05`: Step4 / Step5 / Step6 では、性能確認観点、確認データ件数、使用端末条件、更新した index / 運用資料を明記する
