# 08_実機確認手順

## 1. 目的

このファイルは、Step01 `bills親docとcurrent_state管理` が**実機確認の観点でも完了していると言えるか**を判断するための手順書である。

Step01 は parent target contract の導入が主責務であり、UI の全面切替は Step06 で行う。  
したがって本手順では、**実機上の操作で代表導線を通したうえで、Firestore 上の parent field が target contract どおりに更新されているか**を確認する。

## 3. 確認対象

実機確認では、少なくとも次を確認する。

1. bill 作成時の parent 初期 field
2. 会計開始時の `ops / draftAccountingInput`
3. 会計取消時の `ops / status`
4. 通常会計確定時の `settlementSnapshot / currentSummary / postSettlementState / reopenSummary`
5. 閉店持ち越し付与時の `closeSummary`
6. 未会計解消時の `closeSummary.unresolved`

## 4. 前提

- 実機または開発端末から、通常の bill 作成・会計開始・会計取消・会計確定・閉店処理が行えること
- Firestore を確認できること
  - Firebase Console
  - Firestore Emulator UI
  - もしくは手元の inspection script
- unreleased 前提のため、検証用データを自由に作成してよい

## 5. 実機確認シナリオ

### シナリオA: bill 作成

#### 操作

1. ユーザーを入店状態にする
2. terminal から bill を新規作成する
3. 作成された `bills/{billId}` を Firestore で開く

#### 期待結果

- top-level
  - `status = open`
  - `businessDate` が入る
  - `receiptNumber = null`
- `party`
  - `party.userId`
  - `party.pokerName`
- `place`
  - `place.table = null`
  - `place.seat = null`
- `ops`
  - `accountingStartedAt = null`
  - `accountingStartedBy = null`
  - `accountingCompletedAt = null`
  - `accountingCompletedBy = null`
  - `accountingCanceledAt = null`
  - `accountingCanceledBy = null`
- `draftAccountingInput`
  - `paymentMethodsByCategory = null`
  - `paymentMethodsByAmount = null`
- `settlementSnapshot`
  - `amounts = null`
  - `categoryBreakdown = null`
  - `paymentTotals = null`
  - `paymentsSummary = null`
  - `closedAt = null`
  - `contentHash = null`
- `currentSummary`
  - `claimTotalIncl = 0`
  - `receivedTotalIncl = 0`
  - `refundedTotalIncl = 0`
  - `netSalesIncl = 0`
- `postSettlementState`
  - `hasPostSettlementActivity = false`
  - `totalAdjustmentsIncl = 0`
  - `totalCollectedIncl = 0`
  - `totalRefundedIncl = 0`
  - `requiredActionType = none`
  - `requiredActionIncl = 0`
  - `lastRecordType = none`
  - `lastRecordAt = null`
  - `lastRecordId = null`
- `reopenSummary`
  - `hasReopenHistory = false`
  - `reopenCount = 0`
  - `currentSettlementCycle = 1`
  - `latestSettledCycle = 0`
  - `lastReopenedAt = null`
  - `lastReopenedBy = null`
  - `lastResettledAt = null`
- `closeSummary`
  - `unresolved = false`
  - `markedAt = null`
  - `closedBusinessDate = null`
  - `displayAmountAtMark = null`
  - `lastCloseRunId = null`

### シナリオB: 会計開始

#### 操作

1. bill に item を追加して金額を発生させる
2. accounting 画面から会計開始を行う
3. 支払方法を 1 種または複数種入力する
4. `bills/{billId}` を Firestore で確認する

#### 期待結果

- `status = settling`
- `ops.accountingStartedAt` が入る
- `ops.accountingStartedBy` が入る
- `draftAccountingInput.paymentMethodsByAmount` が入力に応じて入る
- `draftAccountingInput.paymentMethodsByCategory` が入力した場合は入る
- 既存互換のため `meta.paymentMethodsByAmount / paymentMethodsByCategory` も更新されていてよい

### シナリオC: 会計取消

#### 操作

1. シナリオBで `settling` にした bill に対して、会計取消を行う
2. `bills/{billId}` を Firestore で確認する

#### 期待結果

- `status = open`
- `ops.accountingStartedAt = null`
- `ops.accountingStartedBy = null`
- `ops.accountingCanceledAt` が入る
- `ops.accountingCanceledBy` が入る

### シナリオD: 通常会計確定

#### 操作

1. シナリオBの bill で会計を最後まで完了する
2. `bills/{billId}` を Firestore で確認する

#### 期待結果

- `status = settled`
- `ops.accountingCompletedAt` が入る
- `ops.accountingCompletedBy` が入る
- `settlementSnapshot`
  - `amounts` が入る
  - `categoryBreakdown` が入る
  - `paymentTotals` が入る
  - `paymentsSummary` が入る
  - `closedAt` が入る
  - `contentHash` が入る
- `currentSummary`
  - `claimTotalIncl > 0`
  - `netSalesIncl > 0`
  - `receivedTotalIncl >= 0`
  - `refundedTotalIncl = 0`
- `postSettlementState`
  - `hasPostSettlementActivity = false`
  - `requiredActionType = none`
  - `requiredActionIncl = 0`
  - `lastRecordType = none`
- `reopenSummary`
  - `latestSettledCycle = currentSettlementCycle`
  - `lastResettledAt` が入る

### シナリオE: 閉店持ち越し未会計マーキング

#### 操作

1. bill を `open` のまま残す
2. 閉店処理を実行する
3. `bills/{billId}` を Firestore で確認する

#### 期待結果

- `status = open` のまま
- `closeSummary.unresolved = true`
- `closeSummary.markedAt` が入る
- `closeSummary.closedBusinessDate` が入る
- `closeSummary.displayAmountAtMark` が入る
- `closeSummary.lastCloseRunId` が入る
- 互換のため `closeSnapshot` も並行更新されていてよい

### シナリオF: 未会計解消後処理

#### 操作

1. シナリオEの bill を通常会計で解消する
2. 未会計解消後処理が走ったあとに `bills/{billId}` を Firestore で確認する

#### 期待結果

- `closeSummary.unresolved = false`
- 互換のため `closeSnapshot.unresolved = false` も同時に更新されていてよい

## 6. Step01 完了判定

Step01 は、次を満たした時に実機確認の観点でも完了とする。

1. シナリオA〜Fの parent field が target contract と矛盾しない
2. `create / start / cancel / settle / close` の主要導線で parent field の更新が確認できる
3. `postEvents` や `closeSnapshot` が残っていても、それが**互換維持の暫定共存**として説明できる
4. Step01 で扱わない
   - adjustment 起点の parent 更新
   - cashAction 起点の parent 更新
   - reopen 起点の exact 更新
   - UI の新 field 参照切替
   が、後続 step の責務として整理されている
