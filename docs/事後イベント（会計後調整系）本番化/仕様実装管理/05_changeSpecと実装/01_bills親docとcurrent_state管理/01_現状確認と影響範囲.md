## 2. 現行実装の確認結果

### 2.1 bills 親 doc の作成時点

現行の bill 親 doc は、`createBillWithActiveStay` で作成されている。

主な作成 field:
- `businessDate`
- `status = open`
- `createdAt`
- `updatedAt`
- `billId`
- `receiptNumber = null`
- `party.userId`
- `party.pokerName`
- `place.table = null`
- `place.seat = null`
- `meta.schemaVersion`
- `meta.contentHash`

確認ファイル:
- `functions/src/domains/bills/repos/createBillWithActiveStay.ts`

確認結果:
- `party`, `place`, top-level の一部は既に存在する
- `ops`, `settlementSnapshot`, `currentSummary`, `postSettlementState`, `reopenSummary`, `closeSummary`, `draftAccountingInput` は未導入
- `status` は `open` ベースで作成されるが、target schema の summary 群はまだ作られていない

### 2.2 会計開始時の更新

現行の会計開始は `startAccounting` ヘルパと callable で行っている。

主な更新 field:
- `status = settling`
- `ops.accountingStartedAt`
- `ops.accountingStartedBy`
- `updatedAt`
- `meta.paymentMethodsByCategory`
- `meta.paymentMethodsByAmount`

確認ファイル:
- `functions/src/domains/bills/repos/startAccounting.ts`
- `functions/src/domains/bills/callables/accounting.ts`

確認結果:
- `ops` グループは部分的に既に存在する
- 支払方法入力は `draftAccountingInput` ではなく `meta.paymentMethodsByCategory / meta.paymentMethodsByAmount` に保存されている
- current-scope 仕様書で target にしている `draftAccountingInput` との橋渡し設計が必要

### 2.3 会計確定時の更新

現行の会計確定 (`completeAccountingV2`) 自体は bill 親 doc に最小限の更新しか行わず、実質的な親 summary の構築は `billsOnSettle` trigger に寄っている。

`completeAccountingV2` の主な更新 field:
- `status = settled`
- `ops.accountingCompletedAt`
- `ops.accountingCompletedBy`
- `updatedAt`

`billsOnSettle` の主な更新 field:
- `amounts.*`
- `categoryBreakdown`
- `itemsSnapshot`
- `sideGameChipsSummary`
- `tournamentsSnapshot`
- `paymentTotals`
- `paymentsSummary.*`
- `postEvents.totalRefundedIncl`
- `postEvents.totalAdjustmentsIncl`
- `postEvents.netSalesIncl`
- `closedAt`
- `meta.contentHash`
- `updatedAt`

確認ファイル:
- `functions/src/domains/bills/callables/accounting.ts`
- `functions/src/domains/bills/triggers/billsOnSettle.ts`
- `functions/src/domains/bills/services/snapshots.ts`

確認結果:
- 現行 parent doc は `settlementSnapshot / currentSummary / postSettlementState` ではなく、旧 `amounts / categoryBreakdown / paymentTotals / paymentsSummary / postEvents` 前提で構築されている
- `itemsSnapshot` などの旧 root field も書き込まれており、target schema の `settlementCycles/{cycleNo}/baselineSnapshot` とは責務がずれている
- `closedAt` は root に直接保存されているが、target schema では `settlementSnapshot.closedAt` と `reopenSummary.lastResettledAt` に責務が分散する

### 2.4 閉店持ち越し未会計の管理

## 4. 仕様との差分

### 4.1 field グループ差分

target schema:
- `settlementSnapshot`
- `currentSummary`
- `postSettlementState`
- `reopenSummary`
- `closeSummary`
- `draftAccountingInput`

現行 schema:
- `amounts`
- `categoryBreakdown`
- `paymentTotals`
- `paymentsSummary`
- `postEvents`
- `closeSnapshot`
- `meta.paymentMethodsByAmount`
- `meta.paymentMethodsByCategory`

差分整理:
- parent summary の責務が、現行では root 直置き field と `postEvents` に分散している
- target schema では summary 群に再編する必要がある
- 既存 `meta.paymentMethods*` は current-scope では source として残すが、親 doc の target 参照面は `draftAccountingInput` に寄せる必要がある

### 4.2 status contract 差分

target schema:
- `open`
- `settling`
- `settled`
- `post_settlement_pending`

現行:
- `in_progress`
- `partially_refunded`
- `refunded`
- 旧 ToBe docs にも細かい状態が残存

差分整理:
- parent doc 上の正規 state contract を target schema に合わせる必要がある
- 旧 status は後続 step で除去または内部処理へ吸収が必要

### 4.3 close 系差分

target schema:
- `closeSummary.unresolved`
- `closeSummary.markedAt`
- `closeSummary.closedBusinessDate`
- `closeSummary.displayAmountAtMark`
- `closeSummary.lastCloseRunId`

現行:
- `closeSnapshot.*`

差分整理:
- UI / close process / users.unsettledBillsCount 連携は `closeSnapshot` 前提
- Step01 で parent contract を決め、Step06 UI と close process 変更に伝播させる必要がある

### 4.4 post-event summary 差分

target schema:
- `postSettlementState.*`
- `requiredActionType`
- `requiredActionIncl`
- `lastRecordType`

現行:
- `postEvents.*`
- `paymentsSummary.balanceDueIncl`
- 旧 event trigger ロジック

差分整理:
- 会計後要対応一覧や parent summary は target schema では新しい summary 群に一本化する必要がある
- 旧 `postEvents` 中心の UI / trigger は Step03/04/05 と連動して見直す必要がある

## 5. 影響範囲

### 5.1 後続ステップへの依存

- Step02
  - `settlementSnapshot` と `latestSettledCycle` の責務整理に依存する
- Step03
  - `postSettlementState.totalAdjustmentsIncl` と `requiredAction*` の導出に依存する
- Step04
  - `postSettlementState.totalCollectedIncl / totalRefundedIncl / lastRecordType` の更新に依存する
- Step05
  - `reopenSummary.*` の更新に依存する
- Step06
  - `status`, `closeSummary`, `postSettlementState.requiredActionType` の query / view model に依存する
- Step07
  - `settlementSnapshot`, `draftAccountingInput`, payment source の読み方に依存する

### 5.2 既存機能への影響

- 会計開始 / 取消 / 会計完了
- 閉店処理と未会計持ち越し
- 会計後調整 / 返金 / reopen
- 会計一覧 / 未会計一覧 / 要対応一覧
- 履歴画面 / analytics 連携

### 5.3 実装上の注意

- current-scope では unreleased 前提のため、既存データ migration は不要
- ただし既存コードは旧 field 名を広く参照しているため、実装は一括置換ではなく段階的移行を前提にする必要がある
- Step01 単独で全 field の実利用箇所を書き換えるのではなく、parent contract と write/update 起点をまず固定するのが安全

## 6. この時点のメモ

- Step01 の中心は「新しい親 doc 契約の導入」と「旧 root summary / postEvents / closeSnapshot からの移行計画化」である
- 実装時は、`closeSnapshot -> closeSummary` と `postEvents -> postSettlementState/currentSummary` が主な差し替え論点になる
- `draftAccountingInput` は target 概念として導入するが、現行 `meta.paymentMethodsBy*` を source として再利用する前提を崩さない
