# 05_changeSpecと実装 README

## 1. このフォルダの役割

このフォルダは、`04_仕様書/` で確定した 7 本の詳細仕様書を入力として、**changeSpec 作成 -> 実装 -> 確認 -> テスト -> 結果整理 -> 後続伝達** を一貫して進めるための実装管理フォルダである。

ここでは、仕様書単位で 1 ステップずつ進める。各ステップは、原則として **仕様書 1 本に対して changeSpec 1 本** の対応関係を保つ。

この README は、各ステップを誰が進めても同じ順序・同じ確認粒度で進められるように、進め方・フォルダ構成・完了条件を固定する正本とする。

## 2. 参照優先順位

本フォルダで作業する時の参照優先順位は次のとおり。

1. `../04_仕様書/`
2. `../03.1_前提再設計/step3.12_全体整合性確認/`
3. `../03.1_前提再設計/step3.11_未決論点の再決定/`
4. `../03.1_前提再設計/step3.15_詳細仕様書の分割方針.md`
5. `../03.1_前提再設計/step3.16_詳細仕様書作成.md`
6. `../03_ToBe意思決定/`
7. `../02_AsIs/`

補足:
- `04_仕様書/` が、このフェーズの直接入力となる正本である。
- 仕様書と `03.1` に差異が見えた場合は、まず `03.1` の最新判断と照合し、必要なら仕様書補強を先に行う。
- `02_AsIs/` は historical record であり、新仕様の判断元にはしない。

## 2.5 各ステップ README との関係

- 各ステップ配下の `README.md` は、ステップ固有の責務と読み順を説明する入口である。
- ただし、進め方の正本は常に `05_changeSpecと実装/README.md` とし、各ステップの作業時にも必ず参照する。
- 各ステップ README だけで作業を進めず、全体ルール・参照優先順位・完了条件・非対象は本 README を基準に判断する。

## 3. 基本方針

### 3-1. 仕様書単位で閉じる

各ステップは、1 本の仕様書に対して次をまとめて進める。

1. 現状確認
2. changeSpec 作成
3. 仕様書トレース確認
4. 確認観点の整理
5. 実装
6. テスト実装 / 更新
7. 網羅的確認
8. サマリ作成
9. 後続伝達事項整理

### 3-2. スコープを広げすぎない

各ステップでは、対象仕様書に書かれている current-scope だけを実装する。future 扱いの機能は、このフェーズに持ち込まない。

### 3-3. 実装前に確認観点を固定する

実装を始める前に、最低限の確認観点・確認方法・テスト方針を決めてから進める。

### 3-4. changeSpec と実装を 1:1 で追える状態を保つ

`02_changeSpec.md` と、実装 / テスト / 確認結果の各ファイルの対応を明確に残す。

### 3-5. テストが実行できない時は、先にエミュレータの再起動を試す

エミュレータ依存のテストが失敗した時は、まず Firebase Emulator など必要なエミュレータを閉じて再起動し、再実行する。単発の `fetch failed` や接続失敗を即座に未解決バグ扱いせず、再起動後も再現するかを確認してから判断する。

### 3-6. ステップ完了前に、進め方と仕様書の両面から再点検する

各ステップの完了前には、次の 2 観点で再点検する。

1. `05_changeSpecと実装/README.md` の標準手順・完了条件を満たしているか
2. 対応する `04_仕様書/*.md` の current-scope が、実装・テスト・確認結果へ漏れなく反映されているか

### 3-7. 実機確認手順を必ず残す

各ステップでは、最終的に `08_実機確認手順.md` を作成し、実機や画面操作でどこをどう確認すればそのステップが完了と言えるかを、なるべく平易な言葉で残す。期待する画面表示、Firestore / API / ログの確認ポイント、完了判定も明記する。

## 4. 推奨実施順

依存順の推奨は次のとおり。

1. `01_bills親docとcurrent_state管理`
2. `02_settlementCyclesとbaselineSnapshot`
3. `03_adjustments管理`
4. `04_cashActions管理`
5. `05_reopenと再会計`
6. `06_要対応の会計画面と一覧取得`
7. `07_analyticsMonthly更新と日付帰属とline配賦`

理由:
- 1,2 で保存モデルと親 summary の土台を固める
- 3,4,5 で会計後処理の中核を固める
- 6 で UI 導線を接続する
- 7 で read model 更新と日付帰属を閉じる

## 7. 標準の進め方

各ステップは、必ず次の順番で進める。

1. 対応する `04_仕様書/*.md` を確認する
2. `01_現状確認と影響範囲.md` を埋める
3. `02_changeSpec.md` を作成する
4. `03_仕様書トレース確認.md` で仕様漏れを確認する
5. `04_確認観点と確認方法.md` でテスト / 確認方法を先に決める
6. コード実装を行う
7. テストファイルを作成または更新する
8. 自動テスト・手動確認・目視確認を実施する
9. テストが実行できない時は、先に必要なエミュレータを再起動して再実行する
10. `05_実装サマリ.md` を更新する
11. `06_確認結果サマリ.md` を更新する
12. `07_後続ステップへの伝達事項.md` を更新する
13. `08_実機確認手順.md` を作成または更新する
14. 進め方と仕様書の両面から残タスクがないか再点検する
15. `00_全体進行管理.md` を更新する

## 8. 完了条件

各ステップは、少なくとも次を満たした時に完了とする。

- `02_changeSpec.md` が完成している
- `03_仕様書トレース確認.md` で仕様項目に未対応が残っていない
- `04_確認観点と確認方法.md` が埋まっている
- 実装と必要なテスト更新が終わっている
- `06_確認結果サマリ.md` に確認結果が反映されている
- 後続への伝達事項が整理されている
- `08_実機確認手順.md` に、実機での確認方法と完了判定が整理されている
- 進め方と仕様書の両面から再点検し、残タスクなしと判断できている

## 9. 現時点で非対象とするもの

このフェーズでも、次は current-scope 外とする。

- strict な税務・会計 read model の本実装
- `reportingEntries / reportingMonthly / cashflowMonthly`
- card 後日入金 / fee の厳密管理
- point treatment の厳密化
- product-level analytics
- advisor review / period close

これらは `../05_今後検討_税務会計read_model拡張.md` で継続管理する。

## 10. 実務上の注意

- 1 ステップの中で仕様変更が発生した場合は、先に `04_仕様書/` と `03.1_前提再設計/` に戻って整合を取る。
- 実装後に docs を追いかけるのではなく、docs を埋めながら実装を進める。
- 隣のステップにまたがる変更が必要でも、まず主責務のステップを進め、影響は `07_後続ステップへの伝達事項.md` に残す。
- テストが作れない確認観点は、手動確認手順を必ず残す。
- エミュレータ依存テストが失敗した時は、ログ保存だけで終わらず、再起動後の再確認結果まで `06_確認結果サマリ.md` に残す。
- `08_実機確認手順.md` は、実装者以外が見ても同じ確認ができる粒度で書く。
