# 07_後続ステップへの伝達事項

## 1. このファイルの役割

Step07 完了時点で、後続 step（旧経路統廃合 / 運用調整 / nightly 再集計の整備）に引き継ぐ事項と、Step07 で意図的に扱わなかった範囲を整理する。

## 2. nightly 再集計（仕様書 §10.5）への伝達

Step07 で実装した analytics 更新は **逐次集計**（settle / adjustment / cashAction / reopen の各イベントで都度 increment）。仕様書 §10.5 / §6.5 で示されている「nightly 再計算による訂正」は **別タスク** として後続 step で実装する。

### 2.1 nightly 再計算が必要なケース

- Step07 の analytics 更新で、main transaction 成功後の separate-tx が落ちた場合（`logOpsError` で観測される）
- 既存 marker `{billId}` で集計済みの bill が reopen された場合の baseline 同期（Step07 では rollback aggregator が `bill.categoryBreakdown` から再構築しているため正しく動くが、念のため nightly で整合チェック）
- `addToMonthlyIndex` 等の既存 settle path と Step07 の adjustment / cashAction path で field schema が **微妙に違う**（例: 既存 settle は `entrySalesIncl`、新 adjustment は `entrySales`）。これは rollback aggregator で吸収しているが、**byTemplateTournaments の totals` 集計値**は long-term で nightly 整合チェックを入れたい

### 2.2 nightly 集計の実装方針（後続 step）

1. `analyticsMonthly/{monthKey}` をすべて再構築するバッチを夜間 cron で動かす
2. その日の `bills`（`businessDate` がその月）を全件読み、`categoryBreakdown` / `tournamentsSnapshot` / `paymentTotals` から再集計
3. その月の `settlementCycles/{cycleNo}/adjustments` / `cashActions` も読み、Step07 の delta builder を再利用して反映
4. 既存 marker（`{billId}_cycle{cycleNo}_settle` / `adj_{adjustmentId}` / `cash_{cashActionId}` / `reopen_{billId}_cycle{oldCycleNo}`）はそのまま audit 証跡として残し、再構築 doc に上書きしない

## 3. 旧経路統廃合への伝達（後続 step / 運用 step）

### 3.1 旧 events 経路の analytics 反映の停止

Step07 では旧 `bills/{billId}/events` 経路の analytics 反映 (`enqueueEvent` / `buildEventDelta`) には **touch なし**。後続 step で:

- 新 `recordPostSettlement*` callable に完全移行した時点で、旧 `enqueueEvent` 呼び出し元（`billsEventsOnCreate` 等）を停止
- 旧 `appendEventLog` の `analyticsMonthly/{monthKey}/eventsLog` も新規書き込み停止
- 旧 marker（event ID ベース）は audit 用途で残す

### 3.2 旧 settle marker `{billId}` の deprecation

Step07 の `processBillAnalyticsAtomically` は `cycleNo` 未指定で legacy `{billId}` marker を維持している（後方互換）。後続 step で:

1. 全呼び出し元（現状は `enqueueSettlement` のみ）が `cycleNo` を渡すことを確認
2. legacy fallback を削除
3. 既存の `{billId}` marker は残し、新仕様 `{billId}_cycle{cycleNo}_settle` に集約

### 3.3 旧 callable の段階的廃止

Step07 では旧 callable に touch なし。Step06 と同じ段階的廃止方針を維持。

## 4. Step07 が意図的に扱わなかった事項

- 旧 events 経路（`enqueueEvent` / `buildEventDelta` / `appendEventLog`）の analytics 反映 → 後続 step（旧経路停止と同時）
- nightly 再集計バッチの実装 → 別 step（運用整備 step）
- `analyticsMonthly` の field schema 統一（`entrySalesIncl` vs `entrySales` 等の suffix 差） → 後続 step（schema migration 必要）
- migration / backfill → 行わない（未リリース前提、既存 marker doc は audit として残す）
- Firestore security rules（`analyticsMonthly` の write 権限） → 確認のみ。Step07 で書き込むのは server-side（admin SDK）からなので rules 影響なし。client-side からの read は別 step で
- `analyticsMonthly` 配下の field 値の妥当性検証ツール → 後続 step（運用 dashboard との突合）
- Flutter 側の analyticsMonthly 表示画面 → 別画面（既存の集計画面は touch なし）
- legacy event 経路のデータ rollback → 行わない（Step07 は新経路のみ rollback）
- 月跨ぎの adjustment / cashAction（cashflowBusinessDate が翌月）の paymentTotals → 仕様書 §8.5 通り **売上帰属月** に計上、cashflowBusinessDate は使わない。Step07 で実装済み

## 5. 共通注意事項

### 5.1 separate-tx の運用観点

Step07 の analytics 更新は main transaction 後の separate-tx で実施する設計。運用観点で:

- main 成功 → analytics 失敗 のケースは `logOpsError` で観測される
  - `functionEntry: 'createPostSettlementAdjustment' / 'recordPostSettlementCashAction' / 'reopenAccountedBill'`
  - `operation: 'processAdjustmentAnalyticsAtomically' / 'processCashActionAnalyticsAtomically' / 'processReopenRollbackAnalyticsAtomically'`
- 監視 dashboard で `outcome: 'fail' AND operation: ^process.*Analytics.*Atomically$` をカウント
- 一定回数連続して fail する場合は emulator / 本番 firestore の状態を確認、nightly 再集計で訂正

### 5.2 `analyticsApplied` log field の使い方

各 callable の `logOpsSuccess` の context に Step07 で追加:

| field | 値 | 意味 |
|---|---|---|
| `analyticsEnabled` | `true` / `false` | feature flag (`storeConfig.features.settlementAggregatorEnabled`) の状態 |
| `analyticsApplied` | `true` / `false` | adjustment / collection / refund の analytics 反映が成功したか（`reused` 時 / flag OFF 時 / 失敗時は false） |
| `analyticsCashActionApplied` | `true` / `false` | `createPostSettlementAdjustment` で immediate cashAction が作られた場合の analytics 反映成否 |
| `analyticsRollbackApplied` | `true` / `false` | `reopenAccountedBill` の analytics rollback 反映成否 |

これらを使って「analytics 集計が main 操作と一致しているか」を BigQuery / Logs Explorer で検証できる。

### 5.3 後方互換

- Step07 で touch した既存 src ファイル（`updateAnalyticsForBill.ts` / `aggregator/index.ts` / `aggregator/types.ts` / `billsOnSettle.ts` / `createPostSettlementAdjustment.ts` / `recordPostSettlementCashAction.ts` / `reopenAccountedBill.ts`）の API は **追加のみ**。既存呼び出し元は変更不要
- 既存の `addTo*` 関数群は不変
- `analyticsMonthly/{monthKey}` の field schema 変更なし（既存 sub-collection / field 名をそのまま使用）

### 5.4 既存リグレッション

- `develop` baseline に 9 suites の既存 fail（Step05 / Step06 完了時点と同じセット、Step07 で増えていない）
- これらは Step01〜07 の本番化対象外（`FunctionCustomError` 移行後の test 期待値ズレ等が中心）
- 個別タスクとして別ブランチで対応する（`standardization/basis` の続編で対応）

### 5.5 capture pattern の applicability

Step07 で導入した「main transaction 内で capture → tx 後に separate-tx で apply」のパターンは、analytics 以外にも以下の用途で再利用可能:

- 通知送信（push notification の trigger）
- BigQuery / Looker への export
- 第三者 webhook 連携

将来同様の case で:
1. main transaction 内で `let captureXxx: ... | null = null;` を用意
2. transaction 内で `captureXxx = { ... };` で値を確定
3. transaction 後に `if (!reused && captureXxx) { ... try { /* separate apply */ } catch (e) { logOpsError(...); } }`

の構造を踏襲。

### 5.6 仕様書 §6.5 の SoT 原則維持

- `analyticsMonthly` は **read model**、SoT は `bills` 配下（cycle / adjustments / cashActions）
- Step07 で touch した applier はすべて `bills` 系の SoT に書き戻さない（read のみ）
- 万が一 `analyticsMonthly` が破損しても、`bills` 配下から再構築可能（nightly batch で実装）

### 5.7 marker docId の意味づけマップ

後続 step / 運用観点で参照しやすいよう、Step07 完了時点での marker docId 一覧:

| marker docId | type | 集計内容 | 冪等保証 |
|---|---|---|---|
| `{billId}` | settle (legacy) | 旧 cycleNo 未指定時の settle baseline | 旧 settle のみ |
| `{billId}_cycle{cycleNo}_settle` | settle | 当該 cycleNo での settle baseline | 同 cycle 再 settle 時 |
| `adj_{adjustmentId}` | adjustment | adjustment lines の analytics 反映 | 同 adjustment 重複呼び出し時 |
| `cash_{cashActionId}` | cashAction | collection cashAction の paymentTotals 反映 | 同 cashAction 重複呼び出し時 |
| `reopen_{billId}_cycle{oldCycleNo}` | reopen_rollback | 旧 cycle の baseline + adj + collection cash の rollback | 同 reopen 二度目呼び出し時 |

各 marker doc の中身（`type` / `billId` / `cycleNo` / `adjustmentId` / `cashActionId` / `oldCycleNo` / `monthKey` / `businessDate` / `processedAt`）は audit 証跡として残す。
