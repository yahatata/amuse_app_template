## 1. 仕様書 §1〜§20 の要点

### 1.1 役割（§5）

- `analyticsMonthly` は **運用ダッシュボード用 read model**
- SoT は `bills / settlementCycles / baselineSnapshot / adjustments / cashActions`
- `analyticsMonthly` を current state 正本にしない（§19）

### 1.2 3 つの日付軸（§6）

| 日付軸 | 値 |
|---|---|
| 売上帰属日 | `bill.businessDate` |
| adjustment 確定日 | `adjustment.createdAt` |
| cashflow 実行日 | `cashAction.executedAt` / `cashAction.cashflowBusinessDate` |

### 1.3 analyticsMonthly が使う日付（§7）

- 売上系 (`grossSales`, `itemsSales`, `extraCostSales`, `sideGameChipSales`, `tournamentsSales`, `dailySales`, `orderCount`, `paymentTotals`) は **`bill.businessDate` ベース**
- `adjustment.createdAt` / `cashAction.executedAt` は **audit 軸として持つが `days` を更新する日付キーとしては使わない**（§14.2）

### 1.4 paymentTotals（§8 / §11）

- 売上帰属月ベースの受領方法配分
- collection 完了で **`paymentTotals` を増やす**（§11 増額系 + 追加徴収完了時）
- refund では **`paymentTotals` を直接減らさない**（§8.4 / §11 減額系）
- 後日回収による後付け増加を許容（§8.3）

### 1.5 更新責務（§10 / §11）

| パターン | adjustment 作成時 売上差分更新 | 同時 cashflow | 後続 cashAction で cashflow | paymentTotals |
|---|---|---|---|---|
| 減額 + 返金済 | する | する | なし | 直接減らさない |
| 減額 + 返金前 | する | しない | refund 完了時 | 直接減らさない |
| 増額 + 追加徴収済 | する | する | なし | この時点で増える |
| 増額 + 追加徴収前 | する | しない | collection 完了時 | 回収完了時に増える |

### 1.6 lines[] 配賦ルール（§12〜§16）

- top-level: `grossSales = 全 line 合計`、各 category sales = 同 category line 合計
- `days/{businessDate}`: `bill.businessDate` の day bucket に加算（§14.2）
- `byCategory/summary`: `targetCategory → items / extraCost / sideGameChip / tournaments`
- `byUser/{userId}`: `bill.party.userId` がある場合のみ更新、line ごとに user は変えない（§15）
- `byTemplateTournaments/{templateKey}`: tournament line のみ、`operationType` 別に `entryCount/entrySales` / `reentryCount/reentrySales` / `addonCount/addonSales` を更新（§16）

### 1.7 整合条件（§18）

1. `analyticsMonthly` は SoT ではない
2. 売上系日付軸は `bill.businessDate` を正
3. `sum(lines[].amountInclDelta) = adjustment.adjustmentAmountIncl`
4. tournament line は template / operationType を持つ
5. 支払手段 source は現行 `bills` 実装から派生できるものに限定

### 1.8 不可条件（§19）

- `analyticsMonthly` を current state 正本にしない
- card 後日入金や fee を current-scope に混ぜない
- product-level analytics を今回追加しない
- generic line だけで category を特定できない adjustment を許可しない

## 3. Step07 で対象とする実装範囲（計画フェーズでの整理）

> **現状**: 以下 §3.1〜§3.x は計画確定までのドラフト。**実際に入れた実装との対応は [05_実装サマリ.md](./05_実装サマリ.md) を優先参照**。

仕様書 §10 / §11 を adjustment / cashAction / reopen rollback 経路に絞ると、計画として次が Step07 で必要になる、としていた。

### 3.1 adjustment 作成時 — 売上差分の analyticsMonthly 反映

- 対象 callable: `createPostSettlementAdjustment`
- 入力: 当該 adjustment の `lines[]` + bill `businessDate` / `party.userId`
- 反映先:
  - `analyticsMonthly/{month}` top-level: `grossSales`, `itemsSales`, `extraCostSales`, `sideGameChipSales`, `tournamentsSales` を line 合計分 increment
  - `analyticsMonthly/{month}/days/{billBusinessDate}`: 同等の category 合計を increment（`bill.businessDate` の day bucket に加算）
  - `analyticsMonthly/{month}/byCategory/summary`: `totals.{items|extraCost|sideGameChip|tournaments}` += line 合計
  - `analyticsMonthly/{month}/byUser/{userId}`: `userId` 有時のみ各 sales fields を line 合計分 increment
  - `analyticsMonthly/{month}/byTemplateTournaments/{templateKey}`: tournament line のみ、`operationType` ごとに `entryCount/entrySales` / `reentryCount/reentrySales` / `addonCount/addonSales` を increment、`totalTournamentSales` を tournament line 合計で increment
- idempotency marker: `analyticsMonthly/{month}/aggregationMarkers/adj_{adjustmentId}`

### 3.2 cashAction 実行時 — paymentTotals 反映

- 対象 callable: `recordPostSettlementCollection` / `recordPostSettlementRefund`（共通 repo `recordPostSettlementCashAction`）
- collection の場合:
  - 反映先: `analyticsMonthly/{month}.paymentTotals.{method}` += `methodBreakdown[].amountIncl`、`days/{billBusinessDate}.byPaymentMethod.{method}` += 同
  - 月キー: bill.businessDate ベース（cashflowBusinessDate ベースではない、仕様書 §11 / §8 に従い「売上帰属月」側）
- refund の場合:
  - 反映なし（仕様書 §8.4 / §11、`paymentTotals` 直接減らさない）
- idempotency marker: `analyticsMonthly/{month}/aggregationMarkers/cash_{cashActionId}`

### 3.3 reopen 時 — 仕様書外、Step07 で明示判断

仕様書では reopen 時の analytics rollback を要求しない。
existing marker 設計（`{billId}` 1 件）のままだと、reopen 後の resettle で **再反映が起きない**ため、運用上 baseline が増えない（重複計上は防げる）。

ただしこれは仕様書 §10.1「resettle 時 baseline 売上を反映」と矛盾する。

Step07 では：
- (a) reopen 時に旧 baseline を rollback し、resettle 時に再反映できるよう marker を `bill_cycle{cycleNo}` 単位にする
- (b) 仕様書 §10.1 の「resettle 時反映」は本番化対象外（後続 step に逃がす）として、既存挙動（marker = billId 単独）のまま運用する

ユーザー判断が必要。
