## 5. リスク評価と対応

### 5.1 settle marker key 変更による既存データとの衝突（changeSpec §5.3.4）

- 旧 marker `{billId}` は legacy 互換のため、`cycleNo` 未指定の呼び出しでは現在も使用される（`processBillAnalyticsAtomically` の fallback）
- 新仕様 `{billId}_cycle{cycleNo}_settle` は別 doc として共存できるため、既存 marker doc を削除する移行は不要
- ただし Step07 デプロイ後に同一 bill が **「`{billId}` で 1 度集計済み + `{billId}_cycle1_settle` で再集計される」** 二重計上リスクがあり得る
- 対策: deploy 直後の bills は再 settle が走らない限り `{billId}` のみ。再 settle（reopen + 再会計）の場合のみ `{billId}_cycle{cycleNo}_settle` 系になる
- 旧 marker `{billId}` で集計済みの bill が reopen された場合、rollback applier は `bill.categoryBreakdown` 等から baseline を負号適用するため正しく rollback される（marker docId に依存しない計算ロジック）

### 5.2 separate-tx の analytics 失敗時の整合性（changeSpec §5.6）

- main 成功 → analytics 失敗 のケースでは bill の状態は更新されているが analyticsMonthly に未反映
- 仕様書 §10.5「analytics は SoT ではなく nightly 再計算で訂正可能」に基づき、`logOpsError` で観測 → 必要に応じて nightly batch / 手動再集計で訂正
- callable は成功で返るため UI は影響を受けない

### 5.3 rollback の `tournamentsSnapshot` field 名差分

- settle path（`addToByTemplateTournaments`）は `entrySalesIncl` 等の `*Incl` 名で書き込む
- adjustment path（`buildAdjustmentAnalyticsDelta`）は `entrySales` 等の suffix なし
- rollback aggregator は `*Incl` 優先 + legacy 名 fallback を実装し、両方の field 名で書かれた値を正しく rollback できる

### 5.4 reopen rollback の対象 adjustment 範囲

- `cancelled_by_reopen` 状態の adjustment は **元から analytics 反映なし**（後続 reopen で cancelled された adjustment は analytics に乗らない）
- それ以外（`effective` / `completed_by_cash_action` / `superseded`）は反映済みとして rollback 対象
- 実装では `data.adjustmentState !== 'cancelled_by_reopen'` で filter

## 7. 補足メモ

### 7.1 capture pattern について

- transaction は Firestore 仕様により retry し得るため、`analyticsCapture` は最終 commit 時の値で確定する
- 各 attempt で同じ計算結果になるため race-safe

### 7.2 `paymentTotals` の sales 帰属月

- 仕様書 §8.4 / §8.5 の通り、`paymentTotals` は **売上帰属月（bill.businessDate.substring(0, 7)）** に集約
- post-settlement の collection cashAction が翌月実行されても、対応する売上は元の `bill.businessDate` の月に計上される
- 実装: `monthKey = capture.billBusinessDate.substring(0, 7)` で固定（`cashAction.cashflowBusinessDate` は使わない）

### 7.3 reopen 後の resettle で marker は別 doc になる

- reopen 完了 → bill.reopenSummary.currentSettlementCycle が `oldCycleNo + 1` に進む
- 再 settle 時に `billsOnSettle` が `cycleNo: newCycleNo` で `enqueueSettlement` を呼ぶ
- marker docId は `{billId}_cycle{newCycleNo}_settle` で衝突なく書き込まれる
- 旧 marker `{billId}_cycle{oldCycleNo}_settle` も audit 証跡として残る

### 7.4 既存 spec への影響

- `processBillAnalyticsAtomically.spec.ts` / `aggregator.spec.ts` は `cycleNo` 未指定で従来通り legacy `{billId}` marker を使うため挙動変化なし
- `bills.onSettle.spec.ts` は `cycleNo: 1` を渡す形に変更されたが、marker docId が `{billId}_cycle1_settle` でも spec が doc 名に依存していなかったため問題なく pass
