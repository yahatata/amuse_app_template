## 1. このファイルの役割

- Step07 のコードがデプロイ済み、または `firebase emulators:start --only firestore,functions` で起動済み

- `storeMeta/config.features.settlementAggregatorEnabled = true`（または default 値 `true`）
- 確認用 device が `accounting` 権限を持つ
- Firestore Console / Emulator UI で `analyticsMonthly` ツリーを直接確認できる

## 4. 実機確認シナリオ一覧

| No | シナリオ | 操作入口 | 期待結果 | 備考 |
|---|---|---|---|---|
| A | 通常 settle で analytics に baseline が入る | bill 会計（status: open → settled） | `analyticsMonthly/{monthKey}` の `grossSales` 等が増加 + marker `{billId}_cycle1_settle` 生成 | Phase C |
| B | post-settlement adjustment（line のみ）で analytics に増分 | `createPostSettlementAdjustment` callable | `analyticsMonthly/{monthKey}` の `grossSales` が adjustment.lines[].amountInclDelta 合計分 increment + marker `adj_{adjustmentId}` 生成 | Phase D |
| C | post-settlement adjustment（immediate cashAction 付き）で paymentTotals も increment | 同上、`immediateCashAction` 指定 | `paymentTotals.{method}` が cashAction.amountIncl 分 increment + marker `cash_{cashActionId}` 生成 | Phase D |
| D | post-settlement collection で paymentTotals 増分（`recordPostSettlementCollection`） | `recordPostSettlementCollection` callable | `paymentTotals.{method}` が increment + marker `cash_{cashActionId}` 生成、grossSales/byCategory は変わらない | Phase D |
| E | post-settlement refund で paymentTotals は変わらない | `recordPostSettlementRefund` callable | callable 成功、`paymentTotals` 不変、marker は作成されない（refund early return） | Phase D（仕様書 §8.4） |
| F | reopen で baseline + adj + collection が rollback | `reopenAccountedBill` callable | `analyticsMonthly` の各値が 0（または rollback 前の状態）に戻り、marker `reopen_{billId}_cycle1` が生成、`{billId}_cycle1_settle` / `adj_{...}` / `cash_{...}` は audit 残存 | Phase E |
| G | reopen 後の resettle で新 cycle marker で再反映 | reopen 完了 → 再 settle | marker `{billId}_cycle2_settle` で settle 反映、cycle1 系 marker は残存（衝突なし） | Phase C / E |
| H | adjustment idempotency（同 adjustmentId で 2 回呼び出されても analytics は 1 回のみ） | callable 二重呼び出し（同 idempotencyKey） | reused: true で再分は反映されず、`analyticsApplied` が false で log 記録 | Phase D 冪等 |
| I | analytics 失敗時の callable 成功保証（separate-tx 設計） | feature flag を一時的に true→false→true 切替 / Firestore 書き込み失敗を induce | callable は成功で返り、`logOpsError` のみで bill 状態は完了。再 settle / 再 reopen は個別判断 | 設計検証 |
| J | feature flag OFF で analytics 反映なし | `storeConfig.features.settlementAggregatorEnabled = false` | callable 成功、`analyticsApplied:false` ログ、`analyticsMonthly` 不変 | Phase D / E |

## 5. シナリオ別の確認手順

### 5.1 シナリオ A: 通常 settle で baseline が入る

**準備**:
1. 新規 bill を作成（`createBillWithActiveStay` 等）
2. `accounting` callable で settle まで進める

**期待**:
1. `bills/{billId}.status === 'settled'`
2. `analyticsMonthly/{monthKey}` doc が存在し、以下が増分されている:
   - `grossSales` += `bill.amounts.grandTotalRounded`
   - `itemsSales` / `extraCostSales` / `sideGameChipSales` / `tournamentsSales` += それぞれの categoryBreakdown
   - `orderCount` += 1
   - `dailySales.{businessDate}` += grossSales
   - `paymentTotals.{method}` += それぞれの paymentTotals
3. `analyticsMonthly/{monthKey}/aggregationMarkers/{billId}_cycle1_settle` doc が作成され、中身は `{ type: 'settle', billId, cycleNo: 1, businessDate, processedAt }`
4. `analyticsMonthly/{monthKey}/days/{businessDate}` / `byCategory/summary` / `byUser/{userId}` / `byTemplateTournaments/{templateKey}` も同様に増加

### 5.2 シナリオ B: post-settlement adjustment（line のみ）

**準備**:
1. シナリオ A で settle 済みの bill `B-A` を用意
2. `createPostSettlementAdjustment` callable に以下のリクエストを送る:
   ```json
   {
     "billId": "B-A",
     "idempotencyKey": "adj-test-1",
     "adjustmentType": "increase_collection_pending",
     "adjustmentAmountIncl": 500,
     "lines": [
       { "targetCategory": "extra", "targetName": "late-fee", "operationType": "extra", "qtyDelta": 1, "amountInclDelta": 500 }
     ]
   }
   ```

**期待**:
1. callable response で `adjustmentId` が返る
2. `bills/{B-A}/settlementCycles/1/adjustments/{adjustmentId}` doc 作成
3. `analyticsMonthly/{monthKey}.grossSales` += 500、`extraCostSales` += 500、`dailySales.{businessDate}` += 500
4. `aggregationMarkers/adj_{adjustmentId}` 作成（`{ type: 'adjustment', billId, adjustmentId, monthKey, businessDate }`）
5. log で `analyticsApplied: true` / `analyticsCashActionApplied: false`

### 5.3 シナリオ C: adjustment + immediate cashAction

**準備**:
1. シナリオ A の bill `B-A2` を用意
2. `createPostSettlementAdjustment` で `adjustmentType: 'decrease_refunded'` + `immediateCashAction: { method: 'cash' }` を送る

**期待**:
1. response で `adjustmentId` と `cashActionId` が両方返る
2. adjustment 反映: `grossSales` -= 1000、`itemsSales` -= 1000 等
3. cashAction 反映: `paymentTotals.cash` -= 1000... ではなく、refund では paymentTotals は **減らない**（仕様書 §8.4）
   - **注**: refund cashAction の場合、`processCashActionAnalyticsAtomically` が early return するため `paymentTotals` は不変
   - immediateCashAction が refund なら `aggregationMarkers/cash_{cashActionId}` も作成されない（applier 内で early return）
4. `analyticsApplied: true` / `analyticsCashActionApplied: false`（refund は no-op）

### 5.4 シナリオ D: collection で paymentTotals 増分

**準備**:
1. bill `B-D`: `status='post_settlement_pending'` で `requiredActionType='collection'`、`requiredActionIncl=2000` を保持
2. `recordPostSettlementCollection` callable に以下を送る:
   ```json
   {
     "billId": "B-D",
     "idempotencyKey": "col-test-1",
     "amountIncl": 2000,
     "methodBreakdown": [{ "method": "credit_card", "amountIncl": 2000 }],
     "allocations": [{ "adjustmentId": "<対象 adj id>", "amountIncl": 2000 }]
   }
   ```

**期待**:
1. callable 成功
2. `analyticsMonthly/{monthKey}.paymentTotals.credit_card` += 2000
3. `analyticsMonthly/{monthKey}/days/{businessDate}.byPaymentMethod.credit_card` += 2000
4. `analyticsMonthly/{monthKey}/byUser/{userId}.paymentTotals.credit_card` += 2000
5. `grossSales` / `itemsSales` 等は不変
6. `aggregationMarkers/cash_{cashActionId}` 作成
7. log で `analyticsApplied: true` / `analyticsEnabled: true`

### 5.5 シナリオ E: refund で paymentTotals は変わらない

**準備**:
1. bill `B-E`: `requiredActionType='refund'`、`requiredActionIncl=1500`
2. `recordPostSettlementRefund` callable に同型のリクエストを送る

**期待**:
1. callable 成功
2. `bills/{B-E}/settlementCycles/.../cashActions/{cashActionId}` doc 作成（cashActionType: refund）
3. **`analyticsMonthly` の paymentTotals は不変**
4. `aggregationMarkers/cash_{cashActionId}` doc は **作成されない**（refund 時は applier 内で early return）
5. log で `analyticsApplied: false`（refund はそもそも analytics 反映なし）

### 5.6 シナリオ F: reopen で rollback

**準備**:
1. シナリオ A〜E の合算 state を持つ bill `B-F` を用意（settle + adjustment + collection cashAction 完了）
2. `reopenAccountedBill` callable を呼ぶ

**期待**:
1. `bills/{B-F}.status='open'` に戻る
2. `bills/{B-F}.reopenSummary.currentSettlementCycle = 2`、`latestSettledCycle = 1` 維持
3. `bills/{B-F}/settlementCycles/1.cycleState='reopened'`
4. `bills/{B-F}/settlementCycles/1/adjustments/*` の effective なものが `cancelled_by_reopen` に遷移
5. `analyticsMonthly/{monthKey}` の各値が **rollback され、reopen 直前の状態から baseline + adj + collection 分が引かれている**:
   - `grossSales`: シナリオ A の baseline + シナリオ B の adjustment が引かれる（シナリオ E の refund は元から無寄与なので変わらない）
   - `paymentTotals.{method}`: シナリオ A の baseline + シナリオ D の collection が引かれる
6. `aggregationMarkers/reopen_{billId}_cycle1` 作成（`{ type: 'reopen_rollback', billId, oldCycleNo: 1, monthKey, businessDate, processedAt }`）
7. 既存 marker（`{billId}_cycle1_settle` / `adj_{...}` / `cash_{...}`）は **残存**（audit 用）
8. log で `analyticsRollbackApplied: true` / `analyticsEnabled: true`

### 5.7 シナリオ G: reopen 後の resettle

**準備**:
1. シナリオ F の reopen 直後の bill `B-F` を用意
2. 必要なら `appendItem` 等で内容変更
3. 再 settle まで進める（`accounting` callable 等）

**期待**:
1. `bills/{B-F}.status='settled'` に戻る
2. `bills/{B-F}.reopenSummary.latestSettledCycle = 2`
3. `analyticsMonthly/{monthKey}` の各値が **新 cycle の baseline で増分される**（cycle1 が rollback 済みなので、cycle2 の値で純増）
4. `aggregationMarkers/{billId}_cycle2_settle` 作成
5. `aggregationMarkers/{billId}_cycle1_settle` / `reopen_{billId}_cycle1` も並行して残存

### 5.8 シナリオ H: idempotency

**準備**:
1. シナリオ B と同じ bill / リクエストで callable を **2 回送る**

**期待**:
1. 1 回目: 通常通り反映、`analyticsApplied: true`
2. 2 回目: callable response が同じ（idempotency hit）
3. `analyticsMonthly` は 1 回目の値のまま（2 回 increment されていない）
4. 2 回目の log では `reused: true` / `analyticsApplied: false`（reused 時は analytics スキップ）

### 5.9 シナリオ I: analytics 失敗時の callable 成功

**準備**:
1. (可能なら) Firestore セキュリティルールやネットワーク障害を一時的に induce して `analyticsMonthly` への書き込みを失敗させる
2. シナリオ B と同様の adjustment callable を呼ぶ

**期待**:
1. callable は **成功で返る**（`success: true`）
2. `bills/{billId}/settlementCycles/.../adjustments/{adjustmentId}` doc は作成されている（main tx 成功）
3. `analyticsMonthly` には反映されない
4. `logOpsError` で `operation: 'processAdjustmentAnalyticsAtomically'`、`outcome: 'fail'` のエラーログが出る
5. 後続の運用で nightly 再集計（後続 step）または手動補正で訂正可能

### 5.10 シナリオ J: feature flag OFF

**準備**:
1. `storeMeta/config.features.settlementAggregatorEnabled = false` に設定
2. シナリオ B と同様の adjustment callable を呼ぶ

**期待**:
1. callable は成功
2. `bills/{billId}/.../adjustments/...` doc は作成される（main tx 成功）
3. `analyticsMonthly` には反映されない（applier が呼ばれない）
4. log で `analyticsEnabled: false` / `analyticsApplied: false`

## 6. Firestore Console / Emulator UI での確認ポイント

各シナリオで:

1. `analyticsMonthly/{monthKey}` doc の各 field 値（`grossSales` / `itemsSales` / `paymentTotals.*` 等）
2. `analyticsMonthly/{monthKey}/days/{businessDate}` doc
3. `analyticsMonthly/{monthKey}/byCategory/summary` doc
4. `analyticsMonthly/{monthKey}/byUser/{userId}` doc
5. `analyticsMonthly/{monthKey}/byTemplateTournaments/{templateKey}` doc（tournament line がある場合のみ）
6. `analyticsMonthly/{monthKey}/aggregationMarkers/*` の各 marker doc（type / billId / cycleNo / processedAt 等）

## 7. ログ確認

Cloud Logging（または Functions Emulator のログ）で次を確認:

- 成功時:
  - `processAdjustmentAnalyticsAtomically: starting analytics update`
  - `processAdjustmentAnalyticsAtomically: analytics update completed`
  - 各 callable の `logOpsSuccess` で `analyticsApplied: true` / `analyticsCashActionApplied` / `analyticsRollbackApplied` / `analyticsEnabled`
- 失敗時:
  - `logOpsError` で `operation: 'processAdjustmentAnalyticsAtomically' / 'processCashActionAnalyticsAtomically' / 'processReopenRollbackAnalyticsAtomically'`
  - `outcome: 'fail'`
- skip（idempotent）時:
  - `processAdjustmentAnalyticsAtomically: marker already exists, skipping`
  - `processCashActionAnalyticsAtomically: marker already exists, skipping`
  - `processReopenRollbackAnalyticsAtomically: marker already exists, skipping`

## 8. 旧 events 経路の不変確認

- 旧 `enqueueEvent` / `buildEventDelta` / `appendEventLog` / 旧 `bills/{billId}/events` 経路は touch していない
- 既存の旧経路 trigger（`billsEventsOnCreate` 等）は不変
- 旧 events 経路は段階的に廃止予定（後続 step）

## 9. NG パターンと対処

| 症状 | 想定原因 | 対処 |
|---|---|---|
| `analyticsMonthly` に値が反映されない | feature flag が OFF / storeMeta/config 不在 | `storeMeta/config` を Firestore で確認、デフォルト `true` でも値が反映されない場合 emulator 設定を確認 |
| `aggregationMarkers/adj_*` が生成されない | 同 idempotencyKey で 2 回目以降の呼び出し（reused: true） | log で `reused: true` を確認、これは正常挙動 |
| `paymentTotals` が refund 時に減っていない | 仕様書 §8.4 通り | これは正常挙動。refund では paymentTotals を直接減らさない |
| reopen 後 `analyticsMonthly` が負値 | rollback の対象 adjustment 範囲ミス | log で `processReopenRollbackAnalyticsAtomically: starting analytics rollback` の `grossSalesNeg` / `paymentMethodsNegCount` を確認、bill 配下の `adjustments` の `adjustmentState` を Firestore Console で確認 |
| reopen 後 resettle で marker 衝突 (`already exists` エラー) | `currentSettlementCycle` が古いまま | bill の `reopenSummary.currentSettlementCycle` を Firestore で確認、`reopenAccountedBill` 完了後に +1 されているはず |
| `analyticsApplied: false` で log にエラーなし | feature flag OFF or businessDate 不在 | `storeConfig` の値、`bill.businessDate` の値を確認 |
