## 1. 実装概要

仕様書 [03_adjustments管理.md](/Users/yahatayuusei/Documents/GitHub/amuse_app_template/docs/事後イベント（会計後調整系）本番化/仕様実装管理/04_仕様書/03_adjustments管理.md) に基づき、bill の会計後差分を `bills/{billId}/settlementCycles/{cycleNo}/adjustments/{adjustmentId}` に保存する新経路を、**新規 callable / 新 service** として追加した。

主な実装:

- 4 パターン (`decrease_refund_pending` / `decrease_refunded` / `increase_collection_pending` / `increase_collected`) の adjustment を保存
- `lines[]` の必須化と `sum(amountInclDelta) = ±adjustmentAmountIncl` の整合検証
- tournament line の `targetId` / `operationType` 必須要件
- `settlementCycles/{cycleNo}.nextSequenceNo` の採番と increment（同一カウンタを adjustment と cashAction で共有）
- opposite-direction 内部相殺ロジック（仕様書 §15）
- `requiredActionRemainingIncl` の direction 別合計から parent `requiredActionType / requiredActionIncl` を派生
- 仕様書 §16.3 の不変則（refund 側と collection 側の両 remaining 同時 > 0 を許可しない）assertion
- immediate パターン (`decrease_refunded` / `increase_collected`) で同一トランザクション内に最小 shape の cashAction doc を作成
- parent doc の `currentSummary.claimTotalIncl / netSalesIncl / refundedTotalIncl / receivedTotalIncl` および `postSettlementState.totalAdjustmentsIncl / totalRefundedIncl / totalCollectedIncl / requiredActionType / requiredActionIncl / lastRecordType / lastRecordAt / lastRecordId / hasPostSettlementActivity` を更新
- 新 status (`post_settlement_pending` / `settled`) を新経路でのみ書き込む

旧 `bills/{billId}/events` 系列（`postEventAdjustment` / `postEventRefund` / `postEventCancel` / `postEventReopen` / `billsEventsOnCreate` / `updateAccounting` / `processRefund`）は **一切変更していない**。Step01 / Step02 と同方針で、新経路の追加のみで旧経路と並行する。UI 切替は Step06 主責務。

## 3. 実装中の判断

### 3.1 仕様解釈

- 仕様書 §13.5「`sum(lines[].amountInclDelta) = adjustmentAmountIncl`」と §11 の `requiredActionRemainingIncl >= 0` を両立させるため、`adjustmentAmountIncl` を **正の絶対値**、`amountInclDelta` を **direction に応じた符号付き** とする解釈で実装した。`sum` 検証は `±adjustmentAmountIncl`（direction による）で行う。
- 仕様書 §11 の `adjustmentState` 値域に `cancelled_by_reopen` を含めるが、この値への遷移ロジックは Step05 主責務であり、Step03 では値域定義と offset / cashAction 計算で当該 state を **対象外** として扱う実装に閉じた。
- 仕様書 §16.1 の `lastRecordType = adjustment` は immediate パターンでも **`adjustment` 固定** とした。Step04 で later cashAction を実装する際に `cash_action` を上書きする想定。

### 3.2 Step04 / Step06 / Step07 / Step05 への境界

- cashAction の field 拡張・later パターン・厳密 validation・`cashflowBusinessDate` の `calcBusinessDate` 連携 → **Step04 主責務**
- `cancelled_by_reopen` への遷移、`reopen` 実行フロー → **Step05 主責務**
- UI からの新 callable 接続、旧 `updateAccounting` / `processRefund` の差し替え → **Step06 主責務**
- adjustment line の `analyticsMonthly` 配賦本接続 → **Step07 主責務**

### 3.3 実装都合での判断

- adjustment doc の id は `adjustmentsCollectionRef.doc()` で **transaction 冒頭に確定** させる。これは immediate cashAction の `allocations[].adjustmentId` に同一 id を載せる必要があるため。
- idempotency doc の id は `createPostSettlementAdjustment:${idempotencyKey}` で prefix を付ける。同一 bill に対する `startAccounting` 等の idempotency と key 衝突を避ける。
- idempotency doc に `result` field として最小限の構造体（adjustment id / sequenceNo / type / direction / amountIncl / state / parent status 等）を保存し、replay 時にそれを返却する。Step01 / Step02 では `result` を保存していなかったため、ここでパターンを足した形になる。
- cashAction の `methodBreakdown` は引数 `method`（default: `'cash'`）を 1 件のみで構成する。Step04 で multi method 対応する。
- cashAction の `cashflowBusinessDate` は引数で渡された値を優先し、なければ `bill.businessDate` を借用する。`calcBusinessDate` の AMBIGUOUS / NONE 処理は Step04 で本格化。
- transaction 内のロジック量が多いため、検証 / offset / parent 派生はすべて純粋関数 (`services/adjustments.ts` / `services/cashActions.ts` / `services/parentSummary.ts`) に切り出し、repo は read / build / write の組み立てに集中させた。

### 3.4 見送ったもの

- 旧 `bills/{billId}/events` 経路の改修・廃止
- 旧 callable (`updateAccounting` / `processRefund`) の新経路への差し替え
- `adjustment` の取消・再発行（`supersededByAdjustmentId` の運用本実装）
- `lines[]` の `analyticsMonthly` への line-level 配賦

## 5. 補足メモ

- 旧経路と新経路を同時に呼ぶと、parent doc の `postEvents.*`（旧経路が更新）と `postSettlementState.*`（新経路が更新）が並走する。Step03 では UI が新経路を呼ばないため業務的には発生しない想定だが、Step06 で UI 切替する際にこの dual-write が解消される前提を 07_後続伝達 に明記する。
- `post_settlement_pending` 新 status は新経路のみが書く。旧経路（`billsEventsOnCreate`）が `partially_refunded` / `refunded` / `voided` / `in_progress` を書き続けるが、`createPostSettlementAdjustment` は `settled` または `post_settlement_pending` 以外の status を許可しない（`open` / `settling` / `partially_refunded` / `refunded` / `voided` / `in_progress` を弾く）。
- adjustment doc id はクライアント生成ではなく Firestore auto-id を採用。仕様書 §6 では `{adjustmentId}` の生成方法は明示されていないため、auto-id で衝突を避ける選択にした。
- `setStaleStatusForOldClient` 等の特殊ハンドリングは入れていない。
