# 08_実機確認手順

## 1. このファイルの目的

このファイルは、Step03 が本当に完了しているかを実機 / Firestore 目視で確認するための手順書である。

ただし Step03 では UI 切替を行っていないため、**画面操作だけでは新経路 (`createPostSettlementAdjustment` callable) を呼び出せない**。

したがって本ファイルでは次の 2 種類の確認手順を併記する。

- 自動確認（CI / Emulator 経由）: 必須
- 手動確認（callable を直接呼び出す）: 推奨

UI 切替後の実機確認は Step06 の `08_実機確認手順.md` で改めて行う。

## 2. 事前準備

- 開発環境で Functions / Firestore Emulator を起動できる
- node_modules がインストール済み（`functions` で `npm install`）
- 検証用の bill を Step02 までの手順で作成し、settle 状態にできる
- Firestore Emulator UI で `bills/{billId}/settlementCycles/{cycleNo}` 配下が見られる

```bash
cd functions

npm run test
```

確認ポイント:

- build が exit 0 で成功する
- 既存テスト + Step03 で追加した次のテストがすべて pass する

  - `__tests__/helpers/billsApi/cashActions.spec.ts`

### 3.2 Step02 / Step01 の regression

```bash
npm run test -- __tests__/callables/cancelAccounting.spec.ts
```

## 4. 手動確認手順（推奨）

### 4.1 シナリオ1: `decrease_refund_pending`（差額返金が残る）

1. 検証用 bill を `status = settled` の状態にする
2. Functions Emulator 上で次の callable を直接実行する（`functions:shell` か curl、もしくは ad-hoc test script）
   - callable 名: `createPostSettlementAdjustment`
   - 入力例:

```json
{
  "billId": "<billId>",
  "adjustmentType": "decrease_refund_pending",
  "adjustmentAmountIncl": 500,
  "lines": [
    { "targetCategory": "item", "targetId": "i1", "targetName": "Beer", "operationType": "delete", "qtyDelta": -1, "amountInclDelta": -500 }
  ],
  "note": "shortage"
}
```

3. Firestore で次を確認

- `bills/{billId}` 親
  - `status = post_settlement_pending`
  - `postSettlementState.totalAdjustmentsIncl = -500`（差は負）
  - `postSettlementState.requiredActionType = 'refund'`
  - `postSettlementState.requiredActionIncl = 500`
  - `postSettlementState.lastRecordType = 'adjustment'`
  - `currentSummary.netSalesIncl` が 500 減
- `bills/{billId}/settlementCycles/{cycleNo}/adjustments/{adjustmentId}`
  - `adjustmentType = decrease_refund_pending`
  - `adjustmentSignedAmountIncl = -500`
  - `requiredActionRemainingIncl = 500`
  - `adjustmentState = effective`
  - `lines[]` が入力どおり 1 件
- `bills/{billId}/settlementCycles/{cycleNo}/cashActions` が**空**

### 4.2 シナリオ2: `decrease_refunded`（即時返金）

1. 同じ bill か、別の settled bill に対して次を実行

```json
{
  "billId": "<billId>",
  "adjustmentType": "decrease_refunded",
  "adjustmentAmountIncl": 300,
  "lines": [
    { "targetCategory": "item", "targetId": "i2", "targetName": "Wine", "operationType": "delete", "qtyDelta": -1, "amountInclDelta": -300 }
  ],
  "immediateCashAction": { "method": "cash" }
}
```

2. Firestore で次を確認

- `bills/{billId}` 親
  - `status = settled`（即時で消化されたため `post_settlement_pending` には入らない、もしくは短期間でクリアされる）
  - `postSettlementState.totalAdjustmentsIncl = -300`
  - `postSettlementState.requiredActionType = 'none'`
  - `postSettlementState.requiredActionIncl = 0`
  - `postSettlementState.lastRecordType = 'adjustment'`
  - `currentSummary.refundedTotalIncl` が 300 増
- `bills/{billId}/settlementCycles/{cycleNo}/adjustments/{adjustmentId}`
  - `adjustmentType = decrease_refunded`
  - `requiredActionRemainingIncl = 0`
  - `adjustmentState = completed_by_cash_action`
- `bills/{billId}/settlementCycles/{cycleNo}/cashActions/{cashActionId}`
  - `cashActionType = refund_for_adjustment`
  - `amountIncl = 300`
  - `methodBreakdown[0].method = 'cash'`
  - `allocations[0].adjustmentId == adjustmentId`

### 4.3 シナリオ3: `increase_collection_pending`（差額徴収が残る）

入力例:

```json
{
  "billId": "<billId>",
  "adjustmentType": "increase_collection_pending",
  "adjustmentAmountIncl": 800,
  "lines": [
    { "targetCategory": "item", "targetId": "i3", "targetName": "Whiskey", "operationType": "add", "qtyDelta": 1, "amountInclDelta": 800 }
  ]
}
```

確認ポイント: シナリオ1 と対称。`requiredActionType = 'collection'`, `requiredActionIncl = 800`, `currentSummary.netSalesIncl += 800`

### 4.4 シナリオ4: `increase_collected`（即時徴収）

入力例:

```json
{
  "billId": "<billId>",
  "adjustmentType": "increase_collected",
  "adjustmentAmountIncl": 200,
  "lines": [
    { "targetCategory": "extra", "targetId": "e1", "targetName": "ServiceCharge", "operationType": "add", "qtyDelta": 0, "amountInclDelta": 200 }
  ],
  "immediateCashAction": { "method": "cash" }
}
```

確認ポイント:

- `cashAction.cashActionType = collection_for_adjustment`
- `currentSummary.receivedTotalIncl` が 200 増
- `adjustmentState = completed_by_cash_action`

### 4.5 シナリオ5: opposite-direction offset

シナリオ3 で `requiredActionRemainingIncl = 800`（collection 残）の bill に対して、`decrease_refund_pending` で 500 を adjustment 追加する。

入力例:

```json
{
  "billId": "<billId>",
  "adjustmentType": "decrease_refund_pending",
  "adjustmentAmountIncl": 500,
  "lines": [
    { "targetCategory": "item", "targetId": "i9", "targetName": "Discount", "operationType": "delete", "qtyDelta": 0, "amountInclDelta": -500 }
  ]
}
```

確認ポイント:

- 既存 collection adjustment の `requiredActionRemainingIncl` が `800 - 500 = 300` に減る
- 既存 collection adjustment の `adjustmentState = effective`（部分相殺なので未完了）
- 新 refund adjustment の `requiredActionRemainingIncl = 0`
- 新 refund adjustment の `adjustmentState = completed_by_offset`
- bill 親
  - `postSettlementState.requiredActionType = 'collection'`
  - `postSettlementState.requiredActionIncl = 300`

### 4.6 シナリオ6: idempotent replay

シナリオ1 と同じ `idempotencyKey` で 2 回実行する。

確認ポイント:

- 1 回目で adjustment doc が作られる
- 2 回目で adjustment doc は新規作成されず、レスポンスは 1 回目と同じ shape を返す
- `bills/{billId}/idempotency/createPostSettlementAdjustment:{key}` に `requestHash` と `result` が保存されている

## 5. Step03 を完了と言ってよい判定

次をすべて満たしたら Step03 は完了と言ってよい。

1. 自動確認（3.1 / 3.2）がすべて pass する
2. シナリオ1〜4 が手元で動作確認できる、または Emulator integration test (`createPostSettlementAdjustment.spec.ts`) で代替確認できる
3. シナリオ5 の opposite-direction offset が想定どおり動く
4. シナリオ6 の idempotent replay が想定どおり動く
5. 旧経路（`postEventAdjustment` / `processRefund` / `updateAccounting`）が壊れていない（手動 or 既存 e2e で確認）
6. `bills/{billId}/events` への書き込みが Step03 では発生しない（新経路は events を一切触らない）

## 6. 補足

- analytics / dailyReport への反映は Step07 の責務
- 後続 cashAction による remaining 解消（later パターン）は Step04 の責務
