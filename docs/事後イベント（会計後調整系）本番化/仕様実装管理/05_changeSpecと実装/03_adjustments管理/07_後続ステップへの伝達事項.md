# 07_後続ステップへの伝達事項

## 1. Step04（cashActions 管理）への伝達

### 1.1 Step03 で先行実装した cashAction の最小範囲

Step03 で immediate パターン (`decrease_refunded` / `increase_collected`) を仕様書 §14.2 / §14.4 どおりに動かすため、以下を **最小 shape** で先行実装した。Step04 ではこれを土台にして本実装する。

- `bills/{billId}/settlementCycles/{cycleNo}/cashActions/{cashActionId}` への保存
- 必須 field（`sequenceNo` / `cashActionType` / `amountIncl` / `executedAt` / `executedBy` / `cashflowBusinessDate` / `methodBreakdown[]` / `allocations[]` / `note`）を `services/cashActions.ts` の `buildImmediateCashActionDoc` で組み立て
- `methodBreakdown[]` は引数 `method`（default: `'cash'`）を 1 件のみで構成
- `allocations[]` は新規 adjustment 1 件分の単一 allocation のみ
- `cashflowBusinessDate` は引数を優先し、なければ `bill.businessDate` を借用
- `sequenceNo` は `settlementCycles/{cycleNo}.nextSequenceNo` を adjustment と共有して採番（adjustment + 1）
- `cashAction.amountIncl == sum(methodBreakdown[].amountIncl) == sum(allocations[].amountIncl)` の self-consistency check を実装

### 1.2 Step04 で Step03 から **拡張する必要がある** 範囲

- later パターン（`adjustment` 既存 → 後続 `cashAction` で remaining を解消）の callable / writer
- multi method の `methodBreakdown[]`（cash / credit_card / electronic_money 混在など）
- multi adjustment の `allocations[]`（1 cashAction で複数 adjustment の remaining を解消）
- `cashflowBusinessDate` の `calcBusinessDate` AMBIGUOUS / NONE 処理
- 仕様書 04 §9.4 / §10 / §11 / §12 / §13 / §14 / §15 / §16 の full validation
- parent 反映で `lastRecordType = 'cash_action'` を書く（Step03 では `'adjustment'` 固定）
- Step03 で immediate cashAction を作る分岐がある `repos/createPostSettlementAdjustment.ts` のロジックは、Step04 で立てる新 callable と整合する形で残す
  - 互換のため、Step03 の immediate 経路は **そのまま動かし続ける** 方針が自然
  - Step04 で immediate を新 callable 経由に統合したくなった場合は、その時点で別途設計

### 1.3 Step04 で **触っていい** Step03 産のコード

- `services/cashActions.ts`：field 拡張 / multi method / multi allocation 対応で書き換え可
- `repos/createPostSettlementAdjustment.ts` の immediate 部分：必要なら拡張可

### 1.4 Step04 で **触らない** 方が良い Step03 産のコード

- `services/adjustments.ts`：4 パターン分岐 / opposite offset / lines 検証は仕様書 §14 / §15 / §16 を Step03 で確定させたもの
- `services/parentSummary.ts` の `buildPostSettlementStateAfterAdjustment` / `buildCurrentSummaryAfterAdjustment` / `deriveStatusAfterAdjustment`：adjustment 派生だけを担当する。Step04 では **cashAction 専用の派生 helper** を別途追加する想定

## 2. Step05（reopen と再会計）への伝達

### 2.1 `cancelled_by_reopen` 遷移

Step03 では `adjustmentState` の値域として `cancelled_by_reopen` を**定義のみ**している。実際にこの値を書く処理は Step05 で実装する。

具体的には:

- old cycle の `cycleState = reopened` 遷移
- old cycle の `adjustmentState = effective` adjustment を `cancelled_by_reopen` に一括遷移する
- このとき `requiredActionRemainingIncl` は変更しないが、`summarizeRemainingByDirection` で集計対象外になる
- Step03 の `applyOppositeDirectionOffset` / `summarizeRemainingByDirection` は `cancelled_by_reopen` を集計対象外として既に扱っているので、Step05 はその前提で安心して使える

### 2.2 reopen 後の current cycle 切替

- Step03 で書いた `repos/createPostSettlementAdjustment.ts` は、bill の `reopenSummary.currentSettlementCycle` を current cycle として参照する
- Step05 で reopen して new cycle を open するとき、`reopenSummary.currentSettlementCycle` を進めれば、Step03 の callable は自動的に new cycle 配下の `adjustments/` を見るようになる
- 新 cycle の `nextSequenceNo` 初期値は `1`（Step02 の `buildInitialCycleDoc` 参照）

### 2.3 cycle の整合性

- Step03 が要求する事前条件: 対象 cycle doc が存在し、`nextSequenceNo` が number として書かれていること
- Step02 の `createBillWithActiveStay` / `billsOnSettle` で初期 cycle が確実に作られているため、通常運用では欠損しない
- Step05 で reopen 時に作る new cycle も、`buildInitialCycleDoc` を使えば自動的に `nextSequenceNo: 1` で始まる

## 3. Step06（要対応の会計画面と一覧取得）への伝達

### 3.1 新 callable

- callable 名: `createPostSettlementAdjustment`
- input: `{ billId, idempotencyKey?, clientNonce?, adjustmentType, adjustmentAmountIncl, lines[], note?, immediateCashAction?: { method?, cashflowBusinessDate?, note? } }`
- output: `{ success, billId, cycleNo, adjustmentId, cashActionId, adjustment{...}, parent{...}, diagnostics? }`
- 権限: `device.role === 'admin'` または `device.options.accounting === true`
- 旧 callable (`updateAccounting` の eventType=`adjustment`、`processRefund`) は今後しばらく並存

### 3.2 UI 切替方針

- Step06 では UI（`postAccountingAdjustmentDialog.dart` / `postAccountingRefundDialog.dart` 等）を新 callable 経由に切り替える
- 切り替え時の同等性確認のため、旧経路の `bills/{billId}/events` への書き込みが停止する一方、新経路の `bills/{billId}/settlementCycles/{cycleNo}/adjustments/` への書き込みが開始される
- parent doc では `postEvents.*` の更新が止まり、`postSettlementState.*` / `currentSummary.*` / `status (post_settlement_pending / settled)` の更新だけが続くようになる

### 3.3 status 値の扱い

- Step03 が書く status: `post_settlement_pending` / `settled`
- 旧 trigger が書く status: `partially_refunded` / `refunded` / `voided` / `in_progress`
- UI 切替後は新 status のみが書かれるようになる前提で、画面側の status 表示処理を更新する必要がある

### 3.4 一覧取得

- 「要対応」一覧は `postSettlementState.requiredActionType !== 'none'` または `status === 'post_settlement_pending'` で抽出する
- Step03 で旧 `getRefundHistory` 等は触っていないため、Step06 で新一覧 API を立てるか、Flutter 側でローカルに `bills/{billId}/settlementCycles/{cycleNo}/adjustments` を read するかを設計する

## 4. Step07（analyticsMonthly 更新）への伝達

### 4.1 line[] の最小 shape 保証

Step03 では仕様書 18 / step3.12 blockC §2.5 / 2.6 が要求する line 構造（`targetCategory`, `targetId`, `targetName`, `operationType`, `qtyDelta`, `amountInclDelta`）を必須として保存する。Step07 ではこれを analytics 反映に使える前提でよい。

特に tournament line:

- `targetCategory = 'tournament'`
- `targetId` は templateKey / templateId（Step03 で必須化済み）
- `operationType` は `entry` / `reentry` / `addon`
- `analyticsMonthly.byTemplateTournaments` 更新に必要な情報がそのまま揃う

### 4.2 Step07 で触る場所

- adjustment 作成時の analyticsMonthly 差分は **Step03 の `repos/createPostSettlementAdjustment.ts` の中では実装していない**
- Step07 では bills のサブコレクション `settlementCycles/{cycleNo}/adjustments/{adjustmentId}` への書き込みを契機にした trigger を新規追加するか、既存 `aggregator` 系列に hook を足すかを設計する
- 現行 `postEventAdjustment` 経由の旧 events は `aggregator` 側で `eventsLog` への追記対象になっている（Step03 では旧経路を触っていない）。新経路の analytics 接続は Step07 で別途設計する

### 4.3 cashAction の analytics 接続

- immediate cashAction の `paymentTotals` への反映は仕様書 04 §13 / 07 §の責務
- Step03 の cashAction 最小 writer は analytics には接続していない
- Step04 の field 拡張完了 → Step07 で analytics 接続、の順で進める想定

## 5. 共通注意

### 5.1 旧経路と新経路の併存

- Step03 では UI 切替を行わないので、新 callable は呼ばれない（テスト経由でのみ実行される）
- 業務的には旧経路（`postEventAdjustment` / `processRefund` / `updateAccounting`）が引き続き動く
- Step06 で UI 切替後、新経路のみが業務的に呼ばれるようになる

### 5.2 dual write はしない

- 同一 bill に対して新経路と旧経路を両方書くことは仕様化していない
- もし両方が呼ばれた場合、parent の `postEvents.*`（旧）と `postSettlementState.*`（新）は別 field なので **データ衝突は起きない** が、`status` は最後に書いた方が勝つ
- Step06 で UI 切替するときに、旧 callable を実質呼ばなくなる前提で運用設計する

### 5.3 migration / backfill

- Step03 では既存 bill の adjustments を新経路へ移すような migration は **行っていない**
- 既存 settled bill に対して新 callable を呼ぶことは仕様上可能（`status = settled` を許可しているため）
- 旧 events に基づく postEvents.* と新 adjustments に基づく postSettlementState.* は同一 bill 上で **別々の歴史** を持つ可能性がある

### 5.4 `supersededByAdjustmentId`

- Step03 では仕様書 §7 の必須 field として `supersededByAdjustmentId: null` を保存している
- adjustment 訂正フロー（既存 adjustment を別 adjustment で置き換える運用）は current-scope では未実装
- 後続 step で訂正フローを設計する場合、`supersededByAdjustmentId` に置き換え先 id を入れて、`adjustmentState` を `effective` 以外（例: `superseded`）にする想定

### 5.5 idempotency doc の result 保存

Step03 では `bills/{billId}/idempotency/createPostSettlementAdjustment:{key}` に `requestHash` だけでなく `result` field（adjustment id / 主要状態）も保存している。これは replay 時に正しいレスポンスを返すために必要であり、Step01 / Step02 にはない新パターン。Step04 / 以降で同様の callable を作る場合は同じパターンで `result` を保存することを推奨する。
