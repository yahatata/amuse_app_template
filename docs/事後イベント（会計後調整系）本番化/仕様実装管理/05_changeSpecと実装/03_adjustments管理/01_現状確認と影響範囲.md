## 4. 仕様との差分

### 4.1 保存先

仕様書 §6 では `bills/{billId}/settlementCycles/{cycleNo}/adjustments/{adjustmentId}` に保存することを要求。AsIs では `bills/{billId}/events/{eventId}` に保存しており、この path に新規実装が必要。

### 4.2 必須 field

仕様書 §7 で `sequenceNo` / `adjustmentType` / `adjustmentDirection` / `adjustmentAmountIncl` / `cashActionTypeAtCreation` / `cashActionHandledAtCreation` / `adjustmentState` / `requiredActionRemainingIncl` / `createdAt` / `createdBy` / `note` / `lines[]` / `supersededByAdjustmentId` を要求。AsIs の `events` doc では `type` / `adjustment.{sign, amountIncl}` 等しか保存しておらず、新仕様の field が一切揃わない。

### 4.3 4 パターンの分岐

仕様書 §8 と §14 で `decrease_refund_pending` / `decrease_refunded` / `increase_collection_pending` / `increase_collected` の 4 パターンを明示的に分岐する必要がある。AsIs は `sign` (+1/-1) のみで、cash 即時処理の有無を表す概念が存在しない。

### 4.4 `requiredActionRemainingIncl` と内部相殺

仕様書 §11.2 / §15 で同一 cycle 内の opposite-direction adjustment 同士を `sequenceNo` 順で内部相殺し、`completed_by_offset` で marking する必要がある。AsIs にはこの概念がない。

### 4.5 lines[] 必須化

仕様書 §13 と 18 で `lines[]` 必須・`sum(amountInclDelta) = adjustmentAmountIncl`・tournament line は `targetId / operationType` 必須を要求。AsIs は line 構造を持たない。

### 4.6 immediate cashAction の同一トランザクション化

仕様書 §14.2 / §14.4 で `decrease_refunded` / `increase_collected` は同一トランザクションで cashAction を作る必要がある。AsIs の `postEventRefund` は別 callable で別タイミングに動く。

### 4.7 parent 反映

仕様書 §16 で `currentSummary.claimTotalIncl/netSalesIncl` / `postSettlementState.totalAdjustmentsIncl/requiredActionType/requiredActionIncl/lastRecordType` / `status (post_settlement_pending or settled)` を組み立てる必要がある。AsIs trigger は `postEvents.*` 系のみを更新し、新仕様の field は未対応。

## 5. 影響範囲

### 5.1 Step04（cashActions 管理）

- Step03 で immediate cashAction の最小 writer を入れるため、Step04 では later パターンと field 拡張に集中できる
- `cashActions/{cashActionId}` の path / `sequenceNo` 採番 / `allocations[]` / `cashAction.amountIncl = sum(allocations[].amountIncl)` の不変則は Step04 で full validation を担う
- Step03 で書く cashAction は `methodBreakdown[]` の固定（例: `[{ method: 'cash', amountIncl }]`）と `allocations[]` 1 件の単純構造で start し、Step04 で多 allocation / multi method / `cashflowBusinessDate` のロジック化を行う

### 5.2 Step05（reopen と再会計）

- `cancelled_by_reopen` への遷移は Step05 で実装する
- Step03 では `adjustmentState` の値域として `cancelled_by_reopen` を受け入れる前提で field を定義するが、実際にこの値を書く処理は Step05

### 5.3 Step06（要対応の会計画面と一覧取得）

- 新 callable `createPostSettlementAdjustment` の UI 接続は Step06 主責務
- Step03 では internal API として完成させ、UI からの差し替えは Step06 で行う

### 5.4 Step07（analyticsMonthly 更新）

- adjustment line の category / tournament 配賦ルールは Step07 で `analyticsMonthly` に反映する
- Step03 では `lines[]` の最小 shape を仕様書 18 どおりに保存できることを保証する

### 5.5 既存機能

- 旧 `bills/{billId}/events` 経路の callable / trigger / spec は引き続き動く
- 旧 status (`partially_refunded` / `refunded` / `voided` / `in_progress`) は旧 trigger から引き続き書かれる
- 新 status `post_settlement_pending` は新経路でのみ書く
- 旧 `postEvents.*` フィールド群は新経路では更新しない（互換のため残置）

## 6. この時点のメモ

- Step03 は **新経路の追加** がメインで、旧経路は削除しない（Step01 / Step02 と同方針）
- immediate cashAction を Step03 で同一トランザクションで作ることに決めるが、最小 shape にとどめ、本実装は Step04 へ送る
- `supersededByAdjustmentId` は仕様書 §7 で必須 field だが、運用本実装（adjustment 訂正フロー）は current-scope では扱わない。Step03 では `null` 初期値で保存し、後続 step で利用する
- `note` は必須 field 扱いだが、ユーザー入力を許す実装ではなく、空文字や callable 引数で受け取った値をそのまま保存する形でよい
- `cancelled_by_reopen` への遷移ロジックは Step05 主責務、Step03 では値域定義のみ
