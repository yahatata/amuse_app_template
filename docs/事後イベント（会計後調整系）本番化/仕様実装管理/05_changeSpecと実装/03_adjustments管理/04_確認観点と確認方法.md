# 04_確認観点と確認方法

## 1. 自動確認

### 1.1 TypeScript build

- 目的: 新 service / repo / callable の追加で型崩れがないことを確認する
- コマンド:

```bash
npm --prefix functions run build
```

- 期待結果:
  - build 成功
  - TypeScript error なし
  - 既存のいずれの module にも no breaking change

### 1.2 unit テスト: `services/adjustments.ts`

- 目的: 純粋関数の正常系・異常系を Emulator 不要で検証する
- コマンド:

```bash
npm --prefix functions test -- __tests__/services/adjustments.spec.ts --runInBand
```

- 観点:
  - `validateAdjustmentInput` が 4 パターン以外を拒絶
  - `validateLines` が
    - line-less 入力で失敗
    - `sum(amountInclDelta) !== adjustmentAmountIncl` で失敗
    - 符号不一致で失敗
    - tournament line の `targetId / operationType` 不足で失敗
  - `applyOppositeDirectionOffset` が
    - 仕様書 §15.4 の例（refund 1000 後 collection 1500 → collection 残 500）を再現
    - 完全相殺ケースで両 adjustment が 0 になる
    - 同方向のみ存在で no-op
  - `summarizeRemainingByDirection` が
    - 両残り検出（不変則違反）を見抜ける
  - `buildAdjustmentDoc` が仕様書 §7 の必須 field を全部埋める

- 期待結果:
  - 全 it() 成功

### 1.5 Emulator 統合テスト: `createPostSettlementAdjustment`

- 目的: 4 パターン / opposite offset / status 遷移 / sequenceNo 採番を end-to-end で確認する
- コマンド:

```bash
firebase emulators:exec --only firestore "npm --prefix functions test -- __tests__/callables/createPostSettlementAdjustment.spec.ts --runInBand"
```

- ケース:
  1. happy path `decrease_refund_pending`
     - adjustment doc が `bills/{billId}/settlementCycles/1/adjustments/{adjustmentId}` に作成される
     - `adjustmentType=decrease_refund_pending` / `adjustmentDirection=decrease` / `cashActionTypeAtCreation=refund` / `cashActionHandledAtCreation=false`
     - `requiredActionRemainingIncl == adjustmentAmountIncl`
     - `adjustmentState=effective`
     - parent `currentSummary.claimTotalIncl` が減額分マイナスされる
     - parent `postSettlementState.requiredActionType=refund` / `requiredActionIncl=adjustmentAmountIncl` / `lastRecordType=adjustment`
     - parent `status='post_settlement_pending'`
     - cycle.nextSequenceNo: 1 → 2
  2. happy path `decrease_refunded` (immediate)
     - adjustment doc + cashAction doc が同一 transaction で作成される
     - adjustment `requiredActionRemainingIncl=0` / `adjustmentState=completed_by_cash_action`
     - cashAction `cashActionType=refund` / `amountIncl=adjustmentAmountIncl`
     - cashAction `allocations` が 1 件（adjustment 自身）、`methodBreakdown` が 1 件
     - parent `status='settled'` / `requiredActionType='none'`
     - cycle.nextSequenceNo: 1 → 3（adjustment と cashAction で 2 つ消費）
  3. happy path `increase_collection_pending`
     - parent `requiredActionType=collection`
     - その他は 1) と方向反対
  4. happy path `increase_collected` (immediate)
     - 2) と方向反対
  5. opposite-direction offset
     - 1) `decrease_refund_pending 1000` → 2) `increase_collection_pending 1500` を続けて作成
     - 1) の adjustment が `completed_by_offset` に遷移
     - 2) の adjustment は `requiredActionRemainingIncl=500`、`adjustmentState=effective`
     - parent `requiredActionType=collection` / `requiredActionIncl=500`
     - parent `status='post_settlement_pending'`
  6. opposite-direction offset 完全相殺
     - 1) `decrease_refund_pending 1000` → 2) `increase_collection_pending 1000`
     - 1) `completed_by_offset` / 2) `completed_by_offset`
     - parent `requiredActionType='none'` / `status='settled'`
  7. invalid input
     - `lines.length === 0` → `failed-precondition` HttpsError
     - `sum(amountInclDelta) !== adjustmentAmountIncl` → `failed-precondition`
     - tournament line の `targetId` 不足 → `failed-precondition`
  8. idempotent replay
     - 同一 `idempotencyKey` で再実行すると既存 adjustment doc が返り、cycle.nextSequenceNo が増えない
  9. status precondition
     - `status='open'` の bill に対して呼ぶと `failed-precondition`
     - `status='settling'` も同様

- 期待結果:
  - 全 it() 成功

## 2. テスト失敗時の再試行

### 2.1 エミュレータ再起動

エミュレータ依存テストが失敗した時は、まず Firebase Emulator を再起動して再試行する。

実施例:

```bash
firebase emulators:exec --only firestore "npm --prefix functions test -- __tests__/services/adjustments.spec.ts __tests__/services/cashActions.spec.ts __tests__/services/parentSummary.spec.ts __tests__/callables/createPostSettlementAdjustment.spec.ts --runInBand"
```

### 2.2 注意事項

- workspace 外の Jest を拾わないよう、必ず `npm --prefix functions test -- ...` を使う（`npx jest` を直接実行しない）
- adjustment / cashAction / cycle の transaction は同一 trx でコミットされるため、Emulator 接続が一時的に不安定だと一見「不変則違反」のように見えることがある。再起動して再試行する。

## 3. 手動 / 目視確認

### 3.1 Firestore 目視確認

対象 path:

- `bills/{billId}`（parent doc, 特に `currentSummary` / `postSettlementState` / `status`）
- `bills/{billId}/settlementCycles/{cycleNo}`（`nextSequenceNo` の変化）
- `bills/{billId}/settlementCycles/{cycleNo}/adjustments/{adjustmentId}`
- `bills/{billId}/settlementCycles/{cycleNo}/cashActions/{cashActionId}`（immediate のみ）

確認ポイント:

- adjustment doc の必須 field（仕様書 §7）が全て揃っている
- `lines[]` が 1 件以上、`sum(amountInclDelta) = adjustmentAmountIncl`
- pending パターンで `requiredActionRemainingIncl == adjustmentAmountIncl`
- immediate パターンで `requiredActionRemainingIncl == 0` / `adjustmentState='completed_by_cash_action'`
- cashAction doc が immediate の場合のみ存在し、`allocations[].adjustmentId` が adjustment 自身を指す
- parent `status` が `post_settlement_pending` または `settled`
- 旧 `postEvents.*` フィールドが新 callable 経由では更新されないこと（旧経路を呼んでいないため）

### 3.2 コードレビュー確認

- 新 callable / repo / service が transaction を 1 つにまとめている
- 旧 `events` 経路 (`postEventAdjustment` / `billsEventsOnCreate`) が変更されていない
- 旧 status 値 (`partially_refunded` / `refunded` / `voided` / `in_progress`) を新 callable から書いていない
- `parentSummary` の helper が adjustment 種別ごとに正しい field を更新している
- `cancelled_by_reopen` への遷移が含まれていない（Step05 へ送る）
- `cashAction` の field が最小 shape にとどまっている（Step04 で field 拡張する余地が残っている）
