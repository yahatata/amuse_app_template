# 07_後続ステップへの伝達事項

## 1. このファイルの役割

Step06 完了時点で、後続 step（Step07 / 旧経路統廃合 / 運用調整）に引き継ぐ事項と、Step06 で意図的に扱わなかった範囲を整理する。

## 2. Step07（analyticsMonthly 更新と日付帰属と line 配賦）への伝達

Step07 は仕様書 [07_analyticsMonthly更新と日付帰属とline配賦.md](/Users/yahatayuusei/Documents/GitHub/amuse_app_template/docs/事後イベント（会計後調整系）本番化/仕様実装管理/04_仕様書/07_analyticsMonthly更新と日付帰属とline配賦.md) を主責務とする。Step06 で関連する事項:

### 2.1 要対応一覧と analytics の関係

- Step06 の要対応一覧画面は `bills` 親 doc の `closeSummary` / `postSettlementState` / `status` のみを read。analytics 集計は読まない
- Step07 で analyticsMonthly に「未会計（carryover_unsettled）の bill 寄与」を反映するか否かを再検討する
- 寄与が遷移した場合、要対応一覧画面の数値は変えなくていい（一覧は `bills` 直接読みで完結）

### 2.2 post-settlement adjustment の analytics 配賦

- 仕様書 §15.x で analytics は別 collection で集計と書いてあるが、Step07 で正本を確定する
- `postSettlementState.requiredActionType` は要対応一覧の表示用、analytics は `adjustments[].lines[]` 経由の集計
- Step06 一覧画面は `requiredActionIncl` を表示用に使うが、analytics 集計には使わない

### 2.3 reopen 時の rollback 影響

- Step05 で reopen 時に effective adjustment が `cancelled_by_reopen` に遷移する
- Step07 の analytics 集計で、`cancelled_by_reopen` adjustment を rollback するか / 履歴として残すかを決める
- Step06 一覧画面は `adjustmentState='effective'` のみ判定対象なので、analytics 配賦の挙動とは独立

## 3. 旧経路統廃合への伝達（後続 step / 運用 step）

### 3.1 旧 dialog の統廃合

Step06 では新 dialog (`PostSettlementCollectionDialog` / `PostSettlementRefundDialog`) を要対応一覧画面の primary action からのみ呼ぶよう実装した。次の旧 dialog は **併存維持** している:

| 旧 dialog | 呼び出し元 | Step06 での扱い |
|---|---|---|
| `lib/Accounting/refundProcessingDialog.dart` | `AccountingPage` 内 | 不変、touch なし |
| `lib/Accounting/postAccountingRefundDialog.dart` | 旧 events 経路 | 不変、touch なし |
| `lib/Accounting/postAccountingAdjustmentDialog.dart` | 旧 events 経路 | 不変、touch なし |
| `lib/Accounting/postAccountingReopenDialog.dart` | 旧 events 経路 | 不変、touch なし |
| `lib/Accounting/postAccountingCancelDialog.dart` | 旧 events 経路 | 不変、touch なし |
| `lib/Accounting/postAccountingAdjustmentsPage.dart` | 既存 list | 不変、touch なし |

後続 step で:
- `AccountingPage` 内の事後操作も新 dialog に切り替える
- 旧 events 経路 dialog 群を削除
- `RefundProcessingDialog` 等の callable 接続を整理

### 3.2 旧 callable の段階的廃止

| 旧 callable | 新 callable |
|---|---|
| `postEventAdjustment` | `createPostSettlementAdjustment`（Step03 で追加） |
| `postEventRefund` / `processRefund` | `recordPostSettlementRefund`（Step04 で追加） |
| `postEventCollect` 系 | `recordPostSettlementCollection`（Step04 で追加） |
| `postEventReopen` | `reopenAccountedBill`（Step05 で追加） |

Step06 では併存維持。旧 callable の deprecation は別 step（運用調整 step）で:
1. 旧 callable に warn ログを追加
2. 旧 dialog を新 dialog に置き換え
3. 一定期間後、旧 callable を削除

### 3.3 `closeSnapshot` field の段階的廃止

- Step04 で `applyCloseSnapshot` が `closeSnapshot` と `closeSummary` の dual-write を実装
- Step06 では `closeSummary` のみ read
- `closeSnapshot` は他の場所（Flutter 旧画面など）でまだ read される可能性があるため、削除前に grep で全 read 箇所を洗い出すこと

## 4. Step06 が意図的に扱わなかった事項

- 旧 dialog (`RefundProcessingDialog` 等) の touch / 廃止 → 後続 step
- 旧 callable (`processRefund` / `postEventReopen` 等) の touch / 廃止 → 後続 step
- analytics への寄与（`analyticsMonthly` への書き込み） → Step07
- migration / backfill → 行わない（未リリース前提）
- Firestore security rules（要対応一覧 read 権限） → 後続 step
- 件数カウンター増設（`users.pendingAttentionCount` 等） → 行わない（client-side 集計で十分）
- paging（要対応 bill が大量にある店舗向け） → post-MVP（仕様書 §17.x）
- 複数 adjustment への按分 UI → post-MVP（仕様書 §17.5）
- 各 dialog で `cycleNo` / `targetAdjustmentId` を URL パラメータから取得 → 仕様書 §17.x、現状は dialog 起動時に bill から再 fetch
- `closeSnapshot` field の削除 → 段階的に運用調整 step で行う

## 5. 共通注意事項

### 5.1 旧経路と新経路の併存

Step06 完了時点で:

- 旧: `terminalHome` `未会計の会計` メニュー → 削除済（要対応の会計に統合）
- 旧: `AccountingPage` 内の事後操作（`refundProcessingDialog` 等） → 残存、後続 step で整理
- 新: `terminalHome` `要対応の会計` → `RequireSpecialAttentionPage` → 新 dialog → 新 callable

### 5.2 dual-write 維持

Step04 / Step05 で確定した dual-write 方針は Step06 でも維持:

- `applyCloseSnapshot` 内で `closeSnapshot` と `closeSummary` を dual-write
- Step06 では UI 側が `closeSummary` を read するが、`closeSnapshot` は touch しない
- Step06 完了後も dual-write を継続（`closeSnapshot` の他経路 read を考慮）

### 5.3 後方互換

- Step01〜05 で書いた既存 callable / trigger / helper の API 不変
- Step06 では Functions コードに変更なし
- 既存 cycle = 1 の bill に対する settle / post-settlement adjustment / cashAction 経路は不変

### 5.4 stream 設計

- `RequireSpecialAttentionPage` は 3 stream を別 listen で受けて client-side merge
- 後続 step で paging / 検索を入れる場合、`StreamBuilder` ではなく `query.snapshots(includeMetadataChanges: true)` で fine-grained に制御
- 件数が大量に伸びる店舗では、後続 step で `limit` + `paging` 戦略を検討（現在は無制限）

### 5.5 既存リグレッション

- `develop` baseline に 11 suites / 29 tests の既存 fail がある（`itemOrder/placeOrder.spec.ts` / `helpers/billsApi/startAccounting.spec.ts` 等）
- これらは Step01〜07 の本番化対象外（`FunctionCustomError` 移行後の test 期待値ズレ等が中心）
- 個別タスクとして別ブランチで対応する（Step01〜07 の path 上ではなく、`standardization/basis` の続編で対応）

### 5.6 dialog の input / callable の対応

| dialog | callable | 主な引数 |
|---|---|---|
| `PostSettlementCollectionDialog` | `recordPostSettlementCollection` | `{billId, amountIncl, methodBreakdown[], allocations[]}` |
| `PostSettlementRefundDialog` | `recordPostSettlementRefund` | 同上 |

dialog の current 実装では `allocations` を「effective adjustment の最初の 1 件に全額割り当て」で簡略化（仕様書 §17.5 の post-MVP）。複数 adjustment への按分 UI を入れる場合:
- dialog 内で `effectiveAdjustments` 全件を表示
- 各 adjustment に「割り当て金額」入力欄
- 合計が `amountIncl` と一致するかをクライアント validation
- callable に `allocations[]` を構造化して渡す

### 5.7 idempotencyKey の生成

- 新 dialog 内では callable 呼び出しに `idempotencyKey` を **明示的に渡していない**（callable 側で `clientNonce ?? randomUUID()` から自動生成）
- これは「dialog の submit 押下 1 回 = 1 callable 呼び出し」前提
- ダブル tap / 連打を防ぐため、dialog 側で `_submitting` フラグでボタン disabled 制御済み
- 仕様書 §11 の冪等性は callable 側で担保
