## 6. この時点のメモ

### 6.1 設計上の論点（要ユーザー確認）

#### 論点 1: ファイル分割方針

Step06 で `UnsettledAccountingPage` をどう扱うか:

- 案 A: 既存 `unsettledAccountingPage.dart` を改修してリネーム（`requireSpecialAttentionPage.dart`）し、内部実装も刷新。既存 import 箇所は新ファイル名に置換
- 案 B: 新規ファイル `requireSpecialAttentionPage.dart` を作成、旧 `unsettledAccountingPage.dart` は touch しない（旧画面は terminalHome から外し、デッドコード化）
- 案 C: 既存 `unsettledAccountingPage.dart` を改修、ファイル名は維持し中身だけ刷新

選択肢の比較:

| 案 | 影響 | 旧 dialog test への影響 | 実装ボリューム |
|---|---|---|---|
| A | rename + 改修 | 旧 import 全置換が必要 | やや大 |
| B | 新規追加、旧は孤立 | なし（旧は影響受けない） | 中 |
| C | ファイル名維持、中身刷新 | なし | 中 |

→ **推奨: 案 B**（旧画面が touch されないので影響範囲が明確、dead code として残るが Step07 以降で削除可能）

#### 論点 2: primary action 導線の callable 切替範囲

Step06 で primary action を経由した先の callable をどこまで切り替えるか:

- 案 A: Step06 では一覧画面のみ実装、primary action ボタンは tap で既存 dialog (`RefundProcessingDialog` / `postAccountingAdjustmentDialog`) を起動（callable 切替なし）
- 案 B: Step06 で `refund` / `collect` ボタンを新 callable (`recordPostSettlementRefund` / `recordPostSettlementCollection`) を呼ぶ新 dialog に切替（一覧 + 切替）
- 案 C: 案 A をベースに、新 dialog の最小プレースホルダだけ作って Step07 以降で本実装

→ **推奨: 案 A**（仕様書 §3「UI デザイン詳細」「component 構成」が非対象であることを尊重、Step06 のスコープを「一覧画面と判定条件」に限定。新 callable 切替は別 step で扱う）

ただし「Step04 handoff doc では Step06 で UI 切替予定」と書いていたため、ユーザーの意向次第で **案 B（refund / collection の新 callable 切替まで Step06 で実施）** にも対応可能。

#### 論点 3: ユーザー別カード件数内訳の取得方法

仕様書 §11.2 では `総件数` / `未会計 x件` / `追加徴収 x件` / `要返金 x件` を表示する必要がある:

- 案 A: 3 種別 (carryover / collection / refund) を `bills` から query → client-side で userId ごとに集計
- 案 B: users 配下に `requireSpecialAttentionCount` `collectionPendingCount` `refundPendingCount` を新設（counter 増設）

→ **推奨: 案 A**（仕様書 §15「要対応一覧都合で新しい共通正本 collection を作らない」/ §13 client-side merge OK と整合）

#### 論点 4: `closeSnapshot` 読み出し vs `closeSummary` 読み出し

現状 Flutter は `closeSnapshot.unresolved` を読んでいる（旧 field）。仕様書は `closeSummary.unresolved` を正本とする:

- 案 A: Step06 で `closeSummary` のみ読むように切替
- 案 B: dual-read defensive (`closeSummary || closeSnapshot`) で旧 field も並行サポート

→ **推奨: 案 A**（functions/applyCloseSnapshot.ts が `closeSummary` を必ず書くため、defensive dual-read は冗長）

#### 論点 5: `carryover_unsettled` の status 範囲

現状コードは `status in [open, settling]`。仕様書 §9.1 は `status=open` のみ:

- 案 A: 仕様書通り `status=open` のみ
- 案 B: defensive に `status in [open, settling]` を維持

→ **推奨: 案 A**（仕様書通り、`settling` は accounting 進行中の中間状態であり要対応一覧で表示する積極理由がない）

#### 論点 6: ユーザー表示名の選択

view model `userDisplayName` の source:

- 案 A: `bills.party.pokerName` を使う
- 案 B: `users/{userId}` を join して `users.displayName` を使う
- 案 C: 現状の `unsettledAccountingPage` で使っている `users.pokerName` を継続

→ **推奨: 案 A**（bill 単位で確定している pokerName を使うのが自然、user.displayName は bill 作成後の変更を取り込みすぎる）

### 6.2 安全策

- 既存 `unsettledAccountingPage.dart` は Step06 では touch しない（論点 1 案 B 採用なら）
- 旧 dialog (`RefundProcessingDialog` 等) の挙動は Step06 では変えない（論点 2 案 A 採用なら）
- 新画面は既存の `sectioned_user_list_page.dart` 等の utility を再利用して可能な限り共通化
- `users.unsettledBillsCount` の counter は Step06 で touch しない（既存挙動維持）

### 6.3 不確定事項（要ユーザー確認）

- 上記論点 1〜6 のうち、論点 1（ファイル分割）と論点 2（callable 切替範囲）は方針決定が必要
- 論点 3〜6 は推奨案でユーザー合意を得る形
