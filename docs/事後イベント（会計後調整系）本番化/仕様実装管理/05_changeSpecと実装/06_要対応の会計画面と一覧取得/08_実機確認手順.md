## 5. シナリオ別の確認手順

### 5.1 シナリオ A: メニュー入口の改名

1. terminal device で起動
2. `terminalHome` のメニュー一覧を確認
3. `要対応の会計` というラベルがあること、`未会計の会計` ラベルが存在しないことを確認

### 5.2 シナリオ B: 画面進入と AppBar / タブ / フィルタ

1. `要対応の会計` メニュー tap
2. 画面が開いた直後を確認:
   - AppBar title: `要対応の会計`
   - 上部に 4 つの ChoiceChip: `すべて` / `未会計` / `追加徴収` / `要返金`
   - デフォルトは `すべて`
   - 中央に 2 タブ: `日付ごと` / `ユーザー別`、デフォルトは `日付ごと`

### 5.3 シナリオ C: 日付ごと タブ + すべて

**準備**:
| billId | status | closeSummary.unresolved | postSettlementState | 期待 cardType |
|---|---|---|---|---|
| B-A | open | true | - | carryover_unsettled |
| B-B | post_settlement_pending | - | type=collection, incl=1000 | post_settlement_collection_pending |
| B-C | post_settlement_pending | - | type=refund, incl=500 | post_settlement_refund_pending |
| B-D | settled | - | - | （要対応一覧に出ない） |
| B-E | post_settlement_pending | - | type=none, incl=0 | （要対応一覧に出ない） |

**手順**:
1. `日付ごと` + `すべて` 状態で初期表示
2. B-A / B-B / B-C のカードが `sortDate` 降順で並んでいる
3. B-D / B-E のカードは表示されない
4. 各カードに `displayLabel` バッジ（`未会計` / `追加徴収` / `要返金`）が正しく出ている
5. 金額は `displayAmountIncl`（B-A=`closeSummary.displayAmountAtMark` / B-B=1000 / B-C=500）

### 5.4 シナリオ D / E / F: 日付ごと + 各 chip

1. シナリオ C 続きで `未会計` chip tap → B-A のみ表示
2. `追加徴収` chip tap → B-B のみ表示
3. `要返金` chip tap → B-C のみ表示
4. `すべて` chip tap → 元の 3 件表示に戻る

### 5.5 シナリオ G: ユーザー別 + すべて

**準備（追加）**:
- B-A は `party.userId='user-1'`、`party.pokerName='Alice'`
- B-B は `party.userId='user-1'`、`party.pokerName='Alice'`
- B-C は `party.userId='user-2'`、`party.pokerName='Bob'`

**手順**:
1. `ユーザー別` タブに切替
2. ユーザー一覧画面が出る
3. user-1 (Alice) のカード:
   - 名前: `Alice`
   - 総件数: `2 件`
   - `未会計 1 件 / 追加徴収 1 件 / 要返金 0 件`
4. user-2 (Bob) のカード:
   - 名前: `Bob`
   - 総件数: `1 件`
   - `未会計 0 件 / 追加徴収 0 件 / 要返金 1 件`

### 5.6 シナリオ H: ユーザー別 + フィルタ

1. `ユーザー別` タブで `追加徴収` chip 選択
2. user-1 (Alice) のみ表示（B-B が collection のため）
3. Alice カードの件数内訳は **filter 適用前** の値（`総件数 2 / 未会計 1 / 追加徴収 1 / 要返金 0`）
4. user-2 (Bob) は表示されない（持っている bill (B-C) が refund のみで filter から外れる）

### 5.7 シナリオ I: ユーザーカード tap

1. `ユーザー別` + `すべて` で Alice カード tap
2. Alice の bill 一覧（Card 形式）が出る
3. B-A と B-B が表示
4. 上部にバックバー（`Alice の要対応`）と戻るボタン
5. 戻るボタン tap で user 一覧に戻る

### 5.8 シナリオ J: carryover カード primary action

1. B-A カードの `会計を再開する` ボタン tap
2. `AccountingPage(forUnsettledBillId: 'B-A', forUnsettledUserId: 'user-1')` に遷移
3. `AccountingPage` が `startAccounting` を内部で呼ぶ（既存挙動）
4. 戻るで一覧に戻る

### 5.9 シナリオ K: collection カード primary action

1. B-B カードの `徴収する` ボタン tap
2. `PostSettlementCollectionDialog` が開く
3. 表示確認:
   - title: `追加徴収`
   - `billId: B-B`
   - `対象 adjustment: <id>（残額 ¥<n>）`
   - 金額入力欄: 初期値 `1000`
   - 支払方法: `現金` （default）/ `カード` / `QR` / `その他`
4. 金額を変更せず（または減額して）`徴収する` tap
5. callable `recordPostSettlementCollection` 発火 → 成功
6. dialog 閉じる
7. SnackBar `追加徴収を記録しました（cashActionId: <id>）`
8. B-B カードが一覧から消える（stream の自動更新）
9. `bills/B-B/settlementCycles/<cycle>/cashActions/<id>` doc が作成されている（Firestore Console / Emulator UI で確認）
10. `bills/B-B.postSettlementState.requiredActionType='none'` または `bills/B-B.status='post_settlement_resolved'` に遷移

### 5.10 シナリオ L: refund カード primary action

1. B-C カードの `返金する` ボタン tap
2. `PostSettlementRefundDialog` が開く（collection と同型 UI）
3. `返金する` tap → callable `recordPostSettlementRefund` 発火 → 成功
4. SnackBar `返金を記録しました（cashActionId: <id>）`
5. B-C が一覧から消える

### 5.11 シナリオ M: dialog エラー

**準備**: 一旦 callable 呼び出しを失敗させる状況を作る（例: B-B の `requiredActionIncl` を 0 にしておく / Functions Emulator を停止）

**手順**:
1. B-B の `徴収する` ボタン tap
2. dialog で金額入力 → `徴収する` tap
3. callable が `failed-precondition` 等で reject
4. dialog が閉じない、inline で赤字エラーメッセージ `徴収に失敗しました: [<code>] <message>` が表示
5. `キャンセル` tap で dialog 閉じる、bill は一覧に残る

### 5.12 シナリオ N: リアルタイム更新

1. `日付ごと` + `すべて` 表示状態
2. 別 terminal / Firestore Console から B-B の `postSettlementState.requiredActionType` を `'none'` に手動更新
3. 数秒以内に B-B が一覧から消える

### 5.13 シナリオ O: 排他（同 bill が複数 cardType に出ない）

**準備**:
- bill `B-X` を `status='post_settlement_pending'`、`closeSummary.unresolved=true`（異常データ）、`postSettlementState.requiredActionType='collection'` で作成

**期待**:
- `classifyBill` の最初の分岐 `if (status === 'open')` が false なので carryover_unsettled には行かない
- 次の分岐で post_settlement_pending → collection と判定
- 一覧に **1 枚** だけ `追加徴収` バッジで表示される（carryover_unsettled としては表示されない）

### 5.14 シナリオ P: reopen 後の bill

1. シナリオ K（または別の bill）で post_settlement_pending → collection で 1 件残っている状態
2. 別経路（コマンド or `reopenAccountedBill` 直接 invoke）で reopen 実行
3. bill が `status='open'` に戻る + `closeSummary.unresolved` は touch されない（仕様書 §7.3）
4. 要対応一覧から消える（`status='open'` だが `closeSummary.unresolved` が false / 不在のため carryover_unsettled として判定されない）

**注**: もし `closeSummary.unresolved=true` のまま reopen される業務シナリオがあるなら、要対応一覧に `未会計` として再表示される。これは Step05 の reopen 仕様（spec_only reset）と整合。

## 6. Firestore Console / Emulator UI での確認ポイント

各シナリオで:

1. `bills/{billId}` doc の `status` / `closeSummary` / `postSettlementState`
2. シナリオ K / L 後の `bills/{billId}/settlementCycles/{cycleNo}/cashActions/{cashActionId}` 作成
3. `bills/{billId}/settlementCycles/{cycleNo}/adjustments/{adjustmentId}.adjustmentState` の遷移（`effective` → `completed_by_cash_action`）
4. `bills/{billId}/idempotency/<entry>` doc の確認（callable 経由）

## 7. ログ確認

Cloud Logging（または Functions Emulator のログ）で次を確認:

- 成功時 `recordPostSettlementCollection` / `recordPostSettlementRefund`:
  - `logOpsSuccess` の `outcome='success'`、`functionEntry='recordPostSettlement(Collection|Refund)'`、`context.billId` / `cashActionId` / `adjustmentId` 含み
- 失敗時:
  - `logOpsError` で適切な `errorKey`（例 `ACCOUNTING_INVALID_STATE` / `BILLS_CASH_ACTION_AMOUNT_MISMATCH` 等）

## 8. 旧経路の不変確認

- `lib/Accounting/refundProcessingDialog.dart` / `postAccountingRefundDialog.dart` 等の旧 dialog は touch していない
- 既存 `AccountingPage` 経由の事後操作は今までどおり動作する
- 旧経路は段階的に廃止予定（後続 step）

## 9. NG パターンと対処

| 症状 | 想定原因 | 対処 |
|---|---|---|
| 一覧に何も出ない | `bills` query の field 名 typo / 存在しない場合 | Firestore Console で `bills/{billId}.status` / `closeSummary.unresolved` / `postSettlementState.*` を確認 |
| 一覧に出るべき bill が出ない | `requiredActionIncl <= 0` で client-side filter で外れる | `bills/{billId}.postSettlementState.requiredActionIncl > 0` を確認 |
| 一覧に出る bill の `displayAmountIncl=0` | `closeSummary.displayAmountAtMark` または `requiredActionIncl` の取得漏れ | doc field を確認、view model の `computeDisplayAmountIncl` 実装を確認 |
| dialog で `対象 adjustment が見つかりません` | effective adjustment が 0 件（既に解消済み）または cycle 番号取得失敗 | `bills/{billId}/settlementCycles/{currentCycle}/adjustments where adjustmentState='effective'` を確認 |
| dialog の callable 呼び出しで permission-denied | device 権限不足 | terminal device の `device.accounting` 権限を確認、Step01 device 認証要件と一致するか |
| dialog で SnackBar が出ない | `Navigator.of(context).pop()` 後に `ScaffoldMessenger` を呼んでいる順序問題 | Step06 実装では pop の前に `mounted` チェック → `pop` → `showSnackBar` の順で実装済み、再現したらコード（`postSettlementCollectionDialog.dart` / `postSettlementRefundDialog.dart`）の `_submit` を確認 |
| `failed-precondition: The query requires an index` | Firestore で composite index が必要だった | 仕様書 §13.5 / `02_changeSpec.md §5.8` に記載した index を `firestore.indexes.json` に追加して deploy |
