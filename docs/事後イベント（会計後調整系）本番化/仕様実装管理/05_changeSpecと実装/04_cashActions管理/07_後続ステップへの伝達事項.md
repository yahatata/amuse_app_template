# 07_後続ステップへの伝達事項

## 1. このファイルの役割

Step04 完了時点で、後続 step（Step05 / Step06 / Step07）に引き継ぐ事項と、Step04 で意図的に扱わなかった範囲を整理する。

## 2. Step05（reopen と再会計）への伝達

Step05 は仕様書 [05_reopenと再会計.md](/Users/yahatayuusei/Documents/GitHub/amuse_app_template/docs/事後イベント（会計後調整系）本番化/仕様実装管理/04_仕様書/05_reopenと再会計.md) を主責務とする。Step04 で関連する事項:

### 2.1 reopen 時の cashAction 扱い

- 仕様書 04 §3 で `reopen` は cashAction を直接扱わないことを明示
- ただし `reopen` 実行時には現 cycle の `adjustments` を `cancelled_by_reopen` に遷移させるルールがある（仕様書 03 §11）
- 同様に **`cashActions` 自体は不変**だが、その allocation 先 adjustment が `cancelled_by_reopen` になる場合の整合確認が必要

### 2.2 確認推奨事項

- Step05 で reopen 実装後、以下を確認:
  - cashAction doc は `cancelled_by_reopen` に遷移しない（cashAction は履歴として残る）
  - allocation 先 adjustment が `cancelled_by_reopen` になっても、cashAction の allocations[] と methodBreakdown[] はそのまま保持
  - 新 cycle では `nextSequenceNo` が `1` から再スタート（既存仕様）

### 2.3 Step04 で前提化したインターフェース

- `recordPostSettlementCashAction` repo は `currentSettlementCycle` をもとに動作する。Step05 が `reopen` で `currentSettlementCycle` を進めた直後の cycle に対しても同じ entry point で動く想定。
- 旧 cycle の adjustment への later cashAction 作成は、Step04 では不可（仕様書 §15.3 の異 cycle 混在禁止）。Step05 はこれを前提にしてよい。

## 3. Step06（要対応の会計画面と一覧取得）への伝達

Step06 は仕様書 [06_要対応の会計画面と一覧取得.md](/Users/yahatayuusei/Documents/GitHub/amuse_app_template/docs/事後イベント（会計後調整系）本番化/仕様実装管理/04_仕様書/06_要対応の会計画面と一覧取得.md) を主責務とする。Step04 で関連する事項:

### 3.1 UI 接続用 callable

Step06 では UI 側を以下に切り替える:

- 新: `recordPostSettlementRefund` / `recordPostSettlementCollection` （Step04 で追加）
- 旧: `processRefund`（旧 events 経路）

旧 callable は Step04 では併存維持。Step06 で UI 切り替えに合わせて段階的に整理する。

### 3.2 一覧取得（`getRefundHistory` の本実装）

- `functions/src/domains/bills/callables/refundProcessing.ts` の `getRefundHistory` は現状スタブ（常に空配列）
- Step04 では本実装に **触らない**（Step04 のスコープ外）
- Step06 で本実装する際は次の path を読む:
  - 新: `bills/{billId}/settlementCycles/{cycleNo}/cashActions`
  - 旧: `bills/{billId}/events`（type=refund）
- どちらを正本とするかは Step06 で決定。仕様書 04 が「正本は cashActions」を示唆

### 3.3 必要なフィールド

UI で表示・編集に使う場合に Step04 で確実に書いてある field:

- `cashActionType` / `amountIncl` / `executedAt` / `executedBy` / `cashflowBusinessDate`
- `methodBreakdown[].method` / `methodBreakdown[].amountIncl`
- `allocations[].adjustmentId` / `allocations[].amountIncl`
- `note`

UI 側で adjustment との紐付き表示が必要な場合、`allocations[].adjustmentId` から adjustment doc を読みに行く（同一 cycle 配下なので path 解決は容易）。

## 4. Step07（analyticsMonthly 更新と日付帰属とline配賦）への伝達

Step07 は仕様書 [07_analyticsMonthly更新と日付帰属とline配賦.md](/Users/yahatayuusei/Documents/GitHub/amuse_app_template/docs/事後イベント（会計後調整系）本番化/仕様実装管理/04_仕様書/07_analyticsMonthly更新と日付帰属とline配賦.md) を主責務とする。Step04 で関連する事項:

### 4.1 analyticsMonthly の入力源

仕様書 12_analyticsMonthlyと入出金データの役割分担.md §8 のとおり:

- baseline 入力: `settlementCycles/{cycleNo}/baselineSnapshot`（Step02 で導入済）
- 売上差分入力: `settlementCycles/{cycleNo}/adjustments/{adjustmentId}` の `lines[]`（Step03 で導入済）
- 実入出金入力: `settlementCycles/{cycleNo}/cashActions/{cashActionId}` の `allocations[]` / `methodBreakdown[]`（Step04 で導入済）

### 4.2 日付軸

仕様書 step3.12 BlockC §2.3 のとおり:

- 売上帰属日: `bill.businessDate`
- adjustment 確定日: `adjustment.createdAt`
- cashflow 実行日: `cashAction.executedAt` / `cashAction.cashflowBusinessDate`

Step04 では `cashflowBusinessDate` を以下のロジックで解決済み（仕様書 04 §6 / changeSpec §5.7）:

1. 入力指定があればそれを採用
2. 空なら `calcBusinessDate(executedAt)` を試行
3. NONE / AMBIGUOUS / 例外の場合は `bill.businessDate` を borrow

Step07 はこの `cashflowBusinessDate` を analytics 反映の日付軸として使用してよい。

### 4.3 paymentTotals の更新タイミング

仕様書 12 §4.1 のとおり:

| パターン | analytics 反映時点 |
|---|---|
| `減額 + 返金済` | adjustment 作成時（売上差分） |
| `減額 + 返金前` | adjustment 作成時（売上差分） |
| `増額 + 追加徴収済` | adjustment 作成時（売上差分） + cashAction 作成時（受領内訳） |
| `増額 + 追加徴収前` | adjustment 作成時（売上差分） + cashAction 完了時（受領内訳） |

Step04 では cashAction を保存するのみで、`analyticsMonthly` への `paymentTotals` 反映は **行っていない**。Step07 で本接続する。

### 4.4 line 配賦

- `adjustments.lines[].targetCategory` / `targetId` / `operationType` / `qtyDelta` / `amountInclDelta` を Step03 で必須化済み
- tournament line は `targetId` (templateKey) と `operationType` (entry/reentry/addon) を持つ
- Step07 はこれらを `byTemplateTournaments` 等の analytics 更新に使う

### 4.5 cashflow 系 analytics の責務

- `delta.cashflow.refundsByMethod` / `delta.cashflow.paymentTotals` 等は既存 aggregator にあるが、Step04 では未配線
- Step07 で `cashAction.methodBreakdown[]` を集計入力として接続する想定

## 6. 共通注意事項

### 6.1 旧経路と新経路の併存

Step04 完了時点で:

- 旧: `bills/{billId}/events` ＋ `billsEventsOnCreate` trigger
- 新: `bills/{billId}/settlementCycles/{cycleNo}/cashActions` ＋ `recordPostSettlementCashAction`

両者が並存。Step06 で UI 切替が完了するまでは、UI からの呼び出しは旧経路のまま。

### 6.2 dual-write はしない

- 新 callable は `events` 配下に書かない
- 旧 callable は `cashActions` 配下に書かない
- 両系統の整合は Step06 で UI 切替時に検討

### 6.3 後方互換

- `buildImmediateCashActionDoc` の API は Step03 と互換維持（内部委譲）
- `createPostSettlementAdjustment` のレスポンス shape は Step03 と互換維持
- ただし `createPostSettlementAdjustment` の immediate ケースで `lastRecordType` が `'adjustment'` から `'cash_action'` に変わったため、当該 field を assert していた既存テスト（Step03 で書いたもの）は期待値を更新済み

### 6.4 method allow list

- Step04 で `cashActions.method` を current-scope の許容値（`cash` / `credit_card` / `electronic_money` / `qr` / `bank_transfer` / `other`）に制限
- 旧経路（`postEventRefund`）の `method` は string 自由入力のまま（Step04 で触らない）
- Step06 で UI 側を新 callable に切り替える際、UI から渡す method 値を allow list に揃える必要あり
