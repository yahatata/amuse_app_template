# 08_実機確認手順

## 1. このファイルの役割

Step04 で導入した cashActions まわりの動作を、実環境（または Emulator）で確認するための手順を整理する。Step04 では UI 切替を行わないため、実機確認は callable の直接 invoke、Emulator 経由、Firestore Console での doc 確認が中心となる。

## 2. 前提

- Step04 のコードがデプロイ済み、または `firebase emulators:start --only functions,firestore` で起動済み
- 確認用の bill が `status='settled' | 'post_settlement_pending' | 'post_settlement_resolved'` のいずれかで存在
- 確認用 bill の `settlementCycles/{cycleNo}` に少なくとも 1 件の adjustment が存在し、`requiredActionRemainingIncl > 0` の状態

## 3. 確認シナリオ

### 3.1 シナリオ A: later refund cashAction の作成（method 1 つ・allocation 1 つ）

**目的**: 仕様書 04 §3 / §15 の later 経路の最小確認

**手順**:

1. テスト bill `B-A` を準備し、`adj-A`（cashActionType=refund, requiredActionRemainingIncl=3000）を作る
2. `recordPostSettlementRefund` を以下入力で invoke
   ```json
   {
     "billId": "B-A",
     "cycleNo": 1,
     "amountIncl": 3000,
     "executedAt": "2026-05-09T12:00:00+09:00",
     "executedBy": { "userId": "user-1", "deviceId": "device-1" },
     "methodBreakdown": [{ "method": "cash", "amountIncl": 3000 }],
     "allocations": [{ "adjustmentId": "adj-A", "amountIncl": 3000 }],
     "idempotencyKey": "ik-001",
     "requestHash": "rh-001"
   }
   ```
3. レスポンス取得後 Firestore で次を確認:

| 確認項目 | 期待値 |
|---|---|
| `bills/B-A/settlementCycles/1/cashActions/{cashActionId}` の存在 | あり |
| `cashActionType` | `refund` |
| `amountIncl` | 3000 |
| `methodBreakdown[0]` | `{ method: 'cash', amountIncl: 3000 }` |
| `allocations[0]` | `{ adjustmentId: 'adj-A', amountIncl: 3000 }` |
| `cashflowBusinessDate` | 入力 executedAt から `calcBusinessDate` 解決値（NONE/AMBIGUOUS なら `bill.businessDate`） |
| `bills/B-A/settlementCycles/1/adjustments/adj-A.requiredActionRemainingIncl` | 0 |
| `bills/B-A/settlementCycles/1/adjustments/adj-A.adjustmentState` | `completed_by_cash_action` |
| `bills/B-A.currentSummary.lastRecordType` | `cash_action` |
| `bills/B-A.currentSummary.lastRecordId` | `{cashActionId}` |
| `bills/B-A.postSettlementState.requiredActionRemainingIncl` | 残 adjustment 合計に応じた値 |
| `bills/B-A.status` | 残 0 なら `post_settlement_resolved`、残あれば `post_settlement_pending` |
| `bills/B-A/settlementCycles/1.nextSequenceNo` | invoke 前 +1 |

### 3.2 シナリオ B: later refund cashAction の作成（method 複数 + allocation 複数）

**目的**: 仕様書 04 §15.1 / §15.2 の合計突合確認

**手順**:

1. テスト bill `B-B` を準備し、以下 adjustment を作る
   - `adj-B1`: cashActionType=refund, remaining=2000
   - `adj-B2`: cashActionType=refund, remaining=3000
2. `recordPostSettlementRefund` を以下入力で invoke
   ```json
   {
     "billId": "B-B", "cycleNo": 1, "amountIncl": 5000,
     "executedAt": "...",
     "executedBy": { "userId": "user-1", "deviceId": "device-1" },
     "methodBreakdown": [
       { "method": "cash", "amountIncl": 2000 },
       { "method": "credit_card", "amountIncl": 3000 }
     ],
     "allocations": [
       { "adjustmentId": "adj-B1", "amountIncl": 2000 },
       { "adjustmentId": "adj-B2", "amountIncl": 3000 }
     ],
     "idempotencyKey": "ik-002", "requestHash": "rh-002"
   }
   ```
3. Firestore で `adj-B1.remaining=0`, `adj-B2.remaining=0`, `cashAction` doc が `methodBreakdown` 2 件、`allocations` 2 件で保存されていることを確認

### 3.3 シナリオ C: 部分 allocation（adjustment 残あり）

**目的**: 仕様書 04 §15.2 の部分配賦が成立すること

**手順**:

1. テスト bill `B-C` を準備し、`adj-C`（remaining=5000）を作る
2. `recordPostSettlementRefund` で `amountIncl=2000`, `allocations=[{ adj-C, 2000 }]` を invoke
3. Firestore で `adj-C.remaining=3000`, `adjustmentState='effective'`（completed にならない）、`bills.status='post_settlement_pending'` のままを確認

### 3.4 シナリオ D: バリデーション失敗（allocations 合計と amountIncl の不一致）

**目的**: 仕様書 04 §15.2 の合計突合バリデーション

**手順**:

1. `recordPostSettlementRefund` を `amountIncl=3000`, `allocations=[{ X, 1000 }]` で invoke
2. `INVALID_ARGUMENT` でエラー、Firestore に何も書かれていないことを確認

### 3.5 シナリオ E: バリデーション失敗（method 合計と amountIncl の不一致）

**目的**: 仕様書 04 §15.1 の合計突合バリデーション

**手順**:

1. `recordPostSettlementRefund` を `amountIncl=3000`, `methodBreakdown=[{cash, 1500}, {credit_card, 1000}]` で invoke
2. `INVALID_ARGUMENT` でエラー、Firestore に何も書かれていないことを確認

### 3.6 シナリオ F: バリデーション失敗（direction 不一致）

**目的**: 仕様書 04 §15.3 の cashActionType と adjustment.cashActionType 一致確認

**手順**:

1. `adj-F` を `cashActionType=collection`（増額側）で作成
2. `recordPostSettlementRefund` を `allocations=[{ adj-F, ... }]` で invoke
3. `INVALID_ARGUMENT` でエラー（refund callable から collection adjustment への配賦は禁止）

### 3.7 シナリオ G: バリデーション失敗（completed adjustment への配賦）

**手順**:

1. `adj-G` を完了状態（remaining=0, adjustmentState='completed_by_offset' など）で作成
2. `recordPostSettlementRefund` を `allocations=[{ adj-G, ... }]` で invoke
3. `FAILED_PRECONDITION` でエラー（remaining=0 への配賦は禁止）

### 3.8 シナリオ H: idempotency 再送

**目的**: 仕様書 04 §11 の冪等性

**手順**:

1. シナリオ A と同じ入力で 1 回目 invoke
2. 同じ `idempotencyKey` / `requestHash` で 2 回目 invoke
3. レスポンスが 1 回目と同一の `cashActionId`、Firestore の `nextSequenceNo` は **+1 のまま**（2 にならない）、cashAction doc が **重複していない** ことを確認

### 3.9 シナリオ I: collection 経路（増額側）

**目的**: `recordPostSettlementCollection` の動作確認

**手順**:

1. `adj-I` を `cashActionType=collection`, `remaining=2000` で作成
2. `recordPostSettlementCollection` を `amountIncl=2000`, `methodBreakdown=[{cash,2000}]`, `allocations=[{ adj-I, 2000 }]` で invoke
3. Firestore で `cashAction.cashActionType='collection'`, `adj-I.remaining=0`, `adjustmentState='completed_by_cash_action'`, `bills.currentSummary.lastRecordType='cash_action'` を確認

### 3.10 シナリオ J: status 前提違反（settled 以外で invoke）

**手順**:

1. bill を `status='active'` で作成
2. `recordPostSettlementRefund` を invoke
3. `FAILED_PRECONDITION` でエラー、Firestore に何も書かれていないことを確認

### 3.11 シナリオ K: cashflowBusinessDate 入力指定

**手順**:

1. シナリオ A と同じセットで `inputBusinessDate='2026-05-08'` を追加して invoke
2. cashAction doc の `cashflowBusinessDate=Timestamp('2026-05-08T00:00:00')`（store TZ 解釈）であることを確認

### 3.12 シナリオ L: cashflowBusinessDate 入力なし → calcBusinessDate 解決

**手順**:

1. シナリオ A と同じセットで `inputBusinessDate` を渡さずに invoke
2. cashAction doc の `cashflowBusinessDate` が `executedAt` を `calcBusinessDate` で解決した値、または `bill.businessDate` であることを確認
3. `businessHoursMonthlyMap` が未登録（NONE）または境界（AMBIGUOUS）の月を含むケースで `bill.businessDate` にフォールバックすること

### 3.13 シナリオ M: immediate cashAction 経路（Step03 連携）

**目的**: Step04 で改修した immediate 経路の lastRecordType 確認

**手順**:

1. `createPostSettlementAdjustment` を `decrease_refunded` で invoke（Step03 機能）
2. レスポンス成功後、Firestore で次を確認:
   - `cashActions/{cashActionId}` が作成されている（minimal shape）
   - `adjustment.adjustmentState='completed_by_cash_action'`, `requiredActionRemainingIncl=0`
   - `bills.currentSummary.lastRecordType='cash_action'`（Step04 で改修した点）
   - `bills.currentSummary.lastRecordId={cashActionId}`

## 4. Firestore Console / Emulator UI での確認ポイント

- 各シナリオで以下の path を順に確認:
  1. `bills/{billId}` ルート doc（`currentSummary` / `postSettlementState` / `status` / `requireSpecialAttention` 等）
  2. `bills/{billId}/settlementCycles/{cycleNo}` の `nextSequenceNo`
  3. `bills/{billId}/settlementCycles/{cycleNo}/adjustments/{adjustmentId}` の `requiredActionRemainingIncl` / `adjustmentState`
  4. `bills/{billId}/settlementCycles/{cycleNo}/cashActions/{cashActionId}` の全 field
  5. `idempotency/{idempotencyKey}` の `result` 保存

## 5. ログ確認

- Cloud Logging（または Functions Emulator のログ）で次を確認:
  - 成功時: `logOpsSuccess` 呼び出しが該当 callable 名で出ている
  - 失敗時: `logOpsError` が `INVALID_ARGUMENT` / `FAILED_PRECONDITION` などの code で出ている
  - 実行 user / device / billId が context として記録されている

## 6. 旧経路の不変確認

- Step04 で旧経路（`processRefund` / `postEventRefund` / `billsEventsOnCreate`）には触っていないため、`bills/{billId}/events` 配下に新規 doc が増えないこと（シナリオ A〜M ではすべて `events` 配下が空または既存のまま）を確認
- 旧 UI からの `processRefund` 呼び出しは Step04 でも今までどおり動作することを別途確認（Step06 で切替予定）

## 7. NG パターンと対処

| 症状 | 想定原因 | 対処 |
|---|---|---|
| `recordPostSettlementRefund` が `INTERNAL` で落ちる | Emulator 起動なし／network 問題 | Emulator 再起動、`firebase emulators:start --only functions,firestore` |
| `cashAction` doc は作成されているのに `adjustment.remaining` が更新されていない | トランザクションの分離違反 | Step04 では single transaction にまとめている。再現したらコード（`repos/recordPostSettlementCashAction.ts`）を見直し |
| `lastRecordType` が `'adjustment'` のまま | `createPostSettlementAdjustment` の immediate 経路で cashAction が作成されていない可能性 | `adjustmentState` が `effective`（pending）になっていないか確認。なっていれば仕様通り adjustment last。`completed_by_cash_action` になっているのに lastRecordType が adjustment のままなら回帰。|
| `nextSequenceNo` が +2 されている | idempotency が効いていない | `idempotencyKey` の保存と再読が出来ているか確認。`idempotency/{ik}` を確認 |

## 8. 実機確認の完了条件

- シナリオ A〜M（13 シナリオ）すべてが期待値通り
- 旧経路に副作用なし
- ログに想定外のエラーなし
