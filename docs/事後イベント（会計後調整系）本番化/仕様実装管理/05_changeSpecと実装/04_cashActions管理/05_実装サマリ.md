## 3. 主要決定事項（changeSpec で確定 → 実装）

### 3.1 immediate 経路で `lastRecordType = 'cash_action'` を書く（changeSpec 論点 1 = 案A）

- 仕様書 04 §12.3 を完全準拠
- adjustment と cashAction が同一 transaction で作られる場合、最終状態として `'cash_action'` を採用
- adjustment のみ（pending パターン / offset で完全相殺）の場合は `'adjustment'` のまま

### 3.2 callable 名は refund / collection で 2 本に分割（changeSpec 論点 3 = 案C）

- `recordPostSettlementRefund` / `recordPostSettlementCollection`
- 旧 `processRefund` の命名思想と整合
- 内部 repo は共通 (`recordPostSettlementCashAction.ts`) で重複を排除

### 3.3 `cashflowBusinessDate` フォールバック方針（changeSpec 論点 2 = 推奨案 D）

- 入力 `cashflowBusinessDate` が空でなければ採用
- 空なら `calcBusinessDate(executedAt)` を試みる
- `OK` でなければ（NONE / AMBIGUOUS / 例外） `bill.businessDate` を borrow
- すべて空なら `failed-precondition`

選択理由:

- 仕様書 §6 で必須化されており、内部で必ず string 値を保証する
- AMBIGUOUS / NONE のときに運用が止まらない
- UTC 日付は日付帰属を誤る恐れ
- `bill.businessDate` borrow は「元会計日」の意味を保つ
- 入力で明示指定する経路を残し運用上の柔軟性も確保

## 5. リスク評価と対応

### 5.1 immediate 経路の `lastRecordType` 仕様変更による既存テストへの影響

- Step03 immediate ケース（`decrease_refunded` / `increase_collected`）で `lastRecordType` 期待値を `'cash_action'` に更新
- pending ケースは `'adjustment'` のまま不変
- 確認: `createPostSettlementAdjustment.spec.ts` 13 tests すべて pass

### 5.2 calcBusinessDate の transaction 内呼び出し

- `recordPostSettlementCashAction` では transaction 開始前に calcBusinessDate を試行
- `createPostSettlementAdjustment` の immediate 経路では transaction 内で calcBusinessDate を呼ぶ
- 後者は厳密には transaction の atomicity 範囲外だが、`businessHoursMonthlyMap` が cashAction 作成中に変わることはない master 設定なので問題なし

### 5.3 over-allocation の race condition

- 同一 adjustment に対して複数 cashAction が同時実行される可能性
- transaction で `tx.get(adjustmentRef)` を行うため、Firestore の標準動作で contention retry → 最新 remaining で再評価される
- Emulator test の `completed_by_cash_action 済 adjustment への allocate` で同様のシナリオを再現し弾かれることを確認
