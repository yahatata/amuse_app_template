## 4. 仕様との差分

### 4.1 bill 作成時

仕様書では bill 作成時に `settlementCycles/1` を `open` で作る必要があるが、AsIs では未作成だった。

### 4.2 settle 時

仕様書では settle 時に次を作る必要がある。

- `settlementCycles/{cycleNo}` 親 doc の settled 化
- `baselineSummary`
- `baselineSnapshot` 単一 doc

AsIs では root snapshot 更新のみで、cycle 配下への永続化がなかった。

### 4.3 baseline line 配列

仕様書では `items[] / extras[] / tournaments[] / sideGameChips[]` を baseline full snapshot として保持する必要があるが、AsIs では analytics 向け root summary しかなかった。

### 4.4 reopen 境界

仕様書では Step02 で cycle の概念を導入する一方、実際の `reopen` 実行と cycle 進行は Step05 の責務である。
AsIs ではこの境界がコードにも docs にも明示されていなかった。

## 5. 影響範囲

### 5.1 Step03 / Step04

- `settlementCycles/{cycleNo}.nextSequenceNo` を adjustment / cashAction 採番の起点として使う前提になる

### 5.2 Step05

- `reopen` 実行時に old cycle を閉じ、新 cycle を開くための保存先として `settlementCycles` を利用する
- Step02 では actual reopen runtime は未実装のため、Step05 で必ず接続する必要がある

### 5.3 Step07

- `baselineSummary` と `baselineSnapshot` を analytics 再構成の基礎データとして参照できるようになる

### 5.4 既存機能

- root snapshot 群を残したまま dual-write するため、既存 caller / trigger の互換性を保てる
- 追加した `baselineSnapshot/snapshot` は current-scope の新規参照先であり、既存 UI を直ちに壊さない

## 6. この時点のメモ

- Step02 の完了条件は「create / settle パスで `settlementCycles` と `baselineSnapshot` が仕様どおり作られること」である
- `reopen` 実行パスまで Step02 で閉じようとすると Step05 と責務が衝突するため、ここでは行わない
- 実装時は root snapshot 群を削除せず、仕様書どおり段階実装で進める
