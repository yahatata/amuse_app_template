# 08_実機確認手順

## 1. このファイルの役割

Step05 で導入した `reopenAccountedBill` callable と関連する reopen / 再会計の動作を、実環境（または Emulator）で確認するための手順を整理する。Step05 では UI 切替を行わないため、実機確認は callable の直接 invoke、Emulator 経由、Firestore Console での doc 確認が中心となる。

## 2. 前提

- Step05 のコードがデプロイ済み、または `firebase emulators:start --only functions,firestore` で起動済み
- 確認用の bill が `status='settled' | 'post_settlement_pending'` のいずれかで存在
- 確認用 bill の `businessDate` が **当日の `storeMeta.currentBusinessDateKey` と一致** している（Step05 の hard precondition）
- 確認用 bill の `reopenSummary.latestSettledCycle >= 1`（settle 済み）
- 確認用 device が accounting 権限あり（`isActive(device.status)` を満たす）

## 4. 実機確認シナリオ一覧

| No | シナリオ | 操作入口 | 期待結果 | 備考 |
|---|---|---|---|---|
| A | settled bill から reopen | `reopenAccountedBill` callable 直接 invoke | bill.status='open'、新 cycle=2 作成 | happy path |
| B | post_settlement_pending bill から reopen | 同上 | effective adjustment が `cancelled_by_reopen` に遷移 | happy path |
| C | 完了済 adjustment が touch されない | reopen 前後で adjustment 比較 | `completed_by_cash_action` は不変 | 不変則 |
| D | 旧 cycle baselineSnapshot が不変 | reopen 前後で snapshot 比較 | hash 同一 | immutable history |
| E | 旧 cycle cashActions が不変 | reopen 前後で cashAction 比較 | allocations[] / methodBreakdown[] 不変 | immutable history |
| F | 親 doc reset 範囲 | reopen 後の親 doc 確認 | `requireSpecialAttention` / `closeSummary` / `amounts` 不変 | spec_only reset |
| G | 当日営業日でない bill は弾かれる | bill.businessDate を当日と異なる値に変更 | `failed-precondition` / errorKey `BILLS_REOPEN_NOT_TODAY` | hard precondition |
| H | latestSettledCycle = 0 の bill は弾かれる | settle 前の bill で reopen | `failed-precondition` / errorKey `BILLS_REOPEN_NEVER_SETTLED` | hard precondition |
| I | status precondition 違反 | open / voided / settling bill で reopen | `failed-precondition` / errorKey `ACCOUNTING_INVALID_STATE` | hard precondition |
| J | idempotent replay | 同 idempotencyKey + 同 requestHash で 2 回 invoke | reused: true、副作用なし | idempotency |

| L | permission denied | auth なし / device 不在 / 権限なし | `unauthenticated` / `permission-denied` | permission |
| M | reopen 後の再会計 end-to-end | reopen → `accounting` callable invoke → `billsOnSettle` trigger | 新 cycle baselineSnapshot 作成、`latestSettledCycle` 追いつき | end-to-end |

## 5. シナリオ別の確認手順

### 5.1 シナリオ A: settled bill から reopen

**目的**: 仕様書 §6 / §7 の最小 happy path 確認

**手順**:

1. テスト bill `B-A` を `status='settled'`、`reopenSummary.currentSettlementCycle=1`、`reopenSummary.latestSettledCycle=1`、`businessDate=storeMeta.currentBusinessDateKey` で準備
2. `reopenAccountedBill` を以下入力で invoke
   ```json
   {
     "billId": "B-A",
     "idempotencyKey": "ik-A-001",
     "reason": "test reopen"
   }
   ```
   `requestHash` は repo 内で `{billId, idempotencyKey, reason, reopenedBy}` から SHA-256 で computed（client から渡す必要なし）
3. レスポンス取得後 Firestore で次を確認:

| 確認項目 | 期待値 |
|---|---|
| レスポンス `success` | `true` |
| レスポンス `oldCycleNo` | `1` |
| レスポンス `newCycleNo` | `2` |
| レスポンス `cancelledAdjustmentIds` | `[]`（settled で adjustment なし想定） |
| レスポンス `diagnostics?.reused` | `undefined`（reused でないとき） |
| `bills/B-A.status` | `open` |
| `bills/B-A.currentSummary` | reset（`currentTotalIncl=0` 等） |
| `bills/B-A.postSettlementState.requiredActionType` | `none` |
| `bills/B-A.reopenSummary.hasReopenHistory` | `true` |
| `bills/B-A.reopenSummary.reopenCount` | `1`（増加） |
| `bills/B-A.reopenSummary.currentSettlementCycle` | `2` |
| `bills/B-A.reopenSummary.latestSettledCycle` | `1`（据え置き） |
| `bills/B-A.reopenSummary.lastReopenedAt` | now |
| `bills/B-A.reopenSummary.lastReopenedBy` | invoke した uid |
| `bills/B-A/settlementCycles/1.cycleState` | `reopened` |
| `bills/B-A/settlementCycles/1.closedReason` | `reopen` |
| `bills/B-A/settlementCycles/1.closedAt` | now |
| `bills/B-A/settlementCycles/2.cycleState` | `open` |
| `bills/B-A/settlementCycles/2.openedReason` | `reopen` |
| `bills/B-A/settlementCycles/2.openedFromCycleNo` | `1` |
| `bills/B-A/settlementCycles/2.nextSequenceNo` | `1` |
| `bills/B-A/settlementCycles/2/baselineSnapshot/snapshot` | **存在しない** |
| `bills/B-A/idempotency/reopenAccountedBill:ik-A-001` | doc 存在、`requestHash='rh-A-001'`、`result` に response |

### 5.2 シナリオ B: post_settlement_pending bill から reopen

**目的**: effective adjustment が `cancelled_by_reopen` に遷移することを確認

**手順**:

1. テスト bill `B-B` を `status='post_settlement_pending'` で準備し、cycle=1 配下に effective adjustment `adj-B1`（`adjustmentState='effective'`、`requiredActionRemainingIncl=2000`）を 1 件作成
2. `reopenAccountedBill` を invoke (`{billId: 'B-B', idempotencyKey: 'ik-B-001', requestHash: 'rh-B-001'}`)
3. Firestore で次を確認:

| 確認項目 | 期待値 |
|---|---|
| レスポンス `cancelledAdjustmentIds` | `['adj-B1']` |
| `bills/B-B/settlementCycles/1/adjustments/adj-B1.adjustmentState` | `cancelled_by_reopen` |
| `bills/B-B/settlementCycles/1/adjustments/adj-B1.cancelledAt` | now |
| `bills/B-B/settlementCycles/1/adjustments/adj-B1.cancelledBy` | invoke した uid |
| `bills/B-B/settlementCycles/1/adjustments/adj-B1.cancelReason` | `reopen` |
| `bills/B-B/settlementCycles/1/adjustments/adj-B1.requiredActionRemainingIncl` | `2000`（**touch されない**、履歴として残る） |
| `bills/B-B/settlementCycles/1/adjustments/adj-B1.adjustmentAmountIncl` | 不変 |
| `bills/B-B/settlementCycles/1/adjustments/adj-B1.lines[]` | 不変 |

### 5.3 シナリオ C: 完了済 adjustment が touch されない

**目的**: `completed_by_cash_action` / `completed_by_offset` 不変則

**手順**:

1. テスト bill `B-C` を準備し、cycle=1 配下に `adj-C-completed`（`adjustmentState='completed_by_cash_action'`、`requiredActionRemainingIncl=0`）を作成
2. reopen 前に `adj-C-completed` の全 fields を hash 取得（snapshot として記録）
3. `reopenAccountedBill` を invoke
4. reopen 後に `adj-C-completed` の全 fields を再取得
5. 次を確認:

| 確認項目 | 期待値 |
|---|---|
| レスポンス `cancelledAdjustmentIds` | `adj-C-completed` を含まない |
| reopen 前後で `adj-C-completed` の全 fields | 完全一致（hash 同一） |

### 5.4 シナリオ D: 旧 cycle baselineSnapshot が不変

**目的**: immutable history 検証

**手順**:

1. テスト bill `B-D` を `status='settled'`、`settlementCycles/1/baselineSnapshot/snapshot` 存在状態で準備
2. reopen 前に `baselineSnapshot/snapshot` の全 fields を取得（snapshot として記録）
3. `reopenAccountedBill` を invoke
4. reopen 後に `baselineSnapshot/snapshot` を再取得
5. fields が完全一致することを確認

### 5.5 シナリオ E: 旧 cycle cashActions が不変

**目的**: cashActions の immutable history 検証

**手順**:

1. テスト bill `B-E` を準備し、cycle=1 配下に `cashAction-E1`（`cashActionType='refund'`、`allocations=[{adjustmentId: 'adj-E1', amountIncl: 1000}]`、`methodBreakdown=[{method: 'cash', amountIncl: 1000}]`）を作成
2. reopen 前に `cashAction-E1` の全 fields を取得
3. `reopenAccountedBill` を invoke
4. reopen 後に `cashAction-E1` を再取得
5. `cashActionType` / `amountIncl` / `allocations[]` / `methodBreakdown[]` / `cashflowBusinessDate` が完全不変であることを確認

### 5.6 シナリオ F: 親 doc reset 範囲（spec_only）

**目的**: 仕様書 §7.3 記述外フィールドが touch されないこと

**手順**:

1. テスト bill `B-F` を `requireSpecialAttention=true`、`closeSummary={...}`、`amounts={...}`、`itemsSnapshot={...}` 等の補助 fields を持つ状態で準備
2. reopen 前に補助 fields の全 values を記録
3. `reopenAccountedBill` を invoke
4. reopen 後に補助 fields を再取得
5. `requireSpecialAttention` / `closeSummary` / `amounts` / `itemsSnapshot` 等の補助 fields が完全不変であることを確認
6. `status` / `currentSummary` / `postSettlementState` / `reopenSummary` のみが更新されていることを確認

### 5.7 シナリオ G: 当日営業日でない bill は弾かれる

**目的**: 仕様書追加 precondition `BILLS_REOPEN_NOT_TODAY` の確認

**手順**:

1. テスト bill `B-G` を `businessDate='2026-05-08'`、`storeMeta.currentBusinessDateKey='2026-05-09'` の状態で準備
2. `reopenAccountedBill` を invoke
3. `failed-precondition` エラーで弾かれること、Firestore に何も書かれていないこと（idempotency も含めて）を確認
4. Cloud Logging で `errorKey='BILLS_REOPEN_NOT_TODAY'` を確認

### 5.8 シナリオ H: latestSettledCycle = 0 の bill は弾かれる

**目的**: 未会計 bill の reopen 拒否

**手順**:

1. テスト bill `B-H` を `status='open'`（または `settling`）、`reopenSummary.latestSettledCycle=0` で準備
2. `reopenAccountedBill` を invoke
3. `failed-precondition` エラーで弾かれること、Cloud Logging で `errorKey='BILLS_REOPEN_NEVER_SETTLED'` または `errorKey='ACCOUNTING_INVALID_STATE'` を確認

### 5.9 シナリオ I: status precondition 違反

**目的**: `settled` / `post_settlement_pending` 以外のステータスを弾く

**手順**:

1. テスト bill `B-I-open` を `status='open'` で準備、`reopenAccountedBill` invoke → `failed-precondition` / `ACCOUNTING_INVALID_STATE`
2. テスト bill `B-I-voided` を `status='voided'` で準備、同 → `failed-precondition` / `ACCOUNTING_INVALID_STATE`
3. テスト bill `B-I-settling` を `status='settling'` で準備、同 → `failed-precondition` / `ACCOUNTING_INVALID_STATE`
4. テスト bill `B-I-resolved` を `status='post_settlement_resolved'` で準備、同 → `failed-precondition` / `ACCOUNTING_INVALID_STATE`（Step05 では拒否）

### 5.10 シナリオ J: idempotent replay

**目的**: 仕様書 §11 の冪等性

**手順**:

1. シナリオ A と同じ入力で 1 回目 invoke
2. 同じ `idempotencyKey` / `requestHash` で 2 回目 invoke
3. レスポンスが 1 回目と同一の `oldCycleNo` / `newCycleNo` / `reopenedAt` / `cancelledAdjustmentIds`、`diagnostics.reused === true` を返すこと
4. Firestore の cycle 数が **2 のまま**（3 に増えていない）、新 cycle が **重複していない** ことを確認
5. `bills/{billId}/idempotency/reopenAccountedBill:{key}` doc は 1 件のまま

### 5.11 シナリオ K: idempotency hash 不一致

**目的**: 同 idempotencyKey + 異 requestHash で `failed-precondition`

**手順**:

1. シナリオ A と同じ idempotencyKey で 1 回目 invoke（`reason: 'first'`）→ 成功
2. 同 idempotencyKey + **異 reason**（例 `reason: 'second'`）で 2 回目 invoke（reason が変わると repo が computed する requestHash が変わる）
3. `failed-precondition` エラーで弾かれること、Cloud Logging で `errorKey='ACCOUNTING_IDEMPOTENCY_MISMATCH'` を確認
4. 1 回目の reopen が rollback されていない（cycle=2 がそのまま残る）ことを確認

### 5.12 シナリオ L: permission denied

**手順**:

1. auth なしで `reopenAccountedBill` を invoke → `unauthenticated`
2. 不存在の deviceId で auth ありで invoke → `permission-denied`
3. accounting 権限なしの terminal device で invoke → `permission-denied`
4. いずれも Firestore に何も書かれていないことを確認

### 5.13 シナリオ M: reopen 後の再会計 end-to-end

**目的**: reopen → 再会計の end-to-end 動作

**手順**:

1. シナリオ A の状態（reopen 済み、`status='open'`、cycle=2 が `cycleState='open'`）から開始
2. `accounting` callable を invoke して再会計
3. `billsOnSettle` trigger 発火を待つ
4. Firestore で次を確認:

| 確認項目 | 期待値 |
|---|---|
| `bills/B-A.status` | `settled` |
| `bills/B-A.reopenSummary.latestSettledCycle` | `2`（追いつき） |
| `bills/B-A.reopenSummary.lastResettledAt` | now |
| `bills/B-A/settlementCycles/2.cycleState` | `settled` |
| `bills/B-A/settlementCycles/2/baselineSnapshot/snapshot` | **存在する**（trigger が作成） |
| `bills/B-A/settlementCycles/2.settledAt` | now |
| `bills/B-A/settlementCycles/2.openedReason` | `reopen`（保持） |
| `bills/B-A/settlementCycles/2.openedFromCycleNo` | `1`（保持） |

## 6. Firestore Console / Emulator UI での確認ポイント

- 各シナリオで以下の path を順に確認:
  1. `bills/{billId}` ルート doc（`status` / `currentSummary` / `postSettlementState` / `reopenSummary` / `requireSpecialAttention` 等）
  2. `bills/{billId}/settlementCycles/{oldCycleNo}` の `cycleState` / `closedAt` / `closedReason`
  3. `bills/{billId}/settlementCycles/{oldCycleNo}/baselineSnapshot/snapshot`（不変確認）
  4. `bills/{billId}/settlementCycles/{oldCycleNo}/adjustments/{adjustmentId}` の `adjustmentState` / `cancelledAt` / `cancelReason`
  5. `bills/{billId}/settlementCycles/{oldCycleNo}/cashActions/{cashActionId}`（不変確認）
  6. `bills/{billId}/settlementCycles/{newCycleNo}` の存在と `cycleState='open'` / `openedReason='reopen'`
  7. `bills/{billId}/settlementCycles/{newCycleNo}/baselineSnapshot/snapshot` の **不在確認**（resettle 前）
  8. `bills/{billId}/idempotency/reopenAccountedBill:{key}` の `result` 保存

## 7. ログ確認

- Cloud Logging（または Functions Emulator のログ）で次を確認:
  - 成功時: `logOpsSuccess` 呼び出しが `functionEntry='reopenAccountedBill'`、`outcome='success'`、`operation='reopenAccountedBillRepo'`、`context.billId` / `oldCycleNo` / `newCycleNo` / `cancelledAdjustmentCount` / `reused` / `requestHash8` 含み
  - 失敗時: `logOpsError` が以下の error key と code で出ている
    - `BILLS_REOPEN_NOT_TODAY` / `BILLS_REOPEN_NEVER_SETTLED` / `BILLS_REOPEN_CYCLE_STATE_INVALID` (Step05 固有 / `failed-precondition`)
    - `ACCOUNTING_BILL_NOT_FOUND` / `ACCOUNTING_INVALID_STATE` / `ACCOUNTING_CYCLE_NOT_FOUND` / `ACCOUNTING_IDEMPOTENCY_MISMATCH` (既存共有 / `failed-precondition`)
    - `operation` も `validateReopenBusinessDate` / `validateLatestSettledCycle` / `validateOldCycleState` / `validateBillState` / `validateIdempotencyRequest` / `loadBillContext` 等の判定段階別に分岐
  - 実行 user / device / billId が context として記録されている

## 8. 旧経路の不変確認

- Step05 で旧経路（`postEventReopen` callable / `billsEventsOnCreate` trigger）には触っていないため、`bills/{billId}/events` 配下に新規 doc が増えないこと（シナリオ A〜M ではすべて `events` 配下が空または既存のまま）を確認
- 旧 UI からの `postEventReopen` 呼び出しは Step05 でも今までどおり動作することを別途確認（Step06 で切替予定）

## 9. NG パターンと対処

| 症状 | 想定原因 | 対処 |
|---|---|---|
| `reopenAccountedBill` が `INTERNAL` で落ちる | Emulator 起動なし／network 問題 | Emulator 再起動、`firebase emulators:start --only functions,firestore` |
| 新 cycle が作成されているのに親 doc の `currentSettlementCycle` が古いまま | transaction の partial commit | Step05 では single transaction にまとめている。再現したらコード（`repos/reopenAccountedBill.ts`）を見直し |
| 完了済 adjustment が `cancelled_by_reopen` に遷移してしまう | `effective` フィルタ漏れ | `repos/reopenAccountedBill.ts` の adjustment query が `adjustmentState == 'effective'` を where 句で絞っているか確認 |
| 当日営業日 bill なのに `BILLS_REOPEN_NOT_TODAY` で弾かれる | `storeMeta.currentBusinessDateKey` 値の取得失敗 / store TZ ずれ / storeMeta が `running` でない | `storeMeta/currentBusinessDay` doc の `status='running'` と `currentBusinessDateKey` を Firestore Console で確認 |
| storeMeta が `running` でないため `getCurrentBusinessDateKeyOrThrow` で先に弾かれる | `closeStore` 進行中など | storeMeta state を確認、必要なら開店処理を完了させてから retry |
| `BILLS_REOPEN_NEVER_SETTLED` で settled bill も弾かれる | `reopenSummary.latestSettledCycle` の初期化漏れ | bill 作成時の `latestSettledCycle` 初期値を確認（Step01 で `0`、settle 時に `cycleNo` に更新されるべき） |
| idempotency が効かず cycle が +2 進む | `idempotency/{key}` の保存と再読が出来ていない | `bills/{billId}/idempotency/reopenAccountedBill:{key}` doc を確認、保存されているか検証 |
