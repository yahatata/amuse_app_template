## 6. この時点のメモ

### 6.1 設計上の論点

#### 論点 1: 新 callable の名前

候補:
- `reopenAccountedBill`（精会計済みを示唆 / 推奨）
- `reopenBill`（簡潔 / 旧 callable 名 `postEventReopen` と差別化弱い）
- `reopenSettledBill`（前提を反映）
- `restartBillForReaccounting`（用途明示）

#### 論点 2: bill status の許可範囲

仕様書 §6 「直前状態は `settled` でも `post_settlement_pending` でもよい」を踏まえ:
- 案 A: `settled` / `post_settlement_pending` のみ許可（仕様書通り）
- 案 B: 上記 + `post_settlement_resolved` も許可（adjustment 完了後の最終状態でも reopen できると運用上有利）

#### 論点 3: idempotency キーの扱い

- 案 A: `reopenAccountedBill:{billId}:{idempotencyKey}` を `bills/{billId}/idempotency` に保存（adjustment / cashAction と同一スキーム）
- 案 B: それ以外

→ 案 A で adjustment / cashAction と統一が望ましい

#### 論点 4: 旧 cycle 配下の cashAction / 完了済 adjustment の扱い

- 案 A: 完了済 adjustment (`completed_by_cash_action` / `completed_by_offset`) と cashAction はすべて触らない（履歴として残す）
  - 仕様書 §7.2 が「未完了 adjustment」のみを対象としていることと整合
  - cashAction の `allocations[]` も不変
- 案 B: 部分配賦の cashAction を持つ adjustment は `cancelled_by_reopen` に遷移しても、cashAction 側に影響を与えない（案 A と同じ）

→ 案 A で良い（仕様書通り）

#### 論点 5: zero-yen / 一切活動なし bill の reopen 可否

- `latestSettledCycle = 0`（settle 経験なし）の bill は reopen 不可（仕様書 §6 通り）
- これは precondition で弾く

#### 論点 6: 親 doc の `requireSpecialAttention` / `closeSummary` などの reset 範囲

- 仕様書 §7.3 は `status` / `reopenSummary` / `postSettlementState.requiredActionType` / `requiredActionIncl` / current summary を明示
- `closeSummary` / `requireSpecialAttention` 等の補助フィールドは仕様書記述外
- 案 A: 仕様書記述項目のみ更新（requireSpecialAttention は postSettlementState の派生だが reset しない）
- 案 B: 関連する派生フィールドも reset

→ 案 A を推奨。Step05 では仕様書記述項目に絞り、補助 field は変えない
