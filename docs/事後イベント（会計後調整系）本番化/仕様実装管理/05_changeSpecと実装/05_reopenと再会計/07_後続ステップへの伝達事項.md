  - そうでない場合は disable / hidden / tooltip で「翌日以降の reopen は不可」と表示

## 4. Step05 が意図的に扱わなかった事項

- 旧経路（`postEventReopen` callable / `billsEventsOnCreate` trigger）の改修・廃止 → Step06
- UI 切替（旧 callable から新 callable への差し替え） → Step06
- `analyticsMonthly` への reopen 影響反映 → Step07
- `requireSpecialAttention` / `closeSummary` フィールドの reopen 時 reset / forward → 仕様書記述外、Step05 では touch しない
- 当日以外の bill に対する reopen → 上流ルールで禁止、本実装でも `BILLS_REOPEN_NOT_TODAY` で hard reject
- `latestSettledCycle = 0` の bill（未会計）に対する reopen → `BILLS_REOPEN_NEVER_SETTLED` で hard reject
- migration / backfill → 行わない（未リリース前提）
- Firestore security rules（reopen 権限） → Step06 で UI 切替に合わせて整理する想定

## 5. 共通注意事項

### 5.1 旧経路と新経路の併存

Step05 完了時点で:

- 旧: `bills/{billId}/events` への `type=reopen` event 書き込み ＋ `billsEventsOnCreate` trigger
- 新: `reopenAccountedBill` callable ＋ 新 cycle 作成

両者が並存。Step06 で UI 切替が完了するまでは、UI からの呼び出しは旧経路のまま想定。

### 5.2 dual-write はしない

- 新 callable は `events` 配下に書かない
- 旧 callable は `settlementCycles` 配下を新たに書かない（既存挙動のまま）
- 両系統の整合は Step06 で UI 切替時に検討

### 5.3 後方互換

- Step01 / Step02 / Step03 / Step04 で書いた既存 callable / trigger / helper の API 不変
- Step05 で追加した callable / repo / helper はすべて新規追加
- 既存 cycle = 1 の bill に対する settle / post-settlement adjustment / cashAction 経路は不変

### 5.4 transaction 設計

- `reopenAccountedBill` は single-transaction で全更新を atomically に実行
- transaction 開始前に `getCurrentBusinessDateKeyOrThrow()` を呼び、その値を transaction 内で精確比較
- transaction 中に営業日切替（`closeStore` / `openStore`）が走った場合の race は実害なし（closeStore は営業中の bill が存在する状態では走らない）
- Step06 / Step07 で reopen 後の追加更新を行う場合、`reopenAccountedBill` の transaction とは別 transaction にすること（atomic を維持しないこと）

### 5.5 idempotency

- Step05 で追加した idempotency path: `bills/{billId}/idempotency/reopenAccountedBill:{key}`
- TTL: 既存 adjustment / cashAction と同じく 48 時間想定（運用設定）
- Step06 で UI 側から idempotencyKey を生成する際、UUID v4 等で衝突しない値を使う想定
