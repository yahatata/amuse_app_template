## 3. 主要決定事項（changeSpec で確定 → 実装）

### 3.1 callable 名 → `reopenAccountedBill`（changeSpec §4.1）

- 旧 events 経路 callable `postEventReopen` と差別化
- 「会計済みを再開する」用途を明示

### 3.2 status 許可範囲 → `settled` / `post_settlement_pending` のみ（changeSpec §4.2）

- 仕様書 §6 に厳密準拠
- `post_settlement_resolved` は許可しない（「事後 resolved 後の reopen」というアクション意図が現在仕様書になく、明示禁止のほうが安全）

### 3.3 親 doc reset 範囲 → spec_only（changeSpec §4.3）

- `status` / `currentSummary` / `postSettlementState` / `reopenSummary` のみ touch
- `requireSpecialAttention` / `closeSummary` 等の補助 field は touch しない（仕様書記述外）

### 3.4 当日営業日のみ reopen 可（changeSpec §4.3 / 上流 11 §7）

- ユーザー追加要件として、`bill.businessDate === storeMeta.currentBusinessDateKey` を hard precondition とする
- 「営業日基準で当日のみ」の意味で実装。UTC / カレンダー日ではなく、storeMeta が管理する営業日 key で判定
- 営業時間外 / 閉店処理中は `getCurrentBusinessDateKeyOrThrow` が throw するため自然に弾かれる

### 3.5 idempotency / 完了済 adjustment / zero-yen（changeSpec §4.4）

- 既存 adjustment / cashAction と同一スキーム（`bills/{billId}/idempotency/reopenAccountedBill:{key}`）
- 完了済 adjustment (`completed_by_cash_action` / `completed_by_offset`) と cashActions は touch しない（履歴）
- `latestSettledCycle = 0` の bill は `failed-precondition` で reject

## 5. リスク評価と対応

### 5.1 transaction 内で複数 doc を read する競合

- 旧 cycle / effective adjustments / bill / idempotency を一気に read
- 同一 bill に対する複数 reopen 同時実行: idempotency check で先行が doc を作成すると後続は Firestore の transaction retry → 既存 idempotency match 経路に倒れる
- adjustment / cashAction との競合: bill status が `settled` / `post_settlement_pending` でないと reopen 不可 → reopen 直後は `'open'` になるため adjustment / cashAction 側が `failed-precondition` で弾く

### 5.2 当日営業日 key 取得の transaction 外呼び出し

- `getCurrentBusinessDateKeyOrThrow()` を transaction 開始前に呼び、その値を transaction 内で精確比較
- 営業日切替（`closeStore` / `openStore`）が transaction 中に走った場合: bill.businessDate と乖離する可能性があるが、closeStore は営業中の bill が存在する状態では走らないため実害はない

### 5.3 `billsOnSettle` trigger の cycle > 1 動作

- 既存実装は `bill.reopenSummary.currentSettlementCycle` を参照して cycle を特定するため、Step05 で reopen された後の再会計でもそのまま動作する
- `merge: true` で cycle data を update するため、`openedReason='reopen'` / `openedFromCycleNo` 等は保持される
- 既存 `bills.onSettle.spec.ts` のリグレッション pass で挙動安定を確認

### 5.4 旧 events 経路 (`postEventReopen`) との併存

- Step05 では旧経路を touch しない
- Step06 で UI 切替時に整理する想定

### 7.1 storeMeta state error テストの取り扱い

- `getCurrentBusinessDateKeyOrThrow` の throw 条件 (`status !== 'running'` / doc missing) は storeMeta module の unit テストで担保済み

- そのため Emulator integration spec では storeMeta state error 単体テストは含めず、不安定要因を排除した

- Step05 では analyticsMonthly に直接書かない（Step02 と同様）
- resettle 時の analyticsMonthly 更新は Step07 で扱う
