# 06_要対応の会計画面と一覧取得

## 1. 役割

本仕様書は、`terminalHome` から入る `要対応の会計` 画面について、対象 bill、フィルタ、表示軸、一覧取得条件、ユーザー別カード表示、導線分岐を定める。

## 2. スコープ

本仕様書で扱う対象:

- メニュー名
- 画面の表示軸
- カテゴリフィルタ
- 内部カード種別
- bill 判定条件
- 共通 view model
- 日付ごと / ユーザー別表示
- primary action 導線

## 3. 非対象

本仕様書では次を扱わない。

- `bills` 保存 schema の詳細
- `analyticsMonthly` 集計
- reopen 実行フローの内部処理
- UI デザイン詳細
- exact component 名 / widget 構成

## 5. 基本方針

### 5.1 同じ画面で扱う対象

1. 閉店持ち越し未会計
2. 会計後要対応
   - 追加徴収
   - 要返金

### 5.2 保存構造は混ぜない

同じ画面に出すが、正本構造や lifecycle は統一しない。

### 5.3 導線は分ける

- 未会計 → 通常会計再開
- 追加徴収 → collection 実行
- 要返金 → refund 実行

## 6. 入口

### 6.1 メニュー名

`terminalHome` の現在の `未会計の会計` は、**`要対応の会計`** に変更する。

## 7. 画面構造

### 7.1 表示軸

- `日付ごと`
- `ユーザー別`

### 7.2 フィルタ

- `すべて`
- `未会計`
- `追加徴収`
- `要返金`

デフォルトは `すべて`。

## 8. 内部カード種別

- `carryover_unsettled`
- `post_settlement_collection_pending`
- `post_settlement_refund_pending`

### 8.1 画面ラベル

- `carryover_unsettled` → `未会計`
- `post_settlement_collection_pending` → `追加徴収`
- `post_settlement_refund_pending` → `要返金`

## 9. 判定条件

### 9.1 `carryover_unsettled`

- `status = open`
- `closeSummary.unresolved = true`

### 9.2 `post_settlement_collection_pending`

- `status = post_settlement_pending`
- `postSettlementState.requiredActionType = collection`
- `postSettlementState.requiredActionIncl > 0`

### 9.3 `post_settlement_refund_pending`

- `status = post_settlement_pending`
- `postSettlementState.requiredActionType = refund`
- `postSettlementState.requiredActionIncl > 0`

### 9.4 `すべて`

上記 3 種の和集合。

## 10. 日付ごと表示

### 10.1 意味

カテゴリフィルタ適用後の要対応 bill を、日付単位で一覧表示する。

### 10.2 日付キー

current-scope では、`日付ごと` の grouping / sorting に使う主日付は **cardType ごとに次を使い分ける**。

- `carryover_unsettled`
  - `closeSummary.closedBusinessDate` を主キーにする
  - 取れない場合のみ `bill.businessDate` を fallback にする
- `post_settlement_collection_pending`
  - `bill.businessDate`
- `post_settlement_refund_pending`
  - `bill.businessDate`

理由:

- `carryover_unsettled` は、どの閉店処理で未会計として持ち越されたかが運用上重要
- 会計後要対応は current-scope では parent に別の normalized attention date を持たないため、元売上の `bill.businessDate` を基準にする

### 10.3 `sortDate`

共通 view model の `sortDate` は、上記の日付キーをそのまま使う。

### 10.4 例

- `日付ごと + すべて`
  - その日付の要対応 bill 全件
- `日付ごと + 未会計`
  - その日付の持ち越し未会計のみ
- `日付ごと + 追加徴収`
  - その日付の追加徴収 bill のみ
- `日付ごと + 要返金`
  - その日付の要返金 bill のみ

## 11. ユーザー別表示

### 11.1 意味

カテゴリフィルタ適用後の要対応 bill を持つユーザー一覧を表示する。

### 11.2 ユーザーカードに必須の件数

- `総件数`
- `未会計 x件`
- `追加徴収 x件`
- `要返金 x件`

### 11.3 補足

フィルタ適用中でも、少なくとも当該ユーザーが持つ要対応件数内訳はカードに表示する。

## 12. 共通 view model

current-scope では、画面表示用に少なくとも次を導出できればよい。

- `billId`
- `cardType`
- `displayLabel`
- `businessDate`
- `displayTitle`
- `displayAmountIncl`
- `primaryActionType`
- `sortDate`
- `badgeText`
- `userId`
- `userDisplayName`

### 12.1 `displayAmountIncl`

- `carryover_unsettled`
  - `closeSummary.displayAmountAtMark` 優先
- `post_settlement_collection_pending`
  - `postSettlementState.requiredActionIncl`
- `post_settlement_refund_pending`
  - `postSettlementState.requiredActionIncl`

### 12.2 `primaryActionType`

- `carryover_unsettled` → `resume_accounting`
- `post_settlement_collection_pending` → `collect`
- `post_settlement_refund_pending` → `refund`

### 12.3 `businessDate` と `sortDate` の使い分け

- `businessDate`
  - 元売上の営業日として常に `bill.businessDate` を持つ
- `sortDate`
  - `日付ごと` 一覧の grouping / sorting 用に使う
  - `carryover_unsettled` では `closeSummary.closedBusinessDate` を優先できる

## 13. 一覧取得方式

current-scope では、同じ画面に出すために Firestore query まで 1 本化する必要はない。

許容する実装:

1. 種別ごとに別 query し、クライアント側でマージする
2. 近い条件でまとめて取得し、クライアント側で cardType を判定する

ただし、判定条件は本仕様書を正とする。

## 14. 整合条件

1. `未会計` は carryover unsettled のみを指す
2. `追加徴収` は parent `requiredActionType = collection` を持つものだけを指す
3. `要返金` は parent `requiredActionType = refund` を持つものだけを指す
4. 同じ bill が同時に複数 cardType に分類されない

## 15. 不可条件

- 要対応一覧都合で新しい共通正本 collection を作らない
- 旧 `partially_paid` などの status を前提に判定しない
- 持ち越し未会計と会計後要対応を同一 lifecycle として扱わない

## 16. テスト観点

1. `status = open + closeSummary.unresolved = true` が `未会計` に出る
2. `post_settlement_pending + collection` が `追加徴収` に出る
3. `post_settlement_pending + refund` が `要返金` に出る
4. ユーザー別カードに件数内訳が出る
5. 各カードから正しい導線に遷移する
