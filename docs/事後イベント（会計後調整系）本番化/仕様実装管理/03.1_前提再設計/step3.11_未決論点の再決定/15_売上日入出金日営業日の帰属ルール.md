# 15_売上日入出金日営業日の帰属ルール

## この候補の役割

売上、adjustment、返金 / 徴収、営業日の各日付をどのルールで扱うかを整理する。

今回の `step3.11` では、**現行実装から派生でき、`bills` との整合性を保ったまま実装できる範囲**に絞って帰属ルールを定義する。  
厳密な税務・会計 read model、クレカ後日入金、ポイント treatment、期間締めは future doc に逃がす。

## `step3.11` で先に確定させる必要があるか

- 判定: 必要あり
- 理由:
  - 売上発生日 / adjustment 確定日 / cashflow 実行日を分けないと、`analyticsMonthly` と `bills` 保存モデルの役割分担が崩れる
  - ここが曖昧だと `step3.12` での整合性確認、特に `baselineSnapshot` / `adjustments` / `cashActions` の責務と整合しなくなる

## 今回の前提

### 1. 今回のスコープ

今回ここで確定するのは次に限る。

1. `bills` に既にある / 今回追加する date 軸の意味整理
2. `analyticsMonthly` がどの日付軸を使うかの整理
3. `adjustments` と `cashActions` に最低限必要な日付の整理
4. 将来の税務・会計 read model を作る場合でも、まずは **現行 `bills` 実装から派生し、`bills` との整合性を保って実装する**こと

今回ここで確定しないもの（current-scope ではスコープ外とする future 機能）:

- カード会社から店舗への後日入金日
- 決済手数料の計上日
- 自社ポイント / 他社ポイントの税務 treatment
- 月締め / 年締め / closed period
- 過年度修正や advisor review の厳密ルール

### 2. ここで使う 3 軸

今回の current-scope では、少なくとも次の 3 軸を分けて持つ前提とする。

1. **売上発生日 / 売上帰属日**
2. **adjustment 確定日**
3. **cashflow 実行日**

この 3 軸を分けることで、

- 売上発生
- 売上調整
- 実際の金銭移動

を混同しないようにする。

## 今回確定する仕様

### 3. 売上発生日 / 売上帰属日

#### 3.1 定義

- 売上発生日 / 売上帰属日は、**`bill.businessDate` を正とする**
- 通常会計で baseline が確定した時、その cycle baseline は `bill.businessDate` に属する売上として扱う

#### 3.2 どこに現れるか

- 親 doc の `businessDate`
- `settlementSnapshot` の売上系 summary
- `settlementCycles/{cycleNo}/baselineSnapshot`
- `analyticsMonthly` の売上系集計

#### 3.3 意味

- 通常会計 / `reopen` 後再会計で作られる `baselineSnapshot` は、**その時点の full snapshot** である
- その snapshot の売上帰属先は、current scope では `bill.businessDate` とする

### 4. baseline 確定時刻

#### 4.1 定義

- 初回会計や `reopen` 後再会計で baseline が確定した時刻は、次を代表値として扱う
  - 親 doc 側: `ops.accountingCompletedAt`
  - cycle 側: `settlementCycles/{cycleNo}.settledAt`

#### 4.2 current-scope の考え方

- `businessDate` は売上帰属の軸
- `settledAt` / `accountingCompletedAt` は「いつ確定したか」の軸
- 今回のスコープではこの 2 つを明確に分ける

### 5. adjustment 確定日

#### 5.1 定義

- adjustment が確定した日時は、**`adjustment.createdAt` を正とする**

#### 5.2 意味

- `adjustments/{adjustmentId}` は baseline に対する会計後差分である
- したがって、adjustment の作成時刻は「売上調整が確定した時刻」を表す
- current scope では、別の `confirmedAt` を増やさず `createdAt` を使う

#### 5.3 売上帰属日との関係

- adjustment は **元売上の `businessDate` を書き換えない**
- つまり、
  - 元売上の発生軸は `bill.businessDate`
  - 調整がいつ確定したかは `adjustment.createdAt`
  を分けて持つ

### 6. cashflow 実行日

#### 6.1 定義

- cashAction の実行時刻は、**`cashAction.executedAt` を正とする**
- 営業日キーとして扱いたい場合は **`cashAction.cashflowBusinessDate`** を持つ

#### 6.2 current-scope の考え方

- 返金 / 徴収は、売上そのものではなく **実入出金** である
- したがって、cashflow 側の帰属は `cashAction` 側で持つ
- current scope では、カード会社からの後日入金までは扱わず、あくまで「店舗が返金 / 徴収した操作日」を指す

#### 6.3 `cashflowBusinessDate`

- 実務上、営業時間帯や締め処理の都合で `executedAt` の日付と営業日がずれる余地がある
- そのため `cashflowBusinessDate` を別 field として持てる設計にしておく
- ただし current scope では、もし個別決定がなければ `executedAt` の属する営業日として扱ってよい

### 7. `analyticsMonthly` はどの日付を使うか

#### 7.1 売上系

`analyticsMonthly` の既存 top-level 売上系は、引き続き **`bill.businessDate` ベース**で扱う。

対象:

- `grossSales`
- `itemsSales`
- `sideGameChipSales`
- `extraCostSales`
- `tournamentsSales`
- `dailySales`
- `orderCount`
- `paymentTotals`

#### 7.2 実入出金系

実入出金は `analyticsMonthly` 既存 top-level には混ぜず、`cashActions` を起点に別責務として扱う。

### 8. 4 パターンと日付軸の関係

| パターン | 売上帰属日 | adjustment 確定日 | cashflow 実行日 |
|---|---|---|---|
| `減額 + 返金済` | 元の `bill.businessDate` | adjustment 作成時刻 | 同時 cashAction の `executedAt` |
| `減額 + 返金前` | 元の `bill.businessDate` | adjustment 作成時刻 | 後続 refund cashAction の `executedAt` |
| `増額 + 追加徴収済` | 元の `bill.businessDate` | adjustment 作成時刻 | 同時 cashAction の `executedAt` |
| `増額 + 追加徴収前` | 元の `bill.businessDate` | adjustment 作成時刻 | 後続 collection cashAction の `executedAt` |

ポイント:

- 売上帰属日は元売上側に残す
- adjustment は「後からどう変えたか」を示す
- cashAction は「実際にいつ金が動いたか」を示す

### 9. `reopen` と日付軸

- `reopen` は adjustment ではなく cycle の切替である
- `reopen` 自体は元の `businessDate` を変更しない
- `reopen` 後に再会計して新 baseline を作る時も、売上帰属日は bill 側の `businessDate` を正にする
- `reopen` の実行時刻は `reopenSummary.lastReopenedAt` / cycle state change として残す

### 10. 現行実装から派生させる時の source

今回の current-scope では、支払手段や受領内訳を含む派生処理は、**現行 `bills` 実装から読める source を使って実装する**。

優先順位:

1. `/payments`
2. `meta.paymentMethodsByAmount`
3. `meta.paymentMethodsByCategory + categoryBreakdown`
4. settle 後は `settlementSnapshot.paymentTotals / paymentsSummary`

これにより、今回の仕様は **既存 `bills` と整合する形**で実装できる。

補足:

- 現行実装では、1 回の会計で複数の支払手段を金額配分付きで持てる
- したがって current-scope では、新しい payment ledger を先に作らなくても、既存 source から受領方法配分を派生できる

### 11. current-scope ではスコープ外とする future 機能

今回ここでは、次を決め切らない。

- strict な `reportingEntries / reportingMonthly / cashflowMonthly` schema
- クレカ後日入金日
- カード手数料計上日
- 自社ポイント / 他社ポイントの税務 treatment
- 月締め / 年締め / 過年度修正

## current-scope の結論

今回の `step3.11` では、売上 / 調整 / cashflow の 3 軸を次のように整理して進める。

1. 売上帰属日
   - `bill.businessDate`
2. adjustment 確定日
   - `adjustment.createdAt`
3. cashflow 実行日
   - `cashAction.executedAt`
   - 必要に応じて `cashAction.cashflowBusinessDate`

この整理により、

- `analyticsMonthly` は引き続き売上分析の read model
- `bills` は current state の SoT summary
- `adjustments` は売上差分
- `cashActions` は実入出金

という責務分担を保つ。
