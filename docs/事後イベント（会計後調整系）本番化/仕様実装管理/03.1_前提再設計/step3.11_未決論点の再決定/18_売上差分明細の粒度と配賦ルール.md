# 18_売上差分明細の粒度と配賦ルール

## この候補の役割

減額・増額を `adjustments` 側でどの粒度の明細として持つか、また `analyticsMonthly` にどの粒度で反映するかを整理する。

今回の `step3.11` では、**現行実装の `analyticsMonthly` 集計軸に必要な範囲だけを確定し、`bills` との整合性を保ったまま実装できる形**に閉じる。

## `step3.11` で先に確定させる必要があるか

- 判定: 必要あり
- 理由:
  - `adjustments.lines[]` の粒度が曖昧だと、`analyticsMonthly` にどの category / user / tournament 集計をどう増減させるかが決められない
  - ここが曖昧だと、12 の役割分担と 13 の保存モデルが結び付かない

## 今回の前提

### 1. current-scope で対象にする analytics 軸

今回の current-scope では、`analyticsMonthly` の次の既存集計軸だけを対象にする。

- monthly index top-level
- `days`
- `byCategory`
- `byUser`
- `byTemplateTournaments`

今回ここで対象にしないもの:

- 商品別 / menuItem 別の専用 analytics
- 個別 extra 種別ごとの独立 analytics
- sideGameChip の行動種別ごとの独立 analytics

つまり、**product-level の新しい analytics 軸を増やすことは今回のスコープに含めない**。

### 2. `adjustments.lines[]` は必須

current-scope では、**line-less adjustment は許可しない**。

理由:

- `analyticsMonthly` 反映に category 単位以上の差分情報が必要
- `adjustmentAmountIncl` だけでは、どの category を増減させるかが分からない

したがって、すべての adjustment は少なくとも 1 件以上の `lines[]` を持つ。

## 今回確定する仕様

### 3. line の基本ルール

各 line は少なくとも次を持つ。

- `lineNo`
- `targetCategory`
- `targetId`
- `targetName`
- `operationType`
- `qtyDelta`
- `amountInclDelta`
- `note`

### 4. `adjustmentAmountIncl` との整合

1 adjustment に含まれる `lines[].amountInclDelta` の合計は、`adjustment.adjustmentAmountIncl` と一致する。

ルール:

1. `sum(lines[].amountInclDelta) = adjustmentAmountIncl`
2. `amountInclDelta` の符号は adjustment の方向に合わせる
   - 減額なら負方向
   - 増額なら正方向
3. quantity を持つ line は、`qtyDelta` の符号も同方向に合わせる

### 5. `targetCategory` の current-scope 値

current-scope では次に固定する。

- `item`
- `extra`
- `tournament`
- `sideGameChip`

### 6. category ごとの粒度

#### 6.1 `item`

`item` line は、item 系売上の差分を表す。

最低限必要なもの:

- `targetCategory = item`
- `amountInclDelta`
- item が特定できるなら `targetId`
- 表示用 `targetName`

current-scope の扱い:

- `analyticsMonthly` では item を **items category の売上差分**として反映する
- product-level 専用 analytics は今回の対象外

つまり、item line の `targetId / targetName` は audit と説明可能性のために残すが、current-scope の analytics 反映は category 単位でよい。

#### 6.2 `extra`

`extra` line は、extraCost 系売上の差分を表す。

最低限必要なもの:

- `targetCategory = extra`
- `amountInclDelta`
- `targetName`

current-scope の扱い:

- `analyticsMonthly` では extra を **extraCost category の売上差分**として反映する
- extra 種別別 analytics は今回の対象外

#### 6.3 `sideGameChip`

`sideGameChip` line は、sideGameChip 系売上の差分を表す。

最低限必要なもの:

- `targetCategory = sideGameChip`
- `amountInclDelta`
- `targetName`

current-scope の扱い:

- `analyticsMonthly` では sideGameChip を **sideGameChip category の売上差分**として反映する
- chip 行動種別別 analytics は今回の対象外

#### 6.4 `tournament`

`tournament` line は、tournament 系売上の差分を表す。

これは current-scope で最も細かい粒度を要求する。

最低限必要なもの:

- `targetCategory = tournament`
- `targetId`
  - templateKey / templateId 相当
- `targetName`
  - templateName
- `operationType`
  - `entry`
  - `reentry`
  - `addon`
- `qtyDelta`
- `amountInclDelta`

current-scope の扱い:

- `analyticsMonthly.byTemplateTournaments` を更新するため、tournament line は **template 単位かつ operationType 単位**で持つ
- 1つの adjustment で tournament 差分が複数種類ある場合は、line を分ける

例:

- `entry` を 1 回減額
- `addon` を 2 回追加

は別 line にする。

### 7. `operationType` の current-scope ルール

current-scope では、次でよい。

- `item`
  - `sale`
- `extra`
  - `extra`
- `sideGameChip`
  - `chip`
- `tournament`
  - `entry`
  - `reentry`
  - `addon`

補足:

- item / extra / chip の `operationType` は主に説明用
- tournament の `operationType` は analytics 反映上の必須情報

### 8. `byCategory` への配賦ルール

`byCategory` は `targetCategory` ごとに line を合算して更新する。

対応:

- `item` → `items`
- `extra` → `extraCost`
- `sideGameChip` → `sideGameChip`
- `tournament` → `tournaments`

### 9. monthly index / daily summary への配賦ルール

top-level monthly index と `days` は、`lines[]` を category 単位で合算して反映する。

更新対象:

- `grossSales`
- `itemsSales`
- `extraCostSales`
- `sideGameChipSales`
- `tournamentsSales`
- `dailySales`

ルール:

1. `grossSales` は全 line の `amountInclDelta` 合計
2. 各 category field は対応 category の合計
3. 日別は adjustment 作成時の売上差分反映先日付に対して更新する

### 10. `byUser` への配賦ルール

`byUser` は、bill の `party.userId` がある場合に限り更新する。

ルール:

1. user は line ごとに変えない
2. line の category 合計を、その bill の user に対して反映する
3. userId がない場合は `byUser` 更新を行わない

つまり、`byUser` は line の対象物ではなく **bill 所有者** に対する配賦である。

### 11. `byTemplateTournaments` への配賦ルール

`byTemplateTournaments` は tournament line のみを対象にする。

ルール:

1. `targetCategory = tournament` の line だけ使う
2. `targetId` を templateKey / templateId として使う
3. `operationType` ごとに
   - `entryCount / entrySales`
   - `reentryCount / reentrySales`
   - `addonCount / addonSales`
   を更新する
4. `totalTournamentSales` は tournament line の合計で更新する

### 12. line が不足している adjustment を許可するか

current-scope では、**不足 line のまま analytics へ反映することは許可しない**。

整理:

- category が分からない adjustment は作れない
- tournament なのに template が分からない line は `byTemplateTournaments` を正しく更新できないため current-scope では不可
- generic な金額だけを持つ adjustment を許すと、analytics 反映ルールがぶれるため採らない

### 13. ここまでで必要十分と言えるか

current-scope では **はい** と判断する。

理由:

- 今回対象にする analytics 軸は
  - top-level
  - `days`
  - `byCategory`
  - `byUser`
  - `byTemplateTournaments`
  に限定されている
- それぞれについて、どの line 情報があれば反映可能かを定義できている
- product-level analytics のような未実装軸は今回の対象外に明示的に切っている

したがって、**18 は current-scope では未確定事項なしで閉じてよい**。

## current-scope ではスコープ外とする future 機能

今回は次を future に回す。

- 商品別 / menuItem 別 analytics の新設
- extra 種別別 analytics の新設
- sideGameChip 行動別 analytics の新設
- line からさらに複雑な会計配賦を行うルール
- strict な税務・会計 read model への line 展開

## current-scope の結論

今回の `step3.11` では、

- **すべての adjustment に `lines[]` を必須化**
- **line の category と tournament template / operationType まで定義**
- **現行 `analyticsMonthly` の集計軸に必要な範囲で配賦ルールを固定**

とする。

これにより、`bills` と `analyticsMonthly` の整合を保ったまま、実装に必要な粒度を確定できる。
