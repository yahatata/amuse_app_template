# 11_事後イベントの機能と業務パターン

## この候補の役割

事後イベントとして何を機能として提供するか、またそれをどの業務パターンで整理するかを検討する。

## `step3.11` で先に確定させる必要があるか

- 判定: 必要あり
- 判断理由:
  - ここが決まらないと、後続の `analyticsMonthly`、`bills` 保存モデル、`adjustments / cashActions` 設計、status 管理、未会計との接続方針の単位が定まらない
  - 特に、`reopen` を金銭系イベントと同列に扱うのか、baseline を切り替える別操作として扱うのかは、全体整合性に強く影響する

## 今回確定する仕様

### 1. 利用者に見える機能

事後イベントとして利用者に提供する機能は、次の 5 つとする。

1. `減額 + 返金済`
2. `減額 + 返金前`
3. `増額 + 追加徴収済`
4. `増額 + 追加徴収前`
5. `再会計に戻す（reopen）`

補足:

- `会計後キャンセル` は独立機能として実装しない
- 会計後に全額取り消したい場合は、`減額` 系の中で全額を対象にする運用へ統一する
- `未会計キャンセル` は事後イベントではない
- `未会計キャンセル` は未会計タブ側で、会計不要 bill を論理削除する機能として別実装する

### 2. 利用者向け UI 原則

- まず利用者には `減額` / `増額` / `再会計に戻す` の大分類を選ばせる
- `減額` または `増額` を選んだ場合にだけ、次の段階で `今回その場でお金を動かすか` を選ばせる
- その結果として、内部的な金銭系 4 パターンに分岐する
- `reopen` は同じページを起点にしてよいが、金銭系 4 操作とは視覚的・操作上少し分けて見せる
- 利用者に対しては、`会計前に戻す` ではなく `再会計に戻す` という文言を使う

### 3. 金銭系の業務パターン

金銭系の業務パターンは次の 4 つとする。

1. `減額 + 返金済`
2. `減額 + 返金前`
3. `増額 + 追加徴収済`
4. `増額 + 追加徴収前`

補足:

- `reopen` は金銭系の業務パターンではなく、baseline を切り替える補助操作として扱う
- `会計後キャンセル` は業務パターンとして持たない

### 4. 金銭系業務パターンと内部記録の関係

金銭系 4 パターンと内部記録の関係は次のように整理する。

- `減額 + 返金済`
  - 会計内容の変更を `adjustment` として残す
  - 返金実行を `cashAction` として残す
- `減額 + 返金前`
  - 会計内容の変更を `adjustment` として残す
  - 返金は後続 `cashAction` まで未実行
- `増額 + 追加徴収済`
  - 会計内容の変更を `adjustment` として残す
  - 徴収実行を `cashAction` として残す
- `増額 + 追加徴収前`
  - 会計内容の変更を `adjustment` として残す
  - 徴収は後続 `cashAction` まで未実行

この時の責務分担:

- `settlementCycles/{cycleNo}/baselineSnapshot`
  - その cycle の通常会計 / 再会計で確定した baseline
- `settlementCycles/{cycleNo}/adjustments/{adjustmentId}`
  - baseline に対して何をどう変更したか
- `settlementCycles/{cycleNo}/cashActions/{cashActionId}`
  - 実際にいくら返したか / 受け取ったか

### 5. pending の考え方

pending refund / pending collection は独立 subcollection としては持たない。

代わりに、各 `adjustment` が次を持つ前提とする。

- `cashActionTypeAtCreation`
- `requiredActionRemainingIncl`
- `adjustmentState`

意味:

- `requiredActionRemainingIncl`
  - その adjustment に対して、まだ cash action が必要な残額
- `adjustmentState`
  - `effective` / `completed_by_cash_action` / `completed_by_offset` / `cancelled_by_reopen` / `superseded` などの lifecycle 状態

### 6. `reopen` の位置づけ

`reopen` は、金銭系 4 パターンとは別の補助操作として定義する。

- `reopen` の目的は、確定済み bill を再度会計できる状態へ戻すこと
- `reopen` は金銭系の減額 / 増額 / 返金 / 追加徴収の代替ではない
- `reopen` は baseline を切り替える強い操作であり、adjustment ではない
- `reopen` 後の `status` は `open` とする

### 7. `reopen` の実行条件

`reopen` は次の条件をすべて満たす場合にのみ実行可能とする。

- 対象 bill の現在 status が `settled` である
- 対象 bill の `businessDate` が、`storeMeta.currentBusinessDateKey` と一致する
- つまり、当日営業日分の会計完了済み bill のみ `reopen` できる

### 8. `reopen` の用途

`reopen` の用途は次の 2 つとする。

1. 誤操作で誤って会計完了した bill を未会計側へ戻す
2. 顧客がまだ目の前にいる状態で、複雑な減額 / 増額を事後イベントではなく通常の再会計としてやり直す

### 9. `reopen` の監査と履歴

`reopen` は adjustment としてではなく、cycle と親 doc 要約で追跡する。

最低限追える必要があるもの:

- 何回 `reopen` されたか
- 最後にいつ `reopen` されたか
- 最後に誰が `reopen` したか
- 現在どの cycle を current state の基準にしているか
- 最後にどの cycle まで baseline が確定しているか

### 10. `reopen` の rollback 方針

`reopen` 実行時は、会計完了により発生した影響を、再度会計できる状態まで rollback する必要がある。

#### 10.1 bill 親 doc 内で戻すもの

- `status = open`
- `ops.accountingCompletedAt` / `ops.accountingCompletedBy`
- `settlementSnapshot.*` は old cycle の baseline キャッシュとしては残してよいが、current state 判定は新 cycle 基準へ切り替える
- `currentSummary.*`
- `postSettlementState.*`
- `reopenSummary.currentSettlementCycle`

#### 10.2 cycle 側で残すもの

- old cycle の `baselineSnapshot`
- old cycle の `adjustments`
- old cycle の `cashActions`

ただし、old cycle の未完了 adjustment は `cancelled_by_reopen` 相当にして current 集計対象から外す。

### 11. current cycle と old cycle の扱い

- old cycle の baseline / adjustment / cashAction は history として残す
- 親 doc の current state は current cycle だけで組み立てる
- `reopen` 後は new cycle を current とし、再会計前は `open` 状態として扱う

### 12. 同一 cycle 内の順番

同じ cycle の中で adjustment / cashAction が複数回起きるため、両方に `sequenceNo` を持たせる。

- `sequenceNo` は同じ cycle 内で単調増加
- current state は `baselineSnapshot` に対して、`adjustments` と `cashActions` を `sequenceNo` 順で適用して作る

この前提により、

1. `減額 + 返金前`
2. `返金完了`
3. `増額 + 追加徴収前`
4. `徴収完了`

のような連続操作でも、どの状態の上に次の差分が積まれたかを曖昧にしない。
