# 16_未会計一部未徴収会計後イベントの接続方針

## この候補の役割

閉店時に未会計として持ち越された bill と、会計後イベントにより未徴収 / 未返金の対応が残っている bill を、運用画面でどう接続して扱うかを整理する。

今回の `step3.11` では、**現行 `bills` 保存モデルから派生でき、かつ `bills` との整合性を保ったまま実装できる current-scope 方針**を確定する。

## `step3.11` で先に確定させる必要があるか

- 判定: 必要あり
- 理由:
  - 同じ画面で扱うのか、別画面に分けるのかで、一覧取得条件、カード表示、導線、Step4 の画面仕様が大きく変わる
  - ここが曖昧だと、14 で決めた `status / closeSummary / postSettlementState` の役割が UI へ落ちない

## 今回の前提

### 1. 対象にする 2 系統

今回同じ画面で扱う対象は、次の 2 系統とする。

1. 閉店時に未会計として残り、その後まだ通常会計が完了していない bill
2. 会計後イベントが発生し、その後の未徴収 / 未返金対応がまだ残っている bill

### 2. 保存構造の共通化は current-scope では不要

今回の current-scope では、**保存構造を 1 つに統一することは要求しない**。

つまり、

- 持ち越し未会計は `open` 系の bill
- 会計後要対応は `post_settlement_pending` 系の bill

として分離したままでよい。

代わりに、**同じ画面で扱うための読み取りモデルだけを共通化する**。

### 3. `bills` と整合性を保つ

今回の方針では、新しい共通 status や中間 collection を追加して接続するのではなく、**既に `bills` 親 doc に持たせると決めた summary から導出する**。

したがって、実装時は次を前提にする。

- 持ち越し未会計は `status` と `closeSummary` から判定する
- 会計後要対応は `status` と `postSettlementState` から判定する
- current-scope では、両者を接続するためだけの新しい正本 collection は作らない
- 一覧画面の表示モデルも、**現行 `bills` 実装から派生させる**

## 今回確定する仕様

### 4. 同じ画面で扱う

閉店時持ち越し未会計と、会計後イベント由来の未対応 bill は、**同じ画面で扱う**。

`terminalHome` では、現在の「未会計の会計」メニューを **「要対応の会計」** に変更し、この画面を入口として扱う。

### 5. 画面の基本構造

#### 5.1 一覧の表示軸

画面には、現在の導線を踏襲して次の 2 軸を持たせる。

- `日付ごと`
- `ユーザー別`

#### 5.2 カテゴリフィルタ

さらに、同じ画面の中で次のカテゴリフィルタを持たせる。

- `すべて`
- `未会計`
- `追加徴収`
- `要返金`

デフォルトは `すべて` とする。

### 6. フィルタと内部カード種別の対応

内部のカード種別は、current-scope では次の 3 つを使う。

1. `carryover_unsettled`
2. `post_settlement_collection_pending`
3. `post_settlement_refund_pending`

画面上のラベルは次を使う。

- `未会計`
- `追加徴収`
- `要返金`

#### 6.1 `未会計`

対象:

- `carryover_unsettled`

意味:

- 閉店持ち越し未会計

判定条件:

- `status = open`
- `closeSummary.unresolved = true`

#### 6.2 `追加徴収`

対象:

- `post_settlement_collection_pending`

意味:

- 会計後に追加徴収が必要な bill

判定条件:

- `status = post_settlement_pending`
- `postSettlementState.requiredActionType = collection`
- `postSettlementState.requiredActionIncl > 0`

補足:

- 元の操作が単純な増額だけでなく、opposite-direction adjustment の内部相殺後に collection が残った case も含む

#### 6.3 `要返金`

対象:

- `post_settlement_refund_pending`

意味:

- 会計後に返金が必要な bill

判定条件:

- `status = post_settlement_pending`
- `postSettlementState.requiredActionType = refund`
- `postSettlementState.requiredActionIncl > 0`

#### 6.4 `すべて`

対象:

- `未会計`
- `追加徴収`
- `要返金`

の全件

### 7. 日付ごと表示

`日付ごと` が選択されている場合は、**その日付に当てはまる要対応 bills の一覧**を表示する。

ここでいう当てはまる bill とは、カテゴリフィルタ適用後の bill である。

例:

- `日付ごと + すべて`
  - その日付の要対応 bills をすべて表示
- `日付ごと + 未会計`
  - その日付の持ち越し未会計 bills のみ表示
- `日付ごと + 追加徴収`
  - その日付の追加徴収対象 bills のみ表示
- `日付ごと + 要返金`
  - その日付の要返金対象 bills のみ表示

### 8. ユーザー別表示

`ユーザー別` が選択されている場合は、**何らかの要対応 bills を持つユーザー一覧**を表示する。

カテゴリフィルタ適用後は、その条件に合う bill を持つユーザーのみを表示する。

例:

- `ユーザー別 + すべて`
  - 何らかの要対応 bill を持つユーザー一覧
- `ユーザー別 + 未会計`
  - 未会計 bill を持つユーザー一覧
- `ユーザー別 + 追加徴収`
  - 追加徴収対象 bill を持つユーザー一覧
- `ユーザー別 + 要返金`
  - 要返金対象 bill を持つユーザー一覧

### 9. ユーザーカードに表示する件数

`ユーザー別` のカードには、少なくとも次の件数を表示する。

- `総件数`
- `未会計 x件`
- `追加徴収 x件`
- `要返金 x件`

フィルタ適用中であっても、カード内には少なくともそのユーザーが持つ要対応件数の内訳が分かるようにする。

### 10. 共通画面の読み取りモデル

current-scope では、画面表示用に次のような **共通 view model** を導出する前提でよい。

- `billId`
- `cardType`
- `displayLabel`
- `businessDate`
- `displayTitle`
- `displayAmountIncl`
- `primaryActionType`
- `sortDate`
- `badgeText`
- `userId`
- `userDisplayName`

#### 10.1 `displayLabel`

- `carryover_unsettled`
  - `未会計`
- `post_settlement_collection_pending`
  - `追加徴収`
- `post_settlement_refund_pending`
  - `要返金`

#### 10.2 `displayAmountIncl`

- `carryover_unsettled`
  - まず `closeSummary.displayAmountAtMark` を使う
  - これがない場合の fallback は後続で定義してよい
- `post_settlement_collection_pending`
  - `postSettlementState.requiredActionIncl`
- `post_settlement_refund_pending`
  - `postSettlementState.requiredActionIncl`

理由:

- 持ち越し未会計は、閉店時点の表示額を安定して出せることが重要
- 会計後要対応は、今必要な差額だけが重要

#### 10.3 `primaryActionType`

- `carryover_unsettled`
  - `resume_accounting`
- `post_settlement_collection_pending`
  - `collect`
- `post_settlement_refund_pending`
  - `refund`

### 11. 一覧取得は分離してよい

current-scope では、同じ画面に出すために **Firestore query まで 1 本化する必要はない**。

次のどちらでもよい。

1. 別 query で取得してクライアント側でマージする
2. `status in (...)` などで近い範囲を取り、クライアント側で種別判定する

ただし、**正として使う判定条件は本ファイルで定めた条件に従う**。

### 12. 詳細画面・導線は分ける

同じ一覧に出すが、遷移先の導線は分けてよい。

#### `carryover_unsettled`

- 通常会計の再開
- 未会計 bill 詳細
- 会計編集導線

#### `post_settlement_collection_pending`

- 会計後詳細
- 追加徴収導線

#### `post_settlement_refund_pending`

- 会計後詳細
- 返金導線

つまり、**一覧は共通、処理導線は bill の種類ごとに分岐**でよい。

### 13. current-scope で追加しないもの

今回は次を追加しない。

- 両系統を 1 つにまとめた専用 collection
- 新しい共通 status
- `attentionType` などの親 doc 永続 field
- 持ち越し未会計と会計後要対応を無理に同一 lifecycle に乗せる設計

理由:

- 今の `bills` 設計だけで十分導出可能
- current-scope では保存構造を増やしすぎない方が安全
- 一覧都合で SoT をねじ曲げない方がよい

### 14. current-scope での着地点

今回の `step3.11` では、次を確定する。

1. 閉店持ち越し未会計と会計後要対応は、**同じ画面で扱う**
2. 画面入口は `terminalHome` の **「要対応の会計」** とする
3. 画面には
   - `日付ごと`
   - `ユーザー別`
   と、
   - `すべて`
   - `未会計`
   - `追加徴収`
   - `要返金`
   のフィルタを持たせる
4. 保存構造は分けたままでよい
5. 読み取りモデルだけ共通化する
6. 判定は `bills` 親 doc の `status / closeSummary / postSettlementState` から導出する

これにより、**現行 `bills` 保存モデルから派生でき、かつ `bills` との整合性を保ったまま、同一画面での運用を成立させる**。

## 今回ここで確定しないもの

今回は次を後続へ回す。

- 画面名の最終日本語ラベル微調整
- デフォルト並び順の最終固定
- 一覧を 1 query にするか 2 query にするかの実装選択
- カードの細かい表示項目
- 閉店持ち越し未会計の表示額 fallback
- unified attention read model を将来別 collection に切り出すかどうか

## current-scope の結論

今回の `step3.11` では、**閉店持ち越し未会計と会計後要対応を同じ画面で扱い、`terminalHome` の「要対応の会計」を入口にする**方針を採る。

ただし、保存構造や lifecycle は無理に統一せず、`bills` 親 doc から導出したカード種別とフィルタで UI 上だけ接続する。
