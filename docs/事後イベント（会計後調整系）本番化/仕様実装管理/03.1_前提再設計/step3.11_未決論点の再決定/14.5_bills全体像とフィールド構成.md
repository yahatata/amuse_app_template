# 14.5_bills全体像とフィールド構成

## このファイルの役割

本ファイルは、`13_billsのSoTと保存モデル` と `14_status_summary_pending管理` で決めた内容をもとに、**最終的な `bills` の全体像**を 1 か所で確認できるようにまとめる補助ファイルである。

重要:

- ここでの field 名は、**現時点では仮**のものを含む
- 本ファイルは詳細実装仕様ではなく、**方針と構造の集約**を目的とする
- 正式 schema、transaction 境界、idempotency、migration 方針などは後続の詳細仕様で詰める
- 今回の `step3.11` では、**現行実装から派生でき、`bills` との整合性を保ったまま実装できる範囲**を前提とする

## 1. `bills` 全体構造

```text
bills/{billId}
├─ 親doc
├─ items/{itemId}
├─ extras/{extraId}
├─ tournaments/{tournamentId}
├─ sideGameChips/{chipDocId}
├─ payments/{paymentId}
└─ settlementCycles/{cycleNo}
   ├─ cycle親doc
   ├─ baselineSnapshot
   ├─ adjustments/{adjustmentId}
   │  └─ lines[]（埋め込み推奨）
   └─ cashActions/{cashActionId}
      └─ allocations[]（埋め込み必須）
```

## 2. レイヤごとの役割

### 2.1 bill 親 doc

- 一覧・運用画面用の current-state summary
- `status`
- 現在の請求 / 受領 / 返金 / 純売上
- 今必要な対応の向きと金額
- `reopen` 履歴
- 閉店持ち越し未会計情報

### 2.2 bill 直下ライブサブコレ

- 会計前の編集対象
- `reopen` 後の再会計でも再利用する作業領域
- 現時点の実装では、支払手段入力の source としても使われる

### 2.3 `settlementCycles/{cycleNo}`

- baseline の版管理
- `baselineSnapshot`
- adjustment / cashAction の所属単位
- `sequenceNo` の採番単位

### 2.4 `baselineSnapshot`

- その cycle で通常会計 / 再会計した時の full snapshot
- 後から更新しない

### 2.5 `adjustments`

- baseline に対する会計後差分
- 何をどう変えたか
- まだどれだけ現金処理が必要か

### 2.6 `cashActions`

- 実際の返金 / 徴収履歴
- どの adjustment をどれだけ解消したか

## 6. `baselineSnapshot` 現時点案

baseline は `settlementCycles/{cycleNo}/baselineSnapshot` の **1 doc** にまとめる。

持つ想定:

- `items[]`
- `extras[]`
- `tournaments[]`
- `sideGameChips[]`
- `amounts`
- `categoryBreakdown`
- `paymentTotals`
- `paymentsSummary`
- `contentHash`

### baselineSnapshot の原則

- 通常会計時 / `reopen` 後会計時の full snapshot
- 通常の事後イベントでは更新しない
- 差分だけを持つ場所ではない

### baselineSnapshot と現行実装の接続

- `paymentTotals` / `paymentsSummary` は、現時点では existing `bills` 実装から自然に派生できる summary として使う
- したがって、今回の `step3.11` では支払手段を含む派生処理も、まずは `baselineSnapshot` と親 doc summary の整合を優先する

### 本体 field

| field | 意味 |
|---|---|
| `sequenceNo` | 同一 cycle 内での順番 |
| `cashActionType` | `refund` / `collection` |
| `amountIncl` | 実行金額 |
| `executedAt` | 実行時刻 |
| `executedBy` | 実行者 |
| `cashflowBusinessDate` | 実際に金が動いた営業日 |
| `methodBreakdown[]` | 方法別内訳 |
| `allocations[]` | どの adjustment をどれだけ解消したか |
| `note` | 備考 |

### `methodBreakdown[]`

| field | 意味 |
|---|---|
| `method` | 現金 / QR / 振込 など |
| `amountIncl` | その方法での金額 |

### `allocations[]`

| field | 意味 |
|---|---|
| `adjustmentId` | 対象 adjustment |
| `amountIncl` | その adjustment に充当した金額 |

### `allocations[]` の必須ルール

1. `cashAction` は必ず `allocations[]` を持つ
2. `cashAction.amountIncl = allocations[].amountIncl の合計`
3. allocation 対象は同一 cycle の adjustment のみ
4. allocation 対象は `requiredActionRemainingIncl > 0` の adjustment のみ

## 9. `requiredActionRemainingIncl` 更新ルール

### 9.1 adjustment 作成時

- pending 系 adjustment は provisional remaining = `adjustmentAmountIncl`
- 即時返金 / 即時徴収系 adjustment は、同一処理内で対応 cashAction を作る前提で、最終 remaining は 0 にする

### 9.2 opposite-direction adjustment が来た時

- 古い未解消 adjustment から `sequenceNo` 昇順で内部相殺する
- 相殺で 0 になったものは `completed_by_offset` 相当
- internal offset 後に残った片側の差額だけが親 doc の required action になる

### 9.3 cashAction 作成時

- `allocations[]` に従って各 adjustment の remaining を減らす
- 0 になった adjustment は `completed_by_cash_action` 相当
- まだ残るものは `effective` のまま

## 10. current state 再計算の原則

親 doc の current state は次から再計算する。

- `settlementCycles/{latestSettledCycle}/baselineSnapshot`
- current cycle の `adjustments`
- current cycle の `cashActions`

この時、`sequenceNo` 順に適用する。

## 11. cycle の進み方

- bill 作成時
  - `currentSettlementCycle = 1`
  - `latestSettledCycle = 0`
- 初回会計時
  - cycle 1 baseline を確定
  - `latestSettledCycle = 1`
- 通常の adjustment / cashAction 時
  - cycle は進めない
- `reopen` 時
  - `currentSettlementCycle` を次 cycle に進める
  - new cycle を `open` で作る
- `reopen` 後会計時
  - new cycle baseline を確定
  - `latestSettledCycle = currentSettlementCycle`

## 12. 現行実装から派生させる時の読み順

今回の current-scope では、支払手段や受領内訳を使う派生処理は次の順で source を読む前提でよい。

1. `/payments`
2. `meta.paymentMethodsByAmount`
3. `meta.paymentMethodsByCategory + categoryBreakdown`
4. settle 後は `settlementSnapshot.paymentTotals / paymentsSummary`

この方針により、**既存 `bills` 実装を壊さず、`bills` との整合性を保ったまま派生コレクションを作る**ことができる。
