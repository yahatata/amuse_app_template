# 03.1_前提再設計 README

このディレクトリは、詳細仕様書の作成に進む前に、事後イベント本番化と `bills × analyticsMonthly` 再設計の前提を整理し直すための作業場所である。

ここでは、個別画面や API の詳細仕様に入る前に、次の 6 ステップで前提を固める。

1. `step3.11`: 決まっていないことを再度決める
2. `step3.12`: 全体の整合性を確認する
3. `step3.13`: 整合性が取れていない部分を再設計する
4. `step3.14`: 全体設計を完成させる
5. `step3.15`: 詳細仕様書をどの粒度で分けるか決定する
6. `step3.16`: 詳細仕様書作成の着手条件を確認する

## この段階で固めるべき中心論点

- 事後イベントの 5 機能と 4 業務パターンの定義
- `bills` 親 doc / `settlementCycles` / `baselineSnapshot` / `adjustments` / `cashActions` の SoT
- 未会計 bills と会計後要対応 bills の関係
- 売上帰属日と cashflow 帰属日の扱い
- 4 パターンごとの `analyticsMonthly` 更新方針
- 複数 adjustment / cashAction 実行時でも整合性が壊れない親 doc 再計算ルール

## このディレクトリの役割分担

- `step3.11_未決論点の再決定/`: 仕様候補の洗い出し、必要性評価、確定対象整理
- `step3.12_*.md`: 整合性確認メモ
- `step3.13_*.md`: 再設計論点と改訂案
- `step3.14_*.md`: 全体設計の完成版
- `step3.15_*.md`: 詳細仕様書の分割方針
- `step3.16_*.md`: 詳細仕様書作成の着手条件と入力整理
- `../04_仕様書/`: `Step4` で作成する詳細仕様書の正本

## 進め方の原則

- この段階では、実装に入らない
- `03_ToBe意思決定/` で決めた内容は、無条件で維持するのではなく、全体整合性の観点から再確認する
- ただし、すでに妥当と判断できる決定事項は再利用し、全てをゼロから書き直さない
- 事後イベント本番化と analyticsMonthly 再設計が混線しないよう、常に「業務パターン」「SoT」「帰属日」「analytics 更新」の 4 層に分けて整理する
- `settlementCycles` は baseline の版、`adjustments` は会計後差分、`cashActions` は実入出金という責務分担を崩さない
