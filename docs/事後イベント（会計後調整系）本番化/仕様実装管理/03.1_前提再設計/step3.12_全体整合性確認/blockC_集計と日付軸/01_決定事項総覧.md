# Block C 01_決定事項総覧

## 1. このブロックで扱う話

このブロックは、集計責務と日付軸を current-scope でどう定義するかを扱う。

## 2. current-scope の結論

### 2.1 `analyticsMonthly` の役割

- 運用ダッシュボード用 read model
- SoT ではない
- 現行実装から派生できる source に限定して使う

### 2.2 支払手段 source の読み順

current-scope では、支払手段情報は次の優先順位で読む。

1. `/payments`
2. `meta.paymentMethodsByAmount`
3. `meta.paymentMethodsByCategory + categoryBreakdown`
4. settle 後の `settlementSnapshot.paymentTotals / paymentsSummary`

### 2.3 3 つの日付軸

- 売上帰属日
  - `bill.businessDate`
- adjustment 確定日
  - `adjustment.createdAt`
- cashflow 実行日
  - `cashAction.executedAt`

### 2.4 4 パターンと更新責務

- adjustment 作成時
  - 売上差分を更新
- cashAction 実行時
  - 実入出金を更新
- settle / resettle 時
  - baseline を反映

### 2.5 `adjustments.lines[]`

- line は必須
- `targetCategory` は current-scope で
  - `item`
  - `extra`
  - `tournament`
  - `sideGameChip`
- `sum(lines[].amountInclDelta) = adjustmentAmountIncl`

### 2.6 tournament line

`tournament` は current-scope で最も細かく持つ。

- template 単位
- `entry / reentry / addon` 単位

### 2.7 current-scope でスコープ外とする future 機能

今回やらないもの:

- tax/accounting 用 strict read model の本実装
- product-level analytics 新設
- card 後日入金や fee の厳密管理
- points treatment の厳密判定

これらは current-scope の仕様書には持ち込まず、future 機能として別管理する。

## 3. 2026-05-09 時点で確定したこと

- `analyticsMonthly` は運用ダッシュボード用 read model として扱う
- 日付軸は `bill.businessDate` / `adjustment.createdAt` / `cashAction.executedAt` の 3 本で分ける
- 支払手段 source は現行 `bills` 実装から派生できる範囲に限定する
- `adjustments.lines[]` は必須
- current-scope を超える strict な税務・会計 read model は future 機能とする

## 4. なぜこの方針にしたか

- 改修範囲を広げすぎないため
- 今の実装から派生させられるものに絞るため
- `bills` と `analyticsMonthly` の整合を保つため

## 5. このブロックの核

一言でいうと、

**「current-scope では、`analyticsMonthly` は運用用途に限定し、売上日・差分確定日・資金移動日を分け、line 粒度は既存集計軸に必要十分な範囲に固定する」**

という方針である。
