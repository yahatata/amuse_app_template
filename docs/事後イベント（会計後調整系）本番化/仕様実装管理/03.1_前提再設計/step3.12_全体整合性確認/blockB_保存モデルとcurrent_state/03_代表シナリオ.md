# Block B 03_代表シナリオ

## 1. シナリオA: 通常会計のみ

### 状況

- bill 作成
- 初回会計確定

### 期待される構造

- `settlementCycles/1`
- `baselineSnapshot`
- `adjustments` なし
- `cashActions` なし
- parent `status = settled`

## 2. シナリオB: `減額 + 返金前` → 後で返金

### 状況

- cycle 1 baseline がある
- adjustment を作る
- 後日 refund の cashAction を作る

### 期待される構造

- `adjustments/adj_1`
  - `requiredActionRemainingIncl > 0`
- `cashActions/cash_1`
  - `allocations = [{ adjustmentId: adj_1, amountIncl: ... }]`
- parent は
  - adjustment 時: `post_settlement_pending`
  - refund 後: `settled`

## 3. シナリオC: opposite-direction adjustment

### 状況

- 先に refund 側 adjustment
- 後で collection 側 adjustment

### 期待される構造

- opposite-direction の内部相殺が行われる
- parent には差額だけが required action として残る
- `cashActions` は複数 adjustment をまたいで解消できる

## 4. シナリオD: `reopen`

### 状況

- cycle 1 settled
- `reopen`

### 期待される構造

- `currentSettlementCycle = 2`
- `latestSettledCycle = 1`
- old cycle の未完了 adjustment は `cancelled_by_reopen`
- cycle 2 は open

## 5. シナリオE: 未リリース前提

### 状況

- 既存開発データがある
- 新仕様に切り替える

### 期待される方針

- 旧データを backfill しない
- 新規生成 bill から新仕様を適用する
- 必要設定があれば初期化時に作る
