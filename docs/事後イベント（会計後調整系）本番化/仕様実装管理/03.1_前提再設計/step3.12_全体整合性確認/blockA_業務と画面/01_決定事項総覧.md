# Block A 01_決定事項総覧

## 1. このブロックで扱う話

このブロックは、利用者から見える業務ルールと、会計管理 UI の大枠を決めるためのもの。

主語は次の 2 つである。

1. 事後イベントとして何をできるようにするか
2. `terminalHome` の `要対応の会計` で、要対応 bill をどうまとめて見せるか

## 2. current-scope の結論

### 2.1 利用者に見せる機能

金銭系の操作は次の 4 パターンに整理する。

- `減額 + 返金済`
- `減額 + 返金前`
- `増額 + 追加徴収済`
- `増額 + 追加徴収前`

これに加えて、金銭系ではない強い操作として `reopen` を持つ。

### 2.2 `reopen` の意味

`reopen` は、会計後差分を積み続けるのではなく、**現在の会計を未会計へ戻して再会計し直す入口**である。

そのため:

- `reopen` は adjustment ではない
- baseline を切り替える操作である
- `reopen` 後の bill は `open` に戻る

### 2.3 `要対応の会計` 画面

`terminalHome` の現在の `未会計の会計` メニューは、**`要対応の会計`** へ改名する。

この画面で扱う対象は次の 2 系統である。

- 閉店持ち越し未会計
- 会計後要対応

この 2 つは、**同じ画面で扱う**。

ただし、同じものとして扱うわけではない。

- 閉店持ち越し未会計
  - まだ通常会計が終わっていない bill
- 会計後要対応
  - いったん会計済みだが、未徴収 / 未返金が残っている bill

この 2 つは保存構造も lifecycle も違うため、**同じ画面に出すが、カード種別は分ける**。

### 2.4 画面構造

#### 表示軸

- `日付ごと`
- `ユーザー別`

#### フィルタ

- `すべて`
- `未会計`
- `追加徴収`
- `要返金`

デフォルトは `すべて` とする。

### 2.5 内部カード種別と表示ラベル

current-scope では、同じ画面に出す内部カード種別を次の 3 つに固定する。

- `carryover_unsettled`
- `post_settlement_collection_pending`
- `post_settlement_refund_pending`

画面上のラベルは次の 3 つを使う。

- `未会計`
- `追加徴収`
- `要返金`

### 2.6 種別の判定

#### `carryover_unsettled`

- `status = open`
- `closeSummary.unresolved = true`

#### `post_settlement_collection_pending`

- `status = post_settlement_pending`
- `postSettlementState.requiredActionType = collection`
- `postSettlementState.requiredActionIncl > 0`

#### `post_settlement_refund_pending`

- `status = post_settlement_pending`
- `postSettlementState.requiredActionType = refund`
- `postSettlementState.requiredActionIncl > 0`

### 2.7 同じ画面で扱うが、導線は分ける

- `未会計`
  - 通常会計再開導線
- `追加徴収`
  - 追加徴収導線
- `要返金`
  - 返金導線

つまり、一覧は共通、処理導線は分岐でよい。

### 2.8 ユーザー別表示の件数要件

`ユーザー別` では、ユーザーカードに少なくとも次を表示する。

- `総件数`
- `未会計 x件`
- `追加徴収 x件`
- `要返金 x件`

## 3. なぜこの方針にしたか

### 3.1 利用者都合

利用者は「今対応が必要なもの」を 1 画面で見たい。

### 3.2 SoT 都合

しかし、一覧都合で保存構造まで無理に統一すると、`bills` 側の構造が不自然になる。

### 3.3 今回のスコープ都合

current-scope では、**新しい共通 collection や共通 status を増やさず、既存 parent summary から導出する**方が安全である。

### 3.4 現行実装との接続都合

現在の `terminalHome` には、`日付ごと` と `ユーザー別` の整理が既にある。
今回の方針は、それを壊さずに **`要対応の会計` + 4 フィルタ** を足す形なので、現行画面構造から自然に派生できる。

## 4. ここで明示的に採らないもの

- `partially_paid` のような新 status
- 持ち越し未会計と会計後要対応を同じ lifecycle に乗せる設計
- 一覧都合での共通正本 collection
- `in_progress` を `reopen` 後 status として残す設計
- `voided` を current-scope の標準 UI 状態として使う設計

## 5. このブロックの核

一言でいうと、

**「`要対応の会計` という 1 画面に要対応 bill を集めるが、正本構造は無理に混ぜず、`bills` 親 doc から種別を導出して UI だけ共通化する」**

という方針である。
