# 01_改修項目再編

## 1. 目的

本ファイルは、事後イベント（会計後調整系）本番化に向けた改修候補を、**以後の仕様化・changeSpec・実装で扱いやすい 5 項目**に再編した正本である。

Step1 完了後は、項目定義の参照元を [../改修フォーカス候補.md](../改修フォーカス候補.md) から本ファイルへ切り替える。

---

## 2. 再編ポリシー

- 画面単位ではなく、**責務と依存関係**でまとめる
- `F1` から `F15` は **重複なく** `I1` から `I5` に割り当てる
- 後続フェーズで迷わないよう、**業務ルール -> 表示/状態 -> UI導線 -> 集計/監査 -> 性能仕上げ** の順に並べる
- 旧資料にしかない補助論点も、本ファイルに引き継いで扱い先を明示する

## 5. 依存順

### 5.1 基本の依存関係

```text
I1 -> I2 -> I3 -> I5
I1 -> I4 -> I5
I2 -> I4
```

### 5.2 依存順をこの並びにした理由

1. `I1` を先に確定しないと、返金・追加徴収・未収・ポイント・営業日境界の扱いがぶれ、後続の画面/集計仕様が固まらない
2. `I2` は `I1` の結果を受けて、画面がどの状態・どのデータ源を見ればよいかを固定する段階である
3. `I3` は `I2` で見せ方と取得条件が定まったあとでないと、会計完了タブ再設計や閉店中の導線設計がぶれやすい
4. `I4` は `I1` のイベント契約が前提であり、再開や返金の最終 status ルールは `I2` の結果も参照する
5. `I5` は `I2` `I3` `I4` でクエリ形状が固まったあとに実施するのが最も手戻りが少ない

補足:
`I4` は `I1` と `I2` が固まった時点で、`I3` と並行して一部検討を進めてもよい。ただし番号としては、全体運用上わかりやすいよう `I3` の後ろに置く。

## 6. 後続フェーズでの扱い

### I1. 事後イベント業務ルールとデータ契約

- Step2 で必ず固定する観点:
  - 返金イベントの `method` とその粒度
  - 返金/追加徴収の支払内訳を単一 `method` で持つか、`byMethod` 配分で持つか
  - 返金を元の支払内訳でどこまで拘束するか
  - 追加徴収と未収の切り分け
  - post-settlement collection の保存先と status 設計
  - 減額可能範囲の計算ルール
  - `selectedBusinessDateKey` の受け渡し
  - ポイント/ユーザー残高返還の責務境界

### I2. 伝票状態・表示データ・一覧取得の正規化

- Step2 で必ず固定する観点:
  - 未会計/会計完了タブの取得条件
  - `settled` 以外の返金系 status の見せ方
  - 明細/内訳の正規データ源
  - 会計完了カードに `postEvents` / 残高 / 純売上差分をどう表示するか
  - 返金画面で元支払内訳と方法別返金上限をどう表示するか
  - 再開後の status と再表示条件
  - 再開時に集計側へどの差分が必要か

### I3. 会計管理 UI 導線と営業状態別アクセス設計

- Step2 で必ず固定する観点:
  - 会計管理配下でどこまで完結させるか
  - 会計後キャンセル導線
  - 閉店中に表示/操作可能な範囲
  - 強警告ゲートとの関係
  - 旧テスト導線/旧ダイアログの扱い

### I4. 分析・監査反映基盤

- Step2 で必ず固定する観点:
  - Analytics 差分反映の対象イベント
  - 再開時の analytics 差分減額またはロールバック方式
  - analytics 失敗時の検知と再処理、bill 本体処理との責務分離
  - 運用資料に残すべき反映範囲、再処理手順、非対象
  - `getRefundHistory` の取得単位
  - 監査上必要な履歴参照項目

### I5. クエリ性能・インデックス・リリース仕上げ

- Step2 で必ず固定する観点:
  - 一覧クエリの最終条件
  - 必須 `orderBy`
  - 必要複合インデックス
  - 一覧 read model による N+1 解消方針
  - `limit` / `もっと見る` の適用対象
  - 件数増加時の性能劣化ポイント
  - リリース前の性能確認基準

## 7. 旧資料から引き継ぐ補助論点

`初期検討事項まとめ.md` にある論点のうち、`F1` から `F15` に明示されていないものは、以下の扱いで本管理に引き継ぐ。

| 補助論点 | 扱い先 | 引き継ぎ方針 |
|----------|--------|--------------|
| G4: `RefundProcessingDialog` と現行 `processRefund` のペイロード不整合 | I3 | 旧導線/旧ダイアログ整理の一部として扱う |
| G8: 金額を伴わない注記のみイベント | I1 | 新しいイベント種別が必要かどうかを業務ルール検討対象に含める |
| G9: 設計ドキュメントと実装の差 | 全体共通 | 各 Step 完了時に、関連ドキュメントの更新要否を必ず確認する共通ルールとする |

補足:
G1, G2, G3, G5, G6, G7 はそれぞれ `F9`, `F10`, `F11`, `F12`, `F13`, `F14` に内包済みである。
