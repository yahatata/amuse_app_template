## 2. 共通基盤で何を追加・変更したか

- `FunctionCustomError` を追加。
  - 必須: `errorKey`, `message`
  - 任意: `context`, `cause`
  - `service` / `functionEntry` / `operation` は持たせない。
- `logOpsError` を差分仕様・changeSpec方針で拡張。
  - 主軸: `errorSource`, `service`, `functionEntry`, `projectId`, `errorMessage`, `errorName`, `context`
  - `function_custom` 時のみ `errorKey`
  - `external_api` 時、および **`function_custom` かつ `cause` から外部 shape を抽出できるとき**に `sourceProduct`, `sdkCode`, `httpStatus`, `detailReason`（取得分のみ）
  - `context` は payload 直下で `context` オブジェクトとして保持（フラット展開しない）
- `errorSource` 判定を共通化。
  - 明示指定 > `errorKey`/`FunctionCustomError` > external shape > `function_common`
- external 抽出処理を共通化（`externalFromCause.ts`）。
  - shape 優先（`status`, `code`, `details` 等）
  - 取得できない項目は未設定
  - 補助指定は `sourceProductHint` のみ
  - **追記（2026-04-08）**: Admin Storage と同様の方針で、**Firestore クライアントがプレーン `Error` + 定型メッセージだけで投げるケース**（例: `not a valid Firestore document`、`as a Firestore value`、`ignoreUndefinedProperties` を含む文言）を **`message` の部分一致**で検知し、`sourceProduct: firestore` を付与する。`code` が無くても `errorSource` が `external_api` になりうる（hint 不要）。
- `functionEntry -> service` マップを `serviceByFunctionEntry.ts` として追加。
  - 対応表（主表+export外）由来
  - 未登録は `unknown_service`
  - 対応表の整理（`platform` 廃止、端末3件は `device`、`controlHookHttp` は `tournament_schedule`、`close_process` を `store` に統合 等）は `functionEntry_service_対応表.md` を正とする。
- **`operation` の必須化・一意性（2026-04-11 追記）**
  - ログ引数の **`functionEntry` が同一文字列リテラル**として現れる **`logOpsError` 呼び出しが 2 回以上**ある場合、**各呼び出しに `operation` プロパティを付与する**（値は文字列リテラルまたは式）。
  - **`operation` が文字列リテラル**で指定されている呼び出し同士では、**同一 `functionEntry` スコープ内で値の重複を禁止**する（モニタ上の区別のため）。
  - **静的検証**: `functions/scripts/verifyLogOpsOperation.cjs`（`npm run verify:logops-operation`）。`functions/src/**/*.ts` を走査し、上記をチェックする。`src/debug` / `demo_data` / `unused_function_lib` は対象外。
  - **仕様書**: `エラーログ拡張仕様書_差分実装版.md` の **§6.4.1** / **§8.5**（改訂履歴 **2026-04-11**）。

## decisionLog (2026/04/09 〜)

本節は、`service` / `errorSource` / `FunctionCustomError` / logOpsError 呼び出し分類に関する**判断の整理**と、**本ドキュメント・実コードで触れた更新**を記録する（実装の一次情報は引き続き §15 等を正とする）。

### DL-1. `platform` service と対応表

- **仕様上の説明**: `functionEntry_service_対応表.md` 冒頭に、**`platform` は廃止**と記載あり（横断インフラの粒度が業務 `service` と揃わないため）。代替として **`device`**（店舗端末）、**`scheduler`**（スケジューラ／ジョブ基盤）、**`config`**（店舗設定ロード）への分割を明示。
- **実装サマリとの整合**: 本書 §2・§4 にあるとおり、`controlHookHttp` の `service` は **`tournament_schedule`**（旧 `platform` 粒度の整理）。

### DL-2. `finalizeDay` / `finalizeMonth` / `initShiftDaysForMonth` の service

- **実コード** `functions/src/shared/logging/serviceByFunctionEntry.ts` では、上記 3 つとも **`shift`**。
- **対応表** `functionEntry_service_対応表.md` でも同様に **`shift`**（`finalizeDay`・`finalizeMonth` を `business_hours` と誤認しない。`initShiftDaysForMonth` も **`shift`**）。

### DL-3. `service` と `errorSource`（会計・店舗・トーナメント系 logOpsError）

- **`service`** は `functionEntry` → `SERVICE_BY_FUNCTION_ENTRY` で付与。**`errorSource`** は `resolveErrorSource` により、`cause` / `args.errorKey` の形で決まる。よって **同一 `service` でも `function_custom` と限らない**。
- **big4**（`accounting` / `store` / `tournament_schedule` / `tournament`）に限った `logOpsError` 呼び出しは **175 件**（マップ基準）。
- **静的に「ログ出力時、必ず `errorSource=function_custom`」と言える呼び出し**について、**リポジトリ全体（§14.9 のスコープ）の再集計は 52 件**（`functions/scripts/countStaticFunctionCustomLogOps.cjs`）。旧メモの **44** は **big4 中心の別定義・別時点**の目安であり、**正は §14.9 / `実装ベース精査_function_custom_20260408.md`**。

### DL-4. 175 未満保証（131）の分類メモ（監査用）

- **A（22）**: 同一 `catch` で **先に `FunctionCustomError` 分岐**があり、その**後**の汎用 `logOpsError`。**この行が実行されたとき `cause` は `FunctionCustomError` ではない**と分岐構造から言える → **`function_custom`（FC 規則）にはならない**。
- **C（5）**: 直前ソース窓の参考分類（確定には不向き）。
- **D（104）**: 自動分類では起因を確定できない群。

### DL-5. 実コード変更（本整理に関連）

- `updateScheduledTournamentStartAt.ts` / `updateScheduledTournamentStatus.ts`: `logOpsError` から **`errorKey: e.errorKey` を削除**（`cause` のみ。`errorSource` / payload の `errorKey` の意味は `logOpsError.ts` のマージ仕様どおり維持）。

### DL-6. 来店処理（user）の `errorKey` 明示（2026-04-10）

- **`domains/user/callables/`** の 6 Callable で、**例外時 `logOpsError` に `errorKey` を付与**（§3 節の表を正とする）。`FunctionCustomError` の新規 throw は行わない。
- 仕様書 `エラーログ拡張仕様書_差分実装版.md` の **§16.5 / §16.6 / §21** を更新。

### DL-7. Firestore クライアントの定型メッセージから `sourceProduct: firestore`（2026-04-08）

- **課題**: Firestore がプレーン `Error` + メッセージのみで失敗を返すと、`extractExternalFromCause` が `sourceProduct` を付けず **`errorSource` が `function_common`** になりうる（例: スケジューラ実行ログの Firestore 書き込み失敗）。
- **方針**: Storage の GCS 定型メッセージと同様、**誤検知しにくい定型フレーズの部分一致**で `sourceProduct: firestore` を付与（`functions/src/shared/logging/externalFromCause.ts` の `looksLikeFirestoreSdkClientMessage`）。
- **仕様書**: `エラーログ拡張仕様書_差分実装版.md` **§9.4** 補足を参照。

### DL-8. `operation` の必須条件と文字列リテラル一意性（2026-04-11）

- **方針**: 同一 **`functionEntry` 文字列リテラル**に対する **`logOpsError` が 2 回以上**ある場合は **各呼び出しに `operation` を必須**とする。**`operation` が文字列リテラル**の呼び出し同士は **同一 `functionEntry` 内で重複禁止**（式による `operation` は「必須」の対象に含め、**一意性の静的検証はリテラル同士に限定**）。
- **検証**: `functions/scripts/verifyLogOpsOperation.cjs`（`npm run verify:logops-operation`）。`debug` / `demo_data` / `unused_function_lib` は走査対象外。
- **実装**: `functions/src` 全域で `operation` の付与・重複解消（callable / repo / webhook 等の**ファイル横断**で同名 `functionEntry` が衝突していた箇所を含む）。
- **仕様書**: `エラーログ拡張仕様書_差分実装版.md` **§6.4.1** / **§8.5** / **改訂履歴（2026-04-11）**。

### DL-9. 静的 `function_custom` 確定の `logOpsError` 再集計（2026-04-11）

- **件数**: **52 件**（AST 走査。§14.9・`実装ベース精査_function_custom_20260408.md` を正とする）。
- **旧スナップショット**（同精査ファイルにあった **48 件**表および **48+7=55 件**見込み）は、**FC 分岐の外にある汎用 `catch` 側の `logOpsError` を誤って二重に数えた**等の理由で **撤回**。
- **呼び出し側**で `errorSource: 'function_custom'` を渡している行は **なし**（`logOpsError.ts` の `resolveErrorSource` が決定）。
