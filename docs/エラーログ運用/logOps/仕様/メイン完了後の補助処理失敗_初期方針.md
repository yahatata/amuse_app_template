# メイン完了後の補助処理失敗：初期方針

## 1. 文書情報

- **文書名**: メイン完了後の補助処理失敗：初期方針
- **対象**: Firebase Cloud Functions における、メイン処理完了後の補助処理
- **対象範囲**:
  - Firestore Trigger
  - Callable
  - Scheduler / Batch
  - Cloud Tasks worker
- **関連文書**:
  - [`エラーログ拡張仕様書_差分実装版.md`](./エラーログ拡張仕様書_差分実装版.md)

## 2. 目的

本書は、メイン処理が完了した後に実行される補助処理が失敗した場合の、**初期運用方針**を定める。

本書の目的は、初期フェーズで過剰な repair 基盤や専用 UI を作らず、既存の `logOpsError`、batch、migrate、retry、手動再実行導線を前提に、現実的な扱いを整理することである。

## 3. 用語

### 3.1 メイン処理

業務上の主目的となる処理。

例:

- 会計を完了し、`bill.status = settled` にする
- 勤怠 doc を作成・更新する
- トーナメント doc を作成する
- payroll run を作成・進行する
- bill event を作成する

### 3.2 補助処理

メイン処理の完了後に行われる派生・補完・集計・通知・task 生成などの処理。

例:

- analytics 反映
- 親 doc への snapshot 反映
- `paymentsSummary` / `postEvents` 更新
- `activeStay` / `visitLog` 更新
- Cloud Tasks enqueue
- 通知作成・通知送信
- cleanup
- marker / idempotency 関連処理
- payroll で利用される補助フィールドの付与

## 4. 基本方針

### 4.1 メイン処理未完了と補助処理失敗を分ける

メイン処理が完了していない失敗と、メイン処理完了後の補助処理失敗は分けて扱う。

```text
メイン処理が未完了の失敗:
  元の未完了状態に残す
  ユーザーが再試行できる状態を維持する

メイン処理は完了し、補助処理だけ失敗:
  メイン状態は原則戻さない
  logOpsError で検知可能にする
  既存 batch / migrate / retry / 手動再実行導線で補えるものはそれを使う
```

### 4.2 初期フェーズでは共通 repair ledger / 専用 UI は作らない

補助処理失敗は、初期フェーズでは発生頻度が低いものとして扱う。

そのため、初期フェーズでは以下を作らない。

- 共通 `opsRepairJobs`
- 補助未完了一覧 UI
- 全補助処理共通の repair scheduler
- 全補助処理共通の repair Callable
- 通知再送込みの自動 repair

ただし、補助処理失敗を見逃してよいという意味ではない。  
補助処理失敗は `logOpsError` により検知可能にし、後から対象を特定できる `context` を残す。

### 4.3 既存導線を優先する

既に以下のような補完・再処理導線がある場合は、初期フェーズではそれを優先する。

- Cloud Tasks retry
- Scheduler / batch
- migrate / backfill Callable
- 手動再実行 Callable
- 既存の status / marker / idempotency による再処理
- 閉店処理内の補完ステップ

調査上、analytics には `migrateSettledBillsForBusinessDay` や閉店フロー内の補完導線があり、payroll staff 単位の失敗には `retryFailedStaffTasks` 等の既存導線が確認されている。

一方で、以下は gap として残る。

- `billsEventsOnCreate` の parent bill 再反映
- `billsOnSettle` の parent snapshot 欠落補完
- `completeAccountingV2` 後の activeStay / visitLog 専用 replay
- `attendanceOnWrite` の補助フィールド欠落補正

## 5. 初期フェーズでの扱い

### 5.1 既存導線で補う対象

初期フェーズでは、以下は既存導線を優先する。

| 対象 | 初期方針 |
|------|----------|
| analytics 取りこぼし | 日次 / 閉店後 batch、migrate で補完する |
| payroll staff 単位の失敗 | 既存の payrollRun / staffResult / `retryFailedStaffTasks` を使う |
| tournament task 生成 | 既存の `enqueueTournamentTasks` / scheduler / planHash を使う |

### 5.2 gap として残す対象

以下は、初期フェーズでは専用 repair を作らず、gap として残す。

| 対象 | 現状 | 初期方針 |
|------|------|----------|
| `billsEventsOnCreate` | 正常完了時は parent bill へ反映するが、失敗・スキップ時に event のみ残る可能性がある | `logOpsError` で検知し、後続の個別 repair 候補とする |
| `billsOnSettle` parent snapshot | analytics は補えるが、親 snapshot は専用 backfill 未確定 | `logOpsError` で検知し、実害が出た場合に個別 backfill を検討 |
| `completeAccountingV2` post-settle | activeStay / visitLog の専用 replay なし | `logOpsError` context で手動確認可能にする |
| `attendanceOnWrite` | payroll で利用される補助フィールドの一括補正 batch なし | payroll に重大影響を与えうる重要 gap として扱い、後続で一括補正 batch または payroll 実行前 validation を検討する |

### 5.3 attendanceOnWrite の補助フィールド欠落

`attendanceOnWrite` では、勤怠 doc 作成・更新後に以下の補助フィールドを付与する。

- `paymentPeriodKey`
- `payrollStatus`
- `weekStartDate`
- `weekday`

これらの補助フィールドは、payroll 側で `date` から再導出されるのではなく、**attendance doc 上の値として参照**される。

そのため、欠落・誤りがある場合、以下の影響が発生しうる。

**`paymentPeriodKey` 欠落・誤り:**

- 給与候補クエリから漏れる
- 通常 / キャリー分類を誤る
- 計算対象外になる可能性がある

**`payrollStatus` 欠落・誤り:**

- 給与候補クエリから漏れる
- 計上対象外になる可能性がある

**`weekStartDate` 欠落・誤り:**

- 同一週の attendance 参照が崩れる
- 週単位の残業計算・配分が崩れる可能性がある

**`weekday` 欠落・誤り:**

- 法定休日判定がずれる
- 割増計算に影響する可能性がある

現状、一括補正 batch は未実装であり、payroll 実行時にこれらを再計算して補正する処理もない。

初期フェーズでは共通 repair ledger や専用 UI は作らないが、`attendanceOnWrite` の補助フィールド欠落は **payroll に重大影響を与えうる重要 gap** として扱う。

後続候補として、以下を検討対象に残す。

- attendance 補助フィールドの一括補正 batch
- payroll 実行前 validation
- 欠落・不整合検出用の管理クエリ
- `logOpsError` context の補強

## 6. logOpsError に求める情報

補助処理失敗時は、可能な範囲で以下を `logOpsError` の payload / context に残す。

**必須寄り:**

- `functionEntry`
- `operation`
- `errorKey`
- 対象 ID（例: `billId`, `eventId`, `attendanceId`, `tournamentId`, `payrollRunId`, `staffId`）
- `businessDate` / `targetDate` / `targetMonth`
- 補助処理名
- メイン処理は完了済みであることが分かる `message`

**可能なら残す:**

- `userId`
- `adminId`
- `activeStayId`
- `visitLogId`
- `idempotencyKey`
- `appliedAt`
- `planHash`
- `taskKind`
- `retryCount`
- `paymentPeriodKey`
- `weekStartDate`
- `weekday`
- `payrollStatus`

## 7. 通知失敗の扱い

通知がメイン処理ではなく、メイン処理完了後の付随処理である場合、通知作成・通知送信の失敗は**補助処理失敗**として扱う。

ただし、通知失敗は失敗位置によって再処理時のリスクが異なる。

```text
通知 doc 作成前に失敗:
  再実行しても二重通知になりにくい

決定的な通知 docId / idempotency key がある:
  再実行しても二重通知になりにくい

通知 doc 作成後に失敗:
  再実行時に二重通知の可能性がある

外部送信は成功したが記録に失敗:
  システム上は失敗でも、ユーザーには通知済みの可能性がある
```

そのため、通知系の補助処理は「失敗したから常に安全に再送できる」とは扱わない。

**初期方針:**

- **通知データの補正**: 必要に応じて実施する
- **通知再送**: 原則、自動では行わない
- **通知再送を行う条件**: 送信済み状態、通知 docId、idempotency key 等により二重通知にならないと判断できる場合、または管理者が明示的に再送を判断した場合に限る

## 8. 後続で個別 repair を検討する条件

以下に該当する場合のみ、後続フェーズで個別 repair を検討する。

- 同じ補助処理失敗が複数回発生した
- 店舗運営に実害が出た
- 金額・会計・勤怠・給与・トーナメント進行に影響した
- 手動復旧が困難だった
- `logOpsError` の context だけでは復旧判断できなかった
- 既存 batch / migrate / callable / retry では補えなかった

## 9. 後続検討候補

現時点での後続検討候補は以下とする。

| 対象 | 後続候補 |
|------|----------|
| `billsEventsOnCreate` | `appliedAt` なし event の検出と安全な再適用 |
| `billsOnSettle` parent snapshot | snapshot backfill |
| `completeAccountingV2` post-settle | activeStay / visitLog 個別 repair |
| `attendanceOnWrite` | attendance 補助フィールドの一括補正 batch / payroll 実行前 validation |
| tournament task 個別再生成 | tournamentId 指定 repair |
| payroll finalize | 状態機械と retry 運用の明文化 |

## 11. まとめ

初期フェーズでは、メイン完了後の補助処理失敗に対して、専用の補助未完了画面や共通 repair ledger は作らない。

既存の batch / migrate / retry / callable で補えるものはそれを使い、補えないものは `logOpsError` の context により検知・調査・手動復旧できる状態にする。

ただし、`attendanceOnWrite` の補助フィールド欠落は payroll に重大影響を与えうるため、**重要 gap** として扱う。

発生頻度や実害が確認された gap に限り、後続フェーズで個別 repair を検討する。
