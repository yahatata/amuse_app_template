## 2. 背景と目的

今回のエラーログ実装では、運用上追跡したい失敗を **`logOpsError` に統一して出力**するようにした。  
また、**`tenant-errors`** には `logOpsError` による運用エラーログに加え、**プラットフォームまたはランタイムが自動で出力する失敗ログ**も集約される（各店舗プロジェクトから severity >= ERROR のシンク）。

当初の整理では、監視・確認の必要性が低いログを**ノイズ**として事前に定め、初期運用の負荷を下げることを検討した。その検討の過程で、**再試行・一時障害に見える失敗**をログだけで切り分けられないこと、および**失敗と後続の成功・正常状態を紐づける必要**があることが明確になった。

本書の目的は次のとおりである。

1. **再試行系の失敗は監視対象**であり、**1件の失敗ログだけでは再試行の成否が判断できない**ため、**同一処理の後続（再試行・再実行・結果確認）を必ず追う**ことを明文化する。
2. **再試行候補シグナル**は、ログ上から見て **再試行により成功する可能性がある**ことを示唆する**参考情報**にすぎない。**追跡を打ち切る・継続するかの判断とは無関係**であり、**シグナル別に追跡を打ち切る運用は想定しない**ことを明文化する。
3. 後続を追うために、**相関キー**や観測手段を揃えるにあたり何が不足かを示す。

---

## 3. ノイズ候補として想定していたもの

| 候補 | 内容のイメージ |
|------|----------------|
| 入力ミス | 正しく弾かれて終わるクライアント起因 |
| 安全な冪等 no-op / 重複リクエストの正常拒否 | 同一リクエストの安全な replay や業務ルール上の却下 |
| 一時的な外部依存失敗 | 通信失敗、timeout、rate limit、外部 API / GCP SDK の一時エラー、quota 等（「インターネットエラー」だけに言い換えない） |
| 再試行で最終的に成功する失敗 | 上記を含み、自動リトライ・再実行・再操作で回復しうるもの |

---

## 4. 入力ミス・冪等による正常拒否

**通常の入力ミス**や、**安全な冪等 no-op / 重複リクエストの正常拒否**は、想定内の通常制御として扱うべきものであり、**原則として `logOpsError` には載せない**実装が多い（`invalid-argument` のみ、`success: false` のみ、など）。

したがって、これらは **`logOpsError` 由来の監視ノイズの主戦場にはなりにくい**。

**補足:** 業務上、弾きながらも観測したい失敗は **`FunctionCustomError` として `logOpsError` に残す**設計がある（例: 冪等キー不一致、業務キー付きの重複登録など）。これはノイズ回避とは別軸の**意図的な記録**である。

## 5. 再試行候補シグナルと監視判断

### 5.1 方針：再試行系は監視対象であり、後続を必ず追う

**再試行に見える失敗ログを、監視対象外にする話ではない。**  
再試行系の失敗は **監視対象**として扱う。

1件の失敗ログだけでは、**再試行（自動・手動を含む）により成功するかどうか**も、**実際に成功したかどうか**も判断できない。  
したがって運用上は、**同一処理について、再試行の結果が成功であるか失敗であるかにかかわらず、必ず後続のアクション・結果を追う**（初期運用も同様）。  
「このログだけ見てノイズとして捨てる」「追跡を省略する」ことはしない。

### 5.2 代表的な再試行候補シグナル（参考）

以下は、失敗ログに現れた情報から **「再試行により成功しうる」可能性を示唆する**ための参考である。**示唆にすぎず、成功が確定するわけでもない**。

**追跡を打ち切る・継続するかの判断とは無関係**である。§5.1 のとおり **監視対象**であり後続を追うことに変わりはなく、**シグナルの有無や種類によって追跡を打ち切る運用は想定しない**。

- **`httpStatus`**: `429`, `500`, `502`, `503`, `504`
- **`sdkCode`（概念）**: `unavailable`, `deadline-exceeded`, `resource-exhausted`, `aborted` 等
- **`errorMessage` / `detailReason`**: `timeout`, `deadline`, `temporary`, `transient`, `rate limit` 等の表現
- **`context`**: `retryAttempt`, `attempt`, `retryCount`, `taskRetry` 等、再試行文脈を示す情報

### 5.3 追跡の末に「追加対応不要」と判断できる場合

**監視・追跡を省略する**のではなく、**後続の確認まで行ったうえで**、**再試行または再実行**により **同一処理・同一対象**が正常完了し、かつ **主処理の成否・データ整合性・後続処理・運用判断に影響が残っていない**と確認できた場合に限り、その失敗に対する**追加のインシデント対応は不要**と判断できる。

ここでの判断は、**自動ルールでアラートを消す**ことではなく、**追跡完了後の運用判断**を指す。

「再試行」の例は次を含む。

- Cloud Tasks / Scheduler 等の**自動リトライ**後に成功した
- 管理側が**同じ処理を再実行**して成功した
- 店舗スタッフが**再操作**して成功した
- **後続の成功ログ**または**対象データの最終状態**が正常であると確認できた

### 5.4 追跡を継続し、追加調査が必要になりうる場合

後続の確認の結果、次に当てはまる場合は **監視・追跡の流れの中で**エスカレーションや追加調査の対象とする。

- 再試行後も**失敗している**
- 再試行・再実行の**結果が確認できない**（同一処理に紐づく成功・失敗が特定できない）

## 6. 失敗と成功・正常状態の相関

再試行系は **監視対象**であり、**1件のログだけで追跡を完了できない**。**別ユーザー・別伝票・別リクエストの成功と混同できない**ため、**同一処理の失敗と後続の成否**を紐づける必要がある。

したがって、運用で後続を確実に追えるようにするには、次を**関連付けられる**必要がある。

- 失敗ログと**後続の成功ログ**
- **再実行結果**
- **対象データの正常状態**（コンソール・クエリ・ダッシュボード等での確認を含む）

**`tenant-errors`** は ERROR 中心であり、成功側は多く **店舗プロジェクトの INFO 等**に残る。突き合わせは**プロジェクトやクエリをまたぐ**前提になりうる。

「仕組み」は、**相関キーの統一・成功ログのフィールド整備・Runbook** から段階的に進めてよく、必ずしも一度に大規模なシステム実装だけを指すものではない。

**実装メモ（`context`）:** 相関キーを足すときは、**既存の `logOpsError` の `context`（診断用の `code` / `reason` 等を含む）を残したまま、推奨の相関キーを追加する**方針とする。詳細は `エラーログ_context推奨_269件.md` の「実装方針（context の扱い）」を参照する。

## 7. サマリ（再試行追跡向けの実装）

**目的（本書 §2・§6 と対応）:** 再試行・再実行・手動の再操作のあとに、**同一処理の失敗ログと後続の成功・結果をログ上で突き合わせやすくする**ため、運用で追う経路について **`logOpsError` / `logOpsSuccess` の `context` に相関 key（店舗・請求・タスク・トーナメント等、処理に応じた推奨キー）を載せる**実装を進めた。

### 7.1 実施したこと

| 区分 | 内容 |
|------|------|
| 失敗側 | `logOpsError` の `context` に、診断用フィールドを残したまま推奨の相関 key を追加する方針に沿った整備（調査スコープ・推奨キー一覧は `エラーログ_context推奨_269件.md`）。 |
| 成功側 | 同一スコープで **`logOpsError` はあるが `logOpsSuccess` が無かった Callable 等**に `logOpsSuccess` を追加し、**失敗と同種の相関 key を `context` に揃えた**（成功は多く INFO 相当で残る前提との突き合わせをしやすくする）。 |
| 冗長ログ | **同一の成功内容を言い直すだけ**の `logger.info` / `console.log` を整理し、成功の観測は **`logOpsSuccess` に寄せた**（関係のないログの全面削除は対象外）。 |

### 7.2 機械検証・到達点

- **集計**: `エラーログ_成功ログ調査_269件_機械集計.md` により、当該スコープで **「`logOpsError` あり・`logOpsSuccess` なし」が 0** であることを確認した。
- **結論（スコープ内）:** 再試行・再実行後のログ追跡のために **失敗・成功の双方に相関 key を持たせる**という今回の目的は、**対象範囲において十分達成した**と判断できる。また **成功ログの二重化は、機械集計・監査の観点では解消した**と言える（「すべての `logger.info` を廃止した」という意味ではない）。

### 7.3 意図的に別扱いとするもの

- **監査で残りうる項目**: 同一ファイル内で **`context` 付きの成功がある一方、一部の `logOpsError` 行だけ `context` が未整備**など、機械監査が指摘しうる差分は **任意のフォロー**とする（追跡の主経路は整っている前提）。
- **プラットフォーム／ランタイムの自動 ERROR**: 本書 §2 のとおり **`tenant-errors` にも入りうるが、`logOps*` の `context` と同一実装にはならない**。**インフラ付与のリクエスト ID・トレース ID**や、**エントリの外側 try/catch／グローバルハンドラでの別レコード出力**など、レイヤの違いとして切り分ける。**ランタイムが出力する行そのものへアプリの `context` を差し込むことは難しい**一方、**インフラ ID やハンドラでの別レコード**により、相関の意味は近づけられる。

### 7.4 関連スクリプト・実装（参照）

- 成功・失敗の対応関係の機械監査: `functions/scripts/auditLogOpsSuccessCorrelation.cjs`（運用で使用する場合）
- ログ実装: `functions/src/shared/logging/logOpsError.ts`、および `logOpsSuccess` を呼び出している各 Callable／タスク処理
