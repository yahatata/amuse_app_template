## 1. 背景

国内のアミューズメントカジノバー向け業務管理アプリについて、各店舗を 1 Firebase プロジェクト = 1店舗 の単位で運用する前提で、保守運用時のエラーログを店舗横断で扱えるようにするための基盤整備を進めている。ログ集約先として amuse-central-monitoring プロジェクトの tenant-errors ログバケット を用い、各店舗プロジェクトから sink により severity >= ERROR のログを集約する構成はすでに整備済みである。

また、logOpsError を主軸としたログ形式統一についても実装を進め、現時点で共通形式への寄せは完了している。

一方で、これまでの実装では 重要度判定要件を先に定義しないまま ログ形式統一を進めてきた。そのため、現行のログ項目が、tenant-errors に集約された業務エラーログに対して重要度判定を行うために本当に十分かどうかは、まだ未確定である。実装サマリ上でも、業務重要度判定要件の確定前に、errorSource 分類精度、service 解決、errorKey 出力、external 4項目の取得率、operation 分解状況、context ネスト変更影響などを確認すべき点として整理されている。

このため、次の段階では、どのような重要度判定を行うのかを定義したうえで、その判定に必要な情報が現行実装で十分に揃っているかを評価すること が必要となる。

## 2. 目的

本要件定義の目的は、tenant-errors に集約された業務エラーログに対して重要度判定を行うために、必要な情報の十分性を定義すること にある。
あわせて、その定義を既存実装に照らし、不足している情報は追加対象、過剰かつ不要と判断できる情報は削除対象として評価できる状態 を作ることを目的とする。

## 3. 前提

- 各店舗は 1 Firebase プロジェクト = 1店舗 の単位で運用する。
- エラーログの集約先は、amuse-central-monitoring プロジェクトの tenant-errors ログバケット とする。
- 各店舗プロジェクトからは、sink により severity >= ERROR のログを tenant-errors ログバケットに集約する。
- リリースまでに必要な状態は、tenant-errors に統一形式のログが漏れなく集約され、重要度判定が可能であること とする。
- 管理用アプリ本体は現時点では実装対象に含めない。
- 重要度判定の対象は、tenant-errors に集約された業務エラーログ とする。
- 重要度は 1 / 3 / 5 の3段階 を今回の基本とし、将来的な拡張を考慮して 2 / 4 を追加可能な設計とする。
- logOpsError を主軸としたログ形式統一は実装済みである。
- ただし、重要度判定要件を先に定義していないため、現行ログ項目が重要度判定に十分かどうかは未確定 である。
- したがって、本要件定義では 重要度判定に必要な情報の十分性を定義し、既存実装との差分を評価する。

## 4. スコープ

本要件定義のスコープは、**tenant-errors に集約された業務エラーログに対し、重要度判定を行うために必要な情報の十分性を定義し、既存実装との差分を評価すること** とする。

具体的には、以下を含む。

- 重要度 1 / 3 / 5 の判定基準の定義
- 重要度判定に用いる判定用語の定義
- 重要度判定に必要なログ情報の整理
- 既存実装のログ項目と、上記必要情報との差分評価
- 不足している情報の追加要否の整理
- 過剰かつ不要と判断できる情報の削除要否の整理

また、既存実装との差分評価における主対象は、実装サマリ（`docs/エラーログ運用/logOps/実装サマリ/実装サマリ_エラーログ拡張_20260406.md`）における **業務本体 280 件**（`logOpsError` 呼び出しの機械集計 **304 件**から `functions/src/debug` **17 件**および `functions/src/unused_function_lib` **7 件**を除いた件数: 304 − 17 − 7 = 280）を出発点とする。  
次に掲げるものは、本番運用向け重要度判定の**主対象には含めない**。

- `functions/src/debug` に属するログ
- `functions/src/unused_function_lib` に属するログ
- 次の **2 呼び出し分**（`functionEntry` ごとにテスト・開発・検証用であり、本番運用の主業務フローではないため、重要度判定の十分性要件の対象外とする）。
  - `generateDummyData`（`functions/src/domains/analytics/callables/generateDummyData.ts`）— テスト用ダミーデータ生成
  - `debugSideGame`（`functions/src/domains/sideGame/callables/debugSideGame.ts`）— サイドゲーム状態の開発・検証用

上記を踏まえ、**本番運用向け重要度判定の十分性を評価する主対象は 269 件**とする。  
これは、旧 **278 件**（280 − 2）から、`unused_function_lib` へ移管した `logOpsError` **9 呼び出し分**を除いた件数であり、`functionEntry_業務役割一覧.md` における Step2-1 実質スコープ（101 + 168）と整合する。

## 5. 非スコープ

本要件定義では、以下を対象に含めない。

- 管理用アプリ本体の画面仕様、UI 設計、検索仕様、通知仕様、アラート仕様
- tenant-errors 以外のログ集約基盤の再設計
- `severity >= ERROR` 以外のログを含めた新たな集約方針の設計
- debug 用、検証用、未使用機能用、本番未使用コード用ログの重要度判定設計（**§4** において主対象外とした `generateDummyData` / `debugSideGame` を含む）
- 人為的な誤入力・誤判断であっても、システム上は正常処理として完了し、エラーとして観測されない事象の判定
- 既存実装の全面的なログ再設計または業務ロジック再設計
- 緊急性、通知優先度、オンコール優先度等の運用判断軸の定義  
  ただし、将来的に別軸として定義・活用することは妨げない

## 6. 要件定義

- tenant-errors に集約された業務エラーログを対象に、重要度判定を行えること。
- 重要度は 1 / 3 / 5 の3段階 を基本として扱えること。
- 将来的に 2 / 4 を追加可能な拡張性を阻害しないこと。
- 重要度判定は、定義済みの判定基準に基づき、担当者によらず一定の再現性をもって行えること。
- 重要度判定に必要なログ情報の十分性を定義できること。
- 既存実装のログ項目を上記十分性定義と照合し、不足情報と不要情報を評価できること。

### 6.1 重要度判定の基本方針

本要件定義における重要度は、対象ログに対して人的対応（確認、調査、修正、補正、運用判断等）を行わなかった場合の業務影響の大きさを基準として判定する。

業務影響の判定にあたっては、影響対象が主要業務または高頻度業務か、当該業務フローの実行不能・継続不能・通常手順のままでは続行できない程度の処理阻害につながるか、または金額不整合を含む状態不整合、処理未完了等のシステム上の異常状態を残すかを確認する。  
また、当該エラーが適切な再操作、再実行、または補正により異常状態を残さず解消可能か、または継続・再発・残存しうるかも補足的に確認する。

技術的なエラー種別、HTTP ステータス、SDK エラーコード等は、上記の業務影響を判断するための補助情報として扱う。

### 6.1.1 重要度判定で判断する事項

重要度判定に必要なログ情報を定義する前提として、まず、対象ログに対してどのような判断が必要かを明確にする。

重要度判定にあたっては、少なくとも以下を判断できる必要がある。

- 影響対象が主要業務または高頻度業務か
- 対応を行わなかった場合に、当該業務フローの実行不能、継続不能、または通常手順のままでは続行できない程度の処理阻害につながるか
- 対応を行わなかった場合に、金額不整合を含む状態不整合、処理未完了等のシステム上の異常状態を残すか

なお、上記判断にあたっては、当該エラーが適切な再操作、再実行、または補正により異常状態を残さず解消可能か、または継続・再発・残存しうるかも補足的に確認する。

### 6.2 重要度の定義

重要度は 1 / 3 / 5 の3段階 を基本とし、5 を最も重大、1 を最も軽い区分 として扱う。

なお、将来的な拡張のため、2 / 4 を追加可能な設計 を前提とする。

### 6.3 重要度 5 の定義

以下のいずれかに該当するものを、重要度 5 とする。

- 当該エラーに対する対応を行わなかった場合に、主要業務または高頻度業務の実行不能、継続不能、または著しい処理阻害につながるもの
- 当該エラーに対する対応を行わなかった場合に、業務が継続できたとしても、状態不整合、金額不整合、処理未完了等のシステム上の異常状態を残し、後続業務へ重大な影響を及ぼすもの

### 6.4 重要度 3 の定義

以下のいずれかに該当し、重要度 5 には該当しないものを、重要度 3 とする。

- 当該エラーに対する対応を行わなかった場合に、業務へ支障を与えるが、主要業務または高頻度業務の実行不能、継続不能、または著しい処理阻害には至らないもの
- 当該エラーに対する対応を行わなかった場合に、不整合な状態または不完全な状態を残す可能性はあるが、後続業務への重大な影響には直結しないもの

### 6.5 重要度 1 の定義

当該エラーに対する対応を行わなかった場合の業務影響が限定的であり、重要度 5 および重要度 3 のいずれにも該当しないものを、重要度 1 とする。

### 6.6 判定用語の定義

#### 主要業務

主要業務とは、店舗運営を成立させるために必要な中核業務を指す。  
停止または誤処理が発生した場合に、営業継続、売上計上、会計確定、来店管理、開閉店運用等へ直接支障を生じる業務を含む。  
少なくとも、**来店処理、会計開始、会計完了、開店、閉店、トーナメント進行の中核処理** を含む。

#### 高頻度業務

高頻度業務とは、1営業日の中で繰り返し実行される、または複数スタッフにより日常的に操作される業務を指す。  
単一回の失敗であっても、反復発生により運用負荷または店舗運営上の支障が蓄積しやすい業務を含む。  
少なくとも、**来店処理、注文処理、会計関連操作、トーナメント操作、勤怠打刻、日常的な状態更新** を含む。

#### 著しい処理阻害

著しい処理阻害とは、技術的には完全停止していなくても、通常手順のままでは業務を続行できず、**再実行、回避操作、補正操作、担当者確認、別手段への切替** のいずれかが必要となる状態を指す。  
少なくとも、**同一処理の反復失敗、必須後続処理の未実行、処理結果確認なしでは次操作に進めない状態** を含む。

#### 重大な影響

重大な影響とは、対象ログに対する確認、調査、再実行、補正等の対応を行わなかった場合に、**主要業務または高頻度業務の停止、著しい遅延、不整合状態の残存、後続処理失敗、手動介入の発生** のいずれかを招く影響を指す。  
少なくとも、**会計確定不能、開閉店不能、後続ジョブ未実行、金額不整合残存、状態遷移不整合残存** を含む。

#### 業務影響が限定的

業務影響が限定的とは、対象ログに対する確認、調査、再実行、補正等の対応を行わなかった場合でも、**主要業務または高頻度業務の継続が可能** であり、影響が **単一処理、単一利用者、単一時点** にとどまり、後続処理や全体運用へ波及しない状態を指す。  
少なくとも、**一部補助処理の失敗、代替操作で継続可能な処理失敗、後続業務へ伝播しない局所的失敗** を含む。

#### 業務エラーログ

業務エラーログとは、保守運用上の重要度判定対象とするログであり、**店舗運営に関係する実業務処理の失敗または異常を示すログ** を指す。  
少なくとも、**会計、来店、注文、勤怠、開閉店、トーナメント、店舗運営に関係する Cloud Functions / タスク / トリガの異常ログ** を含む。  
一方で、**debug 用、検証用、未使用機能用、本番未使用コード用のログ** は含まない。

#### 後続業務

後続業務とは、当該処理の完了または結果を前提として実行される、**次の処理、関連処理、集計処理、状態更新処理、締め処理、通知処理、タスク処理** を指す。  
同一リクエスト内の次処理だけでなく、**後続タスク、後続トリガ、営業日内の関連処理、締め時点で参照される処理** を含む。

#### 不整合な状態

不整合な状態とは、システム内で保持される **状態、金額、件数、ステータス、処理済み/未処理の対応関係** が一致していない状態を指す。  
少なくとも、**親子データの不一致、請求状態とイベント状態の不一致、金額合計不一致、処理記録はあるが集計に反映されていない状態** を含む。

#### 不完全な状態

不完全な状態とは、本来完了しているべき処理のうち、**一部だけ成功し、一部が未実行・未反映・未更新のまま残っている状態** を指す。  
少なくとも、**主処理は成功したが後続更新が未実行、途中まで反映されたが完了状態に達していない、補償処理が終わっていない状態** を含む。

#### 処理未完了

処理未完了とは、処理の完了条件を満たす前に終了し、**本来必要な書き込み、状態更新、後続起動、結果確定** のいずれかが行われていない状態を指す。  
少なくとも、**トランザクション未完了、後続 Cloud Task 未投入、必要イベント未作成、完了ステータス未反映** を含む。

#### 手動介入

手動介入とは、異常解消または運用継続のために、**人が内容確認、再操作、再実行、補正更新、再集計、状態修正、利用者説明** のいずれかを行うことを指す。  
単なる監視ではなく、**異常を解消するための人手作業** を意味する。

#### 正常な運用継続

正常な運用継続とは、追加の補正、回避操作、手動確認なしで、**定められた通常手順のまま次の業務へ進める状態** を指す。  
少なくとも、**主要処理が完了し、必要な後続処理が起動し、状態・金額・件数・ステータスに矛盾がない状態** を含む。

#### 影響範囲が限定的

影響範囲が限定的とは、異常の影響が **単一の処理、単一のレコード、単一の利用者、または局所的な一画面・一操作** にとどまり、他業務・他利用者・後続処理へ広がらない状態を指す。  
少なくとも、**単発の補助処理失敗、局所データの一時的不備、他機能へ波及しない操作失敗** を含む。

## 7. 重要度判定の具体的な判断方法

### 7.1 観点1の判断方法

観点1では、**影響対象が主要業務または高頻度業務か** を判断する。

観点1の判断は、抽象的な都度判断ではなく、別紙 **`functionEntry 業務役割一覧`** を正として行う。  
当該一覧には、本番運用向け重要度判定の十分性評価の主対象 269 件について、各判定単位ごとの **業務上の役割**、**主要業務**、**高頻度業務** の整理結果が記載されている。  
したがって、観点1については、対象ログがどの判定単位に対応するかを特定し、当該一覧を参照することで判断するものとする。

なお、観点1においては、`message`、`errorMessage`、`errorName`、`errorSource`、`service`、`sdkCode`、`httpStatus`、`detailReason` 等は、一覧参照そのものに必須の情報とはしない。  
これらは必要に応じて補助的に参照しうるが、観点1の判断成立要件そのものではない。

### 7.1.1 観点1の判断に必要なログ情報

観点1の判断を成立させるために、エラーログには **`functionEntry 業務役割一覧` の判定単位を識別できる情報** が含まれている必要がある。

必要なログ情報は、以下のとおりとする。

- **operation を持たない判定単位** の場合: `functionEntry`
- **operation を持つ判定単位** の場合: `functionEntry` および `operation`

また、同一 `functionEntry` に複数の `logOpsError` 呼び出しが存在する場合は、`operation` によって判定単位を区別できることを要する。

このため、観点1に関する十分性判定では、少なくとも以下を確認対象とする。

- 対象ログに `functionEntry` が出力されていること
- `operation` により区別すべき判定単位については、対象ログに `operation` が出力されていること
- 出力されている `functionEntry` または `functionEntry + operation` が、`functionEntry 業務役割一覧` の判定単位と対応付け可能であること
