# warningログ方針

## 1. 目的

この文書は、Cloud Functions 側の本番業務コードにおける warning ログの扱いを定める。

特に、`console.warn` を使用せず、警告ログを `logger.warn` または `logOpsError` に整理するための判断基準を明確にする。

---

## 2. 基本方針

`functions/src` 配下の本番業務コードでは、原則として `console.warn` を使用しない。

warning としてログを残す必要がある場合は、内容に応じて以下のいずれかを使用する。

| 使用するログ | 用途 |
|---|---|
| `logger.warn` | 軽微・想定内・補助的な警告 |
| `logOpsError` | 業務影響があり、中央監視・重要度判定・復旧対象にしたい異常 |

また、直後に例外を throw し、上位で `logOpsError` が出力されるなど、同じ事象を重複して記録している warning は削除する。

---

## 3. `console.warn` を使用しない理由

`console.warn` は Cloud Logging に出力される可能性はあるが、本プロジェクトの保守運用では使用しない。

理由は以下の通り。

- 構造化された context を持たせにくい
- 監視・検索・重要度判定に使いづらい
- `logger.warn` / `logOpsError` と混在すると、ログ運用ルールが曖昧になる
- 復旧対象や影響範囲の特定に必要な情報を安定して残しにくい

そのため、本番業務コードでは `console.warn` を残さず、`logger.warn` または `logOpsError` に統一する。

---

## 4. `logger.warn` を使用する基準

以下に該当する場合は、`logger.warn` を使用する。

- 想定内の入力不備
- 古い task、期限切れ、削除済みデータなどによる no-op
- 業務本体は成功しており、補助処理だけが失敗した場合
- すぐに人間対応するほどではない場合
- 中央監視に載せるとノイズが大きい場合
- 復旧対象ではないが、調査用に状況を残したい場合
- 仕様上許容されるスキップやフォールバックの場合

`logger.warn` は、中央監視で即時対応する異常ではないが、運用上の調査や状態確認に役立つ情報を残すために使用する。

---

## 5. `logOpsError` を使用する基準

以下に該当する場合は、`logOpsError` を使用する。

- 金額・会計・集計に影響する
- 給与・勤怠分類に影響する
- 主要業務の状態整合性が崩れる
- SSoT と派生データがズレる可能性がある
- 成功扱いだが、重要な補助処理が失敗している
- 後続で人間確認または復旧が必要になる
- 中央監視に上げないと見逃す可能性がある
- 重要度判定の対象にしたい

`logOpsError` は、単なる警告ではなく、保守運用上の検知・判断・復旧対象にしたい異常を記録するために使用する。

---

## 6. warning を削除する基準

以下に該当する warning は、`logger.warn` や `logOpsError` に置き換えず、削除する。

- 直後に例外を throw している
- 上位 catch で同じ事象が `logOpsError` として記録される
- 同じ異常を二重に記録している
- 本番運用上の調査に使わない診断ログである
- ログとして残しても復旧・判断・調査に役立たない

同一事象を複数のログに分散して残すと、監視上のノイズや誤検知につながるため、重複ログは避ける。

---

## 7. `logger.warn` に含める情報

`logger.warn` を使用する場合でも、可能な範囲で調査に必要な context を含める。

含めてよい情報の例:

- 対象ドキュメントID
- 業務日
- 対象月
- 関数内の処理名
- スキップ理由
- fallback 理由
- 不正件数
- 正規化件数

ただし、以下は原則として含めない。

- 秘密情報
- 生の認証情報
- QRコードやトークンの生値
- 大きな request body
- Firestore document 全体
- 過度な個人情報
- 長大な金額オブジェクト全体

必要な場合は、件数・差分サマリ・識別子など、調査に必要な最小限の情報に留める。

---

## 8. `logOpsError` に含める情報

`logOpsError` を使用する場合は、保守運用で重要度判定や復旧判断ができるよう、必要な構造化情報を含める。

含めるべき情報:

- どの関数で発生したか
- どの処理段階で発生したか
- 何が失敗したか
- どの業務データに影響し得るか
- 復旧時に対象を特定できる識別子
- 例外情報

ただし、`logger.warn` と同様に、秘密情報・過度な個人情報・巨大なデータ全体は含めない。

---

## 9. 判断に迷う場合の原則

`logger.warn` と `logOpsError` の判断に迷う場合は、以下の順で判断する。

1. 業務本体が成功しているか
2. データ整合性が崩れるか
3. 金額・会計・集計・給与・勤怠に影響するか
4. 人間による確認や復旧が必要か
5. 中央監視で検知しないと見逃すか
6. 発生頻度が高く、`logOpsError` にするとノイズになりすぎないか

原則として、業務影響・整合性影響・復旧必要性があるものは `logOpsError` 寄りに判断する。

一方で、想定内の入力不備、期限切れ、削除済みデータ、補助処理の軽微な失敗は `logger.warn` 寄りに判断する。

---

## 10. 結論

本プロジェクトの本番業務コードでは、`console.warn` を使用しない。

warning を残す場合は、以下の基準で整理する。

```text
軽微・想定内・補助的な警告:
  logger.warn

業務影響があり、監視・重要度判定・復旧対象にしたい異常:
  logOpsError

上位で同じ事象が記録される重複 warning:
  削除
```
