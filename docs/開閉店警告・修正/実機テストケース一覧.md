# 開閉店警告・修正 実機テストケース一覧（ケース軸）

## 0. 前提（共通）
- 対象プロジェクト: `amuse-app-template`
- 代表端末:
  - 管理端末A: `role=admin`
  - 管理端末B: `role=terminal`, `options.store_management=true`
  - 非管理端末C: 上記以外
- 監視ドキュメント:
  - `storeMeta/currentBusinessDay`
  - `storeMeta/currentBusinessDay/assessmentLogs/*`
- 主要確認フィールド:
  - `status`, `currentBusinessDateKey`, `lastClosedBusinessDateKey`
  - `closeAssessment`, `openAssessment`
  - `manualOverrides.close`, `manualOverrides.open`
  - （移行互換）`manualOverride` が不要に残っていないこと

---

## A. 権限・画面ブロック系

### CASE-A01 非管理端末で強警告が出ている
- どのようなケースで: `getTopStrongWarning(meta) != null` かつ端末C（非管理）
- 試行する操作: Terminalホームを表示
- 期待される画面:
  - 常駐バナー表示
  - 文言は詳細ではなく「営業状態の警告があります。管理者に確認してください。」
  - 初回ダイアログ文言も「管理者に確認してください。」
- 期待されるstoreデータ:
  - 読み取りのみで更新なし
- 期待されるassessmentLogs:
  - 新規作成なし

### CASE-A02 管理端末で強警告が出ている
- どのようなケースで: `getTopStrongWarning(meta) != null` かつ端末A/B（管理）
- 試行する操作: Terminalホームを表示
- 期待される画面:
  - `StrongWarningGate` による画面ブロック（閉じられない）
  - 第1ボタン: 「<対象日> の閉店処理へ」
  - 第2ボタン:
    - `needs_manual_close` / `next_day_started_strong` → 「営業継続」
    - `already_running_different_date` → 「緊急一時解除（xx分）」
- 期待されるstoreデータ:
  - ボタンを押さない限り更新なし
- 期待されるassessmentLogs:
  - ボタンを押さない限り新規なし

### CASE-A03 非管理端末で閉店中かつ開店処理必要
- どのようなケースで: `status=closed` かつ `shouldShowOpenNeeded(meta)=true`、端末C
- 試行する操作: AppBarの営業状態チップをタップ
- 期待される画面:
  - 「管理者に確認してください。」の案内ダイアログのみ
  - 開店操作は実行できない
- 期待されるstoreデータ:
  - 更新なし
- 期待されるassessmentLogs:
  - 新規なし

### CASE-A04 開閉店管理ダイアログに初期化ボタンがない
- どのようなケースで: 任意状態（`running/closed/error`）
- 試行する操作: 開閉店管理ダイアログを開く
- 期待される画面:
  - `初期化` ボタンが存在しない
- 期待されるstoreデータ:
  - 更新なし
- 期待されるassessmentLogs:
  - 新規なし

## B. 開店日付調整（毎回パスワード）

### CASE-B01 閉店中ダイアログで開店対象営業日が見える
- どのようなケースで: `status=closed` または `status=error`
- 試行する操作: 開閉店管理ダイアログを開く
- 期待される画面:
  - 「開店対象営業日: YYYY-MM-DD」表示
  - 「開店日付調整」ボタン表示
- 期待されるstoreデータ:
  - 更新なし
- 期待されるassessmentLogs:
  - 新規なし

### CASE-B02 調整開始ごとに毎回パスワード要求される
- どのようなケースで: CASE-B01の画面
- 試行する操作: 「開店日付調整」を連続2回押す
- 期待される画面:
  - 1回目・2回目ともにパスワード入力ダイアログが出る（セッション保持しない）
- 期待されるstoreデータ:
  - 更新なし
- 期待されるassessmentLogs:
  - 新規なし

### CASE-B03 開店日付調整パスワード不一致
- どのようなケースで: CASE-B01の画面、誤パスワード入力
- 試行する操作: パスワード入力→認証
- 期待される画面:
  - エラーSnackBar表示
  - 日付選択ダイアログは開かない
  - `plannedOpenBusinessDateKey` は変更されない
- 期待されるstoreデータ:
  - 更新なし
- 期待されるassessmentLogs:
  - 新規なし

### CASE-B04 開店日付調整パスワード一致
- どのようなケースで: CASE-B01の画面、正パスワード入力
- 試行する操作: パスワード入力→認証成功→日付選択
- 期待される画面:
  - 日付選択ダイアログが開く
  - 選択後、表示中の「開店対象営業日」が選択日へ更新
- 期待されるstoreデータ:
  - 更新なし（開店実行まではローカル表示のみ）
- 期待されるassessmentLogs:
  - 新規なし

### CASE-B05 調整した日付で開店実行
- どのようなケースで: CASE-B04後
- 試行する操作: 「開店処理を開始する」押下
- 期待される画面:
  - 成功SnackBar（対象日の営業開始）
- 期待されるstoreデータ:
  - `status=running`
  - `currentBusinessDateKey=<選択日>`
  - `openAssessment=null`
  - `manualOverrides` / `manualOverride` がクリア
- 期待されるassessmentLogs:
  - この操作自体では必須ログ追加なし（認定task側に依存）

### CASE-B06 開店未調整時の既存仕様（JST当日）
- どのようなケースで: 開店日調整せずに開店実行
- 試行する操作: `businessDateKey` 未調整のまま開店
- 期待される画面:
  - 成功SnackBar
- 期待されるstoreデータ:
  - `currentBusinessDateKey` が表示されていた「開店対象営業日」と一致
  - （デフォルトはJST当日）
- 期待されるassessmentLogs:
  - 必須追加なし

### CASE-B07 開店認証Callableの直接検証（API）
- どのようなケースで: `verifyOpenBusinessDateAdjustmentPassword` を直接実行
- 試行する操作:
  - 未認証
  - 誤パスワード
  - 正パスワード
- 期待される結果:
  - 未認証: `unauthenticated`
  - 誤り: `permission-denied`
  - 正解: `{ success: true }`
- 期待されるstoreデータ/assessmentLogs:
  - 更新なし

## C. 営業継続・緊急一時解除

### CASE-C01 `needs_manual_close` で営業継続
- どのようなケースで: 強警告=`needs_manual_close`
- 試行する操作: 「営業継続」→時間(1〜8h)選択→決定
- 期待される画面:
  - 成功SnackBar（リマインド予約）
- 期待されるstoreデータ:
  - `manualOverrides.close = { type:'close_skip', intendedBusinessDateKey, overrideUntil }`
  - `closeAssessment.result='needs_manual_close_suppressed'`
  - `closeAssessment.suppressedByOverride=true`
  - `manualOverride` は削除
- 期待されるassessmentLogs:
  - `type='continue_business'` のログ1件

### CASE-C02 `next_day_started_strong` で営業継続
- どのようなケースで: 強警告=`next_day_started_strong`
- 試行する操作: CASE-C01同様
- 期待される画面/store/log:
  - CASE-C01と同様（close側抑制）

### CASE-C03 重複警告時に営業継続1回で両方抑制
- どのようなケースで:
  - `closeAssessment` が強警告（営業継続対象）
  - かつ `openAssessment.result='skipped'` + `blockers` に `already_running_different_date`
- 試行する操作: 営業継続を1回実行
- 期待される画面:
  - 1回で完了（2回押下不要）
- 期待されるstoreデータ:
  - `manualOverrides.close` 設定
  - `manualOverrides.open` も同時設定（`type='open_skip'`）
  - `openAssessment.suppressedByOverride=true`
- 期待されるassessmentLogs:
  - `type='continue_business'` に `openOverrideApplied=true`

### CASE-C04 `already_running_different_date` で緊急一時解除
- どのようなケースで: 強警告=`already_running_different_date`、管理端末
- 試行する操作: 「緊急一時解除（xx分）」→確認ダイアログで実行
- 期待される画面:
  - 成功SnackBar（xx分後再評価）
- 期待されるstoreデータ:
  - `manualOverrides.open = { type:'open_skip', intendedBusinessDateKey, overrideUntil }`
  - `openAssessment.suppressedByOverride=true`
  - `manualOverride` は削除
- 期待されるassessmentLogs:
  - `type='open_temporary_unlock'` 追加

### CASE-C05 緊急一時解除の不正条件
- どのようなケースで:
  - `status!=running` または
  - `openAssessment` が `already_running_different_date` 条件を満たさない
- 試行する操作: 緊急一時解除実行
- 期待される画面:
  - エラーSnackBar
- 期待されるstoreデータ:
  - 更新なし
- 期待されるassessmentLogs:
  - 新規なし

### CASE-C06 非管理端末では解除操作不可
- どのようなケースで: 強警告発生 + 非管理端末C
- 試行する操作: 解除系操作を試みる
- 期待される画面:
  - 管理者確認の案内のみ
  - 解除操作UIは提供されない
- 期待されるstoreデータ/assessmentLogs:
  - 更新なし

## D. 再評価タスク・期限到達

### CASE-D01 営業継続で予約された closeAssessment 再評価
- どのようなケースで: CASE-C01/C02後、予約時刻到達
- 試行する操作: 予約時刻まで待つ
- 期待されるstoreデータ:
  - `closeAssessment` が task結果で更新される
  - override有効期限内なら `needs_manual_close_suppressed` 維持
  - 期限切れ後かつ未解消なら `needs_manual_close` 等へ戻る
- 期待されるassessmentLogs:
  - `type='close'` のtaskログ追加

### CASE-D02 開店側override期限到達で再ブロック
- どのようなケースで: CASE-C04またはCASE-C03でopen override設定済み、期限到達
- 試行する操作: 期限到達を待つ
- 期待されるstoreデータ:
  - `openAssessmentTask(action='open_assessment_recheck')` 実行
  - 条件継続なら `openAssessment.result='skipped'` + `blockers=['already_running_different_date']`
  - `suppressedByOverride` は外れる（再ブロック）
- 期待されるassessmentLogs:
  - `type='open'`, `action='open_assessment_recheck'` ログ追加

### CASE-D03 `open_assessment_recheck` は日付範囲外でも date_out_of_range にしない
- どのようなケースで: `intendedBusinessDateKey` が今日/明日以外
- 試行する操作: `action='open_assessment_recheck'` 実行
- 期待されるstoreデータ:
  - `date_out_of_range` で即skipしない
  - 通常判定ロジックで結果が決まる
- 期待されるassessmentLogs:
  - `type='open'` ログ（`action='open_assessment_recheck'`）

### CASE-D04 正常閉店直後のopen即時再評価予約
- どのようなケースで: `closeStoreTerminal` 正常完了
- 試行する操作: 閉店実行
- 期待されるstoreデータ:
  - `status='closed'`, `currentBusinessDateKey=null`
  - `closeAssessment=null`
  - `manualOverrides` / `manualOverride` クリア
  - `openAssessment` は直後に直接改変しない（再評価待ち）
- 期待されるassessmentLogs:
  - `type='open_recheck_after_close'` が追加
  - `enqueueSucceeded` が記録される

### CASE-D05 正常閉店時の再評価対象日選定
- どのようなケースで:
  1. `openAssessment.intendedBusinessDateKey` が有効
  2. それがない/不正
- 試行する操作: 正常閉店
- 期待される結果:
  - 1: 既存 intended を再評価対象に使う
  - 2: `generateJstDateKey()` を再評価対象に使う
- 期待されるassessmentLogs:
  - `open_recheck_after_close.intendedBusinessDateKey` が上記通り

## F. Secret / Config

- 試行する操作: 開店日付調整認証を実行
- 期待される結果:

  - UIでは認証失敗として表示

### CASE-F02 新keyが正しく設定されている
- どのようなケースで: `business-secrets.openBusinessDateAdjustmentPassword` 設定済
- 試行する操作: 正パスワードで認証
- 期待される結果:
  - 認証成功し日付調整可能

### CASE-F03 recheckMinutesのデフォルト適用
- どのようなケースで: `storeMeta/config.autoOpenClose.alreadyRunningDifferentDateRecheckMinutes` 未設定
- 試行する操作: 緊急一時解除を表示/実行
- 期待される結果:
  - UI表記もバックエンド予約も `15分`

### CASE-F04 recheckMinutesが異常値
- どのようなケースで: configに0や181など不正値
- 試行する操作: 緊急一時解除を表示/実行
- 期待される結果:
  - `15分` にフォールバック

## 付録: 合格判定の最小チェック項目
- 1. 強警告の端末別表示が要件通り（管理はブロック、非管理は管理者確認文言のみ）
- 2. 開店日付調整は「押すたび毎回」パスワードが必要
- 3. `already_running_different_date` は緊急一時解除で一定時間のみ抑制され、期限後に再評価される
- 4. 営業継続の1回操作で重複警告（close/open）を同時抑制できる
- 5. 正常閉店後は `openAssessment` を即時再評価予約し、`manualOverrides` は確実にクリアされる
