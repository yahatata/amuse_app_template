# 実機テスト改善項目（運用フロー別・実装順序付き）

実機で試して必要だと思った内容を、**遷移・データの動きに沿った運用フロー**単位で仕分けし、手戻りを防ぐための実装順序を定めたもの。

---

## 実装順序の考え方

- **上流→下流**: データや遷移の依存関係がある場合、前提となるフローを先に実装する
- **基盤→応用**: 他フローに影響する基盤（例: 卓競合）は早めに対応する
- **独立フロー**: 依存の少ないものは並行しやすい

---

## 実装順序一覧

| 順 |  | 運用フロー | 理由 |
|----|----|-----------|------|
| 1 | [ ] | ユーザーログイン | 他に依存しない。入店の入口 |
| 2 | [ ] | メニュー管理 | 注文フローの前提。アーカイブでタブ位置が変わる問題もここ |
| 3 | [ ] | サイドゲーム×トーナメント（卓競合） | 両フローの基盤。後から直すと手戻り大 |
| 4 | [ ] | トーナメント | 閉店フローの前提。卓競合解消後に着手 |
| 5 | [ ] | 閉店処理 | トーナメント終了後の遷移に依存 |
| 6 | [ ] | サイドゲーム | 卓競合解消後。トーナメントと卓を共有 |
| 7 | [ ] | 入店後ユーザー管理・LINE | トーナメント参加など、他フローと接続 |
| 8 | [ ] | 注文 | メニュー管理の後に。閉店後の注文カード表示も含む |
| 9 | [ ] | 会計 | 独立フロー。遷移・後で再開・完了タブ |
| 10 | [ ] | 勤怠・ダッシュボード・デバイス・その他 | 独立または横断 |

## 運用フロー1: ユーザーログイン（入店の入口）

- [ ] **フロー全体**

**遷移**: ホーム → ユーザーログイン画面 → 手動/QR選択 → ログイン成功/失敗

- [ ] Flutter側の手動及びQRユーザーログインで成功/失敗どちらもユーザーログイン画面に戻っているのではなく、新しいユーザーログイン画面が重なって表示されている状態。つまり、10人連続でその画面からログインすると11画面重なることになる。
  - **解決案**: `UserManualCheckInPage`/`userQRCheckInPage` の成功・失敗時の `Navigator.pushReplacement` をやめ、`Navigator.pop(context)` で手動/QRページを閉じたうえで、親の `UserCheckInPage` 上で `showDialog` する。`pushReplacement` だと毎回新しい `UserCheckInPage` が積み重なるため。

- [ ] 手動ユーザーログインに失敗した場合にQRか手動の選択画面に戻るのではなくもう一度同じ画面のまま試行できた方が良い。（QRは戻って良いかも）
  - **解決案**: `UserManualCheckInPage` の失敗時は `Navigator.pushReplacement` せず、`showDialog` でエラー表示のみ。OKでダイアログを閉じ、同じ手動画面のまま再試行可能にする。

## 運用フロー3: サイドゲーム×トーナメント（卓競合）※基盤

- [ ] **フロー全体**

**遷移・データ**: 卓(tables) と scheduledTournament.tableseat の二重管理により競合が発生。サイドゲームのテーブル選択 → トナメ実施中卓を選択 → 競合状態

**重要**: この解消を後回しにすると、トーナメント・サイドゲーム両方の実装で手戻りが発生する。

- [ ] ※サイドゲームのテーブル選択時にトナメ実施中のテーブルを選択した際に確認ダイアログが表示される。そこで確認を押すと確認画面ではなくゲーム選択画面になる。そこでゲームを選択できてしまい、トーナメントとサイドゲーム両方で卓が使用されているという状況がUI上で発生。Firestoreのtablesは後者を採用し、scheduledTournamentのtableseatはサイドゲームの処理によって上書きされないために起きている？そしてトナメの卓追加はtablesを参照しているため卓一覧にtableDがあっても同じ卓を追加できてしまった。すると元のtableDの情報は上書きされ新たに卓追加後の情報のないtableDとなった。そのため元々座っていたユーザーはエントリーには残っているがバーストしておらず参加中でもなくリエントリーとして参加できる状態だった。
  - **解決案**: `side_game_table_list.dart` の `_handleTableSelection` で `isInUse` かつトナメ実施中の場合、`_showGameSelectionDialog` を出さず「トーナメント使用中のため選択できません」と表示して終了。または、サイドゲームの卓選択は `tables` の `status` が `open` のもののみ許可し、`scheduledTournament.tablesSeat` に存在する卓は除外。`addTableToTournament` は `tables` と `scheduledTournament.tablesSeat` の両方を確認して重複を防ぐ。

※実装時に考慮すべきポイントであり、独立しているタスクではなく密接に関係している可能性大なので実装順序や実装方法を考慮して進める。

サイドゲームのテーブル選択時にユーザーがいない卓がトナメに登録してあってもサイドゲームで使えた方が都合が良いので、サイドゲームからの上書きを拒否する実装はしない。

卓ページは運用デバイス等も使えるが卓専用デバイスで使う想定。登録してある卓の情報が基本的にデフォルトで表示してあり、そこからもトナメ登録やサイドゲーム登録が行える。

- [ ] トナメ参加登録・卓追加・待機者一覧の際に参加登録ボタン・追加を押すとボタン内でロード表示になっている。（サイドゲームの登録時のロードが良いかも）
  - **解決案**: `assign_seat_dialog.dart`、`add_table_dialog.dart` 等で、ボタン押下時に `Stack` で `CircularProgressIndicator` をボタン上にオーバーレイ（半透明）、またはボタン全体を `disabled` にして上部にロード表示。

  - **解決案**: `tournament_home_page` 等で `status == 'ended'` のとき、参加登録・卓追加・着席ボタンを非表示または `disabled` に。`endTournament` で `status` を `ended` にしているか確認。

- [ ] トナメ終了後は卓一覧から卓を自動削除しても良いかも。
  - **解決案**: `endTournament` の Callable 内で、`tablesSeat` の `waiting`/`busted` 以外を削除するか、`removeTableFromTournament` を呼ぶ。または Flutter 側で終了後に `tablesSeat` をクリアする処理を追加。

- [ ] トナメ終了時の卓の削除検討。論理削除するかどうか。

## 運用フロー5: 閉店処理（トーナメント終了後の流れ）

- [ ] **フロー全体**

**遷移**: 営業中 → 閉店処理へ → トーナメント終了確認 → トーナメントページ（必要なら）→ 終了処理 → 閉店処理実行

**前提**: トーナメント終了処理が完了していること。遷移設計が閉店フローに影響する。

- [ ] 閉店処理未実施の場合の警告で、営業継続を選択して時間のリマインド選択後も警告が表示され続け継続ができない。
  - **解決案**: `continueBusinessTerminal` が `manualOverride` を書き込み、`closeAssessment.suppressedByOverride` を true にする。`store_assessment_utils.dart` の `_closeSuppressed` が true なら表示しない。Callable の `manualOverride` 書き込みが正しく `closeAssessmentTask` に反映されているか確認。

- [ ] 閉店処理へというボタンを押すと閉店前確認があるが、トーナメントの終了処理を終えてからという記載に従ってトーナメントを選択するとトーナメントページへの案内が表示される。そこでトーナメントページに遷移するとここでも閉店処理の警告ダイアログが表示されるため結局終了処理を行えない。
  - **解決案**: `close_pre_confirmation_page.dart` のトーナメント選択時の遷移先で、閉店警告ダイアログを表示しないようにする。または、トーナメントページ内で `StoreMetaService` の強警告を一時的に非表示にするオプションを渡す。または、閉店前確認→トーナメントページへの遷移を「モーダルで開く」にして、戻ったときに閉店前確認に戻れるようにする。

- [ ] 閉店処理未実施の警告でリマインドを選択して、その後閉店処理を終えると、閉店処理が終わっているにも関わらずリマインドが表示された。この時はすでに閉店処理できてる？それとも閉店未実施の状態に戻っている？確認。
  - **解決案**: `continueBusinessTerminal` が予約した Cloud Tasks のリマインドは、閉店完了後にキャンセルされていない可能性。`closeStoreTerminal` 実行時に、該当 `intendedBusinessDateKey` のリマインドタスクをキャンセルする処理を追加。または `store_warning_first_dialog_prefs` でリマインド表示済みフラグを閉店完了時にクリアする。

  - **解決案**: `table_select_page.dart` などで `tablesSeat` を `get()` で取得している場合、`snapshots()` に変更してリアルタイム更新。または表示を「参加人数」ではなく「登録時点の人数」と明記。

**ダッシュボード**
- [ ] ダッシュボードのカテゴリ詳細の4つのカテゴリの表記を統一。
  - **解決案**: `dashboard_home_page.dart` 等でカテゴリ名の参照元を `storeMeta/config.menuCategories` に統一。ハードコードがあれば削除。

**デバイス管理**
- [ ] デバイス管理のオプション編集でトナメ卓専用にして卓を指定する際にtableDがないのはなぜ？
  - **解決案**: `device_management_page.dart` の卓選択オプションで、`tables` コレクションの `isEnabled` が true のものを表示。`scheduledTournament.tablesSeat` に存在する卓はトーナメント開催中のみ存在するため、`tables` を基準にする。

- [ ] オプション編集のダイアログで卓指定が必要なオプション選択時にスクロールしないとオプションが全て表示されないのにスクロールバーがない。
  - **解決案**: `ListView` や `SingleChildScrollView` に `Scrollbar` ウィジェットを追加。`Scrollbar(isAlwaysShown: true, child: ListView(...))`。

- [ ] オプション編集の際に編集ボタン押下でロード表示が必要。
  - **解決案**: 編集 Callable 呼び出し前後に `setState` でロード表示。

- [ ] オプション編集のブロックと退役とデバイス削除がエラーになる。機能の必要性をまず洗ってエラー確認。
  - **解決案**: `device_management_page.dart` の該当処理の Callable 名・パラメータを確認。Functions 側に実装があるか確認。必要なければ削除、必要ならエラー原因を特定。
