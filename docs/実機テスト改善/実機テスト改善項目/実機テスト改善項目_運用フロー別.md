# 実機テスト改善項目（運用フロー別・実装順序付き）

実機で試して必要だと思った内容を、**遷移・データの動きに沿った運用フロー**単位で仕分けし、手戻りを防ぐための実装順序を定めたもの。

---

## 実装順序の考え方

- **上流→下流**: データや遷移の依存関係がある場合、前提となるフローを先に実装する
- **基盤→応用**: 他フローに影響する基盤（例: 卓競合）は早めに対応する
- **独立フロー**: 依存の少ないものは並行しやすい

---

## 運用フロー1: ユーザーログイン（入店の入口）

- [x] **フロー全体**

**遷移**: ホーム → ユーザーログイン画面 → 手動/QR選択 → ログイン成功/失敗

- [x] Flutter側の手動及びQRユーザーログインで成功/失敗どちらもユーザーログイン画面に戻っているのではなく、新しいユーザーログイン画面が重なって表示されている状態。つまり、10人連続でその画面からログインすると11画面重なることになる。
  - **解決案**: `UserManualCheckInPage`/`userQRCheckInPage` の成功・失敗時の `Navigator.pushReplacement` をやめ、`Navigator.pop(context)` で手動/QRページを閉じたうえで、親の `UserCheckInPage` 上で `showDialog` する。`pushReplacement` だと毎回新しい `UserCheckInPage` が積み重なるため。
  - **対応済（2026-06）**: `UserCheckInResult` で `pop` 返却。親 `UserCheckInPage` が成功/QR失敗ダイアログを表示。実機確認済。

- [x] 手動ユーザーログインに失敗した場合にQRか手動の選択画面に戻るのではなくもう一度同じ画面のまま試行できた方が良い。（QRは戻って良いかも）
  - **解決案**: `UserManualCheckInPage` の失敗時は `Navigator.pushReplacement` せず、`showDialog` でエラー表示のみ。OKでダイアログを閉じ、同じ手動画面のまま再試行可能にする。
  - **対応済（2026-06）**: 手動失敗は当該画面でエラーダイアログのみ。QR 失敗は `pop` で選択画面に戻り親がダイアログ表示。実機確認済。

## 運用フロー3: サイドゲーム×トーナメント（卓競合）※基盤

- [x] **フロー全体**

**遷移・データ**: 卓(tables) と scheduledTournament.tableseat の二重管理により競合が発生。サイドゲームのテーブル選択 → トナメ実施中卓を選択 → 競合状態

**重要**: この解消を後回しにすると、トーナメント・サイドゲーム両方の実装で手戻りが発生する。

- [x] ※サイドゲームのテーブル選択時にトナメ実施中のテーブルを選択した際に確認ダイアログが表示される。そこで確認を押すと確認画面ではなくゲーム選択画面になる。そこでゲームを選択できてしまい、トーナメントとサイドゲーム両方で卓が使用されているという状況がUI上で発生。Firestoreのtablesは後者を採用し、scheduledTournamentのtableseatはサイドゲームの処理によって上書きされないために起きている？そしてトナメの卓追加はtablesを参照しているため卓一覧にtableDがあっても同じ卓を追加できてしまった。すると元のtableDの情報は上書きされ新たに卓追加後の情報のないtableDとなった。そのため元々座っていたユーザーはエントリーには残っているがバーストしておらず参加中でもなくリエントリーとして参加できる状態だった。
  - **解決案**: `side_game_table_list.dart` の `_handleTableSelection` で `isInUse` かつトナメ実施中の場合、`_showGameSelectionDialog` を出さず「トーナメント使用中のため選択できません」と表示して終了。または、サイドゲームの卓選択は `tables` の `status` が `open` のもののみ許可し、`scheduledTournament.tablesSeat` に存在する卓は除外。`addTableToTournament` は `tables` と `scheduledTournament.tablesSeat` の両方を確認して重複を防ぐ。
  - **対応済（2026-06）**:
    - **データ破壊防止**: `active_tournament_table_usage.dart` で当日・未終了TNの `tablesSeat` を参照。着席者あり（`userId` / `okibakeEntryId`）は SG 開始拒否。登録済み・着席なしは警告後に一時利用可（上書き拒否はしない方針を維持）。
    - **卓二重登録防止**: CF `addTableToTournament` で `tablesSeat` 重複をトランザクション拒否。Flutter `getAvailableTables` で登録済み卓を除外。
    - **表示と実態の整合**: SG一覧は `tables.status` + `tablesSeat` usage を合成表示（使用可能 / トーナメント登録中 / トーナメント着席中 / SG中）。SG終了時は `tablesSeat` 登録が残っていれば `tables.status=tournament` に復元。
    - **警告文言**: TN登録中の確認は「一時使用」前提のメッセージ（上書き表現は不使用）。
    - **主な変更ファイル**: `active_tournament_table_usage.dart`, `side_game_table_list.dart`, `side_game_table_home.dart`（終了復元）, `addTableToTournament.ts`, `tournament_data_service.dart`, `add_table_dialog.dart`。
    - **実機確認済**。

※実装時に考慮すべきポイントであり、独立しているタスクではなく密接に関係している可能性大なので実装順序や実装方法を考慮して進める。

サイドゲームのテーブル選択時にユーザーがいない卓がトナメに登録してあってもサイドゲームで使えた方が都合が良いので、サイドゲームからの上書きを拒否する実装はしない。

卓ページは運用デバイス等も使えるが卓専用デバイスで使う想定。登録してある卓の情報が基本的にデフォルトで表示してあり、そこからもトナメ登録やサイドゲーム登録が行える。

## 運用フロー5: 閉店処理（トーナメント終了後の流れ）

- [x] **フロー全体**

**遷移**: 営業中 → 閉店処理へ → トーナメント終了確認 → トーナメントページ（必要なら）→ 終了処理 → 閉店処理実行

**前提**: トーナメント終了処理が完了していること。遷移設計が閉店フローに影響する。

**補足（2026-06）**: 営業継続後の警告抑制・閉店後リマインド再表示は、現状コード上は解消済み想定。今後の実機テストで再発した場合は、Firestore の `closeAssessment` / `manualOverrides` / `openAssessment` と Cloud Tasks ログを確認して切り分ける。

- [x] 閉店処理未実施の場合の警告で、営業継続を選択して時間のリマインド選択後も警告が表示され続け継続ができない。
  - **解決案**: `continueBusinessTerminal` が `manualOverride` を書き込み、`closeAssessment.suppressedByOverride` を true にする。`store_assessment_utils.dart` の `_closeSuppressed` が true なら表示しない。Callable の `manualOverride` 書き込みが正しく `closeAssessmentTask` に反映されているか確認。
  - **対応済（2026-06・一旦）**: `continueBusinessTerminal` で `manualOverrides.close` + `closeAssessment.suppressedByOverride=true`（`needs_manual_close_suppressed`）。Flutter は `_closeSuppressed` で強警告ゲート非表示。`closeAssessmentTask` は override 有効中に suppressed を維持。再発時は上記補足のとおり Firestore / Cloud Tasks で切り分け。

- [x] 閉店処理へというボタンを押すと閉店前確認があるが、トーナメントの終了処理を終えてからという記載に従ってトーナメントを選択するとトーナメントページへの案内が表示される。そこでトーナメントページに遷移するとここでも閉店処理の警告ダイアログが表示されるため結局終了処理を行えない。
  - **解決案**: `close_pre_confirmation_page.dart` のトーナメント選択時の遷移先で、閉店警告ダイアログを表示しないようにする。または、トーナメントページ内で `StoreMetaService` の強警告を一時的に非表示にするオプションを渡す。または、閉店前確認→トーナメントページへの遷移を「モーダルで開く」にして、戻ったときに閉店前確認に戻れるようにする。
  - **対応済（2026-06）**: `suppressStoreStrongWarning` + `fullscreenDialog` 遷移。

- [x] 閉店処理未実施の警告でリマインドを選択して、その後閉店処理を終えると、閉店処理が終わっているにも関わらずリマインドが表示された。この時はすでに閉店処理できてる？それとも閉店未実施の状態に戻っている？確認。
  - **解決案**: `continueBusinessTerminal` が予約した Cloud Tasks のリマインドは、閉店完了後にキャンセルされていない可能性。`closeStoreTerminal` 実行時に、該当 `intendedBusinessDateKey` のリマインドタスクをキャンセルする処理を追加。または `store_warning_first_dialog_prefs` でリマインド表示済みフラグを閉店完了時にクリアする。
  - **対応済（2026-06・一旦）**: 正常閉店時 `closeStoreTerminal` が `closeAssessment` / `manualOverrides` をクリア。`closeAssessmentTask` は `already_closed` / `target_day_already_closed` で古いリマインドを無害化。Cloud Tasks の明示 cancel は未実装だが、現状コード上は再表示しない想定。再発時は上記補足のとおり切り分け（閉店成否・open 側警告の混同含む）。
