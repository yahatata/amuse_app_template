# エラー監視

## 1. 目的

中央管理アプリの `エラー一覧` を使って、

- 障害の見落としを防ぐ
- 重要度の高いものを先に拾う
- 対応済み・未対応を中央で管理する

ための運用手順をまとめる。

---

## 2. どこで確認するか

| 場所 | 何を見るか |
|------|------------|
| HOME | 店舗ごとの未解決件数、監視対象店舗 |
| `店舗詳細 > エラー一覧` | 個別エラー、重要度、対応状況 |
| `Analysis` | 横断的な errorGroup 傾向 |
| `設定 > 重要度ルール` | 通知・重要度の判定基準 |
| `設定 > 通知先` | 通知経路の有効/無効、送信先 |

---

## 3. データ正本

中央 Firestore 上の主な正本。

| 用途 | パス |
|------|------|
| 店舗別 error log | `errorLogs/{storeId}/logs/{logId}` |
| 横断グルーピング | `errorGroups/{groupKey}` |
| 重要度ルール | `importanceRules/{ruleId}` |
| 通知先 | `notificationTargets/{targetId}` |

---

## 4. 日常運用

### 4.1 毎日の最小確認

1. HOME で未解決件数の多い店舗が無いか見る
2. 対象店舗の `エラー一覧` を開く
3. `未対応` と `重要度` の高いものを先に確認する
4. 内容を見て
   - 即対応
   - 監視継続
   - ノイズなのでルール調整
   に分ける

### 4.2 エラーを開いたときに見るもの

| 項目 | 見る理由 |
|------|----------|
| `message` | まず事象を掴むため |
| `service` / `functionEntry` | どの機能系か絞るため |
| `occurredAt` | 継続中か単発か判断するため |
| `importance` | 先に見る優先順位を決めるため |
| `context` | `storeId`, `taskId`, `projectId` など実体確認のため |

### 4.3 対応済みにする基準

次のどちらかを満たしたら `対応済み` にする。

- 原因が解消され、再発監視フェーズに入った
- ノイズであり、重要度ルールや設定調整で再発時の扱いが決まった

単に「一度見た」だけでは対応済みにしない。

---

## 5. どのように保守するか

### 5.1 障害時

1. `エラー一覧` で対象店舗と対象関数を特定する
2. 同じ `functionEntry` / `errorKey` が複数あるかを見る
3. 必要なら `Analysis` で横断傾向を見る
4. 中央だけでは足りない場合は、店舗側 GCP の Cloud Logging を確認する

### 5.2 ノイズが多いとき

1. `設定 > 重要度ルール` を確認する
2. 既存ルールで過検知していないかを見る
3. ルール修正で抑えるのか、コード/設定修正を先にやるのか決める

### 5.3 通知がおかしいとき

1. `設定 > 通知先` で対象通知先が有効か確認する
2. `重要度ルール` の通知条件を確認する
3. それでも不明なら、店舗側 error 発生有無と中央 `errorLogs` への書き込み有無を確認する

---

## 6. 中央に何も出ないとき

| 事象 | 確認すること |
|------|--------------|
| 店舗が HOME に出ない | 中央 `stores/{storeId}` 登録、`enabled=true` |
| error が来ない | 店舗側 Cloud Logging、中央 `errorLogs` への書き込み |
| 通知だけ来ない | `notificationTargets` と `importanceRules` |
