# リリース前後チェックリスト

## 1. 目的

本資料は、アプリと Firebase プロジェクトの紐付けを誤らずにリリースするための運用チェックリストである。  
クライアント側 / デプロイ・CLI 側 / Functions 側が同じ対象 Firebase プロジェクト（Firebase Project ID）を扱っていることを、
導入時（初回リリース時）と通常リリース時の両方で確認できるようにする。

用語ルール:

- `GitHubリポジトリ名`: 例 `yahatata/amuse_app_template`
- `Firebase Project ID（= GCP Project ID）`: 例 `amuse-app-template`
- `project_id`: GitHub Actions workflow の入力名（値は Firebase Project ID）
- `projectId`: Functions コード内の変数名（表す値は Firebase Project ID）

## 2. 初回導入時（初回リリース時）

### 2.1 対象 Firebase プロジェクト（Firebase Project ID）決定

- [ ] 今回リリースするアプリ名を確定した
- [ ] 紐付ける Firebase Project ID（コード変数名: `projectId`）を確定した
- [ ] 同じ Firebase Project ID をクライアント側 / デプロイ・CLI 側 / Functions 側で扱う前提を確認した

### 2.2 クライアント側設定

- [ ] `lib/firebase_options.dart` が対象 Firebase Project ID 向けに生成または更新されている
- [ ] `android/app/google-services.json` が対象 Firebase Project ID のものになっている
- [ ] `ios/Runner/GoogleService-Info.plist` が対象 Firebase Project ID のものになっている
- [ ] `macos/Runner/GoogleService-Info.plist` が対象 Firebase Project ID のものになっている
- [ ] クライアントコードに別プロジェクト用の固定文字列が残っていない

### 2.3 デプロイ・CLI側設定

- [ ] `.firebaserc` の alias / default 設定を確認した
- [ ] `firebase.json` の内容が対象アプリの deploy 対象と矛盾していない
- [ ] リリース手順上、`firebase deploy --project=<Firebase Project ID>` のように Firebase Project ID を明示できる
- [ ] 誤った default プロジェクトへ deploy しない運用になっている
- [ ] GitHub Actions workflow の `project_id` が `choice` で定義され、Firebase Project ID を選択できる
- [ ] GitHub Secrets に `WIF_PROVIDER` / `WIF_SERVICE_ACCOUNT` が登録されている
- [ ] WIF（Pool/Provider/SA impersonation）が対象リポジトリで有効である

### 2.4 Functions側設定

- [ ] Firebase Project ID（コード変数名: `projectId`）を必要とする箇所が `getRequiredProjectId()` へ寄っている
- [ ] Firebase Project ID（`projectId`）の固定文字列フォールバックが残っていない
- [ ] Cloud Tasks / Secret Manager / SA メール組み立てで Firebase Project ID（`projectId`）の取得元が統一されている

### 2.5 GCP / Firebase コンソール確認

- [ ] 対象 Firebase Project ID 側に必要な Secret が作成されている
- [ ] 対象 Firebase Project ID 側に必要な Cloud Tasks Queue が存在する
- [ ] 対象 Firebase Project ID 側に必要な Service Account / 権限が存在する
- [ ] 対象 Firebase Project ID 側に Functions / Hosting / Firestore など必要リソースが用意されている
- [ ] Functions / Cloud Tasks / Cloud Run が `asia-northeast1` 前提で整っている
- [ ] `task-endpoints`（`controlHookUrl` / `closeAssessmentUrl` / `openAssessmentUrl`）が最新リージョンURLを指している

## 3. 通常リリース時

### 3.1 リリース前確認

- [ ] 今回の対象アプリと Firebase プロジェクトの組み合わせを再確認した
- [ ] クライアント設定ファイルが今回の対象 Firebase Project ID 向けになっている
- [ ] deploy コマンドの対象 Firebase Project ID（`projectId`）が正しい
- [ ] 今回追加した Functions コードに独自の `process.env.GCLOUD_PROJECT` 読みが増えていない
- [ ] GitHub Actions 実行時は `project_id` の選択値（Firebase Project ID）が今回の対象と一致している
- [ ] リージョン前提が `asia-northeast1` に統一されている（コード・設定・運用手順）

### 3.2 リリース実行時

- [ ] `firebase deploy --project=<Firebase Project ID>` など、Firebase Project ID を明示して実行した
- [ ] deploy 実行ログに想定外のプロジェクト名が出ていない
- [ ] クライアントビルド対象と deploy 先が同じプロジェクトであることを確認した

### 3.3 リリース後確認

- [ ] アプリ起動後、対象 Firebase プロジェクトのデータを参照していることを確認した
- [ ] Functions ログで Firebase Project ID（`projectId`）が想定どおりであることを確認した
- [ ] Cloud Tasks / Secret Manager 参照先が対象 Firebase Project ID であることを確認した
- [ ] 誤プロジェクトへのデータ書き込みや task 作成が起きていない
- [ ] `task-endpoints` の URL 参照先がデプロイ後の実体（`asia-northeast1`）と一致している
- [ ] `us-central1` 側の旧queue/functionを誤って参照していない

## 4. Functions側の実装確認ポイント

- [ ] `tasks.ts` が `getRequiredProjectId()` 経由で queuePath を組み立てている
- [ ] `weeklyPlanner.ts` が `getRequiredProjectId()` 経由で queuePath / taskPath を組み立てている
- [ ] `continueBusinessTerminal.ts` が `getRequiredProjectId()` 経由で queuePath / taskPath を組み立てている
- [ ] `logOpsError.ts` が `getRequiredProjectId()` もしくは同等の共通経路で Firebase Project ID（`projectId`）を解決している
- [ ] 新規に Firebase Project ID（`projectId`）が必要なファイルを追加した場合、適用対象一覧を更新している

## 5. 導入後の運用ルール

- Firebase Project ID（`projectId`）を使う新規処理を追加した場合は、共通 helper を使う
- クライアント設定ファイルの更新と deploy 先変更を別々に行わない
- `default` alias の思い込みで deploy しない
- リリースレビュー時に「対象アプリ」「対象 Firebase Project ID」「Functions の projectId 取得方法」の 3 点を確認する

## 6. 失敗例として防ぎたいこと

- Android / iOS は A プロジェクト、Functions は B プロジェクトに向いている
- `.firebaserc` の default を見誤って別プロジェクトへ deploy する
- Functions コードに残っていた固定文字列フォールバックで別プロジェクトを参照する
- Cloud Tasks / Secret Manager の参照先だけが古い Firebase Project ID（`projectId`）のまま残る
