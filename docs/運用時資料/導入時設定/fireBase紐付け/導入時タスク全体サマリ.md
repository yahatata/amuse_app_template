# 導入時タスク全体サマリ

## 1. この資料の目的

新しい Firebase Project ID を導入するときに、
「どの順番で、何を、どこまでやれば完了か」を迷わず実行するためのサマリ。

詳細手順は以下を参照する。

- `新規Firebaseプロジェクト追加時_デプロイ手順.md`
- `docs/運用時資料/導入時設定/SecretManager/初回導入_SecretManager設定手順.md`
- `リリース前後チェックリスト.md`

## 2. 全体の流れ（先に全体像）

1. 対象 Firebase Project ID を決める
2. GCP API / IAM / WIF を準備する
3. Secret Manager を作成し、実行 SA に権限を付ける
4. Cloud Tasks の必須 queue を作る
5. Functions をデプロイする
6. `task-endpoints` をデプロイ後 URL で更新する
7. Cloud Tasks の OIDC 呼び出し SA と `run.invoker` を整える
8. 完了チェック（リージョン・queue・secret・実行確認）を行う

## 3. タスク一覧（実行順）

| No | 何をするか | どこで作業するか | 完了条件 |
|---|---|---|---|
| 1 | 対象 `projectId` を確定する | 運用判断 | リリース対象アプリと `projectId` の組み合わせが確定している |
| 2 | 必須 API を有効化する | GCP CLI | Functions / Run / Tasks / Scheduler / Secret Manager API が有効 |
| 3 | deploy 用 SA と WIF を設定する | GCP + GitHub | GitHub Actions から対象 `projectId` へ deploy できる |
| 4 | 3 secret を作成する | GCP CLI | `line-config` / `task-endpoints` / `business-secrets` が存在し latest 参照可 |
| 5 | Secret 参照権限を付与する | GCP CLI | 実行 SA が 3 secret で `secretAccessor` を持つ |
| 6 | queue を作成する | GCP CLI | `tournament-queue` / `business-date-assessment-queue` が `asia-northeast1` に存在 |
| 7 | Functions をデプロイする | GitHub Actions | 対象関数が `asia-northeast1` で `ACTIVE` |
| 8 | `task-endpoints` を更新する | GCP CLI | 3 URL がデプロイ済み実体 URL と一致 |
| 9 | OIDC 用 SA と `run.invoker` を設定する | GCP CLI | `tasks-invoker` / `openclose-tasks-invoker` が対象 service を呼べる |
| 10 | リリース後確認を行う | GCP + アプリ実機 | task 実行と主要機能が正常、想定外リージョン参照なし |

## 4. この導入で「手動 env 設定」が必要か

- 原則不要。Functions に custom env を手で入れない。
- この導入で人が設定するのは、主に次の 3 つ。
  - Secret Manager の値
  - IAM（secretAccessor / run.invoker）
  - Cloud Tasks queue

## 5. 迷いやすいポイント

- `task-endpoints` 更新は **Functions デプロイ後** に行う  
  （デプロイ前は URL が確定しない）
- queue は「確認」だけでなく「無ければ作成」まで行う
- `us-central1` は調査対象として見ることはあっても、本線運用は `asia-northeast1` 前提
- `probe*` 関数は本線と別で扱う
