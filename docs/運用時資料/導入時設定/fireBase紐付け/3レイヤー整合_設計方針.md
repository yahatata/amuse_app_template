# 3レイヤー整合_設計方針

## 1. 目的

1 つのリポジトリから複数アプリをリリースし、それぞれ別の Firebase プロジェクトへ紐付ける前提で、
クライアント側 / デプロイ・CLI 側 / Functions 側が同じ対象 Firebase Project ID を矛盾なく扱える状態を維持する。

本資料の目的は、以下を明確にすること。

- 各レイヤーが何を責務として持つか
- どのファイルが何のために存在するか
- どの値をコード固定せず、実行環境や設定から解決すべきか
- 導入時（初回リリース時）および通常リリース時に何をそろえるべきか

用語ルール:

- `GitHubリポジトリ名`: 例 `yahatata/amuse_app_template`
- `Firebase Project ID（= GCP Project ID）`: 例 `amuse-app-template`
- `project_id`: GitHub Actions workflow の入力名（値は Firebase Project ID）
- `projectId`: Functions コード内の変数名（値は Firebase Project ID）

## 2. 基本方針

### 2.1 共通原則

- どのアプリをどの Firebase プロジェクトへ紐付けるかは、リリース前後の設定・生成・デプロイ手順で確定する。
- 各レイヤーは同じ対象 Firebase Project ID を扱うが、参照するファイルと取得方法はレイヤーごとに異なる。
- `projectId` はコードに固定文字列として埋め込まない。
- 実行時に必要な `projectId` は、Functions 側で `getRequiredProjectId()` のような共通ヘルパーから取得する。
- クライアント側設定ファイルは、対象 Firebase プロジェクトに合わせて生成または配置する。
- デプロイ時は、CLI がどの Firebase プロジェクトに対して実行しているかを明示的に確認する。

### 2.2 レイヤー別の責務

#### クライアント側

対象ファイル:

- `lib/firebase_options.dart`
- `android/app/google-services.json`
- `ios/Runner/GoogleService-Info.plist`
- `macos/Runner/GoogleService-Info.plist`

責務:

- Flutter / native アプリが初期化時に使用する Firebase 設定を保持する
- 対象アプリが接続する Firebase プロジェクトをクライアント初期化時に確定させる

注意:

- クライアント側は `projectId` を実行時に自前判定するのではなく、生成済み設定を使う
- アプリコード中に別プロジェクト用の `projectId` を直書きしない

#### デプロイ・CLI側

対象ファイル:

- `.firebaserc`
- `firebase.json`

責務:

- Firebase CLI がどのプロジェクトに対して操作するかを管理する
- リリース対象アプリと Firebase プロジェクトの組み合わせを、生成・デプロイ手順に接続する

注意:

- `.firebaserc` の default だけに依存しない
- リリース時は `firebase deploy --project=<Firebase Project ID>` のように、対象 Firebase Project ID を明示できる手順を優先する
- クライアント側の生成設定とデプロイ先が別プロジェクトにならないように確認する
- GitHub Actions で deploy する場合は `workflow_dispatch` の `project_id`（choice: Firebase Project ID）を必須入力にし、手入力を許可しない
- GitHub Actions の認証は WIF を使い、`WIF_PROVIDER` / `WIF_SERVICE_ACCOUNT` を GitHub Secrets で管理する
- GitHub Actions 自体に Secret Manager 読み取り権限は付与しない（実行時は Functions 実行 SA が Secret を参照）

#### Functions側

対象ファイル:

- `shared/runtime/projectId.ts`（想定）
- `functions/src/...` のうち `projectId` を処理時に必要とするファイル

責務:

- 実行環境から現在の `projectId` を安全に取得する
- Cloud Tasks、Secret Manager、SA メールアドレスなど、`projectId` を必要とする処理で共通ヘルパーを使う

注意:

- 各ファイルが独自に `GCLOUD_PROJECT` / `GCP_PROJECT` / `PROJECT_ID` を読む構成にしない
- `'amuse-app-template'` のような固定フォールバックを持たない
- `projectId` が不要なファイルには無理に helper を導入しない

## 3. 導入時にアプリごとに分ける必要があるもの

導入時設定として、Firebase Project ID（コード変数名: `projectId`）以外にもアプリごとに分ける必要があるものを以下に整理する。

### 3.1 Firebase クライアント設定

対象ファイル:

- `lib/firebase_options.dart`
- `android/app/google-services.json`
- `ios/Runner/GoogleService-Info.plist`
- `macos/Runner/GoogleService-Info.plist`
- `firebase.json`

主な対象値:

- `projectId`
- `appId`
- `apiKey`
- `messagingSenderId`
- `authDomain`
- `storageBucket`
- `measurementId`

役割:

- Flutter / native クライアントが接続する Firebase App を確定する
- 対象 Firebase Project ID に応じた Firebase 設定一式を生成または配置する

### 3.2 Web / LIFF 用 Firebase 設定と店舗表示設定

対象ファイル:

- `public/user/config.js`
- `public/staff/config.js`

主な対象値:

- `firebaseConfig.projectId`
- `firebaseConfig.apiKey`
- `firebaseConfig.authDomain`
- `firebaseConfig.storageBucket`
- `firebaseConfig.appId`
- `storeInfo.name`
- `storeInfo.id`

役割:

- LIFF ミニアプリが接続する Firebase Web 設定を確定する
- 店舗名や店舗識別子など、Web 側に表示・利用する導入値を確定する

### 3.3 LINE / LIFF 連携設定

対象ファイル / リソース:

- `public/user/config.js`
- `public/staff/config.js`
- LINE Developers 側設定
- Functions 側 Secret / 設定

主な対象値:

- `liffId`
- `userLiffId`
- `LINE_CHANNEL_ACCESS_TOKEN`
- `STAFF_RICHMENU_ID`
- `USER_RICHMENU_ID`

役割:

- 対象アプリに紐づく LINE ミニアプリ / Messaging API 設定を確定する
- スタッフ用 / ユーザー用の LIFF 導線とリッチメニューを整合させる

### 3.4 モバイルアプリ識別子・表示名

対象ファイル:

- `android/app/build.gradle.kts`
- `android/app/src/main/AndroidManifest.xml`
- `ios/Runner.xcodeproj/project.pbxproj`
- `macos/Runner/Configs/AppInfo.xcconfig`

主な対象値:

- Android `applicationId`
- Android `namespace`
- Android `android:label`
- iOS/macOS `PRODUCT_BUNDLE_IDENTIFIER`
- macOS `PRODUCT_NAME`

役割:

- Firebase 連携以前に、配布対象アプリそのものの識別子を確定する
- 別アプリとして配布・インストール・識別できる状態にする

### 3.5 Functions / GCP 側のプロジェクト別 Secret・運用値

対象:

- Secret Manager に置く値
- Functions 実行時に参照するプロジェクト別設定

主な対象値:

- `LINE_CHANNEL_ACCESS_TOKEN`
- `QR_SECRET_KEY`
- `UNCLOCKED_ATTENDANCE_EDIT_PASSWORD`
- `CONTROL_HOOK_URL`
- `CLOSE_ASSESSMENT_URL`
- `OPEN_ASSESSMENT_URL`

役割:

- プロジェクトごとに異なる機密値やエンドポイントを安全に分離する
- コード固定にできない運用値を各 Firebase / GCP プロジェクトに正しく投入する

### 3.6 GCP リソースの存在確認

対象:

- Secret Manager
- Cloud Tasks Queue
- Service Account / IAM
- Functions / Hosting / Firestore / Storage

役割:

- 対象 Firebase Project ID 側で必要な GCP / Firebase リソースが作成済みであることを保証する
- コードだけでは解決しない導入時作業を明示する

リージョン方針:

- Functions / Cloud Tasks / Cloud Run は `asia-northeast1` で統一する
- `task-endpoints` は `controlHookUrl` / `closeAssessmentUrl` / `openAssessmentUrl` の実体リージョンと一致させる

## 4. 今の fireBase紐付け 資料で不足していた点

従来の `fireBase紐付け` 資料は、主に Functions 側の `projectId` 整合に焦点が当たっていた。  
そのため、以下の観点が不足していた。

1. `projectId` 以外の Firebase App 設定一式
- `apiKey`、`appId`、`authDomain`、`storageBucket`、`measurementId` などを資料上で十分扱えていなかった

2. Web / LIFF 用の設定ファイル
- `public/user/config.js`、`public/staff/config.js` に入っている Firebase Web 設定、LIFF ID、店舗表示設定を導入時設定として扱えていなかった

3. LINE / LIFF の導入値
- LINE Developers 側の値や、Functions から使う LINE 関連 Secret を、Firebase 紐付け資料と横断して整理できていなかった

4. モバイルアプリ識別子
- Android `applicationId`、iOS/macOS `bundle identifier`、表示名など、配布アプリ固有の識別子を含められていなかった

5. GCP リソース作成・権限付与
- Secret 作成、Queue 作成、IAM 付与など、コンソール側の導入作業がチェック対象として十分に見えていなかった

以後、本フォルダ配下の資料では、Functions 側の `projectId` だけでなく、
導入時にアプリごとに分ける必要がある設定全体を扱う。

## 5. 3レイヤーの整合条件

同じ対象 Firebase Project ID を扱えていると判断する条件は、少なくとも以下の 3 点である。

1. クライアント側設定ファイルが、対象 Firebase プロジェクトの情報で生成または配置されている
2. デプロイ・CLI が、同じ対象 Firebase プロジェクトに向けて実行されている
3. Functions 実行環境で取得される `projectId` が、その Firebase プロジェクトと一致している

この 3 点のどれかがずれると、以下のような不整合が起きる。

- クライアントは A プロジェクト、Functions は B プロジェクトに接続する
- Secrets や Cloud Tasks の参照先が別プロジェクトを向く
- リリース対象と異なる Firebase プロジェクトへ deploy してしまう

## 6. Functions側の To-Be 設計

### 6.1 `getRequiredProjectId()` の責務

`getRequiredProjectId()` は以下のみを責務とする。

- 実行環境注入値から `projectId` を取得する
- `projectId` が取得できない場合は fail-fast する
- 呼び出し元に「現在の実行対象 Firebase Project ID」を返す

`getRequiredProjectId()` が担わないこと:

- アプリごとの分岐
- 手動で別プロジェクトを選ぶこと
- クライアント設定ファイルを読むこと
- `.firebaserc` や `firebase.json` を読むこと

### 6.2 `getRequiredProjectId()` の適用先

対象は、`projectId` を処理時に必要とする箇所だけとする。

主な対象:

- Cloud Tasks の `queuePath` / `taskPath`
- Secret Manager の `projects/{projectId}/...`
- SA メールアドレス組み立て
- 運用ログへの `projectId` 付与

### 6.3 禁止事項

- 各ファイルが独自に `process.env.GCLOUD_PROJECT` などを読む
- `projectId` の固定文字列フォールバックを持つ
- クライアント設定ファイルを Functions runtime の共通参照元として扱う

## 7. 導入時（初回リリース時）にそろえるべきこと

### 7.1 クライアント側

- 対象 Firebase プロジェクトに対応した `firebase_options.dart` を生成または反映する
- `google-services.json` / `plist` を対象 Firebase Project ID のものに置き換える
- `public/user/config.js` / `public/staff/config.js` の Firebase Web 設定、LIFF ID、店舗表示設定を対象アプリ向けにそろえる
- Android / iOS / macOS のアプリ識別子と表示名が対象アプリ向けになっていることを確認する

### 7.2 デプロイ・CLI側

- 対象 Firebase Project ID の alias / `projectId` を確認する
- deploy コマンドが対象 Firebase Project ID を明示していることを確認する
- 必要な Secret / Functions / Hosting などがそのプロジェクトに対して用意されていることを確認する
- LINE / LIFF、GCP リソース、Secret Manager の投入先が同じ対象 Firebase Project ID 前提で準備されていることを確認する
- GitHub Actions workflow の `project_id` options に対象 Firebase Project ID が含まれていることを確認する
- GitHub Secrets（`WIF_PROVIDER`/`WIF_SERVICE_ACCOUNT`）が対象リポジトリで有効になっていることを確認する
- WIF 側で対象リポジトリに対する impersonation 権限が付与されていることを確認する
- `asia-northeast1` の queue/function/service が先に準備されていることを確認する
- `task-endpoints` の3URLが新リージョン実体を向いていることを確認する

### 7.3 Functions側

- `getRequiredProjectId()` を共通ヘルパーとして実装する
- `projectId` 利用箇所を helper 経由へ置き換える
- 固定文字列フォールバックを削除する
- `projectId` 以外のプロジェクト別機密値は Secret Manager に寄せる

## 8. 通常リリース時の考え方

- クライアント設定ファイルが対象 Firebase Project ID 向けに更新されていることを確認する
- deploy 実行先が対象 Firebase Project ID になっていることを確認する
- Functions 側では、実行環境が `projectId` を注入する前提を崩さない
- 新しい `projectId` 利用箇所が増えた場合は、共通 helper を使う
- Web / LIFF 設定、モバイル識別子、LINE 連携値の変更がある場合は、同じリリース単位で見直す
- GitHub Actions から実行する場合、`project_id` 選択値（Firebase Project ID）と対象アプリの紐付けが一致していることを確認する
- `asia-northeast1` 以外のリージョン前提設定が混入していないことを確認する

## 9. このタイミングで実装すべきこと / まだ実装しなくてよいこと

### 9.1 今このタイミングで資料化・実装してよいもの

- `getRequiredProjectId()` の方針確定
- `getRequiredProjectId()` の適用対象一覧の明文化
- 3 レイヤー整合の設計方針の明文化
- 導入時にアプリごとに分ける必要がある設定一覧の明文化

### 9.2 今は資料化のみに留めてよいもの

- クライアント設定ファイル生成フローの自動化
- deploy 手順の完全自動化
- 複数アプリ / 複数プロジェクト切り替えの CLI ラッパー整備
- Android / iOS / macOS の識別子差し替え自動化
- LINE / LIFF 設定の自動投入
