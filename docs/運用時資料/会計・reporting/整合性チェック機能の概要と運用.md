# 整合性チェック機能の概要と運用

## 1. 概要

会計後調整機能の本番化に合わせて、analytics と reporting の集計結果を手動で点検できるよう、4つの callable が追加されています。

- `analyticsDailyCheck`
- `analyticsMonthlyCheck`
- `reportingDailyCheck`
- `reportingMonthlyCheck`

これらの結果は `batchJobLogs` に保存され、Flutter の管理画面 `詳細設定` から手動実行できます。

## 2. 4つの callable の役割と実行タイミング

| callable | 主な役割 | 対象単位 | 既定の対象 | 現在の主な使い方 |
|---|---|---|---|---|
| `analyticsDailyCheck` | `analyticsMonthly/{YYYY-MM}/days/{YYYY-MM-DD}` と bill 件数の整合を確認 | 日次 | 前日 | 日次障害確認、当日反映漏れ確認 |
| `analyticsMonthlyCheck` | `analyticsMonthly/{YYYY-MM}` の合計値、カテゴリ合計、遡及変更を確認 | 月次 | 前月 | 月締め前の最終点検 |
| `reportingDailyCheck` | `reportingEntries` の当日増分と `bills.closedAt` / `reportingMonthly` 増分を確認 | 日次 | 前日 | reporting の当日反映漏れ確認 |
| `reportingMonthlyCheck` | `reportingMonthly/{YYYYMM}` と `reportingEntries`、marker の件数・金額整合を確認 | 月次 | 前月 | 税務集計の月次点検 |

## 3. なぜ 4種類必要か

### 3-1. analytics と reporting は基準日が違う

- analytics は `businessDate` を基準に `analyticsMonthly/{YYYY-MM}` へ集計します。
- reporting は `settledAt` や `cashAction` の実行時刻を基準に `reportingEntries` と `reportingMonthly/{YYYYMM}` へ集計します。

### 3-2. 日次確認と月次確認で見る観点が違う

- 日次確認は「前日分が想定どおり増えたか」を見る運用向けチェックです。
- 月次確認は「月全体の doc が entries と一致しているか」を見る精査向けチェックです。

そのため、analytics / reporting × 日次 / 月次 の4本が必要になります。

## 4. `batchJobLogs` の構造と Firestore Console での読み方

### 4-1. コレクション構造

- 親: `batchJobLogs/{jobKey}`
- 子: `batchJobLogs/{jobKey}/executions/{executionId}`

### 4-2. 親ドキュメントで見ること

親ドキュメントには、次のようなサマリが入ります。

- `lastExecutedAt`
- `lastStatus`
- `lastJudgment`
- `recentResults`
- `recentNgCount`
- `recentFailureCount`
- `totalCount`
- `updatedAt`

日常運用では、まず親ドキュメントを見て直近結果が `ok` か、`warning` / `ng` が続いていないかを確認します。

### 4-3. `executions` サブコレクションで見ること

各実行明細には次が入ります。

- `executionId`
- `triggeredBy`
- `targetDate` または `targetMonth`
- `executedAt`
- `durationMs`
- `status`
- `judgment`
- `failedChecks`
- `errorMessage`
- `details`

調査時は、直近の `executions` を開いて `failedChecks` と `details` を読むのが基本です。

## 5. Flutter 管理画面からの手動実行手順

対象画面は `詳細設定` です。

### 5-1. 事前準備

1. 管理者権限のある端末でアプリに入ります。
2. `詳細設定` を開きます。
3. 画面内の `整合性チェック` セクションまでスクロールします。

### 5-2. 日次チェック

1. `対象日（日次用）` を選びます。
2. `Analytics 日次チェック` または `Reporting 日次チェック` を押します。
3. 実行中は `Analytics 日次 実行中...`、`Reporting 日次 実行中...` が表示されます。
4. 完了後、SnackBar に `ok` / `warning` / `ng` が表示されます。

### 5-3. 月次チェック

1. `対象月（月次用）` を選びます。
2. `Analytics 月次チェック` または `Reporting 月次チェック` を押します。
3. 実行中は `Analytics 月次 実行中...`、`Reporting 月次 実行中...` が表示されます。
4. 完了後、SnackBar に `ok` / `warning` / `ng` が表示されます。

## 6. 結果の読み方

| 表示 | 意味 | 基本判断 |
|---|---|---|
| `ok` | 想定どおり。主要な不一致なし | 記録だけ確認して終了 |
| `warning` | 軽微な差分、初回実行、遡及変更の可能性 | 直近履歴と `details` を確認 |
| `ng` | 目立つ不一致あり | Firestore と Cloud Logging で原因調査 |

## 7. 現在の手動運用フロー

現在の実装では、整合性チェックは管理画面から手動実行できます。運用としては次の流れが安全です。

1. 障害報告または数字の違和感が出たら、対象日・対象月を決めます。
2. `analyticsDailyCheck` または `reportingDailyCheck` を先に実行します。
3. 月単位の疑いがある場合は `analyticsMonthlyCheck` または `reportingMonthlyCheck` を実行します。
4. `reportingMonthly` 側のズレであれば `rebuildReportingMonthlyCallable` の対象月を決めます。
5. 実行後は `batchJobLogs` に結果が保存されるので、再実行時は前回との差分も追えます。

## 8. Phase 2（スケジューラー統合）の予定

仕様書では、これら4つのチェックを将来的にスケジューラーへ統合する Phase 2 が想定されています。

- `analyticsDailyCheck` / `reportingDailyCheck`: 毎日 JST 05:05
- `analyticsMonthlyCheck` / `reportingMonthlyCheck`: 毎月2日 JST 05:10

ただし、現時点の運用上は「実装済みの callable を管理画面から手動実行する」が基本です。スケジューラー統合後も、障害調査や再確認のために手動実行は残しておく想定です。

## 9. 保守担当が押さえるべき補足

1. analytics は `businessDate` 基準、reporting は `settledAt` / `eventAt` 基準です。
2. `reportingDailyCheck` は bill 側の `closedAt` を参照します。
3. `reportingMonthlyCheck` は `reportingEntries` と `reportingMonthly/{YYYYMM}` の両方を見ます。
4. `batchJobLogs` への書き込みが失敗しても、各 callable 自体の主処理が終わっていることがあります。Cloud Logging も必ず確認してください。
