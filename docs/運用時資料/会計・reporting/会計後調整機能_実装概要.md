# 会計後調整機能 実装概要

## 1. 機能の全体概要

会計後調整機能は、いったん会計完了した伝票に対して、あとから差額補正や再会計を行うための基盤です。現行実装では、次ができます。

- 即時返金: `decrease_refunded`
- 即時追加徴収: `increase_collected`
- 後続返金待ち: `decrease_refund_pending`
- 後続追加徴収待ち: `increase_collection_pending`
- 後続返金 / 後続徴収の cashAction 記録
- reopen による再会計

この機能が必要な理由は、現場で会計完了後に差額が見つかった場合でも、伝票履歴を壊さずに補正できるようにするためです。

## 2. 関係する Firestore コレクション一覧と役割

| パス | 役割 |
|---|---|
| `bills/{billId}` | 親伝票。現時点の `status`、`currentSummary`、`postSettlementState`、`reopenSummary`、`settlementSnapshot` を持つ |

## 4. データフロー

### 4-1. 通常 settle / resettle

1. Flutter が `completeAccountingV2` を呼びます。
2. 親 `bills/{billId}` の `status` が `settled` になります。
3. trigger `billsOnSettle` が動きます。
4. `amounts`、`categoryBreakdown`、`paymentTotals`、`currentSummary`、`settlementSnapshot` を親へ書き戻します。
5. `settlementCycles/{cycleNo}` を `settled` にし、`baselineSnapshot/snapshot` を作ります。
6. `settlementAggregatorEnabled = true` なら `analyticsMonthly` を更新します。
7. `reportingAggregatorEnabled = true` なら `buildSettleEntry` → `writeReportingEntry` → `applyEntryToReportingMonthly` を実行します。

### 4-2. 会計後 adjustment

1. Flutter が `createPostSettlementAdjustment` を呼びます。
2. `adjustments/{adjustmentId}` が作られます。
3. 親 `currentSummary`、`postSettlementState`、status を更新します。
4. 即時系の場合は同じ transaction 内で `cashActions/{cashActionId}` も作ります。
5. analytics は adjustment delta を反映します。
6. reporting は pending adjustment 単体では直接積まず、即時 cashAction がある場合、または後続 cashAction 実行時に `cashAction` entry を積みます。

### 4-3. 後続徴収 / 後続返金

1. Flutter が `recordPostSettlementCollection` または `recordPostSettlementRefund` を呼びます。
2. `cashActions/{cashActionId}` を作ります。
3. 対象 adjustment の `requiredActionRemainingIncl` を減らし、0 なら `completed_by_cash_action` にします。
4. 親 `currentSummary`、`postSettlementState`、status を更新します。
5. analytics は collection のみ `paymentTotals` を更新します。refund は `paymentTotals` を直接減らしません。
6. reporting は `buildCashActionEntry` で `reportingEntries` と `reportingMonthly` を更新します。

### 4-4. reopen

1. Flutter が `reopenAccountedBill` を呼びます。
2. 旧 cycle を `reopened` にし、`effective` adjustment を `cancelled_by_reopen` にします。
3. 親 `bills/{billId}` を open 状態へ戻します。
4. `activeStays/{userId}` を復元します。
5. 新しい `settlementCycles/{newCycleNo}` を `open` で作ります。
6. analytics は旧 cycle の settle / adjustment / collection を負号で rollback します。
7. reporting は `reopen_rollback` entry を作り、元月へ逆符号反映します。

## 5. 冪等性の仕組み

### 5-1. settle trigger の冪等性

- `billsOnSettle` は `meta.contentHash` を使います。
- 既存 `meta.contentHash` と今回計算した内容が一致すると `contentHash matches, skipping update` で終了します。
- これにより、同じ内容の二重 settle 反映を防ぎます。

### 5-2. analytics の冪等性

- `analyticsMonthly/{YYYY-MM}/aggregationMarkers` を使います。
- marker 例:
  - `{billId}_cycle{cycleNo}_settle`
  - `adj_{adjustmentId}`
  - `cash_{cashActionId}`
  - `reopen_{billId}_cycle{oldCycleNo}`
- marker が既に存在すれば、その反映は skip します。

### 5-3. reporting の冪等性

- `reportingEntries/{entryId}` は `create` で書き込みます。
- 既にある entryId を再作成しようとすると、`entryWriter` が `written: false` を返します。
- `reportingMonthly/{YYYYMM}/aggregationMarkers/entries_{entryId}` でも月次反映の二重実行を防ぎます。

### 5-4. callable リクエスト単位の冪等性

- `createPostSettlementAdjustment` などの callable は `bills/{billId}/idempotency/{requestKey}` を使います。
- 同じ `idempotencyKey` での再送時は、既存結果を再利用します。

## 6. 保守時の注意点

### 6-1. `closedAt` と `settledAt` の違い

- 親 `bills/{billId}` では会計完了時刻を主に `closedAt` として参照します。
- `settlementCycles/{cycleNo}` では `settledAt` を持ちます。
- `reportingDailyCheck` は bill 親の `closedAt` を使って件数照合します。
- そのため、日次 reporting の調査では `settledAt` ではなく `closedAt` を先に見ます。

### 6-2. `reportingAggregatorEnabled` の確認を忘れない

- reporting が書かれないとき、最初に見るべき設定は `storeMeta/config.features.reportingAggregatorEnabled` です。
- analytics の ON/OFF は別フラグ `settlementAggregatorEnabled` です。
- どちらか片方だけ OFF でも、会計本体は成功して見えるため、障害切り分け時に見落としやすいです。

### 6-3. `taxReportingBehavior` を変えたら再集計が必要

- `storeMeta/taxReportingBehavior` を変更すると、新規に作られる `reportingEntries` の月帰属が変わります。
- 既存 `reportingMonthly` は自動で作り直されません。
- 変更後は必ず対象月以降に対して `rebuildReportingMonthlyCallable` を実行してください。

### 6-4. pending adjustment は analytics と reporting で扱いが違う

- analytics は pending adjustment の時点で売上差分を積みます。
- reporting は `pendingAdjustmentTiming = onCashAction` のため、原則 cashAction 実行時に entry 化します。
- analytics と reporting の数字が一時的にずれることがあるのは、この設計差が原因です。

### 6-5. 旧導線は保守対象外

- 旧 UI は `lib/to_be_deleted/` に移されています。
- 旧 Functions は `functions/src/unused_function_lib` へ退避されています。
- 不具合調査時は、現行の `会計後操作` / `要対応の会計` / `会計管理` 導線だけを見てください。
