# 07 通知仕様

> **用語は README.md の定義に従う。**  
> このファイルは中央管理アプリがエラー・scheduler 異常を検知したとき「どこへ・何を・どのように通知するか」の仕様書。

---

## 1. 通知チャンネル

| チャンネル | 識別子 | 実装方法 |
|---------|:----:|---------|
| LINE | `'line'` | LINE Messaging API（Bot アカウント経由）|
| メール | `'email'` | SendGrid または Firebase Extensions の `Trigger Email`（推奨）|

### LINE 通知の前提
- 中央管理アプリ用の **LINE Bot アカウント**（LINE Official Account）を別途作成する
- 通知先の LINE ユーザー / グループは、Bot を友だち追加または Bot が参加しているグループである必要がある
- LINE Channel Access Token を中央プロジェクトの Secret Manager または Firebase Environment Variables に保存する

### メール通知の前提
- SendGrid の API キーを中央プロジェクトの Secret Manager に保存する
- または Firebase Extensions の `Trigger Email` を使うと実装が最小限になる

## 2. 通知トリガー

### 2-1. エラー通知（リアルタイム）

**トリガー**: 中央 Firestore の `errorLogs/{storeId}/logs/{logId}` に重要度判定結果（`importance`, `shouldNotify`）が書き込まれたとき。

**フロー**:
1. Firestore onWrite トリガーが `shouldNotify: true` を検知
2. `notificationTargets` を読み込み、条件に一致する通知先を選択
3. デバウンスチェック（同一 `(storeId, functionEntry, errorKey)` で 10 分以内の重複送信を防ぐ）
4. 通知を送信

**デバウンスチェックの実装**:

```typescript
const debounceKey = `${storeId}__${functionEntry}__${errorKey ?? 'unknown'}`;
const debounceDoc = db.collection('_notificationDebounce').doc(debounceKey);

const snapshot = await debounceDoc.get();
if (snapshot.exists) {
  // デバウンス中 → 通知しない
  return;
}

// デバウンスレコードを書き込み（10分後に TTL で自動削除）
const expireAt = new Date(Date.now() + 10 * 60 * 1000);
await debounceDoc.set({ createdAt: FieldValue.serverTimestamp(), expireAt });
```

### 2-2. Scheduler 異常通知

**トリガー**: 中央 Functions の検知バッチ（毎時）が `schedulerAnomalies` にドキュメントを書き込んだとき、  
または `schedulerAnomalies/{storeId}/alerts/{alertId}` への onWrite トリガー。

**フロー**:
1. 異常ドキュメントの `notified: false` を確認
2. `notificationTargets` で `notifyOnSchedulerAnomaly: true` の通知先を選択
3. 通知を送信
4. `notified: true` に更新（再通知防止）

## 4. 通知先の管理 UI 仕様

### 通知先一覧画面

| 表示項目 | 説明 |
|---------|------|
| 通知先名 | `displayName` |
| チャンネル | LINE / メールのアイコン |
| 送信先 | LINE: userId / groupId の末尾4文字マスク / メール: メールアドレス |
| 通知する重要度 | `notifyOnImportance`（例: 3, 5）|
| Scheduler 異常 | `notifyOnSchedulerAnomaly`（チェックマーク）|
| 対象店舗 | 全店舗 or 絞り込み済み |
| 有効/無効 | `enabled`（トグル）|
| 操作 | 編集・削除・テスト送信 |

### テスト送信

「テスト送信」ボタンを押すと、その通知先にダミーの通知を送信する。  
送信結果（成功/失敗）を UI に表示する。

### LINE 通知先の追加フロー

1. 管理者が LINE Bot を友だち追加（または Bot をグループに招待）
2. Bot に話しかけて userId / groupId を確認する（Bot 側でエコーバックする仕組みを用意）
3. 管理アプリ UI に userId / groupId を入力して通知先として登録

## 5. LINE Bot の実装

### 最小実装

中央プロジェクトに Webhook 用の Cloud Functions を追加:

```typescript
// LINE Webhook Handler
export const lineWebhook = onRequest(async (req, res) => {
  const events = req.body.events;
  for (const event of events) {
    if (event.type === 'message') {
      // ユーザーが Bot にメッセージを送ったとき userId を返す
      const userId = event.source.userId;
      const groupId = event.source.groupId;
      const replyToken = event.replyToken;

      const idInfo = groupId
        ? `グループID: ${groupId}`
        : `ユーザーID: ${userId}`;

      await lineClient.replyMessage(replyToken, {
        type: 'text',
        text: `通知先登録用ID:\n${idInfo}`,
      });
    }
  }
  res.status(200).send('OK');
});
```

### 通知送信

```typescript
async function sendLineNotification(
  destination: string, // userId または groupId
  message: string
): Promise<void> {
  const accessToken = process.env.LINE_CHANNEL_ACCESS_TOKEN;
  await fetch('https://api.line.me/v2/bot/message/push', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'Authorization': `Bearer ${accessToken}`,
    },
    body: JSON.stringify({
      to: destination,
      messages: [{ type: 'text', text: message }],
    }),
  });
}
```

## 6. 通知失敗時の挙動

- 通知送信が失敗した場合は Cloud Logging にエラーを記録する（`logOpsError` で記録）
- リトライは **しない**（通知の遅延よりも重複通知の回避を優先）
- デバウンスレコードは通知失敗時も維持する（10 分後に再度同じエラーが来れば再通知される）

## 7. 通知量の上限（コスト管理）

LINE Messaging API の無料枠（月 200 通）を超えないよう管理する。

| プラン | 無料枠 | 超過時 |
|-------|:------:|-------|
| LINE Messaging API（無料）| 200 通/月 | 従量課金 |
| LINE Messaging API（軽量）| 500 通/月 | 月 ¥5,000〜 |

### 通知量の見積もり

- 1 店舗あたり 1 日 1〜3 件のエラー通知（重要度 3 以上）
- デバウンスにより同一エラーの重複を 10 分以内で抑制
- 100 店舗 × 2 件/日 × 30 日 = 6,000 通/月

→ **無料枠は超えるため LINE の有料プランまたはメール通知を主とする設計を推奨**

## 8. 通知優先度設計

**推奨構成**:

| 通知先 | チャンネル | 重要度 | Scheduler 異常 |
|-------|----------|:------:|:-------------:|
| 運用グループ LINE | LINE | 5 のみ | ✅ |
| エラー通知メール | メール | 3, 5 | ✅ |

- 重要度 5 のみ LINE に送る（LINE 通知量を抑制）
- 重要度 3 以上はメールにも送る（完全な記録を残す）
- Scheduler 異常は LINE とメール両方に送る
