---

## 1. システム全体の構成

### 1.1 プロジェクト一覧

| 名称 | Firebase Project ID | 役割 | 数 |
|------|---------------------|------|----|
| **店舗プロジェクト** | 例: `amuse-app-template`, `amuse-store-shibuya`, ... | 店舗の業務データ・Functions を保持 | 店舗数分（最大 500）|
| **中央プロジェクト** | `amuse-central-monitoring` | ログ集約・管理アプリ・通知 | 1 つ |

### 1.2 中央プロジェクトが持つリソース

| リソース | 内容 |
|---------|------|
| **中央 Firestore** | エラーログ・scheduler ログ・タスクログ・重要度ルール・通知設定・店舗マスタ |
| **Firebase Hosting** | 中央管理アプリ（Next.js）のホスティング先 |
| **Cloud Functions** | 通知送信 handler（エラー検知 → LINE / メール）・scheduler 健全性判定バッチ |
| **Firebase Auth** | 中央管理アプリへのログイン（Google 認証） |
| **tenant-errors ログバケット** | 全店舗の severity >= ERROR ログが sink で集約される（既存）。保全・深堀り調査用。管理アプリの主データソースは中央 Firestore |

## 2. データの流れ

### 2.1 エラーログ

```
[店舗プロジェクト]
  Cloud Functions 内 logOpsError() 呼び出し
       │
       ├──► Cloud Logging（店舗プロジェクト側）
       │         │
       │         └──sink──► tenant-errors バケット（中央プロジェクト）← 保全・深堀り用
       │
       └──► 中央 Firestore: errorLogs/{storeId}/logs/{autoId}  ← 管理アプリ用（best-effort）
```

**best-effort の意味**: 中央 Firestore への書き込みが失敗しても、店舗の本処理には影響しない。silent fail。

### 2.2 Scheduler ログ（supervisor → dispatch → handler 完了連鎖）

```
[店舗プロジェクト]
  Cloud Scheduler（毎日 03:00 JST）
    → schedulerSupervisor（Cloud Functions）
        │
        ├──► 店舗 Firestore: schedulerDispatchLogs/{autoId}  ← 既存（各 job の enqueue/skip 記録）
        │
        └──► Cloud Tasks: scheduled-job-* キュー（6 job）
               → executeScheduledJobTask（Cloud Functions）
                   │
                   ├──► 店舗 Firestore: schedulerExecutionLogsByCloudTask/{autoId} ← 既存（started/completed）
                   │
                   └──► 中央 Firestore: schedulerLogs/{storeId}/runs/{autoId}  ← 新規（管理アプリ用）
```

### 2.3 タスクログ（downstream Cloud Tasks）

```
[店舗プロジェクト]
  Cloud Tasks（business-date-assessment-queue / tournament-queue 等）
    → 各 handler（openAssessmentTask / closeAssessmentTask / controlHookHttp 等）
        │
        └──► 中央 Firestore: taskLogs/{storeId}/runs/{autoId}  ← 新規（管理アプリ用）
```

## 3. 中央管理アプリの立ち位置

### 3.1 何者か

- **使用者**: 開発者・保守担当者（店舗オーナーや店舗スタッフは使わない）
- **アクセス方法**: PC ブラウザ経由の Web アプリ（Firebase Hosting でホスト）
- **認証**: Google ログイン（Firebase Auth）+ 許可メールアドレスの whitelist
- **接続先 Firebase**: 中央プロジェクト（`amuse-central-monitoring`）のみ

### 3.2 何をするか

| 機能カテゴリ | 内容 |
|-----------|------|
| **エラー監視** | 全店舗・または特定店舗のエラーを一覧表示。重要度フィルターで「見るべきエラー」を絞り込む |
| **scheduler 監視** | 各店舗の daily/weekly job が正常完了しているか確認。未完了・未実行を検知 |
| **task 監視** | downstream task（assessment, tournament 等）の到達・完了を確認 |
| **通知** | 重要エラー検知・scheduler 未実行検知時に LINE / メールへ通知 |
| **対応管理** | エラーに対応済みフラグ・メモを付けて管理 |
| **店舗管理** | 監視対象の店舗を登録・管理 |

### 3.3 何をしないか

- 店舗 Firestore の業務データを直接操作しない
- 店舗用アプリの Flutter コードを管理しない
- 給与・会計など業務ロジックには関与しない

## 4. 各プロジェクト間の認証・権限

### 4.1 店舗プロジェクト → 中央 Firestore への書き込み

- **主体**: 各店舗プロジェクトの Cloud Functions 実行 SA
  - SA メールアドレス: `firebase-adminsdk-xxxxx@{storeProjectId}.iam.gserviceaccount.com`
- **付与する権限**: 中央プロジェクトの Firestore への `datastore.documents.write`（または `roles/datastore.user`）
- **付与先**: 中央プロジェクトの IAM で、各店舗 SA に権限を追加
- **付与タイミング**: 店舗プロジェクト追加時（`docs/運用時資料/導入時設定/` の手順に追加）

### 4.2 中央管理アプリ → 中央 Firestore の読み取り

- **主体**: Firebase Auth でログインしたユーザー（許可メールアドレスのみ）
- **方法**: Firestore セキュリティルール（管理者 UID のみ読み書き可）

### 4.3 中央管理アプリ → 店舗 Firestore

- **読み取りしない**: 管理アプリは中央 Firestore のみ参照する。店舗 Firestore を直接読まない。
- 理由: 500 店舗 × Firestore は IAM 管理コストが高い。中央 Firestore への集約で解決する。

## 5. 技術スタック

### 5.1 中央管理アプリ（新規リポジトリ: `amuse-admin`）

| 要素 | 採用技術 | 理由 |
|------|---------|------|
| フレームワーク | **Next.js（App Router）** | Web ダッシュボード向け、AI 実装効率、豊富な UI ライブラリ |
| スタイリング | **Tailwind CSS + shadcn/ui** | 高品質な管理 UI を最小コストで構築可能 |
| Firebase | Firebase JS SDK v10（modular） | 中央 Firestore / Auth に接続 |
| ホスティング | **Firebase Hosting**（中央プロジェクト） | 既存インフラ活用 |
| サーバーサイド | Next.js API Routes（必要に応じて） | 通知送信等の秘匿処理 |
| 言語 | TypeScript | 型安全、既存 Functions との型共有可能 |

### 5.2 店舗用アプリ（既存リポジトリ: `amuse_app_template`）

| 要素 | 技術 |
|------|------|
| モバイルアプリ | Flutter（iOS / Android / Web 対応） |
| バックエンド | Cloud Functions for Firebase（TypeScript） |
| DB | Firestore（店舗プロジェクト内） |
| スケジューラー | Cloud Scheduler → Cloud Tasks（`asia-northeast1`）|
| ログ | Cloud Logging（`logOpsError` / `logOpsInfo` / `logOpsSuccess`）|

## 6. Cloud Tasks / Scheduler の構成（店舗側の現状）

中央管理アプリが監視する対象を理解するため、店舗側の構成を記載する。

### 6.1 Cloud Scheduler

| job 名 | スケジュール | 役割 |
|--------|------------|------|
| `schedulerSupervisor` | 毎日 03:00 JST | 6 つの scheduled job を Cloud Tasks キューに投入する「親」|

### 6.2 Scheduled Job（Cloud Tasks キュー: `scheduled-job-*`）

| jobKey | スケジュール種別 | 実行タイミング | 役割 |
|--------|--------------|-------------|------|
| `weeklyPlanner` | weekly | 木曜 04:40 JST | 翌週の営業日・シフト計画を生成。assessment キューへ downstream |
| `enqueueTournamentTasksByScheduler` | daily | 毎日 04:00 JST | トーナメントタスクを tournament キューへ投入 |
| `generateRecurringTournamentsByScheduler` | weekly | 木曜 04:20 JST | 定期トーナメントの自動生成 |
| `scheduledCleanup` | daily | 毎日 05:00 JST | 期限切れデータの削除・クリーンアップ |
| `scheduleGenerateNextYearBusinessHours` | yearly | 1/29 | 翌年の営業時間スロットを生成 |
| `payrollNotificationScheduler` | daily | 毎日 10:00 JST | 給与通知タスクを processPayrollNotifications キューへ投入 |

### 6.3 Downstream Cloud Tasks キュー

| キュー名 | 主な投入元 | handler |
|---------|---------|---------|
| `business-date-assessment-queue` | weeklyPlanner, continueBusinessTerminal 等 | openAssessmentTask, closeAssessmentTask |
| `tournament-queue` | enqueueTournamentTasksByScheduler 等 | controlHookHttp |
| `processPayrollNotifications` キュー | payrollNotificationScheduler | processPayrollNotifications |
| `processStaffPayroll` キュー | 給与計算トリガー | processStaffPayroll → finalizePayrollRun |

### 6.4 Firestore ログコレクション（店舗プロジェクト内）

中央管理アプリは**これらを直接読まない**。中央 Firestore への集約データを参照する。

| コレクション | 記録内容 |
|------------|--------|
| `schedulerDispatchLogs` | supervisor による各 job の enqueue / skip 記録 |
| `schedulerExecutionLogsByCloudTask` | 各 job の started / completed / skip / error |

## 7. ログの 3 層構造（店舗側）

```
層 A: Cloud Scheduler
  schedulerSupervisor の start / success（logOpsInfo / logOpsSuccess）
  → "supervisor が仕事を振れたか"

層 B: Dispatch（Firestore）
  schedulerDispatchLogs への書き込み
  → "各 job が enqueue / skip されたか"

層 C: Handler 到達・完了（Cloud Logging + Firestore）
  各 handler の logOpsInfo(start) → logOpsSuccess / logOpsError
  schedulerExecutionLogsByCloudTask への書き込み
  → "task が handler に届き、処理が終わったか"
```

**検知の正条件**: 層 C まで到達していること（start があり success がある）。  
A のみ・B のみは「正常」とみなさない。

---

## 8. セキュリティ境界まとめ

| 境界 | ルール |
|------|--------|
| 店舗プロジェクト → 中央 Firestore | 各店舗 SA に write 権限付与。read は不要 |
| 中央管理アプリ → 中央 Firestore | 許可された Google アカウントのみ（Firestore rules + Auth）|
| 中央管理アプリ → 店舗 Firestore | **アクセスしない** |
| 中央管理アプリ → tenant-errors | 必要に応じて Cloud Logging API 経由（深堀り調査用）。通常の監視には使わない |
