# 06 スケジューラー・タスク監視仕様

> **用語は README.md の定義に従う。**  
> このファイルは「scheduler が動いたか」「task が完了したか」を中央管理アプリが判定するロジックの仕様書。

---

## 1. 監視する対象

### 1-1. Scheduler Jobs（6 種）

`SchedulerJobKey` として定義されている 6 つのジョブが、毎日期待どおりに実行されているかを確認する。

| ジョブキー | 目的 | 実行タイミング |
|---------|------|------------|
| `weeklyPlanner` | 週次スタッフ計画の生成 | 毎週（設定した曜日）|
| `enqueueTournamentTasksByScheduler` | トーナメントタスクのキュー投入 | 毎日 |
| `generateRecurringTournamentsByScheduler` | 定期トーナメントの自動生成 | 毎日 |
| `scheduledCleanup` | 不要データの定期削除 | 毎日 |
| `scheduleGenerateNextYearBusinessHours` | 翌年営業時間の自動生成 | 毎年（年次）|
| `payrollNotificationScheduler` | 給与通知のキュー投入 | 毎日（給与締日前後）|

### 1-2. 監視しない対象（タスクログで確認のみ）

scheduler 経由ではなく、ユーザー操作やタイマーで起動する Cloud Tasks:

| handler | 起動契機 |
|--------|---------|
| `openAssessmentTask` | 店舗開店操作 |
| `closeAssessmentTask` | 店舗閉店操作 |
| `controlHookHttp` | LINE ミニアプリ等の Webhook |
| `processPayrollNotifications` | `payrollNotificationScheduler` からの enqueue |
| `processStaffPayroll` | 給与計算バッチ |
| `finalizePayrollRun` | 給与確定バッチ |

これらは「動いているか」の検知（scheduler 未実行検知）ではなく、**taskLogs から実行履歴を参照する**のみ。

## 2. Scheduler 未実行検知ロジック

### 検知の考え方

scheduler supervisor は毎日 `planningDate` を決定して各 job の Cloud Task を enqueue する。  
Cloud Task が実行されると handler に到達し、`start` → `success` の順で中央 schedulerLogs に記録される。

**「要確認」の定義**: 以下のどちらかの状態。

1. **`start` がない**: `plannedRunAt + grace` を超えても `start` イベントが記録されていない
2. **`success` がない**: `start` はあるが `plannedRunAt + success_grace` を超えても `success` が記録されていない

### grace 時間の設定

| 状態 | デフォルト grace | 説明 |
|------|:-------------:|------|
| start なし | **+2 時間** | supervisor 実行後 2 時間以内に handler が届かなければ異常 |
| success なし | **+4 時間** | start から 4 時間以内に完了しなければ異常 |

> grace 時間は将来的に job ごとに設定できるようにする（`importanceRules` と同様に Firestore で管理）。  
> 導入当初は固定値で実装する。

### 検知アルゴリズム（中央管理 Functions の定期バッチ）

```typescript
// 毎時（または毎日 1 回）実行する Cloud Scheduler ジョブ
async function detectSchedulerAnomalies(): Promise<void> {
  const today = getTodayJst(); // '2026-06-01' 等
  const enabledStores = await getEnabledStores();
  const now = new Date();

  for (const storeId of enabledStores) {
    for (const jobKey of SCHEDULER_JOB_KEYS) {
      // 今日の planningDate の schedulerLogs を取得
      const runs = await db
        .collection('schedulerLogs').doc(storeId).collection('runs')
        .where('planningDate', '==', today)
        .where('jobKey', '==', jobKey)
        .get();

      const events = runs.docs.map(d => d.data());

      // skip が正当なケース（weekly planner の非実行曜日等）
      const hasValidSkip = events.some(e => e.eventType === 'skip');
      if (hasValidSkip) continue;

      // success があれば正常
      const hasSuccess = events.some(e => e.eventType === 'success');
      if (hasSuccess) continue;

      // plannedRunAt を取得（start または dispatch ログから）
      const startEvent = events.find(e => e.eventType === 'start');
      const plannedRunAtStr = startEvent?.plannedRunAt;
      const plannedRunAt = plannedRunAtStr ? new Date(plannedRunAtStr) : null;

      if (!startEvent) {
        // start がない: plannedRunAt + 2h を過ぎているか
        if (plannedRunAt && now > addHours(plannedRunAt, 2)) {
          await flagAnomaly(storeId, jobKey, today, 'start_missing');
        }
      } else {
        // start はある: start から 4h を過ぎているか
        const startedAt = startEvent.loggedAt?.toDate() ?? now;
        if (now > addHours(startedAt, 4)) {
          await flagAnomaly(storeId, jobKey, today, 'success_missing');
        }
      }
    }
  }
}
```

### 異常フラグの保存先

検知された異常は `schedulerAnomalies/{storeId}/alerts/{autoId}` に保存する（スキーマは §3 参照）。

## 3. `schedulerAnomalies/{storeId}/alerts/{autoId}` スキーマ

| フィールド | 型 | 説明 |
|-----------|-----|------|
| `storeId` | string | 店舗 ID |
| `jobKey` | string | 異常が検知された jobKey |
| `planningDate` | string | 対象の日付（`'YYYY-MM-DD'`）|
| `anomalyType` | string | `'start_missing'` / `'success_missing'` |
| `detectedAt` | Timestamp | 検知日時 |
| `isResolved` | boolean | 対応済みフラグ |
| `resolvedAt` | Timestamp | 対応済み日時 |
| `memo` | string | 対応メモ |
| `notified` | boolean | 通知送信済みか |

## 4. 異常検知時の通知

scheduler 異常が検知されたとき、`notificationTargets` で `notifyOnSchedulerAnomaly: true` に設定された通知先に通知を送る。

### 通知タイミング
- 異常を検知したときに **1 回だけ** 通知する（繰り返さない）
- `schedulerAnomalies` ドキュメントに `notified: true` を付け、通知済みのものは再通知しない

### 通知内容（例）
```
【scheduler 異常検知】
店舗: 渋谷店 (amuse-app-template)
ジョブ: weeklyPlanner
対象日: 2026-06-01
異常種別: start_missing（handler に到達していません）
検知時刻: 2026-06-01 06:00
```

## 5. `weeklyPlanner` の特別ルール

`weeklyPlanner` は週次（毎週特定曜日）ジョブなので、実行日以外は `skip` が正常。

### skip が正常なケース
- job の `scheduleKind: 'weekly'` で `dayOfWeek` が今日でない
- job 自体が `enabled: false`（店舗側の schedulerConfig で無効化）

### 異常検知からの除外条件
- `schedulerLogs` に `eventType: 'skip'` かつ `reason: 'schedule_not_today'` が存在する → 正常な非実行日

---

## 6. `scheduleGenerateNextYearBusinessHours` の特別ルール

年次ジョブ（毎年 1 回）のため、1 日 1 回の監視では「ほぼ毎日 skip が正常」になる。

### 監視方針
- 毎日の監視では除外する（`skip` が続くのが正常）
- 実行月（通常 11〜12 月）のみ通常の scheduler 検知を有効化する
- 導入当初は**監視対象から除外**して手動確認でもよい

## 7. Task 実行履歴の確認（taskLogs の活用）

### 確認できること

管理アプリの「店舗詳細 > タスク履歴」画面から:

| 表示項目 | Firestore クエリ |
|---------|---------------|
| 特定 handler の全イベント | `taskLogs/{storeId}/runs` where `functionEntry == xxx` |
| 直近 24h のエラー | `taskLogs/{storeId}/runs` where `eventType == 'error'` and `loggedAt >= 24h ago` |
| start あり success なし（未完了）| start と success の突合（`taskId` or `context.runId` で紐付け）|

### 突合の方法

Cloud Tasks は同一 task に複数のイベントが発生する（start → success）。  
突合キーは以下の優先順で使用する:

1. `taskId`（Cloud Tasks の task name から取得可能な場合）
2. `context.idempotencyKey`
3. `context.runId`（handler がランダム ID を付与している場合）

## 8. HOME 画面向け scheduler 健全性の集計

HOME 画面では各店舗の「今日の scheduler 状態」を 1 行で表示する。

### 表示ステータスの判定ロジック

| 条件 | 表示ステータス |
|------|-------------|
| 全 job が success または valid skip | ✅ 正常 |
| 1 件以上 `schedulerAnomalies` で `isResolved: false` | ⚠️ 要確認 |
| 店舗の `enabled: false` | — 監視対象外 |

### クエリ方法

```typescript
// 今日の schedulerAnomalies を確認（店舗ごと）
const anomalies = await db
  .collection('schedulerAnomalies').doc(storeId).collection('alerts')
  .where('planningDate', '==', today)
  .where('isResolved', '==', false)
  .limit(1)
  .get();

const isAnomalous = !anomalies.empty;
```

## 9. 監視バッチ（中央管理 Functions）の設計

### 検知バッチ
- **Cloud Scheduler** から毎時または毎日特定時刻に起動
- grace 時間を過ぎた未完了 job を検知して `schedulerAnomalies` に書き込む
- 通知が未送信であれば通知を送る

### バッチ実行のタイミング

| バッチ | 実行時刻（JST）| 説明 |
|-------|:------------:|------|
| scheduler 健全性チェック | 翌 02:00 | 大半の job は夜間実行なので、翌朝の確認が適切 |
| 通知バッチ（エラー）| リアルタイム（Firestore onWrite）| errorLogs に書き込まれたら即座に判定・通知 |

> ただし start_missing の検知は「実行予定時刻 + 2h」であるため、  
> バッチを毎時実行することで最大 1h の検知遅延が発生する。これは許容範囲とする。
