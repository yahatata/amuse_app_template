> **用語は README.md の定義に従う。**

---

## 1. 店舗用アプリの構成概要

### 1.1 基本方針

- **1 店舗 = 1 Firebase プロジェクト**（= 1 GCP プロジェクト）
- 全店舗のコードベースは `amuse_app_template` リポジトリを共通テンプレートとして使用する
- **店舗ごとの差分**は、原則として `storeMeta` コレクション（Firestore）内の設定で吸収する
- コードを店舗ごとに変えない（同一 Functions を全店舗にデプロイする）

### 1.2 店舗識別子

| 識別子 | 値 | 用途 |
|--------|-----|------|
| **Firebase Project ID** | 例: `amuse-app-template`, `amuse-store-shibuya` | GCP・Firebase の全リソースの識別子 |
| **storeId** | Firebase Project ID と同一値 | Functions 内・Firestore ドキュメント内での店舗識別 |
| **tenantId** | Firebase Project ID と同一値 | Functions 内での tenant 識別（storeId と揃える）|

> `storeId` と `tenantId` はコード内では `getProjectScopedStoreTenantIdentity()` から取得し、  
> 直接 `projectId` を書き込む実装にしない。

### 1.3 技術スタック（店舗用アプリ）

| レイヤー | 技術 | 備考 |
|---------|------|------|
| モバイルアプリ | Flutter | iOS / Android 対応。Web 対応あり |
| バックエンド | Cloud Functions for Firebase v2（TypeScript） | `asia-northeast1` リージョン統一 |
| データベース | Firestore（ネイティブモード） | 店舗プロジェクト内 |
| ストレージ | Cloud Storage | 店舗プロジェクト内 |
| 認証 | Firebase Auth | LINE 連携 |
| スケジューラー | Cloud Scheduler → Cloud Tasks | `asia-northeast1` |
| Secrets | Secret Manager | LINE トークン・エンドポイント等 |
| LINE | LINE Messaging API / LIFF | スタッフ用・ユーザー用ミニアプリ |

## 2. 店舗プロジェクトの構成要素（導入時に設定が必要なもの）

### 2.1 Firebase クライアント設定（店舗ごとに異なる値）

以下のファイルは店舗ごとに生成・差し替えが必要。

| ファイル | 含まれる主な値 |
|---------|-------------|
| `lib/firebase_options.dart` | `projectId`, `appId`, `apiKey`, `authDomain`, `storageBucket`, `messagingSenderId`, `measurementId` |
| `android/app/google-services.json` | 同上（Android 向け） |
| `ios/Runner/GoogleService-Info.plist` | 同上（iOS 向け） |
| `macos/Runner/GoogleService-Info.plist` | 同上（macOS 向け） |

### 2.2 Web / LIFF 設定（店舗ごとに異なる値）

| ファイル | 含まれる主な値 |
|---------|-------------|
| `public/user/config.js` | `firebaseConfig.*`（projectId, apiKey 等）, `liffId`, `userLiffId` |
| `public/staff/config.js` | 同上 + `storeInfo.name`, `storeInfo.id` |

### 2.3 モバイルアプリ識別子（店舗ごとに異なる値）

| 対象 | 値 |
|------|-----|
| Android `applicationId` | 店舗用の一意な ID（例: `com.amuse.template`） |
| iOS/macOS `PRODUCT_BUNDLE_IDENTIFIER` | 店舗用の一意な ID |
| アプリ表示名 | 店舗名（例: 「Amuse App Template」） |

### 2.4 Secret Manager（店舗プロジェクト内）

以下の 3 つの Secret が各店舗プロジェクトに存在する。

| Secret 名 | 内容 |
|-----------|------|
| `line-config` | `channelAccessToken`, `staffRichMenuId`, `userRichMenuId` |
| `task-endpoints` | `controlHookUrl`, `closeAssessmentUrl`, `openAssessmentUrl`（デプロイ後に更新）|
| `business-secrets` | `qrSecretKey`, `unclockedAttendanceEditPassword` |

### 2.5 Cloud Tasks キュー（`asia-northeast1`）

導入時に手動作成が必要なもの（デプロイで自動作成されないもの）:

| キュー名 | 備考 |
|---------|------|
| `tournament-queue` | 手動作成必須 |
| `business-date-assessment-queue` | 手動作成必須 |

以下は Functions デプロイ時に自動作成される:

| キュー名 | 投入される job |
|---------|--------------|
| `scheduled-job-weekly-planner` | weeklyPlanner |
| `scheduled-job-enqueue-tournament-tasks-by-scheduler` | enqueueTournamentTasksByScheduler |
| `scheduled-job-generate-recurring-tournaments-by-scheduler` | generateRecurringTournamentsByScheduler |
| `scheduled-job-scheduled-cleanup` | scheduledCleanup |
| `scheduled-job-schedule-generate-next-year-business-hours` | scheduleGenerateNextYearBusinessHours |
| `scheduled-job-payroll-notification-scheduler` | payrollNotificationScheduler |
| `processStaffPayroll-queue`（推定）| 給与計算 |

### 2.6 Service Account（店舗プロジェクト内）

| SA | 役割 |
|----|------|
| `firebase-adminsdk-xxxxx@{projectId}.iam.gserviceaccount.com` | Functions 実行 SA（Cloud Logging、Firestore、Secret Manager の権限を持つ）|
| `tasks-invoker@{projectId}.iam.gserviceaccount.com` | Cloud Tasks から Cloud Run を OIDC 認証で呼び出すための SA |

### 2.7 Firestore 設定（`storeMeta` コレクション）

店舗ごとの運用差分を吸収するメイン設定。中央管理アプリは参照しないが、理解のために記載。

| ドキュメント | 主な設定値 | 用途 |
|-----------|-----------|------|
| `storeMeta/config` | `linePlan`, `features.*`, 各種業務設定 | 業務機能フラグ・設定 |
| `storeMeta/schedulerConfig` | `supervisorEnabled`, `planningHorizonDays`, `jobs.*（enabled, runAtJst 等）` | scheduler の動作設定 |

`schedulerConfig` のデフォルト値:

```
schemaVersion: 2
supervisorEnabled: true
planningHorizonDays: 7
jobs:
  weeklyPlanner:         { enabled: true, runAtJst: "04:40", scheduleKind: "weekly", dayOfWeek: 4 }
  enqueueTournamentTasksByScheduler: { enabled: true, runAtJst: "04:00", scheduleKind: "daily" }
  generateRecurringTournamentsByScheduler: { enabled: true, runAtJst: "04:20", scheduleKind: "weekly", dayOfWeek: 4 }
  scheduledCleanup:      { enabled: true, runAtJst: "05:00", scheduleKind: "daily" }
  scheduleGenerateNextYearBusinessHours: { enabled: true, runAtJst: "00:00", scheduleKind: "yearly", month: 1, dayOfMonth: 29 }
  payrollNotificationScheduler: { enabled: true, runAtJst: "10:00", scheduleKind: "daily" }
```

## 3. 店舗プロジェクト追加の全体フロー

新規店舗を追加する際の作業一覧。詳細手順は `docs/運用時資料/導入時設定/` を参照。

| No | 作業 | 場所 | 完了条件 |
|----|------|------|---------|
| 1 | Firebase Project ID を決定 | 運用判断 | 命名規則に沿った一意な ID が確定 |
| 2 | 必須 GCP API を有効化 | GCP コンソール / CLI | Functions, Tasks, Scheduler, SecretManager 等 |
| 3 | デプロイ用 SA と WIF を設定 | GCP + GitHub | GitHub Actions から deploy できる |
| 4 | Secret Manager に 3 つの Secret を作成 | GCP CLI | `line-config`, `task-endpoints`, `business-secrets` |
| 5 | Secret 参照権限を実行 SA に付与 | GCP CLI | `secretAccessor` |
| 6 | Cloud Tasks queue を作成 | GCP CLI | `tournament-queue`, `business-date-assessment-queue` |
| 7 | Flutter アプリの Firebase 設定を生成・配置 | flutterfire CLI | `firebase_options.dart` 等 |
| 8 | Web / LIFF config.js を更新 | 手動 | Firebase Web 設定・LIFF ID・店舗名 |
| 9 | Functions をデプロイ | GitHub Actions | 対象関数が `asia-northeast1` で ACTIVE |
| 10 | `task-endpoints` を更新 | GCP CLI | 3 URL がデプロイ後の実体 URL |
| 11 | OIDC 用 SA と `run.invoker` を設定 | GCP CLI | `tasks-invoker` が Cloud Run を呼べる |
| 12 | **中央プロジェクトの IAM に店舗 SA を追加（新規）** | GCP CLI | 店舗 SA が中央 Firestore に write できる |
| 13 | **中央管理アプリの店舗レジストリに登録（新規）** | 管理アプリ UI | `stores/{storeId}` ドキュメントが作成される |
| 14 | リリース後確認 | GCP + 実機 | task 実行・主要機能が正常 |

> **No.12・13 は中央管理アプリ導入後に追加される手順**  
> 詳細は `04_店舗アプリ側変更点.md` §4 を参照。

## 4. 店舗レジストリ（中央 Firestore）

### 4.1 目的

中央管理アプリが監視対象の店舗を把握するための「店舗マスタ」。  
手動登録（管理アプリの UI または Firestore コンソール直接）が基本。

### 4.2 スキーマ

コレクション: `stores`  
ドキュメント ID: `{storeId}`（= Firebase Project ID）

| フィールド名 | 型 | 必須 | 説明 |
|------------|-----|------|------|
| `storeId` | string | ✅ | Firebase Project ID（= ドキュメント ID と同値。冗長だが検索用）|
| `displayName` | string | ✅ | 表示用店舗名（例: 「渋谷店」「銀座店」）|
| `projectId` | string | ✅ | Firebase Project ID（`storeId` と同値。明示的に持つ）|
| `region` | string | ✅ | Functions のリージョン。原則 `asia-northeast1` |
| `enabled` | boolean | ✅ | false にすると監視・通知の対象から除外される |
| `addedAt` | Timestamp | ✅ | 登録日時（サーバー時刻）|
| `updatedAt` | Timestamp | — | 最終更新日時 |
| `note` | string | — | 運用メモ（一時休業中、移行中等）|
| `functionsVersion` | string | — | デプロイ済み Functions のバージョン識別子（後述 §4.3）|

### 4.3 functionsVersion について

どの店舗がどのバージョンの Functions を動かしているかを管理するための任意フィールド。  
店舗用アプリのデプロイ時に更新する運用を推奨する（詳細は `10_更新・リリース方針.md`）。

## 5. 店舗の有効化・無効化

`enabled` フィールドで制御する。

| `enabled` | 挙動 |
|-----------|------|
| `true` | 通常どおり監視・通知の対象 |
| `false` | エラーログや scheduler ログは中央 Firestore に書き込まれるが、通知・HOME 表示の対象から除外される |

**使用場面の例:**
- 一時休業中の店舗
- 新規導入中でテスト期間の店舗（誤通知を避けたい）
- 閉店した店舗（過去データは残すが監視はしない）

## 6. 全店舗横断での確認が必要な場合

中央管理アプリは中央 Firestore のみを参照するため、  
以下のシナリオでは別途 GCP コンソール / gcloud CLI での確認が必要。

| シナリオ | 参照先 |
|---------|--------|
| プラットフォームエラー（OOM, timeout 等）の調査 | `tenant-errors` バケット（Cloud Logging Explorer）|
| 各店舗の Cloud Tasks キュー積み状況 | GCP Console > Cloud Tasks（各店舗プロジェクト）|
| Functions のデプロイ状況 | GCP Console > Cloud Functions（各店舗プロジェクト）|
