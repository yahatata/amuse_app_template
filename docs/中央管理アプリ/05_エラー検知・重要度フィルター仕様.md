# 05 エラー検知・重要度フィルター仕様

> **用語は README.md の定義に従う。**  
> このファイルは中央管理アプリが「どのエラーを検知すべきか」「どの重要度か」を判定するロジックの仕様書。

---

## 1. 全体フロー

```
店舗 Functions
  └─ logOpsError 呼び出し
      └─ (best-effort) 中央 Firestore に errorLogs 書き込み
                                    │
                                    ▼
                     中央管理アプリ / 中央 Functions
                       ├─ Firestore onWrite トリガー (or 定期バッチ)
                       │    └─ importanceRules を読み込み
                       │    └─ 重要度を算出 → errorLogs に importance フィールドを付与
                       │    └─ importance >= しきい値 なら notificationTargets を読み込み
                       │         └─ LINE / メール送信
                       │
                       └─ 管理アプリ UI
                            ├─ HOME: 店舗別・エラー件数（importance フィルター後）
                            └─ 店舗詳細: エラー一覧（自由フィルター）
```

## 2. 重要度判定ロジック

### 判定タイミング
新しい `errorLogs` ドキュメントが書き込まれたとき（Firestore onWrite トリガー）。

### 判定アルゴリズム

1. `importanceRules` コレクションを全件読み込む（`isActive: true` のものだけ）
2. エラーログの各フィールドを各ルールの `conditions` と照合する
3. マッチするルールのうち **最大の `importance` を採用する**（複数ルールがマッチした場合）
4. どのルールにもマッチしない場合は `importance: 0`（≒ 検知なし）

### 条件マッチングの詳細

`conditions` の各フィールドは AND 条件。**1 フィールドでも不一致なら非マッチ**。

```typescript
function matchesRule(
  errorLog: ErrorLog,
  conditions: ImportanceRuleConditions
): boolean {
  if (conditions.service && errorLog.service !== conditions.service) return false;
  if (conditions.functionEntry && errorLog.functionEntry !== conditions.functionEntry) return false;
  if (conditions.errorSource && errorLog.errorSource !== conditions.errorSource) return false;
  if (conditions.errorKey && errorLog.errorKey !== conditions.errorKey) return false;
  if (conditions.sourceProduct && errorLog.sourceProduct !== conditions.sourceProduct) return false;
  if (conditions.sdkCode && errorLog.sdkCode !== conditions.sdkCode) return false;
  if (conditions.httpStatus !== undefined && errorLog.httpStatus !== conditions.httpStatus) return false;
  if (conditions.httpStatusMin !== undefined) {
    const status = typeof errorLog.httpStatus === 'number'
      ? errorLog.httpStatus
      : parseInt(String(errorLog.httpStatus), 10);
    if (isNaN(status) || status < conditions.httpStatusMin) return false;
  }
  return true;
}

function calcImportance(errorLog: ErrorLog, rules: ImportanceRule[]): number {
  let maxImportance = 0;
  for (const rule of rules) {
    if (!rule.isActive) continue;
    if (matchesRule(errorLog, rule.conditions)) {
      maxImportance = Math.max(maxImportance, rule.importance);
    }
  }
  return maxImportance;
}
```

### 判定結果の保存

重要度判定が完了したら、`errorLogs/{storeId}/logs/{logId}` のドキュメントに以下のフィールドを追加書き込みする（merge）:

```typescript
{
  importance: 5,          // 0 / 1 / 3 / 5
  importanceCalcAt: serverTimestamp(),
  matchedRuleIds: ['accounting-all'], // マッチしたルールの ID 一覧（デバッグ用）
  shouldNotify: true,     // importance >= 通知しきい値 かどうか（通知判定に使う）
}
```

## 3. 通知しきい値（デフォルト）

| importance | 意味 | デフォルト通知 |
|:----------:|------|:------------:|
| 5 | 主要業務の実行不能・金額不整合リスク | ✅ 通知する |
| 3 | 業務に支障はあるが重大ではない | ✅ 通知する（変更可）|
| 1 | 業務影響が限定的 | ❌ 通知しない |
| 0 | ルール未マッチ（重要度未定義）| ❌ 通知しない |

通知しきい値は `notificationTargets` の `notifyOnImportance` フィールドで通知先ごとに設定する（`03_中央Firestoreスキーマ.md` §6 参照）。

## 4. importanceRules のキャッシュ方針

`importanceRules` は頻繁に書き込まれないが、重要度判定のたびに全件読むのは非効率。

### キャッシュ方針

#### Option A: Firestore onSnapshot（推奨）
中央管理 Functions が起動時に `importanceRules` を `onSnapshot` で購読し、インメモリにキャッシュする。  
ルールが更新されると自動的にキャッシュが更新される。  
Functions のコールドスタートは別途考慮（起動時に一度 `get()` する）。

#### Option B: バッチ判定
`errorLogs` への onWrite トリガーで毎回 `importanceRules` を全件 `get()` する。  
実装が単純で確実。判定頻度が低い（ERROR は多くて 10〜100 件/日/店舗）なら現実的。

**導入当初は Option B を採用**し、パフォーマンス問題が発生したら Option A に切り替える。

## 5. 対応管理（isResolved / memo）

### 対応済みフラグ付け

管理アプリ UI のエラー一覧から「対応済み」にすると:

1. `errorLogs/{storeId}/logs/{logId}` の以下のフィールドを更新:
   ```typescript
   {
     isResolved: true,
     resolvedAt: serverTimestamp(),
     resolvedBy: 'operator@example.com', // ログイン中の管理者メール
   }
   ```
2. `auditLogs` に操作記録を追加（`action: 'resolve'`）

### メモ追加

管理アプリ UI のエラー詳細画面からメモを追加・編集すると:

1. `errorLogs/{storeId}/logs/{logId}` の `memo` フィールドを更新
2. `auditLogs` に操作記録を追加（`action: 'memo_update'`）

### 担当者アサイン

管理アプリ UI からアサインすると:

1. `errorLogs/{storeId}/logs/{logId}` の `assignedTo` フィールドを更新
2. `auditLogs` に操作記録を追加（`action: 'assign'`）

## 6. 重要度フィルターのライフサイクル

### 導入当初（安定化前）

- **広めに検知**: 全ドメインで importance >= 1 のエラーを通知対象とする
- 初期ルールセット（`03_中央Firestoreスキーマ.md` §5 参照）を設定する
- 誤検知が多い場合: ルールの `isActive` を false にするか、`importance` を下げる

### 運用が安定してきたら

- 繰り返し発生するが問題ない（または自動回復する）エラーを特定する
- そのエラーの条件（`functionEntry`, `errorKey`, `sdkCode` 等）に合わせて `importance: 1` に下げるか、  
  専用ルールを追加して `importance: 0` 相当にする
- 変更は管理アプリ UI から行い、コードデプロイ不要

### 新しいエラーキーが追加されたとき

- 新しい業務機能が追加されたとき、その `functionEntry` が既存ルールの `service` に属していれば自動でカバーされる
- `service` の粒度でルールを作っておくことで、個別の `functionEntry` のルール追加を最小化する

## 7. importanceRules の管理 UI 仕様

### ルール一覧画面

| 表示項目 | 説明 |
|---------|------|
| ルール名 | `displayName` |
| 重要度 | `importance`（1/3/5 のアイコン表示）|
| 有効/無効 | `isActive`（トグル）|
| 条件サマリ | `conditions` のキーと値を読みやすく表示（例: `service=accounting`）|
| 最終更新 | `updatedAt` + `updatedBy` |
| 操作 | 編集・削除 |

### ルール編集画面

- `displayName`, `importance`, `isActive`, `description` を編集可能
- `conditions` の各フィールドを個別に入力できるフォーム
- 「このルールがどのエラーにマッチするか」をプレビューできると理想（実装は Optional）

## 8. ルール評価の順序・優先度

### 最大値採用の理由

複数ルールがマッチした場合に「どちらを優先するか」をルール間で管理すると複雑になる。  
「最大値採用」にすることで、**細かいルールを追加するだけで自動的に重要度が上がる**仕様になる。

#### 具体例

| ルール | conditions | importance |
|-------|-----------|:----------:|
| `accounting-all` | `{ service: "accounting" }` | 5 |
| `external-all` | `{ errorSource: "external_api" }` | 3 |

→ `accounting` ドメインの外部 API エラーには両方マッチ → `importance: 5`（最大値）

#### 重要度を下げたい場合

重要度を下げるには、対象のルールの `importance` を下げるか `isActive: false` にする。  
「このルールは除外する」という負のルールはサポートしない（シンプルさを保つ）。

---

## 9. 未定義フィールドの扱い

エラーログに特定フィールドが存在しない場合（例: `errorKey` がない）、  
そのフィールドを条件に含むルールは**非マッチ**として扱う。

```typescript
// errorKey がないエラーに対して errorKey 条件ありのルールは非マッチ
if (conditions.errorKey && errorLog.errorKey !== conditions.errorKey) return false;
// errorLog.errorKey が undefined の場合、undefined !== conditions.errorKey → false → return false
```

## 10. クエリ最適化の考慮

`errorLogs` は中央 Firestore で最も読み取り頻度の高いコレクション。

### HOME 画面向け集計（店舗ごとの未対応エラー件数）

全店舗の `errorLogs` を走査するのは N 店舗 × クエリになる。

#### Option A: 店舗ごとにサブコレクションを走査（シンプル）
```typescript
// 各店舗のエラー件数を個別にクエリ（N 回のクエリ）
for (const storeId of enabledStoreIds) {
  const count = await db
    .collection('errorLogs').doc(storeId).collection('logs')
    .where('isResolved', '==', false)
    .where('importance', '>=', 3)
    .where('occurredAt', '>=', last24h)
    .count()
    .get();
}
```
100 店舗で 100 クエリ。Firestore 無料枠（50,000 reads/日）内なら問題なし。

#### Option B: 集計カウンタの維持（高速・複雑）
重要度判定時に `storeStats/{storeId}` ドキュメントのカウンタをインクリメントする。  
HOME 画面は `storeStats` を読むだけで済む。

**導入当初は Option A**、店舗数が増えてパフォーマンス問題が出たら Option B に切り替える。
