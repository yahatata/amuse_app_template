# 10 更新・リリース方針

> **用語は README.md の定義に従う。**  
> このファイルは「店舗用アプリ」と「中央管理アプリ」それぞれの更新・リリース・バージョン管理の方針書。

---

## ⚠️ 重要: 2 つのアプリの独立性

**店舗用アプリ**（`amuse_app_template`）と**中央管理アプリ**（`amuse-admin`）は  
**リポジトリも Firebase プロジェクトも完全に独立している**。

| 項目 | 店舗用アプリ | 中央管理アプリ |
|-----|-----------|-------------|
| リポジトリ | `amuse_app_template` | `amuse-admin`（新規）|
| Firebase Project ID | 店舗ごと（例: `amuse-app-template`）| `amuse-central-monitoring` |
| デプロイ先 | 各店舗の Firebase Hosting / Functions | 中央プロジェクト |
| 更新頻度 | 機能追加・バグ修正ごと | 監視ニーズの変化に応じて |
| バージョン管理 | Git タグ（例: `v1.2.0`）| Git タグ（例: `v1.0.0`）|

## 1. 公開・ホスティング方針

### 対象ユーザー

中央管理アプリは**社内（内部）専用**。外部公開は不要。

### ホスティング先

**Firebase Hosting（`amuse-central-monitoring` プロジェクト）を使用する。**  
カスタムドメインの取得・設定は**不要**。

### アクセス URL

```
https://amuse-central-monitoring.web.app
```

Firebase プロジェクト作成時に自動で発行されるドメイン。  
追加費用・ドメイン契約なしで永続利用できる。

### セキュリティ方針

URL は公開状態（誰でも開ける）だが、アクセス制限は **認証で行う**。

| 状態 | 結果 |
|-----|------|
| 未ログイン | ログイン画面にリダイレクト |
| Google ログイン済みだが `adminUsers` 未登録 | アクセス拒否（403）|
| `adminUsers` に登録・`enabled: true` | 利用可能 |

> URL が漏れても `adminUsers` に登録されていない限り一切操作できない。

### デプロイコマンド

```bash
cd amuse-admin
npm run build          # Next.js をビルド
firebase deploy        # Hosting + Functions を一括デプロイ
```

### 初回デプロイ前の準備

```bash
# Firebase CLI のインストール（未インストールの場合）
npm install -g firebase-tools

# 中央プロジェクトにログイン・設定
firebase login
firebase use amuse-central-monitoring

# Hosting と Functions を初期化
firebase init hosting functions
```

## 3. 店舗用アプリの更新方針

### 1-1. テンプレートからのリリース方式

- `amuse_app_template` がマスターテンプレート
- 各店舗向けアプリは このテンプレートから派生し、店舗固有の設定は **Firestore 内のデータ**で差分を持つ
- アプリコード（Flutter + Functions）は店舗間で**ほぼ同一**

### 1-2. Functions のデプロイ単位

各店舗は独立した Firebase プロジェクトを持つため、**店舗ごとに Functions をデプロイする**必要がある。

```bash
# 特定店舗へのデプロイ例
firebase use amuse-app-template
firebase deploy --only functions
```

### 1-3. 全店舗への一括更新手順

中央管理アプリ連携機能（`writeToCentralFirestore.ts` 等）の変更は全店舗に適用する。

```bash
#!/bin/bash
# 店舗プロジェクトリスト
STORE_PROJECTS=(
  "amuse-app-template"
  "amuse-store-shibuya"
  # ... 追加店舗 ...
)

for PROJECT_ID in "${STORE_PROJECTS[@]}"; do
  echo "Deploying to ${PROJECT_ID}..."
  firebase use "${PROJECT_ID}"
  firebase deploy --only functions
done
```

> 現時点では手動で各店舗にデプロイする。  
> 店舗数が増えたら CI/CD（GitHub Actions）による自動化を検討する。

### 1-4. 変更の影響範囲の確認

店舗 Functions を更新する際に確認すること:

| チェック項目 | 確認方法 |
|-----------|---------|
| `tsc --noEmit` でコンパイルエラーなし | ローカルで実行 |
| 既存テストが全 PASS | `npm test` で確認 |
| `writeToCentralFirestore` の best-effort write が主業務をブロックしないこと | テスト + コードレビュー |
| デプロイ後に中央 Firestore にログが届くこと | 中央管理アプリまたは Firestore コンソールで確認 |

### 1-5. ロールバック方針

デプロイ後に問題が発生した場合:

1. `firebase deploy` は前のバージョンに自動ロールバックしない
2. 問題を検知したら手動で前のコードに戻してデプロイする
3. 緊急時は `CENTRAL_PROJECT_ID` を空文字に設定してデプロイすることで中央 Firestore への書き込みを即停止できる

```bash
# 緊急時: 中央 Firestore 書き込みを無効化
# functions/.env.production
CENTRAL_PROJECT_ID=  # 空にする
```

## 4. 中央管理アプリの更新方針

### 2-1. デプロイ先

- **Firebase Hosting**: 中央管理アプリの Web UI
- **Cloud Functions**: 重要度判定・通知・scheduler 検知バッチ
- Firebase Project: `amuse-central-monitoring`

### 2-2. デプロイコマンド

```bash
cd amuse-admin
firebase use amuse-central-monitoring
firebase deploy  # Hosting + Functions 両方
```

### 2-3. Firestore のデータ（`importanceRules` 等）の更新

**コードのデプロイなしに**以下のデータを更新できる:

| データ | 更新方法 | 必要な権限 |
|-------|---------|----------|
| `importanceRules` | 管理アプリ UI / Firestore コンソール | 管理者 |
| `notificationTargets` | 管理アプリ UI | 管理者 |
| `stores` | 管理アプリ UI | 管理者 |
| `adminUsers` | 管理アプリ UI / Firestore コンソール | 管理者 |

これにより、**検知ルールの調整はデプロイなしでリアルタイムに反映**される。

### 2-4. バージョン管理

- Git タグで管理（例: `v1.0.0`）
- major / minor / patch のルール:
  - **major**: Firestore スキーマの破壊的変更、または認証の仕様変更
  - **minor**: 新機能追加（新画面、新フィルター等）
  - **patch**: バグ修正、UI 調整

### 2-5. Firestore スキーマの変更を伴う更新

`importanceRules` や `errorLogs` のフィールドが変わる場合:

1. 旧フィールドを読んでいるコードを確認する
2. **新旧両フィールドを一時的にサポート**するコードを書く（移行期間）
3. 古いドキュメントをマイグレーションスクリプトで更新する
4. 旧フィールドのサポートコードを削除する

> 中央 Firestore に書き込む店舗 Functions 側と、中央管理アプリ側を  
> 同時にデプロイする必要があるケースでは、**店舗側→中央側の順**でデプロイする。

## 5. 店舗追加時の手順

新規店舗を監視対象に追加するとき:

1. **店舗プロジェクトの作成**（別途: Firebase コンソールでプロジェクト作成）
2. **IAM 設定**（店舗 SA に中央 Firestore への write 権限を付与）
   ```bash
   gcloud projects add-iam-policy-binding amuse-central-monitoring \
     --member="serviceAccount:{NEW_STORE_ID}@appspot.gserviceaccount.com" \
     --role="roles/datastore.user"
   ```
3. **中央管理アプリで店舗を登録**（`/settings/stores` 画面から）
4. **店舗 Functions のデプロイ**（`CENTRAL_PROJECT_ID` が設定されていることを確認）
5. **動作確認**（中央 Firestore にログが届いているかを確認）

## 6. 店舗削除・無効化時の手順

店舗が閉店または監視不要になった場合:

1. **中央管理アプリで `enabled: false` に設定**
   - HOME から除外され、通知も停止する
   - データは残り続ける（閲覧は可能）
2. **完全に削除する場合**（慎重に）:
   - 中央 Firestore の `stores/{storeId}` ドキュメントを削除
   - 中央 Firestore の `errorLogs/{storeId}`, `schedulerLogs/{storeId}`, `taskLogs/{storeId}` サブコレクションを削除
   - IAM から店舗 SA の権限を削除:
     ```bash
     gcloud projects remove-iam-policy-binding amuse-central-monitoring \
       --member="serviceAccount:{STORE_ID}@appspot.gserviceaccount.com" \
       --role="roles/datastore.user"
     ```

## 7. セキュリティ更新方針

| 項目 | 方針 |
|-----|------|
| LINE Channel Access Token | Secret Manager に保存。漏洩時は即座にローテーション |
| Firebase Admin SDK 秘密鍵 | 使用しない（ADC を使用）|
| 管理者アカウント | 退職・離任時に即座に `enabled: false` に変更 |
| Firestore セキュリティルール | コードレビュー必須。`write: if false` の原則を維持 |

## 8. 監視体制の定期見直し

### 月次レビュー（推奨）

| 確認項目 | 方法 |
|---------|------|
| `importanceRules` の適切性 | 検知されたエラーの内容を確認し、不要なルールを無効化 |
| 通知量の確認 | LINE 通知の月間送信数を確認 |
| Scheduler 異常の傾向 | 繰り返し発生している異常がないか確認 |
| `adminUsers` の棚卸し | 不要なアカウントが残っていないか確認 |

### 適切性の判断基準

| 状況 | 対応 |
|-----|------|
| 同じエラーが毎日 10 件以上来て全て実害なし | `importance` を 5→3 または 3→1 に下げる |
| 検知漏れが発生した | `importanceRules` に新しいルールを追加 |
| 通知が多すぎて見逃す | 通知先の `notifyOnImportance` を `[5]` のみに絞る |
| 店舗数が増えてパフォーマンスが落ちた | `05_エラー検知・重要度フィルター仕様.md` の Option B（集計カウンタ）に切り替え |
