# D02-D01 2025-09再利用 最終互換性確認

## 0. 調査事実（集約・簡潔）

追加調査専用 md は残さない。判断に必要な事実のみここに持つ。

| 項目 | 結果 |
|------|------|
| 現行 settle / migrate / adjustment / reopen | `dailySales[date]` と `days.grossSales` を **同一 delta・同一 TX** で更新。日常運用での相互ズレは実質なし |
| cashAction | gross / dailySales は触らない（payment のみ） |
| 未配線 `enqueueEvent`→`applyMonthlyDailyDelta` | 理論上 `dailySales` 未更新のまま days だけ増え得るが、**本番 call site なし** |
| 2026-08 実データ | dailySales ↔ days.grossSales 全10日一致（正規経路の痕跡あり） |
| 2025-09 不整合 | markers 0・seed っぽい ID・dailySales が丸い千円単位 vs days が不規則 → **ダミー別生成 High**。現行 atomic 経路では説明しづらい |
| Cursor からの投入 | Admin SDK + ADC で **CONDITIONAL 可**。Client rules は write false（Admin は bypass）。guarded writer 必須 |
| analytics の位置づけ | isolated read model。直接書込による bills/users 等への逆流 trigger なし |

デモ投入ではホームが `dailySales`、日次画面が `days.grossSales` を使うため、**両フィールドを同一値で書くこと**が必須（以降の正規化仕様）。

## Compatibility verdict

**B** — ほぼそのままは不可。月次のカテゴリ/支払/gross/orderCount は使えるが、`dailySales`・`days` は再構成が必須。日付 remap・Timestamp 刷新・不要 key 除去後に再利用可能。

## Existing inconsistency repair strategy

### 不採用

| 候補 | 理由 |
|------|------|
| A. dailySales を正 | 合計 5721000 ≠ gross 4520000。ホーム総売上と日次グラフが致命的に矛盾 |
| B. days.gross を正 | 合計 4880258 ≠ gross。各日も内部分解不一致。orderCount 合計758 ≠ 1250 |

### 採用: **C（月次カテゴリ/支払/gross/orderCount を SoT に日次を再構成）**

1. **SoT（触らない核）**  
   - `grossSales = 4520000`  
   - `items/sideGameChip/tournaments/extraCost` 各フィールド  
   - `paymentTotals`（`sideGameTip` 除去後。現状 chip=0 のまま合計は 4520000）  
   - `orderCount = 1250`, `avgOrderValue = 3616`
2. **日次シェイプ**  
   - ソース `days/{d}.grossSales` の相対比率を形状用に使う（絶対値は捨てる）  
   - またはソース `dailySales` 比率でも可だが、gross との乖離が大きいため **days 比率優先**
3. **再配分**  
   - 選定日（§6）ごとに targetGross / targetOrder を整数配分（端数は最終日に吸収）  
   - 各日: category 4種・payment（KEEPキー）を **同比率で月次 SoT から按分**し、  
     `day.gross == day cat合計 == day pay合計`  
   - `monthly.dailySales[date] = days[date].grossSales`  
   - `sum(dailySales) == grossSales`  
   - `sum(days.orderCount) == monthly.orderCount`
4. **byCategory.summary.totals** は月次カテゴリと同値を維持。`itemSales` はそのまま（スケールしてもよいが必須ではない）

必須 assert（最終デモデータ）はユーザー指定どおり。

## orderCount / avgOrderValue consistency

| 項目 | 値 | 判定 |
|------|-----|------|
| monthly orderCount | 1250 | 表示利用可 |
| monthly avgOrderValue | 3616 | `4520000/1250=3616` 一致。表示利用可 |
| sum(days.orderCount) | 758 | **不一致** → 日次再構成時に 1250 へ合わせる |
| byCategory.orderCounts 合計 | 1770 | 月次来店数とは別指標。現行UIはカテゴリ別「件数」表示用。月次1250と一致不要 |

**修正方針:** 月次の 1250 / 3616 を維持。days の orderCount を再配分して合計 1250 にする。days 側を正にして月次を 758 に落とすのは、客単価・総売上のデモ数字を崩すため非推奨。

日付圧縮（§6）後は:

- `avgOrderValue = round(grossSales / orderCount)` を再計算して保存  
- または比率スケール後も 3616 付近を維持するよう整数調整

## Date transformation strategy

### 採用: **B（DemoDay までのソース日だけ採用し、月次も再計算）**

| 方式 | 評価 |
|------|------|
| A. 30日を DemoDay 日数へ圧縮 | 可能だが配分ロジックが重い |
| **B. 1..DemoDay のみ採用＋月次再計算** | **自然・簡単・未来日なしを保証しやすい** |
| C. 月日数で再配分 | B と類似。DemoDay 超の日を捨てる点が B で足りる |

### ルール

1. `TARGET_MONTH = DemoDay の YYYY-MM`
2. ソース営業日番号 `d = 1..min(DemoDay.day, 30)` のみ採用  
   - マップ: `2025-09-{dd}` → `{TARGET_MONTH}-{dd}`（同日番号）
3. **未来日禁止**: `date > DemoDay` の doc / dailySales キーを作らない
4. **月次 SoT（4,520,000 / 1,250 等）は維持**し、選定日 1..N へ相対配分する（`sum(daily)==grossSales` を保証）
5. 形状: 選定ソース日の `days.grossSales` 相対比率。カテゴリ/支払は月次 SoT 比率を各日に按分

### 月初（DemoDay の日が 1〜3）

- 同じ方式: 採用日は 1日のみ / 1〜2日 / 1〜3日
- 月次 SoT 全量をその少数日へ圧縮（デモ説明用の金額感を優先。未来日は作らない）
- 旧 148k テンプレの「D−8圧縮」は使わない（当該ファイルは **物理削除済**）
