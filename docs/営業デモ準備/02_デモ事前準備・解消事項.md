## 1. 位置づけ

**最上位目的:** 営業デモ成立。

本資料（`02`）の対象:

- 当日までに事前確認すべきもの
- 事前に解消可能な問題
- デモ品質に影響する既知懸念
- 必要な環境・データ・端末状態

対象外:

- 当日しか起きない偶発事故（→ 予定 `04_当日事故・代替手段.md`）
- 通し台本（→ 予定 `03`）
- 機能仕様そのもの
- UI残タスク全文（→ UI正本。ここでは ID・要否・状態のみ）

**本資料は「事前データ一覧」ではない。**  
事前データはデモ成立のための手段の一つ（判断原則は `00` §2.1）。

### 1.1 `02` と `04` の境界

| こちら（`02`） | あちら（`04`・未作成） |
|----------------|------------------------|
| 再現できる不安定さの調査・改善 | 回線瞬断など偶発障害 |
| optionKeys / seed不足 / 既知UI | 予期せぬログアウトのその場対応 |
| LINEウォーム手順の確定 | ウォーム済みでも起きる再認証失敗の代替 |
| 空ダッシュボードの解消 | 突発的な読み込み遅延の見せ方切替 |

「不安定だから `04` へ逃がす」は禁止。事前に改善・再現条件整理できるものは本資料で扱う。

### 1.2 UI正本との責務分離

| 本資料（デモ観点） | UI正本（リリース観点） |
|--------------------|------------------------|
| デモで対応するか・優先度・進捗 | リリース前必須などの本文・ステータス |
| `デモ対応不要` = 営業デモ準備の対象外 | **リリース必須は消えない** |

`状態 = 不要` は **デモ対応不要** の意味。プロジェクト全体として不要にしたのではない。UI側ステータスは変更しない。

### 1.3 確認と修正の分離

問題が確定していないものを、最初から修正タスクにしない。

1. **確認 / 調査**（再現・影響）
2. **判断**（デモ品質上、要対応か）
3. **解消**（必要な場合のみ実装・データ修正）

例: Redmi/Philips UI差、G2-09/G2-10、LINEコールド起動は、いずれも確認→判断→必要なら解消。

## 2. 優先度

| 優先度 | 意味 | 厳格な適用 |
|--------|------|------------|
| **P0** | デモ成立必須 | **未解消のままでは営業デモを実施しない** |
| **P1** | デモ品質に強く影響 | 未解消でも回避・代替・見せないで実施可能な場合あり |
| **P2** | できれば対応 | 成立への影響は限定的 |
| **P3** | デモ後可 / デモ対応不要 | 営業デモ準備のゲートにしない。UI正本のリリース必須は別途維持 |

P0にしないもの（例）:

- 軽微な見た目差
- 当日使わない経路だけの問題
- 代替があり重大影響しないもの
- 管理・追跡専用の重複行
- リリース前には必要だがデモ自体には不要なもの

### 2.1 種別（準備 / 確認 / 解消 / 判断）

| 種別 | 意味 |
|------|------|
| 準備 | 必要な状態・データを整える |
| 確認 | 実機・環境で成立を確かめる（修正前提にしない） |
| 調査 | 再現条件・原因・影響を洗う（解消の前段） |
| 解消 | 既知の不具合・懸念を直す（確認/調査のあと） |
| 判断 | 対応要否・見せ方を決める |

## 4. 事前データの扱い（再掲）

用意するのは次のいずれかに該当する場合のみ。

- 空だと価値が伝わりにくい
- その場で生成すると時間がかかる
- 当日生成は失敗リスクが高い
- 量が必要
- 見せたい状態の再現に必要

当日操作した方が価値が伝わるものは実演を優先（例: 注文1件、LINE入店）。
