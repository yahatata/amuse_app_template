## 1. 目的

JOPT様向け営業で、現在作成済みの店舗管理アプリ / Admin / 顧客LINE / 従業員LINEを実際に見せることで、次を伝える。

- システムが実装済みであること
- 店舗業務を一連で扱えること
- 顧客LINE / 店舗端末 / Admin / スタッフLINEが連携していること
- 実運用を想定した完成度があること

**目的にしないこと:**

- 機能を全部見せること
- UIを完璧にすること
- 残タスクを全部消化すること
- **事前データを全部用意すること**（事前データは手段であり目的ではない）

**最上位目的:**

営業デモを気持ちよく、滞りなく成立させること。  
デモが止まらず、「良いシステムを作っている」と感じてもらうこと。

---

## 2. 基本原則

1. **デモ成立を最優先**する
2. **見せる必要のない機能は無理に操作しない**
3. **破壊的・状態変更量が大きい操作は説明優先**とする
4. **事前データは手段の一つ**とする
   - 流れ・見栄え・安定性を高める箇所では用意する
   - 当日操作した方が価値が伝わるものは実演し、その場で生成してよい
   - 「事前データありき」「全部事前に作る」を目的化しない
5. **当日生成と事前準備を使い分ける**
6. **事前に潰せる問題は `02` で解消する**（`04` へ逃がさない）
7. **事前に完全排除できない偶発事故だけを `04` で扱う**
8. **UI修正は営業デモに必要な範囲だけ行う**（「残っているから」ではやらない）
9. **既存正本を複製しない**（参照・IDリンクに留める）
10. **実機確認を重視する**
11. **本番品質とデモ品質を混同しない**
    - 営業デモでは見せ方・事前ウォーム等による事故回避を許容する
    - ただし虚偽の状態を見せることはしない

判断基準:

> 「残タスクがあるからやる」ではなく、  
> 「デモ成立に必要だからやる」

### 2.1 事前データ判断原則

事前データを用意するのは、次のいずれかに該当する場合。

- その場で作るとデモ時間が長くなる
- 空状態だと価値が伝わりにくい
- 当日生成すると失敗リスクが高い
- データ量が必要で即時生成が現実的でない
- 見せたい状態を再現するために必要

逆に、当日操作した方が価値が伝わるものは実演を優先する。

例（当日実演向き）: 注文 1 件、LINE入店  
例（事前準備向き）: 売上集計、見せたい状態の TN、会計 preview 用の未会計伝票

### 2.2 `02` と `04` の分離原則

| 資料 | 扱うもの | 扱わないもの |
|------|----------|--------------|
| `02` | 当日までに確認・準備・解消できること | 偶発的な当日事故そのものの台本 |
| `04` | 事前に完全排除できない当日事故と、その場の代替 | 既知不具合の放置、seed不足、optionKeys未確認、UI残タスク |

「不安定だから `04`」は禁止。再現・改善できるものは `02`。

## 3. 完了条件（営業デモ準備 COMPLETE）

以下をすべて満たしたとき、営業デモ準備を **COMPLETE** とする。

| # | 条件 |
|---|------|
| 1 | デモ範囲が確定している（`01`） |
| 2 | 実操作 / 説明のみの境界が確定している（`01`） |
| 3 | 端末運用方針が確定している（機種固定しない・両端末確認等。`01`） |
| 4 | `02` の **P0（デモ成立必須）がすべて PASS / 不要** である |
| 5 | 各デモ項目の準備方針に沿い、**必要な事前状態だけ**整っている（「事前データがあること」単体は完了条件にしない） |
| 6 | DeviceOption / optionKeys 確認済みである（`02`） |
| 7 | 顧客LINE必須実演が成立する（ウォーム含む。安定性の事前解消は `02`。偶発失敗の代替は `04`） |
| 8 | 主要デモ画面の確認済みである（必要UI IDのみ。`02`） |
| 9 | `04` の当日事故に対し、最低限の代替手段がある |
| 10 | 当日手順書が確定している（`03`） |
| 11 | 通し予行が PASS である（`05`） |
| 12 | 致命的な詰まりがない |

未達の項目がある場合は COMPLETE としない。部分的な準備完了は「準備中」として扱う。

### 4.1 `02` の責務

当日までに準備・確認・解消すべき事項の正本。  
**「事前データ一覧」ではない。** データはデモ成立のための手段の一つ。

持つもの:

- 事前確認事項
- デモ成立のための事前準備
- 既知不具合・懸念の事前解消
- 必要データ（方針が事前準備のもの）
- 端末状態
- optionKeys
- LINE安定性（事前に改善・再現整理できる範囲）
- UI確認（ID参照・要否判定）
- Firebase / build 状態
- 優先度（P0〜P3）
- 対応方針・完了条件・ステータス

持たないもの:

- 当日しか起きない偶発事故の代替台本（→ `04`）
- 通し台本（→ `03`）
- 機能仕様そのもの
- UI残タスク全文（→ UI正本）

### 4.2 `04` の責務（未作成・予定）

事前に完全排除できない当日事故だけを扱う。

例: 回線不調、LINE再認証失敗、端末フリーズ、予期せぬログアウト、外部サービス一時障害、突発的な読み込み遅延。

`02` で潰せるものを先に潰したうえで、残った偶発事故だけを登録する。

### 4.3 作成順

1. `00` / `01`（完了）
2. `02`（作成済み → P0/P1 を潰す）
3. `04`（`02` で潰し切れない偶発事故のみ）
4. `03`（事前状態が整ったあと）
5. `05`（予行後）

## 5. 既存資料との責務分離

### 5.1 UIデザイン調整

- **正本:** `docs/UIデザイン調整/`（`01_タスク一覧.md` / `03_残タスクまとめ.md` 等）
- 営業デモ準備側では UI 残タスク本文を **コピーしない**
- 必要な場合は ID 参照のみ（例: `G1-01`, `PRE-01`, `G6-08`）
- UI作業の採否は「デモ成立に必要か」で判断し、UI側ステータスを勝手に書き換えない
- デモ観点の優先度・対応要否は `02` で持つ

### 5.2 綺麗化

- **正本:** `docs/綺麗化/00_営業向け綺麗化_統合管理.md`
- cleanup / Final Cleanup の結果は **参照のみ**
- 営業デモ準備で cleanup 履歴を再定義しない

### 5.3 各機能仕様

- トーナメント / 会計 / 勤怠 / Device / LINE 等の仕様正本は既存 docs / コード側
- 営業デモ準備では仕様を再定義しない
- デモに必要な入口・前提・危険操作の境界だけを持つ

### 5.4 二重管理禁止

| やってよい | やってはいけない |
|------------|------------------|
| ID・path で既存正本を参照 | UI残タスク全文の転記 |
| デモ専用の見せ方・当日判断を書く | 機能仕様のコピー |
| デモ観点の優先度を別に持つ | UI側の優先度記号を上書き変更 |
| 既知懸念を `02` で解消する | 既知不具合を `04` へ逃がす |

| 状態 | 意味 |
|------|------|
| 未着手 | まだ着手していない |
| 準備中 | 作成・準備中 |

## 8. 更新ルール

1. 営業デモ準備に関する **current な方針・完了条件・資料責務** は本 `00` を更新する
2. **何を見せるか** が変わったら `01` を更新する
3. **事前に潰すべきこと・準備進捗** が変わったら `02` を更新する
4. UI / 綺麗化 / 機能仕様の正本はそれぞれの場所で更新し、こちらは参照を保つ
5. 虚偽デモは禁止。未準備なら見せないか HOLD
6. 事前データの要否は §2.1 で判断し、「必要状態」と「準備方針」を混同しない
7. Firebase は現行環境前提。端末機種は固定しない
8. `02` で潰せるものを `04` に移さない
