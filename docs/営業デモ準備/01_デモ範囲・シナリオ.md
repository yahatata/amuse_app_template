## 2. デモの狙い（短く）

一連の店舗業務が、店舗端末・Admin・LINEでつながって動くことを見せる。  
全部操作して証明する必要はない。

事前データは目的ではない。流れ・見栄え・安定性を高める手段として使う（詳細は `00` §2.1）。

---

## 2.1 必要状態と準備方針の区別

| 用語 | 意味 |
|------|------|
| 必要状態 | そのデモ項目が成立するために必要なデータ・画面状態・権限など |
| 準備方針 | その必要状態を **事前に用意するか / 当日操作で作るか / 不要か** |

「必要だから事前に作る」は短絡。判断は `00` の事前データ判断原則に従う。

## 3. デモ方針（確定）

### 3.1 Terminal

#### 1. ユーザーログイン / 入店

| 項目 | 方針 |
|------|------|
| 見せる | ユーザーログイン入口、LINE QRでログイン可能、手動ID入力も可能 |
| 実操作 | **LINE入店を実演**（顧客LINE必須実演と連動）。手動IDは説明のみ |
| 必要状態 | 店舗開店、デモ用ユーザー、脱線しにくいユーザー選定（okibake誘導を避ける） |
| 準備方針 | 開店・ユーザーは環境として用意。**入店（activeStay）は当日生成** |
| 関連UI | G1 入口確認、PRE（`user_entry_exit`） |

#### 2. 注文

| 項目 | 方針 |
|------|------|
| 見せる | 注文画面、カテゴリ、メニュー、ユーザー選択、注文管理への反映 |
| 実操作 | **注文 1 件を実演**（その場生成の価値が高い） |
| 必要状態 | activeStay、menu、紐づく bill、DeviceOption `order` / `kitchen` |
| 準備方針 | menu・権限は環境として用意。**activeStay は入店実演に連動して当日生成**。注文レコード自体は当日操作で生成 |
| 関連UI | G1、PRE |

#### 3. トーナメント

| 項目 | 方針 |
|------|------|
| 見せる | 作成方法があることの画面説明、カレンダー、事前準備済みTN、TNホーム、卓画面、reentry/addon **ダイアログ** |
| 実操作 | 事前準備済みTNを開く。addon/reentryは **ダイアログを開くまで**（「ここで実行可能」と説明） |
| 説明のみ | **TN作成操作そのもの**、TN終了、addon/reentryの実行、大規模な状態破壊操作 |
| 必要状態 | 見せたい状態の TN（必要なら参加者/卓）、`tournament` option |
| 準備方針 | **事前準備必須**（作成は実演しないため、見せたい状態のTNを事前配置） |
| 関連UI | 卓を見せるなら G2-10（B）。必須にはしない |

#### 4. 会計

| 項目 | 方針 |
|------|------|
| 見せる | 会計管理、未会計伝票、プレビュー、「ここから会計確定できる」ことの説明 |
| 実操作 | **プレビューまで**。`completeAccountingV2` 等の会計確定は **実行しない** |
| 必要状態 | 未会計 `bills`、`accounting` option |
| 準備方針 | **流れ優先のため事前配置**（デモ途中で一から作ると長い）。注文デモで作った bill を流用してもよい |
| 関連UI | G1、PRE |

#### 5. 勤怠（店舗端末）

| 項目 | 方針 |
|------|------|
| 見せる | 勤怠打刻画面、事前データとしての勤怠表示 |
| 実操作 | **しない**（実打刻しない） |
| 必要状態 | staff / QR、`staff_entry_exit`、見栄え用の勤怠データ |
| 準備方針 | スタッフは環境として用意。**勤怠データは事前準備**して見せる |
| 関連UI | G1、PRE |

### 3.2 Admin

#### 6. 営業日

| 項目 | 方針 |
|------|------|
| 見せる | 現在営業日（Terminal AppBar または営業管理）、営業日設定が可能であること |
| 説明のみ | **閉店実行・強制閉店** |
| 必要状態 | `currentBusinessDay`（開店状態が分かる） |
| 準備方針 | 営業デモ開始時点で開店済みにしておく（環境準備）。スタイル名ホーム表示は未実装・必須にしない |
| 関連UI | 閉店を見せるなら G6-08 が必須 → **見せない**（確定） |

#### 7. シフト

| 項目 | 方針 |
|------|------|
| 見せる | シフト画面、作成/編集可能、スタッフごとの状態 |
| 実操作 | 深い操作は不要。一覧・代表日の表示中心 |
| 必要状態 | 対象月の営業時間・シフト日・staff |
| 準備方針 | **空月だと価値が伝わりにくいため事前準備**。深い編集は当日不要 |

#### 8. 勤怠管理

| 項目 | 方針 |
|------|------|
| 見せる | 全スタッフ勤怠、修正可能であること、修正申請画面 |
| 実操作 | 一覧表示中心。承認操作は必須にしない |
| 必要状態 | 一覧が空でない見栄えのため `attendances`。修正申請デモなら pending |
| 準備方針 | **事前準備**（店舗端末で当日打刻しないため、流用前提にしない） |

#### 9. 給与

| 項目 | 方針 |
|------|------|
| 見せる | 給与計算画面、計算可能であること |
| 説明のみ | **本番計算 execute** |
| 必要状態 | 勤怠・給与設定 |
| 準備方針 | 画面紹介中心。候補表示まで見せるなら事前準備 |

#### 10. 売上ダッシュボード

| 項目 | 方針 |
|------|------|
| 見せる | 売上・集計・グラフ/一覧（**必須**） |
| 実操作 | **しない**（閲覧・説明のみ） |
| 必要状態 | `analyticsMonthly` 等（データが表示される状態） |
| 準備方針 | **事前準備必須**（当日生成は現実的でない） |
| 関連UI | G2-09 は B（データ準備の方が先） |

### 3.3 顧客LINE

#### 11. 顧客LINE

| 項目 | 方針 |
|------|------|
| 見せる | ログイン、入店状態、注文導線、店舗端末との連携 |
| 基本方針 | **必須実演** |
| 依存 | コールド起動、LIFF init、Firebase Auth、Functions、回線 |
| 必要状態 | 登録済みユーザー、入店状態 |
| 準備方針 | **LIFFウォーム・ログイン状態は事前必須**。入店は実演と連動して当日生成可 |
| 必須付帯 | **失敗時の代替手段**（事前に潰せる不安定は `02`。偶発失敗のその場対応は予定 `04_当日事故・代替手段.md`） |
| 環境 | **現行 Firebase 環境**を使用（デモ専用 project は作らない） |

### 3.4 従業員LINE

#### 12. スタッフLINE

| 項目 | 方針 |
|------|------|
| 見せる | シフト申請、勤怠管理画面 |
| 実操作 | **画面表示と機能説明**。実打刻は必須にしない |
| 必要状態 | active `staffs`（retired 不可） |
| 準備方針 | スタッフアカウントは環境として用意。申請データは空でも画面紹介可。見栄え用なら任意事前準備 |

## 4. 見せない / 説明のみ（確定）

実操作しない / 説明のみ:

- 閉店実行 / 強制閉店
- **トーナメント作成操作**（作成方法の画面説明のみ）
- トーナメント終了
- **addon / reentry の実行**（ダイアログを開いて「実行可能」と説明するまで）
- **会計確定**（preview まで。`completeAccountingV2` 等は実行しない）
- **店舗端末での勤怠打刻**
- 給与本実行（execute）
- 売上ダッシュボード上の操作（閲覧・説明のみ）
- 不要な管理設定の深い編集
- デモ価値の低い内部画面
- debug 画面（`lib/debug/` は未ルート。開かない）

「機能があるから見せる」は禁止。

## 7. 端末・環境（方針確定）

| 項目 | 方針 |
|------|------|
| 端末運用 | **機種を固定しない**。Redmi / Philips のどちらでもデモ成立する前提 |
| 機能差 | 現時点で機能操作上の差異は認識していない |
| UI差 | あり（例: Redmiは画面いっぱい、Philipsは余白・表示範囲が異なる） |
| 確認 | 主要デモ画面は **両端末で表示確認**する。UI差がデモ品質に影響する場合のみ修正検討 |
| Admin / Terminal / LINE端末 | 役割は分けるが、機種の固定はしない |
| Firebase | **現行環境を使用**。デモ専用 Firebase project は新規作成しない |
| データ調整 | デモ成立に必要な場合のみ、現行環境の DB 状態・データを調整する（目的化しない） |
| Functions / Hosting / Auth | 現行環境前提 |
| DeviceOption | 見せる機能の keys をセット。PRE-01〜04 確認対象 |

端末・ログイン・optionKeys・ウォーム・必要データ・既知懸念の事前解消は `02_デモ事前準備・解消事項.md` で管理する。
