# 環境変数管理とデプロイ時の上書き防止

## 問題の整理

### 1. 何が起きていたか

- `firebase deploy --only functions:lineWebhook,...` を実行したら、**本番の環境変数が .env の値で上書きされた**
- `createStaffAccount` と `lineWebhook` で `LINE_CHANNEL_ACCESS_TOKEN` が**別の値**になっている
- QR_SECRET_KEY も同様に上書きされた可能性がある

### 2. 原因（Firebase 公式ドキュメントより）

Firebase Functions Gen2 では、**デプロイ時に `.env` や `.env.projectId` を読み込み、そこにある環境変数をデプロイ対象の関数に反映する**。

> "The environment variables from .env and project-specific .env files (if they exist) will be **included in all deployed functions**."

そのため：

- `.env` に空や誤った値があると、デプロイ時にそれが本番へ送られる
- 一部の関数だけデプロイした場合、デプロイ対象の関数だけが現在の `.env` で更新され、それ以外は以前の値のままになる
- その結果、関数ごとに環境変数の値が食い違う

### 3. 「全関数で共通」ではない理由

- Gen2 では各関数が**別々の Cloud Run サービス**になる
- デプロイするのはその関数の Cloud Run サービスのみ
- `firebase deploy --only functions:lineWebhook` では `lineWebhook` だけが `.env` で更新され、`createStaffAccount` は更新されない
- デプロイのタイミングや `.env` の内容が違うと、関数ごとに違う値が入る

---

## 方針：リポジトリ外で一括管理し、デプロイで上書きされないようにする

### 要件

1. **デプロイしても環境変数が変わらない**  
   → `.env` 経由で値を流し込まない
2. **全関数で同じ値を使う**  
   → プロジェクト共通の Secret / 設定を使う
3. **リポジトリに機密を持たない**  
   → 1 リポジトリから複数 Firebase プロジェクトへデプロイする運用に対応

---

## 推奨: Secret Manager（defineSecret）を使う

### メリット

- 値は **Cloud Secret Manager** に保存され、`.env` とは完全に独立
- デプロイ時は `.env` を読まないので、誤って上書きされない
- プロジェクト単位で共通のシークレットを参照できる
- リポジトリに機密を置かず、プロジェクトごとに別のシークレットを登録できる

### 設定の流れ

1. **Secret の登録（CLI）**

   ```bash
   firebase functions:secrets:set LINE_CHANNEL_ACCESS_TOKEN
   firebase functions:secrets:set QR_SECRET_KEY
   ```

2. **コード側で defineSecret を使用**  
   - 現在の `process.env.LINE_CHANNEL_ACCESS_TOKEN` を `defineSecret('LINE_CHANNEL_ACCESS_TOKEN')` に変更
   - 同様に `QR_SECRET_KEY` も `defineSecret` に変更
   - 各関数の定義で `secrets: [lineChannelAccessToken, qrSecretKey]` のようにバインド

3. **.env から該当キーを削除**  
   - `LINE_CHANNEL_ACCESS_TOKEN`, `QR_SECRET_KEY` を `.env` に入れない

---

## .env がデプロイに影響しないようにする方法

### 方法 A: 対象キーを .env から完全に削除（推奨）

- `LINE_CHANNEL_ACCESS_TOKEN`, `QR_SECRET_KEY` を `.env` / `.env.projectId` から削除する
- これらは **defineSecret** のみから取得する設計にする
- デプロイ時にこれらの値が `.env` 由来で上書きされることがなくなる

### 方法 B: .env を使わない運用にする

- `functions/` 直下の `.env`, `.env.projectId`, `.env.*` を削除（または `env.local.example` のみ残す）
- `index.ts` の `require('dotenv').config()` を削除するか、ローカル専用（例: エミュレータ時のみ）に限定する
- 本番・ステージングは、Secret Manager や Cloud Console の環境変数のみで管理

### 方法 C: .env を .gitignore に維持しつつ、デプロイ時には読み込まない

- Firebase CLI はデプロイ時に `functions/` 直下の `.env` 等を自動で読み込むため、**ファイルが存在するだけで影響する**
- プロジェクトごとに別の値を使いたい場合は `.env.projectId` が使われるが、本番値は Secret Manager に集約するのが安全

---

## 複数 Firebase プロジェクトへのデプロイ

1 リポジトリから複数プロジェクトへデプロイする場合：

- 各 Firebase プロジェクトごとに Secret Manager に値を登録する
- `firebase use project-a` で project-a を選択してデプロイ → project-a の Secret を参照
- `firebase use project-b` で project-b を選択してデプロイ → project-b の Secret を参照
- リポジトリにはシークレットを一切含めず、プロジェクト単位で管理できる

---

## 即時対応（抜本的でない暫定策）

`defineSecret` の実装を入れるまでの間は：

1. **Cloud Console** で各関数の環境変数を正しい値に再設定する  
   Cloud Run → 対象サービス →  revisions → 変数編集
2. **`functions/` 直下の `.env` と `.env.projectId` を削除**（または該当キーを消す）  
   → デプロイ時にそのキーが上書きされなくなる
3. 次回デプロイで再び上書きされないよう、上記「推奨」の Secret Manager への移行を進める

## Secret Manager（defineSecret）の詳細：仕組みと移行手順

### 1. 管理方法のイメージ

| 従来（.env） | Secret Manager |
|-------------|----------------|
| 値は `.env` ファイルに書く | 値は **Google Cloud の「金庫」** に保存する |
| デプロイ時にそのファイルが読み込まれる | デプロイ時には**ファイルを読まない** |
| ファイルを差し替えると値が変わる | 金庫の中身は**デプロイとは無関係**に保持される |

**「金庫」= Google Cloud Secret Manager**  
APIキーやトークンなどを暗号化して保存するGoogleのサービス。Firebase と連携している。

---

### 2. 仕組み（流れ）

#### 現在の仕組み（.env）

```
[.env ファイル]  --デプロイ時に読み込み-->  [Cloud Run 各関数]
      ↑
  値がここにある
  → デプロイのたびに送られる
  → .env の内容で上書きされる
```

#### Secret Manager の仕組み

```
[Secret Manager]  ← 人間が事前に値を登録（1回きり or 更新時のみ）
      |
      | 関数実行時だけ、必要な関数が取りに行く
      ↓
[Cloud Run 各関数]  ← デプロイでは触らない
```

- **登録**：`firebase functions:secrets:set 名前` を実行すると、その値が Secret Manager に保存される
- **利用**：関数が動くときに、`defineSecret('名前').value()` で取り出す
- **デプロイ**：コードやデプロイ作業では Secret Manager の値は変わらない

---

### 3. どう使うか（コードのイメージ）

**現在（process.env）**

```javascript
const token = process.env.LINE_CHANNEL_ACCESS_TOKEN;  // .env 由来の値
```

**移行後（defineSecret）**

```javascript
const lineToken = defineSecret('LINE_CHANNEL_ACCESS_TOKEN');

// 関数定義時に「この関数はこのシークレットを使う」と宣言
export const myFunction = onRequest(
  { secrets: [lineToken] },  // ここで紐づけ
  (req, res) => {
    const token = lineToken.value();  // 実行時に取得
    // ...
  }
);
```

- `defineSecret('名前')` で「Secret Manager のこの名前の値を参照する」と宣言
- 関数のオプションに `secrets: [lineToken]` を書くことで、その関数だけがその値を利用できる
- `.value()` は関数が動いているときだけ呼び出す（グローバルスコープでは不可）

---

### 4. 実際の管理のしかた

| 作業 | いつ | やり方 |
|------|------|--------|
| **初回登録** | 環境構築時 | `firebase functions:secrets:set LINE_CHANNEL_ACCESS_TOKEN` を実行し、プロンプトで値を入力 |
| **値の更新** | トークン再発行など | 同じ `firebase functions:secrets:set` を再度実行 |
| **値の確認** | 必要なとき | GCP コンソール → Secret Manager で名前の一覧は確認可能（中身は表示されない） |
| **複数プロジェクト** | プロジェクトごと | `firebase use project-a` で切り替えてから `secrets:set`。各プロジェクトに別々の値が入る |

**リポジトリには一切書かない**  
トークン・秘密鍵はすべて Secret Manager 側にあり、コードや .env には載せない。

---

### 5. 移行に必要な工程

#### 工程1：Secret の登録（各プロジェクトで1回）

```bash
firebase use <対象プロジェクト>
firebase functions:secrets:set LINE_CHANNEL_ACCESS_TOKEN
# プロンプトでトークンを入力

firebase functions:secrets:set QR_SECRET_KEY
# プロンプトで秘密鍵を入力
```

#### 工程2：コードの修正

対象ファイルと変更内容：

| ファイル | 変更内容 |
|----------|----------|
| `lineRichMenu.ts` | `process.env.LINE_CHANNEL_ACCESS_TOKEN` → `defineSecret` を利用 |
| `lineWebhook.ts` | 同上 + 関数に `secrets: [lineToken]` を追加 |
| `lineMessaging.ts` | 同上 + 呼び出し元の関数に `secrets` を追加 |
| `qrCodeUtils.ts` | `process.env.QR_SECRET_KEY` → 呼び出し元で `defineSecret` を受け取り使用 |

※ `qrCodeUtils` は他のモジュールから呼ばれるため、**呼び出し元の各関数**（createStaffAccount, createUserAccount, など）で `defineSecret` を宣言し、`secrets` に追加し、`qrCodeUtils` に渡す形にする必要がある。

#### 工程3：.env から該当キーを削除

- `LINE_CHANNEL_ACCESS_TOKEN`
- `QR_SECRET_KEY`

を `.env` / `.env.projectId` から削除する。

#### 工程4：デプロイと動作確認

```bash
firebase deploy --only functions
# または必要な関数だけ
```

デプロイ後、LINE 連携・QR コード生成などが正常に動くか確認する。

---

### 6. 注意点

1. **バインドが必要**  
   シークレットを使う関数は、必ず `secrets: [xxx]` でバインドする。バインドしていない関数からは参照できない。
2. **動的取得**  
   `.value()` は関数実行時に呼ぶ。関数定義時（グローバルスコープ）では使わない。
3. **共通化**  
   同じ `defineSecret('LINE_CHANNEL_ACCESS_TOKEN')` を複数関数で共有できる。実体は Secret Manager の同じ値。
4. **ローカル開発**  
   エミュレータでは Secret Manager の値を使えない場合がある。その場合は `.env` をローカル専用で残し、本番デプロイ時には読まない運用にする。
