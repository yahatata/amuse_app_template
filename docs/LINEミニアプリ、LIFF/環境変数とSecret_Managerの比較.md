# 環境変数と Secret Manager の比較

## 1. 認識の確認

### 「環境変数を使わない」について

**正確には：**  
「**.env ファイル由来の環境変数**は使わない」という方針です。

- **Secret Manager を使う場合**：`process.env` ではなく `defineSecret().value()` で取得するので、この値は**環境変数とは別の仕組み**です。
- **環境変数そのもの**：Cloud Run には従来どおり環境変数の仕組みがあり、Firebase が自動で渡す `FIREBASE_CONFIG` などは今後も使われます。

### 「環境変数とは別もの」について

**はい、別の仕組みです。**

| | 環境変数（process.env） | Secret Manager（defineSecret） |
|--|------------------------|--------------------------------|
| **値の置き場所** | Cloud Run の設定 or .env 経由 | Google Cloud Secret Manager |
| **取得方法** | `process.env.KEY` | `defineSecret('KEY').value()` |
| **管理の入口** | .env / Cloud Console | `firebase functions:secrets:set` / Secret Manager API |

---

## 2. 比較一覧

| 観点 | 環境変数 | Secret Manager |
|------|----------|----------------|
| **デプロイで変わるか** | .env 由来なら **変わる**（上書きされる） | **変わらない** |
| | Console で直接設定しただけなら変わらない | 値は Secret Manager 側で管理 |
| **保存場所** | Cloud Run の設定（キー・値を保持） | Secret Manager（暗号化して保存） |
| **ログ・コンソールでの可視性** | コンソールで名前・値が見える場合がある | **値は原則非表示**（名前のみ） |
| **アクセス制御** | Cloud Run の閲覧権限があれば見える可能性 | **IAM で細かく制御**できる |
| **取得の仕方** | `process.env.KEY` のみ | 関数ごとに `secrets: [xxx]` を**明示的にバインド**が必要 |
| **更新時の流れ** | 再デプロイ or リビジョン更新 | **Secret の値だけ更新**すればよい（再デプロイ不要） |
| **利用の手軽さ** | **シンプル**（バインド不要、どこからでも読める） | 設定・バインドが必要 |
| **ローカル・エミュレータ** | .env でそのまま使える | エミュレータでの扱いが複雑な場合がある |
| **コスト** | Cloud Run に含まれる（追加課金なし） | 無料枠あり、超過分はアクセス数に応じて課金 |
| **監査・ログ** | 標準の Cloud Run ログ | **Secret アクセスのログ**が別途取れる |

---

## 3. 環境変数のメリット

1. **実装が簡単**
   - `process.env.KEY` で参照するだけ
   - 関数オプションに何も書かなくてよい

2. **どの関数でも使える**
   - 関数の `secrets` にバインドしなくても、Cloud Run の環境変数なら同じサービス内で共有される

3. **ローカル開発が楽**
   - `.env` を置いて `require('dotenv').config()` するだけで使える
   - エミュレータでもそのまま動かしやすい

4. **既存の仕組みと相性が良い**
   - 多くのライブラリが `process.env` を前提としている
   - 導入・理解のコストが低い

5. **追加コストがない**
   - Cloud Run の料金に含まれる

---

## 4. Secret Manager のメリット

1. **デプロイで上書きされない**
   - .env を読まない
   - 一部関数だけデプロイしても、他の値には影響しない

2. **セキュリティ**
   - 暗号化して保存
   - 値はコンソールに表示されない
   - IAM でアクセスを制御できる

3. **更新がデプロイ不要**
   - Secret の値を更新するだけで、次回の関数実行から新しい値になる
   - コードの再デプロイは不要

4. **リポジトリに秘密を載せない**
   - コードや .env に書かない
   - 複数プロジェクトに同じコードをデプロイしても、プロジェクトごとに別の値を保持できる

5. **監査しやすい**
   - Secret の参照履歴をログに残せる

---

## 5. どのように使い分けるか

| 用途 | 向いている方 |
|------|--------------|
| **API キー・トークン（LINE, QR など）** | Secret Manager |
| **デプロイで変えてほしくない値** | Secret Manager |
| **リポジトリ外で管理したい値** | Secret Manager |
| **ログレベル、フラグなど非機密の設定** | 環境変数 |
| **ローカル開発の利便性を最優先** | 環境変数（.env） |
| **極力シンプルにしたい** | 環境変数 |

---

## 6. まとめ

- **環境変数**：簡単・低コストだが、.env 由来だとデプロイで上書きされ得る。
- **Secret Manager**：デプロイの影響を受けず、機密管理・監査に向く一方で、実装と運用の手間は増える。
- 本番の API キー・トークンは **Secret Manager**、それ以外の気軽な設定は **環境変数** という使い分けが一般的です。
