# UIデザイン調整 作業ルール

> ⚠️ このフォルダ配下のすべてのドキュメント・作業は、このルールに従って進める。

---

## フォルダ構成

```
docs/UIデザイン調整/
  00_作業ルール.md           ← このファイル
  00_暫定メモ_方針決定経緯.md ← 方針決定の経緯メモ（暫定）
  01_タスク一覧.md           ← 全グループの進捗管理表
  G1_ホーム画面/             ← グループごとのフォルダ
  G2_レスポンシブ/
  G3_ログイン画面/
  G4_Terminalインジケーター/
  G5_テーマ/
  G6_バグ修正/
  G7_要検討/
  99_全体確認用ドキュメント.md ← 全修正完了後の最終確認用（最後に作成）
```

各グループフォルダの中身（作業を通じて順番に作成する）:

> グループをまたぐ連携事項は `02_申し送り・グループ間連携メモ.md` に集約する。各グループの設計着手前に必ず参照すること。

```
Gx_xxxx/
  設計.md         ← 問題の再確認・修正方針の詳細
  changeSpec.md   ← どのファイルのどこをどう修正するか
  確認手順.md     ← このグループの修正後に確認する内容
```

---

## 各グループの作業フロー

### Step 1: 問題の再確認（設計着手前に必ず実施）

- タスク一覧や方針決定メモをベースとしつつ、**フラットに・先入観なく**改めてコードを読む
- 「本当にそれが問題なのか」「具体的に何が問題なのか」を確認する
- 方針決定時の判断と矛盾があれば、作業前にユーザーへ確認する

### Step 2: 設計（`設計.md` の作成）

- 修正対象ファイル・修正箇所・修正方針を具体的に記載する
- 複数の修正案がある場合は選択肢と推奨理由を明記する
- **人間の最終確認・承認を得てから次のステップへ進む**（設計だけで実装に入らない）
- 設計が確定したら `設計.md` に「確定」と日付を記入する

### Step 3: changeSpec の作成（`changeSpec.md` の作成）

- 設計確定後、「どのファイルのどの行を・どのように・なぜ変更するか」を記述する
- 新規作成ファイルがある場合はその内容の概要も記載する
- 削除・移動があれば明記する

### Step 4: 確認手順ドキュメントの作成（`確認手順.md` の作成）

- 修正後に人間が確認すべき内容を表形式でまとめる
- 記載する内容:
  - 確認する画面・機能
  - ホーム画面からのアクセス手順（何をタップすればその画面に到達できるか）
  - 各画面で確認すべき具体的なポイント
  - 推奨確認端末
- changeSpec 作成と並行して作成してよい

### Step 5: コードの修正（実装）

- changeSpec に従い実装する
- changeSpec にない変更は行わない（追加変更が必要な場合は changeSpec を先に更新してユーザーへ確認）
- 実装中に発見した新たな問題は実装を止めてユーザーへ報告する

### Step 6: AI 自己確認（実装直後・人間確認前に必ず実施）

以下を順番に実施し、結果を簡潔にユーザーへ報告する。

1. **設計書との照合**: `設計.md` の修正方針がコードに反映されているか確認
2. **changeSpec との照合**: 全変更箇所が changeSpec 通りになっているか確認
3. **静的解析**: `flutter analyze` を実行しエラー・警告がないか確認
4. **計算値の数値検証**: 画面サイズから高さ・幅を計算している箇所は、推奨端末の実際のサイズを当てはめて数値が正しいか手動計算で検証する
   - 例: iPad Air 11"（1668×2388px / 264ppi → 論理サイズ約820×1180px）
   - 例: Redmi Pad SE 11"（1920×1200px / 207ppi → 論理サイズ約約800×1280px 横向き）
5. **その他**: 有効なテスト手段があれば実施する（ウィジェットテスト等）
6. 上記で問題が発見された場合は修正してから人間確認に進む

### Step 7: 人間確認

- `確認手順.md` に従い人間が実機で確認する
- 確認完了後 `01_タスク一覧.md` の該当グループのステータスを「完了」に更新する

---

## 確認ドキュメントのルール

| ファイル | 作成タイミング | 目的 |
|---------|-------------|------|
| `Gx_xxxx/確認手順.md` | changeSpec 作成と並行 | そのグループの修正完了時に使う確認手順 |
| `99_全体確認用ドキュメント.md` | 全グループの修正が完了した後 | 全修正の最終確認（回帰確認含む） |

---

## 品質・判断に関するルール

- **予想工数に迎合しない**。効率よく・適切なアプローチを選ぶ。工数が変わる場合はユーザーへ報告する
- **タスク一覧の「確定」フラグはAI判断**。実際の採否は設計確認時にユーザーが決定する
- 設計・実装中に「方針決定メモの内容と実態が違う」と気づいた場合は、実装前にユーザーへ確認する
- グループ間で実装順の変更が合理的な場合は提案してよい
