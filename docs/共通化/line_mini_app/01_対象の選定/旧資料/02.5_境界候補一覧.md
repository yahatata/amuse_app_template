# 境界候補一覧（LINE ミニアプリ・退避・判断用）

**`02.5_基盤業務境界整理.md` で「境界候補」としたものだけを抜き出した。**  
**staff（スタッフ向けミニアプリ）**と **user（来店客・エンドユーザー向けミニアプリ）** で HTML 構造・ページ集合・表示経路が揺れる帯域。**基盤 HTML/CSS だけ先に進めると整合が崩れやすい**ため、人間が軸を決める前提の一覧。

**関連**: `02_共通化価値評価.md` / `02.5_基盤業務境界整理.md` / `02.5_業務候補一覧.md`

---

## 凡例（人間目線の例）

- **スタッフ（staff 画面）**: `public/staff` 想定。シフト・勤怠・店舗オペ寄り。`alert` や `window` 公開の扱いが user と違いやすい。
- **ユーザー（user 画面・LIFF）**: `public/user` 想定。注文・カート・来店導線。`showError` やモーダル寄りのパターンが混じりやすい。

---

## 1. （変更なし）QR コード表示エリアの状態遷移

| 項目 | 内容 |
|------|------|
| **境界に置いた理由（要約）** | 状態機械は横断的だが、**staff は `alert` / user は `showError`** など**通知経路差**が表示ポリシーと密結合（`02` 備考）。 |
| **スタッフの具体例** | 受付 QR の「生成中・表示中・エラー」表示。失敗時にネイティブ `alert` で済ませ、客側とは違う見せ方になることがある。 |
| **ユーザーの具体例** | 客側で QR 読み取り待ち・期限切れ・再発行の案内。インライン文言とトーンの統一がポリシー領域。 |

---

## 2. LIFF / Firebase 認証フロー（`liff.init`〜`signInWithCustomToken`・タイムアウトまで）

| 項目 | 内容 |
|------|------|
| **境界に置いた理由（要約）** | **初期化シーケンス本体**。`window` 公開・Callable 準備と隣接し、staff / user で**待ち時間・再試行 UX**が分岐しうる。 |
| **スタッフの具体例** | 出勤前に開くとログイン待ちが長い／タイムアウト時に「再読み込み」の文言をどう出すか、運用で決まりやすい。 |
| **ユーザーの具体例** | 初回起動で LIFF が遅い／トークン失効時に静かに失敗させない、など**客の離脱**に直結するフロー。 |

---

## 3. 初期化後の `window` 公開（`Firebase` / `LiffFirebase` / staff の `getFunctions` 等）

| 項目 | 内容 |
|------|------|
| **境界に置いた理由（要約）** | staff / user で**グローバル公開形が異なる**。初期化完了の定義とセットで切り出し線を決める必要がある。 |
| **スタッフの具体例** | `getFunctions` や Callable 名の前提が staff 固有。共通ラッパに寄せると user 側の制約と衝突しうる。 |
| **ユーザーの具体例** | user は最小限の API だけ見せたい／デバッグ用グローバルを出さない、など**攻撃面と開発体験**の境目。 |

---

## 4. （変更なし）グローバル処理中オーバーレイ

| 項目 | 内容 |
|------|------|
| **境界に置いた理由（要約）** | **`executeWithGlobalLoading` と一体化**している箇所が多く、非同期ヘルパーと**対で決めないと基盤だけ取り出せない**。 |
| **スタッフの具体例** | シフト一括取得・カレンダー再描画中に画面全体を覆う。メッセージは「読み込み中」で統一するか業務ごとに変えるか。 |
| **ユーザーの具体例** | 注文確定の待ちを全面オーバーレイにする／軽い操作はスピナーのみ、など**客への圧**の設計。 |

---

## 5. （変更なし）非同期実行ヘルパー（ボタン disable・文言差し替え・オーバーレイ包み）

| 項目 | 内容 |
|------|------|
| **境界に置いた理由（要約）** | **ガイドライン維持 vs API 抽出**の境目。オーバーレイ・グローバルロードとの整合が必要。 |
| **スタッフの具体例** | 「保存」連打防止でボタンを無効化し、失敗時だけ元に戻す。カレンダー画面と会計画面で文言テンプレが揃うかは論点。 |
| **ユーザーの具体例** | カート更新中は操作ロック／エラー時にボタンを戻すまでの一貫性。客の「押したのに反応しない」ストレスとの折り合い。 |

---

## 6. （変更なし）マルチページの表示切替（showPage）

| 項目 | 内容 |
|------|------|
| **境界に置いた理由（要約）** | **ページ集合・`requestAnimationFrame` 利用の有無**など staff / user で差がある。ナビ規約と一体。 |
| **スタッフの具体例** | シフト・勤怠・設定のページ切替。DOM が重く rAF で段階表示するなど、user よりオペ向け最適化が入りやすい。 |
| **ユーザーの具体例** | メニュー・カート・履歴の `showPage`。客はページ数が少なく、遷移アニメや戻る導線の扱いが staff と別問題になりうる。 |

---

## 7. （変更なし）URL ハッシュに基づく画面オープン・ナビゲーション

| 項目 | 内容 |
|------|------|
| **境界に置いた理由（要約）** | **ディープリンク・業務パラメータ**（`#shift?…` 等）と参照ルールが絡む。 |
| **スタッフの具体例** | 勤怠から特定日シフトへ直リンク。ブックマークから開いたときの初期化順と表示の整合。 |
| **ユーザーの具体例** | キャンペーン URL から特定ページを開く。客向けはパラメータを限定し、内部 ID を晒さない、など。 |

---

## 8. （変更なし）初期化失敗向けインラインエラー表示・再試行 UI

| 項目 | 内容 |
|------|------|
| **境界に置いた理由（要約）** | **初期化フロー × 表示ポリシー**。`alert` / `showError` / インラインの**三経路**とセット。 |
| **スタッフの具体例** | Firebase や LIFF 初期化失敗時、画面上部にエラー＋再試行。固まった画面をどう説明するかは店舗サポート都合も絡む。 |
| **ユーザーの具体例** | 客が迷子にならない一文・「LINE に戻る」導線の有無。staff より感情に配慮したコピーが必要になりやすい。 |

---

## 9. `confirm` を伴う確認フロー（カート削除・注文確定・シフト削除等）

| 項目 | 内容 |
|------|------|
| **境界に置いた理由（要約）** | **ネイティブ confirm / モーダル / インライン**の三経路。**業務操作**に紐づくが、カート本体は業務候補として別ファイル。 |
| **スタッフの具体例** | シフト申請削除・勤怠確定取消で `confirm`。ネイティブのままか、店舗ブランドに合わせたモーダルにするかは境界。 |
| **ユーザーの具体例** | カート全削除・一括注文の最終確認。`confirm` とカートモーダルの**見た目の温度差**をどう埋めるか。 |

---

## 10. `alert` による単純通知（成功・エラー・注意の一方通行）

| 項目 | 内容 |
|------|------|
| **境界に置いた理由（要約）** | **表示ポリシー主軸**。`showError` 併用箇所との整理が要る。 |
| **スタッフの具体例** | 保存完了や軽いバリデーションエラーを `alert`。一覧ページでは邪魔、編集画面では許容、など画面センスで混在しうる。 |
| **ユーザーの具体例** | user では `alert` を避けたいが、緊急の一本化メッセージでは使う、など**客への品質**と開発コストの折り合い。 |

---

## 11. リスト・埋め込み領域の待機・空表示・汎用エラーのプレースホルダパターン

| 項目 | 内容 |
|------|------|
| **境界に置いた理由（要約）** | 「型」の共通化は基盤に近いが、**業務 HTML と同一関数内混在**しうるため切り出し線を人間が決める（`01.5`）。 |
| **スタッフの具体例** | カレンダーセル枠の「読み込み中…」プレースホルダと、セル内の業務 HTML を同じブロックで組んでいる。 |
| **ユーザーの具体例** | メニュー一覧のスケルトンと、実際の商品カード生成。デザインを揃えると業務テンプレまで引っ張られる。 |

---

## 12. （変更なし）実行時設定の参照・Firestore 上書き（`__CONFIG__`）

| 項目 | 内容 |
|------|------|
| **境界に置いた理由（要約）** | **読取タイミング・user の Firestore 上書き未実装**等、参照ルールの揺れが主題。 |
| **スタッフの具体例** | 機能フラグで勤怠 UI を出し分け。初期表示で一度古い設定がチラつく、など順序依存の体験。 |
| **ユーザーの具体例** | メンテ表示・注文停止フラグ。客向けは**誤表示の許容度が低い**ため、参照の一貫性が重要。 |

---

## 13. ページ骨格・コンテナ・`.page` 等のレイアウト基盤

| 項目 | 内容 |
|------|------|
| **境界に置いた理由（要約）** | **トークン／規約 vs 再利用コンポーネント**の軸が揺れる。ボタン・スピナー（基盤）との距離は Step3。 |
| **スタッフの具体例** | 多ページ・高密度 UI。`.page` の余白・ヘッダ固定でオペ効率を確保。 |
| **ユーザーの具体例** | シンプルな縦スクロール・安全ゾーン。staff と同じシェル HTML に寄せると客には窮屈、など。 |

---

## 14. （変更なし）非同期完了後の画面更新・モーダル操作

| 項目 | 内容 |
|------|------|
| **境界に置いた理由（要約）** | **業務フロー依存**が強い。オーバーレイ候補とは別枠のまま整理。 |
| **スタッフの具体例** | 勤怠登録後にカレンダーを閉じて一覧へ戻る／モーダル内で完結させる、などオペ手順で分岐。 |
| **ユーザーの具体例** | 注文完了後にカートを空にしてトップへ／完了モーダルだけ閉じる。客の次の行動をどこに誘導するか。 |
