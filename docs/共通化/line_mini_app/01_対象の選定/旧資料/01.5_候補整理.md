## 3. 境界衝突候補一覧

| 候補名 | ぶつかっている境界 | 理由 | Step2 での扱い注意 |
|--------|---------------------|------|---------------------|
| 初期化失敗向けインラインエラー表示・再試行 UI | UI コンポーネント vs UX・画面挙動ルール（表示ポリシー） | DOM 部品だが「いつ再試行／何を出すか」はフロー依存 | 部品の良さだけ／ポリシーだけで判断しない |
| `confirm` / `alert` 系 | ルール vs インラインエラー UI | 同一内容を `showError` と `alert` の両方で出す箇所がある | **三経路**（インライン・モーダル・ネイティブ）の軸を短文で決めてから評価 |
| グローバル処理中オーバーレイ | UI コンポーネント vs 非同期二重操作防止 | オーバーレイと `executeWithGlobalLoading` が一体 | メッセージ引数の是非はルール寄り |
| 非同期実行ヘルパー | ルール vs helper / util 実装 | ガイドライン化か関数抽出か | 「ダメな延ばし方」の禁止と「推奨 API」の両方を視野 |
| リストプレースホルダパターン | helper vs 業務 HTML 組み立て | 境界を分けたが呼び出しが同一関数内に混在しうる | 業務行は**分割前提**として雑にまとめ評価しない |
| 実行時設定（`__CONFIG__`） | service / 初期化 vs 参照ルール | `config.js` のメソッドと `index.html` の `await` タイミング | **設定値そのもの**ではなく参照・上書き・読取タイミングを評価 |
| LIFF 認証フロー本体 | 初期化フロー vs helper（fetch URL） | `functionsUrl` 等がフローに埋まっている | 切り出しの是非は価値と複雑さで Step 2 で扱う |
| カートモーダル（補足） | UI vs confirm ルール | モーダル＋`confirm` が直列 | user のみの候補として staff 同等を期待しない |

## 4. Step 2 に入る際の注意点

1. **着地先（仮）は確定ではない**。helper に落とす／shared script にする等、Step 2 で変えてよい。
2. **共通コンポーネント向き**だけを「画面に効く」と決めつけず、**ルール / service 向き**も同列で評価する（二重送信・初期化・表示ポリシー）。
3. **分割した行は別々に評価**してよい。元候補名で束ねて 1 回の「残す／落とす」にしない。
4. **境界衝突候補**は Step 2 冒頭で整理軸を 1 文書くと、評価のブレが減る。
5. **staff / user の両方にあるか**だけで価値を決めない。user のみ（カート）・staff のみ（大規模カレンダー）も補足・分割前提として別扱い。
6. **`config.js` は設定値の比較ではなく**、`loadLinePlanFromFirestore` の有無・`await` の型・機能フラグ参照の揺れを評価する。
7. **類似パターン数**は補助情報のままにし、分割後の再カウントに時間をかけすぎない。
8. **ページ骨格・`.page` 等のレイアウト基盤**は、**ルール / 共通基盤**と**広義のコンポーネント**の解釈が両立しうる。Step 2 では「トークン・規約中心か、再利用パーツ中心か」を先に決めず、価値の書き方だけブレないようにする。
