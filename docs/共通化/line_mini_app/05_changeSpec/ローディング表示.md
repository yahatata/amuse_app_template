## 1. 目的

本 changeSpec は、LINE ミニアプリ（`public/`）におけるローディング表示・操作ロックの実装方針を定める。

目的は、処理中であることをユーザーに明確に伝え、二重タップ・連打・誤操作を防ぎ、画面ごとの挙動差を減らすことである。

本 changeSpec では、ローディングが必要な箇所に対して実装を行う。  
実装するローディング表示は、既存の共通ヘルパ・共通 CSS を活用し、基本的には共通の形式に寄せる。

ただし、すべての箇所を同一の表示範囲・同一のロック強度にするものではない。

---

## 2. 基本方針

### 2.1 共通方針

- ローディング表示の見た目・ヘルパ・解除順序は共通化する。
- 既存の `showGlobalLoading` / `hideGlobalLoading` / `executeWithButtonLoading` / `executeWithGlobalLoading` / `.spinner` / `.global-loading-overlay` 等を活用する。
- 成功・失敗の両方で、`finally` 相当によりローディング・ロックを解除する。
- 結果表示は、ローディング・ロック解除後に行う。
- ボタン単位のみのローディングを、更新系の標準とはしない。
- `confirm` 確定後に `await` する処理では、確定後から処理完了まで送信中表示を出す。
- 共通化するのは「見た目・ヘルパ・解除順序・基本ルール」であり、すべてをグローバルオーバーレイに統一するものではない。

### 2.2 類型別方針

| 類型 | 方針 |
|------|------|
| 画面表示時の読込 | 既存の `#loading`・進捗表示・再試行 UI を基本とする。今回の個別改修対象にはしない。 |
| 画面内ユーザー操作による読取系処理 | 待機状態が見えない箇所に spinner 等の待機表示を追加する。原則として強い操作ロックは追加しない。 |
| 画面内ユーザー操作による更新系処理 | ローディング表示と操作ロックを原則セットで扱う。同一処理の再実行、状態不整合、処理中 UI の回避を防ぐ。 |

### 2.3 表示単位・ロック単位

表示単位・ロック単位は、処理文脈に応じて決める。

| 単位 | 用途 |
|------|------|
| ページ全体 | ページ全体の操作を止めるべき更新処理 |
| セクション単位 | QR 領域、注文領域、カレンダー領域など、処理対象が限定される場合 |
| モーダル単位 | モーダル内で完結する更新処理 |
| 行・カード単位 | 一覧内の一部だけが処理対象の場合 |

### 2.4 CSS の適用範囲（ユーザー／スタッフ）

- **`public/user/index.html`** は `common.css` と **`user.css`** を読み込む想定である。
- **`public/staff/index.html`** は現状 **`common.css` のみ**を読み込んでおり、**`user.css` は参照しない**。

そのため、**ユーザー／スタッフの両方で共有する** `.spinner`・`.global-loading-overlay`・`.global-loading-content`・セクション用 overlay クラスなどは、原則 **`public/css/common.css` で定義・変更する**。`user.css` はユーザー画面固有の上書き・拡張に留める。

## 3. 冪等性との関係

本 changeSpec で実装するローディング表示・操作ロックは、ユーザーの二重タップ・連打・誤操作を減らすための **クライアント側の一次防御** である。

ただし、クライアント側のローディング表示・UI ロックだけでは、更新系処理における重複実行・二重更新・状態不整合を完全には防げない。

たとえば、以下のようなケースはクライアント側だけでは防ぎきれない。

- 通信遅延中の再送
- 画面リロード
- ブラウザバック
- LIFF / WebView の制約による操作抑止漏れ
- 別端末からの同時操作
- タイムアウト後の再実行
- 前回処理が Cloud Functions 側では成功していたが、クライアント側では失敗に見えるケース

そのため、更新系処理における最終的な重複実行防止・状態不整合防止は、**Cloud Functions / HTTP API 側の冪等性・状態チェック・重複防止**で担保する。

本 changeSpec では、LINE ミニアプリ側のローディング表示・操作ロックを実装する。  
一方で、Cloud Functions / HTTP API 側の冪等性確認・実装は、本 changeSpec の直接スコープ外とし、別途確認対象とする。

### 3.1 更新系処理での扱い

更新系処理では、クライアント側で以下を行う。

- 処理中であることを spinner / overlay 等で表示する
- 同一処理の再実行を防止する
- 関連ボタン・関連入力を disabled にする
- 処理中 UI を別導線・戻る・閉じる等で回避しにくくする
- 成功・失敗の両方で finally 相当により解除する

ただし、これらはあくまで一次防御である。  
更新処理の安全性は、最終的には Cloud Functions / HTTP API 側で担保する。

### 3.2 冪等性確認が特に重要な対象

本 changeSpec の対象のうち、以下は特に Cloud Functions / HTTP API 側の冪等性・状態チェック確認が重要である。

| No | 対象箇所 | 確認観点 |
|---:|----------|----------|
| 19 | user 登録フォーム submit → `createUserAccount` | 二重登録・重複 user 作成が **防げているか** |
| 20 | user QR 手動再生成 → `generateQRCode` | QR の多重発行・期限競合が問題にならないか |

## 6. 個別 To-be

### 6.1 No.10 `showAllTournamentsCalendar`

#### 現状

- `getUpcomingTournaments({ includeAll: true })` を呼ぶ読取系処理。
- Callable 待ちだが、視覚的待機表示がない。

#### To-be

- 全トーナメントカレンダー取得中は、対象セクション内に共通 spinner を表示する。
- ページ全体ロックは行わない。
- 取得完了後、spinner を解除して一覧・カレンダーを表示する。
- 取得失敗時は、既存のエラー表示方針に従う。

### 6.2 No.12 `loadSubmittedShiftsList`

#### 現状

- 提出済み申請リスト取得中に、テキスト「読み込み中…」中心の待機表示がある。
- `.spinner` ではないが、最低限の待機表示は成立している。

#### To-be

- 提出済み申請リストの取得中は、対象セクション内に共通 spinner を表示する。
- ページ全体ロックやグローバルオーバーレイは使用しない。
- 読取系であるため、強い操作ロックは追加しない。
- 取得完了後、spinner を解除して一覧を表示する。
- 取得失敗時は、既存のエラー表示方針に従い、必要に応じて再試行導線を表示する。

### 6.3 No.13 シフト申請 `renderCalendar` チェーン

#### 現状

- 営業時間、申請済み日付、不足日関連など、カレンダー描画に関わる読取がある。
- グローバル spinner は基本ない。
- チェックマーク等の反映は後追いで行われている。

#### UX・他画面との統一からの推奨（適切な主軸）

仕様では読取の不定待ちは **`.spinner` に統一**（セクション内でよい）。確定シフトタブ（No.14）は **`calendar-grid` 内 `.spinner`** で待っている。

| フェーズ | 推奨 | 理由 |
|----------|------|------|
| **ブロッキング待ち**（カレンダー格子を描画するまで内部で `await` している読取があり、画面が空または古いままになりうる） | **`#calendar`（またはカレンダーを載せるセクション容器）内に共通 `.spinner`** | No.14 と同パターンで統一でき、読取の「ページ全体 overlay は原則避ける」とも整合する。 |
| **非ブロッキングの後追い反映**（申請中日付のチェックマークなど、格子は既に触れる状態でマークだけ更新） | **原則ローディングを増やさない**。必要時のみカレンダー上部など **一行の「反映中…」等の軽いテキスト**や極小インジケータを検討 | 後追いだけに大きな spinner を重ねるとちらつき・操作の妨げになりやすい。文言のみを単独の標準とすると §8.2 の「spinner 統一」とずれるため **補助**にとどめる。 |
| **月切替・再描画の連打** | 二重取得・崩れが出る場合のみ **前月／翌月ボタンの一時 disabled**（読取で許容される弱い抑止） | 読取系に強いページロックは避ける。 |

**結論（実装の優先）**: **ブロッキング部分＝セクション内 `.spinner`** を主とする。**後追いチェックマークは基本サイレント**、運用上「反映が遅い」と判明したときだけ軽い文言を足す。

#### To-be（要約）

- カレンダー全体を強くロックするページ全体 overlay は行わない。
- ブロッキング読取がある場合は、**確定シフトと揃えてカレンダーセクション内 `.spinner`** を出す。
- 後追い反映については上表に従い、過剰なグローバル／全面 spinner は避ける。
- 月切替等で二重取得が問題になる場合のみ、ナビボタンの一時 disabled を認める。

### 6.7 No.23 `orderAllItems`

#### 現状

- 一括注文は `placeOrderByUser` を伴う更新系処理。
- 現状でもカート内 spinner と `#order-all-btn` disabled はある。
- ただし、ロック範囲がカート内中心であり、注文関連の別操作・別導線を回避できる可能性がある。

#### To-be

- 表示単位・ロック単位は注文領域全体を基本とする。
- 一括注文送信中は、注文領域全体に spinner または overlay を表示する。
- 少なくとも以下の操作を処理中は抑止する。
  - 一括注文ボタンの再押下
  - カート内の数量変更
  - カート内の商品削除
  - 単品注文ボタン
  - 注文ページ内で同一注文状態を変える操作
- **必要に応じて**、注文ページ内のカテゴリ切替やメニュー操作も抑止する（過剰ロックにならないよう実装時に判断。チェックリストでは任意とする）。
- ページ全体ロックまでは必須としない。
- ただし、注文処理を回避できる導線が残る場合は、注文ページ全体 overlay を検討する。
- 成功・失敗の両方で、finally 相当でローディング・ロックを解除する。
- 結果表示は解除後に行う。

## 7. 共通ヘルパ・共通スタイル To-be

### 7.1 共通ヘルパ

対象:

- `showGlobalLoading`
- `hideGlobalLoading`
- `executeWithButtonLoading`
- `executeWithGlobalLoading`

To-be:

- `showGlobalLoading` / `hideGlobalLoading` は、ページ級または広範囲の更新処理で使える共通 overlay として維持・補強する。
- `executeWithGlobalLoading` は、更新系の標準ラッパーとして利用できるようにする。
- `executeWithButtonLoading` は、更新系の標準とはしない。
- `executeWithButtonLoading` を使う場合でも、更新系ではセクション overlay やグローバル overlay と組み合わせる。
- すべてのラッパーは、成功・失敗の両方で finally 相当の解除を保証する。
- 二重ローディングにならないよう、`#loading`・セクション spinner・グローバル overlay の使い分けを整理する。

ユーザー／スタッフでヘルパ実装が二重にある場合、挙動の差が出ないよう **必要に応じて双方を同じ解除・メッセージ規約に揃える**（§2.4 と合わせて確認）。

### 7.2 共通スタイル

対象:

- `.spinner`
- `.global-loading-overlay`
- `.global-loading-content`
- 必要に応じたセクション overlay 用 class

To-be:

- 不定の待機表示は `.spinner` を基本とする。
- ページ級ローディングは `.global-loading-overlay` を基本とする。
- セクション単位の処理には、必要に応じてセクション overlay / inline spinner を使う。
- 読取系に対しては、強い overlay ではなく、対象セクション内 spinner を優先する。
- 更新系に対しては、処理中 UI を回避できない範囲で overlay / disabled / pointer-events を組み合わせる。
- overlay の見た目と実際のロック範囲がずれないようにする。

**スタッフ画面は `user.css` を読み込まない**ため、両画面で共通にしたい定義は **`common.css` に置く**（§2.4）。

## 8. 実装時チェックリスト

### 8.1 共通

- [ ] 成功・失敗の両方でローディングが解除される。
- [ ] `finally` 相当で解除されている。
- [ ] 結果表示はローディング・ロック解除後に行われる。
- [ ] 二重ローディングになっていない。
- [ ] spinner / overlay の見た目が既存共通 CSS と整合している。
- [ ] `alert` / `confirm` を処理中ロックの本体として使っていない。

### 8.2 読取系

- [ ] 待機状態が無反応に見えない。
- [ ] 不定の待機表示は spinner に寄せている。
- [ ] 原則として強い操作ロックを追加していない。
- [ ] セクション単位の表示に留めている。
- [ ] キャッシュ・先読み・後追い反映に過剰なローディングを出していない。

### 8.3 更新系

- [ ] ローディング表示と操作ロックがセットになっている。
- [ ] ボタン単位のみで完結していない。
- [ ] 同一処理の再実行を防止している。
- [ ] 関連ボタン・関連入力が disabled になっている。
- [ ] `confirm` 後 await の無反応が解消されている。
- [ ] 処理中 UI を別導線・戻る・閉じる等で回避できないよう、可能な範囲で抑止している。
- [ ] クライアント側のローディング・UI ロックは一次防御として扱い、最終的な重複実行防止・状態不整合防止は Cloud Functions / HTTP API 側の冪等性・状態チェックで担保する前提になっている。

## 9. 受け入れ条件

- 対象 No について、処理中であることが画面上で分かる。
- 更新系について、少なくとも同一処理の再実行が防止されている。
- 更新系について、関連操作による状態不整合・二重送信リスクが下がっている。
- 読取系について、待機状態が無反応に見えない。
- 共通ヘルパ・共通 CSS の利用により、画面ごとのローディング表現のばらつきが減っている。
- 成功・失敗の両方で、ローディング・ロックが解除される。
- 結果表示は、ローディング・ロック解除後に行われる。
- クライアント側ロックを最終防衛とせず、更新系の最終的な安全性は Cloud Functions / HTTP API 側の冪等性・状態チェックで担保する前提が維持されている。
- config 系、静的ページ、バックグラウンド先読み、定期読取には不要なローディングが追加されていない。
- **スタッフ画面でも**、`common.css` に定義した共通 spinner／overlay が意図どおり表示される（`user.css` にだけ追加してスタッフが変わらない、という状態になっていない）。
