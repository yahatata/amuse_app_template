|----------|----------|------|

| **LIFF スタッフ** | `public/staff/index.html` | `alreadyRegistered` 時は完了メッセージと区別して `showSuccess('このアカウントは既に登録済みです。')`。`success` 検証を追加。 |

## 注意・確認してほしい点

1. **LIFF 実機** で、登録／QR／カート／注文／シフト／勤怠修正／トーナメント参加の各フローで overlay が二重にならないか。  
2. **修正申請フォーム** で送信後、`correction-type` の状態に応じた入力の disabled が期待どおりか。  
3. **シフト提出（No.27）** 成功後、`initializeCalendar` は非同期描画のため、**グローバル overlay 解除がカレンダー描画完了より先**になることがある。主処理は「申請送信」であり、続くカレンダー再描画は読取・反映フェーズなので **許容しやすい** が、「送信完了直後に一瞬だけ古いカレンダーが見える」などが気になる場合は、(a) **送信完了後は overlay を外し、カレンダー領域だけ spinner／反映中表示に切り替える**（自然になりやすい）、または (b) **主要描画完了まで global overlay を維持する**、のどちらかを検討する。  
4. **注文系** で、単品注文中・一括注文中に、数量変更、カート削除、別商品の注文、カートを閉じる操作が抑止されるか（`order-flow-busy` とモーダル側 `disabled` の組み合わせの実機確認）。  
5. **QR 再生成** で、自動再生成と手動ボタン押下が競合しないか。`regenInFlight` が期待どおり効いているか。  
6. **登録フォーム** で、送信中に入力欄・select・送信ボタンが無効化され、失敗時に再入力可能な状態へ戻るか。  
7. **深リンク確定（No.29）** で、自動実行中に overlay が表示され、完了・失敗どちらでも解除されるか。  
8. **読取系 No.10 / 12 / 13 / 16** で、spinner が異常に出続けないか（エラー時も UI が復帰するか）。  
9. **Cloud Functions 側の冪等性・状態チェック** は本 changeSpec のスコープ外だが、更新系 No.19〜27 / 29 / 30 は **別工程で確認する**（上記「対象外」節および [**CF冪等性_監査メモ.md**](./CF冪等性_監査メモ.md) を参照）。

## 実機テスト：確認項目と操作手順（人間操作の目安）

下表は **「注意・確認してほしい点」1〜9** と対応する **画面上の導線** を結んだものです。店舗設定・プラン（シフト要請など）・データ状態により画面が出ない場合は、該当テストをスキップまたは検証用データで再現してください。

### 補足（画面ラベルとコード上の対応）

- **ユーザー**: ホームの機能名は `home-page` のボタン文言（「入店QR」「注文」「トーナメント」など）。登録は未登録時の初回表示が確実。
- **スタッフ**: 「シフト申請」「確定シフト」は `shift-page` 上部の `#shift-application-btn` / `#confirmed-shifts-btn`。未提出リスト・カレンダーどちらが出るかは **店の締め日程ロジック**（`showShiftApplication` 内の `isNextMonthFinalized` / `isInShiftSchedulingPeriod`）依存。
- **深リンク（No.29）**: ハッシュは `#shift` で始まり、`requestId` と `date` が渡ると要請確認 Callable が非同期実行される（実装は `openShiftManagement` 内）。

以上です。
