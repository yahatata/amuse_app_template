# 保守運用時のエラーログ 仕様書 たたき台

## 1. 背景

各店舗ごとに Firebase プロジェクトを分けて運用する構成では、障害や重要失敗が各プロジェクトに分散する。  
この状態では、提供側が異常に気づくまで時間がかかりやすく、また店舗横断での状況把握もしづらい。

そのため、本仕様では、各店舗プロジェクトで発生する重要な失敗ログを中央監視プロジェクトへ集約し、保守運用時に横断的に扱える状態を目指す。

---

## 2. 目的

本仕様の目的は以下とする。

- 異常の早期検知
- 原因特定の迅速化
- 店舗横断管理

本仕様は、単に「エラーを残すこと」ではなく、  
**中央集約後に運用保守上使えるログに揃えること** を目的とする。

---

## 3. 対象範囲

### 3-1. 本仕様の主対象

本仕様の主対象は、**本リポジトリで管理している Cloud Functions のエラーログ** とする。

初期段階では、Cloud Functions 側を主軸とする。理由は以下。

- 業務ロジックの中核が Functions 側にある
- Firestore 更新、外部連携、安全性が重要な処理が集中している
- クライアント側よりログ形式を統一しやすい
- 店舗横断管理に向いている

### 3-2. 初期段階で主対象にしないもの

初期段階では、以下は主対象に含めない。

- クライアント側の一般エラー
- 高頻度に発生しうる軽微な失敗
- SDK 内部ログや既知ノイズ

クライアント側について将来的に別途検討対象とするのは、主に以下のようなものとする。

- クラッシュ
- 操作不能
- 重要画面の致命的不具合
- Functions 側では十分に把握できないクライアント固有の重大障害

### 3-3. 本仕様で定めるもの

本仕様で定めるのは、主に以下とする。

- 中央集約対象ログの考え方
- `logger.error()` を用いる対象ポリシー
- ログ情報の設計原則
- 共通化の前提
- changeSpec に引き継ぐべき論点

本仕様では、**対象関数の最終一覧** や **具体的なフィールド定義** までは固定しない。  
それらは本仕様を前提として、後続の changeSpec で定義する。

**実装の進め方（本仕様が想定するもの）**  
Cloud Functions は本リポジトリに多数存在するが、**すべての Callable を精査して「エラーを出す／出さない」を一から判断する**ことは、工数が大きく、判断の正しさを機械的に証明することも難しい。  
そのため実装フェーズでは、**既存のエラー出力箇所を起点とする**。ここでいう既存のエラー出力箇所とは、`logger.error()`、`console.error()`、およびランタイムが ERROR として記録する未処理例外など、**現状 Cloud Logging 上で ERROR として把握可能な経路**を指す（いずれも **初期起点**であり、`console.error()` については §5-5 のとおり原則 `logger.error()` へ寄せる）。  
当該箇所について **本仕様および changeSpec で定めるデータ形式に統一する**ことを主とする。  
「何をエラーとみなすか」のポリシーを **全関数に対して最初から棚卸しする**ことと**混同しない**。

## 4. 全体方針

### 4-1. 中央集約の基本方針

各店舗プロジェクトで発生した重要な失敗ログは、各プロジェクトの sink を通じて中央監視プロジェクトへ集約する。  
初期段階では、**severity が ERROR 以上のログ** を中央集約の主軸とする。

### 4-2. 重要失敗を主軸とする

中央集約の対象は、Cloud Functions 内で起きるすべての失敗ではなく、  
**運用保守上追跡価値が高い失敗** を主軸とする。

### 4-3. Firebase 由来の失敗の扱い

Firebase 由来の失敗は、すべてを一律に対象とするのではなく、  
**業務継続や整合性に影響するもの** を対象とする。

例:

- Firestore 書き込み失敗
- transaction failure
- Auth 作成 / 更新失敗
- Cloud Tasks enqueue 失敗
- Functions から見た Firebase 連携失敗のうち、業務継続や整合性に影響するもの

---

## 5. ログ出力ポリシー

### 5-1. 中央集約対象とする失敗は原則 `logger.error()` で出力する

中央集約対象とする失敗ログは、原則として `logger.error()` を用いて出力する。  
これにより、severity を明示し、中央集約および横断比較に耐える形へ寄せる。

### 5-2. すべての失敗を `logger.error()` にしない

Cloud Functions 内で発生するすべての拒否・失敗・例外を、一律に `logger.error()` にするものではない。  
`logger.error()` は、**運用保守上追跡価値が高い失敗** に限定して用いる。

### 5-3. 1失敗につき1件の主ログを原則とする

同一失敗に対して `logger.error()` を複数回出力すると、  
中央集約後の件数比較や状況把握が不正確になる。

そのため、原則として **1つの失敗につき1件の主ログ** を出力する。

### 5-4. `success: false` だけでは中央集約対象としない

レスポンスとして `success: false` を返すだけでは、Logging 上の severity に反映されない。  
そのため、中央集約対象としたい失敗については、必要に応じて別途 `logger.error()` により主ログを出力する。

### 5-5. `console.error()` と `logger.error()` の関係

`console.error()` は Cloud Logging 上は ERROR になりうるが、構造化・共通化・横断比較の観点から**主手段とはしない**。  
中央集約対象として追跡したい**既存の** `console.error()` 出力箇所は、**原則として `logger.error()` に統一する**（データ形式は本仕様および changeSpec に従う）。  
一括置換の負荷・優先順位などの**現実的な進め方**は changeSpec で定める。  
置き換え時は同一失敗に対する **二重出力** にならないよう注意する（§10 の changeSpec で扱う）。

## 6. `logger.error()` の対象とする失敗

`logger.error()` の対象は、**運用保守上追跡価値が高い失敗** とする。  
代表例は以下の通り。

### 6-1. 想定外例外・未処理例外

- 業務処理継続不能な想定外例外
- 想定外の分岐や状態不整合による失敗
- 未処理例外のうち、共通文脈を付与して追跡価値を高めたいもの

### 6-2. 業務継続や整合性に影響する失敗

- 会計完了不能
- 営業開始 / 営業終了処理失敗
- 締め処理失敗
- 状態遷移不整合
- 必要な更新の未完了

### 6-3. Firebase / 基盤連携の重要失敗

- Firestore 書き込み失敗
- transaction failure
- Auth 作成 / 更新失敗
- Cloud Tasks enqueue 失敗

### 6-4. 外部サービス連携失敗

- LINE 連携失敗
- 決済連携失敗
- Webhook 連携失敗
- その他、業務成立条件に関わる外部連携失敗

### 6-5. トランザクション競合・中断のうち最終的に失敗となったもの

- 自動再試行で吸収できず、最終的に失敗となったもの
- 競合頻発などにより業務影響があるもの
- 想定外の競合パターンで処理成立しないもの

### 6-6. 冪等・二重実行の境界異常

- 正常 no-op では吸収しきれない重複疑い
- 想定外の `already exists`
- 二重実行境界で結果が曖昧になる失敗
- イベント重複により整合性が崩れるもの

### 6-7. スケジューラ / バッチ / 非同期自動処理の失敗

- 定期集計失敗
- cleanup 失敗
- 自動補正処理失敗
- enqueue 後続処理失敗
- ユーザー操作なしで進む処理の失敗

### 6-8. デュアルライト・移行中の片側失敗

- 本番系とレガシ系の片側だけ失敗
- migration marker 作成失敗
- 補助集計のみ未完了
- 一見成功に見えるが整合性に影響しうる失敗

### 6-9. Storage / ファイル系の重要失敗

- 画像アップロード失敗
- QR 関連生成失敗
- 署名 URL 取得失敗
- 帳票 / CSV / レシート生成失敗

### 6-10. 設定・Secret・環境不備

- 必須 Secret 欠落
- config 読み込み失敗
- 必須環境変数不足
- deploy 構成不備

### 6-11. 金額・会計・給与に関わる失敗

- 金額不整合
- 会計処理失敗
- 支払方法集計不整合
- 給与計算失敗
- 日次 / 月次集計不整合

### 6-12. セキュリティ・監査上追跡価値がある失敗

- 想定外ロールによる重要操作試行
- 監査上追跡したい権限拒否
- 通常利用では起こりにくい不自然な操作失敗

---

## 7. `logger.error()` の対象としないもの

以下は原則として `logger.error()` の対象外とする。

### 7-1. 想定内の通常拒否

- 単純な入力不足
- 軽微なバリデーションエラー
- 通常の `invalid-argument`
- 想定済みの `already-exists`
- 想定済みの `not-found`
- 通常の未ログインや期限切れ

### 7-2. 再試行で吸収された一時失敗

- 再試行後に正常完了した競合
- 一時的な揺らぎだが業務影響なしのもの

### 7-3. 想定通り no-op として処理できた重複

- 正常に冪等制御が効いたもの
- 正常に重複イベントを無害化できたもの

### 7-4. 運用価値の低いノイズログ

- 既知の App Check ノイズ
- SDK 内部ログ
- 高頻度 warning
- 一時的なデバッグ出力

## 8. ログ情報の設計原則

### 8-1. 共通化前提とする

中央集約対象ログは、対象関数が増減しても運用可能なよう、  
**共通ポリシーおよび共通情報項目** を前提とする。

### 8-2. 最小限の文脈を持たせる

中央集約対象ログは、少なくとも以下を識別可能であることを目指す。

- 失敗類型
- **関数エントリ名**（Callable 名・HTTP エントリ名・スケジューラ／トリガ起点の処理名など、**Cloud Functions 側のエントリとしてログ検索に用いる識別子**。Callable 以外の関数も含む）
- **operation 名**（業務上の操作単位。トランザクション・バッチ・スケジューラ等、複数ステップをまとめて区別する補助識別子）
- project 識別子
- 運用者向け要約メッセージ

「関数名」「処理名」だけでは **用語がぶれる**（言語の関数名と混同する等）ため、上記のように **GCP のログエクスプローラでフィルタ・横断検索しやすい語に寄せる**。

必要に応じて、原因調査に必要な補足情報を持てるようにする。

### 8-3. 機微情報を載せない

以下は原則としてログに載せない。

- request body 全文
- token
- password
- 個人情報の生値
- 決済機密情報
- 大きすぎる payload 全文

### 8-4. 詳細スキーマは changeSpec で定義する

ログの具体的なフィールド名、型、ネスト構造、共通関数 I/F、出力例は、  
本仕様を基に作成する changeSpec にて定義する。

### 8-5. 用語とフィールド名（changeSpec で確定）

§8-2 における **関数エントリ名**・**operation 名** 相当の情報は、**Cloud Logging 上の jsonPayload／labels 等で検索しやすいキー名と値の取り決め**に落とし込む。  
具体的な **フィールド名（例: `functionEntryName`, `operationName`）・必須可否・列挙値** は本仕様では固定せず、changeSpec で定義する。

## 9. 補足方針

### 9-1. 未処理例外とランタイムログの関係

未処理例外については、ランタイムが ERROR 相当のログを残す場合がある。  
そのため、未処理例外すべてに対して手動で `logger.error()` を追加することを、現時点では一律必須とはしない。

ただし、**共通文脈を付与したいもの** については、最上位で捕捉して `logger.error()` により補足情報を付けたうえで再 throw または整形する方針を、changeSpec で必要に応じて定義する。

### 9-2. `console.error()` と集約条件の関係

`console.error()` も Cloud Logging 上は ERROR として扱われ、集約条件に一致する場合がある。  
§5-5 のとおり **原則 `logger.error()` へ寄せる**ため、移行が進んだ後は **`console.error()` に依存した中央集約** を前提としない。  
※ 未置換の `console.error()` が残る過渡期は、引き続き集約条件に含まれる場合がある。

### 9-3. 想定内 `HttpsError` と Cloud Logging の関係

想定内の `HttpsError` は `logger.error()` 対象としない。  
ただし、フレームワークや実行形態により、追加ログを出さなくても Cloud Logging 上に関連行が残る可能性がある。

そのため、**「想定内拒否に追加の `logger.error()` を出さない」こと** と、  
**「Cloud Logging 上に関連ログが一切残らない」こと** は同義ではない。

### 9-4. セキュリティ・監査系ログの分離可能性

セキュリティ・監査目的で追跡したい失敗は、本仕様上は中央集約対象候補に含める。  
ただし、本来の障害ログと混在してノイズ化する場合は、将来的に別ラベル・別分類・別 sink 等による分離を検討する。

---

## 10. 本仕様と changeSpec の関係

本仕様は、保守運用時のエラーログに関する **目的・対象範囲・ポリシー・設計原則** を定めるものである。  
具体的な実装内容は、本仕様を前提とした changeSpec にて定義する。

changeSpec では、少なくとも以下を扱う。

- 共通ログ出力方法
- 具体的なフィールド構造（**関数エントリ名・operation 名** 等をログに載せる際の **フィールド名・型・必須可否** を含む）
- 共通関数またはラッパーの設計
- 既存コードからの移行方針（**既存のエラー出力箇所での形式統一**、`console.error` → `logger.error` の**原則**的な置き換え・優先順位、二重ログ防止）
- 対象箇所の差分方針
- 二重ログ防止の実装ルール
- テスト観点
