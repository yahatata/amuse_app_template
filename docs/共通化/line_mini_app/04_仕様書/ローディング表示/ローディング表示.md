# ローディング表示（LINE ミニアプリ・`public/`）

_保存先: `docs/共通化/line_mini_app/04_仕様書/ローディング表示/ローディング表示.md`_  
_判断ルールの参照元: [Flutter ローディング表示](../../../flutter/04_仕様書/ローディング表示/ローディング表示.md)（本書は同一の 3 類型・表示単位／ロック単位を LIFF / Web 実装向けに記す）_

---

## 1. 目的

ローディング表示の目的は、処理中であることをユーザーに明確に伝え、二重タップ・連打や誤操作を防ぎつつ、画面ごとの挙動差を減らして UI/UX を安定させることである。  
**共通化そのものを目的とはしない**（共通化は手続き・整理の枠組みであり、狙いは利用者向けの UI/UX 向上にある）。

---

## 2. 適用対象

本仕様は、**LINE ミニアプリ（LIFF）として提供する Web クライアント**のうち、リポジトリ上 **`public/` 配下**（主に `public/user/index.html`・`public/staff/index.html`・共用 CSS）に適用する。

対象となる処理の種類は、以下の **3 類型**とする（Flutter 側仕様と同名・同意味）。

- **画面表示時の読込** … 画面（または主要セクション）の成立に必要な初回取得・LIFF／認証後の初期チェーンなど
- **画面内ユーザー操作による読取系処理** … ユーザーの操作を起点とし、**永続状態を更新しない**取得・照会・再取得など
- **画面内ユーザー操作による更新系処理** … ユーザーの操作を起点とし、**書込・登録・確定・取消・送信**など副作用や状態遷移を伴う処理

### 2.1 対象箇所と 3 類型への分類（整理の前提）

ローディング表示が論点になりうる対象箇所の列挙は、[対象ファイル・対象箇所の確認 §1](../../02_対象ファイル・対象箇所の確認/対象ファイル・対象箇所の確認.md#1-ローディング表示二重タップ不可処理非同期に伴う待機の必要性を含む) を正とする。

**各対象箇所を、上記 3 類型のいずれか（または複数類型にまたがる場合は行を分ける）に先に帰属させる**ことを推奨する。理由は次のとおりである。

- **§5〜§8** は類型ごとに**表示単位・ロック単位・適用ルール**が異なる（読込・読取は原則ロック不要、更新は原則ロックを強く見る）。
- [現状の使用パターンの確認 §1](../../03_現状の使用パターンの確認/現状の使用パターンの確認.md) にある **UI 上の出方**（スピナー型・オーバーレイ型など）の整理だけでは、**3 類型への分類完了**とはみならない。
- changeSpec 化や改修の優先順位付けの前に **3 類型への帰属**を付けておくと、仕様照合と優先順位が一貫しやすい。

同一 HTML 内に「初回読込」と「ユーザー操作起点の更新」が混在する場合は、Step2 の **対象箇所の切り口**に従い、**類型ごとに論点を分ける**。

**類型別の一覧（As-is 分類）**: [ローディング_対象箇所_3類型分類.md](./ローディング_対象箇所_3類型分類.md)（Flutter の [ローディング_119件_3類型分類.md](../../../flutter/04_仕様書/ローディング表示/ローディング_119件_3類型分類.md) と同じ役割）。

## 3. Flutter 実装概念とミニアプリ側の対応（用語）

本仕様のルールは Flutter 版と同一だが、実装手段は DOM・CSS・JavaScript に置き換える。対応の目安は次のとおり。

| Flutter（参照仕様の語） | LINE ミニアプリ（`public/`）での対応概念 |
|-------------------------|-------------------------------------------|
| `CircularProgressIndicator`（CPI） | スピナー・ローディングインジケータ（例: `.spinner`、`#loading` 内要素）。**不定の待ちはこれに統一**する |
| AppBar／画面上部 | 固定ヘッダ・ナビ領域（実装されている場合） |
| `Dialog`／モーダル | `confirm`／`alert`／自作モーダル DOM（処理中ローディングの本体としての利用は §13.3） |
| `PopScope`（戻れなくする） | 処理中フラグに応じた **履歴操作の抑止**、モーダルの **閉じる無効化**、必要に応じて **ブラウザバック対策**（限界あり §11・§13.5） |
| `AbsorbPointer` | `pointer-events: none`、入力・ボタンの `disabled`、透明オーバーレイでのクリック遮断 |
| `Stack` + 半透明オーバーレイ | `position: fixed`／`absolute` のオーバーレイ、`#global-loading-overlay` 等 |
| `SnackBar` | トースト、画面上のメッセージ領域、`alert`（用途に応じて） |
| `finally` | `try/catch/finally` または `Promise.prototype.finally()` |

**ディム（半透明）の範囲と、無効化している操作の範囲を一致させる**こと（Flutter 実装サマリと同旨）。本文だけを遮断してヘッダだけ触れるようにすると、見た目と挙動がずれやすい。

### 3.1 `alert` / `confirm` の位置づけ

ブラウザ標準の `alert` と `confirm` は、**結果通知・実行前の最終確認**には使用してよい。

一方、次を標準としない。

- **処理中**の待機表示や操作ロックの**本体**を `alert` / `confirm` に依存すること（ローディング表示やオーバーレイと組み合わせられず、端末・WebView により見え方の差も出やすい）。
- 更新系で **`confirm` 確定後だけ await しており、送信中に視覚的ロックが無い**構成を続けること。

更新系で送信中の表示・ロックが必要な場合は、**自作モーダル DOM** または **`#global-loading-overlay` 等のページ／セクションオーバーレイ**で制御する。

## 4. 基本方針

ローディング表示は、**ボタン内スピナーのみ**で完結させず、処理文脈に応じた表示単位で行う。

3 類型の扱いの要点は次のとおりである。

- **画面表示時の読込** … 待機表示は **スピナー（ローディングインジケータ）に統一**。配置は画面全体または主表示領域を認める。**原則、更新系と同等の強い操作ロックは要求しない**。
- **読取系** … 待機表示が必要な場合は **スピナーに統一**。不要な軽微処理には無理に追加しない。**原則ロック不要**。
- **更新系** … 誤操作・重複実行・状態不整合を強く重視。**ローディング表示と操作ロックを原則必須**。ボタン単位のみの待機を標準としない。

更新系におけるローディングおよびロックは **当該処理の終了まで継続**する。終了後に解除し、**その後**に結果出力する。結果出力のために追加ロックは設けない。

---

## 5. 表示単位とロック単位の定義

### 5.1 表示単位

表示単位とは、ある処理に対してローディング表示を出す **DOM／視覚上の範囲** を指す。固定のパターンに縛られず、処理ごとに決定する。

例: 画面本文、特定セクション（一覧コンテナ）、モーダル内、初期ロード用フルスクリーン `#loading` 等。

### 5.2 ロック単位

ロック単位とは、操作不可にする **範囲** を指す（ボタン・フォーム・ページ全体など）。

ロック単位は、少なくとも処理中の誤操作・重複実行・状態不整合を防げる範囲でなければならない。  
そのため、**ロック単位は表示単位より広くてよい**。

---

## 6. 表示単位の決定ルール

表示単位は、ユーザーが処理中だと自然に認知できる範囲で決定する。

### 6.1 画面表示時の読込

骨格やヘッダを先に出し、データ依存部分は取得後に表示する構成を認める。ローディングは必ずしも画面全体でなくてよい。  
待機表示は **スピナーに統一**する。

### 6.2 読取系処理

取得対象や UI 文脈に応じて決定する。少なくとも次を見る。

- どの文脈の処理として見えるか
- どの範囲で待機を明示するか
- 読取対象がどの領域に属するか

待機表示を行う場合は **スピナーに統一**。軽微で無反応に見えないなら省略可。

### 6.3 更新系処理

処理対象と UI 文脈に応じて決定する。ボタン押下が起点でも **ボタン内だけ**で待機を表すことは標準としない（主領域またはページ／モーダル全体のオーバーレイ等を優先）。

---

## 7. ロック単位の決定ルール

### 7.1 画面表示時の読込

**原則ロック不要**。ナビや別セクションへの移動を許容しつつ、主領域でスピナーを出す構成を認める。

### 7.2 読取系処理

**原則ロック不要**。同一読取の短時間多重で UI が著しく乱れる場合のみ、個別に検討する。

### 7.3 更新系処理

読込・読取より強い操作制御を原則とする。少なくとも次を検討する。

- 同一処理の再実行防止に必要なロック範囲
- 処理中 UI を実質回避できないか（別リンク・戻る・モーダル閉じ・二重送信）
- 他操作による状態不整合
- 結果が見失われないか

必要に応じて **ヘッダを含む画面全体** をロック対象とする。

ロック中は原則として認めないものの例:

- 同一処理の再実行
- 状態不整合を生みうる操作
- 処理中 UI を事実上回避できる操作

---

## 8. 適用ルール

### 8.1 画面表示時の読込

画面成立に必要な読込を待機表示する。**スピナーに統一**。**原則ロック不要**。  
既存の `#loading`・プログレス表示・初期化チェーンは、この類型の典型である。

**読込に分類しやすい LIFF 側の代表例**（いずれも完了しないと画面の意味が成立しない場合は、初期ロード用 UI で待つ）。

- LIFF SDK の初期化（例: `liff.init`）
- ログイン状態の確認・未ログイン時の誘導
- プロフィール等の権限まわり（利用可能なら取得・確認）
- URL ハッシュやパラメータに応じた最初の画面決定
- Firebase カスタムトークン取得・`signInWithCustomToken`・店舗／ユーザー／スタッフ登録の有無確認（`public/` の `runUserInitialization` / `runStaffInitialization` チェーン相当）
- 上記に続く **画面を埋めるための最初の Firestore／設定読み取り**（単体 UI は無いがチェーン内では読込の一部）

### 8.2 読取系処理

文脈に応じて待機表示する。行う場合は **スピナーに統一**。**原則ロック不要**。  
一覧セクション内の `.spinner` 等が読み取りに該当しうる。

### 8.3 更新系処理

**ローディング表示と操作ロックを原則必須**とする。

更新系とは、再実行により状態・結果・外部副作用のいずれかが変わりうる処理である。次のいずれかに該当しうるものを含む。

- 永続状態が変わる
- 再実行で結果が変わりうる
- 外部へ送信・発行・通知・実行がある
- 確定・取消・完了などの状態遷移がある

### 8.4 処理終了後の扱い

ローディングおよびロックは **処理終了時に解除**する。結果出力は **その後**。結果表示のためだけの追加ロックは設けない。

---

## 9. 非採用とする扱い

以下を標準としない。

- ボタン単位のみのローディングで処理文脈が伝わらないこと
- 処理中なのに待機が視覚的に分からないこと
- 更新系でオーバーレイがあるのに、背面クリック・別導線・戻るで処理中を回避できること
- 事故防止に必要なロックを実装者判断だけで省略すること
- 3 類型を同一強度で扱うこと
- 結果出力のためにだけローディング／ロックを継続すること

---

## 10. 冪等性との関係

クライアントのロックだけでは重複実行防止は完結しない。**Cloud Functions／HTTP API** の冪等性は別途確認対象とする。クライアント側は一次防御である。

---

## 11. 例外

次は例外として検討してよい。

- 表示遅延が極短く、待機を出さない方が自然なとき
- 軽微な補助読取でロックが UX を著しく損なうとき
- 既存 UI・LIFF 制約により段階移行が必要なとき

例外を認める場合も、更新系の必要なロックを安易に省略しないこと。**必要性と影響範囲を文書化する**こと。

**LIFF／ブラウザ環境の注意**: `history.back` やタブ閉じを完全に抑止できない場合がある。**「完全に抑止できないからロックを弱くしてよい」にはしない**（§13.5）。

---

## 12. 実装時の注意（JavaScript）

- 表示開始・終了は **成功・失敗の両方**で確実に行う
- 解除漏れを防ぐため **finally 相当**でフラグ・オーバーレイ・`disabled` を戻す
- 3 類型を混同しない
- 不定の待ちはスピナー表現に統一する（読込・読取で表示する場合）
- 更新系は読込・読取より強い誤操作防止を前提とする
- **二重ローディング**（ボタン内スピナーと全面オーバーレイの併用など）を避ける
- 背面操作・別導線で処理中 UI を回避できないことを確認する
- 結果出力はロック解除の後に行う
- 更新系に対応する API の冪等性も別途整理する

既存の共通ヘルパの**使い分け**は §13.1 とする。活用しつつ、**表示単位／ロック単位が仕様と一致するか**を箇所ごとに確認する。

## 13. 実装ガイド（Web / LIFF 固有補足）

Flutter 版仕様の転記に加え、`public/` でブレやすい点を次で固定する。

### 13.1 `executeWithGlobalLoading` と `executeWithButtonLoading` の使い分け

更新系では原則として **`executeWithGlobalLoading` と同等の「ページまたはモーダル単位」のローディング＋ロック**を用いる（`#global-loading-overlay` やセクション全体のオーバーレイ・`disabled` の組み合わせでよい）。

**`executeWithButtonLoading` のみで更新系を完結させることは標準としない。**  
`executeWithButtonLoading` のみで足りる可能性があるのは、**更新系ではなく**、主に **読取系または補助 UI 処理**である。

例:

- **同一ボタンの短時間連打防止**と文言差し替えだけで十分な、軽微な読取・補助処理
- **永続状態の更新・送信・外部副作用・状態遷移を伴わない**処理

**登録・送信・確定・取消・決済相当・Firestore／Functions の更新**などは上記に含めない。

更新系（状態更新・送信・確定・取消・登録等を伴うもの）は、**ボタン無効化に加え**、§6.3・§7.3 に沿った**表示単位**でのスピナー／オーバーレイを前提とする。

### 13.2 更新系の表示単位・ロック単位（ページ／モーダル／行）

判断は次の優先で行う（changeSpec でブレないようにする）。

1. **モーダル内で完結する更新**  
   **モーダル全体**を表示単位かつロック単位とする。外タップ閉じ・キャンセル・背面クリックで処理中を抜けられないようにする（実装可能な範囲で）。
2. **ページ本文の更新**  
   **ページ全体**、または少なくとも **当該処理を迂回できる導線（他タブ・他ボタン・上部ナビ）を含む範囲**をロックする。ヘッダのみ操作可能で本文だけディム、などのずれを避ける。
3. **行・カード単位の更新**  
   **対象行のみ**のオーバーレイ／スピナーでもよい（Flutter の一覧内 1 カード更新相当）。ただし **他行の操作で状態不整合や二重実行が起きうる**場合は、一覧コンテナ全体またはページ全体をロックする。

### 13.3 `alert` / `confirm` とローディング

§3.1 に同じ。処理中の本体は DOM オーバーレイ等で担う。

### 13.4 LIFF 初期化チェーンと読込類型

§8.1 の代表例と同一意味。初期チェーンは **画面表示時の読込**にまとめ、`#loading`・プログレス・再試行 UI でユーザーが待てるようにする。

### 13.5 履歴・戻るを完全に抑止できないときの最低限

ブラウザバックやタブ閉じをフックできない場合でも、少なくとも次を **更新系では組み合わせる**（省略を「抑止困難」の言い訳にしない）。

- 同一送信ボタン・関連ボタンの **`disabled`**
- **処理中フラグ**での再入 **`return`**
- **オーバーレイ**または **`pointer-events`** での操作遮断
- 自作モーダルでは **閉じる／キャンセル／外タップ**を処理中は無効化
- **API／Functions 側の冪等性**の確認（§10）
