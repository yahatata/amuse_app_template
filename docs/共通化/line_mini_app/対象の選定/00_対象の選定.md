# 対象の選定

中タスク「対象の選定」。本ファイルに詳細を記載する。

本ファイルは Flutter / LINEミニアプリの両方で共通利用する。  

**目標**：次工程に進める共通化対象が選定されていること。

**完了条件**

- 共通化候補の洗い出し結果が整理されている
- 候補ごとの評価結果が整理されている
- 着手する対象が決まっている
- 対象選定の根拠が記録されている

---

## 共通化の目的（メリット）

以下の恩恵が大きいものを共通化候補とする。

- UI の一貫性向上
- UX の予測可能性向上
- 変更コスト削減
- バグ混入率低下
- レビュー効率向上
- テスト観点の集約
- 実装判断コスト削減
- デザイン負債抑制

共通化価値の評価では、候補が上記のメリットにどれだけ寄与するかを確認する。

---

## 共通化対象選定の4段階

| 段階 | 観点 |
|------|------|
| **1. 候補を見つける** | 複数箇所で繰り返し使われているか、保守運用上形式を揃えるべきか、同じ目的で表現・挙動に差分があるか、横断ルールを持つべきか |
| **2. 共通化価値を評価** | 修正漏れが起きやすいか、将来仕様変更がありそうか、見た目・挙動を揃えるべきか、開発時の判断が毎回発生しているか、テスト・レビュー観点を集約する価値が高いか |
| **3. 設計の成立性を確認** | 例外ケースが少ないか、利用方法やインターフェースが過剰に複雑にならないか |
| **4. 今回着手すべきか判断** | 実装コストがメリットに見合うか、既存コードの安定性 |

## 中タスク：対象の選定（具体4ステップ）

人間が 1 つずつ観点に沿って見にいくのは膨大であり漏れも起き得るため、**Cursor に広い候補を出させ、人間が選別する**フローとする。

### 1. Cursor に候補一覧を抽出させる

- 候補抽出時に、粒度が細かすぎるものや明らかな単発候補は可能な範囲で除外させる。
- 対象の採否判断はさせない。**候補の拾い上げに限定**する。
- 人間がわかりやすいよう、以下の表形式で出力させる。分類は次のいずれかとする：UI コンポーネント / UX・画面挙動ルール / エラーハンドリング・ログ / 表示文言・文言管理 / レイアウト・スタイル。

| 項目 | 内容 |
|------|------|
| 候補名 | 例: 確認ダイアログ |
| 分類 | UI コンポーネント / UX・画面挙動ルール / エラーハンドリング・ログ / 表示文言・文言管理 / レイアウト・スタイル |
| 役割 | 何のための共通化か |
| 主な使用箇所 | 代表ファイル・画面・HTML・設定ファイルなど |
| 類似パターン数 | 厳密でなくてよい |
| 差分の種類 | 文言差分 / レイアウト差分 / 挙動差分 |
| 共通化価値の仮説 | なぜ候補なのか |
| 備考 | 例外が多そう等 |

### 2. 候補ごとに共通化価値を評価する

- Step1 で抽出した候補について、共通化の目的（メリット）にどれだけ寄与するかを評価する。
- 評価時は、以下の観点を用いる。

**修正漏れが起きやすいか**  
主に効くメリット  
変更コスト削減  
→ 一括修正しやすくなる  
バグ混入率低下  
→ 直し漏れによる不整合を減らせる  
レビュー効率向上  
→ 修正対象が点在しにくくなり確認しやすい  

**将来仕様変更がありそうか**  
主に効くメリット  
変更コスト削減  
→ 変更が入るたびに一括修正の恩恵が出る  
デザイン負債抑制  
→ 小さな差分が増殖する前に止められる  
バグ混入率低下  
→ 変更のたびに発生する不整合を減らせる  

**見た目・挙動を揃えるべきか**  
主に効くメリット  
UI の一貫性向上  
→ 見た目が揃う  
UX の予測可能性向上  
→ 操作時の反応が揃う  
テスト観点の集約  
→ 同じ確認を画面ごとに繰り返しにくくなる  

**開発時の判断が毎回発生しているか**  
主に効くメリット  
実装判断コスト削減  
→ 毎回の迷いが減る  
UI の一貫性向上  
→ 判断結果がぶれにくい  
UX の予測可能性向上  
→ 操作結果が揃いやすい  

**テスト・レビュー観点を集約する価値が高いか**  
主に効くメリット  
レビュー効率向上  
→ 共通部品中心に確認できる  
テスト観点の集約  
→ 主要な確認を共通部品側に寄せられる  
バグ混入率低下  
→ 同じ問題が各画面に散らばりにくい  

- 候補ごとに、少なくとも以下を記録する。  
  - メリットへの寄与の要約  
  - 評価結果（残す / 落とす / 保留）  
  - 評価結果の理由  

- 出力は、Step 1 の候補一覧をベースに追記する形でも、別表にしてもよい。

### 3. 残った候補について設計の成立性を確認する

- Step 2 で残した候補について、共通化対象として無理なく成立するかを確認する。
- 確認時は、以下の観点を用いる。  

**例外ケースの多さが、共通化対象としての成立性を損なわないか**  
**共通化しても利用方法やインターフェースが過剰に複雑にならないか**

- 必要に応じて代表箇所や例外が疑われる箇所を限定的に確認するが、この段階では対象箇所の網羅的確定や As-is パターンの詳細整理までは行わない。

- 候補ごとに、少なくとも以下を記録する。  
  - 成立性の判断  
  - 判断の根拠  

### 4. 今回着手する対象を決定する

- Step3 までで残った候補について、今回の着手対象とするかを判断する。
- 判断時は、以下の観点を用いる。  

**実装コストがメリットに見合うか**  
**既存コードが安定しているか**

- 必要に応じて、以下も補助的に見る。  
  - 他候補と比較した優先度  

- 候補ごとに、最終的に以下のいずれかへ分類する。  
  - 今回着手する  
  - 保留  
  - 今回は着手しない  

- 最後に、**今回着手する対象** と **その選定理由** を明記する。
