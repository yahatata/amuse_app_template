# 基盤・業務・境界の再整理（Step 2.5）

**Step 2「共通化価値評価」の結果を前提に、Step 3「設計成立性確認」に入る前に、候補を別軸で再分類した。**  
再分類は Step2 の**別軸のラベル付け**であり、業務・会計などの**一通りの再採点ではない**。  
※ **開発時コンソール（debugPrint）** は `02` 上 **落とす** とし、本表の再分類対象から除外する（`02` の方針メモ参照）。

## 冒頭サマリ

| 項目 | 内容 |
|------|------|
| **なぜ再分類か** | Step2 時点で **残す・保留が合わせて多く**、すべてを同列に Step3 で細かく追うコストが高い。**今回のラウンドでは「基盤候補」を先に進め、業務・境界は扱いを分ける**必要がある。 |
| **今回の優先** | **基盤候補**の共通化を最優先で設計・実装の検討順に載せる。 |
| **業務候補** | Step2 の評価は活かすが、**今回の実装ラウンドでは後回し**。一覧は **`02.5_業務候補一覧.md`** に退避。 |
| **境界候補** | **基盤にも業務にも勝手に確定移送しない**。独立一覧にし、**今回進めるか / 業務側に寄せるかは人間が判断**。**具体例・スタッフ／来店客目線は `02.5_境界候補一覧.md`**。 |
| **本ドキュメントの位置づけ** | **03 設計成立性確認ではない**（API・例外網羅・changeSpec は扱わない）。あくまで **候補の再ラベル付け**。 |
| **今回スコープ外の明示** | **保守運用のための実装**（エラーコード統一、エラー集約基盤、アプリ外の一括管理など）には**触れない**。境界候補の議論でもそこへ拡張しない。 |
