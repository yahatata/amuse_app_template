## 3. 境界衝突候補一覧

| 候補名 | ぶつかっている境界 | 理由 | Step2 での扱い注意 |
|--------|---------------------|------|---------------------|
| SnackBar・短期的メッセージ | UI コンポーネント vs UX・画面挙動ルール | ウィジェットの見た目と「どの結果で何を出すか」が一体で動いている | 部品の良さだけ／ルールの良さだけで片付けない。**表示ポリシーの軸**を一文決めてから評価 |
| 例外→ユーザー向けエラー表示 | エラーハンドリング・ログ vs 表示ポリシー（ルール） | 分類はログ系だが実装はダイアログ・SnackBar 選択に直結 | catch の深さ・再送出と、ユーザー文言の責務を分けて評価 |
| 画面全体・オーバーレイ型ローディング | UI コンポーネント vs 非同期二重操作防止（ルール） | オーバーレイは「押せない」状態とセットで設計されがち | ローディングのみ／disable ルールのみで価値を切らない。セットのときの一貫性も視野 |
| インライン・ボタン内ローディング | 同上 | ボタン内は特に disable とセット | 同上 |
| ユーザー向けメッセージの直書き集散 | 表示文言・文言管理 vs ダイアログ等 UI コンポーネント | 文言を集約するとき「部品の引数」と「文言カタログ」のどちらに寄せるかで論点が変わる | **文言の単一ソース**と**部品 API**のどちらを先に決めるか明記して評価 |
| UI ラベル・ボタン文言の直書き | 同上（ウィジェットの title / label） | 短い文字列がウィジェットに密着 | コンポーネント化で吸収するか、文言表で吸収するかを混同しない |
| 単純確認 / 破壊的確認 / 会計・卓上ダイアログ | UI vs 共通ルール（確認フロー） | 業務によって「二段確認必須」等のルールが付く | **画面単位のルール**と**ウィジェットの再利用**を同時評価しない |

## 4. Step 2 に入る際の注意点

1. **着地先の仮ラベルは確定ではない**。「コンポーネント向きだが helper で足りる」など Step 2 で揺れてよい。揺れたら備考に残す。
2. **共通ルール / ガイドライン向き**の候補（二重防止・完了後遷移・例外表示・debug・文言ルール）を、コンポーネントだけの候補より劣後させない。価値の軸が異なるだけ。
3. **分割後の各行は別々に評価してよい**。元候補名で束ねて「まあ大きいから残す」と雑にしない。
4. **境界衝突候補**は、表のどちらか一方の観点だけで「落とす／残す」を判断しない。Step 2 冒頭で**整理軸を 1 つ書く**（任意・短文で可）。
5. **類似パターン数**は `01` と同様、強い優先度指標にしない。分割後は行ごとの再カウントは不要。
6. **補足・小規模候補**（営業日曖昧・店舗警告）は本筋より評価を薄くてもよいが、「残す理由だけ短く」程度は書くと後工程で迷いにくい。
7. **会計・卓上の分割行**は業務例外が多くても Step 2 では「全体として寄与しそうか」から入り、**スコープ縮小は成立性確認（Step 3）**に回してよい。
