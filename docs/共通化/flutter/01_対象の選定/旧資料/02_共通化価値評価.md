# 共通化価値評価

Step 2「候補ごとに共通化価値を評価する」の成果物。  
入力は **`01.5_候補整理.md`**（整理後候補名を評価単位とする）。**採否（残す / 保留 / 落とす）を付けた**。詳細設計・API・例外網羅は扱わない。

**方針メモ（debugPrint）**  
一時期 **保留** としたが、**基盤優先ラウンド**では開発時ログの共通化を主対象としないため、再び **落とす** に戻した（`02.5` の再分類対象外と整合）。別ラウンドでログ方針を扱う想定。

---

## Step 2 の読み方（本評価の前提）

1. **「ウィジェットとして共通化できるか」だけで価値を決めない。** helper・util・ガイドライン・表示ポリシーに寄る候補も、同じ「共通化の目的（メリット）」に対して評価する。
2. **8 メリットの適用をエンドユーザー向け画面だけに限定しない。** ログ・観測系も、変更コスト・レビュー・テスト・判断コストなどに **フラットに** 寄与しうるとして評価する。
3. **着地先（仮）は参考。** 行ごとの結論は、メリットと補助観点から付けている（着地先で機械的に残す／落とさない）。
4. **境界衝突候補の見方（短く）**  
   - **SnackBar**: 主軸は **表示ポリシー（いつ・何の結果で・どのトーンで出すか）**。部品の統一は従。  
   - **例外→ユーザー表示**: 主軸は **ユーザーに見せる文言・経路・粒度のポリシー**。catch の深さ／ログは副次で Step3 で整理。  
   - **ローディング × 二重操作防止**: 主軸は **非同期中の操作可否・フィードバックのルール**として **対で整合**するか。どちらか片方だけの得点で決めない。

5. **「特に効いた観点」列の書式（方式B：番号＋正式略記）**  
   次の5つに寄せて統一する（厳密採点ではなく判断補助）。  
   - `1 修正漏れ`  
   - `2 将来仕様変更`  
   - `3 見た目・挙動`  
   - `4 実装判断の繰り返し`  
   - `5 テスト・レビュー集約`  
   寄与が弱い・適用が局所的な場合は括弧で注記する（例：`4 実装判断の繰り返し（寄与：弱）`）。5観点のいずれにも主に当てはまらない場合は `—`。

## 4. Step 2 時点での所感

- **残す候補の傾向**: 「責務が読み取りやすい」かつ「横断・再利用のイメージが立つ」ものが多い（単純確認・選択・ローディング類・二重防止・フォーマッタ・卓・シフト・注文）。**安全・予測可能性・変更コスト**に直結しやすい帯域が残った。  
- **迷いが多かった種類**: **会計・卓上（ドメイン厚）**、**表示まわり（SnackBar・例外→ユーザー・文言二行）**、**ローディングと二重防止の整合**、**破壊的確認のスコープ**。開発時コンソールは **落とす**（本ラウンド主戦場外）。  
- **Step 3 に入る時の注意**:  
  - 保留群は **「どの軸で先に切るか」（表示ポリシー / 部品 / ルール）** を一文ずつ置いてから成立性を見る。  
  - **会計・卓上**はスコープを小さくするところから。  
  - **残す 9 件**でも、オーダー×会計・ローディング×二重防止の**境界は Step3 で必ず突き合わせ**る。
