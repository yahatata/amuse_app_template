# 対象の選定

## 本ファイルの目的

今回の共通化ラウンドにおいて、何を対象とするか、またその判断理由を整理すること。

## 今回の対象選定の考え方

- 開発効率向上は今回は主目的に置かない
- 複数箇所で使われているだけでは採用理由として不十分
- UI/UX または保守運用への寄与が特に大きいものを優先する

## 今回対象とする項目

1. ローディング表示（二重タップ不可処理も含む）
2. 保守運用時用のエラーログ
3. ユーザーへの結果出力
4. 確認ダイアログ

## 各対象を採用した理由

### 1. ローディング表示
現状、ローディング表示がない箇所や表示方法にばらつきがある。  
そのため、ユーザーが「押せていないかもしれない」「反応していない」と感じてしまうおそれがある。  
原則としてローディング表示を共通化し、 UI 上の二重タップ不可もあわせて扱うことで、ユーザーの困惑を減らし UX を向上できると考えた。  
なお、実データの重複防止は Functions 側の冪等性で担保する前提とする。

### 2. 保守運用時用のエラーログ
開発段階で、保守運用時に参照すべきエラーログの出力場所や形式が散ってしまった。  
そのため、保守運用時に複数箇所を確認しないと状況を把握できず、障害への気付きや対応が遅れるおそれがある。  
なので、保守運用時用のエラーログを一定の場所・形式に統一することで、確認・切り分け・対応をしやすくすると判断した。

### 3. ユーザーへの結果出力
ユーザー（ここではアプリ使用者を指す）の操作に対する結果を出力している箇所が多々あるが、現状は複数の出力方法が使われている。  
それを原則共通化することで UI に一貫性が生まれ、UX も向上すると考えた。

### 4. 確認ダイアログ
重要操作の確認時にダイアログの表示や挙動にばらつきがあると、ユーザーの意図しない結果につながるおそれがある。  
現時点では、他の3項目ほど問題の強さを確定できていないため優先度は最も低いが、対象候補として含めたうえで、後続の使用パターン確認で必要性を再確認する。

## 補足

現時点では、今回対象外または後回しとする項目を個別には定義しない。
