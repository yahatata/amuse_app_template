# ローディング表示

## 1. 目的

ローディング表示の目的は、処理中であることをユーザーに明確に伝え、二重操作や誤操作を防ぎつつ、画面ごとの挙動差を減らして UI/UX を安定させることである。  
**共通化そのものを目的とはしない**（共通化は手続き・整理の枠組みであり、狙いは利用者向けの UI/UX 向上にある）。

---

## 2. 適用対象

本仕様は、Flutter におけるローディング表示のルールに適用する。  
対象は、以下の 3 類型の処理である。

- 画面表示時の読込
- 画面内ユーザー操作による読取系処理
- 画面内ユーザー操作による更新系処理

### 2.1 対象箇所（母数 119）を 3 類型に分けること（整理の前提）

共通化の As-is 整理におけるローディング関連の**対象箇所**は、Step2 を母数として **119 件**である（`firebase_options.dart` は母数から除外する等の定義は [現状の使用パターンの確認 §1](../../03_現状の使用パターンの確認/現状の使用パターンの確認.md) を参照）。

**各対象箇所を、上記 3 類型のいずれに当てはまるか（または複数類型にまたがるか）を先に切る**ことを推奨する。理由は次のとおりである。

- 本仕様の **§4〜§7** は、類型ごとに**表示単位・ロック単位・適用ルール**が異なる（例: 画面表示時の読込・読取系は原則ロック不要、更新系は原則ロックを強く見る）。
- [現状の使用パターンの確認 §1.1](../../03_現状の使用パターンの確認/現状の使用パターンの確認.md) の**主要パターン**（画面 CPI 型・ダイアログ CPI 型等）は、119 を **UI 上の出方**で束ねた分類であり、**そのまま＝本節の 3 類型への分類完了**ではない。
- **波（P0〜P3）**への対応付けや changeSpec 化の前に、**3 類型への帰属**を付けておくと、仕様照合と優先順位付けが一貫しやすい（[改修方針メモ §7](./改修方針メモ.md) の先行整理とも整合する）。

同一ファイル内に「初回読込」と「ユーザー操作起点の更新」が混在する場合は、**対象箇所の切り口**（Step2 の定義）に従い、**類型ごとに行を分ける**。

**As-is の分類表（母数 119・類型ごとに節分け）**: [ローディング_119件_3類型分類.md](./ローディング_119件_3類型分類.md)

## 3. 基本方針

ローディング表示は、ボタン単位のみで完結させず、処理文脈に応じた表示単位で行う。

本仕様では、以下の 3 類型を分けて扱う。

- 画面表示時の読込
- 画面内ユーザー操作による読取系処理
- 画面内ユーザー操作による更新系処理

画面表示時の読込では、**CPI（CircularProgressIndicator）による待機表示**を行う。  
待機表示の配置は UI 構造に応じて、AppBar を残した本文領域での表示、または画面全体での表示を認める。  
ただし、画面表示時の読込においては、原則として更新系処理と同等の強い操作ロックは要求しない。

画面内ユーザー操作による読取系処理では、**待機表示が必要な場合は CPI を用いる**。  
ただし、待機表示が不要な軽微な処理や、読取待ちとは性質が異なる処理については、無理に CPI を追加しない。  
画面内ユーザー操作による更新系処理では、誤操作防止、重複実行防止、状態不整合防止をより強く重視する。

更新系処理におけるローディング表示および操作ロックは、当該処理の終了まで継続する。  
処理終了後はローディングとロックを解除し、その後に結果出力を行う。  
結果出力は通知であり、確認要求ではないため、結果出力自体のために追加の操作ロックは設けない。

---

## 4. 表示単位とロック単位の定義

### 4.1 表示単位

表示単位とは、ある処理に対してローディング表示を出す範囲を指す。  
表示単位は固定の UI 種別ではなく、処理ごとに決定する。

表示単位の例としては、画面本文領域、タブ領域、ダイアログ領域等がある。  
ただし、これらはあくまで例であり、表示単位をこれらに限定するものではない。

### 4.2 ロック単位

ロック単位とは、ある処理に対して操作を不可とする範囲を指す。  
ロック単位も固定の UI 種別ではなく、処理ごとに決定する。

ロック単位は、少なくとも処理中の誤操作、重複実行、状態不整合を防げる範囲でなければならない。  
そのため、ロック単位は表示単位より広くなることがある。

---

## 5. 表示単位の決定ルール

表示単位は、ユーザーにとって処理中であることを最も自然に認知できる範囲で決定する。

### 5.1 画面表示時の読込

画面表示時の読込では、画面の骨格や AppBar 等を先に表示し、本文や一覧等のデータ依存部分を取得後に表示する構成を認める。  
この場合、ローディング表示は必ずしも画面全体である必要はなく、主表示領域側に出すことを認める。  
待機表示の方式は **CPI に統一**する。

### 5.2 画面内ユーザー操作による読取系処理

読取系処理では、取得対象や UI 文脈に応じて表示単位を決定する。  
その際は、少なくとも以下の観点で判断する。

- どの文脈の処理として見えるのが自然か
- どの範囲で待機状態を明示するのが分かりやすいか
- 読取対象がどの範囲に属しているか

待機表示を行う場合は **CPI に統一**する。  
ただし、待機表示が不要な軽微な処理や、読取待ちとは性質が異なる処理については、無理に CPI を追加しない。

### 5.3 画面内ユーザー操作による更新系処理

更新系処理では、処理対象および UI 文脈に応じて表示単位を決定する。  
その際は、少なくとも以下の観点で判断する。

- どの文脈の処理として見えるのが自然か
- どの範囲で待機状態を明示するのが分かりやすいか
- 処理対象がどの範囲に属しているか

ボタン押下が処理起点であっても、ボタン内のみで待機状態を表現することは標準としない。

---

## 6. ロック単位の決定ルール

ロック単位は、処理中の誤操作、重複実行、状態不整合を防ぐために必要な範囲で決定する。

### 6.1 画面表示時の読込

画面表示時の読込では、原則としてロックを要求しない。  
たとえば AppBar の戻る操作を許容しつつ、本文側の主要領域でローディング表示を行う構成を認める。

### 6.2 画面内ユーザー操作による読取系処理

読取系処理では、原則としてロックを要求しない。  
必要に応じて待機表示を行うが、更新系処理と同等の操作ロックは行わない。

ただし、同一読取処理の短時間多重実行により UI が著しく不自然になる場合など、限定的な制御が必要なときは、個別に対応を検討する。

### 6.3 画面内ユーザー操作による更新系処理

更新系処理では、画面表示時の読込および読取系処理より強い操作制御を原則とする。  
少なくとも以下の観点で判断する。

- 同一処理の再実行を防ぐために、どこまで操作不可にすべきか
- 処理中 UI を実質的に回避できないか
- 処理中に他操作を行うことで状態不整合が起きないか
- 途中で戻る、閉じる、切り替える等の操作により問題が生じないか
- 更新結果を見失いやすくならないか

必要に応じて、本文領域に加えて AppBar を含むより広い範囲をロック対象とすることを認める。

ロック中は、少なくとも以下を許可しない。

- 同一処理の再実行
- 処理中に状態不整合を生みうる操作
- 処理中 UI を事実上回避できる操作

## 7. 適用ルール

### 7.1 画面表示時の読込

画面表示時の読込では、画面成立に必要な読込を適切に待機表示する。  
待機表示は **CPI に統一**する。  
ただし、原則としてロックは行わない。  
画面骨格や AppBar を表示したまま、本文側の主要領域で待機表示する構成を認める。  
また、AppBar を持たず画面全体を CPI のみで表示する構成も認める。

### 7.2 画面内ユーザー操作による読取系処理

画面内ユーザー操作による読取系処理では、取得対象や UI 文脈に応じて待機表示を行う。  
待機表示を行う場合は **CPI に統一**する。  
ただし、原則としてロックは行わない。

軽微な再取得、切替読込、追加読込等については、UX を損なわない範囲で局所的な待機表示を認める。  
ただし、ユーザーに不自然な無反応と認識されないことを前提とする。  
また、待機表示が不要な軽微な処理や、読取待ちとは性質が異なる処理については、現状維持を認める。

### 7.3 画面内ユーザー操作による更新系処理

更新系処理では、ローディング表示と操作ロックを原則必須とする。

ここでいう更新系処理とは、再実行されたときに状態、結果、外部副作用のいずれかが変わりうる処理を指す。  
最低限、以下のいずれかに該当するものを更新系処理とする。

- 永続状態が変わる
- 再実行で結果が変わりうる
- 外部に何か送る
- 消費、発行、予約、通知、実行が起こる
- 使用済み、確定済み、取消済み、完了済み等の状態遷移がある

### 7.4 処理終了後の扱い

ローディング表示および操作ロックは、当該処理の終了時に解除する。  
結果出力はその後に行う。  
結果出力は通知であり、確認要求ではないため、結果出力自体のために追加の操作ロックは行わない。

---

## 8. 非採用とする扱い

本仕様では、以下の扱いを標準としない。

- ボタン単位のみのローディング表示
- 処理中であるにもかかわらず、見た目上は待機状態が分からないこと
- 更新系処理においてローディング表示が出ているにもかかわらず、背面操作、戻る操作、別導線等により処理中 UI を実質的に回避できること
- 実装者判断で、事故防止に必要なロックを省略すること
- 画面表示時の読込、読取系処理、更新系処理を同一強度で扱うこと
- 処理終了後も、結果出力のためだけにローディングやロックを継続すること

---

## 9. 冪等性との関係

更新系処理に対してローディング表示と操作ロックを行っても、UI 側だけでは重複実行防止は完結しない。  
そのため、更新系処理に対応する Functions / callable については、冪等性の要否および現在の対応状況を別途確認対象とする。

ローディング表示および UI ロックは、あくまでクライアント側の一次防御である。  
通信再送、画面再描画、端末状態変化、別経路実行等による重複リスクについては、後続工程においてサーバ側処理の設計・実装状況を確認し、必要な対応を整理する。

---

## 10. 例外

以下は例外として扱う余地がある。

- 表示遅延が短く、待機状態を明示しない方が自然な処理
- 軽微な補助読取であり、ローディング表示やロックを強くかけると UX を著しく損なう処理
- 既存 UI 制約上、段階的移行が必要な箇所

ただし、例外を認める場合でも、誤操作防止に必要なロックを安易に省略しないことを原則とする。  
例外採用時は、必要性と影響範囲を明示すること。

---

## 11. 実装時の注意

- ローディングの表示開始と終了は、成功時・失敗時の両方で確実に制御すること
- ロック解除漏れを防ぐため、終了処理は finally 相当で管理すること
- 表示単位とロック単位は、それぞれ処理特性に応じて決定すること
- 画面表示時の読込、読取系処理、更新系処理を分けて扱うこと
- 画面表示時の読込は CPI に統一すること
- 読取系処理は、待機表示を行う場合は CPI に統一すること
- 更新系処理では、画面表示時の読込および読取系処理より強い誤操作防止を前提とすること
- ボタン単位のみの待機表示を標準としないこと
- 背面操作、戻る操作、別導線等により処理中 UI を回避できないことを確認すること
- ローディングおよびロックは処理終了時に解除すること
- 結果出力はローディング解除後に行うこと
- 結果出力自体のために追加の操作ロックを設けないこと
- 更新系処理では、UI ロックだけでなく Functions 側の冪等性確認事項も別途整理すること
