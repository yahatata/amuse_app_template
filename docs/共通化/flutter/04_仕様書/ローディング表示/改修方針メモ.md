## 2. 共通化全体像との対応

### 2.1 大タスクの目標との関係

[共通化全体像.md](../../../共通化全体像.md) の **大タスク：共通化** の目標は、**UI/UX の向上**と**保守運用時の負担軽減**に寄与する範囲で、仕様決定〜検証までを完了することである。

本メモ（ローディング表示）において **最優先で狙うのは UI/UX 向上**である。共通化は作業手順・成果物整理の枠組みであり、**目的そのものを「共通化」に置かない**（§3 も参照）。

本メモは、全体像のうち次のメリットに主に効く。

| 今回重視するメリット（全体像より） | 本メモでの対応イメージ |
|-----------------------------------|--------------------------------|
| 見た目や挙動の一貫性向上 | 3 類型（画面表示時の読込／画面内ユーザー操作による読取系／更新系）・表示単位／ロック単位の統一 |
| 操作結果の分かりやすさ向上 | 処理終了後の結果通知の順序（仕様 §7.4） |
| 処理中状態やエラー時の認知しやすさ向上 | P0〜P2 の待機・ロック・回避不能性 |
| 画面や機能ごとの差によるユーザーの困惑低減 | 主要パターン表とのギャップ解消 |
| エラー検知・原因調査のしやすさ | **主対象外**（保守運用時のエラーログは **別概念**。必要なら **別メモ／別 changeSpec**） |

**補足（全体像）**: **開発効率向上そのものを主目的には置かない**。レビュー時は「実装のしやすさ」単体を最優先理由にしない。

### 2.2 中タスク上の位置

全体像の **中タスク 1〜3 は完了**、**4 仕様の決定〜7 検証**が続く流れのうち、**本メモ**は次を担う **ドラフト** である。

| 中タスク（全体像 #） | 本メモとの関係 |
|----------------------|----------------|
| **4. 仕様の決定** | [ローディング表示.md](./ローディング表示.md) が To-be のたたき台。必要なら Step3 結果を反映して仕様を確定する。 |
| **5. changeSpec 作成** | **本メモがその入力候補**（確定後に **changeSpec 正本**を起案する）。完了条件は「実装単位での変更内容と**検証観点**が整理されていること」（全体像）。 |
| **6. 実装** | **確定した changeSpec**（または本メモを昇格させた改修仕様）に基づく。 |
| **7. 検証** | 本書 **§8 受け入れ基準**＋全体像の「期待挙動と影響範囲」。 |

**Flutter と LINE ミニアプリ**は全体像どおり **原則別々**に進める。**本メモ**は **Flutter（`lib/`）** 向け。`public/` 用は **別メモ／別 changeSpec** でもよい（§10）。

### 2.3 全体像の補足・運用ルールの取り込み

| ルール（全体像「補足・運用ルール」） | 本メモでの扱い |
|--------------------------------------|----------------|
| 候補ごとに進めることを基本とする | **P0〜P3** を波として切る。一括全件必須としない。 |
| 現状の使用パターンの確認結果は、必要に応じて仕様更新に反映 | As-is の整理メモ・§1.3 は仕様書・本メモの差分確認に利用。 |
| 対象ファイル・対象箇所の確認結果は、必要に応じて changeSpec に反映 | 受け入れ基準は **Step2 の対象箇所**で特定する（確定時は **changeSpec 正本**へ転記）。 |
| changeSpec には検証観点を明記 | 本書 **§8** にチェックリスト案。確定時は **操作手順・期待 UI・失敗時**まで拡張し、**changeSpec 正本**に載せる。 |
| UI 上の二重タップ不可は UX 共通化対象。実データの重複防止は Functions の冪等性 | 仕様書 §9 と整合。**クライアント＝一次防御**、サーバ＝再実行時の抑止。 |
| 保守運用時用のエラーログと、アプリ操作者向けの結果出力は別概念 | 本メモ（ローディング）では **結果出力の文言統一までは扱わない**（全体像どおり分離）。 |

## 3. 目的

- **主目的は UI/UX の向上**である（処理中の認知しやすさ・誤操作抑止・挙動の一貫性）。**「共通化」そのものを目的とはしない**（共通化は手続き・成果物の置き場）。
- As-is（現状パターン）と To-be（仕様書）の **ギャップを変更単位に落とし、中タスク 5〜7（changeSpec 作成・実装・検証）の入口**にする（本メモは **中タスク5** の前段）。
- **本草案は合意文書ではない**。レビュー後に優先度・波・完了定義を埋めて初版化する想定。

## 6. To-be 定義（仕様書・最新合意との合致）

以下を **本メモで置く To-be 完了条件の候補**（**changeSpec 正本**に転記する前提）として置く（採用時は優先度を付ける）。

**分類（名称は仕様書と同一の 3 類型で扱う）**

1. **画面表示時の読込**
2. **画面内ユーザー操作による読取系処理**
3. **画面内ユーザー操作による更新系処理**

**ロック・ローディング（最新合意）**

- **画面表示時の読込**および**画面内ユーザー操作による読取系処理**は、**原則ロック不要**（待機表示は必要に応じて行う）。
- **画面内ユーザー操作による更新系処理**では、**ロックを強く見る**（待機表示＋操作ロックを原則とする。表示単位・ロック単位は処理ごとに決定。仕様 §7.3・§6.3）。
- **ローディング表示と操作ロック**は、**当該処理の終了時に解除**する。
- **結果出力を出すために、追加の操作ロックは設けない**（仕様 §7.4）。
- **ボタン単位のみ**の待機表示を標準としない（仕様 §8）。
- **例外**は仕様 §10 に従い、理由・影響範囲を明示する。

## 7. ギャップ → 提案変更（フェーズ例）

**※波・ファイル一覧の確定はレビュー後に行う。** ここは例示。

| フェーズ | 内容 | 根拠 |
|----------|------|------|
| **P0** | §1.5.2 に掲載の **更新系かつスピナーなし**の箇所について、仕様 §7.3・§6.3 に沿う **最低限の待機表示 + 再実行防止**を設計レビューし、実装する | 現状整理メモ「更新系なのに薄い」 |
| **P1** | 初回表示などの**データ取得待ち（読込）の最中**に、**更新系**の操作が同一画面上で並立しうる箇所を洗い、**更新系側のロック・導線**（または画面構成）を見直す。**読込・読取系に対してロックを強める**のは対象ではない（読込・読取系は原則ロック不要） | 現状整理メモ① |
| **P2** | ダイアログ内 CPI 型・`user_actions` 型で、**閉じる／戻る**と処理中 UI の関係を仕様 §6.3 に照合し、必要ならモーダルバリア等を検討 | 仕様 §8 非採用の回避 |
| **P3** | Skeleton／非 UI 層は **呼び出し元画面**の UX とセットで、必要ならガイドライン化のみ（全面改修はしない） | 仕様 §10 例外の余地 |

### 先行整理（推奨）：ローディング母数 **119 件**の **3 類型**への分類 → 波（P0〜P3）の対応付け

**changeSpec 作成・実装の順序を決めるうえで、次を先行して整理するのが望ましい。**

1. **まず** [ローディング表示.md](./ローディング表示.md) **§2.1** に沿い、**各対象箇所を仕様の 3 類型**（画面表示時の読込／画面内の読取系／画面内の更新系）のいずれに当てはまるかを付ける。  
2. **そのうえで**、**どの波（P0〜P3）**に該当するか／該当しない・既存で足りる／要レビューを付ける。

- **母数 119**は Step2（`対象ファイル・対象箇所の確認`）におけるローディング関連の**対象箇所の合計**である（`firebase_options.dart` は母数から除外、[現状の使用パターンの確認 §1](../../03_現状の使用パターンの確認/現状の使用パターンの確認.md)「母数」行参照）。
- [現状の使用パターンの確認 §1.1](../../03_現状の使用パターンの確認/現状の使用パターンの確認.md) の**主要パターン表**は、119 を**パターン型別に束ねた**ものであり、**そのまま＝3 類型の分類完了**でもなければ、**そのまま＝ P0〜P3 の割当完了**でもない（例: **P0** は §1.5.2 のうち**更新系かつスピナーなし**に絞った一覧が [P0_changeSpec前準備_事実整理](./P0_changeSpec前準備_事実整理.md)）。
- **推奨アウトプット**: **対象箇所ごと**（Step2 の単位）に、**3 類型**列・**波**列・根拠列を持つ表または付録。根拠列には「仕様 §4〜7 のどの類型に照合するか」「§7（本メモ）のどの行の論点か」を書けると changeSpec に引き継ぎやすい。
- **1 対象箇所が複数類型・複数波に関係する場合**は、**論点ごとに行を分ける**か、備考で多義性を明示する。

## 8. 受け入れ基準（案）

- [ ] P0 対象箇所のリストが **Step2 の対象箇所 ID またはファイル＋箇所**で特定されている。
- [ ] 各対象に **表示単位・ロック単位**が文書化されている（仕様 §4〜6）。
- [ ] **画面表示時の読込**および**画面内ユーザー操作による読取系処理**について、**原則ロック不要**が仕様・実装判断と一致している（誤って読込・読取系に強いロックを課していない）。
- [ ] **画面内ユーザー操作による更新系処理**について、**ロックを強く見る**方針が仕様 §6.3・§7.3 と一致している。
- [ ] 更新系 CF を呼ぶ **完了時・失敗時** の両方で、**ローディングとロックが解除**され、その後に結果通知（**結果出力のための追加ロックなし**）（仕様 §7.4・§11）。
- [ ] 仕様 §7.3 の「更新系」に該当する処理に、**意図的にロックを付けない**場合は §10 の例外として記載がある。
