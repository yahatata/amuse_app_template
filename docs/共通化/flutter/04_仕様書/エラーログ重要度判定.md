# 保守運用時のエラーログ重要度判定 仕様書（確定版）

## 1. 文書情報

- 文書名: 保守運用時のエラーログ重要度判定 仕様書
- 対象リポジトリ: `functions/`
- 関連システム:
  - 店舗用アプリ
  - モニタアプリ（保守運用用）
  - Google Cloud / Cloud Logging / Error Reporting
- 作成目的:
  - 保守運用時に、全店舗用アプリから集約されたエラーログに対して、運用上の重要度を付与し、素早い検知・確認・優先順位付けを可能にするため
- 本書の位置付け:
  - 本書は、既存の構造化エラーログ共通化実装を前提として、次段階である `errorKey`（エラーキー）導入および重要度判定の設計方針を定めるものである

---

## 2. 背景

現在、1リポジトリから複数の店舗用アプリをリリースし、それぞれ異なる Firebase / Google Cloud プロジェクトに接続して運用している。  
これらを横断して保守運用を行うため、管理用のモニタアプリにてエラーログやシステム確認結果を集約し、障害の素早い検知を行いたい。

既に第1段階・第2段階として、`logger.error` および `console.error` の共通形式化を行い、`logOpsError` を経由して Cloud Logging に構造化ログを出力する状態まで整備されている。  
一方で、現状の構造化ログのみでは、どのログを優先的に確認すべきかの判断が十分にできない。

そのため、各エラーに対して `errorKey` と `基本重要度` を持たせ、必要に応じて `service` による補正を行うことで、モニタアプリ上での絞り込み・アラート・監視の基盤を作る。

---

## 3. 目的

本改修の目的は以下の通り。

1. エラーを素早く検知できるようにすること
2. 全エラーを完璧に分類することではなく、運用上「早く見るべきもの」を早く見つけること
3. 導入初期は、無視してよいものを切り分け、無視できないものは確認対象とすること
4. 将来的には、より細かい緊急度・通知ルールに発展可能な設計にすること
5. 既存の `logOpsError` ベースの構造化ログ基盤の上に、過度な実装コストをかけずに重要度判定を追加すること

---

## 4. 対象範囲

### 4.1 本改修の対象

- `functions/src/**` の Cloud Functions / 共通ロギング処理
- `logOpsError` を経由して出力される ERROR ログ
- それらを集約して利用するモニタアプリ側の重要度判定基盤

### 4.2 本改修の対象外

- モニタアプリ側の UI 実装詳細
- 通知チャネル（メール、Slack、LINE 等）の最終仕様
- `success: false` のみでログを出していない経路への新規 ERROR ログ追加
- 全未処理例外の全面的な try/catch リファクタ
- `functions/__tests__/**`, `functions/scripts/**` のロギング改善
- すべての関数への個別 `errorKey` 明示指定
- 本段階での完璧な緊急度分類

## 6. 用語定義

### 6.1 errorKey（エラーキー）
エラーの「何が起きたか」を表す粗い大分類ラベル。

### 6.2 基本重要度
各 `errorKey` に対してあらかじめ定義するデフォルトの運用重要度。

### 6.3 補正
同じ `errorKey` でも `service` によって重要度が変わる場合に、基本重要度を上書きまたは調整すること。

### 6.4 service
どの業務領域の処理かを表す粗い分類。重要度補正の主軸として利用する。

### 6.5 functionEntry
Cloud Functions の原則 `export const` 名、または関数名。既存の `logOpsError` で使用しているものを継続利用する。

### 6.6 failureType
既存ログに載っている失敗系統・実行文脈の粗い分類。  
現状は `config`, `datastore`, `external_api`, `business`, `scheduled`, `webhook`, `internal` などが存在する。  
本改修では `errorKey` に置き換えず、当面併用する。

---

## 7. 現状整理（As-is）

### 7.1 現状できていること

- 全体として ERROR ログ出力が `logOpsError` 経由に寄せられている
- Cloud Logging 上で `jsonPayload` に共通項目を載せられる
- `functionEntry`, `failureType`, `projectId`, `errorMessage`, `errorName`, `context` が横断比較可能
- 機微情報や長文 payload はプレビューや truncate に制限している

### 7.2 現状の問題

- 重要度判定のための共通キーがない
- `errorMessage` は原因調査には使えるが、重要度判定の主軸には不向き
- `failureType` は原因分類と実行文脈が混ざっており、重要度判定の主キーにはしづらい
- 同じ種類のエラーでも、業務やサービスによって重みが異なる
- モニタアプリ側で「今すぐ確認すべきか」を自動判定しづらい

---

## 8. To-Be 概要

本改修では、既存の `logOpsError` ベースの構造化ログに対して、以下を追加する。

1. `errorKey` を導入する
2. `service` を導入する
3. 各 `errorKey` に `基本重要度` を持たせる
4. `errorKey` の付与方法として `共通判定 + 個別指定` を採用する
5. 一部の `errorKey` についてのみ、`service` による補正ルールを持たせる
6. 重要度判定は、モニタリングやアラートで利用できるよう構造化ログとして保持できる設計とする

---

## 9. 設計方針

### 9.1 基本方針

- `errorKey` は大分類にとどめる
- 全関数 × 全ケースの個別キー設計は行わない
- 標準情報だけで判定できるものは共通判定に寄せる
- 標準情報だけでは判定できない重要なもののみ個別指定する
- 重要度補正は全 `errorKey` に対して行わず、ぶれやすい一部のみ行う
- 導入初期は厳密な正解ではなく、見逃しにくい運用を優先する

### 9.2 `failureType` の扱い

- `failureType` は削除しない
- `errorKey` は `failureType` を置き換えるものではなく、別軸の分類情報として追加する
- 将来的に `failureType` の再設計はあり得るが、本改修では現状維持とする

### 9.3 `errorMessage` の扱い

- `errorMessage` は調査用に保持する
- 重要度判定の主キーには使わない
- 表示用メッセージと判別用キーは分離する

## 10. errorKey 設計

### 10.1 errorKey の役割

`errorKey` は、エラーの一意識別子ではなく、運用上の分類ラベルとして扱う。

### 10.2 errorKey の粒度

- 関数名や業務名をキー名に埋め込まない
- `NOT_FOUND`, `TIMEOUT`, `CONFIG_ERROR` のような再利用可能な大分類とする
- `functionEntry` や `service` は別フィールドで持つ

### 10.3 errorKey の正式一覧

- `INVALID_INPUT`
- `UNAUTHENTICATED`
- `PERMISSION_DENIED`
- `NOT_FOUND`
- `ALREADY_EXISTS`
- `FAILED_PRECONDITION`
- `CONFLICT`
- `DATA_INCONSISTENCY`
- `IDEMPOTENCY_CONFLICT`
- `CONFIG_ERROR`
- `EXTERNAL_SERVICE_ERROR`
- `TIMEOUT`
- `TEMPORARY_UNAVAILABLE`
- `RESOURCE_EXHAUSTED`
- `INTERNAL_ERROR`

### 10.4 errorKey の命名方針

- 英大文字スネークケースまたは英大文字定数風の統一された形式とする
- 表示用文言として使わない
- 将来的な追加・変更に備え、意味が広すぎず狭すぎない名称にする

### 10.5 各 errorKey の説明（一文）

| errorKey | 説明 |
|---|---|
| `INVALID_INPUT` | リクエストや入力値が形式・範囲・業務ルール上の検証に通らず、処理を続けられない。 |
| `UNAUTHENTICATED` | 認証情報がない、または無効で、呼び出し元の本人性を確認できない。 |
| `PERMISSION_DENIED` | 認証はあるが、対象リソースや操作に対する権限がなく、実行が拒否された。 |
| `NOT_FOUND` | 参照・更新の対象とするリソースやドキュメントが存在しない。 |
| `ALREADY_EXISTS` | 一意制約や重複禁止の文脈で、既に同じものが存在するため作成・登録できない。 |
| `FAILED_PRECONDITION` | 処理に必要な前提（状態・フェーズ・依存関係など）が満たされておらず、実行できない。 |
| `CONFLICT` | 同時更新や競合により、要求した状態遷移や更新が整合的に適用できない。 |
| `DATA_INCONSISTENCY` | データ同士の整合性が崩れている、または整合チェックで不整合が検出された。 |
| `IDEMPOTENCY_CONFLICT` | べき等キーや重複実行の文脈で、既に処理済みや重複と判定され、安全に再実行できない。 |
| `CONFIG_ERROR` | 設定値・環境変数・構成の欠落・不正・読み込み失敗など、システム構成に起因する。 |
| `EXTERNAL_SERVICE_ERROR` | 外部APIや外部サービスからエラー応答を受け取るなど、連携先側の失敗に起因する（タイムアウト専用ではない）。 |
| `TIMEOUT` | 外部サービスや内部処理が許容時間内に完了せず、時間切れとなった。 |
| `TEMPORARY_UNAVAILABLE` | 一時的な障害・メンテナンス・過負荷などにより、当該処理やサービスが利用できない。 |
| `RESOURCE_EXHAUSTED` | クォータ・レート制限・同時実行上限など、リソース上限に達しこれ以上処理できない。 |
| `INTERNAL_ERROR` | 想定外の例外や実装不備の疑いがあり、原因がアプリ内部に帰するエラーである。 |

## 11. 基本重要度設計

### 11.1 基本重要度の段階

- `low`
- `medium`
- `high`

### 11.2 各 errorKey の基本重要度

| errorKey | 基本重要度 |
|---|---|
| `INVALID_INPUT` | `low` |
| `UNAUTHENTICATED` | `low` |
| `PERMISSION_DENIED` | `medium` |
| `NOT_FOUND` | `medium` |
| `ALREADY_EXISTS` | `low` |
| `FAILED_PRECONDITION` | `medium` |
| `CONFLICT` | `medium` |
| `DATA_INCONSISTENCY` | `high` |
| `IDEMPOTENCY_CONFLICT` | `low` |
| `CONFIG_ERROR` | `high` |
| `EXTERNAL_SERVICE_ERROR` | `medium` |
| `TIMEOUT` | `medium` |
| `TEMPORARY_UNAVAILABLE` | `medium` |
| `RESOURCE_EXHAUSTED` | `medium` |
| `INTERNAL_ERROR` | `high` |

### 11.3 基本重要度の意味

- `low`
  - 軽い寄り
  - もしくは現時点では優先確認不要
  - 通知・アラート・優先表示の対象外

- `medium`
  - 重いと断定はしない
  - ただし導入初期は取りこぼし防止のため確認対象に含める
  - 通知・アラート・優先表示の対象

- `high`
  - 設計上、放置リスクが高い
  - 明確に優先確認すべき
  - 通知・アラート・優先表示の対象

### 11.4 各 errorKey の基本重要度の根拠

- `INVALID_INPUT`（`low`）
  - 入力不正・形式不正・必須値不足は、想定内の利用者操作起因であることが多く、導入初期にすべてを通知対象にするとノイズが増えやすいため、基本重要度は low とする。

- `UNAUTHENTICATED`（`low`）
  - 未認証・認証切れは想定内に発生しうるため、基本重要度は low とする。
  - ただし、内部処理や本来認証済みであるべき経路で発生する場合は別途確認対象となりうる。

- `PERMISSION_DENIED`（`medium`）
  - 権限不足は想定内の拒否である可能性がある一方、本来許可されるべき処理が失敗している可能性もあるため、軽いと断定せず基本重要度は medium とする。

- `NOT_FOUND`（`medium`）
  - 対象不存在は、削除済みデータ参照など軽いケースと、業務上必須のデータ欠落など重いケースが混在するため、基本重要度は medium とし、必要に応じて service 補正を行う。

- `ALREADY_EXISTS`（`low`）
  - 重複作成・二重登録防止によって発生するケースを含み、運用上ただちに追うべき障害とは限らないため、基本重要度は low とする。

- `FAILED_PRECONDITION`（`medium`）
  - 前提条件未達は、単なる操作順の問題から業務状態の不整合まで意味の幅が広いため、基本重要度は medium とし、必要に応じて service 補正を行う。

- `CONFLICT`（`medium`）
  - 競合・並行更新は一時的かつ再試行可能な場合もあるが、重要処理で継続発生する場合は問題となるため、導入初期は取りこぼし防止の観点から基本重要度を medium とする。

- `DATA_INCONSISTENCY`（`high`）
  - データ整合性崩れは放置リスクが高く、再試行のみで自然解消しない可能性が高いため、基本重要度は high とする。

- `IDEMPOTENCY_CONFLICT`（`low`）
  - 冪等性防止が正常に機能した結果として発生するケースを含むため、基本重要度は low とする。
  - ただし、設計漏れや再送異常の兆候が疑われる場合は別途確認対象とする。

- `CONFIG_ERROR`（`high`）
  - 設定不備は恒久失敗につながりやすく、再試行では解消しない可能性が高いため、基本重要度は high とする。

- `EXTERNAL_SERVICE_ERROR`（`medium`）
  - 外部サービス連携失敗は単発の一時障害である場合もある一方、業務影響が大きい場合もあるため、導入初期は取りこぼし防止の観点から基本重要度は medium とする。

- `TIMEOUT`（`medium`）
  - タイムアウトは単発の一時遅延である場合もあるが、重要処理や継続発生時には無視しづらいため、基本重要度は medium とする。

- `TEMPORARY_UNAVAILABLE`（`medium`）
  - 一時的な利用不可は軽いケースもありうるが、導入初期は見逃し防止を優先し、基本重要度は medium とする。

- `RESOURCE_EXHAUSTED`（`medium`）
  - クォータ・レート制限・資源不足は単発では即重大と限らないが、継続すると全体影響が大きくなるため、基本重要度は medium とする。

- `INTERNAL_ERROR`（`high`）
  - 実装不備・未分類例外・想定外例外を含み、原因不明のまま放置するリスクが高いため、基本重要度は high とする。

### 11.5 導入初期の通知閾値

- 導入初期は `medium` 以上を通知・アラート・優先表示の対象とする
- これは `medium` を常に高い緊急度として扱うという意味ではなく、取りこぼし防止を優先した通知閾値設定である
- 将来的には、実装・運用結果を踏まえて通知閾値を `high` 以上へ見直す可能性がある

## 12. errorKey 付与方針（共通判定 + 個別指定）

### 12.1 基本方針

`errorKey` の付与は、以下の二段構えとする。

1. 個別指定
   - 関数側で業務文脈を踏まえて明示的に指定する
2. 共通判定
   - 個別指定が無い場合に、共通関数で標準情報から推定する

### 12.2 個別指定の対象

以下のように、標準情報だけでは意味が足りないものを対象とする。

- `CONFIG_ERROR`
- `DATA_INCONSISTENCY`
- `IDEMPOTENCY_CONFLICT`
- 業務的に特別重い `FAILED_PRECONDITION`
- 業務的に特別重い `NOT_FOUND`

### 12.3 共通判定の対象

以下のように、標準情報から比較的寄せやすいものを対象とする。

- `INVALID_INPUT`
- `UNAUTHENTICATED`
- `PERMISSION_DENIED`
- `NOT_FOUND`
- `ALREADY_EXISTS`
- `FAILED_PRECONDITION`
- `CONFLICT`
- `TIMEOUT`
- `TEMPORARY_UNAVAILABLE`
- `RESOURCE_EXHAUSTED`
- `INTERNAL_ERROR`

### 12.4 実装上の優先順位

- `errorKey` が明示指定されている場合は、それを優先する
- 明示指定が無い場合は、共通判定関数で自動推定する

---

## 13. 共通判定方針

### 13.1 共通判定の目的

標準情報から自動で粗い `errorKey` を決め、全関数に重い個別実装を強制しない。

### 13.2 共通判定で見る候補情報

- 例外オブジェクトの `code`
- HTTP status
- gRPC / canonical code
- `error.name`
- `error.message`
- 実行入口情報（scheduled / webhook / callable 相当）
- stack trace の特徴

### 13.3 標準情報からの推定方針（例）

- `INVALID_ARGUMENT` / 400 → `INVALID_INPUT`
- `UNAUTHENTICATED` / 401 → `UNAUTHENTICATED`
- `PERMISSION_DENIED` / 403 → `PERMISSION_DENIED`
- `NOT_FOUND` / 404 → `NOT_FOUND`
- `ALREADY_EXISTS` / 409 → `ALREADY_EXISTS`
- `FAILED_PRECONDITION` → `FAILED_PRECONDITION`
- `ABORTED` / 409 → `CONFLICT`
- `RESOURCE_EXHAUSTED` / 429 → `RESOURCE_EXHAUSTED`
- `DEADLINE_EXCEEDED` / 504 → `TIMEOUT`
- `UNAVAILABLE` / 503 → `TEMPORARY_UNAVAILABLE`
- `INTERNAL` / `UNKNOWN` / `TypeError` / `ReferenceError` → `INTERNAL_ERROR`

### 13.4 注意点

- 共通判定はあくまで技術的分類である
- 業務上の意味づけまではできない
- そのため、業務的に重要なものは個別指定で上書きする

## 14. service 設計

### 14.1 service の目的

- `functionEntry` より粗い単位で業務領域を表す
- 重要度補正の主な軸として使う
- 関数名ベースの補正ルール増殖を防ぐ

### 14.2 service の正式一覧

- `accounting`
- `close_process`
- `store`
- `attendance`
- `payroll`
- `staff`
- `shift`
- `business_hours`
- `tournament_schedule`
- `tournament`
- `orders`
- `user`
- `side_game`
- `audit_log`
- `line`
- `analytics`
- `platform`

### 14.3 service の設計上の補足

- `payroll` は `attendance` と分離する
- `tournament_schedule` は `tournament` と分離する
- `close_process` は `store` と分離する
- `config` は独立 service にせず `platform` に含める
- `business_hours` は **全店舗で参照される営業時間マスタ**を扱う領域とする。実装は `functions/src/shared/businessHours/` にあり、`domains/shift/index.ts` から export されている Callable もあるが、**業務上はシフト運用専用ではない**ため **`shift` には含めない**。
- 次の `functionEntry` は **`service` として `business_hours`** にマッピングする（changeSpec の対応表に記載する）: `initBusinessHoursForMonth`, `generateBusinessHoursForMonthFromStyles`, `generateBusinessHoursForYearFromStyles`, `setBusinessHoursManualForDay`, `scheduleGenerateNextYearBusinessHours`

### 14.4 `service` と `functionEntry` の関係

- `service` は粗い業務分類
- `functionEntry` は具体的な関数識別
- 重要度補正は原則 `service` を優先し、必要な場合のみ将来的に `functionEntry` を使う

## 15. 重要度補正方針

### 15.1 補正の基本方針

- すべての `errorKey` に補正をかけない
- 重みがぶれやすいものだけ補正する
- 補正は原則 `service` 単位で行う
- `functionEntry` 補正は現時点では導入しない
- 将来的に必要が確認できた場合のみ `functionEntry` 補正へ拡張する

### 15.2 補正対象の errorKey

- `NOT_FOUND`
- `FAILED_PRECONDITION`
- `PERMISSION_DENIED`
- `EXTERNAL_SERVICE_ERROR`
- `TIMEOUT`

### 15.3 補正対象にする理由

- 同じ `errorKey` でも文脈による重要度差が大きい
- 標準情報だけでは重みが決めにくい
- 実運用で頻度や影響がありそう

### 15.4 補正対象にしないもの

以下は、初期段階では基本重要度固定寄りで扱う。

- `CONFIG_ERROR`
- `DATA_INCONSISTENCY`
- `INTERNAL_ERROR`
- `UNAUTHENTICATED`
- `ALREADY_EXISTS`
- `IDEMPOTENCY_CONFLICT`
- `INVALID_INPUT`
- `TEMPORARY_UNAVAILABLE`
- `RESOURCE_EXHAUSTED`

### 15.5 補正ルールの基本順序

1. `errorKey` の基本重要度を取得
2. 補正対象 `errorKey` であるか確認
3. 該当する場合、`service` を見て補正
4. 現時点では `functionEntry` 補正は行わない

## 17. 実装方針

### 17.1 `logOpsError` の拡張方針

`logOpsError` には、少なくとも以下の概念を追加できる構成とする。

- `errorKey`
- `service`

### 17.2 共通判定関数

以下のような共通関数を新設する方針とする。

- `classifyErrorToErrorKey(...)`
- 重要度補正を行う共通処理

### 17.3 実装の基本動作

1. 呼び出し側で `errorKey` が明示されていれば採用
2. 無ければ共通判定関数で `errorKey` を決定
3. `errorKey` に対応する基本重要度を取得
4. 必要なら `service` で補正
5. 最終的な重要度情報をモニタリング側で利用可能にする

### 17.4 導入範囲

- まずは `logOpsError` のインターフェース拡張
- 次に共通判定を導入
- 最後に重要関数のみ個別指定を追加

## 18. 個別指定対象の考え方

### 18.1 基本方針

全関数に個別指定を入れない。  
個別指定するのは以下のいずれかに該当するもの。

- 標準情報だけでは意味が足りない
- 事業影響が大きい
- 発生時に運用で見逃したくない
- 恒久失敗になりやすい

### 18.2 個別指定対象の考え方

個別指定は、以下のいずれかに該当する処理を優先対象とする。

- 標準情報だけでは意味が足りない処理
- 事業影響が大きい処理
- 発生時に運用で見逃したくない処理
- 恒久失敗になりやすい処理
- 設定不備・データ整合性・冪等性衝突など、業務文脈による明示的な分類が必要な処理

個別指定の具体的な対象関数・対象ファイル・対象条件は、後続の changeSpec で定める。

## 19. 検証観点

### 19.1 単体観点

- `errorKey` 明示指定時に payload に正しく載る
- `errorKey` 未指定時に共通判定で期待通りの値になる
- `service` が正しく出力される
- 重要度が基本重要度 + 補正で正しく決まる
- `failureType` 既存項目が壊れない

### 19.2 ログ観点

- Cloud Logging 上で `errorKey`, `service`, `functionEntry`, `failureType` でフィルタできる
- 同じ `errorKey` を横断集計できる
- 既存の調査用情報（`errorMessage`, `errorName`, `context`）が失われない

### 19.3 運用観点

- `low` と `medium以上` の切り分けが可能になっている
- 重要な会計・閉店・設定不備・整合性崩れを埋もれさせない
- 初期運用では取りこぼし防止を優先できる
- 想定外エラーが `INTERNAL_ERROR` 等に落ちて見逃されにくい

## 21. 備考

- 本改修の目的は、導入初期段階における素早い検知であり、完璧な障害分類ではない
- `errorKey` は全ケースを一意に表す識別子ではなく、運用上の大分類ラベルとして扱う
- 補正ルールは最小限から開始し、運用しながら増やす
- `medium` 以上を通知・アラート・優先表示対象とするのは、現時点では取りこぼし防止のためであり、`medium` 自体を常に高い緊急度とみなす趣旨ではない
- 今後、実際の誤判定やノイズ状況を見て `errorKey` / `service` / 補正ルール / 通知閾値を見直す前提とする
