# 業務重要度判定要件表（初版）

**目的**: `severity >= ERROR` で既に取得対象のログに対し、モニタアプリ側で業務重要度（高 / 中 / 低、内部スコア 5 / 3 / 1）を判定するために **何の情報が必要か** を実コード・関連仕様から整理する。  
**本稿の位置づけ**: 実装前の「判定に必要な材料」の要件定義初版。業務重要度の最終ラベルは人が決める。  
**調査範囲**: `functions/src/**/*.ts` を主に確認。`functions/lib/**` は対象外。差分仕様・changeSpec・As-is 整理資料と照合。  
**現行ログの前提**: `logOpsError` は現状 `failureType` / `functionEntry` / `operation` / `projectId` / `errorMessage` / `errorName` / `context`（フラット展開）を出力。差分仕様で想定される `errorSource` / `service` / `errorKey` / `sourceProduct` / `sdkCode` / `httpStatus` / `detailReason` 等は **本稿では「拡張後の想定」と現行を区別**して記載する。

## 1. 冒頭サマリ

| 項目 | 内容 |
|------|------|
| **見た範囲** | `logOpsError` 呼び出し箇所、`domains/bills`（会計）、`domains/storeMeta`（店舗開閉・営業日）、`domains/tournament_*`、`domains/webhook`（LINE）、`enqueueTournamentTasksCore`、`processingLease`、`controlHook`、ユーザー作成系 callable の有無 |

| **傾向（custom）** | 仕様・changeSpec 上の `errorKey`（例: `ACCOUNTING_*`, `STORE_PROCESSING_KIND_MISMATCH`）と **実コードの文字列は未接続**（`functions/src` で該当リテラル grep ヒットなし）。会計・店舗は現状 **HttpsError の code/message + `logOpsError` の context** で表現。業務重要度の材料は **errorKey 単独では不足しがち**（同一 `failed-precondition` に複数意味が載る）。`context` に `billId` / `status` / `processing.kind` 等があれば判定しやすい。 |

| **傾向（function_common）** | `getCurrentBusinessDateKeyOrThrow` の非 HttpsError 経路、`registerForTournament` の広い catch、`controlHook` の汎用 catch など、**operation 細分化・errorKey・構造化 context が無いと「高/中/低」の機械判定が難しい**行が多い。 |

## 3. 横断所見

### errorKey 単独で足りるケース / 足りないケース

| 観点 | 内容 |
|------|------|
| **足りる可能性が高い** | 仕様で **1 キー = 1 意味** が保証され、かつ **同一 functionEntry でそのキーしか起きない** と分かっている場合（例: 将来の `STORE_PROCESSING_KIND_MISMATCH` が専用スローに限定される）。 |
| **足りない** | `ACCOUNTING_INVALID_STATE` のように **複数のビジネス理由が同一カテゴリ** に入る場合。**`context` に `status`, `reasonCode`, `billId`** が必要。 |
| **特記** | `ACCOUNTING_ACTIVE_STAY_CONFLICT` は **競合の相手方（既存 stay・卓）** が無いと「高か中か」が決めにくい。 |
| **トーナメント** | 「前提違反」「状態不整合」は **errorKey だけでは足りず**、`tournamentId` / `phase` / `scheduled vs active` を `context` に載せる設計が望ましい。 |

### operation の粒度が不足している箇所

- `registerForTournament`: `recordTournamentAction` 失敗と、メイン catch が区別しづらい。
- `controlHook`: `operation: 'request'` が広すぎる。
- `startAccounting` / `createBillWithActiveStay`: エントリ単位の catch 1 つに複数シナリオ。

### context を足すべき箇所

- 会計: `status`, `accountingStartedAt` の有無、冪等キー再利用フラグ。
- 店舗: `processing.kind`, `runId`, 開閉のどちらのフローか。
- トーナメント: `tournamentId`, `taskType`, `enqueueState` 遷移。
- external: **マスク可能な範囲で** リソース識別子（doc path の一部、task 名）。

### function_common のままだと厳しい箇所

- **HttpsError をそのままクライアントへ返し、`logOpsError` に到達しない**成功系前提違反（例: `getCurrentBusinessDateKeyOrThrow` の failed-precondition）。
- **広い catch** で `message` だけが残る箇所。
- **logOpsError を置いていない callable**（例: `createUserByApp`）。

### external_api で code 抽出補強が必要な箇所

- **Firebase Admin SDK** の Firestore / Auth / Storage: 例外から **`code` / `status`** を正規化して `sdkCode` に載せる（差分仕様の `sourceProduct` とセット）。
- **Cloud Tasks**: enqueue 失敗時の **gRPC/HTTP 相当コード** を `detailReason` 補助ではなく **機械可読フィールド** に。
- **LINE**: 既に `response.status` あり → **`sourceProduct` と `httpStatus` を固定キー化**すればモニタ側が扱いやすい。

## 4. 人間が最終判断すべき論点

- **代替手段**: 当該エラー時に店舗は手動・別端末で継続できるか（例: LINE 通知失敗、Tasks 遅延）。
- **営業時間内の即時性**: 開店・会計・トーナメント開始が **何分の遅延まで許容か**。
- **通知失敗の重み**: 顧客向け Push が落ちても **コア会計が動けば低** とするか。
- **状態競合**: `processing.kind` 不一致や active stay 競合を **運用オペレーションで解消する想定か**、エスカレーション必須か。
- **ベストエフォート成功**: `registerForTournament` のように **API は成功だが内部補助が失敗**する行を、監視上どの重要度にするか。
- **汎用 internal / Error**: スタックのみのログを **一律「要確認」**にするか、**functionEntry ホワイトリストで高**にするか。
- **個人情報と監査**: `context` 拡張時に **どこまで載せるか**（マスク方針と優先度のトレードオフ）。
