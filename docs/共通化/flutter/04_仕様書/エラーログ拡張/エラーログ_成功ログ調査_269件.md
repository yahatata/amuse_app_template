# 成功ログ調査（`logOpsError` 269 件との対応）

## 1. 目的

- 各 **`logOpsError` 呼び出し**（`エラーログ_context調査_269件.md` および本リポの Step2-1 スコープ **269 件**）について、**同じ操作・同じ相関の「成功」が運用上どこに残るか**を把握する。
- 失敗時に載せた **相関用 `context` キー**（およびマージ後の想定）と、成功側で **同じキー名で辿れるか**を確認する（`エラーログ監視_再試行と相関キー.md` §6）。

## 2. 全体の流れ（イメージの確認）

次の順序で進める、という理解で**よい**。

1. **調査** — 269 行それぞれについて、「失敗 `logOpsError`（`functionEntry` / `operation`）に対し、**現状**成功はどの経路のログ／データに出ているか」**をざっくり対応づけ**、不足をメモする。
2. **不足の補完** — 成功が **Cloud Logging 上**ほぼ追えない・相関不能な行については、**新規の成功ログ**（既存 `logger.info` への構造化追記、または共通 INFO ヘルパ等）**を追加する**方針を決め、実装する。
3. **context の揃え** — 失敗の `logOpsError` の `context`（＋必要なら FC マージ）で使っている **相関キー名・値**と、成功側の payload／Firestore 等の**キーを一致**させる（同じ `operationId` 等を同じキー名で載せる）。

**補足（269 件の読み方）**

- 269 は **失敗呼び出しの行**であり、**成功ログが 269 本あるわけではない**。同一 callable 内に複数の `logOpsError` があるため、**成功は「1 リクエストあたり1本」など上位にまとまる**ことが多い。
- 対応づけの単位は厳密には **「`functionEntry` + 該当ハンドラの成功パス」**が現実的。表では **`#`（269 の行番号）を参照しつつ、同一成功パスに複数行を束ねる**書き方でよい。

## 3. 成功が「乗りうる」層（調査の観点）

調査表を埋めるとき、少なくとも次を区別する。

| 層 | 例 | 相関のしやすさのメモ |
|----|----|------------------------|
| **A. Cloud Logging** | `logger.info` / `logger.log`、構造化、一部 `console.log` | `tenant-errors`（ERROR）と**別プロジェクト・別シンク**で突き合わせる想定。フィールド揃えが有効。 |
| **B. Firestore `operationLogs`** | `writeSingleOperationLog` | トーナメント操作系に多い。**業務巻き戻し**向け。Logging 直結ではない。 |
| **C. その他** | クライアント戻り値のみ、他コレクション更新のみ | ログ相関は**弱い**／Runbook では **B や管理画面**に寄せる。 |

「269 に対応する成功」は **A か B（または両方）** になっているかを主に見る。

## 4. 調査表（列定義と記入例）

`エラーログ_context調査_269件.md` の **`#`・ソース・`functionEntry`・`operation`・マージ後キー**を参照しながら、**以下の列**を 1 行ずつ（または成功パス単位にまとめて）埋める。

| # | 失敗ソース（行） | functionEntry | operation | 分類 | 想定相関キー（失敗・調査表ベース） | 成功の出所（A/B/C） | 成功の具体（ファイル・略記） | 失敗と突き合わせ可能か | 不足・メモ | 次アクション |
|---|------------------|---------------|-----------|------|-----------------------------------|--------------------|-----------------------------|------------------------|------------|-------------|
| 例 | `…/addon.ts:221` | `addon` | `recordTournamentActionBestEffort` | 非FC | billId, callerUid, operationId, tournamentId, … | B + （必要なら A） | `writeSingleOperationLog` 成功分 | ○/△/× | 成功のみ operationLog なら Logging 用に A 要否 | 追記 or 新規 INFO |

**記入の目安**

- **突き合わせ可能か**: ○ 同一 `operationId` 等で Firestore/Logging どちらかで辿れる / △ キーはあるが名前や層が違う / × 成功がほぼ無い。
- **次アクション**: 空欄、または `context キー名揃え` / `成功 INFO 1 本追加` / `operationLog 継続でよい` 等。

## 5. 実装フェーズ（調査のあと）の分け方（案）

1. **層の決定** — 行ごとに「**Logging だけ**で足りる」「**operationLog で足りる**（Runbook 明記）」「**両方**」のいずれかを決める。
2. **不足を埋める** — Cloud Logging 上の成功が弱い行から、**既存 `logger.info` への object 追記**または**共通化した INFO 1 本**を追加（キー名は失敗 `context` に合わせる）。
3. **context 揃え** — 失敗 `logOpsError`・成功ログ・（必要なら `operationLogs`）で **`operationId` / `tournamentId` / `callerUid` 等の名前と値**を揃える。

## 7. 調査の進め方（具体手順）

269 行を**上から機械的に1行ずつ**やるのではなく、**作業量を減らす分割**と、**同じパターンの束ね**を併用する。

### 7.1 準備

1. **`エラーログ_context調査_269件.md` を主表**とする（各 `#` に `ソース`・`functionEntry`・`operation`・マージ後キーがある）。必要なら **PDF / スプレッドシートにコピー**して列を足してもよい（失敗 269 行＋上記「調査表」の列）。
2. コードは **`functions/src` 上の `ソース` パス**（`…調査_269件.md` の 1 列目）を開く。行番号は**リファレンス**であり、改行差でズレる場合は **`logOpsError` の `operation` 名で当該 catch を検索**する（IDE の「型定義/参照」より grep の方が速いことが多い）。

### 7.2 負荷を下げる分割

1. **ファイル単位で集約** — `エラーログ_context調査_269件.md` から `ソース` の**ファイルパス**（`:` より前）を抜き出し、**重複を除く**。同一ファイル内の複数 `logOpsError` は、**1 回ファイルを読めば一括判断**しやすい。
2. **ドメイン単位** — 慣れている領域から。トーナメント系（`tournament_activeTournament` / `tournament_createTournament`）は **`writeSingleOperationLog` が多い**ため、**B 層の有無**が先に見える。会計・勤怠等は **A 層（`logger.info`）**の確認が中心になりやすい。
3. **operation 名で束ねる** — 同じ `functionEntry` かつ同じ `operation`（例: `registerUserFailed` とその前後の best-effort）は、**1 行に「# をカンマ区切り」**でまとめてもよい。

### 7.3 1 ファイル（または 1 callable）あたりの見る順

1. **`logOpsError` を全検索**（`rg 'logOpsError' そのファイル`）。catch の位置を把握する。
2. 各 `logOpsError` について、**同じ `try` ブロック内の直後**または**外側**に、**成功 return / 次処理** があるか追う。部分成功（ベストエフォート）の場合は、**メイン return が成功扱い**の注釈（コメント）も確認する。
3. **成功の痕跡**を探す:
   - `writeSingleOperationLog`（引数の `operationId` / `tournamentId` / `deviceId` 等）
   - `logger.info` / 構造化 `logger`（第 2 引数に object があるか）
   - それ以外は **C**（戻り値のみ等）に近い
4. **失敗 `context` に載っている相関 ID**（調査表の「マージ後」列）が、成功側の `writeSingleOperationLog` や `logger` に**同じ変数**で渡っているかざっくり照合する。
