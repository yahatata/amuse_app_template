## 3. 本改修の目的

本改修の目的は、**Functions 側で重要度を判定することではない。**

本改修の目的は以下の通り。

1. モニタアプリ側で重要度判定するための材料を、Functions 側ログに共通形式で残せるようにする
2. 全エラーを `errorSource` で分類できるようにする
3. 業務上重要な一部の関数内エラーのみ、明示的な `errorKey` を付与できるようにする
4. 外部 API 起因エラーについて、現状より詳細な判定材料を残せるようにする
5. As-Is の `logOpsError` 基盤を活かし、過度な try/catch 全面改修を避ける

## 5. 基本方針

### 5.1 まず `errorSource` を切る

本改修では、まず全エラーを次の 3 種類に分類する。

- `external_api`
- `function_common`
- `function_custom`

### 5.2 `errorKey` は `function_custom` のみ

`errorKey` は、**`function_custom` の場合にのみ明示的に付与する。**

- `external_api` では `errorKey` をこちらで用意しない
- `function_common` でも `errorKey` をこちらで用意しない
- `function_custom` だけが、業務上意味のある個別 `errorKey` を持つ

### 5.3 `external_api` と `function_common` は判定材料を残す

`external_api` と `function_common` では、こちらで共通分類キーを定義して運用するのではなく、**後段判定に必要な材料を残すことを優先する。**

### 5.4 重要度判定はモニタアプリ側で行う

本改修では、Functions 側で基本重要度や最終重要度は判定しない。  
重要度はモニタアプリ側・クエリ側・集約側ロジックで判定する。

### 5.5 `failureType` の扱い（仕様上は廃止方向・実装は段階的）

本改修の**分類・観測の主軸**は **`errorSource` / `service` / `functionEntry` / `errorKey`（custom 時）/ `errorName` / `errorMessage` / external 項目（`sourceProduct` / `sdkCode` / `httpStatus` / `detailReason`）/ `context`** である。

- **`failureType` は今後の設計主軸ではない。** 仕様上は**廃止方向**とする。
- 既存コード・既存の Cloud Logging 行には **`failureType` が残存しうる**。「既にコードベースから完全削除済み」とは限らない。
- **本改修（差分実装）の必須スコープに、`failureType` のコードベース全体からの完全削除は含めない。** 完全削除は **後続の専用タスク**で行う。
- 本改修に伴う実装では、**新規追加・新規参照は行わない。** 変更のついでに触れる箇所では、**可能な範囲で `failureType` を除去してよい**（専用タスクまで待たない軽減）。

本改修で追加する **`errorSource` は `failureType` の置換を目的としない**（別軸の分類）。既存ログとの連続性が必要な場合は、移行期間中は payload に `failureType` が残ることもあり得る。

## 6. 用語定義

### 6.1 `errorSource`
エラーの発生源と扱い方の分類。

#### `external_api`
外部 API、外部サービス、SDK が返したエラー。  
例:
- Firestore
- Auth
- Storage
- Cloud Tasks
- LINE API
- その他 SDK / 外部サービス

#### `function_common`
Cloud Functions 内で発生したエラーのうち、個別 `errorKey` を付与していないもの。  
例:
- `TypeError`
- `ReferenceError`
- `RangeError`
- 想定外の `Error`
- promise の未処理失敗
- 関数内ロジックでの想定外失敗

#### `function_custom`
Cloud Functions 内で発生したエラーのうち、業務上の意味を明示するために個別 `errorKey` を付与するもの。

### 6.2 `errorKey`
`function_custom` のときにのみ付与する、業務上の明示ラベル。  
例:
- `ACCOUNTING_ALREADY_STARTED`
- `IDEMPOTENCY_CONFLICT`
- `STORE_CONFIG_MISSING`
- `UNSETTLED_BILL_EXISTS_ON_CLOSE`

### 6.3 `service`
どの業務領域の処理かを表す分類。  
本改修では、重要度補正のためではなく、**ログ集約時の絞り込み・比較軸**として導入する。

### 6.4 `functionEntry`
Cloud Functions の `export const` 名、または As-Is で採用済みの関数名。

### 6.4.1 `operation`（呼び出し位置・段階の区別）

- **目的**: 同一 `functionEntry` でも **どの分岐・どの処理段階**で失敗したかを、Cloud Logging 上で区別するための補助ラベル。
- **必須条件（本改訂・2026-04-11）**: ログ引数の **`functionEntry` が同一文字列リテラル**として現れる **`logOpsError` 呼び出しが 2 回以上**ある場合、**各呼び出しに `operation` プロパティを付与する**（値は文字列リテラルまたは式。例: `operation: operationForStartAccountingKey(error.errorKey)`）。
- **一意性**: **`operation` が文字列リテラルで指定されている呼び出し同士**では、**同一 `functionEntry` スコープ内で値の重複を禁止**する（モニタ上で同一ログに見えないようにする）。
- **静的検証**: `functions/scripts/verifyLogOpsOperation.cjs` を参照。`functions/src` を走査し、上記必須・一意（リテラル同士）をチェックする。`src/debug` / `demo_data` / `unused_function_lib` は対象外とする。
- **単一呼び出しのみ**の `functionEntry` については、従来どおり **`operation` は任意・推奨**（§8.5）。

### 6.5 `failureType`（過去互換・非主軸）
歴史的経緯により、As-Is の payload に含まれることがある**過去互換の粗い分類**。**本仕様の設計主軸ではない。** 新規設計・新規実装では **依存しない。** コードベースからの除去は **後続の専用タスク**とする（§5.5）。

### 6.6 `sourceProduct`
`external_api` に分類されたエラーについて、**どの外部プロダクト起因か** を表す項目。  
`sourceProduct` は出力時に判定する値とし、現時点の集合値は以下とする。

- `firestore`
- `auth`
- `storage`
- `cloud_tasks`
- `line_api`

### 6.7 `sdkCode`
外部 API / SDK が返す **raw の識別コード** を保持する項目。  
ここでいう raw の識別コードとは、API / SDK 側が定義している `code`, `status`, `error code` 名称等のうち、**失敗種別の識別子として扱える短い値** を指す。

例:
- `storage/object-not-found`
- `auth/id-token-expired`
- `NOT_FOUND`
- `FAILED_PRECONDITION`

以下は `sdkCode` に含めない。

- HTTP の数値ステータスコード
- 長文のエラーメッセージ全文
- こちら側で解釈して作成した分類コード

### 6.8 `httpStatus`
外部 API / SDK エラーのうち、**HTTP レイヤで取得できる 3 桁の数値ステータスコード** を保持する項目。

例:
- `400`
- `401`
- `403`
- `404`
- `429`
- `500`

### 6.9 `detailReason`
外部 API / SDK が返す情報のうち、**`sdkCode` や `httpStatus` だけでは表せない補助的な詳細理由を示す短い文字列** を保持する項目。

以下を含めてよい。

- API / SDK レスポンス内の `reason` 相当
- API / SDK レスポンス内の `details` 相当から抽出できる短い理由ラベル
- エラー本文内に含まれる失敗原因を補足する短い識別的文字列

以下は含めない。

- エラーメッセージ全文
- stack trace
- 長文 explanation
- `sdkCode` と同じもの
- `httpStatus` と同じもの

## 7. エラー分類ルール

### 7.1 判定順

エラーは次の順で分類する。

1. 呼び出し側で個別 `errorKey` が明示されているか
2. 外部 API / SDK 由来のエラーか
3. それ以外か

### 7.2 分類結果

1. 個別 `errorKey` が明示されていれば `function_custom`
2. そうでなければ、外部 API / SDK 由来なら `external_api`
3. どちらでもなければ `function_common`

#### 補足（2026-04-10 改訂）
上記の **`errorSource` 分類**と別に、`logOpsError` は **`function_custom` に確定したあとも**、引数 `cause` に対して共通処理 `extractExternalFromCause` で取り込める場合、**同一 payload に** `sourceProduct` / `sdkCode` / `httpStatus` / `detailReason` を載せうる（**§8.4.1**）。これは **分類を `external_api` に変更するものではない**（業務キー `errorKey` と外部 SDK 材料の**併記**）。

### 7.3 外部API利用箇所の考え方

外部 API を使っている処理でも、発生しうるエラーは 3 種類ある。

#### `external_api`
例:
- Firestore が `NOT_FOUND`
- LINE API が `429`
- Storage が `PERMISSION_DENIED`

#### `function_common`
例:
- Firestore 取得後のデータ整形で `TypeError`
- API 呼び出し成功後にローカルロジックで `ReferenceError`

#### `function_custom`
例:
- Firestore 取得後に「既に会計開始済み」と判明し、業務上の明示エラーを投げる

したがって、**外部 API を使う処理は `external_api` / `function_common` / `function_custom` の全てがありうる。**

### 7.4 外部APIを使わない処理の考え方

外部 API を使わない処理では、以下のみがありうる。

- `function_common`
- `function_custom`

### 8.4 `function_custom` で追加する項目
- `errorKey`

### 8.4.1 `function_custom` における外部4項目の併記（本改訂・2026-04-10）

#### 目的
`errorKey` または `FunctionCustomError` により **`errorSource` が `function_custom` に固定される**ケースでも、失敗の直接原因が Firestore / Auth / Storage / LINE 等の **外部 API / SDK** であれば、モニタアプリ側で **SDK 起因の横断集計**ができるよう、**業務キーと同一ログ行に** `sourceProduct` / `sdkCode` / `httpStatus` / `detailReason` を残す。

#### 仕様（確定）
- **`errorSource` は `function_custom` のまま**とする。`external_api` に読み替えない。
- 外部4項目の有無・中身は、**`extractExternalFromCause(cause, sourceProductHint)` の戻り値**に基づく（**§9** の shape 方針と同じ抽出ロジック）。  
  - 「外部 SDK っぽいか」の**独立したブール判定は持たない**。戻り値が取り込み可能ならマージする。
  - 取れた**項目だけ** payload に含める（未取得は未設定。`null` で埋めない）。
- 呼び出し側が `logOpsError` 引数で **`sourceProduct` / `sdkCode` / `httpStatus` / `detailReason` を明示**している場合は、**明示値を優先**する（マージは **`??`**）。
- **`function_common` では**本併記を行わない（§8.3 補足どおり）。

#### 共通処理（実装方針）
- `logOpsError`（`functions/src/shared/logging/logOpsError.ts`）において、`errorSource` が **`external_api` または `function_custom`** のときに限り、上記マージおよび payload への4項目出力を行う。
- `resolveErrorSource` の判定順（明示 `errorSource` → `errorKey` / `FunctionCustomError` → 外部 shape → `function_common`）は**変更しない**。先に `function_custom` になった場合でも、続くマージで `cause` から外部材料を補う。

#### 呼び出し側の推奨
- catch 境界で **`cause` に元の SDK エラー**を渡す。併記の可否は `cause` の shape と `sourceProductHint` に依存する。

### 8.5 本改修における payload の主軸（既存項目＋追加項目）

モニタアプリ側の横断判定・集計の**主軸**とする項目は次のとおり。

- **`errorSource`**（本改修で必須追加）
- **`service`**（本改修で必須追加）
- **`functionEntry`**
- **`errorKey`**（`function_custom` のときのみ明示）
- **`errorName`**
- **`errorMessage`**
- **`sourceProduct`**（`external_api` のとき、または **`function_custom` かつ `cause` から抽出可能なとき**・取得分のみ）
- **`sdkCode`**（同上）
- **`httpStatus`**（同上）
- **`detailReason`**（同上）
- **`context`**
- **`operation`**（単一 `logOpsError` のみの `functionEntry` では任意・推奨。**同一 `functionEntry` で複数回ある場合は必須**。詳細は **§6.4.1**）
- **`projectId`**

### 8.6 `failureType`（過去互換・本改修の主項目ではない）

As-Is の実装では `failureType` が payload に含まれることがある。**仕様上は廃止方向**であり、**本改修の必須成果に「完全削除」は含めない**（§5.5）。新規設計では依存しない。後続の専用タスクで型・呼び出し・ログ出力から除去する。

## 9. `external_api` の判定材料方針

### 9.1 目的
外部 API / SDK が返すエラーについて、モニタアプリ側で後段判定できるだけの材料を残す。  
同一の抽出ロジックは、`errorSource = function_custom` のときの **外部4項目併記**（**§8.4.1**）にも用いる。

### 9.2 正式抽出対象項目
- `sourceProduct`
- `sdkCode`
- `httpStatus`
- `detailReason`

### 9.3 `sourceProduct` の集合値
- `firestore`
- `auth`
- `storage`
- `cloud_tasks`
- `line_api`

### 9.4 取得できない項目の扱い
- 取得できない項目は未設定でよい
- `null` を強制しない
- 固定文字列で雑に補完しない
- 長文レスポンスや機微情報は preview / truncate 方針を維持する
- **補足（実装・2026-04-08）**: 原則「message 単体では決めない」方針の**例外**として、Admin Storage の定型メッセージ判定と同様に、**Firestore クライアントの定型メッセージ**（例: `not a valid Firestore document`、`as a Firestore value`、`ignoreUndefinedProperties` を含む）から `sourceProduct: firestore` を付与する場合がある（`extractExternalFromCause` 内の `looksLikeFirestoreSdkClientMessage`）。

### 9.5 `sourceProduct` の責務分担
- `sourceProduct` の第一判定責務は共通処理が持つ
- 共通処理は `cause` の shape から判定可能な場合に `sourceProduct` を抽出する
- shape だけでは安全に判定できない場合は、呼び出し側が catch 境界の呼び出し文脈に基づいて補助的に指定できる
- 共通処理でも呼び出し側でも安全に判定できない場合は、`sourceProduct` は未設定でよい

### 9.6 `errorName` の扱い
- `errorName` は引き続き payload に載せる
- `external_api` では `sdkCode` や `httpStatus` と一部情報が重なる場合がある
- ただし `errorName` はエラーオブジェクトの型名、`sdkCode` は API / SDK の raw 識別子、`httpStatus` は HTTP 数値であり役割が異なる
- `external_api` では `errorName` は補助項目として扱う

## 10. `external_api` 判定ルール

### 10.1 目的

`errorSource = external_api` は、**外部 API / SDK / 外部サービスが返したエラー**を表す。  
本判定の目的は、Functions 側で重要度を決めることではなく、**モニタアプリ側で後段判定できるだけの材料を、外部起因エラーとして正しく保持すること**にある。

### 10.2 基本方針

`external_api` 判定は、**ログ文字列だけで推測しない**。  
以下の優先順で判定する。

1. **SDK / API エラーの構造（shape）を第一に見る**
2. shape だけでは足りない場合は、**catch の境界における呼び出し文脈**で補う
3. それでも外部起因と安全に言えない場合は、`external_api` に寄せず `function_common` とする

### 10.3 判定順

`errorSource` の全体判定順は以下とする。

1. 呼び出し側で `errorKey` が明示されている場合  
   → `function_custom`
2. `errorKey` がなく、外部 API / SDK 由来と判定できる場合  
   → `external_api`
3. 上記のいずれにも該当しない場合  
   → `function_common`

本節では 2 の判定ルールを定める。

### 10.4 `external_api` と判定するための根拠

以下のいずれかを満たす場合、`external_api` と判定してよい。

#### 10.4.1 shape から強い根拠が取れる場合

以下のような、外部 API / SDK 由来と判断しやすい情報が `cause` から取得できる場合は `external_api` とする。

- `response.status` がある
- `httpStatus` 相当がある
- `reason` 相当がある
- `domain` 相当がある
- SDK 固有 code がある
- Firestore / Auth / Storage / LINE API / Cloud Tasks 等の **典型的な error shape** を持つ
- `sourceProduct` をほぼ一意に特定できる

#### 10.4.2 shape だけでは弱いが、複数の根拠を組み合わせられる場合

単独では弱いが、複数組み合わせると外部起因と判断できる場合は `external_api` とする。

例:
- `code` + `details`
- `code` + SDK 由来と分かる stack / name
- `status` + response body
- `message` + 明確な SDK / API shape

### 10.5 「足りない」とみなす条件

以下のような場合は、**shape だけでは external_api 判定に必要な情報が足りない**とみなす。

#### 10.5.1 情報が落ちている・型が消えている

例:
- `catch (e) { throw new Error(String(e)) }`
- `catch (e) { throw new Error('失敗') }`

このように、元のエラーが持っていた
- `code`
- `status`
- `reason`
- `domain`
- SDK 固有 shape

などが失われると、外部起因かどうかを自動判定しづらくなる。

#### 10.5.2 複数の外部 API が同じ try に入っている

1つの `try` の中で複数の外部呼び出しを行い、最後にまとめて `catch` している場合、  
shape が弱いと **どの API 由来か一意に決めにくい**。

例:
- Firestore 読み取り
- Cloud Tasks enqueue
- HTTP API 呼び出し

を同一 `try` に入れている場合など。

#### 10.5.3 文字列しか残っていない

最終的に `errorMessage` しか残らず、

- `errorName`
- `code`
- `httpStatus`
- `details`
- `reason`
- `domain`

などがない場合は、`sourceProduct` を安全に決めにくい。

例:
- `Network error`
- `Request failed`
- `失敗しました`

のような、複数プロダクトで似た文言になりうるケース。

#### 10.5.4 一意に解釈できない

`code` や `status` があっても、それだけでは複数プロダクトにまたがる共通表現であり、  
**どの外部 API 由来か安全に特定できない**場合は「足りない」とみなす。

例:
- `NOT_FOUND`
- `INTERNAL`
- `UNAVAILABLE`

など、共通コード寄りの表現だけが見えているケース。

### 10.6 「足りない」場合の補い方

shape だけで判定しきれない場合は、**catch の境界における呼び出し文脈**で補う。

#### 10.6.1 呼び出し文脈の意味

ここでいう呼び出し文脈とは、**そのエラーが起きた地点の前後で、どの外部 API を呼んでいたか**を指す。  
関数全体でどの API を使うかではなく、**当該 `try/catch` がどの外部呼び出しを囲っているか**を重視する。

#### 10.6.2 catch 境界で明示してよいケース

以下のように、`catch` が単一の外部 API 呼び出しを実質的に囲っている場合は、そこで `sourceProduct` を明示してよい。

例:
- Firestore 読み取り専用の `try/catch`
- LINE push 送信専用の `try/catch`
- Cloud Tasks enqueue 専用の `try/catch`

この場合、shape が弱くても、catch 境界の意味から `sourceProduct` を安全に補える。

#### 10.6.3 補い方の原則

- `sourceProduct` を明示する
- 必要に応じて `operation` などで呼び出し位置も残す
- ただし、関数全体が複数 API を呼ぶからという理由だけで雑に外部起因へ寄せない

### 10.7 `external_api` に誤分類してはいけないケース

以下は `external_api` に見えやすいが、実際には `function_common` とすべき典型例である。

#### 10.7.1 外部 API 呼び出し後のローカル処理失敗

外部 API 自体は成功しているが、そのレスポンスを加工する処理で失敗している場合は `function_common` とする。

例:
- Firestore 読み取り成功後に `TypeError`
- LINE API レスポンス受領後に自前変換処理で `ReferenceError`

この場合、外部 API 判定材料は不要であり、むしろ `external_api` に寄せないことを優先する。

### 10.8 実装上の原則

#### 10.8.1 推奨
- SDK / API の元エラーをできるだけ潰さない
- `cause` を保持する
- 外部呼び出しごとに `try/catch` を細かく分けられる箇所は分ける
- shape から取れない場合のみ、catch の境界で `sourceProduct` を補う

#### 10.8.2 非推奨
- `message` 文字列だけで `external_api` 判定する
- `code` だけで `external_api` 判定する
- 関数名だけで `external_api` 判定する
- 元エラーの構造を捨てて再 throw する

### 10.9 まとめ

`external_api` 判定における「足りない」とは、  
**外部 API / SDK が本来持つ識別情報（例: `code`, `status`, `reason`, `domain`, SDK 固有 shape）が、ログ時点の `cause` から取得できない、または複数候補にまたがって一意に解釈できない状態**を指す。

その場合は、以下で補う。

- `cause` を潰さない
- 外部呼び出しごとに `try/catch` を分ける
- catch の境界で `sourceProduct` を明示する

それでも安全に外部起因と判断できない場合は、`external_api` に寄せず `function_common` とする。

## 11. `function_common` の扱い

### 11.1 目的
関数内で起きた未個別定義エラーを、少なくとも共通の枠で観測できるようにする。

### 11.2 想定対象
- `TypeError`
- `ReferenceError`
- `RangeError`
- 想定外の `Error`
- その他 runtime / 実装系エラー

### 11.3 残すべき情報
- `errorName`
- `errorMessage`
- `functionEntry`
- `service`
- `operation`

### 11.4 方針
- `function_common` には個別 `errorKey` を付けない
- `sourceProduct` / `sdkCode` / `httpStatus` / `detailReason` は `external_api` 専用項目とし、`function_common` には原則入れない
- `stackPreview` は本改修では導入しない
- runtime error の種類やメッセージが後段判定材料になる

## 12. `function_custom` の扱い

### 12.1 目的
業務上の意味が強く、共通材料だけでは扱いが不十分なものに対して、明示的なラベルを与える。

### 12.2 `errorKey` の原則
- `function_custom` のときのみ付与する
- 業務上の意味がある名前にする
- `functionEntry` をそのまま埋め込むことを原則としない
- 再利用可能性と運用上の分かりやすさを優先する
- **1キー = 1意味** を原則とする
- **曖昧な OR 統合は行わない**
- **見た瞬間に何が起きたか一意に分かる命名**を優先する
- `REJECTED` は使用しない
- `BUSINESS_ERROR` は使用しない
- `INVALID_STATE` は使用可とする
- ただし `INVALID_STATE` は無制限に使わず、**対象箇所を絞って採用する**

### 12.3 実装入口
`function_custom` の実装入口は、**専用エラー型を用いる方式** とする。  
業務上意味のある個別エラーは、専用エラー型を throw して表現し、当該エラー型は少なくとも `errorKey` と `message` を持つものとする。必要に応じて `context` も保持できるようにする。  
catch 側では、この専用エラー型を検知した場合に `errorSource = function_custom` として扱い、`errorKey` を `logOpsError` に渡す。

### 12.4 `function_custom` にする基準候補
以下のいずれかに当てはまる場合を優先対象とする。

- 標準材料だけでは意味が足りない
- 事業影響が大きい
- 発生時に見逃したくない
- 恒久失敗になりやすい
- 運用上の扱いを事前に決めたい
- **そのうえで、よく行われる業務に属する**

補足:
- 対象選定は「分類の美しさ」より **運用価値優先** とする
- 同じく重要でも、発生頻度が低く事後救済しやすいものは後順位になりうる

### 12.5 例
- `ACCOUNTING_ALREADY_STARTED`
- `ACCOUNTING_INVALID_STATE`
- `STORE_ALREADY_OPEN`
- `STORE_CLOSE_BLOCKED`
- `TOURNAMENT_ALREADY_ENDED`
- `TOURNAMENT_SCHEDULE_AMBIGUOUS`

※ `REJECTED` や `BUSINESS_ERROR` のような曖昧語は使わない。  
※ 具体一覧は本書の後半で今回の対象と一覧を確定する。

### 12.6 専用エラー型の shape
`function_custom` の専用エラー型は `FunctionCustomError` とし、`Error` を継承する。

- 必須フィールド:
  - `errorKey`
  - `message`
- 任意フィールド:
  - `context`
  - `cause`

`context` の型は `Record<string, unknown>` とする。

`errorSource` / `service` / `functionEntry` / `operation` などのログ文脈情報は専用エラー型に持たせず、共通処理側で付与する。

catch 側では `instanceof FunctionCustomError` をもって `function_custom` と判定し、`errorKey` と `message` と `context` を payload に反映する。

### 12.7 custom 対象箇所の実装方式
custom 対象箇所の実装方式は、原則として `FunctionCustomError` を throw する方式に統一する。

custom 対象箇所に既存の `HttpsError` がある場合は、**custom に載せる業務エラーとして確定した箇所に限って** `FunctionCustomError` に置き換える。  
これは、想定内の `HttpsError` 全体を廃止する意味ではない。  
`unauthenticated`、`invalid-argument`、`permission-denied` などの想定内 `HttpsError` は従来どおり維持する。

既存の `return { success: false, ... }` を返す関数については、API 契約を維持するため、今回は throw ベースの custom 実装対象には含めない。  
戻り値で表現しているビジネス結果はこのフェーズでは変更しない。

`FunctionCustomError` はドメイン / サーバ内での業務エラー表現とし、callable / trigger / 上位 catch 側で `instanceof FunctionCustomError` を検知して `logOpsError` に `errorSource = function_custom` と `errorKey` を載せる。  
クライアント向けには、必要に応じて適切な `HttpsError` に変換して返す。

## 13. `service` の扱い

### 13.1 目的
`service` は、Functions 側で重要度補正するためではなく、以下のために持たせる。

- モニタアプリ側での絞り込み
- 同一業務領域の横断比較
- `functionEntry` より粗い単位での集計

### 13.2 今回の扱い
- 各 `functionEntry` に対し `service` を対応付ける
- Functions 側では `service` を出力するまで
- `service` 一覧は現状維持とする
- `functionEntry -> service` 対応表も現状維持とする
- `service` を用いた重要度補正は今回行わない

## 14. `logOpsError` 拡張方針

### 14.1 追加可能にする概念
`logOpsError` は少なくとも次を受けられる形にする。

- `errorSource`
- `service`
- `errorKey`（任意。`function_custom` のみ）
- `sourceProduct`
- `sdkCode`
- `httpStatus`
- `detailReason`

本改修で **主軸として扱う payload 直下の項目** は **§8.5** に定めるとおりである。  
`logOpsError` は、`functionEntry`、`operation`、`projectId`、`errorMessage`、`errorName`、`errorSource`、`service`、`context`、`errorKey`、`sourceProduct`、`sdkCode`、`httpStatus`、`detailReason` を payload 直下に載せられるよう拡張する（**`failureType` はこの主一覧には含めない**）。

ただし、`function_custom` 以外では `errorKey` は未設定でよい。  
また、`external_api` 以外では `sourceProduct`、`sdkCode`、`httpStatus`、`detailReason` は原則未設定でよい。**例外として `function_custom` で `cause` が外部 SDK 形のときは、抽出できた分のみ設定する**（§8.3 補足）。

`external_api` においても、`sourceProduct`、`sdkCode`、`httpStatus`、`detailReason` は常に全て必須ではなく、取得できた項目のみを設定し、取得できない項目は未設定でよい。

**`failureType`（過去互換・本改修の設計対象外）**  
As-Is では `failureType` が payload に含まれることがある。**互換目的で残存しうる項目**であり、本改修における **追加・必須化・主軸への組み込みの対象ではない**（§5.5・§8.6）。新規追加・新規参照は行わない。

### 14.2 基本方針
- 既存の `logOpsError` を中核にする
- 新しいログ関数は増やさない
- 既存の 1 エラー = 1 `logger.error` 方針を維持する
- 既存 payload の意味を壊さない

### 14.3 payload 直下と `context` の境界
`payload` 直下には、後段で横断検索・集計・分類軸として扱う共通項目のみを置く。

具体的には、**§8.5 の主軸**に沿い、`functionEntry`、`operation`、`projectId`、`errorMessage`、`errorName`、`errorSource`、`service`、`errorKey`、`sourceProduct`、`sdkCode`、`httpStatus`、`detailReason`、`context` を payload 直下に置く（**`failureType` は過去互換であり主軸ではない**。§8.6）。

`context` には、当該分岐や業務条件を説明する補助情報を置く。  
具体的には、`reason`、`phase`、`currentStatus`、`allowedStatuses`、`billStatus`、各種比較値、関連ID、選択値などを格納する。

`reason` や `phase` のような補助分類は、今回独立した共通項目には昇格させず、`context.reason`、`context.phase` として扱う。  
新しい共通項目を payload 直下へ追加する場合は、横断集計軸として本当に必要な場合に限る。

## 15. 共通処理と呼び出し側の責務分担

### 15.1 基本方針
分類と抽出の主担当は共通処理とし、**共通処理が `errorSource` の最終判定責務を持つ**。呼び出し側は業務文脈と限定的な補助指定だけを担う。

### 15.2 `function_custom` の責務分担
`function_custom` は専用エラー型を throw して表現し、共通処理がそれを解釈して `errorSource` / `errorKey` / `errorMessage` / `context` を payload に変換する。  
`logOpsError` に **`cause` が渡され、外部 API / SDK の shape として取り込める場合**は、`external_api` と同様に `sourceProduct` / `sdkCode` / `httpStatus` / `detailReason` を抽出して併記する（§8.3 補足）。

### 15.3 `external_api` の責務分担
`external_api` は共通処理が shape を第一に判定し、`sourceProduct` / `sdkCode` / `httpStatus` / `detailReason` を抽出する。shape だけで足りない場合に限り、呼び出し側は単一 API 専用 catch において **`sourceProduct` のみ** を補助指定できる。

### 15.4 `function_common` へのフォールバック
上記のいずれにも当てはまらない場合は、共通処理が `function_common` にフォールバックする。

### 15.5 呼び出し側が担うもの
呼び出し側は、少なくとも以下を担う。

- `function_custom` とすべき業務条件の判定
- 専用エラー型の throw
- `operation` の指定
- 個別の `context` の付与
- 単一 API 専用 catch における `sourceProduct` の補助指定

### 15.6 共通処理が担うもの
共通処理は、少なくとも以下を担う。

- `errorSource` の最終判定
- 専用エラー型の解釈
- `external_api` の shape 判定
- `sourceProduct` の一次判定
- `sdkCode` / `httpStatus` / `detailReason` の抽出
- `function_common` へのフォールバック
- 専用エラー型から payload への変換

## 16. `function_custom` 対象選定方針

### 16.1 基本方針
全関数に個別 `errorKey` を入れない。  
個別指定するのは、限定した重要箇所のみとする。

### 16.2 優先対象
- 標準材料だけでは意味が足りない
- 事業影響が大きい
- 発生時に見逃したくない
- 恒久失敗になりやすい
- 運用上の扱いを事前に決めたい
- よく行われる業務である

補足:
- 優先順位は、抽象的な分類の整合性よりも **実運用での検知価値** を優先して決める
- 発生頻度が高く、業務停止や現場オペレーションに直結するものを優先する

### 16.3 対象外
以下は `function_custom` の対象外とする。

- 単なる想定外エラー
- runtime error
- 外部 API / SDK 起因エラー
- デモ・運用診断・一度きり系の処理
- `function_common` / `external_api` と境界が揺れやすいもの
- 単純 not-found で業務上の意味づけが弱いもの
- 認証 / 権限エラー
- 入力バリデーション（`invalid-argument` 相当）
- 外部 API 失敗後の一般的なラップ例外
- バグ・不整合色が強く、業務状態より実装不備の色が強いもの

それぞれ `function_common` または `external_api` として扱う。

### 16.4 実装方法候補
- まず対象業務群を決める
- 対象業務群の中で、対象関数・対象条件を選定する
- 対象箇所でのみ専用エラー型を throw する
- それ以外は `external_api` / `function_common` の共通処理に流す
- 対応箇所は **関数単位ではなく、条件分岐 / throw / return(success:false) 単位** で定義する
- 同じ意味のものは、関数ごとに別 key を増やさず **正式 errorKey に統合** する

### 16.5 今回の対象業務群
今回 `function_custom` の実装対象とする業務群は以下とする。

- 会計
- 店舗開閉
- トーナメント
- **来店処理**（2026-04-10 追記。`service` は `functionEntry_service_対応表` に従い **`user`**。QR 起点の入店・手動チェックイン・入店状態取得・QR 検証、および LIFF 経由のカスタムトークン発行の **例外時 `logOpsError` に `errorKey` を明示**する範囲）

補足:
- 給与・支払・勤怠・シフト等は今回の対象外とする
- 当初の整理では会計 / 店舗開閉 / トーナメントの 3 群が主だったが、**来店処理（user）を後追いで対象に追加**した

- `IDEMPOTENCY_REQUEST_HASH_MISMATCH` 系は `ACCOUNTING_IDEMPOTENCY_MISMATCH` に統合する

- `EVENT_BUSINESS_DATE_NONE` / `EVENT_BUSINESS_DATE_AMBIGUOUS_UNRESOLVED` は `ACCOUNTING_BUSINESS_DATE_UNRESOLVED` に統合する
- `NONE` / `AMBIGUOUS` の差分は key ではなく `context.reason` で持つ
- 負値化・過剰返金等のサマリ不整合は `ACCOUNTING_NEGATIVE_TOTALS` に統合する
- active stay 競合は `ACCOUNTING_ACTIVE_STAY_CONFLICT` に統合する

#### 店舗開閉
- `STORE_CLOSE_INVALID_STATE` / `STORE_OPEN_TERMINAL_PRECONDITION_NOT_MET` は `STORE_INVALID_STATE` に統合する
- `runId` 不一致は独立 key を作らず、まずは `STORE_PROCESSING_LEASE_CONFLICT` に寄せる
- `processing.kind !== kind` は `STORE_PROCESSING_KIND_MISMATCH` に統合する
- `doc.exists` だが `data` が空のケースは `STORE_INVALID_STATE` とする

#### トーナメント
- `TOURNAMENT_PAUSE_INVALID_*` / `TOURNAMENT_RESUME_INVALID_*` は `TOURNAMENT_INVALID_STATE` に統合する
- `TOURNAMENT_END_VALIDATION_RANKING_EMPTY` と `...RANKING_INCOMPLETE` は `TOURNAMENT_RANKING_INCOMPLETE` に統合する
- cancel / restore / reschedule / archived immutability 系の細分化は `TOURNAMENT_SCHEDULE_INVALID_STATUS_TRANSITION` に統合する
- `NONE` と `AMBIGUOUS` は schedule 系では分けて残す

### 16.8 対応箇所の定義単位
対応箇所は、Cloud Functions や repo / service の **関数単位** ではなく、以下の **実装箇所単位** で定義する。

- 1つの条件分岐 (`if`, `switch`, guard)
- 1つの `throw`
- 1つの `return { success: false, ... }`

つまり、1行 = 1箇所 を原則とする。  
同一関数内に複数の業務状態エラーがある場合は、それぞれ別の対応箇所として扱う。

補足:
- 「`startAccounting` 全体に `ACCOUNTING_ALREADY_STARTED` を付ける」のではなく、
  「`startAccounting.ts` 内の `billData.ops?.accountingStartedAt` 判定箇所に `ACCOUNTING_ALREADY_STARTED` を割り当てる」
  という粒度で定義する。

## 19. 検証観点

### 19.1 ログ項目（主軸）
- `errorSource` が正しく載る
- `service` が正しく載る
- `function_custom` でのみ `errorKey` が載る
- `external_api` で `sourceProduct` / `sdkCode` / `httpStatus` / `detailReason` など必要な材料が載る（取得分のみで可）
- `function_custom` でも **`cause` が外部 SDK 形**なら上記4項目が取れた分だけ載る（`errorKey` と併記）
- `function_common` で最低限の runtime error 情報（`errorName` / `errorMessage` 等）が載る
- `context` のネスト方針が仕様どおりである

### 19.2 既存基盤・挙動への影響
- `functionEntry` が意図せず欠落・改変されていない
- `projectId`, `errorMessage`, `errorName`, `context` が維持される
- ERROR 行数が意図せず増えない（**二重ログなし**）
- preview / truncate 方針が壊れない
- **`FunctionCustomError` の境界での `logOpsError` → `HttpsError` 変換**が仕様どおりである

### 19.3 運用
- Cloud Logging 上で `errorSource`, `service`, `functionEntry` でフィルタできる
- `function_custom` のみを簡単に抽出できる
- `external_api` と `function_common` を後段判定用に集計できる

※ **`failureType` の「維持確認」は検証主軸としない**（廃止方向・後続専用タスクで除去。§5.5）。

## 21. 備考

- 本仕様は **差分実装仕様** であり、既存ログ共通化基盤の全面再定義ではない
- 本仕様の主眼は **Functions 側での重要度判定ではなく、モニタアプリ側で判定可能な材料の保持** にある
- **重要度判定要件のスコープ**: 実装サマリにおける **業務本体 280 件**（`logOpsError` 機械集計から `debug` / `unused_function_lib` を除いた件数）のうち、`generateDummyData` / `debugSideGame` は **テスト・開発・検証用**であり、`エラーログ_重要度判定要件定義.md` **§4** に従い **十分性評価の主対象**は **269 件**（旧 278 件から `unused_function_lib` へ移管した 9 呼び出し分を除く）とする。上記は **tenant-errors に載るログの有無や、本書の `logOpsError` 共通化の対象範囲を狭めるものではない**。
- `errorKey` は全エラーの主軸ではなく、**`function_custom` に限定して使う**
- `external_api` / `function_common` は、こちらで共通キーを運用するのではなく、取得したエラー情報を後段判定に渡す
- `external_api` では、正規化済みの共通分類コードよりも、外部 API / SDK が返す raw な識別情報の保持を優先する
- 将来的に共通分類キーや基本重要度を導入する余地はあるが、本段階では扱わない
- `function_custom` の対象選定では、事業影響・見逃したくなさ・業務頻度を重視する
- `errorKey` の命名は `1キー = 1意味` を原則とし、曖昧な OR 統合は行わない
- `REJECTED` / `BUSINESS_ERROR` は使用しない
- `INVALID_STATE` は使用可とするが、対象箇所を絞って採用する
- 今回の `function_custom` 実装対象業務群は、会計 / 店舗開閉 / トーナメントに加え、**来店処理（user）**を含む（§16.5）
- 対応箇所は関数単位ではなく、条件分岐 / throw / return(success:false) 単位で定義する
- 専用エラー型は `FunctionCustomError` とし、サーバ内・ドメイン内の業務エラー表現として使う
- custom 対象箇所の既存 `HttpsError` は、custom に載せる業務エラーとして確定した箇所に限って置換する
- 想定内の `HttpsError`（`unauthenticated` / `invalid-argument` / `permission-denied` 等）は従来どおり維持する
- 既存の `return { success: false, ... }` 契約を持つ関数は、今回の throw ベース custom 実装対象には含めない
- `ACCOUNTING_ACTIVE_STAY_CONFLICT` と `STORE_PROCESSING_KIND_MISMATCH` は、`INVALID_STATE` から独立させた key として扱う
- `logOpsError` 追加候補 catch の一次抽出・二次確認は完了済みであり、今後は追加対象 / 条件付き追加対象 / 保留対象の最終確定に進む
- **`failureType`** は仕様上は廃止方向とし、**本改修の主軸ではない**。コードからの完全削除は **後続の専用タスク**（§5.5・§18-14）
- **`function_custom` と外部4項目の関係**: モニタアプリや集計クエリで「`sourceProduct` 等が付いている ⇒ 必ず `external_api`」と**決め打ちしない**こと。`function_custom` でも `cause` から抽出できた分が載る（**§8.4.1**）。
