# Bills Migration 手動テスト項目

_最終更新: 2025-12-05 (JST)_

## 概要

本ドキュメントは、Bills Migration プロジェクト（P1-01〜P1-10）の実装内容について、手動で確認すべきテスト項目を優先度別に整理したものです。

各テスト項目は以下の4つの優先度に分類されています：
- **必須**: 本番リリース前に必ず確認すべき項目
- **優先度高**: 重要な機能の動作確認項目
- **優先度中**: 通常の運用で確認すべき項目
- **優先度低**: 時間がある場合に確認すべき項目

## テスト環境の準備

### 前提条件
- Firestore Emulator または本番環境が利用可能であること
- Flutter アプリがビルド・実行可能であること
- 管理者権限を持つユーザーでログインしていること

### テストデータの準備
- テスト用のユーザーアカウントを複数作成
- テスト用のメニューアイテムを登録（Chipカテゴリを含む）
- テスト用のトーナメントテンプレートを作成

## P1-01: 入店フロー

### 必須

#### M-01-01: 手動チェックイン（manualCheckIn）
- **確認場所**: `lib/UserLogin/UserManualCheckInPage.dart`
- **操作手順**:
  1. アプリを起動し、「手動チェックイン」ボタンをタップ
  2. ログインIDとPINを入力
  3. 「ログイン」ボタンをタップ
- **確認内容**:
  - `/bills/{billId}` ドキュメントが作成されること
  - `businessDate` がサーバ側で正しく設定されること（クライアント送信値は無視される）
  - `status` が `'open'` であること
  - `/activeStays/{uid}` ドキュメントが作成されること
  - `activeStays` の `isActive` が `true` であること
  - 入店料がある場合、`/bills/{billId}/extras/{extraId}` に追加されること
  - 同一 `idempotencyKey` で再実行した場合、既存docが返却され、`updatedAt` が変更されないこと
- **確認方法**: Firestore Console で `/bills/{billId}` と `/activeStays/{uid}` を確認

#### M-01-02: QRチェックイン（processVisitByQR）
- **確認場所**: `lib/UserRegisterView/userQRCheckInPage.dart`
- **操作手順**:
  1. アプリを起動し、「QRチェックイン」ボタンをタップ
  2. QRコードをスキャン
- **確認内容**:
  - M-01-01 と同様の確認項目
  - QRコード読み取りが正常に動作すること
- **確認方法**: Firestore Console で確認

#### M-01-03: 重複入店チェック
- **確認場所**: `lib/UserLogin/UserManualCheckInPage.dart`
- **操作手順**:
  1. ユーザーAで手動チェックインを実行
  2. 同じユーザーAで再度手動チェックインを実行
- **確認内容**:
  - `failed-precondition` エラーが返されること
  - エラーメッセージが適切に表示されること
- **確認方法**: アプリのエラーメッセージを確認

### 優先度高

#### H-01-01: デュアルライト動作確認（WRITE_TODAYS_BILLS_IN_PARALLEL=true）
- **確認場所**: 手動チェックイン実行後
- **操作手順**:
  1. 環境変数 `WRITE_TODAYS_BILLS_IN_PARALLEL=true` を設定
  2. 手動チェックインを実行
- **確認内容**:

- **確認方法**: Firestore Console で `/todaysBills/{billId}` を確認

## 矛盾点の指摘

### 確認結果

以下のドキュメントを確認した結果、以下の矛盾点が発見されました：

1. **bills.onSettle の発火条件について（P1-10）**
   - **矛盾点**: 
     - `trigger_plan.md` §1.1 では「`before.status == 'settling' && after.status == 'settled'`」と記載されている
     - 実装（`functions/src/triggers/bills.onSettle.ts` 46行目）では「`before.status !== 'settled' && after.status === 'settled'`」となっている
     - P1-10 ChangeSpec では「`before.status !== 'settled' && after.status === 'settled'`」と記載されている
   - **影響**: 
     - `open -> settled` 遷移でも発火するため、会計開始フロー（`startAccounting`）をスキップしてスナップショット確定できてしまう可能性がある
     - `README.md` の「危険点（要判断・要修正候補）」セクションでも指摘されている
   - **テスト観点への影響**: 
     - M-10-01 のテスト観点に「`open -> settled` 遷移でも発火することを確認」を追加する必要がある（または仕様を確定してからテスト観点を修正）
     - 仕様が「`settling` 経由のみ」に確定した場合は、テスト観点を「`settling -> settled` 遷移でのみ発火することを確認」に修正する必要がある

2. **businessDate の扱いについて**
   - **矛盾点**: 
     - `schema_plan.md` では「Functions が `calcBusinessDate` で確定」と記載されている
     - `modification_plan.md` P1-02.1 では「businessDate不変化テストは一時スキップ（P1-06/P1-11へ移管）」と記載されている
   - **影響**: 
     - businessDate の不変性テストが未実施の可能性がある
     - P1-06 で `updateBill` ヘルパAPIの `businessDate` 変更拒否（パターンA）は実装済みだが、P1-11 でトリガによる巻き戻し（パターンB）のテストが必要
   - **テスト観点への影響**: 
     - H-06-01 のテスト観点で businessDate 変更拒否（パターンA）を確認しているが、P1-11 で追加のテスト（パターンB）が必要な可能性がある
     - 現時点では P1-11 が未着手のため、パターンB のテストは実施できない

3. **`/payments` サブコレクションの扱いについて**
   - **矛盾点**: 
     - P1-10 ChangeSpec では「`/payments` サブコレクションの扱い: 方針B（存在する場合のみ読む、存在しない場合は `meta.paymentMethodsByCategory` から算出にフォールバック）を採用」と記載されている
     - `schema_plan.md` では「`/payments` は Functions のみが作成（クライアント直書き禁止）」と記載されている
     - 実装確認結果: `grep` により `/bills/{billId}/payments` を作成する経路は存在しない（`functions/src` 内で `payments` サブコレクションへの書き込み処理が見つからない）
   - **影響**: 
     - 現時点では `/payments` を作成する経路が存在しないため、常に `meta.paymentMethodsByCategory` から算出される
     - 将来 `recordPayment` が導入された場合に `/payments` が優先される設計になっている
   - **テスト観点への影響**: 
     - H-10-02 のテスト観点は現時点では実施できない（将来 `recordPayment` が導入された場合に実施）
     - 現時点では `/payments` が存在しない前提でテストを実施する必要がある

4. **`activeStays` の最小スキーマ化について**
   - **矛盾点**: 
     - `schema_plan.md` では「`activeStays` は最小スキーマ（`uid`, `billId`, `pokerName?`, `isActive`, `startedAt` のみ）」と記載されている
     - `schema_finalization_summary.md` では「`table`, `seat`, `updatedAt`, `expiresAt` (TTL) を削除」と記載されている

   - **テスト観点への影響**:
