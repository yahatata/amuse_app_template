## 変更概要（What）

- **小パッチ（ordersキーをbill.businessDateに統一・SSoT）**:
  - `functions/src/itemOrder/placeOrder.ts`: ordersキー生成ロジックを `billData.businessDate` を唯一のソースに変更（`calcBusinessDate()` は使用しない）
  - `functions/src/itemOrder/placeOrderByUser.ts`: 同様にordersキー生成ロジックを `billData.businessDate` ベースに変更

- **結合テストの追加（4カテゴリ）**:
  - `__tests__/itemOrder/placeOrder.businessDate.spec.ts`: businessDate境界テスト（STORE_CLOSE_HOUR=27/9）
  - `__tests__/helpers/billsApi/appendItem.dualwrite-failure.spec.ts`: DualWrite失敗耐性テスト
  - `__tests__/helpers/billsApi/appendItem.concurrent.spec.ts`: 並行競合テスト（allowed同士/途中settling化）
  - `__tests__/helpers/billsApi/appendItem.mismatch.spec.ts`: appendの内容不一致リプレイテスト

- **既存コードの軽微修正（DualWriteログ三分岐）**:
  - `functions/src/helpers/billsApi/appendItem.ts`: DualWrite処理の分岐ごとに構造化ログに `dualWriteResult: 'failed'|'success'|'skipped'` を明示（成功時・失敗時・スキップ時すべてに対応）

## 実装詳細（How）

### 書込み先（billsサブコレ）

- 既存どおり（不変）:
  - `/bills/{billId}/items/{itemId}`: アイテム追加
  - `/bills/{billId}/idempotency/{key}`: 冪等性記録
  - `/orders/{YYYYMMDD}/_TodaysOrders/{itemId}`: 注文記録
  - **変更点**: `orders` のキー `{YYYYMMDD}` を **`billData.businessDate`（SSoT）を唯一のソースにする**（`calcBusinessDate(new Date())` は使用しない）

### 冪等性（方式・キー・保存先）

- 既存どおり（不変）:
  - `itemId = idempotencyKey`（docID が冪等キー）
  - `/bills/{billId}/idempotency/{key}` に `requestHash` 保存
  - リプレイ時は `requestHash` 一致チェック → 不一致なら `failed-precondition`
  - **新規テスト**: 同一 `idempotencyKey` で `quantity` などを変更した再送は `failed-precondition` を検証

### デュアルライト（最小複写内容）

- 既存どおり（不変）:
  - `WRITE_TODAYS_BILLS_IN_PARALLEL` フラグON時のみ `todaysBills/{billId}` に複写
  - 失敗はログのみで `bills` 成功を維持
  - **変更点**: DualWrite処理の分岐ごとに構造化ログに `dualWriteResult` を必ず出力:
    - 成功時: `logger.info('dualWrite appendItem ok', { op: 'appendItem', billId, itemId, dualWriteResult: 'success' })`
    - 失敗時: `logger.warn('dualWrite appendItem failed', { op: 'appendItem', billId, itemId, dualWriteResult: 'failed', reason })`
    - スキップ時（フラグOFF）: `logger.info('dualWrite appendItem skipped', { op: 'appendItem', billId, itemId, dualWriteResult: 'skipped' })`
  - **新規テスト**: DualWrite失敗時の `bills/items` 成功・`orders` 正動作を検証、スキップ時のログ検証を追加

### 権限境界（Functions/Client）

- 既存どおり（不変）:
  - `placeOrder`: クライアント認証不要（スタッフ画面）
  - `placeOrderByUser`: クライアント認証必須（LIFFユーザー）
  - `/bills/{billId}/items` は Functions 経由のみ書込（クライアント直書き禁止）

### 競合解決（LWW or なし）

- 既存どおり（不変）:
  - `appendItem` はトランザクション内で実行
  - 並行実行時の競合は Firestore トランザクションの再試行で解決
  - **新規テスト**: 
    - `status=open` での並行 `appendItem` は両方成功
    - `appendItem` 中に別Txで `status='settling'` に遷移した場合、遅い方は `failed-precondition`

### ログ/メトリクス（出力フィールド）

- **変更点**: 
  - `appendItem` の DualWrite処理で構造化ログに `dualWriteResult` を追加:
    - 成功時: `dualWriteResult: 'success'`
    - 失敗時: `dualWriteResult: 'failed'`（既存の warn ログと併記）
    - スキップ時（フラグOFF）: `dualWriteResult: 'skipped'`
  - ログ出力: `{ op: 'appendItem', billId, itemId, idempKey, dualWriteResult, result, requestHash8 }`

### 例外（HttpsErrorマッピング）

- 既存どおり（不変）:
  - `invalid-argument`: 入力バリデーション失敗
  - `failed-precondition`: `status` ガード違反、`requestHash` 不一致、並行競合時の `status='settling'` 検出
  - `not-found`: `billId` または `activeStays` が見つからない
  - `permission-denied`: `placeOrderByUser` で認証なし

## 仕様差分（Before→After）

### ordersキーの生成方法

**Before**:
```typescript
const now = new Date();
const yyyy = String(now.getFullYear());
const mm = String(now.getMonth() + 1).padStart(2, "0");
const dd = String(now.getDate()).padStart(2, "0");
const orderDocId = `${yyyy}${mm}${dd}`;  // システム日付（UTC/JST混在の可能性）
const dateString = `${yyyy}-${mm}-${dd}`;
```

**After**:
```typescript
// calcBusinessDate は使用しない（SSoTは bill.businessDate）
const { billId, billData } = await getActiveBillByUser(userId);
const biz = billData.businessDate as string;  // "2025-11-15" (SSoT)
const orderDocId = biz.replace(/-/g, "");     // "20251115"
const dateString = biz;                       // "2025-11-15"
```

**効果**:
- `orders/{YYYYMMDD}` のキーは **常に `bills/{billId}.businessDate` に一致**（SSoT原則）
- `orders/{YYYYMMDD}.date` フィールドも `bills.businessDate` と一致
- `calcBusinessDate(new Date())` を使わないことで、システム日付とbillのbusinessDateの不一致を防止

### DualWrite失敗時のログ

**Before**:
```typescript
catch (error: any) {
  logger.warn('dualWrite appendItem failed', {
    billId,
    itemId,
    reason: error?.message || String(error),
  });
}
```

**After**:
```typescript
// 成功時
if (shouldDualWrite() && legacyRef && legacySnap && legacySnap.exists) {
  try {
    // ... DualWrite処理 ...
    logger.info('dualWrite appendItem ok', {
      op: 'appendItem',
      billId,
      itemId,
      dualWriteResult: 'success',
    });
  } catch (error: any) {
    logger.warn('dualWrite appendItem failed', {
      op: 'appendItem',
      billId,
      itemId,
      dualWriteResult: 'failed',  // 追加
      reason: error?.message || String(error),
    });
  }
} else if (!shouldDualWrite()) {
  logger.info('dualWrite appendItem skipped', {
    op: 'appendItem',
    billId,
    itemId,
    dualWriteResult: 'skipped',  // 追加
  });
}
```

### その他

- 仕様は不変（ordersキーの生成方法のみ変更）
- 既存のテストは全て通過することを前提

### 結合テスト（新規4本）

#### 1. businessDate境界テスト（ordersキー整合・bill基準）

**ファイル**: `__tests__/itemOrder/placeOrder.businessDate.spec.ts`

**目的**: `orders/{YYYYMMDD}` のキーが **常に `bill.businessDate` に一致**すること（SSoT原則、境界時刻でも整合）

**方針**: 
- **now基準との一致 → bill基準との一致** にアサーションを変更
- `createBillWithActiveStay` を使って任意の `bill.businessDate` を作成（環境の時刻に依存しない）

**ケース**:
- ケースA: 02:50 JST入店（`bill.businessDate=前日`）→ 03:10注文 → `orders`キーは前日（`bill.businessDate` と一致）
- ケースB: 03:10 JST入店（`bill.businessDate=当日`）→ 03:10注文 → `orders`キーは当日（`bill.businessDate` と一致）
- STORE_CLOSE_HOUR=27（3:00 JST）:
  - 前日22:00入店（`bill.businessDate=前日`）→ 当日02:50注文 → `orders`キーは前日
  - 当日03:10入店（`bill.businessDate=当日`）→ 当日03:10注文 → `orders`キーは当日
- STORE_CLOSE_HOUR=9（9:00 JST）:
  - 前日20:00入店（`bill.businessDate=前日`）→ 当日08:50注文 → `orders`キーは前日
  - 当日09:10入店（`bill.businessDate=当日`）→ 当日09:10注文 → `orders`キーは当日

**アサーション**:
- `orders/{YYYYMMDD}` の `YYYYMMDD` が `bill.businessDate` から生成される（`biz.replace(/-/g, "")`）こと
- `orders/{YYYYMMDD}.date`（`YYYY-MM-DD`）が `bills/{billId}.businessDate` と完全一致すること
- `orders/{YYYYMMDD}/_TodaysOrders/{itemId}` が仕様通り作成されること

**STORE_CLOSE_HOUR汚染防止**:
```typescript
let prevStoreCloseHour: string | undefined;
beforeEach(() => {
  prevStoreCloseHour = process.env.STORE_CLOSE_HOUR;
});
afterEach(() => {
  process.env.STORE_CLOSE_HOUR = prevStoreCloseHour;
});
```

#### 2. DualWrite失敗耐性（bills成功維持）

**ファイル**: `__tests__/helpers/billsApi/appendItem.dualwrite-failure.spec.ts`

**目的**: `todaysBills` への複写が意図的に失敗しても、`bills/items` は成功・`orders` も期待通りであること

**方法**: 
- `todaysBills` のセキュリティルールを「更新禁止」に切替えるモック（テスト環境のルール差し替え）
- もしくは `legacyRef` に対して `permission-denied` を発生させるよう事前条件を作る

**アサーション**:
- callable結果は `success`
- `bills/{billId}/items/{itemId}` は存在
- `orders/{YYYYMMDD}/_TodaysOrders/{itemId}` は仕様通り作成
- ログ出力に `dualWriteResult: 'failed'` が含まれる（loggerモックで検証 or 文字列含有で代替）

**追加検証（Nice-to-have）**:
- `WRITE_TODAYS_BILLS_IN_PARALLEL=false` で `appendItem` 実行
- loggerモックで `dualWriteResult: 'skipped'` を一度は出力していることを確認

**STORE_CLOSE_HOUR汚染防止**:
```typescript
let prevStoreCloseHour: string | undefined;
beforeEach(() => {
  prevStoreCloseHour = process.env.STORE_CLOSE_HOUR;
});
afterEach(() => {
  process.env.STORE_CLOSE_HOUR = prevStoreCloseHour;
});
```

#### 3. 並行競合テスト（allowed同士／途中でsettling）

**ファイル**: `__tests__/helpers/billsApi/appendItem.concurrent.spec.ts`

**目的**: 
- `status=open` で異なる `idempotencyKey` なら並行 `appendItem` が両方成功
- `appendItem` 中に別Txで `status='settling'` に遷移した場合、遅い方は `failed-precondition`

**ケース**:
1. `open` 状態で `appendItem ×2` を `Promise.all`（異なる `clientNonce`）→ `items` 2件作成
2. `open` で片方を遅延→もう片方のTx中に別Txで `status='settling'` へ更新→遅延側が `failed-precondition`

**実装ヒント**: 
- `setTimeout` や人工遅延用のヘルパを使ってTxの衝突を再現
- `bills/{billId}.status` を Tx外で更新して競合を引き起こす

#### 4. appendの"内容不一致"リプレイ（idempotency requestHash mismatch）

**ファイル**: `__tests__/helpers/billsApi/appendItem.mismatch.spec.ts`

**目的**: 同一 `idempotencyKey` で `quantity` などpayloadを変えた再送は `failed-precondition`

**ケース**:
- 1回目: `{ menuItemId: 'A', quantity: 1 }` で `appendItem`
- 2回目: 同一 `idempotencyKey` で `{ menuItemId: 'A', quantity: 2 }` → `failed-precondition`

**アサーション**:
- 2回目は `HttpsError('failed-precondition')` をthrow
- **必須**: 親 `bills/{billId}.updatedAt` が1回目から変わらない（副作用なし）ことを必ず検証
  - 1回目の `updatedAt` を保存
  - 2回目実行後、`bills/{billId}` を再取得して `updatedAt` が同一であることをassert

**STORE_CLOSE_HOUR汚染防止**:
```typescript
let prevStoreCloseHour: string | undefined;
beforeEach(() => {
  prevStoreCloseHour = process.env.STORE_CLOSE_HOUR;
});
afterEach(() => {
  process.env.STORE_CLOSE_HOUR = prevStoreCloseHour;
});
```
