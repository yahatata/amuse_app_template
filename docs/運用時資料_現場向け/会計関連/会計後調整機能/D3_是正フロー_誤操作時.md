# 会計後調整機能 是正フロー（誤操作時）

## この資料の使い方

この資料は、会計後調整を誤って実行したときに、現場で自己解決できるか、管理者・エンジニア対応が必要かを判断するための手順書です。

## 1. まず最初に判断すること

1. 誤ったのが `その場で完了した操作` か `あとで対応する操作` かを確認します。
2. 誤った対象が `金額だけの問題` か `伝票全体を戻したい問題` かを確認します。
3. reopen が使える当日営業日内かどうかを確認します。
4. 同じお客様・同じ伝票の中で補正できるかを確認します。
5. 迷う場合は、無理に続行せず管理者へ引き継ぎます。

## 2. UI だけで自己解決できるかの判断基準

| 状況 | UI だけで自己解決できるか | 基本対応 |
|---|---|---|
| 金額の増減だけを打ち消せばよい | できることが多い | 反対方向の会計後操作を追加する |
| その場で返金・徴収まで済ませてしまったが、同じ伝票内で相殺できる | できることが多い | 逆方向の即時操作、または返金待ち / 追加徴収待ちで補正する |
| 伝票全体を会計前に戻したい、かつ当日営業日内 | できる | `会計前に戻す` を使う |
| 当日営業日をまたいでいて reopen したい | 原則できない | 管理者・エンジニアへ相談 |
| 別のお客様の伝票に対して誤操作した | 原則できない | 管理者・エンジニアへ相談 |
| エラー表示が出て処理状態が分からない | できないことが多い | 画面を閉じずに管理者・エンジニアへ相談 |

## 3. 誤った即時返金をしてしまった場合

### 3-1. すぐに自己解決できるケース

1. 返しすぎた金額が明確で、同じ伝票の中で元に戻せる場合は、`会計後操作` を開きます。
2. 対象伝票で `この伝票を操作` を押します。
3. `増額（即時徴収）` または `増額（追加徴収待ち）` を選びます。
4. 返しすぎた分と同じ金額を登録します。
5. その場で受け取れるなら `増額（即時徴収）`、後日受け取るなら `増額（追加徴収待ち）` を使います。
6. `メモ` に「即時返金の打ち消し」など、理由が分かる文言を残します。

### 3-2. 伝票全体を戻したいケース

1. 誤返金だけでなく、会計方法や明細全体をやり直したい場合は `会計管理` を開きます。
2. `会計完了` タブから対象伝票を開きます。
3. 当日営業日内であれば `会計前に戻す` を使います。
4. reopen 完了後、未会計一覧で内容を見直して再会計します。

### 3-3. エンジニア対応が必要なケース

- すでに当日営業日をまたいでいる
- 別の伝票・別のユーザーへ返金した
- 返金方法や残高表示がおかしい
- エラー後に一覧から消えた、または重複して見える

## 4. 誤った即時追加徴収をしてしまった場合

### 4-1. すぐに自己解決できるケース

1. 取りすぎた金額が明確なら、同じ伝票で `会計後操作` を開きます。
2. `減額（即時返金）` または `減額（返金待ち）` を選びます。
3. 取りすぎた金額と同じ内容を登録します。
4. その場で返せるなら `減額（即時返金）`、後日返すなら `減額（返金待ち）` を使います。
5. `メモ` に「即時徴収の打ち消し」など、理由を残します。

### 4-2. 伝票全体を戻したいケース

1. 会計全体をやり直したい場合は、当日営業日内なら `会計前に戻す` を使います。
2. reopen 後、未会計一覧から開いて会計し直します。

### 4-3. エンジニア対応が必要なケース

- 当日営業日をまたいだ
- 別のお客様へ誤って徴収した
- 特殊な支払い方法（チップ、ポイント）で残高がおかしい
- 返金しようとしても上限や対象が合わず進められない

## 5. 誤った後続追加徴収（記録後）をしてしまった場合

ここでいう「記録後」は、`追加徴収` ダイアログで `徴収する` を押し、`追加徴収を記録しました（cashActionId: ...）` が表示された状態です。

### 5-1. 自己解決できるケース

1. 追加徴収を取り消したい場合は、同じ伝票で `会計後操作` を開きます。
2. `減額（即時返金）` または `減額（返金待ち）` を使って、同額の補正を入れます。
3. その場で返せるなら `減額（即時返金）`、後日返すなら `減額（返金待ち）` を使います。
4. `メモ` に「誤った後続徴収の補正」など、原因が分かる記録を残します。

### 5-2. reopen を使うかどうか

1. 差額だけでなく、伝票全体を会計前へ戻したい場合は reopen を検討します。
2. ただし reopen は当日営業日内だけに使ってください。
3. すでに日をまたいでいる場合は UI だけで戻せない前提で管理者へ引き継ぎます。

### 5-3. エンジニア対応が必要なケース

- 徴収した相手や伝票が違う
- 同じ伝票内で反対仕訳を入れても意味が通らない
- 一覧上は完了しているのに内容が合わない
- エラー後に `追加徴収待ち` が消えない / 消えすぎた

## 6. 誤った reopen をしてしまった場合

### 6-1. reopen 後、まだ再会計していない場合

1. その伝票は未会計一覧へ戻っています。
2. 内容が元の会計と同じでよいなら、そのまま通常どおり会計を完了してください。
3. 内容を修正したい場合は、未会計状態のまま必要な修正を入れてから会計します。
4. reopen 自体を取り消す専用ボタンはありません。元に戻したい場合は再会計で復旧します。

### 6-2. reopen 後に中断してしまった場合

1. `会計管理` の `未会計` タブで対象伝票を探します。
2. 該当伝票を開いて、内容を確認します。
3. 不足がなければそのまま会計を完了します。
4. 何が元の状態だったか分からない場合は、無理に触らず管理者へ引き継ぎます。

### 6-3. エンジニア対応が必要なケース

- reopen 後に対象伝票が見つからない
- reopen 後に別のユーザーが入店中表示にならない
- 再会計しようとしても明細や支払い情報が不自然
- reopen 直後にエラーが続き、同じ操作が再現できない

## 7. 状態と現状回復できる操作の対応表

| 状態の見方 | 典型状態 | 現場でできること | Firestore 上の目安 |
|---|---|---|---|
| 追加徴収待ち / 要返金が未処理 | まだ後続対応が残っている | `要対応の会計` から `徴収する` / `返金する`、または当日なら reopen | `bills/{billId}/settlementCycles/{cycleNo}/adjustments/{adjustmentId}` の `adjustmentState = effective` |
| すでに徴収 / 返金まで記録済み | お金の受け渡しまで完了している | 反対方向の会計後操作で補正する。必要なら当日中に reopen | `adjustmentState = completed_by_cash_action`、`bills/{billId}/settlementCycles/{cycleNo}/cashActions/{cashActionId}` が存在 |
| 反対方向の差額で相殺済み | 追加操作同士で帳尻が合っている | 原則そのまま。必要なら管理者判断で再調整 | `adjustmentState = completed_by_offset` |
| reopen により未処理差額が取り消された | 会計前に戻してやり直し中 | 未会計一覧から再会計する | `adjustmentState = cancelled_by_reopen` |
| cashAction が残っている | 後続徴収または後続返金の記録がある | 削除はできない。必要なら反対操作で補正 | `bills/{billId}/settlementCycles/{cycleNo}/cashActions/{cashActionId}` |

## 8. 「UI から自己解決できる」か「エンジニア対応が必要」かの判定表

| ケース | UI から自己解決 | 判断理由 |
|---|---|---|
| 金額だけを逆方向に補正すれば済む | できる | 現行 UI は削除ではなく追加入力で履歴を残す方式のため |
| 当日中に伝票全体を会計前へ戻したい | できる | `会計前に戻す` が用意されているため |
| 過去営業日の会計を会計前へ戻したい | できない | reopen は当日営業日分のみ |
| 誤って別伝票・別ユーザーへ記録した | 原則できない | 伝票間の付け替え UI がないため |
| 一覧や残額が不自然で、何が反映されたか分からない | できないことが多い | 履歴確認やデータ調査が必要なため |
| 返金方法 / 徴収方法の上限表示と実態が合わない | できないことが多い | 元の支払い履歴や残高整合の確認が必要なため |

## 9. 引き継ぐときに残すべき情報

1. 対象ユーザー名
2. 対象伝票の billId
3. いつ、どのボタンを押したか
4. 画面に出た完了メッセージまたはエラーメッセージ
5. すでにお金の受け渡しが終わっているか
6. その場で補正を入れたかどうか

この6点があると、管理者・エンジニア側で復旧判断がしやすくなります。
